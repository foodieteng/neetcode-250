Hmm, let me think about this for a sec.

A naive approach would be to try every start index, then walk forward up to n steps with i % n, and keep a running sum. That's O(n²). It's correct, and I'd keep it as a brute force to test against. But at n = 3·104 it's too slow.

This problem reminds me of Kadane's algorithm — the running "extend or restart" scan that solves maximum subarray on a straight line, which fits here because the non-wrapping case is exactly that. Kadane already gives me the best normal subarray. For the wrap case, I flip the question. I don't search for the best wrap. I search for the worst normal block, the minimum subarray, and cut it out. Total minus the minimum block is the best wrap. And I can find the minimum block with the same Kadane, just with min instead of max. Both run in the same loop.

Here's the plan.

// curMx / curMi = best / worst sum ending at x
// subMx / subMi = best / worst block seen so far
total = 0, curMx = 0, curMi = 0
subMx = INT_MIN, subMi = INT_MAX
for each x:
  total += x
  curMx = max(curMx + x, x)  // extend vs restart
  curMi = min(curMi + x, x)  // same, for min
  subMx = max(subMx, curMx)
  subMi = min(subMi, curMi)
if subMx < 0: return subMx  // all negative
return max(total − subMi, subMx)  // wrap vs normal

Here, I'm using curMx and subMx to keep track of the best normal subarray, and curMi and subMi for the worst one. total is the sum of the whole circle.

One thing worth flagging — the guard subMx < 0. Let me walk through that. Take [-3,-2,-3]. The minimum block is the whole array, −8, which is also the total. So total − subMi is 0. But that 0 means "cut out everything", which is the empty subarray. That's not allowed. Without the guard I'd return 0, but the answer is −2. And subMx < 0 happens exactly when every number is negative. In that case no wrap can help, so I just return subMx.

One thing worth flagging too — the guard has to check subMx, not total. A natural wrong idea is "if total < 0, skip the wrap." Take [1,-3,1]. The total is −1, but the wrap [1,1] gives 2. That rule returns 1. So the question is not "is the total negative." It's "is every number negative."

There's a trade-off here. Another way is to double the array and run a sliding window with a monotonic deque on prefix sums. That also works in O(n), but it needs O(n) extra space and much more code. The min-block trick is O(1) space and one loop. So I'll go with that.

class Solution {
public:
    int maxSubarraySumCircular(vector<int>& nums) {
        int total = 0, curMx = 0, curMi = 0;
        int subMx = INT_MIN, subMi = INT_MAX;

        for (int &x : nums) {
            total += x;

            curMx = max(curMx + x, x);
            curMi = min(curMi + x, x);
            subMx = max(subMx, curMx);
            subMi = min(subMi, curMi);
        }

        if (subMx < 0) return subMx;
        return max(total - subMi, subMx);
    }
};

That matches the plan line by line.

One thing worth flagging — the start values. subMx starts at INT_MIN and subMi at INT_MAX, not 0. If subMx started at 0, then [-1] would return 0 instead of −1. Same thing if I swap the order and update sub* before cur*: the first compare would see cur = 0, the empty subarray. curMx = 0 at the start is fine, because on the first number extend and restart are both just x.

Also, the last line still needs the max with subMx. If I only returned total − subMi, then [1] would give 0, because the min block is the whole array again. The max rescues that.

Let me think about complexity here.

The time complexity is O(n). One pass, and two Kadanes share the same loop.

The space complexity is O(1). Just five integers.

In the worst-case scenario it's still exactly n steps. There's no early exit and no extra work. At n = 3·104 it takes about 40 µs per call. And the biggest value I ever hold is 900,000,000, so there's no overflow.

Oh, one more thing — I'd test this against the O(n²) brute force on lots of arrays. I ran 239,530 cases, small and large, with 0 mismatches. That check matters here. The total < 0 guard passes all three official examples, but it fails on [1,-3,1]. And forgetting the guard only breaks on all-negative arrays. Bugs like that hide from a few hand-picked tests, so a brute-force check is worth it.
