Hmm, let me think about this for a sec.

A naive approach would be to actually do the moves. Keep merging pairs, collect every triplet I can reach, and stop when nothing new shows up. Then check if the target is in the set. That works, but the set can blow up fast, and with 10^5 triplets even one round of all pairs is about 10^10 merges. Way too slow.

This problem reminds me of a greedy filter. Because max only goes up, there are just two kinds of triplets. Poison ones I must skip. And safe ones, where every number is <= the target. Merging a safe triplet can't hurt. It can only push me closer to the target, and it can never push me past it.

So the greedy is: merge all the safe triplets together. That gives the biggest triplet I can ever build that still stays under the target. If even that one isn't equal to the target, nothing smaller will be. So the answer is just: does it equal the target? I'll go with that.

Here's the plan.

// state: ans = position-wise max of all safe triplets
ans = [0, 0, 0]  // 0 = "nothing reached yet"
for each t in triplets:
  if t[0] <= x and t[1] <= y and t[2] <= z:  // safe
    ans[k] = max(ans[k], t[k])  for k = 0, 1, 2
  // else: poison, skip it forever
return ans == target
// invariant: ans <= target at every position, always

Here, I'm using ans to keep track of the best triplet I could build so far from safe triplets only.

One thing worth flagging — the start value of ans is a correctness detail, not a style choice. It must be a value no real number can take. Let me walk through that. Say I start at [1,1,1] instead. Take triplets [[1,1,2]] and target [1,1,1]. The only triplet has a 2, so it's poison and gets skipped. The right answer is false. But ans is still [1,1,1], which happens to equal the target, so I'd return true. Wrong. With 0, this can't happen. Every real value is at least 1, so a 0 left over can never look like "reached".

There's a trade-off here. Another way is three found flags. For each safe triplet, if t[k] == target[k], set found[k]. Return true if all three are set. It's the same idea. Safe means every t[k] <= target[k], so the max at spot k hits the target exactly when some safe triplet equals it there. The flags make "did I reach it?" very clear. The max version is closer to what the move really does. Both are one pass, so I'll go with the max version.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool mergeTriplets(vector<vector<int>>& triplets, vector<int>& target) {
        vector<int> ans(3, 0);

        for (auto &t : triplets) {
            if (t[0] <= target[0] && t[1] <= target[1] && t[2] <= target[2]) {
                ans[0] = max(ans[0], t[0]);
                ans[1] = max(ans[1], t[1]);
                ans[2] = max(ans[2], t[2]);
            }
        }

        return ans == target;
    }
};

That matches the plan. One thing worth flagging — I loop with auto &t, not auto t. Each triplet is a vector, so auto t would copy it every time. On 10^5 triplets, one call takes about 0.2 ms with the reference, and about 1.7 ms with the copy. That's around 7x slower for no reason.

Also, ans == target just compares two vector<int> of size 3, element by element. So the last line is the whole check.

Let me think about complexity here.

The time complexity is O(n). I look at each triplet once, and each look is a fixed amount of work: three compares and up to three max calls. The space complexity is O(1) extra. ans is always size 3, no matter how big the input is.

In the worst-case scenario I have 10^5 triplets and all of them are safe, so I do every max. That's still one pass, around 0.2 ms. The biggest value in ans is 1000, so plain int is more than enough. No overflow worries.

Oh, one more thing — the order of the triplets doesn't matter. max doesn't care about order, and the safe test only looks at one triplet at a time. So this also works on a stream. I never need to sort or go back.
