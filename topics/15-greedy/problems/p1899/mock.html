Hmm, let me think about this for a sec.

A naive approach would be to actually do the moves — keep merging pairs and collect every triplet I can reach. With 105 triplets, even one round of all pairs is about 1010 merges. Way too slow.

This problem reminds me of a greedy filter. Because max only goes up, there are just two kinds of triplets: poison ones I must skip, and safe ones, where every number is <= the target. A safe triplet can only push me closer, never past.

So the greedy is: merge all the safe triplets. That's the biggest triplet I can build that stays under the target. If even that isn't the target, nothing smaller will be.

Here's the plan, in three steps.

// state: ans = position-wise max of all safe triplets
ans = [0, 0, 0]  // 0 = "nothing reached yet"
for each t in triplets:
  if t[0] <= x and t[1] <= y and t[2] <= z:  // safe
    ans[k] = max(ans[k], t[k])  for k = 0, 1, 2
  // else: poison, skip it forever
return ans == target
// invariant: ans <= target at every position, always

One: start a running answer ans at [0,0,0]. Two: for each triplet, if all three numbers are <= the target, take the position-wise max into ans; otherwise skip it forever. Three: return ans == target.

One thing worth flagging — the start value is a correctness detail. Start at [1,1,1], and a lone poison triplet with target [1,1,1] gets skipped, yet ans already looks like the target, so I'd wrongly return true. 0 is never a real value, so it can't fake a match.

The trade-off: three found flags work too; both are one pass, and I'll keep max because it mirrors the move.

Does this approach sound good?

class Solution {
public:
    bool mergeTriplets(vector<vector<int>>& triplets, vector<int>& target) {
        vector<int> ans(3, 0);

        for (auto &t : triplets) {
            if (t[0] <= target[0] && t[1] <= target[1] && t[2] <= target[2]) {
                ans[0] = max(ans[0], t[0]);
                ans[1] = max(ans[1], t[1]);
                ans[2] = max(ans[2], t[2]);
            }
        }

        return ans == target;
    }
};

ans starts as [0,0,0]. For each triplet, one if checks all three positions against the target, joined with &&; if it passes, I take the max into each slot. At the end I return ans == target — vector equality compares element by element, so that last line is the whole check.

The one detail worth flagging: I take each triplet by reference, auto &t, not by copy. Each triplet is a vector, so copying it is wasted work. On 105 triplets, that's about 0.2 ms versus 1.7 ms — around 7x slower for no reason.

Corner cases:

• Every triplet poison — ans stays [0,0,0], false.
• All safe, each position from a different triplet — true.
• A lone poison triplet with target [1,1,1] — false, exactly what a [1,1,1] start gets wrong.
• Safe triplets that never reach the last position — false.

Let me think about complexity here.

Time is O(n): each triplet gets three compares and up to three max calls. Space is O(1) extra — ans is always size 3.

In the worst case all 105 triplets are safe, and it's still one pass, around 0.2 ms. The biggest value is 1000, so a plain int is plenty.
