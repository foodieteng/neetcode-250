Hmm, let me think about this for a second.

A naive approach tries every start index and grows the end with a running sum. That's O(n²) — correct, but about 3.7 s at 105 elements when I timed it. Too slow.

This problem reminds me of a one-pass DP, which is Kadane's algorithm. Look at the best subarray that ends right here. It has only two choices: extend the best one that ended one step before, or restart with just the current number. The answer is the best of these "ends here" values over all indexes.

P — plan
C
CANDIDATE

Here's the plan.

// curL = best sum of a subarray that ends at num
// maxL = best sum seen anywhere so far
maxL = INT_MIN, curL = 0
for each num:
  curL = max(curL + num, num)  // extend vs restart
  maxL = max(maxL, curL)
return maxL

One: keep curL, the best sum ending at the current number, and maxL, the best seen so far — maxL starts at INT_MIN, curL at 0.
Two: for each number, curL takes the larger of extend and restart.
Three: maxL takes the larger of itself and curL, and I return it.

One thing worth flagging — restart wins exactly when the past sum is negative, not when the current number is. Reset-on-negative fails on [2,-1,2]: it gives 2, the answer is 3. Also, maxL must start at INT_MIN, not 0 — otherwise [-4] returns 0, and that bug still passes all three official examples.

Divide and conquer is O(n log n) and more code; Kadane is O(n) time, O(1) space. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. Two ints — maxL at INT_MIN, curL at 0 — and one loop with two lines: curL becomes the max of extend and restart, then maxL becomes the max of itself and curL. Return maxL.

class Solution {
public:
    int maxSubArray(vector<int>& nums) {
        int maxL = INT_MIN, curL = 0;

        for (int& num : nums) {
            curL = max(curL + num, num);
            maxL = max(maxL, curL);
        }

        return maxL;
    }
};

That matches the plan line by line.

One thing worth flagging — the order of those two lines. Updating curL first means maxL only ever sees a subarray that includes the current number, which keeps the empty subarray out. Swap them, and the first compare sees curL = 0 — the empty subarray — so [-4] returns 0 again.

Let me think about complexity here.

Time is O(n) — one pass, two max calls per number. Space is O(1) — two integers. There's no early exit, so it's always exactly n steps. At 105 elements it ran in about 0.25 ms, versus nearly 4 s for the O(n²) brute force.

Good. The follow-up asks for divide and conquer. How would that go?

C
CANDIDATE

I split the array in the middle. The best subarray is all in the left half, all in the right half, or crossing the middle. Left and right are recursive calls. For the crossing case, I take the best sum ending at the middle going left, plus the best sum starting right after it going right — one linear scan.

Two half-size subproblems plus linear work gives O(n log n) time, plus an O(log n) recursion stack. When I timed it at 105 elements, it took about 1.6 ms, versus about 0.25 ms for Kadane. So I'd ship Kadane, and keep divide and conquer as the follow-up answer.
