Hmm, let me think about this for a sec.

A naive approach would be to keep a dp array, and for each i, scan the whole range [i - maxJump, i - minJump] to look for one true cell. That's correct, but it costs O(n · (maxJump − minJump)). With all zeros, n = 1e5, minJump = 1, maxJump = 99999, the naive scan took about 1,792.3 ms when I measured it. That's way too slow.

This problem reminds me of a sliding window. Here's why. When i moves right by one, the range [i - maxJump, i - minJump] also moves right by one. Exactly one cell comes in on the right, dp[i - minJump]. Exactly one cell drops off on the left, dp[i - maxJump - 1]. So I don't need to rescan. I just update a running number.

I'll go with the sliding-window DP. It's one pass, and the window update is O(1) per step.

C
CANDIDATE

Here's the plan.

// state
dp[i] = can I stand on index i?  dp[0] = true
cnt   = # of true dp in [i - maxJump, i - minJump]

// for i = minJump .. n-1
if dp[i - minJump]                      : cnt++  // enters
if i-maxJump-1 >= 0 and dp[i-maxJump-1] : cnt--  // leaves
dp[i] = cnt > 0 and s[i] == '0'

// answer
return dp[n - 1]

Here, I'm using cnt to keep track of how many reachable cells are inside the window right now. The invariant is simple: after the two updates, cnt is exactly the number of true dp values in [i - maxJump, i - minJump]. If it's above zero, someone can jump into i.

One thing worth flagging — it has to be a count, not a yes/no flag. Let me walk through that. The window can hold more than one reachable cell. When one of them leaves, a flag would flip to false, even if another reachable cell is still inside. A count just goes down by one and stays correct. The tricky part is that a flag version passes both examples. It still fails on ("000", 1, 1): it says false, but the right answer is true.

There's a trade-off here. I could also do BFS with a "farthest" pointer, so each index gets visited once. It's also linear. I like the DP because the window count is easy to prove and easy to dry-run. The cost is an O(n) dp array.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool canReach(string s, int minJump, int maxJump) {
        int n = s.size();
        vector<int> dp(n, false);
        dp[0] = true;
        int cnt = 0;

        for (int i = minJump; i < n; i++) {
            if (dp[i - minJump]) ++cnt;

            if (i - maxJump - 1 >= 0 && dp[i - maxJump - 1]) --cnt;

            dp[i] = (cnt > 0 && s[i] == '0');
        }
        return dp[n - 1];
    }
};

That matches the plan. The loop starts at minJump, because no index before that can be reached from 0. Those cells just stay false.

One thing worth flagging — the remove guard is >= 0, not > 0. With > 0, the start cell dp[0] never leaves the window, so it keeps "helping" cells it can't really reach. On ("010", 1, 1) that bug returns true, but the answer is false. So this guard is a correctness rule, not a small detail.

Same idea for the s[i] == '0' check. If I drop it, a wall can be marked reachable. ("01", 1, 1) would come back true, and it should be false.

Example 2, "01101110" with (2, 3), returns false. Index 3 is the only reachable cell after the start. While it's inside the window, at i = 5 and i = 6, those cells are walls. At i = 7, dp[3] leaves, so cnt is 0 and the last index stays false.

Let me think about complexity here.

The time complexity is O(n). Each index does one add check and one remove check, both O(1).

The space complexity is O(n) for the dp array.

In the worst-case scenario for the naive scan, all zeros with (1, 99999) and n = 1e5, the window holds up to 99,999 reachable cells. The naive version took 1,792.3 ms. This version took 104.9 µs, because the window size never shows up in the cost.

Oh, one more thing — I return dp[n - 1], not cnt > 0. cnt only says someone can jump into the last index. It ignores whether the last cell is a wall. ("01", 1, 1) shows it: cnt > 0 gives true, the answer is false. And that bug also passes both examples, so it's easy to miss.

Two ways. First, BFS with a farthest pointer. I pop a reachable index i and look at [i + minJump, i + maxJump]. But I keep a pointer to the farthest index I already checked, and I start from there. So every index is looked at once. On the same worst case it ran in 117.7 µs, about the same as the DP.

Second, a prefix-sum version. I keep pre[k] = number of true dp in the first k cells. Then "any reachable cell in the window" is just one subtraction of two prefix values. It's the same idea as cnt, written as a range sum.

Also, vector<bool> works and is much smaller, 12,504 B versus 400,000 B for vector<int>. But it was about 3× slower in my run, 307.9 µs. So I kept vector<int>.
