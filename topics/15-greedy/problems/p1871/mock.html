Hmm, let me think about this for a second.

A naive approach would be a dp array where each index scans its whole range for one true cell. That's correct, but it costs n × the window width — with all zeros and maxJump = 99999, it took about 1.8 s when I measured it. Way too slow.

This problem reminds me of a sliding window. When i moves right by one, the range moves right by one: exactly one cell enters on the right, at i - minJump, and one drops off on the left, at i - maxJump - 1. So I don't rescan — I just update a running number. I'll go with the sliding-window DP: one pass, O(1) work per step.

P — plan
C
CANDIDATE

Here's the plan. dp[i] means I can stand on index i, and dp[0] is true. cnt is how many true dp values sit in the window. First, for each i from minJump, count the cell entering at i - minJump. Second, uncount the cell leaving at i - maxJump - 1, if it exists. Third, dp[i] is true when cnt > 0 and s[i] == '0'.

// state
dp[i] = can I stand on index i?  dp[0] = true
cnt   = # of true dp in [i - maxJump, i - minJump]

// for i = minJump .. n-1
if dp[i - minJump]                      : cnt++  // enters
if i-maxJump-1 >= 0 and dp[i-maxJump-1] : cnt--  // leaves
dp[i] = cnt > 0 and s[i] == '0'

// answer
return dp[n - 1]

One thing worth flagging — it has to be a count, not a flag. When one reachable cell leaves, a flag goes false even if another is still inside. A flag passes both examples but fails ("000", 1, 1).

A farthest-pointer BFS is also O(n), but the count is easier to prove.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool canReach(string s, int minJump, int maxJump) {
        int n = s.size();
        vector<int> dp(n, false);
        dp[0] = true;
        int cnt = 0;

        for (int i = minJump; i < n; i++) {
            if (dp[i - minJump]) ++cnt;

            if (i - maxJump - 1 >= 0 && dp[i - maxJump - 1]) --cnt;

            dp[i] = (cnt > 0 && s[i] == '0');
        }
        return dp[n - 1];
    }
};

One loop from minJump to n − 1, doing exactly the three plan steps: count the entering cell, uncount the leaving cell, then set dp[i] from the count and the character. Cells before minJump just stay false.

One thing worth flagging — the remove guard checks >= 0, not > 0. With > 0, the start cell never leaves the window, so it keeps "helping" cells it can't really reach: ("010", 1, 1) returns true, but the answer is false. The s[i] == '0' check matters the same way — without it, "01" would mark a wall as reachable.

Let me think about complexity here.

The time complexity is O(n) — each index does one add check and one remove check. The space complexity is O(n), for the dp array.

On the naive scan's worst case the window holds almost 100,000 cells, yet this version took about 105 µs instead of 1.8 s, because the window size never shows up in the cost.

Oh, one more thing — I return dp[n - 1], not cnt > 0. The counter ignores whether the last cell is a wall, so ("01", 1, 1) would wrongly give true. That bug also passes both examples, so it's easy to miss.

Two ways. First, BFS with a farthest pointer: from each reachable index I scan its jump range, but start from the farthest index already checked, so every index is looked at once. On the same worst case it ran in about 118 µs, about the same as the DP.

Second, prefix sums: keep a running count of true dp values, and the window check becomes one subtraction. It's the same counter, written as a range sum.

Also, vector<bool> is much smaller — about 12,500 B versus 400,000 B — but it was about 3× slower in my run, so I kept vector<int>.
