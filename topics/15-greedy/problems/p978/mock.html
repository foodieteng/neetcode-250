Hmm, let me think about this for a sec.

A naive approach would be to try every start and every end, and check if the part in between is turbulent. That's O(n³), or O(n²) if I grow each start until it breaks. It's correct, and I'd keep it as a brute force to test against. But at n = 4·104 it's too slow.

This problem reminds me of the two-running-Kadanes pattern: a running best ending at each index, kept as two coupled values — like a running max and a running min, because one state swaps into the other. Here it's the same shape. I keep two runs ending at index i: one whose last step goes up, and one whose last step goes down. An up step can only extend a run that ended going down, and the other way around. So the two values feed each other.

Here's the plan.

// curMx = longest run ending at i, last step UP
// curMi = longest run ending at i, last step DOWN
maxL = 1, curMx = 1, curMi = 1
for i = 1 .. n-1:
  prevMx, prevMi = curMx, curMi  // copy first
  curMx = a[i] > a[i-1] ? prevMi + 1 : 1  // up after down
  curMi = a[i] < a[i-1] ? prevMx + 1 : 1  // down after up
  maxL = max(maxL, curMx, curMi)
return maxL   // equal step → both reset to 1

Here, I'm using curMx and curMi to keep track of the two best runs that end right at index i. maxL is the best length seen anywhere.

The key rule is the cross. If this step goes up, the run before it must have ended going down. So curMx = prevMi + 1. If this step goes down, curMi = prevMx + 1. And whichever direction this step is not, that value resets to 1, because a run whose last step goes the other way can only be a[i] alone. If the step is equal, both reset to 1.

One thing worth flagging — the start value is 1, not 0, for all three. Let me walk through that. One element alone is a valid run. If I started maxL at 0, then [100] never enters the loop and returns 0. And if the reset value were 0 instead of 1, every run would come out one too short. Example 1 would give 4.

There's a trade-off here. I could also use one counter: if the sign of the step flips, add one; if it's equal, go to 1; otherwise go to 2. That also works. But then I need to compare the current step with the previous step, and the easy way to write that is multiplying two differences, which can overflow. I'll come back to that. The two-counter version only uses > and <, and it reads like the definition. So I'll go with that.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int maxTurbulenceSize(vector<int>& arr) {
        int n = arr.size();
        int maxL = 1, curMx = 1, curMi = 1;

        for (int i = 1; i < n; i++) {
            int prevMx = curMx, prevMi = curMi;
            curMx = (arr[i] > arr[i - 1]) ? prevMi + 1 : 1;
            curMi = (arr[i] < arr[i - 1]) ? prevMx + 1 : 1;
            maxL = max(max(curMx, curMi), maxL);
        }

        return maxL;
    }
};

That matches the plan line by line.

One thing worth flagging — the two copies, prevMx and prevMi. They look extra, but they're needed for correctness. Here's a version I almost wrote:

curMx = (arr[i] > arr[i - 1]) ? curMi + 1 : 1;
curMi = (arr[i] < arr[i - 1]) ? curMx + 1 : 1;  // curMx is already new

The problem is the second line. It reads curMx after the first line overwrote it. And on a down step, the first line always sets curMx to 1, because the step isn't up. So the second line always gives curMi = 1 + 1 = 2. Every down step cuts the chain back to 2. On example 1, it returns 3 instead of 5. The first wrong step is i = 4: curMi should be 3 + 1 = 4, but it becomes 2. The smallest input that breaks it is [0,1,0]: it returns 2, but the answer is 3. And it's sneaky: [4,8,12,16] and [100] still pass. That version can never return more than 3. Copying both old values first, before I write either one, fixes it.

Also, I only compare with > and <. I don't write (a[i]-a[i-1]) * (a[i-1]-a[i-2]) < 0 in int. Each difference fits, but the product doesn't. On [0,1e9,0] it's 109 × (−109), which overflows. That's undefined behavior, and in my test it printed garbage, 1486618624. A long long cast fixes it, but not needing it is cleaner.

Let me think about complexity here.

The time complexity is O(n). One pass, and each step is two compares and a max.

The space complexity is O(1). Just a few integers.

In the worst-case scenario it's still exactly n − 1 steps, with no early exit. At n = 4·104, the alternating array takes about 28 µs. The counters never go above n, and I never do math on the values, only compares. So there's no overflow anywhere.

Oh, one more thing — I'd test this against the brute force on lots of arrays. I ran 223,279 cases, every small array plus random large ones, with 0 mismatches. That check matters here. The almost-written version passes two of the three official examples. But on every array of length 1 to 7 with values 0 to 2, it fails 1,923 out of 3,279. And any answer of 4 or more is always wrong. A few hand-picked tests can miss that. A brute-force check won't.
