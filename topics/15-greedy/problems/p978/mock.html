Hmm, let me think about this for a second.

A naive approach tries every start and grows each one until it breaks. That's O(n²) — correct, and I'd keep it as a brute force to test against, but too slow at 4·104 elements.

This problem reminds me of the two-running-Kadanes pattern: a running best ending at each index, kept as two coupled values that swap into each other. Here I keep two runs ending at index i — one whose last step goes up, one whose last step goes down. An up step can only extend a run that ended going down, and the other way around, so the two values feed each other.

CANDIDATE

Here's the plan.

// curMx = longest run ending at i, last step UP
// curMi = longest run ending at i, last step DOWN
maxL = 1, curMx = 1, curMi = 1
for i = 1 .. n-1:
  prevMx, prevMi = curMx, curMi  // copy first
  curMx = a[i] > a[i-1] ? prevMi + 1 : 1  // up after down
  curMi = a[i] < a[i-1] ? prevMx + 1 : 1  // down after up
  maxL = max(maxL, curMx, curMi)
return maxL   // equal step → both reset to 1

One: keep three numbers, all starting at 1 — the best length maxL, the up run curMx, and the down run curMi ending here.
Two: for each index from 1, copy both runs first; an up step makes curMx = prevMi + 1, a down step makes curMi = prevMx + 1, and whichever direction this step is not resets to 1. Equal steps reset both, for free.
Three: refresh maxL with both.

One thing worth flagging — the start value is 1, not 0. Starting maxL at 0 returns 0 for a single element, and resetting to 0 makes every run one short — example 1 would give 4.

A one-counter version works too, but comparing steps the easy way multiplies two differences, which can overflow. Two counters only compare. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. maxL, curMx, and curMi all start at 1, and one loop from index 1: save both runs as prevMx and prevMi, then set each with a ternary — > gives prevMi + 1, < gives prevMx + 1, otherwise 1 — and take the max.

class Solution {
public:
    int maxTurbulenceSize(vector<int>& arr) {
        int n = arr.size();
        int maxL = 1, curMx = 1, curMi = 1;

        for (int i = 1; i < n; i++) {
            int prevMx = curMx, prevMi = curMi;
            curMx = (arr[i] > arr[i - 1]) ? prevMi + 1 : 1;
            curMi = (arr[i] < arr[i - 1]) ? prevMx + 1 : 1;
            maxL = max(max(curMx, curMi), maxL);
        }

        return maxL;
    }
};

One thing worth flagging — those copies are for correctness.

curMx = (arr[i] > arr[i - 1]) ? curMi + 1 : 1;
curMi = (arr[i] < arr[i - 1]) ? curMx + 1 : 1;  // curMx is already new

If the second line reads curMx directly, it sees the value the first line just overwrote, which is 1 on every down step. So every down step cuts to 2: example 1 returns 3, and [0,1,0] returns 2 instead of 3.

Also, I never multiply neighboring differences — on [0,1e9,0], that product overflows an int.

Let me think about complexity here.

Time is O(n) — one pass, two compares and a max per step. Space is O(1) — a few integers. No early exit, so it's always n − 1 steps, about 28 µs at 4·104 elements. I only compare values, never do math on them, so there's no overflow.
