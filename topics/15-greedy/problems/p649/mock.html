A naive approach would be to treat it as a real game and recurse over every possible ban, like minimax. That's exponential — fine for 10 senators, hopeless for 10,000. A majority vote is wrong too: "DDRRR" has 3 R's and only 2 D's, but Dire wins, because both D's act first.

This problem reminds me of a greedy with a simulation, a bit like round-robin scheduling with queues. The key question is who to ban. My answer: ban the next opponent who will act. All enemies are the same except for when they act, and the next one is about to ban one of my people. Banning a later one leaves that threat alive, so it's never better. That's an exchange argument.

Here's the plan. Two queues, qr and qd, hold the indices of live senators in acting order. First, push every index into its party's queue. Second, while both are non-empty, pop both fronts: the smaller index acts first, bans the other front, and goes back into his queue at index + n. Third, when a queue runs dry, the other party wins.

// qr, qd: indices of live R / D senators, in acting order
// invariant: smaller index acts sooner
push each index i into qr or qd
while both queues are non-empty:
  r = pop front of qr, d = pop front of qd
  if r < d:  R acts first, bans d  → push r + n to qr
  else:      D acts first, bans r  → push d + n to qd
return the party whose queue is non-empty

The fronts are the next R and the next D, so that's exactly "ban the next opponent".

One thing worth flagging — the winner goes back at index + n, not plain index. + n means the same seat in the next round, so everyone still waiting this round keeps a smaller number and acts first.

A counter simulation also works, but it rescans the whole string each pass.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    string predictPartyVictory(string senate) {
        int n = senate.size();
        queue<int> qr, qd;

        for (int i = 0; i < n; i++) {
            if (senate[i] == 'R') {
                qr.push(i);
            } else {
                qd.push(i);
            }
        }

        while (!qr.empty() && !qd.empty()) {
            int r = qr.front(); qr.pop();
            int d = qd.front(); qd.pop();

            if (r < d) {
                qr.push(r + n);
            } else {
                qd.push(d + n);
            }
        }

        return !qr.empty() ? "Radiant" : "Dire";
    }
};

One loop fills qr and qd by character. The main loop runs while neither is empty: pop r and d, then push r + n back into qr if r < d, otherwise d + n into qd. That matches the plan line by line.

One thing worth flagging — the loser is simply not pushed back; that is the ban. But the winner must be pushed back, with + n. On all 32,766 strings up to length 14, dropping the + n gets 9,794 wrong. And banning the back of the queue instead of the front loses games too — that's the greedy choice, tested in code.

Let me think about complexity here. The loop looks like it could run many rounds, but each pass pops two and pushes one, so the total queue size drops by exactly one — at most n − 1 passes.

The time complexity is O(n), and the space complexity is O(n) for the two queues.

In the worst-case scenario the game lasts many rounds, but that doesn't matter: only the number of bans does.

Oh, one more thing — I don't need a separate announce-victory step. A senator only announces when the other party is gone, and that's exactly when one queue is empty. So the loop condition already is the victory check.
