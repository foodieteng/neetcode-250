Hmm, let me think about this for a sec.

A naive approach would be to treat it as a real game. On each turn, try every possible ban and recurse, like minimax. That's exponential. Fine for 10 senators, hopeless for 104.

The other naive idea is a majority vote: more R's means Radiant wins. That's wrong. "DDRRR" has 3 R's and only 2 D's, but Dire wins, because both D's act first.

This problem reminds me of a greedy with a simulation, a bit like round-robin scheduling with queues. The key question is: when I get to ban, who should I ban?

My answer: ban the next opponent who will act, going around the circle. All enemies are the same, except for when they act. The one coming up next is the most dangerous, because he is about to ban one of my people. If I ban a later one instead, the next one still gets his turn. So banning a later one is never better. That's an exchange argument.

Here's the plan.

// qr, qd: indices of live R / D senators, in acting order
// invariant: smaller index acts sooner
push each index i into qr or qd
while both queues are non-empty:
  r = pop front of qr, d = pop front of qd
  if r < d:  R acts first, bans d  → push r + n to qr
  else:      D acts first, bans r  → push d + n to qd
return the party whose queue is non-empty

Here, I'm using two queues of indices to keep track of who acts next in each party. The two fronts are the next R and the next D. The smaller index acts first, and he bans the other front. That's exactly "ban the next opponent".

One thing worth flagging — the winner goes back in at index + n, not at index. Let me walk through that. index + n means "the same seat, but in the next round". So anyone still waiting in this round has a smaller number and acts first. That keeps the round order right. If I push back the plain index, the winner looks like he acts again right away, before people who are still waiting this round.

There's a trade-off here. I could also do a counter simulation: walk the string again and again, keep "bans owed" to each party, and skip banned seats. That works too, but each pass rescans the whole string. The queue version only touches live senators, and it's shorter to write.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    string predictPartyVictory(string senate) {
        int n = senate.size();
        queue<int> qr, qd;

        for (int i = 0; i < n; i++) {
            if (senate[i] == 'R') {
                qr.push(i);
            } else {
                qd.push(i);
            }
        }

        while (!qr.empty() && !qd.empty()) {
            int r = qr.front(); qr.pop();
            int d = qd.front(); qd.pop();

            if (r < d) {
                qr.push(r + n);
            } else {
                qd.push(d + n);
            }
        }

        return !qr.empty() ? "Radiant" : "Dire";
    }
};

That matches the plan line by line.

One thing worth flagging — the loser is simply not pushed back. That is the ban. And the winner must be pushed back, or he disappears too. I checked these small details against all 32,766 strings of length 1 to 14:

• Push back without + n: 9,794 wrong. Smallest is "DRR": it returns Dire, but the answer is Radiant.
• Forget to push the winner back: 4,577 wrong. Even "RD" breaks and returns Dire.
• Ban the opponent at the back of his queue instead of the front: 1,990 wrong. Smallest is "DRDRR": it returns Radiant, but the answer is Dire.
• r <= d instead of r < d: 0 wrong. Indices are unique, so r == d never happens.

That third one is the greedy choice, tested in code. Banning a later enemy really does lose games.

Let me think about complexity here. The while loop looks like it could run many rounds. But each pass pops two and pushes one. So the total size of both queues drops by exactly one each time. It starts at n and the loop stops before it hits zero, so there are at most n − 1 passes.

The time complexity is O(n): O(n) to fill the queues, plus at most n − 1 loop passes with O(1) work each. The space complexity is O(n) for the two queues.

In the worst-case scenario, the game can go on for many rounds. It's still at most n − 1 passes, because every pass is one ban. The number of rounds does not matter, only the number of bans.

Oh, one more thing — I don't need a separate "announce victory" step. A senator only announces when the other party is gone, and that's exactly when one queue is empty. So the loop condition already is the victory check.
