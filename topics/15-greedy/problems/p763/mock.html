Hmm, let me think about this for a second.

A naive approach would try every set of cut points — 2n−1 choices. Fine for 10 letters, hopeless for 500. Rescanning each growing part is O(n²); it works, but we can do better.

This problem reminds me of merging intervals. Each letter covers an interval, from its first copy to its last, and overlapping intervals must land in the same part. But a greedy scan with the last positions does the same job.

I keep r, the furthest last position of any letter in this part — the earliest place it may end. When i reaches r, I cut. Cutting earlier splits a letter; cutting later only gives fewer parts. So cutting as soon as possible gives the most parts.

Here's the plan, in three steps.

// pass 1: last[c] = last index of letter c
// pass 2: l = start of the current part
//         r = furthest last[] seen in this part
// invariant: the part can't end before r
for i in 0..n-1:
  r = max(r, last[s[i]])   // update first
  if i == r:                  // then check
    add r - l + 1, then l = r + 1

First pass: record the last index of each letter in a 26-slot array last. Second pass: walk left to right, pushing r out to the furthest last index in the current part. Third: when i == r, record the size and start the next part right after r.

One thing worth flagging — it must be max, not a plain overwrite. Take "aba". After the first 'a', r = 2. The 'b''s last index is 1; overwrite, and r drops to 1, cutting "ab" off with an 'a' still ahead. With max, r stays 2 and I get one part, [3]. The end only grows.

The trade-off: I could build and merge real intervals, but two passes with a small array is simpler and O(n).

Does this approach sound good, or would you rather I think of another way?

Alright. Two loops.

class Solution {
public:
    vector<int> partitionLabels(string s) {
        int n = s.size();
        vector<int> last(26, 0);

        for (int i = 0; i < n; i++) {
            last[s[i] - 'a'] = i;
        }

        vector<int> ans;
        int l = 0, r = 0;

        for (int i = 0; i < n; i++) {
            r = max(r, last[s[i] - 'a']);
            if (i == r) {
                ans.push_back(r - l + 1);
                l = r + 1;
            }
        }

        return ans;
    }
};

The first just overwrites last for each letter, so the last write wins — the last index for free. The second pushes r out with max, and when i == r it records r - l + 1 and moves l past r.

One thing worth flagging — the order of those two lines matters: update r first, then check. I tested small changes against about 1.4 million short strings:

• Checking before updating breaks on "aa": [1,1] instead of [2].
• Overwriting instead of max breaks on "aba".
• l = r instead of l = r + 1 breaks on "ab".
• Storing the first copy is wrong almost everywhere.
• Cosmetic variants, like i >= r, are never wrong.

Let me think about complexity here. There are two passes over the string, and each step is a lookup, a max and a compare. So time is O(n). Space is O(1) extra: the last array is always 26 ints, and the answer has at most 26 parts.

The worst case, like 500 copies of one letter, is still just two passes.

Oh, one more thing — the sizes always add up to n. The last cut always lands at the final index, because the last letter's last copy is the end of the string. So I never need a leftover part after the loop.
