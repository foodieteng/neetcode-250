Hmm, let me think about this for a sec.

A naive approach would be to try every set of cut points. There are n − 1 gaps, so that's 2^(n−1) choices, and each one needs a check. Fine for 10 letters, hopeless for 500.

A better but still slow idea: for each start, keep growing the part, and rescan to see if any letter inside also shows up later. That's O(n²). It works for 500, but we can do better.

This problem reminds me of merging intervals. Each letter covers an interval, from its first copy to its last copy. Overlapping intervals must land in the same part. But I don't need to build the intervals. A greedy scan with the last positions does the same job.

The greedy: walk left to right. Keep r, the furthest last position of any letter I've seen in this part. That's the earliest place this part is allowed to end. When i reaches r, cut right there. Cutting earlier is not allowed, because some letter still has a copy ahead. Cutting later only makes this part bigger and gives fewer parts. So cutting as soon as possible gives the most parts.

Here's the plan.

// pass 1: last[c] = last index of letter c
// pass 2: l = start of the current part
//         r = furthest last[] seen in this part
// invariant: the part can't end before r
for i in 0..n-1:
  r = max(r, last[s[i]])   // update first
  if i == r:                  // then check
    add r - l + 1, then l = r + 1

Here, I'm using an array of 26 ints to keep track of the last index of each letter. Then l and r mark the current part.

One thing worth flagging — it must be max, not a plain overwrite. Let me walk through that. Take "aba". At i = 0, r becomes 2. At i = 1, the last 'b' is 1. If I overwrite, r drops to 1, and I cut "ab" off. But the 'a' at index 2 is still ahead. With max, r stays 2, and I get one part, [3]. The furthest end can only grow, never shrink.

There's a trade-off here. I could build real intervals for each letter, sort them, and merge them. That's correct too, but it's more code and more steps. Two passes with a 26-slot array is simpler, and it's O(n) time.

class Solution {
public:
    vector<int> partitionLabels(string s) {
        int n = s.size();
        vector<int> last(26, 0);

        for (int i = 0; i < n; i++) {
            last[s[i] - 'a'] = i;
        }

        vector<int> ans;
        int l = 0, r = 0;

        for (int i = 0; i < n; i++) {
            r = max(r, last[s[i] - 'a']);
            if (i == r) {
                ans.push_back(r - l + 1);
                l = r + 1;
            }
        }

        return ans;
    }
};

That matches the plan line by line. The first loop just overwrites, so the last write wins. That gives the last index for free.

One thing worth flagging — the order of the two lines in the second loop matters. Update r first, then check i == r. I checked small changes against all 1,398,100 strings over {a,b,c,d} of length 1 to 10:

• Check i == r before updating r: 1,292,424 wrong. Smallest is "aa": it returns [1,1], but the answer is [2].
• Overwrite r = last[...] instead of max: 1,389,600 wrong. Smallest is "aba": [2,1] instead of [3].
• l = r instead of l = r + 1: 345,516 wrong. Smallest is "ab": [1,2] instead of [1,1].
• Store the first copy instead of the last: 1,398,036 wrong. Even "aa" returns [1].
• i >= r, l = i + 1, starting at r = -1, or last(26, -1): 0 wrong. Those are all the same thing.

C
CANDIDATE

Let me think about complexity here. There are two passes over the string. Each step does O(1) work: one array lookup, one max, one compare.

The time complexity is O(n). The space complexity is O(1) extra. The last array is always 26 ints, no matter how long the string is. And the answer has at most 26 parts, so even the output is bounded by a constant.

In the worst-case scenario, like 500 copies of one letter, the whole string is one part. It's still two passes, so it's still O(n).

Oh, one more thing — the sizes always add up to n. Each cut starts the next part at r + 1, and the last cut is always at n − 1, because the last letter's last copy is the end of the string. So I never need a "leftover part" after the loop.
