Hmm, let me think about this for a sec.

A naive approach would be to try both ways of giving change every time a $20 shows up, and search over all the choices. That branches at every $20, so the number of paths grows exponentially. With up to 105 customers, that's way too slow.

This problem reminds me of a greedy coin choice. The only real decision is at a $20: 10 + 5 or 5 + 5 + 5. And I think there's a clear winner. A five is the more useful bill. A five can pay change for a $10 and for a $20. A ten can only help with a $20. So when I have a choice, I should spend the less useful bill — the ten — and keep my fives. That turns it into a simple simulation with two counters.

// state: pay5, pay10 = bills I hold right now
for each bill b:
  b == 5  → pay5++
  b == 10 → give one 5; fail now if pay5 < 0; pay10++
  b == 20 → if I have a 10: give 10 + 5
          else: give 5 + 5 + 5
          fail now if pay5 < 0
// invariant: pay5 >= 0 after every customer
return true

Here, I'm using two integers, pay5 and pay10, to keep track of the bills in my cash box after each customer.

One thing worth flagging — why give the ten first? Let me walk through that. Take [5,5,5,5,10,20,10]. Both strategies are the same up to the $20. Then they split:

At i = 5, the "5 + 5 + 5" way burns all three fives and keeps a ten. Then the next $10 customer needs a five, and there's none left. The greedy way keeps two fives, so it survives. Spending the ten never hurts me, because a ten can't do anything a five can't.

One thing worth flagging too — I check for failure right away, inside the loop. If I only checked pay5 >= 0 at the very end, [10,5] would end at zero fives and look fine. But the first customer already got no change. Checking early is a correctness rule here, not a speed trick.

There's a trade-off here. I could keep the search over both choices to be 100% safe. But the argument above shows greedy is never worse, and it's O(n) with O(1) space. So I'll go with greedy.

class Solution {
public:
    bool lemonadeChange(vector<int>& bills) {
        int pay5 = 0, pay10 = 0;

        for (int& b : bills) {
            if (b == 5) {
                pay5++;
            } else if (b == 10) {
                if (--pay5 < 0) return false;
                pay10++;
            } else {
                // (10, 5) (5, 5, 5)
                if (pay10) {
                    --pay10;
                    if (--pay5 < 0) return false;
                } else {
                    pay5 -= 3;
                    if (pay5 < 0) return false;
                }
            }
        }

        return true;
    }
};

That matches the plan. The comment // (10, 5) (5, 5, 5) is the order I try the two ways for a $20.

One thing worth flagging — in the $20 branch, if I have a ten but no five, I return false right away. I don't fall back to 5 + 5 + 5. Is that too early? No. The other way needs three fives, and I have zero. So no way works, and false is correct. Also, the check is < 0, not <= 0. Landing on exactly zero fives is fine — I paid the change, I'm just out of fives now.

Let me think about complexity here.

The time complexity is O(n). I look at each bill once, and each step is a few constant-time updates.
