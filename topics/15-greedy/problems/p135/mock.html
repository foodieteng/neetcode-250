Hmm, let me think about this for a second.

A naive approach starts everyone at 1 and keeps scanning, bumping any child who breaks a rule, until nothing changes. It's correct, but on a long falling slope each pass fixes only one step, so it's O(n²).

This problem reminds me of a two-sweep greedy pattern: build a lower bound from each side with one scan, then combine them, because the answer at each spot depends on both the left and the right. So: one greedy pass left-to-right for the left rule, one pass right-to-left for the right rule, and take the max.

P — plan
C
CANDIDATE

Here's the plan.

// c[i] = candies for child i, start all at 1
// pass 1, left → right: fix the LEFT rule
if ratings[i] > ratings[i-1]: c[i] = c[i-1] + 1
// pass 2, right → left: fix the RIGHT rule, keep pass 1
if ratings[i] > ratings[i+1]: c[i] = max(c[i], c[i+1] + 1)
// answer
return sum(c)

One: everyone starts at 1 candy. Two: left to right, a child who beats its left neighbor gets one more than that neighbor. Three: right to left, a child who beats its right neighbor gets the max of what it has and one more than that neighbor. Then sum.

Why the minimum? Each pass measures a rising run that any valid answer must cover, so each is a lower bound, and their max is a lower bound we can reach.

One thing worth flagging — the second pass must go right-to-left, so c[i+1] is already final; otherwise [2,1,0] gives 5 instead of 6.

An O(1)-space version exists, but it's trickier.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. A candy array of ones, a forward loop for the left rule, a backward loop for the right rule, then accumulate.

class Solution {
public:
    int candy(vector<int>& ratings) {
        int n = ratings.size();
        vector<int> c(n, 1);

        for (int i = 1; i < n; i++) {
            if (ratings[i] > ratings[i - 1]) c[i] = c[i - 1] + 1;
        }

        for (int i = n - 2; i >= 0; i--) {
            if (ratings[i] > ratings[i + 1]) c[i] = max(c[i], c[i + 1] + 1);
        }

        return accumulate(c.begin(), c.end(), 0);
    }
};

One thing worth flagging — the max in the second loop is about correctness. Pass 1 may already have given a child a big number from a long climb on the left, and plain assignment throws that away: on [0,1,2,0], the 2 drops from 3 to 2, and the total is 6 instead of 7.

Two small details: the backward loop starts at n - 2, since it reads the right neighbor. And both checks are strict > — with >=, [0,0] returns 3 instead of 2.

Let me think about complexity here. Time is O(n): two passes plus one sum. Space is O(n) for the c array. On 50,000 random children it runs in about 0.5 ms.

The worst-case total is a strictly rising line, n(n+1)/2 — about 1.25 billion at 50,000 children, still below INT_MAX, so summing with an int is safe.

Oh, one more thing — if you want O(1) extra space, there's a one-pass version that counts up-slopes and down-slopes as triangle sums. The tricky part is the peak, which belongs to both slopes. For an interview, the two-pass version is much easier to explain and to prove.
