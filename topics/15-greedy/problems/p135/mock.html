Hmm, let me think about this for a sec.

A naive approach would be to start everyone at 1, then keep scanning the line. Every time a rule is broken, bump that child up. Repeat until nothing changes. That gives the right answer, but on a long falling slope one pass only fixes one step. So it can take O(n) passes, which is O(n²) total. Too slow to be happy with.

This problem reminds me of a two-sweep greedy pattern: build a lower bound from each side with one prefix-style scan, then combine the two. The answer at each spot depends on what's on the left and what's on the right. The trick there is one pass from each side, then combine. I'll do the same thing here: one greedy pass left-to-right for the left rule, one pass right-to-left for the right rule, and take the max.

P — plan
C
CANDIDATE

Here's the plan.

// c[i] = candies for child i, start all at 1
// pass 1, left → right: fix the LEFT rule
if ratings[i] > ratings[i-1]: c[i] = c[i-1] + 1
// pass 2, right → left: fix the RIGHT rule, keep pass 1
if ratings[i] > ratings[i+1]: c[i] = max(c[i], c[i+1] + 1)
// answer
return sum(c)

Here, I'm using one array c to keep track of the smallest legal candy count for each child so far.

Now, why is this the minimum, not just a valid answer? Let me walk through that. After pass 1, c[i] is the length of the rising run that ends at i. If five ratings in a row keep going up, the fifth child sits on top of a chain 1 < 2 < 3 < 4 < 5. Any valid answer must give that child at least 5. So pass 1 is a lower bound. Pass 2 gives the same kind of lower bound from the right side. The max of two lower bounds is still a lower bound. And the result follows both rules, so we can reach it. A lower bound we can reach is the optimum.

I like to picture it as terrain. Valleys get 1. Going uphill adds one each step. A peak gets climbed from both sides, so it takes the taller of the two climbs.

One thing worth flagging — the second pass must go right-to-left. To fix child i against its right neighbor, I need c[i+1] to be final already. Going right-to-left means it is. If I go left-to-right, I read c[i+1] before it's fixed. On [2,1,0] that gives 5, but the answer is 6.

There's a trade-off here. This uses O(n) extra space. There's an O(1)-space version that counts up-slopes and down-slopes in one pass. It's trickier to get right, so I'll start with the two-pass one and can talk about the other one after.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int candy(vector<int>& ratings) {
        int n = ratings.size();
        vector<int> c(n, 1);

        for (int i = 1; i < n; i++) {
            if (ratings[i] > ratings[i - 1]) c[i] = c[i - 1] + 1;
        }

        for (int i = n - 2; i >= 0; i--) {
            if (ratings[i] > ratings[i + 1]) c[i] = max(c[i], c[i + 1] + 1);
        }

        return accumulate(c.begin(), c.end(), 0);
    }
};

That matches the plan. One thing worth flagging — the max in the second loop is not just style. It's needed for correctness. Pass 1 may already have given child i a big number from a long climb on the left. If I just write c[i] = c[i+1] + 1, I throw that away. Take [0,1,2,0]. Pass 1 gives the 2 a count of 3. Without max, pass 2 drops it to 2, and it's no longer more than its left neighbor. Total 6 instead of 7.

Two small details. The second loop starts at n - 2, not n - 1, because it reads ratings[i + 1]. Starting at n - 1 would read past the end on every input. And both checks use strict >. With >=, [0,0] would return 3, but equal ratings need nothing, so the answer is 2.

Let me think about complexity here. The time complexity is O(n). It's two passes plus one sum, each touching every child once. The space complexity is O(n) for the c array. On a random input of 5·10⁴ children, it runs in about 0.55 ms.

In the worst-case scenario for the total, ratings go strictly up. Then the total is n(n+1)/2. For n = 2·10⁴ that's 200,010,000. Even at n = 5·10⁴ it's 1,250,025,000, still below INT_MAX of 2,147,483,647. So summing with an int start value of 0 in accumulate is safe.

Oh, one more thing — if you want O(1) extra space, there's a one-pass version that counts the length of each up-slope and down-slope and adds them as triangle sums. The tricky part is the peak, which belongs to both slopes. I'd want to test that one carefully before using it. For an interview, the two-pass version is much easier to explain and to prove.
