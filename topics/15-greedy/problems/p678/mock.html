Hmm, let me think about this for a second.

A naive approach tries all 3k ways to fill the stars — exponential. A step up is a DP over the set of reachable open counts, which is correct but O(n2).

This problem reminds me of the classic balance-counter check for parentheses, plus a greedy idea: instead of trying every choice, I track the range [l, r] of possible open counts. A '(' shifts the range up by one, a ')' shifts it down, and a '*' widens it by one on each side.

The key fact is that the reachable counts are always contiguous — no gaps — so two ints are enough.

C
CANDIDATE

Here's the plan.

// l = fewest possible open, r = most possible open
// invariant: every count in [l, r] is reachable
l = 0, r = 0
for each c in s:
  '(' → l++, r++
  ')' → l--, r--
  '*' → l--, r++   // widen both sides
  if r < 0: return false  // too many ')'
  l = max(l, 0)       // no negative open count
return l == 0         // can I end at zero?

One: start l and r at 0. Two: a '(' bumps both, a ')' drops both, a '*' drops l and bumps r. Three: if r < 0, return false on the spot; clamp l at 0; at the end, return l == 0.

So there are two ways to fail: r < 0 means too many ')' even if every star opens, and l > 0 at the end means too many '('.

One thing worth flagging — the clamp. A negative count is a dead choice, not a real state. Without it, a single "*" breaks: l sits at -1, so I'd say false, but the star can be empty.

The set DP is easier to trust, but the range is O(n) time and O(1) space.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. It's one loop over the string with two ints.

class Solution {
public:
    bool checkValidString(string s) {
        int l = 0, r = 0;

        for (char &c : s) {
            if (c == '(') {
                l++; r++;
            } else if (c == ')') {
                l--; r--;
            } else {
                l--; r++;
            }

            if (r < 0) return false;
            l = max(l, 0);
        }

        return l == 0;
    }
};

Each character shifts or widens the range, then I check r < 0 to fail early, then clamp l up to 0. After the loop, I return l == 0.

One thing worth flagging — every small line is load-bearing. I tested wrong versions on all short strings:

• Dropping the clamp: over 27,000 wrong, and a single "*" is enough to break it.
• if (l < 0) return false instead of clamping: also fails on a single "*".
• Checking r < 0 only at the end: fails on ")*", because the star hides the first ')' that had nothing to match.

The step that matters is the first ')': the range drops from [0, 2] to [-1, 1]. -1 isn't a real state, so I clamp to [0, 1]. 1 stays alive because the star could be a '(', and that lets the last ')' work. l ends at 0, so true.

A failing one: "*)(" ends with l = 1 — that last '(' never closes, so false.

Corner cases:

• "*" is true only thanks to the clamp.
• ")*" fails right away, which is why r is checked inside the loop.

Let me think about complexity here.

Time is O(n) — one pass, O(1) work per character. Space is O(1) — just two ints, however many stars there are.

The worst case is all stars, where brute force needs 3100 tries, but here the range just widens by one each step.

Oh, one more thing — there's a two-pass version too. Left to right, treat stars as opens and fail if closes ever win; right to left, treat stars as closes and fail if opens ever win. The first pass is my r < 0 check; the second matches my end check on l.
