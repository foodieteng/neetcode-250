Hmm, let me think about this for a sec.

A naive approach would be to try all 3k ways to replace the k stars, and check each string. That's exponential. A step up is a DP over the set of reachable open counts. That's correct, but it's O(n2).

This problem reminds me of the classic balance-counter check for parentheses, plus a greedy idea. Here's the reframe. Instead of trying 3k choices, I track the range [l, r] of possible open counts. A '(' moves the whole range up by one. A ')' moves it down by one. A '*' widens it by one on each side: l - 1 if it closes, r + 1 if it opens.

The key fact is that the reachable counts are always a contiguous range. There are no gaps. So two ints are enough. I don't need the whole set.

P — plan
C
CANDIDATE

Here's the plan.

// l = fewest possible open, r = most possible open
// invariant: every count in [l, r] is reachable
l = 0, r = 0
for each c in s:
  '(' → l++, r++
  ')' → l--, r--
  '*' → l--, r++   // widen both sides
  if r < 0: return false  // too many ')'
  l = max(l, 0)       // no negative open count
return l == 0         // can I end at zero?

Here, I'm using two ints, l and r, to keep track of the lowest and highest open count I could have right now.

There are two ways to fail. First, r < 0. Even if every star is '(', there are too many ')'. Nothing later can fix that, so I return false right away. Second, at the end, l > 0. Even if every star closes, there are too many '(' left. So I return l == 0.

One thing worth flagging — I clamp l at 0. Let me walk through that. A negative open count is not a real state. It means "I closed more than I opened", and that choice is just dead. So the lowest real count is 0. Without the clamp, the single string "*" breaks. l goes to -1 and stays there, so l == 0 is false. But the right answer is true, because the star can be empty.

There's a trade-off here. The set DP is easy to trust, but it's O(n2) time and O(n) space. The range version is O(n) time and O(1) space. But it needs the "no gaps" argument to be correct. I think that argument is simple enough to say out loud, so I'll go with the range.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool checkValidString(string s) {
        int l = 0, r = 0;

        for (char &c : s) {
            if (c == '(') {
                l++; r++;
            } else if (c == ')') {
                l--; r--;
            } else {
                l--; r++;
            }

            if (r < 0) return false;
            l = max(l, 0);
        }

        return l == 0;
    }
};

That matches the plan line by line.

One thing worth flagging — each small line here is load-bearing. I checked some wrong versions against all 88,572 strings of length 1 to 10:

• No clamp: 27,516 wrong. Smallest is "*": it returns false, but the answer is true.
• if (l < 0) return false instead of the clamp: 22,731 wrong. "*" returns false again.
• Return r == 0: 22,731 wrong. "*" returns false, because r is 1.
• Treat '*' as empty only: 20,788 wrong. "(*" returns false, but the star can close it.
• One counter, star as '(', no end check: 22,731 wrong. Even "(" returns true.
• Check r < 0 only at the end: 16,153 wrong. ")*" returns true, but the first ')' has nothing to close.

And two changes that are safe: swapping the clamp and the r < 0 check, or returning l <= 0. Both give 0 wrong. They are the same thing.

The highlighted row is step 3. After the star, the range is [0, 2]. The first ')' moves it to [-1, 1]. But -1 means the star closed and then this ')' closed again, with nothing open. That's not a real state. So I clamp to [0, 1]. The count 1 is still alive, because the star could be '('. That's what lets the last ')' work. At the end l = 0, so true.

Now a failing one, "*)(". Expected false. The star gives [-1, 1], clamp to [0, 1]. The ')' gives [-1, 0], clamp to [0, 0]. The '(' gives [1, 1]. At the end l = 1. That last '(' has nothing after it to close it, so false. Correct.

Let's also test with corner cases.

• "*": [-1, 1], clamp to [0, 1], end l = 0. True. This is the case that breaks with no clamp.
• ")": r = -1, so return false right away.
• "(": range [1, 1], end l = 1. False.
• "(*": [1, 1], then [0, 2]. End l = 0. True, the star closes it.
• ")*": the first ')' makes r = -1, so false right away. This is why I check r inside the loop. At the end, the star would hide the problem.

All three official examples pass too.

C
CANDIDATE

Let me think about complexity here. There is one loop, and nothing nested inside it.

The time complexity is O(n). It's one pass, with O(1) work per character. The space complexity is O(1). It's just two ints, no matter how many stars there are.

In the worst-case scenario, every character is a star. Brute force would need 3100 tries. Here, the range just gets wider by one each step. It's still one pass.

Oh, one more thing — there's a two-pass version that's also correct. Go left to right and count '(' and '*' as opens. If closes ever win, return false. Then go right to left and count ')' and '*' as closes. If opens ever win, return false. I checked it on all 88,572 short strings: 0 wrong. The first pass is exactly my r < 0 check. The second pass catches too many '(', like my l == 0 check at the end.
