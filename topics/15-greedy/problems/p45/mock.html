A naive approach would be to use DP. dp[j] = fewest jumps to reach j. For each i, I try every j it can reach and set dp[j] = min(dp[j], dp[i] + 1). That's correct, but it's O(n · max jump). Up to about 107 steps here. I'd keep it as a checker, not the answer.

This problem reminds me of BFS shortest path. "Fewest jumps" is "fewest edges", and every edge costs 1. So I can think in layers. Layer k is the set of cells I can reach in exactly k jumps, and not fewer. The answer is the layer number of index n − 1.

Now the prefix fact pays off. "Reachable within k jumps" is a prefix. So each layer is a contiguous range: it starts right after the last layer ends. That means I don't need a queue. A layer is just a right edge. Here are the layers for example 1:

Here's the plan. It's BFS, but with two numbers instead of a queue.

// curEnd = right edge of the layer I can reach with `step` jumps
// nextEnd = farthest index reachable with ONE more jump,
// from any cell scanned so far
step = 0, curEnd = 0, nextEnd = 0
for i = 0 .. n-2:  // standing on n-1 needs no jump
  nextEnd = max(nextEnd, i + nums[i])  // cell i grows the next layer
  if i == curEnd:  // current layer fully scanned
    step++  // I must take one more jump
    curEnd = nextEnd  // the next layer ends here
return step

Here, I'm using curEnd to keep track of where the current layer stops. And nextEnd collects, from every cell in the current layer, how far one more jump could go. When i reaches curEnd, I've seen every cell of the current layer. The next layer can't grow anymore. So I close it: step++, and the new edge is nextEnd.

The key idea: this code never decides which cell to jump from. It only tracks how far each layer goes. The real path is hidden inside the layers, and I don't need it, because the question only asks for the count.

One thing worth flagging — the loop stops at n − 2, not n − 1. Let me walk through that. Index n − 1 is always the edge of the last layer, because nothing past it exists. If I scanned it, i == curEnd would fire one extra time and add 1 for a jump I never take. That version is always exactly one too high. Even [0] gives 1 instead of 0.

There's a trade-off here. I could also write a plain BFS with a queue, or keep explicit l, r bounds per layer. Same O(n) time, same answers, but more code and more state. The two-number version is shorter, and it's O(1) space. So I'll go with that.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int jump(vector<int>& nums) {
        int step = 0, curEnd = 0, nextEnd = 0;

        for (int i = 0; i < nums.size() - 1; i++) {
            nextEnd = max(nextEnd, i + nums[i]);

            if (curEnd == i) {
                step++;
                curEnd = nextEnd;
            }
        }

        return step;
    }
};

That matches the plan line by line.

One thing worth flagging — the order inside the loop matters. I update nextEnd before the curEnd check. Cell i is part of the layer I'm closing, so its reach must count before I close it. If I swap the two lines, then at i = 0, nextEnd is still 0. The first layer closes with edge 0, and things go wrong from there. Example 1 returns 1 instead of 2.

Also, -Wall -Wextra gives one warning: -Wsign-compare on i < nums.size() - 1, int against size_t. It's harmless here, since n ≥ 1. For n = 1, size() - 1 is 0, and the loop doesn't run. Only an empty vector would wrap to SIZE_MAX, and that's outside the constraints. Writing int n = nums.size(); and i < n - 1 removes the warning and gives the same answers.

Let me think about complexity here.

The time complexity is O(n). One pass over indices 0 to n − 2, with one max and one compare each.

The space complexity is O(1). Three integers.

In the worst-case scenario the loop always runs n − 1 times. There's no early exit. For n = 104 that's 9,999 iterations, about 6.3 µs for all 1000s and 6.5 µs for all ones. The largest nextEnd is 10,998, so int is safe.

I'd test this against a BFS checker. Every array of length 1 to 8, values 0 to 3, that can reach the end: 41,600 arrays. Plus random ones, up to n = 2000 with values up to 1000. 261,600 cases total, 0 mismatches. The same test shows how the bugs fail. Scanning the last index fails 21,376, always exactly +1. Checking before updating fails 41,488. And one trap: "count a jump every time nextEnd improves" fails 23,580, but it passes both official examples. The smallest failure is [2,2,0]: it says 2, the right answer is 1. Always jumping the full nums[i] fails 11,884, and it loops forever on a zero.

Oh, one more thing — this code trusts the guarantee. It never returns −1. If the end were not reachable, it would still return a normal-looking number. [3,2,1,0,4] returns 2, even though index 4 can't be reached. If the guarantee could break, I'd add the Jump Game I check: if nextEnd stays at i when a layer closes, return −1.
