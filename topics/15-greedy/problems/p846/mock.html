A naive approach would be to backtrack — try every way to build each group, and undo when I get stuck. That's exponential, and with 10,000 cards it won't finish.

This problem reminds me of a greedy pass over a sorted count map. The fact from before removes all the choice: the smallest card has only one legal role, so there's nothing to try. And I don't build one group at a time. If the smallest value k has cnt copies, I start that many groups at once, so I subtract cnt from each of k through k+g−1 in a single pass. I'll go with an ordered map<int,int> — it gives me the counts, and sorted keys for free.

C
CANDIDATE

Here's the plan. The state is a frequency map of unused copies, and the invariant is: when I reach key k, every smaller key is already 0. First, build the map from the hand. Second, walk the keys in increasing order; copy the count — not a reference — and skip the key if it's 0. Third, for each of the next groupSize values, return false if it's missing or short; otherwise subtract cnt. If all pass, return true.

// state: freq[v] = copies of v not used yet
// invariant: when I reach key k, every key < k is 0
build freq from hand
for each key k in increasing order:
  cnt = freq[k]   ← copy, not a reference
  if cnt == 0: skip   ← used up by earlier groups
  for i in 0 .. g−1:
    if k+i missing or freq[k+i] < cnt: return false
    freq[k+i] −= cnt
return true

One thing worth flagging — the invariant makes the greedy safe. The copies of k can't join an earlier group, so they must start new ones, and a short value has no other placement. So failing right away is correct, not just fast.

A sort plus a hash map also works; the ordered map is shorter.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool isNStraightHand(vector<int>& hand, int groupSize) {
        map<int, int> freq;
        for (int &x : hand) {
            freq[x]++;
        }

        for (auto &[k, v] : freq) {
            int cnt = v;
            if (cnt == 0) continue;
            for (int i = 0; i < groupSize; i++) {
                if (!freq.count(k + i) || freq[k + i] < cnt) return false;
                freq[k + i] -= cnt;
            }
        }

        return true;
    }
};

One loop builds the map. A second loop walks it with a structured binding, [k, v]: I copy v into cnt, skip zeros, and the inner loop checks and subtracts at k + i. That matches the plan line by line.

One thing worth flagging — int cnt = v; is a copy, and that's needed for correctness. v is a reference to the entry for k, and at i = 0 the subtraction sets that entry to 0. If I used v directly, every later check would use 0, and the groups would never really be taken out. The zero skip matters too: used-up keys stay in the map, and starting groups at them could wrongly return false.

Let me think about complexity here. The nested loop looks like O(n · g), but it isn't. Every passing inner step subtracts at least one card, so across the whole run the inner loop takes at most n + 1 steps — at 10,000 cards, the most I saw was 10,001.

The time complexity is O(n log n), dominated by building the map. The space complexity is O(n), one entry per distinct value. In the worst case, all values are distinct, and it still runs in about 3 ms.

Against exhaustive backtracking on 270,592 cases, there were 0 mismatches.

Oh, one more thing — I don't check up front whether the hand size divides by groupSize. It's still correct without it, but that one-line check is a cheap, optional early exit.
