A naive approach would be to backtrack. Pick a card, try every way to build a group with it, and undo when stuck. That's exponential. With up to 104 cards, it won't finish.

This problem reminds me of greedy with a sorted count map. The fact from before removes all the choice. The smallest card has only one legal role, so there's nothing to try. I just follow it.

And I don't need to build one group at a time. If the smallest value k has cnt copies, I start cnt groups at once. That means I need cnt copies of each of k, k+1, ..., k+g−1. So I subtract cnt from all of them in one pass.

I'll go with an ordered map<int,int>. It gives me counts and walks the keys from small to large for free.

Here's the plan.

// state: freq[v] = copies of v not used yet
// invariant: when I reach key k, every key < k is 0
build freq from hand
for each key k in increasing order:
  cnt = freq[k]   ← copy, not a reference
  if cnt == 0: skip   ← used up by earlier groups
  for i in 0 .. g−1:
    if k+i missing or freq[k+i] < cnt: return false
    freq[k+i] −= cnt
return true

Here, I'm using an ordered map to keep track of how many copies of each value are still free. Because the keys come out sorted, the key I'm on is always the smallest card still left.

One thing worth flagging — the invariant is what makes the greedy safe. Let me walk through that. When I reach k, all smaller keys are already 0. So the copies of k can't join any group that started earlier. They must start new groups. If any of k+1 to k+g−1 is short, there's no other way to place those cards. So returning false right away is correct, not just fast.

There's a trade-off here. I could also sort the array and use a hash map. The ordered map costs O(log n) per access. But it keeps the code short, and it gives sorted keys without a separate sort. At 104 cards, that's fine.

class Solution {
public:
    bool isNStraightHand(vector<int>& hand, int groupSize) {
        map<int, int> freq;
        for (int &x : hand) {
            freq[x]++;
        }

        for (auto &[k, v] : freq) {
            int cnt = v;
            if (cnt == 0) continue;
            for (int i = 0; i < groupSize; i++) {
                if (!freq.count(k + i) || freq[k + i] < cnt) return false;
                freq[k + i] -= cnt;
            }
        }

        return true;
    }
};

That matches the plan line by line.

One thing worth flagging — int cnt = v; is a copy, and that's needed for correctness. v is a reference to freq[k]. At i = 0, the line freq[k] -= cnt sets freq[k] to 0. If I used v directly, v would also become 0 right there. Then every later check and subtraction for k+1 and up would use 0, and the groups would never really be taken out. Copying first freezes the number of groups I'm starting.

Two more small details. The cnt == 0 skip is also needed. Keys that earlier groups used up are still in the map, just with 0. Without the skip, I'd try to start groups at those keys. Near the top end, a key like k+1 may not exist, so it could wrongly return false. And the order inside the if matters. !freq.count(k + i) runs first, and || short-circuits. So freq[k + i] only runs when the key already exists. It never inserts a new key while I'm walking the map. In my tests, the map size never changed.

Let me think about complexity here. The inner loop sits inside the outer loop, so it looks like O(n · g). It's not. Every inner step that passes subtracts cnt, and cnt is at least 1. The total I can subtract is at most n, the number of cards. Plus at most one failing step before I return. So the inner loop runs at most n + 1 times in total. At n = 104, the most I saw was 10,001.

The time complexity is O(n log n). Building the map is n inserts at O(log n) each, and that part dominates. The inner steps are also map lookups, but there are at most n + 1 of them. The space complexity is O(n) for the map, one entry per distinct value.

In the worst-case scenario, all values are distinct, so the map has n keys and every access costs log n. That's still O(n log n). At n = 104, it runs in about 3 ms.

Oh, one more thing — this code doesn't check n % groupSize up front. It's still correct without it, because a bad size always ends up with a short group. But adding if (hand.size() % groupSize) return false; at the top is a cheap, optional early exit.
