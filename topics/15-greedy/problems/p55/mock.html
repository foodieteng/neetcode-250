Hmm, let me think about this for a sec.

A naive approach would be to treat it as a graph. Each index has edges to the next nums[i] indices. Then I run a BFS, or a DP where reach[j] is true if some earlier reachable i has i + nums[i] >= j. That's correct, and I'd keep it as a checker. But it touches every edge, so it can be O(n²). With n = 104 and jumps up to 105, that's wasted work.

This problem reminds me of a greedy "frontier" scan — a running-maximum sweep over one growing covered interval, the same exchange idea as merging overlapping intervals into a single covered prefix. Because the reachable set is a prefix, I only need to push its right edge forward. Each index i that's inside the prefix offers a new edge, i + nums[i]. I take the max. One pass, no set, no queue.

P — plan
C
CANDIDATE

Here's the plan.

// farthest = farthest index reachable using indices 0..i-1
// invariant: reachable set is exactly [0..farthest]
farthest = 0
for i = 0 .. n-1:
  if i > farthest: return false // i is outside the prefix
  farthest = max(farthest, i + nums[i]) // i can push the edge
return true  // every index, including n-1, was reachable

Here, I'm using farthest to keep track of the right edge of the reachable prefix. When I arrive at index i, farthest only counts jumps from 0 to i − 1. If i > farthest, nobody before i can reach i. And since the set is a prefix, nothing after i is reachable either. So I can stop and return false right there.

One thing worth flagging — the order of the two lines matters. The check must come before the update. Let me walk through that. If I update first, then farthest is at least i + nums[i], which is at least i. So i > farthest can never be true. The function never returns false. It fails every unreachable case, including example 2, and even [0,0].

There's a trade-off here. I could also go backward. Keep a goal, starting at n − 1. Walk from the end to the front. If i + nums[i] >= goal, then i can reach the goal, so move the goal to i. At the end, return goal == 0. That's also O(n) and O(1), and it's correct. But the forward version can stop early at the first wall, and it says the prefix idea directly. So I'll go forward.

Does this approach sound good, or would you rather I think of another way?

CANDIDATE

class Solution {
public:
    bool canJump(vector<int>& nums) {
        int n = nums.size();
        int farthest = 0;

        for (int i = 0; i < n; i++) {
            if (i > farthest) return false;

            farthest = max(farthest, i + nums[i]);
        }

        return true;
    }
};

That matches the plan line by line.

One thing worth flagging — the compare is >, not >=. i == farthest means i is the last reachable index. That's fine, I'm standing on it. If I wrote >=, then at i = 0 the check is 0 >= 0, which is true. So it returns false on the very first step, for every input. Even [0], where the answer is true.

And the max is needed. It's tempting to write farthest = i + nums[i], but a small value later would pull the edge back. Take [2,0,0]. Index 0 sets farthest to 2. Then index 1 would set it to 1 + 0 = 1, and index 2 looks unreachable. That returns false, but the answer is true. The sneaky part: that version passes both official examples.

Let me think about complexity here.

The time complexity is O(n). One pass, and each step is one compare and one max.

The space complexity is O(1). Just two integers.

In the worst-case scenario I go through all n indices. For a true answer that's always n steps. The worst false case is all ones but with a zero at index n − 2. Then the wall is found only at i = 9999, the last index, after all 10,000 iterations. The all-105 array runs all 10,000 steps in about 7.75 µs. And the biggest value farthest can hold is 9999 + 105 = 109,999. INT_MAX is about 2.1 billion, so int is safe. No long long needed.

Oh, one more thing — I'd test this against the BFS checker. I ran every array of length 1 to 8 with values 0 to 3. That's 87,380 arrays: 41,600 true and 45,780 false. Plus random large ones, for 307,380 cases total, with 0 mismatches. The same test shows how the small bugs fail. Update-before-check fails exactly the 45,780 false arrays. >= fails exactly the 41,600 true arrays. And dropping the max fails 28,480, while still passing both examples. The backward-goal version had 0 fails too.
