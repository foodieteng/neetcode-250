This problem reminds me of a greedy with a running sum, like Kadane's algorithm: when the sum goes negative, throw it away and start fresh. Why is that safe? A skip lemma. If I start at s and the tank first goes negative at i, nothing from s through i can be the start. Any station in between was reached with a tank of at least zero; starting there gives zero, so I'd fail at i again. So I jump the start straight to i + 1.

class Solution {
public:
    int canCompleteCircuit(vector<int>& gas, vector<int>& cost) {
        int n = gas.size();
        int total = 0, cur = 0, start = 0;

        for (int i = 0; i < n; i++) {
            int diff = gas[i] - cost[i];
            total += diff;
            cur += diff;

            if (cur < 0) {
                start = i + 1;
                cur = 0;
            }
        }

        return total < 0 ? -1 : start;
    }
};

One loop: diff = gas[i] - cost[i], it goes into both total and cur, and when cur < 0, start becomes i + 1 and cur goes back to 0. After the loop, return -1 if total < 0, otherwise start. That matches the plan line by line.

One thing worth flagging — start = i + 1 can end up equal to n, which is out of range. That only happens when the last station fails, which means every piece went negative, so total < 0 and I return -1 instead. And in my tests, returning start with no total check gets every single -1 case wrong.

Let me think about complexity here. There's one loop over the stations. The start jumps forward, but it never moves back, and I never restart the loop. So each station is visited once.

The time complexity is O(n). The space complexity is constant, O(1): just total, cur, and start.

In the worst-case scenario, the start resets at almost every station, like in example 1. That's still O(1) per station. The skip lemma is what lets me never look back.

Oh, one more thing — overflow. total sums up to 105 diffs, each between -104 and 104. So |total| <= 10^9, which is below INT_MAX. A plain int is safe here. If the limits were bigger, I'd switch to long long.
