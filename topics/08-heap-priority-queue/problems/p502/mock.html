Hmm, let me think about this for a second.

A naive approach would be to run k rounds, and in each round scan all n projects and pick the best affordable one I haven't done. It's correct, but O(k · n) is way too slow.

Which one is "best"? The one with the biggest profit. More money only opens up more projects and never closes one, so greedy is safe here.

This problem reminds me of a sort-and-sweep feeding a max-heap.
• Projects unlock in capital order, so I sort the indices by capital once and walk them with one pointer.
• Among the unlocked ones, I need the max profit fast — that's a max-heap of profits.

Each project is pushed and popped at most once, so this is O(n log n + k log n).

Here's the plan.

// state
idx = project indices sorted by capital
i   = next project in idx not unlocked yet
pq  = max-heap of profits  ← unlocked, not done

// repeat k times
push every idx[i] with capital <= w  ← refill each round
if pq is empty: stop  ← nothing affordable
w += pq.top(); pop

One: sort project indices by capital.
Two: in each of the k rounds, push every newly affordable profit into a max-heap.
Three: if the heap is empty, stop; otherwise add the top to w and pop it.

One thing worth flagging — the loop is driven by k, not by i.
• The refill must happen every round, after w grows, because the last profit might unlock new projects.
• The pointer i can reach n early while the heap still has good projects, so that's no reason to stop.
• The only early stop is an empty heap: nothing is affordable, and since w can't change, nothing ever will be.

There's a trade-off: the heap stores plain profits, not indices — I never revisit a project once it's unlocked. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int findMaximizedCapital(int k, int w, vector<int>& profits, vector<int>& capital) {
        int n = profits.size();
        vector<int> idx(n);
        iota(idx.begin(), idx.end(), 0);
        sort(idx.begin(), idx.end(), [&](int a, int b) {
            return capital[a] < capital[b];    // sort indices by threshold
        });

        priority_queue<int> pq;    // profits only
        int i = 0;
        while (k--) {    // run k rounds, don't stop on i
            while (i < n && capital[idx[i]] <= w)
                pq.push(profits[idx[i++]]);    // refill first, every round
            if (pq.empty()) break;    // nothing affordable
            w += pq.top();    // add the profit
            pq.pop();
        }
        return w;    // return the capital
    }
};

I sort the indices by capital, then run k rounds. The inner while is the refill — it runs at the start of every round, after the last profit. The heap stores profits only; priority_queue<int> is a max-heap by default, so the top is the biggest profit I can afford.

One thing worth flagging — the push loop uses <=, not <. With a strict <, project 0 in both examples needs 0 and I have 0, so it never unlocks, and both examples return 0.

And the if (pq.empty()) break; isn't just an early exit — without it, the next line calls top() on an empty heap.

Let me think about complexity here.

Time is O(n log n + k log n). The sort is O(n log n). The pointer i only moves forward, so across all rounds there are at most n pushes, and at most k pops, each O(log n). Space is O(n), for idx and the heap.

In the worst case, n = k = 105. That runs in about 15 to 20 ms, while the rescan-every-round O(k · n) version takes over 20 seconds.

I also checked it against a brute force on over 80 million small cases (80,132,960) with 0 mismatches — worth it, because some buggy versions still pass both examples.
