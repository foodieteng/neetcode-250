範例 Trace// 範例 2 · 樓梯式解鎖

k=3, w=0, profits=[1,2,3], capital=[0,1,2]:每做一個,剛好解鎖下一個。以修正版實跑。

// ROUND 1 w = 0 push #0(門檻 0,利潤 1) 堆 [1] 拿 1 → w = 1
// ROUND 2 w = 1 push #1(門檻 1,利潤 2) 堆 [2] 拿 2 → w = 3
// ROUND 3 w = 3 push #2(門檻 2,利潤 3) 堆 [3] 拿 3 → w = 6 // OUTPUT: 6
每輪堆裡都只有一個專案,根本沒得選 —— 所以最小堆、if 補堆、沒排序這幾種錯在範例 2 都會「剛好對」。 範例 1 在第 2 輪同時解鎖兩個(利潤 2 和 3),才真的在考「挑最大」。

應用題// APPLY IT

App 1. 如果 capital 改成真的要花掉的成本(做專案先扣 capital,做完拿回 profit),這個貪心還成立嗎?
App 2. 題目改成要回傳「依序做了哪些專案的 index」,堆要怎麼改?
App 3. 如果 k 很大(例如 10⁹)但 n 只有 10⁵,修正版的 while (k--) 會跑 10⁹ 圈嗎?
// ANSWERS
A1. 做專案不扣錢(capital 只是門檻),profit 又 ≥ 0,所以每做一個 w 只會不變或變大。

這讓「做得起」是單調的:一旦 capital ≤ w,之後永遠成立。所以專案依門檻排序後,指標 i 只需要往前走一次,進了堆的也不用再拿出來檢查 —— 整體 O(n log n),而不是每輪重掃的 O(k·n)(n = k = 10⁵ 實測超過 20 秒)。
A2. 交換論證:拿最大的利潤 P,資金不會比拿別的 p 少,之後能做的專案只多不少;而 p 留在堆裡,之後還能拿。

把最佳解這一輪的 p 換成 P、之後原本拿 P 的地方換成 p,總和不變、每一步門檻仍然滿足。 實測和 bitmask 暴力解窮舉 80,132,960 組 0 不一致。
A3. 不行。剛拿到的利潤可能讓下一個專案剛好解鎖,要先回頭補堆,補完還空才停。

最小反例 k=2, w=0, profits=[1,1], capital=[0,1]:做完 #0 後堆空,但 w=1 剛好讓 #1 做得起,正解 2。 這就是我原稿的 ③:只剩這個錯時窮舉錯 131,067 / 1,034,592,官方範例 1 也會停在回 1。
A4. 同一輪可能有好幾個專案同時解鎖,要全部進堆一起比,才知道哪個最大。

寫成 if 一輪只補一個:範例 1 第 2 輪 #1(利潤 2)、#2(利潤 3)同時解鎖,只補 #1 就只拿到 2,回 3。 窮舉錯 247,357 / 1,034,592。範例 2 每輪本來就只解鎖一個,所以會過。
A5. 必要。補完堆還是空,代表沒有做得起的專案,這時 pq.top() 是對空堆取值 —— 未定義行為。

實測窮舉錯 205,874 / 1,034,592:135,376 組 segfault、7,235 組 abort,還有 63,263 組靜默回錯答案 (例如 k=2, w=0, profits=[1], capital=[0] 回 2,正解 1,連 ASan/UBSan 都沒報)。範例過了不代表沒事。
A-App 1. 不成立。w 會變小,「做得起」就不再單調。

先做一個高門檻的專案可能把錢花光,反而做不了後面的;進了堆的專案之後也可能又做不起。 指標不回頭、堆裡永遠可做這兩個前提都垮了,要改用別的想法(例如依淨利或依成本分組重新設計),不能直接套這個貪心。
A-App 2. 堆改存 pair<利潤, index>,pop 時記下 index。

就是我原稿用的 priority_queue<pair<int,int>>。答案只要資金時存 int 就夠(兩種寫法對拍 10 萬組 0 不一致);要輸出順序時才需要 index。 如果利潤相同要指定 index 小的先,比較子還要加 tie-break(參考 1834 的錯 ③)。
A-App 3. 不會。每輪至少 pop 一個,堆最多只能 pop n 次;第 n+1 輪堆一定是空的,就 break 了。

所以實際圈數 ≤ min(k, n + 1),複雜度是 O(n log n)。題目的 k ≤ 10⁵ 本來也不大,但這個 break 讓 k 再大都沒關係 —— 也再次說明 if (pq.empty()) break; 不只是防崩潰。

// ONE-LINE TAKEAWAY
w 只增不減,所以依門檻排序 + 最大堆、指標不回頭。每輪先補堆(while)、再拿最大,堆空才停 —— 拿完堆空不能直接結束,新的 w 可能剛好解鎖下一個。範例 2 每輪沒得選,對很多錯都是盲點。
