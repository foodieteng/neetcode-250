Hmm, let me think about this for a sec.

A naive approach would be to check every point on the road and sum the trips that cover it. That's O(n × 1000). It works here, but its cost grows with the road length, not with the trips.

This problem reminds me of a sweep line over intervals with a min-heap of end points. Sort the trips by pick-up point. Keep a min-heap of drop-off points. Before each pick-up, pop everyone whose drop-off is at or before it. The top of the heap is always the next person to leave. That's O(n log n).

One: sort the trips by pick-up point.
Two: at each pick-up, drop everyone whose drop-off is at or before it, then board the new group.
Three: if the count goes over capacity, return false; otherwise push the drop-off and the count onto the heap.

Here, I'm using the min-heap to keep track of who leaves first. I only care about the earliest drop-off, so a heap is enough.

One thing worth flagging — the pop check must be <=. People getting off at a point free their seats for people getting on at that same point. With <, they'd still be counted, and the car looks full when it isn't.

class Solution {
public:
    bool carPooling(vector<vector<int>>& trips, int capacity) {
        // [numPassengersi, fromi, toi]
        sort(trips.begin(), trips.end(), [](auto& t1, auto& t2) {
            return t1[1] < t2[1];                           // sort by pick-up point
        });

        // {to, num}
        using P = pair<int, int>;
        priority_queue<P, vector<P>, greater<P>> pq;        // earliest exit on top
        int passenger = 0;

        for (auto& t : trips) {
            int num = t[0], from = t[1], to = t[2];

            while (!pq.empty() && pq.top().first <= from) { // drop off first (<=)
                passenger -= pq.top().second; pq.pop();
            }

            passenger += num;                               // then board
            if (passenger > capacity) return false;
            pq.emplace(to, num);
        }
        return true;
    }
};

I sort by t[1], the pick-up point, so I see events in road order. The heap stores {to, num} with greater, so the smallest to is on top.

One thing worth flagging — it's a while, not an if. Several groups can leave before one pick-up. And I check capacity right after boarding. The count only goes up at a pick-up, so that's the only place it can break the limit.

Corner cases:

• Back-to-back, [[1,0,1],[1,1,2]], cap 1 → true.
• if instead of while fails when two groups leave at the same point: [[1,0,1],[1,0,1],[2,1,2]], cap 2.
• Skipping the sort fails when trips come out of order: [[1,1,2],[1,0,1]], cap 1.
• Checking >= rejects a car that's exactly full: [[1,0,1]], cap 1.

Let me think about complexity here.

The time complexity is O(n log n). The sort is O(n log n). Each trip is pushed once and popped at most once, so the heap work is O(n log n) in total, even with the inner while. The space complexity is O(n), for the heap.

Oh, one more thing — since positions are at most 1000, there's a difference array. Do d[from] += num and d[to] -= num, then take a prefix sum and check it never goes over capacity. That's O(n + 1001) time, O(1001) space, and no sort. It also gets <= right for free: at the same point, the -num and +num land in the same cell. The heap version is the one that still works if positions were too large for an array.
