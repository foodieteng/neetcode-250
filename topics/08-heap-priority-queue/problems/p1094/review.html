應用題// APPLY IT

App 1. 題目保證座標 ≤ 1000,有沒有比 O(n log n) 更快的做法?
App 2. 如果座標可以到 10⁹,差分陣列還能用嗎?
App 3. 改成問「最少要幾個座位才夠」(會議室 II 的問法),程式要怎麼改?
// ANSWERS
A1. 人數只在上車時增加,兩個上車點之間只會有人下車。

所以全程的最大人數一定出現在某個上車點、而且是那批人上車之後。每個上車點都「先下、再上、再檢查」,就檢查到了每一個可能的最大值。
A2. 行程是 [from, to),到 to 就下車,座位在 to 那一點已經空出來。

寫成 < 會讓 to == from 的人多坐一站:窮舉錯 3,862 / 33,680,最小反例 [[1,0,1],[1,1,2]], 1 回 false(正解 true)。 概念頁動畫在 5 號點就是這個情況:< 會算出 6 人。
A3. 必須依上車順序處理,「到這一點時誰還在車上」才算得對。

依 to 排序時,晚上車但早下車的行程會先處理,早上車的人還沒算進來:錯 258 組,最小反例 [[1,0,3],[1,1,2],[2,0,1]], 2 回 true(正解 false —— 在 0 號點就已經 3 人)。完全不排序錯 2,932 組。
A4. 每次要問的是「誰最早下車」,所以鍵是 to、取最小的。

存 from:剛上車的人在下一個上車點就被當成「已下車」,錯 14,350 組([[1,0,1],[1,0,1]], 1 回 true,正解 false)。 用最大堆:堆頂是最晚下車的,它沒到站時 while 就停了,早該下車的人卡在下面,錯 2,322 組。
A5. 沒差。

同一個 from 的兩組人都是在那一點上車,先處理哪一組,第二組處理完時人數都一樣;中間那次檢查的人數只會比較小,不會誤判。 第二組處理前的 while 也不會讓第一組下車,因為第一組的 to > from。所以 comparator 只比 t[1] 就夠,不用 tie-break。實測把同 from 的行程隨機打亂順序,30 萬組 0 不一致。
A-App 1. 差分陣列:d[from] += num、d[to] -= num,從 0 掃到 1000 做前綴和,任何時候 > capacity 就 false。

O(n + L),L = 1001。1000 個全程行程實測約 0.003 ms(堆的版本約 0.05 ms)。我的對拍就是用這個當參考解。
A-App 2. 不能直接開 10⁹ 的陣列;要先離散化,或改用 map<int,int> 存差分。

用 map 時 diff[from] += num、diff[to] -= num,照 key 順序累加,O(n log n)。 也可以直接用這頁的堆寫法 —— 它本來就和座標範圍無關。
A-App 3. 不檢查 capacity,改成記錄 passenger 的最大值。

把 if (passenger > capacity) return false; 換成 ans = max(ans, passenger);,最後回傳 ans。 會議室 II 每個會議 num = 1,堆的大小就是同時在開的會議數,也可以直接回傳堆的最大 size。

// ONE-LINE TAKEAWAY
人數只在上車點增加,所以依 from 排序、每個上車點先下(to ≤ from)再上再檢查就夠。堆鍵是 to、最小堆;同一個 from 誰先處理沒差。座標小用差分陣列,座標大用堆或 map。
