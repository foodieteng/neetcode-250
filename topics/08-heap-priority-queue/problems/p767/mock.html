Hmm, let me think about this for a second.

A naive approach would be to try every order of the characters and return the first one with no two equal neighbors. That's up to n! orders — hopeless for n up to 500.

This problem reminds me of greedy scheduling with a max-heap. The letter with the most copies left is the one in the most danger, so I should use it as early and as often as I'm allowed.

I'll take two letters per round: the most common, then the second most common. They come from two different heap entries, so they're different letters. Then I put both back with one less copy.

Here's the plan.

// state
freq = count of each letter
pq   = max-heap of (count, letter)  ← letters still left
ans  = string built so far

// each round
pop (cnt1, ch1), append ch1
if ans ends with two equal letters: return ""  ← seam
if pq not empty: pop (cnt2, ch2), append ch2
push back each one that still has copies left

One: count each letter and push every count with its letter into a max-heap.
Two: each round, pop up to two letters, most common first, and append them.
Three: push back each one that still has copies left.

One thing worth flagging — where can two equal letters end up next to each other?

• Inside one round, never: ch1 and ch2 are different heap entries.
• Between rounds, maybe: the last letter of one round can match the first letter of the next.

So I only check that seam — right after adding ch1, compare the last two characters, and if they match, return "".

There's a trade-off: an up-front maxFreq > (n+1)/2 check also works; the loop check needs no formula, but finds out late. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    string reorganizeString(string s) {
        using P = pair<int, char>;    // (count, char)
        vector<int> freq(26, 0);

        for (char c : s) {
            freq[c - 'a']++;
        }

        priority_queue<P> pq;    // max-heap: higher count first
        for (int i = 0; i < 26; i++) {
            if (freq[i]) pq.push({freq[i], i + 'a'});
        }

        string ans = "";
        while (!pq.empty()) {
            auto [cnt1, ch1] = pq.top(); pq.pop();
            ans += ch1;
            // seam check: ch1 vs the last char of the previous round; starts at size 2
            if (ans.size() >= 2 && ans[ans.size() - 1] == ans[ans.size() - 2]) return "";
            if (!pq.empty()) {
                auto [cnt2, ch2] = pq.top(); pq.pop();    // always ≠ ch1
                ans += ch2;
                if (--cnt2) pq.push({cnt2, ch2});
            }
            if (--cnt1) pq.push({cnt1, ch1});    // push back only after both pops
        }

        return ans;
    }
};

I count the letters, fill a max-heap, then loop: pop the top, append it, check the seam, pop a second letter if one is left, and push back whatever still has copies.

The order matters here — I pop ch2 before I push ch1 back. If I pushed ch1 back first, it could come right back out as ch2, and I'd place the same letter twice in a row.

One thing worth flagging — the seam check is ans.size() >= 2, not > 2. The very first seam is at size 2, so it has to be included. I'll come back to this in the review.

Let me think about complexity here.

Time is O(n log 26), which is O(n): each character is popped once and pushed back at most once, and the heap never holds more than 26 entries, so each operation is constant.

Space is 26 counters plus the heap, so O(1) extra, not counting the output.

In the worst case, n = 500, so at most about 1,000 heap operations. That's tiny.

Could you avoid the check inside the loop?

C

Yes. Check maxFreq > (n+1)/2 once at the start, and return "". After that, the greedy never gets stuck, so the loop needs no check. But the formula must be exactly (n+1)/2 — with n/2, even "a" and "aab" would wrongly return "".

The in-loop check works because of the pairing: inside a round, ch1 ≠ ch2 always, so the only place a repeat can appear is the seam, and one compare per round covers it.

Oh, one more thing — the answer depends on tie-breaking. pair<int, char> puts the larger letter first on equal counts, so "aabb" gives "baba", not "abab". That's fine here, but a test should check validity, not one exact string.
