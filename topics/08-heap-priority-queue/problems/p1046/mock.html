Hmm, let me think about this for a second.

A naive approach would be to sort the stones every turn, take the two biggest, and put the difference back. It's correct, and with only 30 stones it's even fast enough, but it's O(n² log n), re-sorting the whole list just to find two items.

A trap here is to sort only once: the new stone can land anywhere in the order, so appending it at the end gives wrong answers — [1,1,3] returns -1.

This problem reminds me of a repeated take-the-maximum simulation, which is exactly what a max-heap does. The top is always the heaviest stone, and popping and pushing are O(log n) each.

Here's the plan.

// pq = max-heap of all stones still in play
build pq from stones  ← heapify, O(n)
while size > 1:
  x = pop()  // heaviest
  y = pop()  // second heaviest, y <= x
  if x != y → push(x - y)  ← always > 0
return size == 1 ? top() : 0
// each loop: size drops by 1 or 2

One: build a max-heap from all the stones.
Two: while at least two stones remain, pop the heaviest and the second heaviest, and if they differ, push back the difference.
Three: return the last stone, or 0 if the heap is empty.

One thing worth flagging — the loop condition is size > 1, not "not empty". Each turn pops two stones, so with while (!pq.empty()) and a single stone, the second pop() runs on an empty heap — a crash or undefined behavior.

The same goes for the return: [1,1] ends with zero stones, so I must check the size before calling top().

A count array of size 1001 would also work, but with at most 30 stones, the heap is simpler. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int lastStoneWeight(vector<int>& stones) {
        // priority_queue is a max-heap by default; the range constructor heapifies in O(n)
        priority_queue<int> pq(stones.begin(), stones.end());

        while (pq.size() > 1) {          // ① need at least two to smash
            int x = pq.top(); pq.pop();    // heaviest
            int y = pq.top(); pq.pop();    // second heaviest (x ≥ y)

            if (x != y) pq.push(x - y);     // equal weight: both vanish
        }

        return pq.size() ? pq.top() : 0;      // ② there may be no stone left
    }
};

By default, priority_queue in C++ is a max-heap, which is what I want, and building it from the iterator range heapifies in O(n) instead of n pushes. The loop pops two, pushes the difference if they differ, and the return checks the size.

One thing worth flagging — in my code, x is the heavier stone and y is the lighter one. That's the opposite of the names in the problem, so I push x - y, not y - x. Mixing them up pushes a negative number: [1,2] returns -1.

Also, when x == y I push nothing; pushing a 0 would still be correct, just extra rounds.

Let me think about complexity here.

Time is O(n log n): heapify is O(n), each turn does at most two pops and one push, so O(log n), and there are at most n - 1 turns, because each one removes at least one stone. Space is O(n) for the heap, which never grows beyond the starting n stones.

The worst case is when each turn removes only one stone, so n - 1 turns.

Oh, one more thing — this copies the stones into a new heap, so the input is left alone. If changing the input was fine, I could run make_heap on stones itself and save the extra O(n) memory.
