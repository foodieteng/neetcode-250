Hmm, let me think about this for a second.

A naive approach would be to sort the array in descending order and return index k − 1. That's O(n log n). It's correct, but you asked for a way without sorting, and sorting does more work than I need — I only care about one position.

This problem reminds me of the "top k elements" pattern: keep a min-heap of size k. The heap holds the k largest values seen so far, and its top is the smallest of those k — exactly the kth largest.

It feels backwards to use a min-heap to find the largest, but the top is the one I'd throw away next, when a bigger value shows up.

Here's the plan.

// pq = min-heap, holds the k largest so far (dups kept)
for each num → push(num); if size > k → pop()  ← drop smallest
return pq.top()  ← smallest of the k largest
// invariant: after each step, size = min(seen, k)

One: keep a min-heap — in C++, pass greater<int>, since priority_queue is a max-heap by default.
Two: for each number, push it, and if the size goes above k, pop the smallest.
Three: return the top.

One thing worth flagging — the heap must keep duplicates, and priority_queue does, so two 5s take two of the k spots. A set<int> would turn [1,2,2], k = 2 into 1, but the answer is 2.

Also, it's push first, then pop when size > k. With >= k, I'd keep only k − 1 values, and [1], k = 1 would call top() on an empty heap.

There's a trade-off here: quickselect is faster on average but changes the array. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int findKthLargest(vector<int>& nums, int k) {
        // min-heap: top = smallest of the k kept so far
        priority_queue<int, vector<int>, greater<int>> pq;
        for (int num : nums) {
            pq.push(num);                  // duplicates go in too, no dedup
            if (pq.size() > k) pq.pop();   // drop the smallest of k+1
        }

        return pq.top();                  // smallest of the k largest (dups kept)
    }
};

greater<int> makes it a min-heap, so the smallest kept value sits on top. The loop pushes every number, duplicates included, and pops the smallest whenever the heap grows past k. At the end, the top is the answer.

One thing worth flagging — if I forget greater<int>, I get a max-heap with the same logic, and each pop throws away the largest value. With [1,2], k = 1, it returns 1 instead of 2.

Let me think about complexity here.

The time complexity is O(n log k): each number is pushed once, there are exactly n − k pops, and each heap operation is O(log k).

The space complexity is O(k) for the heap, and the input array is not changed.

In the worst-case scenario, k is around n/2: about n/2 pops, each costing about log n — so O(n log n), the same as sorting.

Yes. The heap already avoids a full sort, but there are two faster options.

First, quickselect — in C++, nth_element with greater<int>(), then read nums[k − 1]. It's O(n) on average; the catch is that it reorders the input.

Second, counting. Values only go from -10^4 to 10^4, so I count each value in 20,001 buckets, then scan from the top, subtracting counts until I pass k. That's O(n + range), and duplicates come for free.
