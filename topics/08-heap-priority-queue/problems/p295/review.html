範例 Trace// [2,1,1] · 先大後小

資料流 2 1 1,以我的版本實跑。這組是「沒有 swap」那個錯的最小反例。

// ADD 2 size 0 ≤ 0 → mxH.push(2) mxH [2*] miH [] miH 空,不檢查 median = mxH.top = 2
// ADD 1 size 1 > 0 → miH.push(1) mxH [2*] miH [*1] 2 > 1 → swap mxH [1*] miH [*2] median = (1 + 2) / 2 = 1.5
// ADD 1 size 1 ≤ 1 → mxH.push(1) mxH [1,1*] miH [*2] 1 ≤ 2,不用換 median = mxH.top = 1 // OUTPUT: 2, 1.5, 1
如果沒有 swap:第二步 mxH [2] miH [1] 平均還是 1.5(剛好對),第三步 mxH [1,2*] 回 2.0,正解 1。 錯的順序在第二步就埋下了,第三步才露出來 —— 只看前兩個答案抓不到。

應用題// APPLY IT

App 1. (原題 follow-up)如果所有數字都在 [0, 100],怎麼做得更快?
App 2. (原題 follow-up)如果 99% 的數字在 [0, 100],剩下 1% 可能很大或很小呢?

// ANSWERS
A1. 中位數只和中間那一兩個數有關,而兩個 top 正好就是「小半的最大」和「大半的最小」。

只要「左 ≤ 右」成立,左堆的 top 就是整體排序後第 左.size() 個數,右堆的 top 是下一個。奇數個時左邊多一個,第 ⌈n/2⌉ 個就是中位數;偶數個時兩個 top 剛好是中間兩個。堆內部怎麼排都不影響。
A2. 放之前兩邊已經「左 ≤ 右」,能站錯邊的只有剛放的那一個數 x。

x 進左邊又比右 top 大時,x 一定是左 top;和右 top 對調後,右 top 是右邊最小的,到左邊沒問題,x 比左邊每個都大,到右邊也沒問題。進右邊的情況對稱。 交換是各 pop 一次、push 一次,size 不變,數量那條也還成立。窮舉 488,280 條資料流 0 錯;swap 條件寫成 >= 也 0 錯(相等時多換一次,無害)。
A3. 第一次 add 時 miH 是空的,miH.top() 是對空堆取值 —— 未定義行為。

實測(用會檢查空堆的包裝):長度 1~7 的 21,844 條資料流全部在第一個 addNum 就踩到。真的跑 LeetCode 不一定會當掉,可能讀到垃圾值,更難查。
A4. 不能跳過。② 是精簡版唯一保證「左 ≤ 右」的地方。

新數很小時,送過去的其實是 lo 原本的最大值(例如 add 1 時送的是 5),然後 ③ 又把它送回來 —— 看起來白搬,但程式碼不用比較就能保證正確。 把 ② 拿掉、只依 size 搬:21,844 條錯 11,862 條,最小反例 [1,1,2] → 2.0(正解 1.0)。
A5. 前者先用 int 相加再轉 double,和超過 INT_MAX 就溢位;後者先把一邊轉成 double,加法在 double 裡做。

兩個 INT_MAX:前者實跑得到 -1.0(UBSan 報 signed overflow),後者 2147483647.0。 這題 |num| ≤ 10⁵,和最多 200,000,不會出事;但寫後者不用多想。另外 / 2 寫成整數除法會錯:[2,1] 回 1.0。
A-App 1. 開 cnt[101] 計數陣列:add 是 cnt[num]++,find 從 0 掃到 100 找第 k 個。

add O(1)、find O(101) = O(1)。和排序答案對拍 1,547,912 次查詢 0 不一致。偶數個時要找第 n/2 - 1 和第 n/2 個(從 0 數)再平均。
A-App 2. [0,100] 照樣用計數陣列,範圍外的另外記:小於 0 的個數、大於 100 的個數(必要時各放一個有序結構)。

中位數幾乎一定落在 [0,100] 裡(因為 99% 在那裡),只要把「小於 0 的個數」當作掃描的起點偏移就好;極少數情況中位數落在外面時,才去外面的結構找。
A-App 3. 不夠直接用:priority_queue 只能刪堆頂,刪不掉視窗裡任意一個數。

常見兩種改法:① 兩個堆 + 延遲刪除(用 hash map 記「這個值待刪幾次」,等它浮到堆頂時才真的 pop,size 要另外記有效個數); ② 直接用兩個 multiset,可以 erase(find(x))。這就是 LeetCode 480 Sliding Window Median。
