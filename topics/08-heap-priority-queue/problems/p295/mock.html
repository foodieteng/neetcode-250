Hmm, let me think about this for a sec.

A naive approach would be to keep a vector, and sort a copy on every findMedian. That's O(n log n) per query — at 5 · 104 calls it takes over a minute. Way too slow.

A better naive way keeps the vector sorted and inserts in place. Finding the spot is O(log n), but shifting is O(n), so it's quadratic overall and won't scale.

This problem reminds me of the classic two heaps pattern. A max-heap holds the smaller half, so its top is the biggest of the small numbers. A min-heap holds the bigger half, so its top is the smallest of the big numbers. Those two tops are exactly the middle. Each add is O(log n), and each median is O(1).

Here's the plan.

// state
maxHeap = smaller half  (top = largest small)
minHeap = bigger half   (top = smallest big)

// invariant after every addNum
1. size:  max == min  or  max == min + 1
2. order: maxHeap.top() <= minHeap.top()

// findMedian
odd count  → maxHeap.top()
even count → (maxHeap.top() + minHeap.top()) / 2  ← cast first

One: a max-heap for the smaller half, a min-heap for the bigger half.
Two: after every add, the max-heap has the same size or one more, and its top is no bigger than the min-heap's top.
Three: odd count, return the max-heap top; even count, average both tops, casting first.

One thing worth flagging — there are two rules, not one. A big number in the small half keeps the sizes fine but breaks the tops. So every add must fix both size and order.

There's a trade-off here. I can pick the heap by size and then fix the order, or always route the number through both heaps. The first usually does less work; the second is shorter and easier to prove. I'll write mine first, then the clean one.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. Mine picks the heap by size, then fixes the order with one swap.

class MedianFinder {
public:
    priority_queue<int> mxH;                              // smaller half
    priority_queue<int, vector<int>, greater<int>> miH;   // bigger half

    MedianFinder() {

    }

    void addNum(int num) {
        if (mxH.size() <= miH.size()) {                   // size first
            mxH.push(num);
        } else {
            miH.push(num);
        }

        if (!miH.empty() && mxH.top() > miH.top()) {      // then fix order
            auto a = miH.top(); miH.pop();
            auto b = mxH.top(); mxH.pop();
            mxH.push(a); miH.push(b);                     // size unchanged
        }
    }

    double findMedian() {
        if (mxH.size() > miH.size()) {
            return (double)(mxH.top());
        }

        return double(mxH.top() + miH.top()) / 2.0;       // int add first
    }
};

Ties go to mxH, because of <=, so it's always the same size or one bigger — that's why the odd case reads mxH.top().

One thing worth flagging — why is one swap enough? Before this add, both rules held. Only the new number can be in the wrong half, and the swap moves one value each way, so the sizes stay the same and the order holds again. No loop needed.

Also, the !miH.empty() check is required: on the very first add miH is empty, and calling top() on it is undefined behavior.

Clean always pushes into the small half, passes its top to the big half, then rebalances by size.

class MedianFinder {
    priority_queue<int> lo;                               // smaller half
    priority_queue<int, vector<int>, greater<int>> hi;    // bigger half

public:
    void addNum(int num) {
        lo.push(num);                                     // ① into lo first
        hi.push(lo.top()); lo.pop();                      // ② lo's max to hi → order
        if (hi.size() > lo.size()) {                      // ③ hi bigger → send back → size
            lo.push(hi.top()); hi.pop();
        }
    }

    double findMedian() {
        if (lo.size() > hi.size()) return lo.top();
        return (lo.top() + (double)hi.top()) / 2.0;       // cast to double first
    }
};

Let me walk through that. After lo.push(num), the top of lo is the biggest of the small side plus the new number, so moving it to hi keeps the order rule for free. Then, if hi got bigger, I move its smallest back. Both rules hold with no comparison at all.

One thing worth flagging — the cast. Here I turn one top into a double before the add. If I add two ints first and cast after, that's safe with this problem's range, but INT_MAX + INT_MAX would overflow to -1.0. Casting first gives the right answer.

Let me think about complexity here.

The time complexity is O(log n) per addNum, since each one does a constant number of heap pushes and pops. findMedian is O(1); it only reads tops. The space complexity is O(n) — every number is stored once.

In the worst-case scenario the constants differ. Over 5 · 104 adds, Clean always does 125,000 pushes. Mine does about 100,000 on random or sorted input, but a stream that alternates big and small forces a swap on every add — about 150,000.

Oh, one more thing — if all numbers were in [0, 100], I'd skip heaps and keep a counting array cnt[101], then walk it to find the middle.
