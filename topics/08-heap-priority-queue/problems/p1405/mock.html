Here's the plan.

// state
max-heap of (count, char), only counts > 0

// each step
pop the most frequent ch1
if the last two letters are ch1, ch1  ← blocked
  no other letter left → stop
  else add ONE of the 2nd most frequent ch2
add ch1, push back anything still > 0

// max length (x = largest, y, z = the other two)
min(a+b+c, 2(y+z+1) + y+z)

One: put each non-zero count into a max-heap.
Two: pop the top letter; if the string already ends in two of it, I'm blocked — stop if the heap is empty, else add one runner-up.
Three: add the top letter and push back whatever is left.

One thing worth flagging — why the greedy is right. When blocked, I use the runner-up only once: one letter breaks the run, and saving the rest keeps more separators for later.

Call the biggest count x, the others y and z. y + z separators split x into at most y + z + 1 blocks of two, so the best length is 2(y+z+1) + y+z, capped by a+b+c — and the greedy reaches that cap. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    string longestDiverseString(int a, int b, int c) {
        using P = pair<int, char>;
        priority_queue<P> pq;    // most left on top

        if (a) pq.push({a, 'a'});    // zero counts stay out
        if (b) pq.push({b, 'b'});
        if (c) pq.push({c, 'c'});

        string res = "";

        while (!pq.empty()) {
            auto [cnt1, ch1] = pq.top(); pq.pop();    // the most frequent
            int n = res.size();

            if (n >= 2 && ch1 == res[n - 2] && res[n - 1] == ch1) {
                if (pq.empty()) return res;    // no other letter to insert

                auto [cnt2, ch2] = pq.top(); pq.pop();    // insert one of the 2nd most
                res += ch2;
                if (--cnt2) pq.push({cnt2, ch2});
            }

            res += ch1;    // then the most frequent
            if (--cnt1) pq.push({cnt1, ch1});
        }

        return res;
    }
};

The if (a) guards keep zero counts out of the heap. If a zero got in, --cnt would go negative and never hit zero, so the loop would never end.

Each turn, I pop the top and check for a block. One thing worth flagging — when I'm blocked, I add ch2 and then still add ch1 right after. That's safe: ch2 just broke the run, so ch1 is a fresh run of one, and it's never lost.

Also, if (pq.empty()) return res; is required. When only the blocked letter is left, there's nothing to split it with — without that check, I'd call top() on an empty heap.

The decision happens at step 3: the string is cc and the top is still c, so I'm blocked. On equal counts, pair breaks the tie by letter, so b1 comes out above a1 — I add b, then c. Step 5 does the same with a. At the last step, c is blocked and the heap is empty, so I return "ccbccacc" — length 8, one c unused. The formula agrees: 2·(2+1) + 2 = 8.

Corner cases:

• (0,0,2) → "cc" — checking only res[n-1] == ch1 would wrongly give "c".
• (0,0,3) → "cc" — with n > 2, I'd output "ccc".
• (0,1,3) → "ccbc" — a min-heap only reaches length 3.

Let me think about complexity here.

Time is O(a + b + c). Each loop turn adds at least one letter, and the heap never holds more than 3 items, so each push and pop is O(1). Space is O(1) extra, not counting the output.

In the worst case, (100, 100, 100), the answer has 300 letters, so the loop runs at most about 300 times.

Oh, one more thing — the closed-form length is a quick sanity check for any output. I used it to test the whole input range, 1,030,300 inputs, with 0 wrong.
