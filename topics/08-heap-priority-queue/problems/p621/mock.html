Hmm, let me think about this for a second.

A naive approach would be to try every order of the tasks and pick the shortest schedule. That's factorial time — with up to 104 tasks, it's hopeless.

This problem reminds me of greedy scheduling with a max-heap. The task with the most copies left is the one that can cause idle time, so at each step I run the task with the largest count that is allowed to run.

I'll do it in rounds. One round is n + 1 slots, and inside a round every task runs at most once. So after a round, every task I used has cooled down, and I can put them all back.

Here's the plan.

// pq = max-heap of counts (only counts > 0)
while pq not empty:  // one round = n + 1 slots
  repeat n + 1 times:
    if pq empty and buff empty → stop  ← no trailing idle
    if pq not empty → run top, count − 1, save in buff if > 0
    time++  ← a task slot or an idle slot
  push everything in buff back into pq
// invariant: a task runs at most once per round

One: count the letters and push only the non-zero counts into a max-heap.
Two: each round, for n + 1 slots, pop the biggest count, run it, and park what's left in a small buffer, buff; every slot adds one to time, task or idle.
Three: when the round ends, push the buffer back.

One thing worth flagging — the stop check needs two conditions. If pq is empty but buff isn't, tasks are still cooling, so the slot is a real idle. If both are empty, I stop and don't pad the round. Checking only pq.empty() turns "CC", n = 1 into 2 instead of 3.

And the buffer matters: pushing a task back right away lets it run back-to-back. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int leastInterval(vector<char>& tasks, int n) {
        vector<int> freq(26, 0);
        for (char c : tasks) {
            freq[c - 'A']++;                 // uppercase! 'a' would give −32
        }

        priority_queue<int> pq;
        for (int f : freq) {
            if (f) pq.push(f);              // skip tasks that never appear
        }

        int cycle = n + 1;                     // one round = n+1 slots
        int time = 0;
        vector<int> buff;                    // ran this round, still cooling

        while (!pq.empty()) {
            buff.clear();
            for (int i = 0; i < cycle; i++) {
                if (pq.empty() && buff.empty()) break;   // all done: no trailing idle

                if (!pq.empty()) {
                    int cnt = pq.top(); pq.pop();   // most remaining runs first
                    if (--cnt > 0) buff.push_back(cnt);
                }
                time++;                            // pq empty but buff not → idle slot
            }

            for (int f : buff) {                 // round over, cooled down
                pq.push(f);
            }
        }

        return time;
    }
};

I count each letter, push only the non-zero counts into a max-heap, and each pass of the while loop is one round of n + 1 slots. time++ runs for both a task slot and an idle slot, and the buffer only goes back after the round.

One thing worth flagging — if (f) is not just a speed-up. If I pushed the zeros too, every zero would burn a real slot, and Example 1 would give 30. Same for cycle = n + 1: with cycle = n, n = 0 becomes a round of 0 slots, and the loop never ends.

Let me think about complexity here.

The time complexity is O(len + answer): each slot does at most one heap operation, and the heap never has more than 26 items, so each is O(1).

The space complexity is O(1) — the counts, the heap and the buffer, at most 26 each.

In the worst-case scenario, the answer is about maxF · (n + 1). For 'A' × 104 with n = 100, that's 1,009,900 slots, and it still runs in about 0.6 to 2.4 ms.

I
INTERVIEWER

Can you compute it without simulating?

C
CANDIDATE

Yes. There's a formula:

answer = max(len, (maxF − 1) · (n + 1) + countMax)
// maxF = largest count, countMax = how many labels have it

The most frequent task needs maxF − 1 full frames, each n + 1 slots wide. Then one last row holds only the tasks that also have the max count, so it's countMax slots long.

For Example 1: maxF = 3, countMax = 2, so (3 − 1) · 3 + 2 = 8 — same as the simulation.

Why the max with len? If other tasks overflow the frames, I just widen them, there's no idle at all, and the answer is the number of tasks — like Example 2, where the frames give 4 but the length is 6.

It's O(26 + len) with no heap, and it matched the simulation on all 200,000 random tests. Oh, one more thing — the simulation can still print the actual order.
