Hmm, let me think about this for a sec.

A naive approach would be to simulate, and each time the CPU is free, scan all the tasks that have arrived and aren't done, and pick the best one. That's correct, but it's O(n) per pick, so O(n2) in total. With 105 tasks, that's around 1010. Too slow.

This problem reminds me of an event-driven simulation with a heap. Two parts:

• Tasks arrive in enqueue-time order, so I sort the indices by enqueue time and walk them with one pointer.
• Among the tasks that have arrived, I need the best one quickly — that's a min-heap keyed by (processing time, index).

Each task goes into the heap once and comes out once, so this is O(n log n).

Here's the plan.

// state
arr = indices sorted by enqueue time
i   = next task in arr that hasn't arrived yet
pq  = min-heap of (proc, index)  ← arrived, not run
t   = current time (long long)

// loop while tasks are left
if pq is empty: t = max(t, enqueue of arr[i])  ← jump
push every arr[i] with enqueue <= t
pop the best → run it: t += proc, add to ans

One: sort the indices by enqueue time.
Two: if the heap is empty, jump the clock to the next arrival, then push every task that has arrived.
Three: pop the best task, run it, and add its time to the clock.

One thing worth flagging — the heap key needs both parts. Processing time first: shorter wins. Index second: a heap is not stable, so I can't rely on push order to break ties; it has to be in the comparator.

And the idle jump must be a max. The clock must never go backwards.

There's a trade-off here. I could tick the clock one step at a time. Same answer, but a gap of 109 would mean 109 loop steps. The jump takes one.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> getOrder(vector<vector<int>>& tasks) {
        int n = tasks.size();
        vector<int> arr(n);
        iota(arr.begin(), arr.end(), 0);
        sort(arr.begin(), arr.end(), [&](int a, int b) {
            return tasks[a][0] < tasks[b][0];             // sort by arrival
        });

        auto cmp = [&](int a, int b) {                    // ① int params
            if (tasks[a][1] != tasks[b][1]) return tasks[a][1] > tasks[b][1];
            return a > b;                                 // ③ tie: smaller index
        };
        priority_queue<int, vector<int>, decltype(cmp)> pq(cmp);

        long long t = 0;                                  // ④ up to ~10¹⁴
        int i = 0;
        vector<int> ans;

        while (i < n || !pq.empty()) {
            if (pq.empty()) {
                t = max(t, (long long)tasks[arr[i]][0]);  // ② jump forward only
            }
            while (i < n && t >= tasks[arr[i]][0]) {
                pq.push(arr[i]); i++;                     // push all arrived
            }
            int idx = pq.top(); pq.pop();                 // heap non-empty here
            t += tasks[idx][1];
            ans.push_back(idx);
        }
        return ans;
    }
};

The heap stores indices, not copies of the tasks, and the comparator looks the task up through the [&] capture. In a priority_queue, a "greater" comparator puts the smallest on top. So > on processing time, then a > b on the index, gives shortest first, then smallest index.

One thing worth flagging — the inner while uses t >= enqueue, not >. Right after the idle jump, t equals the next enqueue time exactly. With a strict >, nothing gets pushed, and pq.top() runs on an empty heap. That breaks on every input.

Let me think about complexity here.

The time complexity is O(n log n). The sort is O(n log n), and each task is pushed once and popped once, at O(log n) each. The outer loop runs exactly n times, because every pass pops one task, so empty time costs nothing. The space complexity is O(n), for arr, the heap, and the answer.

In the worst-case scenario all tasks arrive at time 1, so the heap holds all 105 at once — that runs in about 43 ms, and a random input in about 60 ms.

One note on the clock: an int would overflow, and the sanitizer flags it, yet the output never changes. To overflow, t must pass about 1.147 · 109, and by then every task is already in the heap. It's still undefined behavior, so it's a long long.
