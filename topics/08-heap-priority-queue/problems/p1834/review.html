PART A · 觀念題// 5 題 × 10 分

第 1 題10 分
迴圈開頭「堆是空的」時,CPU 一定是閒著的嗎?為什麼要寫 t = max(t, …) 而不是直接 t = tasks[arr[i]][0]?
解答與說明 · ANSWER▾
不一定。堆空有兩種情況:CPU 真的閒著(下一個還沒到),或剛做完一個任務、候選剛好用完(下一個早就到了)。

第二種情況下 t 已經比下一個到達時間大,直接 t = 到達時間 會把時間拉回過去。max 讓第一種情況往前跳、第二種情況不動。
範例 1:#0 在 t=3 做完、堆空,原寫法把 t 拉回 2,#2(t=3 到)沒機會進堆比,先做了長的 #1 → [0,1,2,3],正解 [0,2,3,1]。 窮舉錯 6,372 / 66,429。
第 2 題10 分
比較子已經比了處理時間,為什麼還要比 index?官方範例 2 為什麼抓不到這個錯?
解答與說明 · ANSWER▾
題目規定「一樣短選 index 小的」,而 priority_queue 不保證相等元素的出場順序。

最小反例 [[1,1],[2,1],[1,1]]:t=2 時 #1、#2 都在堆裡、處理時間都是 1,要選 #1,沒比 index 會選到 #2 → [0,2,1]。窮舉錯 32,005 / 66,429。
範例 2 的五個處理時間 10、12、5、4、2 全都不同,根本沒有「一樣長」的情況,所以抓不到。
第 3 題10 分
int t 會溢位,但實測答案從來沒錯。為什麼?那為什麼還要改成 long long?
解答與說明 · ANSWER▾
溢位那一刻,所有任務都已經在堆裡,t 之後只會被加、不會再被拿去和到達時間比。

要溢位,t + 處理時間 > INT_MAX,而處理時間 ≤ 10⁹,所以 t 至少 ≈ 1.147×10⁹,已經大於任何到達時間(≤ 10⁹)—— 前面的 push 迴圈早就把所有任務推進去了。實測 300 組隨機大資料,第一次溢位時全部 i == n。
但這是「剛好」:有號整數溢位是未定義行為(UBSan 會報),編譯器可以假設它不發生;而且題目上限一改(見 第 9 題)就會真的錯。
第 4 題10 分
比較子寫成 [&](const auto* v1, const auto& v2) 為什麼編譯不過?
解答與說明 · ANSWER▾
const auto* v1 要求參數是「指標」,但堆裡放的是 int(任務的 index)。

priority_queue 會用兩個 int(堆裡的元素)呼叫比較子,auto* 沒辦法從 int 推導出來: mismatched types 'const auto:28*' and 'int'。 另外 tasks[v1] 用指標當索引本來也不合法。改成 [&](int a, int b)。
第 5 題10 分
把 push 的條件寫成 t > 到達時間(嚴格大於)會怎樣?
解答與說明 · ANSWER▾
所有測資都會壞 —— 而且是崩潰。

堆空時 t 跳到下一個任務的到達時間,但 t > 到達時間 不成立,那個任務推不進去,堆還是空的,接著 pq.top() 對空堆取值。 實測窮舉 66,429 組全錯,-O2 下 segfault。題目說「到達就能做」,所以是 >=。

PART B · 手走模擬// 1 題 × 10 分

第 6 題10 分
拿一張紙,照程式手走 範例 2 · 同時到達:逐步寫出關鍵變數的變化,最後回傳什麼?決定結果的是哪一步?
解答與說明 · ANSWER▾

[[7,10],[7,12],[7,5],[7,4],[7,2]]:五個任務全部在 t=7 到達,之後就是單純照處理時間由短到長。以修正版實跑。

// STEP 1: 閒置 → 跳到第一個到達時間 t = 0,堆空 → t = max(0, 7) = 7 push #0..#4 → 堆 (2,4)(4,3)(5,2)(10,0)(12,1)
// STEP 2: 依序做 做 #4(2) t = 9 做 #3(4) t = 13 做 #2(5) t = 18 做 #0(10) t = 28 做 #1(12) t = 40
// STEP 3: 結果 // OUTPUT: [4,3,2,0,1]
這組為什麼連我的原始寫法都會過:只有一次閒置(t 從 0 跳到 7,本來就該跳),之後堆從來沒空過 → ② 不會觸發; 五個處理時間全都不同 → ③ 不會觸發。範例 2 對 ② 和 ③ 都是「盲點」,範例 1 才抓得到 ②。

PART C · 應用題// 3 題 × 13–14 分

第 7 題13 分
改成有 k 顆 CPU(LeetCode 1882 Process Tasks Using Servers 類似),每顆閒下來就拿最短的任務。要多加什麼資料結構?
解答與說明 · ANSWER▾
再加一個「CPU 什麼時候有空」的最小堆。

除了任務的最小堆(處理時間, index),再用一個最小堆存每顆 CPU 的 (空閒時刻, CPU 編號)。 每次取最早空閒的 CPU,把 t 推進到 max(它的空閒時刻, 下一個到達時間)(一樣只往前),把到了的任務推進任務堆,指派堆頂任務給它,更新它的空閒時刻再放回去。 「時間只往前、用 max 跳」這一條原則完全一樣。
第 8 題13 分
改成「CPU 可以被搶占」:有更短的任務到達時,可以暫停目前的任務先做短的(最短剩餘時間優先,SRTF)。模擬要怎麼改?
解答與說明 · ANSWER▾
把「做完一個任務」拆成「做到下一個事件為止」。

堆裡存 (剩餘時間, index)。每次取堆頂,但只做到 min(t + 剩餘時間, 下一個到達時間): 如果中途有新任務到達,先把目前任務的剩餘時間扣掉、放回堆,再把新任務推進去重新比。 這時事件數最多是「完成 n 次 + 到達 n 次」,仍然 O(n log n)。
第 9 題14 分
題目的 enqueueTime 改成可以到 2×10⁹(超過 int),哪些地方要改?「int 溢位剛好不影響」還成立嗎?
解答與說明 · ANSWER▾
tasks 本身要改成 long long(或至少讀進來的到達時間),而且 第 3 題 的「剛好沒事」就不成立了。

到達時間可以大於 INT_MAX − 10⁹,int t 可能在還有任務沒進堆時就溢位成負數 —— t >= 到達時間 變成假,該推的任務推不進來,答案就錯了。 這就是為什麼一開始就該用 long long:不要依賴「目前的上限剛好讓溢位無害」。
