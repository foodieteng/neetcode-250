範例 Trace// 動畫那組 · 3 人 12 則

user 1 追蹤 2、3;三人輪流發文,時間 1~12(tweetId:user 1 是 11~14、user 2 是 21~24、user 3 是 31~34)。 以下是 feed(1) 實跑印出的過程,tN:id 表示時間 N 的那則推文,堆依時間列出。

// STEP 1: 自己的 4 則,再 user 3 的 4 則(unordered_set 實際先走 3) push t2:11, t5:12, t8:13, t11:14 size 4 push t3:31, t6:32, t9:33, t12:34 size 8
// STEP 2: user 2 的 4 則,兩次淘汰 push t1:21, t4:22 size 10(剛好滿) push t7:23 → size 11 > 10 → pop t1:21 ← 全場最舊 push t10:24 → size 11 > 10 → pop t2:11 ← user 1 自己最舊的一則 堆:t3 … t12(10 則)
// STEP 3: 倒出 + reverse 倒出(舊 → 新):[31,22,12,32,23,13,33,24,14,34] reverse :[34,14,24,33,13,23,32,12,22,31] // OUTPUT: [34,14,24,33,13,23,32,12,22,31] —— 時間 12 到 3
推進的順序是 user 1 → 3 → 2,完全不是時間順序,而且被淘汰的 t=1 是最後一批才進來的。 但堆只在乎「目前手上最舊的是誰」,所以最後剩下的一定是時間最大的 10 則。

應用題// APPLY IT

App 1. 改寫 getNewsFeed,讓每個人最多只看最後 10 則,並且在確定更舊的推文不可能進前 10 時提早停。
App 2. 另一種做法是多路合併:堆裡每個人只放一則(他最新的),每 pop 一則就把那個人的下一則放進去。複雜度是多少?和 App 1 比如何?
App 3. 如果題目保證 tweetId 一定照發文時間遞增,程式可以怎麼簡化?
// ANSWERS
A1. 要留下時間最大的 10 則,就得能隨時踢掉手上最舊的 —— 最小堆的 top 就是它。

和 703 同一個道理:留大的用最小堆。 倒出來的時候,最小堆先吐最舊的,所以 ans 是舊→新,題目要新→舊,就得 reverse。
少了 reverse:窮舉錯 3,506 條,post(1,1)、post(1,2)、feed(1) → [1,2](正解 [2,1])。 改用最大堆又會變成留下最舊的 10 則:12 則時回 [1..10]。
A2. 題目只保證 tweetId 不重複,沒保證照時間遞增。

反例:post(1, 2)、post(1, 1)、feed(1) —— 後發的是 1,正解 [1, 2];用 tweetId 比新舊會回 [2, 1]。 隨機 20,000 個 session 裡錯 18,169 個。全域 ++ts 每發一則加 1,才是真正的先後。
A3. follow 那一行必要;unfollow 那一行可有可無。

getNewsFeed 先加自己的推文,再加每個追蹤對象的。如果 follow(1,1) 讓 1 出現在 followG[1], 自己的推文會被加兩次 → [1,1]。窮舉錯 5,024 條。
unfollow 的那一行:因為 follow 已經擋掉,自己從來不會在集合裡,erase 一個不存在的元素什麼事都不會發生 —— 實測拿掉它 0 錯。
A4. 大小 k 的最小堆,不管輸入順序,最後留下的一定是最大的 k 個。

被 pop 的那則,當下堆裡已經有 10 則比它新 —— 之後不管再來什麼,它都不可能擠回前 10。 所以推進的順序只影響「中間過程」,不影響結果。這和 215 對已排序輸入的觀察一樣。
實測和暴力解逐字比對 789,724 次 feed,0 不一致。
A5. 追蹤很多人、而且歷史很長的時候 —— 每次 feed 都要把所有相關推文重新推一遍堆。

刻意構造:user 1 追蹤 499 人、全站 10,001 則推文,接著 19,500 次 feed(1): 每次推 10,001 則,共 195,019,500 次 push,約 2.4 ~ 2.6 秒。
浪費在哪:每個人的推文本來就照時間排好,一個人最多只可能貢獻 10 則,更舊的根本不用看。 只看最後 10 則的版本同一組測資約 59 ~ 69 ms(App 1)。
A-App 1. 從每個人的 vector 尾巴往前拿,最多 10 則;堆滿了而且這則比堆頂還舊,就提早停。

vector<int> getNewsFeed(int userId) {
    auto cmp = [](const auto& p1, const auto& p2) { return p1.first > p2.first; };
    priority_queue<pair<int, int>, vector<pair<int, int>>, decltype(cmp)> pq(cmp);

    auto addUser = [&](int user) {
        auto it = tweets.find(user);                 // find:不會建出空的 entry
        if (it == tweets.end()) return;
        auto& list = it->second;
        for (int i = (int)list.size() - 1, taken = 0; i >= 0 && taken < 10; i--, taken++) {
            if (pq.size() == 10 && list[i].first < pq.top().first) break;  // 更舊的都進不了
            pq.push(list[i]);
            if (pq.size() > 10) pq.pop();
        }
    };

    addUser(userId);
    auto it = followG.find(userId);
    if (it != followG.end())
        for (int followeeId : it->second) addUser(followeeId);

    vector<int> ans;
    while (!pq.empty()) { ans.push_back(pq.top().second); pq.pop(); }
    reverse(ans.begin(), ans.end());
    return ans;
}
和暴力解對拍 20,000 個隨機 session、749,831 次 feed,0 不一致;-Wall -Wextra -Wshadow 零警告。 提早停的理由:同一個人的推文由新往舊走,這則比堆頂(手上最舊的)還舊,它之前的只會更舊,全部都進不了前 10。
A-App 2. 複雜度 O(F + 10 log F)(F = 追蹤人數 + 1,先用 make_heap 一次建好;逐一 push 則是 O(F log F)):每人先放最新的一則,之後只 pop 10 次、每次補一則。

這次要用最大堆(每次拿全場最新的),堆裡存「(時間, tweetId, 哪個人, 在他 vector 的位置)」。 pop 出一則就把同一個人的前一則(更舊的)補進去,pop 滿 10 次就停,而且 pop 出來就已經是新→舊,不用 reverse。
和 App 1 比:App 1 每人最多推 10 則,O(F · 10 · log 10);多路合併只推 F + 10 次,追蹤人數多時更省。 這就是「合併 k 個已排序串列」(LeetCode 23)的做法。
A-App 3. 可以省掉 ts,直接用 tweetId 當時間。

tweets[user] 只存 tweetId,比較子改成比 tweetId,其他完全不變。 但這題沒有這個保證 —— A2 的反例 post(1,2)、post(1,1) 就會出錯。 設計題裡「編號」和「時間」是兩件事,除非題目明說,不要混在一起。
