Hmm, let me think about this for a second.

A naive approach would be to keep one global list of all tweets. For a feed, I filter it down to me and the people I follow, sort by time, and take the first 10. It's correct, but every feed call touches every tweet ever posted, and sorts them.

This problem reminds me of the top-k pattern. I only need the 10 newest, so I don't sort everything. I keep a min-heap of size 10, keyed by time. The top is the oldest of the 10 I'm keeping, so when a newer tweet pushes the heap over 10, I pop the top and throw away the oldest.

It's also a merge of sorted lists, since each person's tweets are already sorted by time. I'll come back to that when we talk about cost.

Here's the plan.

// state
followG[u] = set of users u follows  ← never u itself
tweets[u]  = list of (time, tweetId), oldest first
ts         = global clock, ++ on every post

// getNewsFeed(u)
pq = min-heap by time
for each tweet of u and of everyone in followG[u]:
  push it; if size > 10 → pop  ← drops the oldest
pop all into ans  // comes out oldest first
reverse(ans)  ← newest first

One: a hash map of sets for who follows whom, so follow and unfollow are O(1) and a repeated follow can't add a duplicate.
Two: each user's tweets as (time, tweetId) pairs from a global clock.
Three: for a feed, push my tweets and every followee's tweets into a min-heap, pop when it goes over 10, then pop everything and reverse.

One thing worth flagging — the heap direction. A min-heap throws out the oldest, so the 10 newest stay. A max-heap with the same pop throws out the newest: with 12 posts, it keeps tweets 1 to 10 instead of 12 down to 3. Side effect: a min-heap pops oldest first, so I have to reverse at the end.

There's a trade-off here: it pushes every old tweet. Does this approach sound good, or would you rather I think of another way?

class Twitter {
public:
    unordered_map<int, unordered_set<int>> followG;          // who follows whom
    unordered_map<int, vector<pair<int, int>>> tweets;    // user → (time, tweetId)
    int ts = 0;                                            // global timestamp

    Twitter() {

    }

    void postTweet(int userId, int tweetId) {
        tweets[userId].push_back({++ts, tweetId});
    }

    vector<int> getNewsFeed(int userId) {
        auto cmp = [&](const auto& p1, const auto& p2) {
            return p1.first > p2.first;                    // min-heap: top = oldest
        };

        priority_queue<pair<int, int>, vector<pair<int, int>>, decltype(cmp)> pq(cmp);

        for (auto& [ts, tweetId] : tweets[userId]) {
            pq.push({ts, tweetId});
            if (pq.size() > 10) pq.pop();               // drop the oldest
        }

        for (auto& followeeId : followG[userId]) {
            for (auto& [ts, tweetId] : tweets[followeeId]) {
                pq.push({ts, tweetId});
                if (pq.size() > 10) pq.pop();
            }
        }

        vector<int> ans;
        while (!pq.empty()) {
            ans.push_back(pq.top().second); pq.pop();   // old → new
        }
        reverse(ans.begin(), ans.end());                   // new → old
        return ans;
    }

    void follow(int followerId, int followeeId) {
        if (followerId == followeeId) return;              // own tweets are already added
        followG[followerId].insert(followeeId);
    }

    void unfollow(int followerId, int followeeId) {
        if (followerId == followeeId) return;
        followG[followerId].erase(followeeId);
    }
};

postTweet stamps the tweet with ++ts, so every stamp is unique. The comparator returns p1.first > p2.first, which in a priority_queue means a min-heap, so the oldest time sits on top. The feed pushes my tweets, then each followee's, popping past 10, then drains and reverses.

One thing worth flagging — the guard in follow is a correctness fix, not a nice-to-have. Without it, follow(1,1), post(1,1), feed(1) gives [1,1]: the first loop adds my tweet, and the followee loop adds it again. The guard in unfollow is harmless either way, since I can never be in my own set.

The key row is the second feed: my own tweet 5 has time 1, and 6 has time 2. The min-heap pops 5 first since it's older, so ans is [5,6] before the reverse, and [6,5] after. That matches.

The example never has more than 10 tweets, so it doesn't test eviction. If user 1 posts twelve tweets, 101 to 112:

pushheap (top = oldest)pop
t=1 … t=10123 … 10— (size 10)
t=1123 … 11(1,101)
t=1234 … 12(2,102)
drain[103, 104, …, 112] → reverse
result[112, 111, …, 103]

Each time the heap hits 11, the oldest is on top and gets dropped, so the 10 newest survive.

Corner cases:

• No tweets and no follows → [].
• Self-follow is a no-op → [1], not [1,1].
• Out-of-order IDs, post(1,2), post(1,1) → [1,2]: the clock decides.
• Exactly 10 tweets: nothing is popped.

And against the brute force — 752,080 random feeds, 37,644 large-session feeds, and 271,452 exhaustive sequences — 0 mismatches.

Let me think about complexity here.

The time complexity is O(1) average for postTweet, follow, and unfollow. A feed is O(T · log 10), where T is the total number of tweets of the user and everyone they follow; the heap never holds more than 11 items.

The space complexity is O(total tweets + total follow edges), plus O(10) for the heap per feed call.

In the worst-case scenario, T is every tweet in the system. The log is small, but T is not.

I
INTERVIEWER

What if a user follows hundreds of people with long histories?

C
CANDIDATE

That's exactly the weak spot. Within the constraints: user 1 follows 499 users, there are 10,001 posts round-robin, then 19,500 calls to feed(1). That's 19,500 × 10,001 = 195,019,500 heap pushes, and my code takes about 2.4 to 2.6 s.

The fix uses the fact that each list is already sorted by time: only the last 10 tweets of any one person can ever make the feed.

// optimized feed
for each person p (me + followees):
  walk tweets[p] backwards, at most 10
  stop early if older than the heap's oldest (size 10)

That takes about 59 to 69 ms, with identical output.

The classic version is a k-way merge: one pointer per person in a max-heap, pop 10 times, about O(F + 10 log F) per feed.

Oh, one more thing — operator[] on an unordered_map creates empty entries; find() avoids that.
