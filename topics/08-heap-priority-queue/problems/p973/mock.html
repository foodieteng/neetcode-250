Hmm, let me think about this for a second.

A naive approach would be to sort all points by squared distance and take the first k. That's O(n log n), and with n = 104 it's honestly fast enough, but it sorts all n points even when I only need a few.

This problem reminds me of top-k selection with a bounded heap. I keep a max-heap of size k, ordered by distance. It holds the k closest points seen so far, and its top is the farthest of those k — the gatekeeper. When a new point comes in and the heap gets too big, the farthest one is kicked out.

It feels backwards to use a max-heap to find the closest points, but I want quick access to the one I'd throw away next.

Here's the plan.

// d(p) = x² + y² (no sqrt, same order)
// pq = max-heap by d, holds the k closest so far
for each p → push(p); if size > k → pop()  ← drop farthest
drain pq into ans  ← farthest first, any order is OK
// invariant: after each step, size = min(seen, k)

One: compare points by squared distance with <, so the farthest point sits on top.
Two: for each point, push it, and if the heap holds more than k, pop the farthest.
Three: drain the heap into the answer.

One thing worth flagging — push first, then pop, and the check is size > k, not >= k. After the push, the heap briefly has k + 1 points, so the new point competes fairly. >= would pop one too many: [[-2,-2]] with k = 1 would return [].

There's a trade-off here: sorting is O(n log n), and quickselect is O(n) on average, but the heap is O(n log k) with O(k) memory, and it works on a stream. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> kClosest(vector<vector<int>>& points, int k) {
        // cmp(p1, p2) true = p1 is closer than p2 → lower priority → farthest on top (max-heap)
        auto cmp = [&](const auto& p1, const auto& p2) {
            return (p1[0] * p1[0] + p1[1] * p1[1]) < (p2[0] * p2[0] + p2[1] * p2[1]);
        };
        priority_queue<vector<int>, vector<vector<int>>, decltype(cmp)> pq(cmp);

        for (const auto& p : points) {
            pq.push(p);
            if (pq.size() > k) pq.pop();   // kick out the farthest of the k+1
        }

        vector<vector<int>> ans;
        while (!pq.empty()) {
            ans.push_back(pq.top()); pq.pop();   // farthest comes out first; any order is accepted
        }
        return ans;
    }
};

The lambda compares squared distances; with <, the farthest point sits on top. The loop is "push, then pop if too big", and at the end I drain the heap into ans.

One thing worth flagging — with decltype(cmp), I must pass cmp into the constructor: pq(cmp). If I just write pq;, it fails to compile in C++17, because a lambda type has no default constructor. C++20 allows it only for a lambda with an empty capture []. My [&] still fails there, even though it captures nothing, so [] would be the cleaner choice.

Corner cases:

• k = n never pops, so every point comes back.
• Corner points at the max range, like [10000,10000], square to 200,000,000 — no overflow.
• A flipped comparator > makes a min-heap that pops the closest.
• Manhattan distance |x| + |y| picks the wrong point when two points tie on it, like [[-1,-1],[0,-2]].

Let me think about complexity here.

Time is O(n log k): each point is pushed once, there are exactly n − k pops in the loop, and each heap operation is O(log k). The drain adds k more pops, O(k log k). Space is O(k) for the heap, plus the output; one small cost is that each push copies a vector<int>.

In the worst case, k is close to n, so log k is close to log n and the heap is no better than sorting. With n = 104, the heap took about 0.24 ms at k = 1, but about 1.9 ms at k = n.

Honestly, no. If I have all the points up front, nth_element is the fastest. It's quickselect, O(n) on average, and it moves the k closest points to the front, in no particular order — which is all this problem asks for. In my timing, it took about a quarter of a millisecond, and the heap only beats sorting when k is small; at k = 5000 it's slower than just sorting.

The heap's real strength is different: it uses only O(k) memory, and it works on a stream. If points keep coming in, I can't run quickselect on data I haven't seen yet.

Oh, one more thing — the output comes out farthest first. That's fine here, but if someone wanted closest first, I'd just reverse ans, in O(k).
