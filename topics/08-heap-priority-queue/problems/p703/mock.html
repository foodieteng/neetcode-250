Hmm, let me think about this for a second.

A naive approach would be to keep every number, and on each add, sort from big to small and take index k - 1. It's correct, but each call sorts up to 20,000 numbers — with 104 nums and 104 adds, that takes about 1.1 s. Too slow.

This problem reminds me of top-k selection with a bounded min-heap. The heap holds the k largest numbers seen so far, and its top is the smallest of them — exactly the kth largest.

It sounds backwards to use a min-heap to find a largest element. But the top is a "gatekeeper": any new number smaller than it can't be in the top k, so it gets kicked out right away.

CANDIDATE

Here's the plan.

// pq = min-heap holding the k largest seen so far
ctor:     for each num → push(num); if size > k → pop()
add(val): push(val);               if size > k → pop()
          return top()  ← kth largest
// after ctor: size = min(len(nums), k)
// from the first add on: size == k exactly

One: keep a min-heap, and store k for add.
Two: in the constructor and in add, push the number, and if the heap grows past k, pop the smallest.
Three: add returns the top.

One thing worth flagging — push first, then pop. Pushing first lets the new number compete fairly; popping first throws away an old number before I even look at the new one. With k = 1 and adds of 2 then 1, pop-first returns [2,1], but the right answer is [2,2].

The constructor must trim too: with k = 1, nums = [1,1], and add 2, the untrimmed version returns 1 instead of 2.

A sorted list would shift elements, O(n) per add; the heap is O(log k) per add, O(k) memory. Does this approach sound good, or would you rather I think of another way?

class KthLargest {
public:
    // min-heap: greater puts the smallest on top — top = smallest of the top k = kth largest
    priority_queue<int, vector<int>, greater<int>> pq;
    int size;
    KthLargest(int k, vector<int>& nums) {
        size = k;
        for (int num : nums) {
            pq.push(num);
            if (pq.size() > k) {
                pq.pop();          // pushed out of the top k, never comes back
            }
        }
    }

    int add(int val) {
        pq.push(val);              // push first: val gets one fair comparison with the gatekeeper
        if (pq.size() > size) {
            pq.pop();              // drops the smallest of the k+1
        }
        return pq.top();
    }
};

The greater<int> comparator turns the priority_queue into a min-heap — by default, C++ gives a max-heap. The constructor and add share the same step: push, then pop if the heap is bigger than k. Then add returns the top.

One thing worth flagging — pq.top() on an empty heap is undefined behavior, so the heap must never be empty there. After the constructor, the size is min(len(nums), k), so at least k - 1. The first add brings it to exactly k, and it stays k from then on. Since k >= 1, the top always exists.

Corner cases:

• k = 1, nums = [], adds 1 then 2 → [1,2] — a max-heap by mistake gives [1,1].
• k = 2, nums = [1], add 2 → 1; an "only push if val > top" shortcut wrongly returns 2.
• >= in the pop check empties the heap when k = 1, so top() crashes.

Let me think about complexity here.

Time is O((n + q) log k), where n is the length of nums and q is the number of add calls. Each number is pushed once and popped at most once, and each heap operation is O(log k). Space is O(k); the heap never holds more than k + 1 numbers.

In the worst case, with 104 nums, 104 adds and k = 5000, the heap takes about 0.9 ms, versus about 1.1 s for sort-every-add.

Oh, one more thing — reading the answer is O(1), so if a system asked for the kth largest far more often than it added numbers, this design already fits.
