A naive approach would be to keep every word in a list. Then startsWith has to check every stored word, so the cost grows with the number of words, not with the length of the prefix. A hash set makes search fast, but it can't answer prefix questions at all.

This problem reminds me of the prefix tree behind autocomplete. Words that share a start should share the same path. Each edge is one letter, and each node is one prefix, so every call costs only the length of its string.

Here's the plan.

// node = one prefix; child[c-'a'] = that prefix + c
TrieNode { child[26] = all null; isWord = false }

insert(w): cur = root
  for c in w: if child is null → create it; step down
  cur.isWord = true

search(w, prefix): cur = root
  for c in w: if child is null → return false; step down
  return prefix ? true : cur.isWord

startsWith(p) = search(p, true)

One: each node has 26 child slots, all null, plus an isWord flag.
Two: insert walks the word, creates a child only when the slot is empty, then marks the last node.
Three: search does the same walk and fails if it falls off; at the end, prefix mode returns true and word mode returns isWord. startsWith just calls search with prefix = true.

The flag matters because a node existing only means some word passes through it.

One thing worth flagging — the nullptr check in insert is a correctness rule, not a speed trick. If I always wrote cur->child[i] = new TrieNode(), inserting "app" after "apple" would replace the old path and cut off the "l" and "e" nodes, so search("apple") would return false.

Does this approach sound good, or would you rather I think of another way?

class TrieNode {
public:
    TrieNode* child[26] = { nullptr };   // ① all 26 slots start as nullptr
    bool isWord = false;                 // ② does a word end here?
};

class Trie {
private:
    TrieNode* root;

public:
    Trie() {
        root = new TrieNode();
    }

    void insert(string word) {
        TrieNode* cur = root;
        for (char c : word) {
            int i = c - 'a';
            if (cur->child[i] == nullptr) {    // ③ create only if missing, else reuse
                cur->child[i] = new TrieNode();
            }
            cur = cur->child[i];
        }
        cur->isWord = true;                  // ④ mark the end
    }

    bool search(string word, bool prefix = false) {
        TrieNode* cur = root;
        for (char &c : word) {
            int i = c - 'a';
            if (cur->child[i] == nullptr) {
                return false;                // fell off midway
            }
            cur = cur->child[i];
        }
        if (prefix) return true;             // ⑤ prefix: reaching the end is enough
        return cur->isWord;                  // ⑥ whole word: also needs isWord
    }

    bool startsWith(string prefix) {
        return search(prefix, true);
    }
};

A TrieNode holds 26 child pointers, all starting as nullptr, and an isWord flag. insert creates a child only when its slot is null, steps down, and marks the last node. search returns false the moment a child is missing; after the loop it returns true in prefix mode, otherwise isWord.

One thing worth flagging — startsWith reuses search through a default argument, bool prefix = false. LeetCode only calls search(word) with one argument, so the public behavior stays the same. The only difference is the last line: in prefix mode I return true before I look at isWord.

Let me think about complexity here.

Time is O(L) per call, for insert, search and startsWith, where L is the string length. It doesn't depend on how many words are stored.

Space is O(total inserted chars × 26) pointers. In the worst case no words share a prefix, so every character makes a new node, and each node carries 26 slots.

Oh, one more thing — there's no destructor, so the nodes are never freed. That's fine on LeetCode. In real code I'd add a destructor that deletes children recursively, or keep the nodes in unique_ptr or a pool.
