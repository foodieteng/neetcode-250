Hmm, let me think about this for a sec.

A naive approach would be to keep every word in a list. Then each search compares the pattern with every stored word, character by character, so the cost grows with the number of words stored.

This problem reminds me of a prefix tree searched with depth-first backtracking. Words that share a start share one path, and a normal letter just follows one child. The new part is the dot. At a dot, I don't know which child to take, so I try all of them, and back up when a branch fails. That's a DFS over the trie.

P — plan
C
CANDIDATE

Here's the plan.

// plain trie insert; only search changes
addWord(w): cur = root
  for c in w: if child is null → create it; step down
  cur.isWord = true

dfs(w, idx, node):
  if node is null → return false
  if idx == len(w) → return node.isWord
  if w[idx] is a letter → dfs(w, idx+1, that child)
  if w[idx] is '.' → try all 26 children, stop at first true

search(w) = dfs(w, 0, root)

One: addWord is a normal trie insert — create a child only when it's missing, then mark the end.
Two: search runs a DFS with idx into the pattern and node in the trie, moving down together.
Three: in the DFS, a null node fails, the end of the pattern returns isWord, a letter follows one child, and a dot tries all 26 children and stops at the first true.

One thing worth flagging — the line if (!node) return false; at the top of dfs does two jobs. It catches a letter with no child, like "p" in "pad", and the many null children the dot loop passes in. Without it, the next line reads node->isWord from a null pointer — a correctness rule, not a style choice.

Does this approach sound good, or would you rather I think of another way?

class TrieNode {
public:
    TrieNode* child[26] = { nullptr };
    bool isWord = false;
};

class WordDictionary {
public:
    TrieNode* root;

    WordDictionary() {
        root = new TrieNode();
    }

    void addWord(string word) {                          // same as a plain trie insert
        TrieNode *cur = root;

        for (char &c : word) {
            int i = c - 'a';
            if (!cur->child[i]) cur->child[i] = new TrieNode();
            cur = cur->child[i];
        }
        cur->isWord = true;
    }

    bool search(string word) {
        return dfs(word, 0, root);
    }

    bool dfs(const string& word, int idx, TrieNode* node) {
        if (!node) return false;                         // ① both kinds of null stop here
        if (idx == word.size()) return node->isWord;     // ② all matched: check isWord

        char c = word[idx];
        if (c != '.') return dfs(word, idx + 1, node->child[c - 'a']);   // ③ letter: one path

        for (TrieNode* child : node->child)              // ④ '.': try all 26
            if (dfs(word, idx + 1, child)) return true;  // ⑤ stop at the first true
        return false;
    }
};

addWord is the same as a plain trie insert. search just starts the DFS at the root. Inside dfs, a letter makes one recursive call, and a dot makes up to 26. The loop returns as soon as one branch finds a match.

One thing worth flagging — inside the dot loop I write if (dfs(...)) return true;. Not return dfs(...) directly. A bare return would give up after the very first child, so addWord("b") then search(".") would wrongly say false, because only child['a'] was ever tried.

Follow-up: allocation dominates, so I'd use a node pool. Every new letter calls new TrieNode(). Instead, I keep all nodes in one big array and use an int index as the pointer. Index 0 is the root, so 0 can also mean "no child" — the root is never anyone's child.

class WordDictionary {
private:
    static const int MAXN = 250001;   // 10^4 calls × length 25 + root
    int nxt[MAXN][26];                // nxt[node][c] = child id, 0 = none
    bool isWord[MAXN];
    int cnt = 1;                      // node 0 is the root

    bool dfs(const string& word, int idx, int node) {
        for (; idx < word.size() && word[idx] != '.'; idx++) {
            node = nxt[node][word[idx] - 'a'];
            if (!node) return false;
        }
        if (idx == word.size()) return isWord[node];
        for (int c = 0; c < 26; c++) {
            int child = nxt[node][c];
            if (child && dfs(word, idx + 1, child)) return true;
        }
        return false;
    }

public:
    WordDictionary() {
        memset(nxt[0], 0, sizeof(nxt[0]));
        isWord[0] = false;
    }

    void addWord(string word) {
        int cur = 0;
        for (char c : word) {
            int i = c - 'a';
            if (!nxt[cur][i]) {
                memset(nxt[cnt], 0, sizeof(nxt[cnt]));
                isWord[cnt] = false;
                nxt[cur][i] = cnt++;
            }
            cur = nxt[cur][i];
        }
        isWord[cur] = true;
    }

    bool search(string word) {
        return dfs(word, 0, 0);
    }
};

Two small changes in dfs. Letters are walked in a loop, so only a dot recurses. And I check child before I recurse, so this version never calls dfs on an empty slot.

One thing worth flagging — this object is big, about 25 MB. It must live on the heap, not the stack. That's fine on LeetCode, because LeetCode creates it with new. And MAXN comes from 104 words × 25 letters, plus the root, so it must be recomputed if the limits change.

Let me think about complexity here.

addWord is O(L), where L is the word length, and a search with no dots is also O(L).

With k dots, each dot can branch 26 ways, so the worst case is O(26k · L). Here the limit is 2 dots, so at most 262 = 676 branches. That's why the dot limit matters — it keeps search small.

Space is O(total added chars × 26) pointers for the trie, plus O(L) recursion depth for the DFS.

The node pool has the same Big-O; the win is the constant. On a LeetCode-like workload, the pointer version took about 167 ms, and the pool about 33 ms. There's a trade-off here: the pool reserves about 25 MB up front, even for a few words.
