Hmm, let me think about this for a second.

A naive approach would try every way to write n as a sum, and the number of those grows exponentially.

This problem reminds me of rod cutting: a DP over where to make a cut. Let dp[i] be the max product of breaking i into at least two parts. At each cut point j, the other piece, i−j, has two options: leave it whole, giving j*(i−j), or break it further, giving j*dp[i−j]. Take the max of both.

Here's the plan.

// dp[i] = max product breaking i into >= 2 parts
for i in 2..n:
  for j in 1..i-1:
    dp[i] = max(dp[i], j*(i-j), j*dp[i-j])
return dp[n]

One: build dp from 2 up to n.
Two: for each i, try every cut point j from 1 to i−1.
Three: keep the max of j*(i−j) and j*dp[i−j], then return dp[n].

One thing worth flagging — both terms are needed because dp[i−j] is defined as "must break," so it excludes leaving i−j whole. That "whole" case is exactly the j*(i−j) term. Concretely, dp[2]=1 and dp[3]=2 here, not 2 and 3. Does this approach sound good, or would you rather I think of another way?

The DP starts every entry at 1 and runs the double loop; the inner line takes the max of the cut term and the no-cut term.

class Solution {
public:
    int integerBreak(int n) {
        vector<int> dp(n + 1, 1);          // dp[i] = max product, i broken into ≥2 parts

        for (int i = 2; i <= n; i++) {
            for (int j = 1; j < i; j++) {      // cut point j: split into j and i-j
                dp[i] = max(dp[i], max(j * dp[i - j],   // cut: break i-j further
                                        j * (i - j)));  // no cut: keep i-j whole
            }
        }

        return dp[n];
    }
};

And an O(n) math version — the optimal split favors 3s. It returns 1 and 2 for n of 2 and 3, then peels off 3s while n > 4, and multiplies in the leftover.

class Solution {
public:
    int integerBreak(int n) {
        if (n == 2) return 1;                // 2 = 1+1
        if (n == 3) return 2;                // 3 = 1+2

        int product = 1;
        while (n > 4) {                     // peel off as many 3s as possible
            product *= 3;
            n -= 3;
        }
        return product * n;                    // leftover 2/3/4 stays whole
    }
};

Both give the same answer. One thing worth flagging — for the math version, a leftover 1 is wasteful, since it only multiplies by one (×1). So I fold 3+1 into 4 = 2×2; the while (n > 4) bound handles that at the end.

Let me think about complexity here.

Time is O(n2) for the DP and O(n) for the math version; space is O(n) and O(1).

Oh, one more thing — the key subtlety is the two terms: dp[i−j] forces a break, so the "keep it whole" case must be added as j*(i−j). And the reason 3s win is that 3^(1/3) > 2^(1/2) — 3 has the best per-unit product. For a huge n, I'd compute 3^(n/3) with fast exponentiation, in O(log n).
