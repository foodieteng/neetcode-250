Hmm, let me think about this for a second.

A naive approach would grab the biggest coin first, but greedy fails. With coins=[1,3,4] and amount 6, grabbing the 4 gives 4+1+1, three coins, while 3+3 is just two.

This problem reminds me of an unbounded knapsack: each coin is an item I can take any number of times, and I want the fewest items that hit the target exactly. So it's DP. dp[i] is the fewest coins to make amount i, and for each coin c, dp[i] = min(dp[i], dp[i-c] + 1). Because coins are unlimited, I sweep amounts low to high, so a coin can be reused.

Here's the plan.

// dp[i] = fewest coins to make amount i
dp[0] = 0; rest = INF
for each coin c:
  for i = c .. amount:  // low-to-high = reuse allowed
    if dp[i-c] reachable: dp[i] = min(dp[i], dp[i-c]+1)
return dp[amount] == INF ? -1 : dp[amount]

One: dp[0] is 0, and every other amount starts at INF.
Two: for each coin, sweep i from the coin up to the amount, and if dp[i-c] is reachable, take the min with it plus one.
Three: if dp[amount] is still INF, return -1; otherwise return it.

One thing worth flagging — I must guard against adding 1 to an INF cell, or it overflows. And the low-to-high sweep is what makes coins reusable; high to low would turn it into 0/1 knapsack. Does this approach sound good, or would you rather I think of another way?

First, coin outer, with an explicit INF guard.

class Solution {
public:
    int coinChange(vector<int>& coins, int amount) {
        vector<int> dp(amount + 1, INT_MAX);
        dp[0] = 0;                       // 0 coins make amount 0

        for (int coin : coins) {
            for (int i = coin; i <= amount; i++) {
                if (dp[i - coin] != INT_MAX)   // extend only if i-coin is reachable
                    dp[i] = min(dp[i], dp[i - coin] + 1);
            }
        }

        return dp[amount] == INT_MAX ? -1 : dp[amount];
    }
};

The outer loop picks a coin, and the inner loop sweeps amounts upward from that coin, so the coin can be used again. The easy-to-miss line is the check dp[i - coin] != INT_MAX — without it, INT_MAX + 1 overflows to a huge negative number and wins the min.

And the amount-outer version: for each amount, try every coin that fits.

class Solution {
public:
    int coinChange(vector<int>& coins, int amount) {
        // amount+1 acts as ∞ (making amount never needs more than amount coins of 1)
        vector<int> dp(amount + 1, amount + 1);
        dp[0] = 0;

        for (int i = 1; i <= amount; i++) {
            for (int coin : coins) {
                if (coin <= i)
                    dp[i] = min(dp[i], dp[i - coin] + 1);
            }
        }

        return dp[amount] > amount ? -1 : dp[amount];
    }
};

It uses amount + 1 as infinity, since no answer needs more than amount coins, so no overflow check is needed.

One thing worth flagging — for the minimum count, both loop orders give the same answer, because min doesn't care about order.

Time is O(amount × coins) — at most 104 × 12, about 1.2 × 105 updates. Space is O(amount).

Oh, one more thing — the sweep direction is the knapsack switch: low to high reuses a coin, which is unbounded; high to low would use each coin once, which is 0/1. If the question asked for the number of ways instead, I'd swap min(...)+1 for a sum, dp[i] += dp[i-c], and keep coins in the outer loop, so I count combinations, not permutations.
