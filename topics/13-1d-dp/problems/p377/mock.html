Hmm, let me think about this for a second.

A naive approach would recursively try every number as the next element, which re-solves the same remaining amount again and again — exponential.

This problem reminds me of an unbounded counting DP over amounts. dp[i] is the number of ordered ways to reach sum i, and dp[i] = sum over num of dp[i−num]. The key is loop order: because order matters, the target is the outer loop and num the inner. That way each amount picks any number as its last element, so (1,2) and (2,1) are counted separately. Swap the loops and you'd count unordered combinations instead.

Here's the plan.

// dp[i] = number of ordered ways to sum to i
dp[0] = 1
for i in 1..target:  // amount OUTER → permutations
  for num in nums:
    if num <= i: dp[i] += dp[i-num]
return dp[target]

One: set dp[0] = 1 — the empty sequence.
Two: loop the amount i from 1 to the target on the outside, and every num on the inside.
Three: if num fits, add dp[i−num] into dp[i], then return dp[target].

One thing worth flagging — a type gotcha. The counts grow fast, and an intermediate dp[i] can exceed INT_MAX even when the final answer fits. Signed overflow is undefined behavior, so I'd use unsigned int, which wraps mod 232. That's fine here because it's pure addition and the answer fits in 32 bits. Does this approach sound good, or would you rather I think of another way?

The unsigned int version wraps mod 232, which is safe for a pure-addition DP: amount outside, num inside, add dp[i - num], and cast back to int at the end.

class Solution {
public:
    int combinationSum4(vector<int>& nums, int target) {
        vector<unsigned int> dp(target + 1, 0);  // overflow wraps mod 2³² (well-defined)
        dp[0] = 1;                            // one empty sequence

        for (int i = 1; i <= target; i++) {       // ← amount outer → permutations
            for (int& num : nums) {
                if (i - num >= 0) {
                    dp[i] += dp[i - num];       // add sequences whose last number = num
                }
            }
        }

        return static_cast<int>(dp[target]);       // answer < 2³¹ → cast back to int is exact
    }
};

The long long version computes the same recurrence.

class Solution {
public:
    int combinationSum4(vector<int>& nums, int target) {
        vector<long long> dp(target + 1, 0);       // 64-bit: only delays overflow (see below)
        dp[0] = 1;

        for (int i = 1; i <= target; i++)
            for (int num : nums)
                if (num <= i)
                    dp[i] += dp[i - num];

        return (int)dp[target];                     // answer guaranteed to fit int
    }
};

One thing worth flagging — long long only pushes the overflow further out; it doesn't remove it. Take every multiple of 10 below 1000 plus 111, with target=999. The answer is 1, but the entries at multiples of 10 reach about 298, so signed 64 bits still overflows, which is undefined. unsigned is the one I'd submit.
