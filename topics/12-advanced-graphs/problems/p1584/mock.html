This problem reminds me of the two classic minimum spanning tree algorithms: Prim's and Kruskal's. Both are greedy, and both give a provably minimum tree. I'll show both — they solve the same problem from two angles.

P — plan
C
CANDIDATE

Here's the plan for both.

// A · Prim — grow one tree from a start node
keep inMST[] + a min-heap of (weight, node)
pop cheapest crossing edge → if node already in tree, skip
else add it, add its weight, push its edges → until n nodes

// B · Kruskal — pick smallest edges globally
push all pair edges → pop smallest by weight
Union-Find: endpoints in different sets → take it
same set → it makes a cycle, drop it → until n−1 edges

One: Prim grows a tree from point 0 with a min-heap, always taking the cheapest edge to a new node.
Two: Kruskal pops all pair edges from the smallest up, and Union-Find drops any edge whose endpoints are already connected.
Three: stop at n nodes for Prim, or n − 1 edges for Kruskal.

One thing worth flagging — greedy is safe because of the cut property: for any split of the points into two groups, the cheapest crossing edge belongs to some MST. Prim uses the cut "tree vs outside"; Kruskal uses it each time it joins two blocks.

Both cost O(n² log n) on this dense graph. Array-based Prim gets O(n²), but the heap versions are cleaner and fast enough for n = 1000. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. Prim first: a min-heap of (weight, node), seeded with point 0 at cost 0. Each fresh pop adds a node to the tree and pushes its edges to every outside node.

class Solution {
public:
    int minCostConnectPoints(vector<vector<int>>& points) {
        auto manhattan = [&](int u, int v) {          // cost of two points = Manhattan distance
            return abs(points[u][0] - points[v][0]) + abs(points[u][1] - points[v][1]);
        };

        int n = points.size();
        vector<bool> inMST(n, false);            // points already in the tree
        using P = pair<int, int>;              // (weight, target node)
        priority_queue<P, vector<P>, greater<P>> pq;  // min-heap

        pq.push({0, 0});                        // grow the tree from point 0, cost 0
        int total = 0, cnt = 0;

        while (!pq.empty() && cnt < n) {
            auto [w, u] = pq.top(); pq.pop();
            if (inMST[u]) continue;              // lazy: skip stale entries

            inMST[u] = true;                   // u joins the tree
            total += w; cnt++;

            for (int v = 0; v < n; v++) {
                if (inMST[v] || u == v) continue;
                pq.push({manhattan(u, v), v});   // push crossing edges u→outside
            }
        }
        return total;
    }
};

One thing worth flagging — the if (inMST[u]) continue; line is required, not an optimization. The same node gets pushed many times with different weights; the first pop settles it, and every later pop is stale and would double-count edges.

Then Kruskal: push every pair edge into a min-heap by weight, and pop until I've added n − 1 edges.

class Solution {
private:
    vector<int> parent;                       // parent[x]<0: root, value = −set size

    int Find(int x) {                         // path compression
        return parent[x] < 0 ? x : parent[x] = Find(parent[x]);
    }

    bool Union(int x, int y) {
        int rootX = Find(x), rootY = Find(y);
        if (rootX == rootY) return false;       // same set → cycle, don't merge
        if (-parent[rootX] < -parent[rootY]) swap(rootX, rootY); // union by size
        parent[rootX] += parent[rootY];
        parent[rootY] = rootX;
        return true;
    }

public:
    int minCostConnectPoints(vector<vector<int>>& points) {
        auto manhattan = [&](int u, int v) {
            return abs(points[u][0] - points[v][0]) + abs(points[u][1] - points[v][1]);
        };

        int n = points.size();
        parent.assign(n, -1);
        using T = tuple<int, int, int>;         // (weight, u, v)
        auto cmp = [&](auto t1, auto t2) {
            return get<0>(t1) > get<0>(t2);    // min-heap by weight
        };
        priority_queue<T, vector<T>, decltype(cmp)> pq(cmp);

        for (int i = 0; i < n; i++) {
            for (int j = i + 1; j < n; j++) {
                pq.push({manhattan(i, j), i, j});   // every pair of points
            }
        }

        int total = 0, add = 0;
        while (add < n - 1) {                    // done after n−1 edges
            auto [w, u, v] = pq.top(); pq.pop();
            if (Union(u, v)) {                   // take it only if no cycle
                total += w; add++;
            }
        }
        return total;
    }
};

Here, Union returning false is the cycle check — both endpoints already share a root, so I drop that edge. Only a true, a real merge, adds to the total.

CANDIDATE

Time is O(n² log n) for both. The graph is complete, so there are about n²/2 edges, and each heap operation costs a log. Space is O(n²), since both can hold that many edges in the heap. In the worst case, with n = 1000, that's about half a million edges — well within limits.

Oh, one more thing — if n were much larger, pushing all those edges would be wasteful. The clean fix for a dense graph is array-based Prim: keep the cheapest distance to each outside node in a plain array, and pick the minimum each round in O(n), with no heap at all. That's O(n²) time and O(n) space.
