Here's the plan. I'm using a multiset per airport to keep the destinations sorted.

// 1. graph[from] = multiset of destinations  (auto lexical order)
// 2. dfs(u):
//     while u still has an edge:
//       v = smallest destination; erase it; dfs(v)
//     routes.push_back(u)       // dead end → post-order
// 3. reverse(routes)            // post-order is the reverse itinerary
key: record a node only after all its edges are used; the dead end lands last

One: build the graph, each airport mapping to a multiset of destinations.
Two: from JFK, while the current airport still has a ticket, take the smallest destination, erase it, and recurse; once it has none left, push the airport.
Three: reverse the pushed list.
The key is to record a node only after all its edges are used, so the dead end lands last.

One thing worth flagging. The multiset keeps the smallest destination at the front, and erasing that one iterator uses exactly one ticket — a duplicate ticket to the same city stays. That covers both "walk lexically smallest" and "use each ticket once" cleanly.

class Solution {
private:
    unordered_map<string, multiset<string>> graph;   // out-edges, lexical order for free
    vector<string> routes;                        // post-order stack (reverse itinerary)

public:
    vector<string> findItinerary(vector<vector<string>>& tickets) {
        for (auto& t : tickets) {
            graph[t[0]].insert(t[1]);
        }

        dfs("JFK");
        reverse(routes.begin(), routes.end());       // reverse itinerary → itinerary
        return routes;
    }

    void dfs(string u) {
        while (graph.count(u) && !graph[u].empty()) {
            auto v = *graph[u].begin();          // smallest destination
            graph[u].erase(graph[u].begin());   // use this ticket
            dfs(v);
        }
        routes.push_back(u);                       // no out-edge = dead end → post-order push
    }
};

I build the multiset graph, call dfs("JFK"), reverse routes, and return it. Inside dfs, the while loop keeps taking the smallest destination, erases that ticket, and recurses.

One thing worth flagging is routes.push_back(u). It only runs once the while loop drains every edge out of u. So the first node pushed is the deepest dead end — the true last stop — and JFK is pushed last. That makes routes the reversed itinerary, which is why I flip it at the end.

The row that matters is the first: JFK's smallest edge is KUL, so I go there first — but KUL is a dead end, so it's pushed first and, after reversing, it lands last. Then JFK takes NRT, NRT returns to JFK, and everything drains. Reversing [KUL,JFK,NRT,JFK] gives [JFK,NRT,JFK,KUL].

Let's also test with corner cases.

• A simple chain like [[JFK,A],[A,B]] just gives [JFK,A,B].
• A there-and-back [[JFK,A],[A,JFK],[JFK,B]] gives [JFK,A,JFK,B] — the reusable JFK is handled because I delete edges, not mark nodes.

Let me think about complexity here.

The time complexity is O(E log E), where E is the number of tickets. Each edge is walked once, and the multiset work is at most O(log E) per ticket. The final reverse is O(E).

The space complexity is O(E) for the graph, the recursion stack, and the routes.

In the worst-case scenario the graph is one long chain, so the recursion goes E deep — fine for E up to 300.

Oh, one more thing — if E could be huge and blow the stack, I'd rewrite the DFS with an explicit stack: keep pushing the smallest neighbor, and when a node has no edges left, pop it into routes. Same logic, no recursion depth limit.
