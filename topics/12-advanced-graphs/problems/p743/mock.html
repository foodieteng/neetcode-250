Hmm, let me think about this for a sec.

A naive approach would be to try every path from k and keep the shortest to each node. That blows up — too many paths.

This problem reminds me of a classic single-source shortest path. Because all weights are non-negative, Dijkstra is the right tool. Bellman-Ford would also work, but it's O(V·E) — slower here for no reason.

So: run Dijkstra from k, get the shortest distance to every node, then take the max.

P — plan
C
CANDIDATE

Here's the plan.

// state
dist[v] = best known time from k to v  (∞ at start)
heap of (d, node), ordered by d

// invariant
when I pop (d, u) with d == dist[u],
dist[u] is final — nothing can make it shorter later
(true because all weights ≥ 0)

// loop
pop (d, u); if d > dist[u]: skip   // stale
for each u→v (w): if d + w < dist[v]: update, push

One: a dist array, ∞ everywhere except 0 at k, and a min-heap of (distance, node) pairs.
Two: pop the closest pair; skip it if it's stale, otherwise lock in its distance and relax its out-edges.
Three: return the largest distance, or -1 if any node is still ∞.

One thing worth flagging: I don't decrease keys. When I find a shorter path to v, I push a new pair and leave the old one in the heap. The guard if (d > dist[u]) continue; throws those stale pairs away when they surface — that's lazy deletion. It keeps the code simple without hurting the complexity: at most one push per successful relax, so pushes stay O(E). Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int networkDelayTime(vector<vector<int>>& times, int n, int k) {
        vector<vector<pair<int, int>>> graph(n + 1);
        vector<int> dist(n + 1, INT_MAX);

        for (auto t : times) {
            int u = t[0], v = t[1], w = t[2];
            graph[u].push_back({v, w});
        }

        using P = pair<int, int>;          // {dist, node}
        priority_queue<P, vector<P>, greater<P>> pq;  // min-heap

        dist[k] = 0;
        pq.push({0, k});

        while (!pq.empty()) {
            auto [d, u] = pq.top(); pq.pop();

            if (d > dist[u]) continue;          // stale entry ⇒ lazy deletion

            for (auto [v, w] : graph[u]) {
                int nd = d + w;
                if (nd < dist[v]) {              // relaxed ⇒ push a new entry
                    dist[v] = nd;
                    pq.push({nd, v});
                }
            }
        }

        int ans = 0;
        for (int i = 1; i <= n; i++) {
            if (dist[i] == INT_MAX) return -1;  // some node is unreachable
            ans = max(dist[i], ans);          // latest arrival time
        }
        return ans;
    }
};

I build an adjacency list of size n + 1, since nodes are numbered from 1, and a dist array full of INT_MAX. I push {0, k}, then pop the smallest pair, skip it if it's stale, and push a new distance whenever a relax improves. At the end, any node still at INT_MAX means -1; otherwise I return the max.

One thing worth flagging: the heap uses greater<P>, so it's a min-heap — priority_queue is a max-heap by default. And the pair is {dist, node}, not {node, dist}, so it sorts by distance. Get either wrong and the whole thing breaks.

The row that matters is the pop of (5, 3). That pair is a leftover: node 3 was first reached at cost 5 straight from node 1, but going through node 2 later found it at cost 3. When the old pair pops, d=5 is bigger than dist[3]=3, so I skip it. Final distances are [0, 2, 3, 5, 6], so the answer is 6 — node 5 hears the signal last. That matches.

Corner cases:

• One edge 1→2:1 with k=1 → 1.
• The same graph with k=2 → -1, since node 1 is unreachable.
• A zero-weight edge is fine — that node just gets the signal at time 0.

E — evaluate
C
CANDIDATE

The time complexity is O(E log V). Each edge causes at most one push, so the heap holds O(E) pairs, and each pop or push is a log of that.

The space complexity is O(V + E) — the adjacency list, the dist array, and the heap.

In the worst-case scenario, a dense graph has E ≈ V² edges, so it's about O(V² log V). With n ≤ 100, that's tiny.

Oh, one more thing — the stale guard is not required for a correct answer. The relax check d + w < dist[v] already blocks useless updates. But without the guard, I'd expand already-settled nodes again and waste time. So it's an efficiency guard, not a correctness one.
