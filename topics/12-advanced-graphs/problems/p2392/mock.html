A naive approach would be to try every possible ordering of rows and columns and check the conditions. But that's k! orderings. With k up to 400, that's hopeless.

This problem reminds me of topological sort. Each "above" or "left" rule is a directed edge. A valid line-up is a topo order of that graph. If the graph has a cycle, no order exists.

The key move is to keep rows and columns separate. Two independent graphs, two independent topo sorts. Mixing them would invent fake cycles across dimensions that don't really conflict.

Here's the plan. I'm using Kahn's algorithm — peel off in-degree-zero nodes — to get each order.

// 1. topo(rowConditions) → rowOrder ; rowOrder[i] sits in row i
// 2. topo(colConditions) → colOrder ; colOrder[i] sits in col i
// 3. if either topo length != k → cycle → return {}
// 4. place value v at (rowPos[v], colPos[v]); rest stay 0
claim: rowPos and colPos are permutations → no two values collide

One: topo-sort rowConditions; the i-th number in that order sits in row i.
Two: do the same for colConditions to get each column.
Three: if either order is shorter than k, there's a cycle, so return {}; otherwise drop each value at its row and column crossing.

One thing worth flagging about correctness. Both position maps are permutations of 0..k-1, so the k values land in k different cells — like a permutation matrix. No collisions, and every other cell is naturally 0.

There's a trade-off here. The matrix itself costs O(k2) space, which I can't avoid since I have to return it. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> buildMatrix(int k, vector<vector<int>>& rowConditions,
                                       vector<vector<int>>& colConditions) {
        vector<int> rowOrder = topo(rowConditions, k);   // row order
        vector<int> colOrder = topo(colConditions, k);   // col order
        if (rowOrder.empty() || colOrder.empty()) return {};  // a cycle → no answer

        vector<pair<int,int>> pos(k + 1, {-1, -1});
        for (int i = 0; i < k; i++) {
            pos[rowOrder[i]].first  = i;          // its row index
            pos[colOrder[i]].second = i;          // its col index
        }

        vector<vector<int>> matrix(k, vector<int>(k, 0));
        for (int v = 1; v <= k; v++)
            matrix[pos[v].first][pos[v].second] = v;   // drop at crossing
        return matrix;
    }

    // Kahn topo sort: an order of length k, or empty on a cycle
    vector<int> topo(vector<vector<int>>& arr, int k) {
        vector<vector<int>> graph(k + 1);
        vector<int> indegree(k + 1, 0);
        for (auto e : arr) {
            auto u = e[0], v = e[1];
            graph[u].push_back(v);                     // u before v (above / left)
            indegree[v]++;
        }

        vector<int> order;
        queue<int> q;
        for (int i = 1; i <= k; i++)
            if (indegree[i] == 0) q.push(i);       // no prerequisite

        while (!q.empty()) {
            auto u = q.front(); q.pop();
            order.push_back(u);
            for (auto v : graph[u])
                if (--indegree[v] == 0) q.push(v);   // freed a node
        }
        return order.size() == k ? order : vector<int>();  // short = cycle
    }
};

The main function runs topo twice, returns empty if either order comes back empty, records each number's row and column index in pos, and drops it at that crossing. topo is plain Kahn: build the edges, push every in-degree-0 number, and when popping a node drops a neighbor to 0, that neighbor joins the queue.

One thing worth flagging in topo. The cycle check is the return line: order.size() == k. In a clean DAG every node enters and leaves the queue once, so the order has all k nodes. If a cycle exists, those nodes never reach in-degree zero, so the order comes up short. That one comparison is my whole "no answer" test.

• A repeated condition just bumps the in-degree twice and gets undone twice.
• A number in no condition starts at in-degree zero and can go anywhere.

Let me think about complexity here.

Time is O(k² + E), where E is the total number of conditions. Each topo sort is O(k + E); the k2 comes from building the k-by-k matrix, which I have to do anyway.

Space is also O(k² + E) — the matrix is k2, and the two graphs are O(k + E).

In the worst-case scenario, one dimension has all the edges, but Kahn still touches each node and edge once, so it stays linear in the graph.

Oh, one more thing — if the caller only needs a yes/no answer, I can skip building the matrix entirely. Just run both topo sorts and return whether both succeeded. That drops it to O(k + E) time and space.
