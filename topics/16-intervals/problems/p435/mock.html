Hmm, let me think about this for a second.

A naive approach would try every subset, which is exponential. A dynamic programming version, like a longest increasing subsequence, works but is O(n²), too slow for 10⁵.

This problem reminds me of the activity selection pattern, a greedy exchange argument. To keep the most intervals, I always keep the one that ends earliest, because it leaves the most room for everything after it.

I
INTERVIEWER

Why sort by the end and not by the start?

C
CANDIDATE

Because starting early doesn't mean getting out of the way early. Take [[1,10],[2,3],[4,5]]. Sorted by start, [1,10] comes first, I keep it, and it blocks the other two, so I'd remove 2. Sorted by end, I keep [2,3] and [4,5] and remove only [1,10].

The scary part is that the start-sorted version passes all three official examples. I checked it on about 111,000 small cases, and it fails over 11,000 of them.

P — plan
C
CANDIDATE

Here's the plan, in three steps.

// keep the most = always keep the earliest end
sort by end  (comparator: a[1] < b[1], strict)
for each interval v:
  if kept is empty or kept.back().end <= v.start:  keep v
return n − kept

Sort by end. Walk through the intervals, and keep one whenever it starts at or after the end of the last one I kept. Return the total minus the number I kept.

One thing worth flagging — there are two comparisons, and they're different. The sort comparator must be strictly <. The keep condition is <=, because touching is allowed.

Alright.

class Solution {
public:
    int eraseOverlapIntervals(vector<vector<int>>& intervals) {
        sort(intervals.begin(), intervals.end(), [&](auto& a, auto& b) {
            return a[1] < b[1];
        });

        vector<vector<int>> res;

        for (auto& v : intervals) {
            if (res.empty() || res.back()[1] <= v[0]) {
                res.push_back(v);
            }
        }

        return intervals.size() - res.size();
    }
};

I sort with a lambda that returns whether a[1] < b[1]. Then one loop: if my kept list is empty, or its last end is at most the current start, I keep it. I return the size difference.

The easy line to get wrong is the comparator. If I write <= there, the comparison isn't strict anymore. With 16 identical intervals it still works, but with 17 it crashes with a segmentation fault. I also take the parameters by reference; passing them by value made the sort about 9 times slower on 10⁵ intervals.

Corner cases:

• A single interval returns 0.
• All identical returns n − 1.
• A chain that only touches returns 0.
• Fully nested intervals keep only the innermost.
