Hmm, let me think about this for a sec.

A naive approach would be to scan every interval for every query. That's 10⁵ × 10⁵, about ten billion checks, which is too slow.

This problem reminds me of an offline sweep line with a min-heap. Since the queries are independent, I can sort them and sweep from small to large. As the sweep moves right, an interval becomes a candidate once its left end is passed, and it stops being one once its right end falls behind. A heap ordered by size keeps the smallest candidate on top.

I
INTERVIEWER

You order the heap by size, but you throw things out by right end. Why not just key it by the right end?

C
CANDIDATE

Because the answer is the smallest size, and the right end tells me nothing about size. Take intervals [[1,3],[3,4]], with query 3. Both contain 3. Keyed by right end, the top is [1,3], so I'd answer 3. But [3,4] has size 2, which is the right answer.

My first draft did exactly that, and it passes both official examples, so it's an easy bug to miss. So the key is size first, and I keep the right end next to it only to check if the entry has expired.

P — plan
C
CANDIDATE

Here's the plan, in three steps.

// offline sweep + min-heap keyed (size, right)
order = query indices sorted by value; sort intervals by left
for qi in order: q = queries[qi]
  while next interval's left <= q: push (right − left + 1, right)
  while top.right < q: pop  // lazy: expired never returns
  ans[qi] = top.size, or −1 if the heap is empty

One: sort the query indices by value, so each answer can go back to its slot, and sort the intervals by left end. Two: for each query, push every interval whose left end is at most q, as a pair of size and right end. Three: pop while the top's right end is less than q; whatever is left on top is the answer.

Here, I'm using the heap to keep track of every interval that has started, smallest first.

One thing worth flagging — I only throw out an expired interval when it reaches the top. Expired ones deeper down never block the top, so they don't hurt. And it's safe, because queries only grow, so an expired interval can never become valid again.

I
INTERVIEWER

CANDIDATE

There's a trade-off here. The heap can hold stale entries, so it may grow to all 10⁵ intervals instead of only the live ones. But each interval is pushed once and popped at most once, so the total work stays the same. And it saves me from deleting from the middle of a heap, which a standard priority queue can't do.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> minInterval(vector<vector<int>>& intervals, vector<int>& queries) {
        int m = (int)queries.size(), n = (int)intervals.size();

        vector<int> order(m);
        iota(order.begin(), order.end(), 0);
        sort(order.begin(), order.end(), [&](int a, int b) {
            return queries[a] < queries[b];
        });
        sort(intervals.begin(), intervals.end());

        priority_queue<pair<int, int>, vector<pair<int, int>>, greater<>> pq;  // {size, right}
        vector<int> ans(m, -1);
        int i = 0;

        for (int qi : order) {
            int q = queries[qi];

            while (i < n && intervals[i][0] <= q) {
                int left = intervals[i][0], right = intervals[i][1];
                pq.push({right - left + 1, right});
                i++;
            }

            while (!pq.empty() && pq.top().second < q) pq.pop();

            if (!pq.empty()) ans[qi] = pq.top().first;
        }

        return ans;
    }
};

The order array holds the query indices, sorted by query value. The heap is a min-heap of pairs, size first, then right end. A pointer i walks the sorted intervals, so each one is pushed exactly once across all queries. The answers start at -1, so a query with an empty heap just keeps it.

One thing worth flagging — the two comparisons. I push while left <= q, and I pop only while right < q, strictly less. Both ends are included, so an interval that starts or ends exactly at q must still count. And the size needs the + 1: a point interval has size one, not zero.

Let me think about complexity here. The time complexity is O(n log n) to sort the intervals, plus O(q log q) to sort the queries. There's a while loop inside the for loop, but the pointer only moves forward and each interval is popped at most once, so all the heap work adds up to O(n log n).

The space complexity is linear, O(n + q), for the heap, the order array and the answers. In the worst-case scenario, the heap holds all 10⁵ intervals. On a random test with 10⁵ of each, it ran in about 25 ms.

Oh, one more thing — this needs all the queries up front. If they came one at a time in any order, I couldn't throw away expired intervals, because a later, smaller query might still need them.
