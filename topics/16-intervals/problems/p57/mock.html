A naive approach would append the new interval, sort everything, and merge. That's O(n log n), and it throws away the fact that the input is already sorted. Binary search could find the overlapping block faster, but I still have to copy every interval into the output, so it stays linear.

This problem reminds me of a linear sweep over sorted intervals. One pointer, three phases: copy the ones on the left, absorb the ones that overlap, copy the ones on the right.

Here's the plan, in three steps.

// one index i, three phases
while i < n and iv[i].end < new.start:  copy iv[i]
while i < n and new.end >= iv[i].start:
  new = [min(starts), max(ends)]
push new
while i < n:  copy iv[i]

First, while the current interval ends before the new one starts, copy it. Second, while the new one's end reaches the current start, absorb it: take the smaller start and the larger end. When that stops, push the new interval. Third, copy everything that's left.

One thing worth flagging — the comparisons. The first loop is strictly <, the second is >=. Touching has to count as overlap.

Alright. Three while loops sharing one index.

class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intervals,
                               vector<int>& newInterval) {
        int n = intervals.size(), i = 0;
        vector<vector<int>> res;

        // Case 1: no overlapping case before the merge intervals
        // Compare ending point of intervals to starting point of newInterval
        while (i < n && intervals[i][1] < newInterval[0]) {
            res.push_back(intervals[i]);
            i++;
        }

        // Case 2: overlapping case and merging of intervals
        while (i < n && newInterval[1] >= intervals[i][0]) {
            newInterval[0] = min(newInterval[0], intervals[i][0]);
            newInterval[1] = max(newInterval[1], intervals[i][1]);
            i++;
        }
        res.push_back(newInterval);

        // Case 3: no overlapping of intervals after newinterval being merged
        while (i < n) {
            res.push_back(intervals[i]);
            i++;
        }
        return res;
    }
};

The first copies intervals whose end is smaller than the new start. The second absorbs: new start becomes the min, new end becomes the max. Then I push the new interval — outside the loop, so it's added even if nothing overlapped. The third copies the rest.

The easy line to get wrong is the first loop's condition. If I write <=, [[1,3]] plus [3,5] comes back as two pieces. And here's the scary part: both official examples still pass with that bug. Out of about 57,000 small cases, it fails 25,000.

The row that matters is index 3, [8,10]. The new interval is [3,8] at that point, and 8 ≥ 8, so it's absorbed and the end grows to 10. With a strict comparison it would stop at [3,8] and split the answer.

Corner cases:

• An empty list gives just the new interval.
• New inside an existing one gives that one back.
• New before everything goes first.
• New after everything goes last.
