Let me reason about where the deletion goes.

A naive approach would delete each index and re-check the rest. That's n checks of O(n) each, so O(n2).

This problem reminds me of converging two pointers: a palindrome is just mirror pairs matching from the ends inward. When I hit s[l] != s[r], everything outside [l, r] already matches, so the deletion must be s[l] or s[r]. Deleting anywhere else can't fix this pair. So I check [l+1, r] or [l, r-1]. That fork happens only once, so it stays O(n).

Here's the plan.

// helper: plain palindrome, NO deletion allowed
isPalindrome(s, l, r):
  while l < r: if s[l] != s[r] return false; l++, r--
  return true
// main: converge, fork once on mismatch
while l < r: if s[l] == s[r] → l++, r--
  else return isPalindrome(s, l+1, r)
      || isPalindrome(s, l, r-1)
return true

One: move l and r inward while the characters match.
Two: on the first mismatch, return whether skipping the left or skipping the right leaves a plain palindrome.
Three: if the pointers meet with no mismatch, return true.

Two things worth flagging. The helper is zero-tolerance. If it also allowed a delete, that would be two deletions total. And I pass the string by reference with indices, not substr, to keep O(1) extra space. Does this approach sound good, or would you rather I think of another way?

class Solution {
private:
    // plain palindrome check (no tolerance); by reference, no string copy
    bool isPalindrome(string& s, int l, int r) {
        while (l < r) {
            if (s[l] != s[r]) return false;
            l++; r--;
        }
        return true;
    }

public:
    bool validPalindrome(string s) {
        int l = 0, r = s.size() - 1;
        while (l < r) {
            if (s[l] == s[r]) {
                l++; r--;                        // match → move inward
            } else {
                // first mismatch: delete left or delete right, check each once
                return isPalindrome(s, l + 1, r)
                    || isPalindrome(s, l, r - 1);
            }
        }
        return true;                          // matched all the way, no deletion needed
    }
};

A private helper, isPalindrome, runs a plain two-pointer check on [l, r] with no tolerance. The main function converges from both ends, and on the first mismatch it returns the helper on [l+1, r], or the helper on [l, r-1].

One detail worth flagging: the || short-circuits. If deleting the left works, it never tries the right, so the fork is at most two passes. And the return sits right at the fork, so it can only happen once.

Let's dry-run "cbbcc", the case where only one side works.

l, raction
0, 4c == c → l++ r--
1, 3b != c → fork
fork AisPalindrome(s, 2, 3) = "bc" → false
fork BisPalindrome(s, 1, 2) = "bb" → true

The outer c's match. Then at l = 1, r = 3, b against c is the mismatch, so we fork. Deleting the left leaves "bc", not a palindrome. Deleting the right leaves "bb", a palindrome, so true. Delete-left fails but delete-right succeeds, which is why both are needed.

Corner cases:

• "abc" → false, since both forks fail.
• "aba" → true, and it never forks.
• a single character → true.

CANDIDATE

Time is O(n). The main converge is one pass, and the fork triggers at most two more O(n) checks, once. Space is O(1) extra: just indices, and the helper takes the string by reference, so no substrings.

One more thing: "at most one" is what keeps it linear. With k deletions, each mismatch could fork again, so it becomes a memoized search over (l, r, k). And a replace-instead-of-delete variant is even simpler: just count mismatched pairs.
