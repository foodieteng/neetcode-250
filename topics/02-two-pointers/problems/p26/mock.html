Let me think about the options.

A hash set of seen values works, but it costs O(n) extra space. Erasing duplicates one by one is O(n²), because every erase shifts the rest.

This problem reminds me of the fast-slow two-pointer pattern, used as a write pointer: the fast pointer decides what to read, the slow one decides what to keep and where to write it. Since the array is sorted, a value is a duplicate exactly when it equals the last kept value, nums[i-1]. That gives O(n) time and O(1) space.

Here's the plan.

// i = write index = unique count so far
i = 0
for num in nums:
  if i > 0 and num == nums[i-1]: continue // dup of last kept
  nums[i++] = num
return i

One: start the write index i at 0.
Two: for each number, skip it if i > 0 and it equals nums[i-1].
Three: otherwise write it at i, move i forward, and finally return i.

Two things worth flagging. The i > 0 guard avoids reading nums[-1] on the first element, which is always kept. And the overwrite is safe: i never passes the scan position, so I only overwrite cells I've already read. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. It's one loop: i is the write index, and num walks through the array.

class Solution {
public:
    int removeDuplicates(vector<int>& nums) {
        int i = 0;  // write index / unique count

        for (int num : nums) {  // fast pointer: scan
            if (i > 0 && num == nums[i - 1]) continue;  // same as last kept → skip
            nums[i++] = num;  // new value → write at i, advance
        }
        return i;  // = k
    }
};

If i > 0 and num == nums[i - 1], I continue; otherwise I write nums[i++] = num. Then I return i.

One thing worth flagging — I compare against nums[i-1], the last kept value, not the previous element of the scan. Here both happen to work, but the last-kept version is the one that stays correct when I change the rule, say to keep two copies.
