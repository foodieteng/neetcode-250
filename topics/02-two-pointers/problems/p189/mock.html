Hmm, let me think about this for a second.

A naive approach would rotate one step at a time, k times — that's O(n·k), way too slow.

There are three standard ways to do better.
(a) An extra array: res[(i+k)%n] = nums[i] — simplest, but O(n) extra space.
(b) Cyclic replacement: O(1) space, but fiddly, because there are gcd(n,k) separate cycles to follow.
(c) This problem reminds me of reversing with converging two pointers: three reversals give O(1) space and are the cleanest to get right.

I'll go with (c). Does this approach sound good, or would you rather I think of another way?

C
CANDIDATE

Because (XY)R = YR XR. Reverse the whole array: (AB)R = BR AR — B is now up front and A at the back, but each block is backwards.

Reverse the first k, and BR is back to B; reverse the rest, and AR is back to A. The result is BA. The full reverse moves the blocks; the two partial reverses fix their internal order.

k %= n
reverse [0, n)  // A B → BR AR
reverse [0, k)  // BR → B
reverse [k, n)  // AR → A
// reverse = swap the ends, walk inward
result: B A

One: take k %= n.
Two: reverse the whole array.
Three: reverse the first k elements, then reverse the rest.

Each reverse is a converging two-pointer: swap the ends, walk inward.

CANDIDATE

Alright, let me code this up. It's five lines: the size, the modulo, and three calls to the standard reverse — the whole array, then begin() to begin()+k, then begin()+k to the end.

class Solution {
public:
    void rotate(vector<int>& nums, int k) {
        int n = nums.size();
        k %= n;                                   // n steps = no-op; k into [0, n)

        reverse(nums.begin(), nums.end());          // ① reverse all
        reverse(nums.begin(), nums.begin() + k);  // ② reverse first k
        reverse(nums.begin() + k, nums.end());    // ③ reverse the rest
    }
};

If the library reverse weren't allowed, each call is just a two-pointer swap loop.

One thing worth flagging — the modulo has to come before the reverses. Without it, begin()+k could point past the end of the array, which is undefined behavior. The half-open ranges matter too: the first part is [0, k), and the rest starts exactly at k.

Corner cases:

• [1,2], k=3 → k%2 = 1 → [2,1]; without the modulo, begin()+3 runs past the end.
• k=0, or any multiple of n → the array is unchanged.
• A single element → always unchanged.
