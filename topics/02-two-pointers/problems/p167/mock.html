Hmm, let me think about this for a second.

A naive approach would check every pair, which is O(n²). The usual fix for unsorted input is a hash map of complements, but that's O(n) space, which is banned here.

This problem reminds me of converging two pointers, and sorted order is exactly what makes it work: l at the front, r at the back, and the sum tells me which way to move.

If sum > target, the largest element, numbers[r], is too big — paired with anything left it still overshoots — so I drop it. If sum < target, the smallest, numbers[l], is too small, so I drop that. O(n) time, O(1) space.

Convince me that moving r can't skip the answer.

C
CANDIDATE

Since it's sorted, numbers[r] is the max in the window [l, r]. Its smallest possible partner is numbers[l], and that sum already exceeds target. So numbers[r] paired with any element in the window exceeds target — it can't be in the answer, and discarding it is safe.

The symmetric argument works for l. So the unique solution always stays inside the shrinking window.

Two: while l < r, compute the sum — equal, return {l+1, r+1}; less, move l right; greater, move r left.

Alright, let me code this up. It's one while loop with l and r closing in from both ends.

class Solution {
public:
    vector<int> twoSum(vector<int>& numbers, int target) {
        int n = numbers.size();
        int l = 0, r = n - 1;

        while (l < r) {
            int sum = numbers[l] + numbers[r];

            if (sum == target) {
                return {l + 1, r + 1};       // 1-indexed
            } else if (sum < target) {
                l++;                       // too small → need larger → move l in
            } else {
                r--;                       // too large → need smaller → move r in
            }
        }

        return {-1, -1};                 // solution guaranteed, never reached
    }
};

Each round I compute the sum: if it hits target I return right away, if it's too small I move l up, and if it's too big I move r down.

One thing worth flagging — the return adds one to both indices, because the answer is 1-indexed; returning {l, r} directly is the easy mistake. The final return {-1, -1} is never reached, since a solution is guaranteed; it's only there so every path returns.
