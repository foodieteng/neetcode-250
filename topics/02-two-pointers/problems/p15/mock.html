A naive approach would use three nested loops — n3 is 2.7 × 1010 here, way too slow, plus messy dedup.

This problem reminds me of fixing one value and running a sorted two-pointer pair search on the rest. Fix the anchor, nums[i], and the rest becomes: find two numbers summing to -nums[i]. Three spots, all "skip adjacent equal values," thanks to sorting.

(1) The outer anchor — if nums[i] == nums[i-1], the same anchor would reproduce the same triplets, so I continue.
(2) and (3) After recording a hit, I move l++, r--, then skip any nums[l] == nums[l-1] and any nums[r] == nums[r+1] — the same left or right value as the triplet I just took.

sort(nums)
for i in 0..n-1:

One: sort, and for each anchor i, skip it if it repeats the previous value.
Two: set l = i+1, r = n-1, and move by the sign of nums[i]+nums[l]+nums[r].
Three: on zero, record it, advance both, then skip duplicate l / r values.

I compare against nums[l-1] / nums[r+1] because I advance before skipping. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. I sort, then loop over anchors, skipping a repeated anchor.

class Solution {
public:
    vector<vector<int>> threeSum(vector<int>& nums) {
        int n = nums.size();
        sort(nums.begin(), nums.end());            // ① sort: equal values adjacent + monotonic
        vector<vector<int>> ans;

        for (int i = 0; i < n; i++) {
            if (i > 0 && nums[i] == nums[i - 1]) continue;  // ② outer dedup

            int l = i + 1, r = n - 1;

            while (l < r) {
                int sum = nums[i] + nums[l] + nums[r];

                if (sum < 0) {
                    l++;                              // too small → move l in
                } else if (sum > 0) {
                    r--;                              // too large → move r in
                } else {
                    ans.push_back({nums[i], nums[l], nums[r]});
                    l++; r--;                        // after a hit, shrink both ends
                    while (l < r && nums[l] == nums[l - 1]) l++;  // ③ skip repeated left values
                    while (l < r && nums[r] == nums[r + 1]) r--;  // ③ skip repeated right values
                }
            }
        }

        return ans;
    }
};

Inside, l and r converge: a negative sum moves l up, a positive sum moves r down, and a zero sum gets pushed into ans.

One thing worth flagging — the hit branch. I do l++; r--; first, and only then skip repeats, comparing each pointer to the neighbor it just left. Both skip loops also check l < r, so they can't run past each other or off the array.

Let me think about complexity here.

Time is O(n²): the O(n log n) sort is absorbed, and it's n anchors × an O(n) converge. Space is O(1) extra beyond the output, apart from the sort's own stack, which is O(log n).

Oh, one more thing — this generalizes. The four-number version wraps one more fixed loop, so O(n3); the general k-number version is a recursion whose base case is exactly this two-pointer pair search.
