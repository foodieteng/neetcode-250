A naive approach would be to try every count for every candidate — 0 copies, 1 copy, 2 copies, and so on — then check the sum. That works, and I'll use it later as a checker, but it builds a lot of dead branches.

This problem reminds me of the backtracking template for building subsets with a start index, where each level only picks from position s onward. There are two changes. A number can be reused, so I recurse with i, not i + 1. And I stop a branch as soon as the sum is too big.

Here's the plan.

// state
path = the numbers picked on this branch
res  = sum of path
s    = first index I may still pick

// setup
sort(candidates)        ← this is what makes break valid

// dfs(path, res, s)
if res == target: record path, return
for i in [s, n):
  if res + candidates[i] > target: break
  path.push_back(candidates[i])
  dfs(path, res + candidates[i], i)  ← i, not i + 1: reuse allowed
  path.pop_back()

One: sort the candidates.
Two: in the search, if the sum equals target, record the path.
Three: loop i from s; if adding candidates[i] passes the target, break; otherwise push, recurse with i, and pop.

I'm using s to keep track of where I may start picking, so every combination is built in non-decreasing index order — [2,3] can appear, but [3,2] never does.

One thing worth flagging — the recursive call passes i, so I may pick the same number again. With i + 1, [2], target 4 would give [] instead of [[2,2]].

There's a trade-off here. I pay for a sort, and in return, once one candidate is too big, every later one is too, so I break the whole loop.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> combinationSum(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end());         // break needs this
        vector<vector<int>> ans;
        vector<int> path;
        dfs(candidates, ans, path, 0, target, 0);
        return ans;
    }

    void dfs(vector<int>& candidates, vector<vector<int>>& ans, vector<int> path, int res, int target, int s) {
        if (res == target) {                                // found one
            ans.push_back(path);
            return;
        }

        for (int i = s; i < candidates.size(); i++) {
            if (res + candidates[i] > target) break;        // later ones are only bigger

            path.push_back(candidates[i]);
            dfs(candidates, ans, path, res + candidates[i], target, i);   // i: may pick itself again
            path.pop_back();
        }
    }
};

The main function sorts, then starts the search with an empty path, sum 0, and start 0. The search records the path when the sum hits target; otherwise it loops from s, pushes, recurses with i, and pops.

One thing worth flagging — the break is only safe because of the sort. It's a correctness point, not just speed. If I drop the sort and keep the break, [3,2], target 2 gives []: the loop sees 3, breaks, and never looks at 2.

Also, I never call dfs with a sum over target, because I check before I push. So there's no "sum > target" base case.

Corner cases:

• [2], 1 → [] in 1 call.
• Recursing with i + 1: [2], 4 → [].
• Recursing with s, or starting at 0: [2,3], 5 → [[2,3],[3,2]], both orders.
• No sort but keeping break: [3,2], 2 → [].

Let me think about complexity here.

Time is exponential, bounded by the size of the search tree. With N candidates, target T, and smallest candidate M, a path is at most T/M deep, with at most N choices per level, so a rough bound is O(NT/M), plus the sort and copying each answer into ans.

Space is O(T/M) extra for the recursion stack and the path, not counting the output; by value, each level also holds its own copy.

On the stress test, far past the 150-answer guarantee, that's 37,271 calls; without any pruning, 635,408.

Oh, one more thing — the real bound is much smaller than O(NT/M). The pruning cuts every branch the moment it passes the target, so the tree is only as big as the sums that still fit.
