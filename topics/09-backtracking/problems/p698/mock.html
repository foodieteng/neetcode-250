Hmm, let me think about this for a sec.

A naive approach would be to try all k^n assignments and check the sums at the end.

This problem reminds me of a bucket-filling backtracking search with symmetry pruning. Each number picks one of k buckets, so I build the assignment one number at a time and prune early: never let a bucket go over the target. There's also a second view — fill bucket 1 to the target, then bucket 2, and so on. I'll start with the bucket view, because the pruning is simple and the code is short.

P — plan
C
CANDIDATE

Here's the plan.

// buckets[0..k-1] = current sum of each subset
if total % k != 0 → false   // quick exit
sort nums descending; target = total / k
exist(idx):
  if idx == n → true   // every number placed, no bucket over target
  for i = 0..k-1:
    if buckets[i] + num > target → continue
    if buckets[i] == buckets[i-1] → continue // same state, skip
    place, recurse, undo

One: if the total doesn't divide by k, return false; otherwise target = total / k, and I sort descending.
Two: each number tries the k buckets — skip one that would go over the target, or one with the same sum as its left neighbor, since that's the same state with buckets swapped.
Three: place, recurse, undo; once every number is placed, return true.

That's enough: the buckets add up to k · target and none is over, so each is exactly the target.

One thing worth flagging — the sort is descending. Big numbers have the fewest places to go, so if they can't fit, I find out near the top of the tree. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. It's the plan almost line for line: sort, divisibility check, then exist places one number per level with the two skips, recursing and taking the number back.

class Solution {
public:
    bool canPartitionKSubsets(vector<int>& nums, int k) {
        sort(nums.begin(), nums.end(), greater<int>());       // big ones first
        int total = accumulate(nums.begin(), nums.end(), 0);
        if (total % k != 0) return false;
        int target = total / k;
        vector<int> buckets(k, 0);

        return exist(nums, buckets, target, k, 0);
    }

    bool exist(vector<int>& nums, vector<int>& buckets, int target, int k, int idx) {
        if (idx >= nums.size()) return true;                  // ① every number placed

        for (int i = 0; i < k; i++) {                         // ② try k buckets
            if (buckets[i] + nums[idx] > target) continue;    // ③ doesn't fit
            if (i > 0 && buckets[i] == buckets[i - 1]) continue;   // ④ same as left: symmetric

            buckets[i] += nums[idx];
            if (exist(nums, buckets, target, k, idx + 1)) return true;
            buckets[i] -= nums[idx];                          // ⑤ take it back
        }

        return false;
    }
};

One thing worth flagging — both skip lines must be continue, not break. The buckets are not sorted, so a full bucket can come before an empty one. Take [1,1], k = 2: the second 1 overflows bucket 0, and a break never tries the empty bucket 1. So it returns false, but the answer is true.

A break on the duplicate line is wrong too, just harder to catch: the smallest failing input has 9 numbers — [10,12,9,2,6,2,5,13,13], k = 3.

Let me think about complexity here.

The time complexity is O(k^n) in the worst case — each number has up to k choices. In practice the pruning is huge: the worst input I found took about 207K calls, around 2 ms.

The space complexity is O(n) for the recursion stack, plus k buckets.

Overflow: the worst total is 160,000, far below INT_MAX.

And the total % k check is just a shortcut. If I drop it, target rounds down, so k · target < total. The numbers can never all fit, and the search still returns false. It's only slower.

Yes, sometimes. The fill-one-bucket-at-a-time version keeps a used[] array. It fills one subset to the target, then starts the next one, and it's also correct. On the hard cases with k = 3..5 it makes far fewer calls: on the k = 4 case, 1,690 vs 206,649. But on the k = 8 case it's 126,593 vs 845. So neither one wins every time.

If I want a guaranteed bound, I'd use a bitmask DP over the set of used numbers, storing the sum of the subset I'm filling.

// dp[mask] = sum of the current subset, or -1 if unreachable
dp[0] = 0
for mask, if dp[mask] ≥ 0:
  for each unused j:
    if dp[mask] + nums[j] ≤ target:
      dp[mask | 1<<j] = (dp[mask] + nums[j]) % target
answer: dp[full] == 0

Taking that sum % target means a full subset resets to 0, and the next number starts a new one. That's O(n · 2^n) time and O(2^n) space — 65,536 states, a few milliseconds at most.
