Hmm, let me think about this for a sec.

This problem reminds me of the backtracking template: fill a path one slot at a time, recurse, then undo. But there's one key difference.

When order doesn't matter, like choosing a group, the loop starts at a start index s, so every path is increasing and [2,1] never shows up. Here order does matter, so every slot must be able to take any element. So the loop always starts from 0, and I need another way to stop reuse: a used[] array.

Here's the plan.

// state
path   = the elements placed so far
used[i] = is nums[i] already in path?

// dfs()
if path.size() == n: record path, return
for i in [0, n):            ← from 0, not from s
  if used[i]: skip
  used[i] = true; path.push_back(nums[i])
  dfs()
  path.pop_back(); used[i] = false   ← undo both

One: if the path has n elements, record it and return.
Two: otherwise loop i from 0, and skip any index that's already used.
Three: mark it used, push it, recurse, then pop it and clear the mark.

The loop decides which element goes in this slot, and used[] makes sure each one goes in only once.

One thing worth flagging — I changed two pieces of state, so the undo has two parts: pop_back and used[i] = false. If I forget either one, the next branch sees a dirty state.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> permute(vector<int>& nums) {
        int n = nums.size();
        vector<vector<int>> ans;
        vector<int> path;
        vector<bool> used(n, false);
        dfs(nums, ans, path, used);
        return ans;
    }

    void dfs(vector<int>& nums, vector<vector<int>>& ans, vector<int>& path, vector<bool>& used) {
        if (path.size() == nums.size()) {                   // every slot is filled
            ans.push_back(path);
            return;
        }

        for (int i = 0; i < nums.size(); i++) {             // every slot may pick from the start
            if (used[i]) continue;                          // already in path

            used[i] = true;
            path.push_back(nums[i]);
            dfs(nums, ans, path, used);
            path.pop_back();                                // undo both
            used[i] = false;
        }
    }
};

permute just sets up the answer list, an empty path and a used array, then calls dfs. In dfs, a full path gets copied into the answer; otherwise the loop runs from 0, skips used indices, and does the set, push, recurse, pop, clear sequence.

path and used are passed by reference. There's one shared copy of each, and every change is undone right after the recursive call returns. I only copy path when I record an answer.

The undo order mirrors the do order: set used, push; then pop, clear used.

Let me think about complexity here.

The time complexity is O(n · n!). There are n! answers, and copying each one costs n. The call count is 1 + n + n(n−1) + … + n!, which is still bounded by a constant times n!.

The space complexity is O(n) extra for the recursion stack, path, and used, not counting the output.

In the worst-case scenario, n = 6: 720 answers and 1,957 calls, in about 0.050 ms.

Yes — the swap version. I keep nums[0..k) as the fixed prefix and nums[k..n) as the unused pool. For slot k, I swap each nums[i] with i ≥ k into position k, recurse on k + 1, then swap back.

// dfs(k)
if k == n: record nums, return
for i in [k, n):
  swap(nums[k], nums[i])
  dfs(k + 1)
  swap(nums[k], nums[i])    ← one-part undo

The array itself is the used set, so there's no extra array and no path, and the undo is one part. It makes the same number of calls: 16 for n = 3 and 1,957 for n = 6. It's a bit faster at n = 6, 0.032 ms vs 0.050 ms, same Big-O. The trade-off: the output order is not the same as the used[] version, but any order is allowed here.
