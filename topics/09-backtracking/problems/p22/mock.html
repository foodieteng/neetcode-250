A naive approach would be to list all 22n strings of ( and ), and keep the balanced ones. It works, and I'll use it later as a checker. But almost every string gets thrown away. At n = 8 that's 216 strings to check, just to keep 1,430.

This problem reminds me of the backtracking template: build the answer one character at a time. Here, at each step I have two choices: add ( or add ). If I only make a choice when it keeps the prefix valid, I never build a bad string. So there's nothing to filter at the end.

Here's the plan.

// state
res   = the prefix built so far
open  = number of '(' in res
close = number of ')' in res
// invariant: close <= open <= n

// dfs(res, open, close)
if len(res) == 2n:    ← full length, save it
  ans.add(res); return
if open < n:          ← still have a '(' to use
  dfs(res + '(', open + 1, close)
if close < open:      ← a '(' is waiting for a match
  dfs(res + ')', open, close + 1)

One: track open and close, the counts in the prefix, so I never have to scan the string again.
Two: if open < n, add (; if close < open, add ).
Three: when the length reaches 2n, save it.

One thing worth flagging — the guard close < open is a correctness rule, not a speed-up. Let me walk through that. If I wrote close <= open, then at n = 1 I could put ) first and get ")(". Same for close < n. Both are wrong on all 8 sizes.

And because the invariant always holds, there are no dead ends. Every call I make reaches at least one answer.

Alright, let me code this up.

class Solution {
public:
    vector<string> generateParenthesis(int n) {
        vector<string> ans;
        string res = "";
        dfs(ans, res, 0, 0, n);
        return ans;
    }

    void dfs(vector<string>& ans, string res, int open, int close, int n) {
        if (res.size() == 2 * n) {                  // length 2n: always valid, record
            ans.push_back(res);
            return;
        }

        if (open < n) {                             // still have a '(' left
            dfs(ans, res + '(', open + 1, close, n);
        }

        if (close < open) {                          // an unmatched '(' is waiting
            dfs(ans, res + ')', open, close + 1, n);
        }
    }
};

That matches the plan: the base case saves a full-length string, and two guarded calls add ( or ).

One thing worth flagging — there's no pop here. res is passed by value, and res + '(' builds a brand-new string. So the caller's res is never changed, and there's nothing to undo.

Also, the two branches are two separate ifs on purpose. With else if (close < open), I'd only try ) when ( was not allowed, so n = 2 gives only ["(())"].

And the base case checks the full length, res.size() == 2 * n: stopping at open == n would return "(" for n = 1.

I
INTERVIEWER

This works. Can you avoid copying res on every call?

C
CANDIDATE

Yes. I'd pass string& res, do push_back before each call, and pop_back right after it. There's a trade-off here. With a reference, the pop_back is required. Without it, the ( stays in the string when I try the ) branch, and n = 2 gives only ["(())"]. The by-value version can't make that mistake.

On speed, at n = 8 I measured ~0.36 ms by value and ~0.15 ms by reference. Same big-O. The reference is a constant-factor win.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

The time complexity is O(4n / √n). The number of answers is the Catalan number Cn, which grows like 4n / n1.5, and each answer has length 2n. Since there are no dead ends, the work is tied to the output.

The space complexity is O(n) for the recursion depth, not counting the output. With by-value strings, each level holds its own copy, so the live characters add up to O(n²); the reference version brings that back to O(n).

Oh, one more thing — the call counts grow just like the answer counts, ending at 6,917 calls for 1,430 answers. That's the "no dead ends" idea in numbers.
