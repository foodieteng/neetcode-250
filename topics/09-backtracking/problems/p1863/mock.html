Hmm, let me think about this for a sec.

A naive approach would be to build each subset as a real vector, then XOR it from scratch. That costs O(n) per subset, so O(n · 2n), plus copying. It works here, but it repeats a lot of work.

This problem reminds me of the classic subsets backtracking pattern. Instead of storing the subset, I carry its XOR down the recursion as cur. Adding one element is just cur ^ nums[i]. So each subset costs O(1).

Here's the plan.

// state
s     = first index I may still pick
cur   = XOR of the subset on this path
total = running sum (passed by reference)

// dfs(s, cur)
total += cur        ← every node is a subset
for i in [s, n): dfs(i + 1, cur ^ nums[i])

// alternative: binary pick / skip
dfs(i, cur): i == n → return cur  ← only leaves
else return dfs(i+1, cur ^ nums[i]) + dfs(i+1, cur)

One: dfs takes a start index s and cur, the XOR so far.
Two: add cur to the total as soon as I enter a call.
Three: loop i from s, and recurse with i + 1 and cur ^ nums[i].

Here, I'm using cur to keep track of the subset's XOR; I never build the subset.

One thing worth flagging — every node in the for-loop tree is a subset: the root is {}, and each child adds one element. So I add cur at every call, not only at the bottom.

There's a trade-off here. The binary pick / skip tree is simpler to reason about, but it has 2n+1 − 1 nodes, and only its 2n leaves are subsets.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int subsetXORSum(vector<int>& nums) {
        int total = 0;
        dfs(nums, 0, total, 0);
        return total;
    }

    void dfs(vector<int>& nums, int s, int& total, int cur) {
        total += cur;                                       // every node is a subset

        for (int i = s; i < nums.size(); i++) {             // who to add next
            dfs(nums, i + 1, total, cur ^ nums[i]);         // pass a new value, cur stays
        }
    }
};

total is an int&, so every call adds into the same counter. When s == n, the loop just doesn't run, and the call returns.

One thing worth flagging — I pass cur ^ nums[i] as a new value. I do not change cur itself. That keeps cur the same for every turn of the loop, so each sibling starts from the parent's subset. With cur ^= nums[i] instead, [1,3] gives 5, not 6, because {3} starts from 1.

Also, I call it cur, not xor. In C++, xor is a reserved alternative token for ^, so a parameter named xor is a compile error.

Binary pick / skip — each element is either in or out.

class Solution {
public:
    int subsetXORSum(vector<int>& nums) {
        return dfs(nums, 0, 0);
    }

    int dfs(vector<int>& nums, int i, int cur) {
        if (i == nums.size()) return cur;                   // only a leaf is a subset

        return dfs(nums, i + 1, cur ^ nums[i])              // pick nums[i]
             + dfs(nums, i + 1, cur);                       // skip nums[i]
    }
};

Let me walk through that. At depth i I decide on nums[i]. The left call picks it, the right call skips it. Only when i == n is the subset complete, so only the leaves return a value. The inner nodes just add up their two children. No reference parameter needed.

Let me think about complexity here.

The time complexity is O(2n) for both. Each call does O(1) work besides its children. The space complexity is O(n), just the recursion depth. I never store a subset.

In the worst-case scenario, n = 12, the constants differ. The for-loop makes exactly 2n = 4,096 calls, one per subset. The binary version makes 2n+1 − 1 = 8,191 calls, about twice as many, because the inner nodes are not subsets.

Oh, one more thing — there's an O(n) formula. The answer is (nums[0] | nums[1] | ...) << (n - 1). For each bit that appears in any number, exactly half of the subsets have that bit set in their XOR. It matched both versions on 20,000 random arrays. I'd mention it as a follow-up, but backtracking is the pattern this problem is testing.
