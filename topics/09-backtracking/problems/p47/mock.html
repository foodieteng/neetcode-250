Here's the plan.

// state
path = the numbers placed so far
used = which indices are already in path

// setup
sort(nums)     ← equal values become adjacent

// dfs
if path is full: record it, return
for i in [0, n):
  if used[i]: continue
  if nums[i] == nums[i-1] and !used[i-1]: skip  ← same level dedupe
  mark, push, dfs, pop, unmark

One: sort, so equal values become neighbors.
Two: in each call, loop over every unused index.
Three: skip index i when nums[i] == nums[i-1] and used[i-1] is false, then mark, push, recurse, pop, unmark.

One loop is one level: it picks the value for the next slot. If the left copy is not used, it was already tried in this same slot and is back off the path, so putting this copy here gives the same subtree. If used[i-1] is true, it sits in an earlier slot, so this copy is fine. In effect, equal values always go in left-to-right order.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> permuteUnique(vector<int>& nums) {
        sort(nums.begin(), nums.end());                     // equal values side by side
        vector<vector<int>> ans;
        vector<int> path;
        vector<bool> used(nums.size(), false);
        dfs(nums, ans, path, used);
        return ans;
    }

    void dfs(vector<int>& nums, vector<vector<int>>& ans, vector<int> path, vector<bool>& used) {
        if (path.size() == nums.size()) {
            ans.push_back(path);
            return;
        }

        for (int i = 0; i < nums.size(); i++) {
            if (used[i]) continue;                          // already in path
            if (i > 0 && nums[i] == nums[i - 1] && !used[i - 1]) continue;   // same-level duplicate: skip just this one

            used[i] = true;
            path.push_back(nums[i]);
            dfs(nums, ans, path, used);
            path.pop_back();
            used[i] = false;
        }
    }
};

The highlighted line is the dedupe. My first draft ended it with break — I'll catch that in the review. This is the final version.

One thing worth flagging — the sort is a correctness requirement. The dedupe only compares neighbors, so without the sort, [1,2,1] gives 6 permutations, with duplicates.

The !used[i-1] part matters too. If I only compare values and skip, [1,1] → []. Nothing at all, because the second 1 can never be placed.

When you search for sums over a sorted array, you can break. Why not here?

C
CANDIDATE

There, the break is on sum: the array is sorted, so if the current candidate already goes over the target, every later one is at least as big and goes over too. The test is monotone for all later i, so stopping loses nothing.

Here the test is "same as the neighbor". That is not monotone — a later i can be a new value, like the 2. So break is only safe when the condition stays true for every later i.

Let me think about complexity here.

The time complexity is O(n · n!) in the worst case, when all values are distinct: n! leaves, and each copy into ans costs n. With duplicates, the dedupe cuts whole subtrees, so it only gets cheaper. Plus O(n log n) for the sort.

For space, the stack and used are O(n). But path is passed by value, so every level holds its own copy, which makes it O(n2) extra; passing path by reference brings it back to O(n).

On [1,1,2,2,3,3,4,4], with 2,520 answers, it takes 7,365 calls. With no dedupe, it's 109,601 calls.

Yes, it works: 0 wrong on the same arrays. It forces equal values in right-to-left order instead.

Oh, one more thing — with that rule, both continue and break are correct. If the left copy is on the path but this copy is not, this copy will be skipped at every deeper level too, so the path can never be finished. That node is a dead end, and breaking out of its loop loses nothing. On [1,1,2], that version makes 12 calls, with 3 dead-end nodes.

But it's slower: on the eight-element input, 16,201 calls vs 7,365. The standard rule cuts at the top; the other one walks into dead ends first.
