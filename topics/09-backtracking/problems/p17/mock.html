Hmm, let me think about this for a second.

A naive approach would write one nested loop per digit. But the number of digits isn't fixed, so I can't hard-code the loops.

This problem reminds me of backtracking on a decision tree. Each digit is one level of the tree. At level i, I try each letter of digits[i], then go one level down. When I've used every digit, the path from the root is one answer. Recursion gives me "a loop per digit" for any length.

P — plan
C
CANDIDATE

Here's the plan.

// dfs(res, i): res holds one letter for each of digits[0..i-1]
dfs(res, i):
  if i == n → save res          // every digit has a letter
  for c in mp[digits[i]]:
    dfs(res + c, i + 1)   // child gets its own new string

One: keep a small table mp, indexed by the digit's value — 10 entries, and the first two are empty.
Two: when i reaches the length, every digit has a letter, so save the string.
Three: for each letter of digits[i], recurse with res + c and i + 1.

One thing worth flagging — I pass res by value, and build the child's string with res + c. The child gets a new string; my own res never changes. So there's no undo step: when the loop moves from 'a' to 'b', res is still the clean prefix.

There's a trade-off here. By reference, string& res with push_back and pop_back, is also correct and avoids the copies, but by value is simpler and harder to get wrong. Does this approach sound good, or would you rather I think of another way?

class Solution {
private:
    const vector<string> mp = {"", "", "abc", "def", "ghi", "jkl", "mno", "pqrs", "tuv", "wxyz"};

public:
    vector<string> letterCombinations(string digits) {
        vector<string> ans;
        string res = "";
        dfs(ans, res, digits, 0);
        return ans;
    }

    void dfs(vector<string>& ans, string res, string& digits, int i) {   // res by value
        if (i >= digits.size()) {                    // ① every digit has a letter
            ans.push_back(res);
            return;
        }

        for (char c : mp[digits[i] - '0']) {         // ② each letter of digit i
            dfs(ans, res + c, digits, i + 1);        // ③ new string to the next level, no undo
        }
    }
};

The search either saves the finished string or loops over the letters of the current digit, passing res + c down.

digits[i] - '0' turns the character '2' into the number 2, so index 2 really is "abc". If I dropped the two empty entries but kept - '0', "2" would give [g,h,i], and 8 or 9 would read past the end.

One thing worth flagging — the return in the base case matters. Without it, the code would read digits[size], the null character '\0', and index mp[-48]. That's undefined behavior.

The key moment is when the whole "a" branch is done: #1 moves on to #6 with "b", and its own res is still "", because res + c never touched it. No cleanup was needed. 13 calls, 9 answers, in the expected order.

Corner cases:

• "2" → ["a","b","c"] in 4 calls.
• "7" → ["p","q","r","s"]: the entry must be "pqrs", not "pqr".
• "2222" → 81 answers, the smallest at length 4.
• "" → [""], one empty string. It's not allowed now, but older versions expected [], so I'd add one defensive line: if (digits.empty()) return {};

CANDIDATE

Let me think about complexity here.

The worst case is every digit a 7 or 9, the only keys with 4 letters. For "7979", that's 256 answers from 1 + 4 + 16 + 64 + 256 = 341 calls, and the output is 256 × 4 = 1,024 characters.

Time is O(4^n · n): up to 4^n answers, and building and saving each one costs O(n). The inner calls are fewer than the leaf calls, so they don't change the bound, and I can't beat the output size.

Space is O(n) recursion depth, not counting the output. Strictly, each frame keeps its own copy of res, so it's O(n²) characters on the stack, but with n ≤ 4 that's nothing.

INTERVIEWER

You said by value means no undo. What if someone "optimizes" it to a reference?

C
CANDIDATE

Good question. With string& res, they must add the undo. The correct form is push_back, recurse, pop_back, and that passes all 4,680 legal inputs.

The bug is to mutate without undo, like res += c with no pop_back. Then the old letter stays: on "2" you get [a, ab, abc] instead of [a, b, c]. It fails every legal input. The same thing happens even by value if you write res += c inside the loop.

// by value (this code): child gets a new string
dfs(ans, res + c, digits, i + 1);
// by reference: choose / explore / un-choose
res.push_back(c); dfs(ans, res, digits, i + 1); res.pop_back();

And the reference version is faster: on "7979", 9.89 µs by value versus 4.58 µs by reference, about 2×. At this size both are tiny, so I'd keep by value for clarity, and switch only in a hot loop.
