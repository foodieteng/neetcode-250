Okay. 16 is tiny, and the question asks for all partitions, so the output itself can be exponential — an exponential search is expected.

A string of length n has n − 1 gaps, and each gap is a cut or not, so there are at most 2^(n−1) ways to cut. The palindrome rule only removes some of them.

Quick check on the example, "aab": a | a | b works. aa | b works. a | ab fails, because "ab" isn't a palindrome, and aab as one piece fails too. So the answer is [["a","a","b"],["aa","b"]]. And "a" gives just [["a"]].

Hmm, let me think about this for a second.

A naive approach would list all 2^(n−1) cut patterns, build every piece, and then throw away the patterns with a bad piece. That works, but it builds lots of pieces for patterns that were dead from the first cut.

This problem reminds me of backtracking over a start index — choose a piece, recurse on the rest, undo. I choose the first piece, then solve the rest of the string the same way. If the first piece isn't a palindrome, I never go deeper on it, so I only grow partitions that are still valid.

P — plan
C
CANDIDATE

Here's the plan.

// dfs(start): s[0..start-1] is already cut; path holds those pieces
dfs(start):
  if start == n → save a copy of path   // whole string covered
  for end = start .. n-1:
    if s[start..end] is not a palindrome → skip, try next end
    path.push(s[start..end])   // choose
    dfs(end + 1)               // explore the rest
    path.pop()                 // un-choose

One: when start reaches the end, the whole string is covered, so save a copy of path.
Two: try every end from start onward; if that piece isn't a palindrome, skip to the next end.
Three: push the piece, recurse from end + 1, then pop.

One thing worth flagging — when a piece isn't a palindrome, I must skip it, not stop. That's continue, not break. In "aba", "ab" is not a palindrome, but the longer "aba" is. With break, I'd return only [["a","b","a"]]. That bug still passes every all-same-letter input, so I'd test "aba" on purpose.

There's a trade-off here. A palindrome table pal[i][j] makes each check O(1) but costs O(n²) space. I'll start with a two-pointer check. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<string>> partition(string s) {
        vector<vector<string>> ans;
        vector<string> path;
        dfs(ans, path, s, 0);
        return ans;
    }

    bool isPalindrome(string s, int start, int end) {      // by value: copies s every call
        while (start < end) {
            if (s[start] != s[end]) return false;
            start++; end--;
        }
        return true;
    }

    void dfs(vector<vector<string>>& ans, vector<string>& path, string& s, int start) {
        if (start >= s.size()) {                           // ① cut to the end: save answer
            ans.push_back(path);
            return;
        }

        for (int end = start; end < s.size(); end++) {     // ② first piece = s[start..end]
            if (isPalindrome(s, start, end)) {             // ③ not a palindrome → next end
                int L = end - start + 1;
                path.push_back(s.substr(start, L));        // ④ cut it off
                dfs(ans, path, s, end + 1);                //    the rest goes to the next level
                path.pop_back();                           // ⑤ undo
            }
        }
    }
};

The search pushes a piece when it's a palindrome, recurses from end + 1, and pops on the way back; when start reaches the end, it saves path. "Skip, don't stop" is built in: if the check fails, the if body just doesn't run, and the loop moves on.

One thing worth flagging — substr takes a length, not an end index, which is why I compute L = end - start + 1. With substr(start, end), "a" would give [[""]]. And the pop_back is a correctness rule: without it, "aa" gives [a,a],[a,a,aa].

The key moment is back at the top call: after the first branch finishes, #1 pops "a", so path is empty again. Then it tries a longer first piece, "aa" — a palindrome, so a whole new branch starts, ending in [aa,b]. 6 search calls, 7 palindrome checks, 2 answers, in the expected order.

Corner cases:

• "a" → [["a"]], one piece.
• "abc" → [[a,b,c]], just one answer.
• "aaa" → [a,a,a], [a,aa], [aa,a], [aaa], four — every cut pattern works.
• "aba" → includes ["aba"], because the loop keeps going after "ab" fails.

Let me think about complexity here.

The worst case is every letter the same, like "a"×16. Then every one of the 2^(n−1) cut patterns is an answer: 32,768 partitions from 65,536 search calls. Each answer holds all n letters, so the output alone is n · 2^(n−1) = 524,288 characters — about half a million.

Time is O(n · 2^n): up to 2^n calls, each doing O(n) work to check and copy pieces. I can't beat the output size, so this is close to the best possible.

Space is O(n) extra, not counting the output — the recursion stack plus path.

C
CANDIDATE

Yes, good catch. It takes string s by value, so every check copies the whole string. On "a"×16, that's 65,535 checks and about 1,048,560 bytes copied, just to read two letters at a time.

The fix is small: const string& s. Measured, that's 14.78 ms down to 4.27 ms — about 3.5× faster, with no change to the logic.

// before
bool isPalindrome(string s, int start, int end)
// after
bool isPalindrome(const string& s, int start, int end)

Oh, one more thing — the usual follow-up is the pal[i][j] table. At n = 16 it gave no gain, 4.63 ms, because the time goes into building the output, not into the checks. So I'd ship the const& fix first, and only add the table if a profile says so.
