A naive approach would be to try every subset of indices, keep the ones that hit the target, sort each one, and drop repeats with a set. That's 2n subsets with n up to 100. Way too many, but I'll still use it as a checker on small inputs.

This problem reminds me of backtracking with a start index over a sorted array. There are two twists. First, each element is used once, so I recurse with i + 1, not i. Second, the input has duplicates, so I skip equal values on the same level — sorting puts them side by side, which makes that skip a single comparison.

Here's the plan.

// state
path = the numbers picked on this branch
cur  = sum of path
s    = first index this level may pick

// setup
sort(nums)      ← groups equal values AND makes break valid

// dfs(path, cur, s)
if cur == target: record path, return
for i in [s, n):
  if i > s and nums[i] == nums[i-1]: continue  ← same level dedupe
  if cur + nums[i] > target: break
  path.push_back(nums[i])
  dfs(path, cur + nums[i], i + 1)  ← i + 1: each element once
  path.pop_back()

One: sort the numbers.
Two: if the sum equals target, record the path.
Three: loop i from s; skip a value equal to the one before it on this level, break once the sum is too big, otherwise push, recurse with i + 1, and pop.

I'm using s to keep track of where this level starts. Equal neighbors give the same answers, so each level tries only the first.

One thing worth flagging — the check is i > s, not i > 0. The first index of each level is always allowed; that's how [1,1] gets built. With i > 0, [1,1], target 2 gives [].

There's a trade-off here. The sort does two jobs: it groups duplicates and makes the break valid.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> combinationSum2(vector<int>& candidates, int target) {
        sort(candidates.begin(), candidates.end());         // equal values end up side by side
        vector<vector<int>> ans;
        vector<int> path;
        dfs(candidates, ans, path, target, 0, 0);
        return ans;
    }

    void dfs(vector<int>& nums, vector<vector<int>>& ans, vector<int> path, int target, int cur, int s) {
        if (cur == target) {
            ans.push_back(path);
            return;
        }

        for (int i = s; i < nums.size(); i++) {
            if (i > s && nums[i] == nums[i - 1]) continue;  // same level: try an equal value only once
            if (cur + nums[i] > target) break;              // sorted, later ones are only bigger

            path.push_back(nums[i]);
            dfs(nums, ans, path, target, cur + nums[i], i + 1);   // i + 1: each position used once
            path.pop_back();
        }
    }
};

The main function sorts, then starts the search with sum 0 and start 0. Inside the loop, the dedupe line comes first, then the break, then push, recurse with i + 1, and pop.

One thing worth flagging — the sort is a correctness requirement here, not just speed. Without it, both the dedupe and the break go wrong. For example, [2,1], target 1 gives []: the loop sees 2, breaks, and never looks at 1.

The order of the two ifs doesn't matter for the result. A skipped duplicate has the same value as the one before it, which already passed the check.

Let me think about complexity here.

Time is exponential in the worst case, up to O(2n) paths. But the dedupe means I never explore the same combination twice, so the real cost is bounded by the number of distinct combinations that still fit under the target, times the copy into ans, plus O(n log n) for the sort.

Space is O(target) extra for the recursion stack and the path, since every value is at least 1, not counting the output. By value, each level also holds its own copy.

In the worst case for duplicates, all 1s, the dedupe makes it tiny: n = 100 ones with target 30 takes only 31 calls.

Oh, one more thing — the dedupe and the break both depend on the sort. If someone "optimizes" the sort away, the code doesn't just get slower. It returns wrong answers.
