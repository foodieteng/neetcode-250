One: keep a path, and a start s, the smallest number I may still pick.
Two: if the path has k numbers, record it and return.
Three: otherwise loop i from s to n, push i, recurse with i + 1, and pop.

Here, I'm using s to keep track of the next number I'm allowed to pick. Every path is strictly increasing, so [1,2] can appear, but [2,1] never does, and no number repeats.

One thing worth flagging — the numbers are 1..n, not 0..n−1. So the first call starts at 1, and the loop runs while i ≤ n.

class Solution {
public:
    vector<vector<int>> combine(int n, int k) {
        vector<vector<int>> ans;
        vector<int> path;
        dfs(ans, path, n, k, 1);
        return ans;
    }

    void dfs(vector<vector<int>>& ans, vector<int>& path, int n, int k, int s) {
        if (path.size() == k) {                             // record only once k are picked
            ans.push_back(path);
            return;
        }

        for (int i = s; i <= n; i++) {                      // the numbers are 1..n
            path.push_back(i);
            dfs(ans, path, n, k, i + 1);                    // each number at most once
            path.pop_back();
        }
    }
};

The main function starts the search at 1. The search records the path once it has k numbers; otherwise it loops i from s up to n, inclusive, pushes i, recurses with i + 1, and pops.

path is passed by reference. There's one shared path, and the push / pop pair puts it back the way it was. I only copy it when I record an answer.

The return after recording matters for speed. Once the path has k numbers, there's nothing more to add on that branch.

Let me think about complexity here.

With pruning, time is O(k · C(n, k)). There are C(n, k) answers, copying each one costs k, and every call is on a path that leads to an answer, so the work is bound by the output.

Space is O(k) extra for the recursion stack and the path, not counting the output.

The worst case for my first version is k close to n. Take n = 20, k = 18: only 190 answers, but no pruning makes 1,048,555 calls, almost 220, in 6.35 ms. Pruned, it's 1,330 calls in 0.017 ms.

Oh, one more thing — the biggest output is n = 20, k = 10: 184,756 answers. There, pruning still helps, but less: 616,666 vs 352,716 calls. And for k = 2, it's 211 vs 210. Pruning only pays off when k is large.
