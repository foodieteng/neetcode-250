A naive approach would be to build all 2n index subsets, sort each one, and drop repeats with a set. It works here, but it still generates every duplicate first. I'll keep it as a checker on small inputs.

This problem reminds me of the subset backtracking template, plus a same-level dedupe. From the template: record the path at every node, then loop from a start index and recurse with i + 1. From the dedupe: sort first, then skip equal values on the same level. It fits because a duplicate only appears when two equal values compete for the same slot.

Here's the plan.

// state
path = the numbers picked on this branch
s    = first index this level may pick

// setup
sort(nums)      ← equal values become adjacent

// dfs(path, s)
record path       ← every node is a subset
for i in [s, n):
  if i > s and nums[i] == nums[i-1]: continue  ← same level dedupe
  path.push_back(nums[i])
  dfs(path, i + 1)
  path.pop_back()

One: sort, so equal values become adjacent.
Two: in each call, record the path, then loop i from s and recurse with i + 1.
Three: on one level, try only the first value of each run of equal values.

Here, I'm using s to keep track of where this level starts. If two equal values sit side by side, picking either one next gives the same subtree.

One thing worth flagging — the check is i > s, not i > 0. The first index of a level, i == s, is always allowed; that's how [2,2] gets built. With i > 0, [1,1] loses the subset [1,1]. Comparing with nums[i+1] keeps the last of the run instead, and loses it too.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> subsetsWithDup(vector<int>& nums) {
        sort(nums.begin(), nums.end());                     // equal values end up adjacent
        vector<vector<int>> ans;
        vector<int> path;
        dfs(nums, ans, path, 0);
        return ans;
    }

    void dfs(vector<int>& nums, vector<vector<int>>& ans, vector<int> path, int s) {
        ans.push_back(path);                                // every node is a subset

        for (int i = s; i < nums.size(); i++) {
            if (i > s && nums[i] == nums[i - 1]) continue;  // same level: try only the first of equal values

            path.push_back(nums[i]);
            dfs(nums, ans, path, i + 1);
            path.pop_back();
        }
    }
};

It's the subsets template with two additions: the sort up front, and the continue line at the top of the loop. That line skips nums[i] when i is past s and it equals the previous value.

One thing worth flagging — the sort is a correctness requirement. The dedupe only compares neighbors. Without the sort, [1,2,1] gives both [1,2] and [2,1], which are the same subset.

There's no base case. Every call records its path first, and the loop just ends when s reaches n.

Let me think about complexity here.

The time complexity is O(n · 2n) in the worst case, when all values are distinct. Then it's plain subsets: 10 distinct values take 1,024 calls, and each copy into ans costs up to n. With duplicates, the dedupe means one call per distinct subset, so it only gets cheaper. Plus O(n log n) for the sort.

The space complexity is O(n) extra for the recursion stack and the path, not counting the output. By value, each level also holds its own copy, so that's O(n²).

In the worst-case scenario for duplicates, all equal, the dedupe makes it tiny: 20 copies of 5 is 21 calls instead of over a million. I also checked against the brute force on 3,279 small arrays, with zero wrong.

At index i, I have two branches. Pick nums[i] and go to i + 1. Or skip it. The catch is the skip: if I skip one 5, I must skip the whole run of 5s, and jump to the first index with a new value. Otherwise "skip the first 5, pick the second" builds the same subset as "pick the first 5". I record the path only at the leaf, i == n.

It's also 0 wrong on the 3,279 arrays. But it makes more calls, because only the leaves are answers. On 20 copies of 5: 41 calls vs my 21. On 10 copies: 21 vs 11.

Oh, one more thing — the loop version records at every node, so every call is an answer. That's why it's the leaner one.
