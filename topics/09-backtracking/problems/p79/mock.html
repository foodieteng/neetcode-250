Hmm, let me think about this for a second.

A naive approach would list every simple path of length L in the grid and compare each one to the word. Most of those paths are wrong from the very first letter, so it wastes almost all the work.

This problem reminds me of backtracking — choose, recurse, undo. I grow the path one letter at a time, and the moment a letter doesn't match, I stop and go back. So I only extend paths that still match a prefix of the word.

BFS fits badly, because every path needs its own used set. DFS keeps one path alive at a time, so I can track used cells on the board itself.

Here's the plan.

// dfs(r, c, i): can word[i..] start at cell (r, c)?
for each cell (i, j): if dfs(i, j, 0) → return true

dfs(r, c, i):
  if board[r][c] != word[i] → false   // prune now
  if i == L - 1                   → true    // last letter matched
  mark board[r][c] = '#'
  for 4 neighbours (in bounds, not '#'):
    if dfs(nr, nc, i + 1) → true
  restore board[r][c] = original  // undo before going back
  return false

One: try every cell as a start.
Two: compare the letter first — a mismatch is false, and a match on the last letter is true.
Three: mark the cell with '#', try the four neighbours, and if all fail, restore the letter and return false.

One thing worth flagging — the mark and the restore are both correctness rules. Without the mark, ["AA"] with "AAA" bounces back and forth and says true. Without the restore, ["BAA"] with "AAB" keeps '#'s from a failed try that block the real path, so it says false.

A separate visited grid would keep the input clean but costs O(m·n) extra space, so I'll mark in place. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    const vector<pair<int, int>> dirs = {{-1, 0}, {1, 0}, {0, -1}, {0, 1}};   // up down left right

    bool exist(vector<vector<char>>& board, string word) {
        int m = board.size(), n = board[0].size();
        for (int i = 0; i < m; i++) {
            for (int j = 0; j < n; j++) {
                if (dfs(board, word, i, j, 0)) return true;   // every cell is a start
            }
        }

        return false;
    }

    bool dfs(vector<vector<char>>& board, string& word, int r, int c, int i) {
        if (word[i] != board[r][c]) return false;      // ① compare the letter first
        if (i == word.size() - 1) return true;        // ② last letter matched too

        const char cache = board[r][c];
        board[r][c] = '#';                              // ③ mark: on this path now

        for (auto [dr, dc] : dirs) {
            auto nr = r + dr, nc = c + dc;
            if (nr < 0 || nr >= board.size() || nc < 0 || nc >= board[0].size() ||
                board[nr][nc] == '#') continue;   // out of bounds or on the path
            if (dfs(board, word, nr, nc, i + 1)) return true;   // ④ success: pass it straight up
        }

        board[r][c] = cache;                             // ⑤ all failed: restore
        return false;
    }
};

The main function tries every cell as a start. The search compares the letter, returns true on the last letter, then marks the cell, tries four directions — skipping cells out of bounds or already '#' — and restores before returning false.

One thing worth flagging — the order of the first two checks matters. If I swap them, the last letter is never compared, so ["A"] with "B" would say true. Checking i == word.size() at the top breaks too: ["A"] with "A" would need a free neighbour to reach that check, so it says false.

The key moment: from the S at (1,3), I try up first. That E matches, so I mark it, but its only free neighbour is a C. The branch dies, and I restore it to E. Then I go down, then left — the last letter, so true, after 15 calls.

Corner cases:

• "ABCB" → false, with every mark undone.
• ["A"] with "AA" → false — no neighbours.
• 2×2 all A with "AAAAA" → false — the mark stops reuse.
• ["ABCDEF"] with "FEDCBA" → true, right to left.

Let me think about complexity here.

Time is O(m · n · 3^L). I try every start cell; the first letter has 4 directions, and after that at most 3, because the cell I came from is marked. Space is O(L) for the recursion stack — marking in place means no visited array.

The worst case is a board full of one letter where only the last letter fails. A 6×6 board of all A, with "AAAAAAAAAAAAAAB" (14 A's then B), returns false after about 4.1 million (4,120,732) calls — around 0.60% of the 36 · 4 · 3^14 = 688,747,536 bound.

Oh, one more thing — when I return true, I don't restore, so the winning path stays as '#' on the caller's board. If the caller needs it again, pass a copy, or restore before return true.

Yes, two cheap checks before the search.

First, a letter count check. If the word needs more of some letter than the board has, return false right away. In that worst case the board has no B, so it's 0 search calls instead of 4 million.

Second, start from the rarer end. If the last letter is rarer on the board than the first, reverse the word. A path exists for the word exactly when one exists for the reversed word, but now the first compare fails fast — "BAAAAAAAAAAAAAA" takes just 36 calls, one per cell.

// before the main loop
if any count_word[ch] > count_board[ch] → return false
if count_board[word.back()] < count_board[word.front()] → reverse(word)

Both checks are linear, so they never hurt the big-O. They just kill the worst cases before the exponential part starts.
