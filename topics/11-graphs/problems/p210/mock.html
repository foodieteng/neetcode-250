Hmm, let me think about this for a sec.

This is a directed graph: each course is a node, each pair is a directed edge. Finishing all courses while respecting prerequisites is exactly a topological sort of that graph, and a topological order exists if and only if the graph has no cycle — which lines up with the one failure case.

This problem reminds me of topological sorting, and there are two standard ways to build it. One is DFS post-order: finish a node only after all its descendants, then reverse. The other is Kahn's algorithm — a BFS that repeatedly removes nodes with no remaining prerequisites. Both run in O(V + E). I'll code the DFS one and then show the Kahn variant.

Here's the plan for the DFS version.

// build edge b → a (prerequisite points to the course it unlocks)
// visit[]: 0 = unvisited, 1 = on current path, 2 = done
dfs(u):
  if visit[u] == 1: return CYCLE  // came back onto the path
  if visit[u] == 2: return OK
  visit[u] = 1
  for v in graph[u]: if dfs(v) == CYCLE: return CYCLE
  visit[u] = 2; order.push(u)  // post-order
for every i: if dfs(i) == CYCLE: return []
reverse(order)

One: build an edge b → a, so a prerequisite points to the course it unlocks.
Two: DFS from every course with three states, and append a node to order only after all its neighbors finish.
Three: if any DFS finds a cycle, return empty; otherwise reverse order.

One thing worth flagging — the cycle check needs three states, not two. In a DAG a node can be reached again by a different path, and that's normal. Only re-entering a node still on the current recursion path (state 1) is a real cycle; a plain visited flag would falsely flag the diamond's shared node.

Why reverse? Post-order puts a node after its descendants; a topological order wants it before them.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> findOrder(int numCourses, vector<vector<int>>& prerequisites) {
        vector<int> visit(numCourses, 0), order;   // visit: 0 unvisited / 1 on path / 2 done
        vector<vector<int>> graph(numCourses);

        for (auto& p : prerequisites) {
            int a = p[0], b = p[1];
            graph[b].push_back(a);              // edge b→a (prerequisite b points to a)
        }

        for (int i = 0; i < numCourses; i++)
            if (hasCycle(graph, visit, order, i)) return {};   // cycle → return empty

        reverse(order.begin(), order.end());          // reversed post-order = topological order
        return order;
    }

    bool hasCycle(vector<vector<int>>& graph, vector<int>& visit, vector<int>& order, int u) {
        if (visit[u] == 1) return true;          // back to an "on path" node → cycle
        if (visit[u] == 2) return false;         // already done, no need to revisit

        visit[u] = 1;                            // in progress (on the current recursion path)
        for (int v : graph[u])
            if (hasCycle(graph, visit, order, v)) return true;
        visit[u] = 2;                            // done

        order.push_back(u);                       // post-order: add self after all descendants
        return false;
    }
};

I build the edges b → a, then run hasCycle from every course and return {} on the first cycle; at the end I reverse order. Inside hasCycle, state 1 means I came back onto my path, state 2 means the node is already finished. Otherwise I mark it 1, explore its neighbors, then mark it 2 and append it.

One thing worth flagging — I set visit[u] = 2 and push to order after the loop over neighbors. That ordering is the whole point: the node is recorded only once every descendant is already recorded.

Sure. Instead of recursion, I track each node's in-degree — how many prerequisites it still has. I start a queue with every node at in-degree 0, and each time I pop one, I "remove" it by decrementing its neighbors; any neighbor that reaches 0 joins the queue. The pop order is the answer.

class Solution {
public:
    vector<int> findOrder(int numCourses, vector<vector<int>>& prerequisites) {
        vector<int> indeg(numCourses, 0);
        vector<vector<int>> graph(numCourses);

        for (auto& p : prerequisites) {
            int b = p[1], a = p[0];
            graph[b].push_back(a);
            indeg[a]++;                          // a gains one prerequisite
        }

        queue<int> q;
        for (int i = 0; i < numCourses; i++)
            if (indeg[i] == 0) q.push(i);          // no prerequisites → start

        vector<int> order;
        while (!q.empty()) {
            int u = q.front(); q.pop();
            order.push_back(u);
            for (int v : graph[u])
                if (--indeg[v] == 0) q.push(v);      // all prerequisites done → ready
        }
        return order.size() == numCourses ? order : vector<int>();  // fewer = cycle
    }
};

One thing worth flagging — here the cycle check is free. Nodes inside a cycle keep a positive in-degree forever, so they never enter the queue. If order.size() ends up less than numCourses, some node was stuck in a cycle, and I return empty. Same O(V + E), no recursion depth risk.

Let me think about complexity here.

Time is O(V + E) for both — every node and edge is touched once. Space is O(V + E) for the adjacency list, plus O(V) for the visit or in-degree arrays and the queue or recursion stack.

Oh, one more thing — for very deep graphs the DFS recursion could risk a stack overflow, so in production I'd lean toward Kahn's iterative version. And if the problem wanted the lexicographically smallest order, I'd swap Kahn's plain queue for a min-heap.
