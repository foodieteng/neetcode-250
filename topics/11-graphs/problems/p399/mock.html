// build: graph[a][b]=v, graph[b][a]=1/v
bfs(start, end):
  if start or end not in graph: return -1 // undefined
  if start == end: return 1
  queue of (node, product), start at (start, 1.0), visited set
  pop (u,w); for (v,nw) in graph[u]: if v==end return w*nw; else push (v, w*nw)
  return -1 // unreachable

One: build the graph with both the forward edge and its reciprocal.
Two: for each query, if either variable isn't in the graph, return -1; if they're equal, return 1.
Three: BFS from the start with a running product, and when the end shows up as a neighbor, return the product times that edge; if the queue empties, return -1.

One thing worth flagging — the running product starts at 1.0, the multiplicative identity, and gets multiplied by each edge weight. And the ordering of the guards matters — the "not in graph → -1" check must come before the "start == end → 1" shortcut, so an undefined x/x correctly returns -1.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<double> calcEquation(vector<vector<string>>& equations,
            vector<double>& values, vector<vector<string>>& queries) {
        unordered_map<string, unordered_map<string, double>> graph;

        for (int i = 0; i < equations.size(); i++) {
            string a = equations[i][0], b = equations[i][1];
            double v = values[i];
            graph[a][b] = v;              // a/b = v
            graph[b][a] = 1.0 / v;        // b/a = 1/v (reversible)
        }

        vector<double> ans;
        for (auto q : queries)
            ans.push_back(bfs(graph, q[0], q[1]));
        return ans;
    }

    double bfs(unordered_map<string, unordered_map<string, double>>& graph,
               string start, string end) {
        if (!graph.count(start) || !graph.count(end)) return -1.0;  // undefined
        if (start == end) return 1.0;

        unordered_set<string> visit;
        queue<pair<string, double>> q;
        q.push({start, 1.0});              // (node, running product)
        visit.insert(start);

        while (!q.empty()) {
            auto [u, w] = q.front(); q.pop();
            for (auto [v, nw] : graph[u]) {
                if (v == end) return w * nw;       // hit → product × edge weight
                if (visit.count(v)) continue;
                visit.insert(v);
                q.push({v, w * nw});            // multiply along the path
            }
        }
        return -1.0;                        // unreachable → can't determine
    }
};

Each equation stores a/b as v and b/a as 1/v. Each query calls a bfs helper: the two guards in that order, then a queue of (node, product), seeded with {start, 1.0}. A neighbor that's the end returns right away; a new one is marked and pushed with the product times the edge weight.

One thing worth flagging — on a hit I return w * nw, not just w: the last edge's weight is part of the answer. And returning on the first hit is safe, because with consistent inputs every path gives the same product.
