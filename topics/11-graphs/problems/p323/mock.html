Hmm, let me think about this for a sec.

This problem reminds me of flood fill on a graph, because counting components is just counting how many separate blobs there are.

One way: DFS — build an adjacency list and loop over every node. Each time I hit an unvisited one, that's a new component, so I bump the count and run a DFS to mark its whole blob.

The other way is Union-Find: merge the two endpoints of every edge, then count how many roots remain. Both are close to linear. I'll show both; Union-Find is nicer if edges arrive online.

One, for DFS: build the adjacency list in both directions, and start cnt at 0.
Two, for each node that is still unvisited, add one to the count and DFS from it.
Three, for Union-Find: start every parent at -1, union every edge, and count the entries that are still negative.

One thing worth flagging — since the graph is undirected, I must push each edge both ways into the adjacency list; otherwise DFS can't always cross it and I'd over-count. And on the counting — in Union-Find every component has exactly one root, so counting negative parent entries gives the answer; equivalently, it's n minus the number of successful merges.

Alright — the DFS version first.

class Solution {
public:
    vector<vector<int>> graph;
    vector<bool> visit;

    int countComponents(int n, vector<vector<int>>& edges) {
        graph.assign(n, {});
        visit.assign(n, false);
        for (auto e : edges) {
            int u = e[0], v = e[1];
            graph[u].push_back(v); graph[v].push_back(u);   // undirected: store both ways
        }

        int cnt = 0;
        for (int i = 0; i < n; i++) {
            if (visit[i]) continue;
            cnt++;                          // unvisited node = new blob
            dfs(i);                        // mark the whole blob
        }
        return cnt;
    }

    void dfs(int u) {
        visit[u] = true;
        for (auto v : graph[u]) {
            if (visit[v]) continue;
            dfs(v);
        }
    }
};

It builds the adjacency list, then the outer loop skips visited nodes, and every node it doesn't skip adds one and starts a DFS that marks the whole blob.

And the Union-Find version — same idea, counting roots instead:

class Solution {
    vector<int> parent;                        // <0: root, -value = size; >=0: parent

    int Find(int x) {
        return parent[x] < 0 ? x : parent[x] = Find(parent[x]);  // path compression
    }

    void Union(int x, int y) {
        int rootX = Find(x), rootY = Find(y);
        if (rootX == rootY) return;            // already same group
        if (-parent[rootX] < -parent[rootY]) swap(rootX, rootY);
        parent[rootX] += parent[rootY];        // union by size
        parent[rootY] = rootX;
    }

public:
    int countComponents(int n, vector<vector<int>>& edges) {
        parent.resize(n, -1);
        for (auto &e : edges) Union(e[0], e[1]);

        int cnt = 0;
        for (int i = 0; i < n; i++)
            if (parent[i] < 0) cnt++;          // each root = one blob
        return cnt;
    }
};

A negative parent means a root, and its absolute value is the size. Find compresses the path, and Union attaches the smaller tree under the larger one.

One thing worth flagging — both loop the outer index over all n nodes, not just the ones touched by edges, so isolated nodes are counted correctly.

C
CANDIDATE

DFS is O(V + E) in time, and its space is also O(V + E), for the adjacency list plus the recursion stack.

Union-Find takes O(V + E·α(V)), where α is the inverse Ackermann function, so it's effectively linear — and its space is just O(V) for the parent array. It never stores the graph.

Oh, one more thing — if edges arrive one at a time and I need the running component count, Union-Find wins: keep a counter that starts at n and goes down by one on each successful merge. DFS would have to re-scan the whole graph each time.
