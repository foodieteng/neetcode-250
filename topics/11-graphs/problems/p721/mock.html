Hmm, let me think about this for a sec.

This problem reminds me of Union-Find, because grouping sets that share elements is exactly what it's built for. The key move is to make the emails the nodes, not the accounts.

I give every distinct email an integer id, and within each account I union its emails together. Because the same email string always maps to the same id, any two accounts that share an email get pulled into the same set automatically. Then I bucket emails by their root, sort each bucket, and prepend the owner's name.

Here's the plan.

// 1. map every email → id; record email[id], owner[id]
// 2. per account: Union(id[acc[1]], id[acc[i]]) for i>=2 (star, not clique)
// 3. bucket[Find(i)].push(email[i]); sort each; prepend owner[root]

One: map every email to an id, and record the email and its owner for each id.
Two: for each account, union its first email with each of the rest.
Three: bucket every email under its root, sort each bucket, and put the owner's name in front.

One thing worth flagging — I union in a star: the first email links to each of the rest, which is O(k) per account, not the O(k2) of connecting every pair. And a subtle indexing point — the mapping loop starts at i=1, so every email, including a lone one, gets registered, while the union loop starts at i=2, since acc[1] is the star center.

Does this approach sound good, or would you rather I think of another way?

class Solution {
    vector<int> parent;
    int Find(int x) { return parent[x] < 0 ? x : parent[x] = Find(parent[x]); }
    bool Union(int x, int y) {
        int rx = Find(x), ry = Find(y);
        if (rx == ry) return false;
        if (-parent[rx] < -parent[ry]) swap(rx, ry);
        parent[rx] += parent[ry]; parent[ry] = rx; return true;
    }
public:
    vector<vector<string>> accountsMerge(vector<vector<string>>& accounts) {
        unordered_map<string, int> id;
        vector<string> email, owner;          // id → email · id → name

        for (const auto& acc : accounts)       // ① give every email an id
            for (int i = 1; i < acc.size(); i++)
                if (!id.count(acc[i])) {
                    id[acc[i]] = email.size();
                    email.push_back(acc[i]);
                    owner.push_back(acc[0]);     // register lone emails too
                }

        parent.assign(email.size(), -1);

        for (const auto& acc : accounts)       // ② star union (not clique)
            for (int i = 2; i < acc.size(); i++)
                Union(id[acc[1]], id[acc[i]]);  // acc[1] links the rest

        unordered_map<int, vector<string>> buf;
        for (int i = 0; i < (int)email.size(); i++)
            buf[Find(i)].push_back(email[i]);       // ③ group by root

        vector<vector<string>> ans;
        for (auto& [root, group] : buf) {
            sort(group.begin(), group.end());          // emails in lexicographic order
            group.insert(group.begin(), owner[root]);  // name in front
            ans.push_back(group);
        }
        return ans;
    }
};

Find and Union are the usual size-based Union-Find. The first loop gives each new email the next id and records its owner. Then I size parent to the number of distinct emails, run the star unions, bucket each id under its root, and for each bucket sort it and insert owner[root] at the front.

One thing worth flagging — registering emails in the first loop from i=1 is what makes single-email accounts like Mary show up at all. They never get a Union, but they still get an id and a bucket.

Let N be the total number of emails. The union and find work is O(N·α(N)), effectively linear. The bottleneck is sorting the buckets — across all groups that's N emails, so O(N log N) overall. Space is O(N), for the map, the parent array, and the buckets.

Oh, one more thing — the same shape solves with plain DFS: build a graph where each account star-links its emails, then flood-fill each component. Union-Find is just tighter here, and it's the same core as counting components or finding a cycle edge — only the nodes changed from integers to email strings.
