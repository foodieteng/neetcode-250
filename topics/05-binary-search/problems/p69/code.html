完整實作// THE CODE

p69.cpp C++17 
class Solution {
public:
    int mySqrt(int x) {
        // 三個變數都必須是 long long:mid*mid 會衝到 2^60
        // (long long)x 的轉型不能省 —— x+1 在 int 裡算會溢位
        long long left = 0, right = (long long)x + 1;

        while (left < right) {
            long long mid = left + (right - left) / 2;

            if (mid * mid > x) {
                right = mid;          // P 為真 → mid 可能就是第一個 T,保留
            } else {
                left = mid + 1;      // P 為假 → mid 是 F,整個跨過
            }
        }

        // 收斂後 left = 第一個 T;退一格才是最後一個 F = floor(sqrt(x))
        return (int)(left - 1);
    }
};

那個 +1 和那個 −1// THE TWO OFFSETS

這支程式有兩個看起來可以隨手拿掉的常數,兩個都不能拿,而且原因完全不同。

// right = x + 1 的 +1:保證真值表裡「有 T 可找」 述詞 P(m) = (m·m > x),二分的前提是候選區間裡至少有一個 T 右界取 x + 1 時:(x+1)² = x² + 2x + 1 > x 對所有 x ≥ 0 恆成立 ⇒ 必有 T ✓ 右界取 x 時:x = 0 → 區間 [0, 0) 是空的,迴圈不跑,return 0 - 1 = -1 ✗ x = 1 → 區間 [0, 1),m=0,P 假 → l=1,return 0 ✗(正解 1) 實測(220 萬個測試點):右界寫 x 只在 x = 0 與 x = 1 失敗,共 2 次 // 只錯兩個點 —— 但兩個都是合法輸入,而且是最容易被跳過的測資
// return left - 1 的 -1:把「第一個 T」翻成「最後一個 F」 二分收斂後,left 指向第一個滿足 m·m > x 的 m 我們要的是最大的滿足 m·m ≤ x 的 m —— 正好是它的前一格 x = 8:真值表 F F F T T T T T T T,left = 3,答案 = 2 ✓ x = 9:真值表 F F F F T T ... ,left = 4,答案 = 3 ✓(9 是完全平方) 實測:忘了 -1(直接 return l)→ 939024 個測試點全錯 // 「找第一個 T」與「找最後一個 F」是同一次二分的兩個讀法,差一格
x = 0 是這題的照妖鏡:left 收斂到 1,return 0 —— 正確,而且不用特判。 但只要右界寫成 x,同一個輸入就會回 −1。

邊界與陷阱// PITFALLS

測試點共 939024 個:x = 0..300000 全掃、所有完全平方數的三鄰居 (k²−1, k², k²+1)(k = 0..46340)、值域最頂端 20 萬個、加上 30 萬個隨機。

陷阱為什麼錯實測
l / r / m 用 int m 會到 2³⁰,m·m 溢位,狀態直接壞掉 220 萬點錯 1987086
x=1000000 → 458753
x=2³¹−1 → 不收斂
只把 m·m 退回 int 算 同上,溢位就在那一次乘法 錯 792749/939024
最小失敗 x=92681 → 65536(正解 304)
right = x + 1 少了 (long long) x + 1 在 int 裡算,x = 2³¹−1 時有號溢位(UB) UBSan 實錘
但 -O2 下碰巧算對 —— 見下方說明
right = x(少了 +1) 真值表裡可能一個 T 都沒有,二分無界可收 錯 2 次:x=0 → −1、x=1 → 0
return left(忘了 −1) 回傳的是第一個 T,不是最後一個 F 錯 939024/939024(全錯)
> 寫成 >= 述詞變成 m² ≥ x,完全平方數時交界整個左移一格 錯 46899/939024
x=0 → −1
while (left < right) 寫成 <= l == r 時 m == r,r = m 讓狀態不動 死迴圈,x=0 即觸發
那個「碰巧算對」的轉型,才是最危險的一個

把 (long long)x + 1 寫成 x + 1(讓 long long right = x + 1; 去接), 我原本預期 x = 2³¹−1 會直接答錯。實測在 -O2 下它回了 46340,答案是對的。

但那不代表沒問題。用 g++ -O0 -fsanitize=undefined 跑同一筆輸入,立刻報: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'。

有號整數溢位是 UB —— 這次編譯器產生的碼恰好還能用,換一版編譯器、換個最佳化等級就未必。 「跑起來沒錯」證明不了記憶體或型別安全,那要靠 sanitizer。(和 81 的越界讀取是同一類教訓。)
