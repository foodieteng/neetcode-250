Hmm, let me think about this for a sec.

A naive approach would be to count up from zero until the square passes x. That's O(√x), about 46,000 steps at worst. It would pass, but it ignores the structure I just noticed.

This problem reminds me of binary search on a predicate. That row of F's and T's is exactly what binary search wants. I never need a sorted array — I need one yes/no question whose answer flips at most once as I walk along. Here the question is m·m > x, and it's monotone because squaring is increasing on non-negative numbers.

So: binary search for the first T, then step back one to get the last F. That's O(log x) — about 31 rounds instead of 46,000. And it never touches a double, so there's no rounding to argue about.

C
CANDIDATE

Here's the plan.

// predicate
P(m) = (m·m > x)  →  F F F T T T  (flips once)
// search range
left = 0, right = x + 1  ← +1 guarantees at least one T exists
// shrink
P true  → right = mid    (mid might BE the first T — keep it)
P false → left = mid + 1 (mid is an F — skip past it)
// read off
return left - 1  ← first T minus one = last F

One: ask whether m·m > x.
Two: search from 0 to x + 1 — true moves right = mid, false moves left past mid.
Three: return left - 1.

Neither offset can be dropped. The +1 guarantees a T exists, since (x+1)² always beats x; with just x, zero would return -1. The -1 turns the first T into the last F.

One thing worth flagging — mid·mid peaks on the very first round, not at the answer: about 260, roughly half a billion times INT_MAX. So left, right and mid all have to be long long. It's tempting to say "the answer is only 46,000, so int is fine" — that's backwards.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up.

class Solution {
public:
    int mySqrt(int x) {
        // all three must be long long: mid*mid reaches 2^60
        // the (long long)x cast can't be dropped — x+1 computed in int overflows
        long long left = 0, right = (long long)x + 1;

        while (left < right) {
            long long mid = left + (right - left) / 2;

            if (mid * mid > x) {
                right = mid;          // P true → mid may be the first T, keep it
            } else {
                left = mid + 1;      // P false → mid is an F, skip past it
            }
        }

        // after converging, left = first T; step back one for the last F = floor(sqrt(x))
        return (int)(left - 1);
    }
};

It's one loop: if mid * mid > x, right = mid; otherwise left moves past mid; then I return left - 1.

One thing worth flagging: the cast in (long long)x + 1. Without it, x + 1 is computed in int before being widened, and at INT_MAX that's signed overflow.

And I want to be honest about how I know that matters, because it surprised me. Built at -O2, the version without the cast still returned 46340 for INT_MAX — the right answer. Then the undefined behaviour sanitizer (-fsanitize=undefined) immediately reported signed integer overflow: 2147483647 + 1. The optimizer just happened to emit code that worked. Passing tests proves the logic, not the types.

C
CANDIDATE

The time complexity is O(log x) — the range starts at 231 and halves each round, so about 31 rounds; x = INT_MAX takes exactly 31. The space complexity is O(1), three variables.

That's 31 multiplications versus roughly 46,000 for counting up.

On the peak magnitude: mid·mid tops out at 260, which is 12.5% of LLONG_MAX. So long long is enough, but only by a factor of 8 — worth knowing rather than assuming.

Oh, one more thing — if you widened x itself to long long, this code would break: mid·mid would need about 124 bits, and there's no wider built-in type. The fix is to rewrite the comparison as a division: mid > x / mid. Same meaning for mid ≥ 1, and it can't overflow.
