重點回顧// RECAP

面向要記住的那一句
形狀旋轉後 = 兩段各自遞增,最小值是斷崖的底
參考點右端 nums[r] —— 唯一「旋不旋轉都成立」的錨
往右收nums[m] > nums[r] ⇒ 斷崖在 (m, r] ⇒ m 出局 ⇒ l = m + 1
往左收nums[m] < nums[r] ⇒ 同段 ⇒ m 還是候選 ⇒ r = m(不減 1)
迴圈條件while (l < r) —— 寫成 <= 會死迴圈,不是答錯
死等號l < r ⇒ m < r,加上值相異 ⇒ nums[m] != nums[r],所以 > 與 >= 等價
不會退化值相異 ⇒ 每輪必砍半。實測 n=5000 → 13 輪 = ceil(log₂ n)
和 81 的差別81 允許重複 ⇒ 相等時分不出方向 ⇒ 最壞 O(n)

範例 Trace// 有斷崖 / 沒斷崖

例 A · nums = [4,5,6,7,0,1,2](官方範例 2,動畫用的也是這個)。

// 第 1 輪 l=0 r=6 m=3 nums[3] = 7 nums[6] = 2 7 > 2 → m 還在高的那段,斷崖夾在 (3, 6] 之間 → l = m + 1 = 4 區間 -> [4, 6]
// 第 2 輪 l=4 r=6 m=5 nums[5] = 1 nums[6] = 2 1 < 2 → m 與 r 同段遞增,最小值在 m 或其左 → r = m = 5 區間 -> [4, 5]
// 第 3 輪 l=4 r=5 m=4 nums[4] = 0 nums[5] = 1 0 < 1 → r = m = 4 區間 -> [4, 4]
// OUTPUT l == r == 4 → 跳出迴圈 return nums[4] = 0 共 3 輪 // 0

例 B · nums = [11,13,15,17](官方範例 3)—— 「旋轉 n 次 = 完全沒動」,這是最容易寫錯的那一類。

// 正解:跟右端比 第 1 輪: l=0 r=3 m=1 nums[1] = 13 nums[3] = 17 13 < 17 → r = m = 1 第 2 輪: l=0 r=1 m=0 nums[0] = 11 nums[1] = 13 11 < 13 → r = m = 0 l == r == 0 → return nums[0] = 11 // 沒有斷崖 ⇒ 每一輪都往左收 ⇒ 自然停在 index 0,不必特判
// 錯法:跟左端比 —— 同一筆輸入 第 1 輪: l=0 r=3 m=1 nums[1] = 13 nums[0] = 11 13 > 11 → l = m + 1 = 2 第 2 輪: l=2 r=3 m=2 nums[2] = 15 nums[2] = 15 不大於 → r = m = 2 l == r == 2 → return nums[2] = 15 // 15,正解是 11 —— 指標一路往右衝過頭
例 B 是這題的照妖鏡。nums[m] > nums[l] 在沒旋轉時恆成立, 所以「跟左端比」的版本會一路往右。實測窮舉全部 55 種結構,跟左端比錯 36 組, 而跟右端比 0 組。

應用題// APPLICATION

App 1. 改成回傳「最小值的索引」(等價於問陣列被旋轉了幾次)。要改什麼?
App 2. 拿掉「所有整數相異」這條約束(就是 LeetCode 154)。這份程式碼還對嗎?要怎麼補?複雜度變成多少?
App 3. 改成找最大值。直覺上「把兩個分支反過來」就好,對嗎?
// ANSWERS
A1. 因為只有右端這個錨,對「有旋轉」和「沒旋轉」都成立。

比較兩個關係:
最小值在 nums[r] 的左側或就是它 —— 永遠成立。理由很樸素:nums[r] 是區間最右邊那格,它右邊沒有東西,最小值不可能跑到那裡去。
最小值在 nums[l] 的右側 —— 只有真的旋轉過才成立。完全沒旋轉時,最小值就是 nums[l] 本身。

而題目說「旋轉 1 到 n 次」,旋轉 n 次就等於沒動 —— 這個 case 題目還特地寫在敘述裡([0,1,2,4,5,6,7] 旋轉 7 次)。所以「跟左端比」的版本必定在這一類輸入上壞掉:nums[m] > nums[l] 恆成立,指標一路往右衝。

實測(窮舉全部 55 種結構):跟 nums[l] 比錯 36/55,最小反例 [1,0] 答 1(正解 0);跟固定的 nums[0] 比錯 9/55,最小反例 [0,1] 答 1;跟 nums[r] 比錯 0/55。選參考點不是風格問題,是正確性問題。
A2. 因為兩個分支能證明的事情不一樣。

nums[m] > nums[r]:若 m 和 r 在同一段遞增裡,必有 nums[m] ≤ nums[r]。既然反了,斷崖一定夾在 (m, r] 之間,而 m 本身落在高的那一段 —— 它被證明不可能是最小值,可以安全跨過 ⇒ l = m + 1。

nums[m] < nums[r]:m 和 r 同段,所以 (m, r] 全都比 nums[m] 大,最小值落在 [l, m]。但m 自己還可能就是最小值 —— 例如 [0,1] 第一輪 m = 0,答案正是它。證不出 m 出局,就只能保留 ⇒ r = m。

寫成 r = m - 1 會把答案丟出區間:實測 55 種結構錯 17 組,最小反例 [2,0,1] 答 2(正解 0)。

這條規則跨題通用:1095 找峰時「下坡」那條也是同樣理由不能減 1,410 的可行分支 right = mid 也是。能證偽的邊界才 +1,證不了的要保留。
A3. 不是漏寫 —— 那個等號永遠不會被觸發,所以 > 和 >= 完全等價,兩種都對。

證明:迴圈條件是 l < r,所以 m = l + (r-l)/2 滿足 l ≤ m < r —— m 和 r 必定是不同的索引。而題目保證「所有整數相異」,所以 nums[m] != nums[r]。

實測:窮舉所有 n ≤ 200 的旋轉量,在全部 140495 次比較中,m >= r 出現 0 次、nums[m] == nums[r] 出現 0 次。把 > 改成 >= 跑完 55 種結構,錯 0 組。

但這是「借來的安全」,借的是題目的約束。一旦允許重複值(見 App 2),等號立刻會發生,而那時分不出斷崖在哪一側 —— 這正是 81 和 154 難那麼多的原因。和 P4 的哨兵是同一類事情:安全來自約束,不是來自寫法。
A4. 會死迴圈,不是答錯。

推導:當區間收到 l == r 時,l <= r 仍然成立,迴圈繼續跑。此時 m = l + (r-l)/2 = l = r,於是判斷式變成 nums[r] > nums[r] —— 恆假。走 else 分支 r = m = r,l 和 r 都沒有變。下一輪一模一樣,永遠出不去。

實測:[0,1] 就足以觸發;[2,0,1] 也是。

為什麼這題必須用 <:這是收斂型二分 —— 答案保證存在,而且就是收斂點本身,所以要一路縮到 l == r 然後直接回傳那一格。<= 是給「可能找不到、要能回 −1」的搜值型用的(例如 1095 的後兩段、704)。模板由「答案會不會不存在」決定,不是隨手挑的。

順帶一提,另一種也會死迴圈的改法是 l = m + 1 寫成 l = m:區間剩兩格時 m == l,等於沒動。實測 55 組錯 45 組,[1,0] 即觸發。
A5. 不矛盾 —— 兩題問的問題不一樣,錨當然不一樣。

153 問的是「斷崖在我的哪一側」。要回答它,需要一個「最小值絕對不會在它右邊」的參考點,而 nums[r] 天生就是(它右邊沒東西)。

33 問的是「哪一半是有序的」。要回答它,需要比較區間的起點和中點:nums[l] ≤ nums[m] 就代表左半 [l, m] 沒有跨過斷崖、是有序的,接著才能用「target 在不在這個有序範圍內」決定往哪走。拿右端來比答不出這個問題。

換句話說:
153 要的是一個穩定的極值錨 → 右端。
33 要的是一段已知有序的區間 → 左端 + 中點。

結論:參考點是被「你要問什麼」決定的,不是習慣、也不是背下來的。如果覺得「旋轉陣列就該跟某某比」,那多半是把某一題的結論當成了通則 —— 81 再加上重複值之後,連 33 的那套判準都得補一手。
App 1. 把最後一行 return nums[left]; 改成 return left;,其他一個字都不用動。

因為這個二分本來就是在找位置,收斂點 left 就是最小值的索引,只是原題要值所以把索引丟掉了。

實測:所有 n ≤ 300 × 所有旋轉量共 45150 組,與 min_element 算出的索引比對不一致 0。

順帶回答「旋轉了幾次」:設最小值索引為 i,則原陣列是被右移了 i 次(等價於左移 n − i 次)。沒旋轉時 i = 0。這也是為什麼 153 常被當成其他旋轉陣列題的前置步驟 —— 拿到 i 之後,整條陣列就能用 (idx + i) % n 映射回「沒旋轉」的座標,後續直接套一般二分。
App 2. 會壞,要補一個分支,而且複雜度從 O(log n) 掉到最壞 O(n)。

為什麼壞:A3 說過,現在的程式碼把 nums[m] == nums[r] 併進了 else(往左收)。值相異時那個等號不會發生,但一旦允許重複,nums[m] == nums[r] 時根本分不出斷崖在哪一側 —— 例如 [2,2,1,2] 和 [2,1,2,2],m 和 r 看起來完全一樣,最小值卻在不同邊。實測拿原版去跑含重複值的資料:300000 組錯 4319 組,最小反例 [2,2,1,2]。

怎麼補 —— 拆成三個分支:
nums[m] > nums[r] → l = m + 1(不變)
nums[m] < nums[r] → r = m(不變)
nums[m] == nums[r] → r--,保守地丟掉一格。安全的理由是:nums[r] 和 nums[m] 一樣,所以就算 nums[r] 是最小值,nums[m] 也是,答案不會因為丟掉 r 而消失。

實測:加上 r-- 後,300000 組大量重複值的測資不一致 0。

複雜度:全部相等時每輪只縮一格 —— 實測 n = 5000 全 1 的陣列跑 4999 輪 = n − 1,確實是 O(n)。這就是 81 那題的同一個病灶,也是 154 為什麼比 153 難的全部原因。
App 3. 不對 —— 這是本頁最值得記的一個「直覺陷阱」。

沿用「跟右端比」只把分支反過來(nums[m] > nums[r] → r = m,否則 l = m + 1),實測 45150 組錯 44551 組,最小反例 [2,0,1]。

為什麼垮:nums[m] < nums[r] 這個情況指不出唯一方向。有斷崖時,m 在低的那段,最大值在它左邊;沒有斷崖時,整條遞增,最大值是 nums[r] 本身,在它右邊。同一個觀察對應兩個相反的動作 —— 二分的前提直接消失。

正解有兩條,都實測過 0 錯(45150 組):
① 改用左端當錨 + 上取整的 mid。對「最大值」而言,穩定的錨是左端(最大值永遠在 nums[l] 的右側或就是它):
mid = l + (r - l + 1) / 2;　nums[mid] >= nums[l] ? l = mid : r = mid - 1;
+1 是必要的 —— 因為有一條是 l = mid,不上取整就會死迴圈。實測 n ≤ 3125 最多 12 輪,仍是 O(log n)。
② 直接沿用本題,找到最小值索引 i 後回傳 nums[(i - 1 + n) % n]。因為最大值就在斷崖頂,也就是最小值的前一格(沒旋轉時繞回最後一格)。

教訓:找 min 用右端、找 max 用左端 —— 錨要挑那個「答案絕對不會越過它」的端點。這不是對稱地把符號反過來就能得到的,我第一次就是這樣猜,然後被 45150 組測資打回來。
