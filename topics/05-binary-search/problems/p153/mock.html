Hmm, let me think about this for a sec.

A naive approach would be to scan and take the min. Correct, but that's O(n), and the problem asks for O(log n).

This problem reminds me of binary search on a predicate rather than on a sorted array. The array as a whole is not sorted, so I can't compare against a target and go left or right. But binary search never really needed "sorted" — it needs one O(1) question that tells me which half to keep.

Here that question is: am I standing left of the cliff, or right of it? To answer it I need a fixed reference point to compare against, and picking that reference is the whole problem. There are two obvious candidates: the left end and the right end. And they are not equally good.

P — plan
C
CANDIDATE

Here's the plan.

// two candidate anchors
"min is at or left of nums[r]" → always true
  (nothing sits right of nums[r])
"min is right of nums[l]"     → only if actually rotated
  (with no cliff, the min IS nums[l])
// so: compare nums[m] against nums[r]
nums[m] > nums[r] → cliff in (m, r] → m is out   → l = m + 1
nums[m] < nums[r] → same run as r    → m still in → r = m

One: anchor on nums[r]. The minimum is always at or left of it — nothing sits to its right — but it's right of nums[l] only if the array is actually rotated.
Two: if nums[m] > nums[r], the cliff sits between them and m is out, so l = m + 1.
Three: otherwise m shares r's run and might be the minimum, so r = m.

One thing worth flagging: that asymmetry is deliberate — I only skip m when I can prove it's out. Un-rotated, I just shrink left to index 0, for free.

The trade-off: this rests on unique values. m is always left of r, so they never compare equal. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. Compare mid with right, skip past mid when it's bigger, otherwise pull right down to mid, and return where the two meet.

class Solution {
public:
    int findMin(vector<int>& nums) {
        int left = 0, right = nums.size() - 1;

        while (left < right) {
            int mid = left + (right - left) / 2;

            // the anchor is always the RIGHT end — not nums[left], not nums[0]
            if (nums[mid] > nums[right]) {
                left = mid + 1;   // cliff is right of mid; mid can't be the min
            } else {
                right = mid;       // mid shares right's run; mid is still a candidate
            }
        }

        return nums[left];       // converged to one slot: that's the answer
    }
};

One thing worth flagging: it's while (left < right), not <=. This search converges — the answer is the meeting point.

With <=, once left == right, mid == right too, the test is always false, and right = mid changes nothing. That's an infinite loop, not a wrong answer, and [0,1] is enough to trigger it.

Same trap on the other side: write left = mid instead of mid + 1, and with two slots left, nothing moves.

The time complexity is O(log n) — every round drops at least half the range. The space complexity is O(1), three integers.

In the worst case, n = 5000: across every rotation it takes 13 rounds, exactly ceil(log2 5000). No overflow concerns — I only compare values.

Oh, one more thing — the uniqueness guarantee is doing more work than it looks. With duplicates, nums[m] == nums[r] can happen, and then I can't tell which side the cliff is on: [2,2,2,1,2] and [2,1,2,2,2] look identical from m and r, but the minimum is on different sides.

The fix is a third branch that does right-- — safe, but it sheds one slot, so the worst case degrades to O(n). This problem is O(log n) because of that constraint.
