Hmm, let me think about this for a sec.

A naive approach would be to just scan every cell. Correct, but O(n), and the problem asks for log time.

This problem reminds me of ordinary binary search with one extra question in front. There are two ways to go. One: find the break point first with its own binary search, then run a normal search on whichever piece the target belongs to. Two: do it in a single pass, deciding each round which half is sorted.

Both are O(log n). I'll do the single pass, since it's one loop. I'll mention the two-step version as the easier-to-debug option.

Here's the plan.

// closed range [left, right], shrink until one cell is left
left = 0, right = n - 1
while left < right:
  mid = left + (right - left) / 2
  if nums[left] <= nums[mid]: // left half is sorted
    in range? right = mid  :  left = mid + 1
  else: // right half is sorted
    in range? left = mid + 1  :  right = mid
return nums[left] == target ? left : -1

One: keep a closed range [left, right] and shrink it to one cell.
Two: each round, ask which half is sorted, and whether the target sits inside that half's range, and go that way or the other.
Three: check that last cell against the target.

One thing worth flagging — the range check and the shrink have to agree about mid. On the left-sorted branch I set right = mid, so mid stays a candidate and the range test must include it: target <= nums[mid]. On the right-sorted branch I set left = mid + 1, so mid is stepped over and the test must exclude it: nums[mid] < target — otherwise a target sitting exactly on mid gets skipped.

The trade-off: four branches make it easy to flip a sign; the two-step version is safer but costs two searches. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int search(vector<int>& nums, int target) {
        int left = 0, right = nums.size() - 1;   // closed range [left, right], shrink to one cell

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (nums[left] <= nums[mid]) {          // (1) left half [left, mid] sorted (=: mid may == left)
                if (nums[left] <= target && target <= nums[mid]) {
                    right = mid;                // inside the sorted half -> go there (keep mid)
                } else {
                    left = mid + 1;            // not inside -> it can only be in the other half
                }
            } else {                            // (2) otherwise right half [mid, right] sorted
                if (nums[mid] < target && target <= nums[right]) {
                    left = mid + 1;            // inside the sorted half -> go there (skip mid)
                } else {
                    right = mid;                // not inside -> it can only be in the other half
                }
            }
        }

        return nums[left] == target ? left : -1;  // the one candidate, still verify it
    }
};

If nums[left] <= nums[mid], the left half is sorted, and I move into it or past it; otherwise the right half is sorted, with the mirror moves. After the loop, I return left only if that cell equals the target.

One thing worth flagging — the <= in that first test. With two cells left, mid equals left, and a single cell must count as sorted. With a strict <, the code calls the right half sorted and shrinks the wrong way: [2,0], looking for 0, returns -1 instead of 1.

CANDIDATE

The time complexity is O(log n). All four branches cut the range in half, so the extra question is just a constant — two or three comparisons per round instead of one. The space complexity is O(1).

In the worst-case scenario it's about 13 rounds at 5000 elements, same as a plain binary search.

Oh, one more thing — this leans hard on the values being distinct. With duplicates, when nums[left] equals nums[mid], you can't tell a flat run from one that hides the break. [0,1,0,0,0], looking for 1, would return -1. The fix is a third branch that just does left++, which is safe but drops the worst case to O(n).
