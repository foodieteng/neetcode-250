Hmm, let me think about this for a sec.

A naive approach would be to try k = 1, then 2, and stop at the first one that works. That's correct, but k can run to 109 and each try costs 104, so the worst case is 1013 operations.

This problem reminds me of binary search — but not on the input. On the answer. Computing k directly is hard, but checking a given k is easy: one pass, summing ceil(pile / k). And the check is monotonic: if a speed works, every faster speed also works.

So the speeds form a F F T T pattern, and I want the first T. It's the same skeleton as searching a sorted array, with the lookup swapped for a simulation.

Here's the plan.

// search the RANGE OF ANSWERS, half-open [1, max+1)
left = 1, right = max(piles) + 1
check(k) = sum of ceil(pile / k) <= h
while left < right:
  mid = left + (right - left) / 2
  if check(mid): right = mid   // fits — maybe slower still fits
  else:          left = mid + 1 // too slow — drop it
return left

One: search speeds in the half-open range [1, max+1).
Two: a speed fits if the per-pile ceilings sum to at most h.
Three: if mid fits, keep it as the right end; otherwise move left past it; return left.

One thing worth flagging — each bound has a reason. The low end is 1: speed 0 never finishes and would divide by zero. Faster than the biggest pile buys nothing, so that's the top. The +1 only reserves a "nothing worked" slot; an answer always exists, so [1, max] works too. And it's <=: finishing exactly on the hour counts.

The trade-off: each step costs O(n), but 1013 drops to about 3 × 105. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int minEatingSpeed(vector<int>& piles, int h) {
        // range [1, max+1); [1, max] is equally correct (an answer is guaranteed)
        int left = 1;
        int right = *max_element(piles.begin(), piles.end()) + 1;

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (getTime(piles, mid) <= h) {
                right = mid;              // fits → maybe slower still fits, keep mid
            } else {
                left = mid + 1;          // too slow → skip past mid
            }
        }

        return left;                     // first feasible speed; it always exists
    }

    int getTime(vector<int>& piles, int k) {
        int t = 0;

        for (int p : piles) {
            t += ceil((double)(p) / k);   // round up per pile (a partial hour is still an hour)
        }

        return t;
    }
};

One thing worth flagging — the ceiling is taken per pile and only then summed; summing first is the broken formula from earlier.

And the accumulator is an int. At k = 1 the total could reach 1013, but the search only probes down to about half the answer, where the time is at most 2h — under 2 × 109, so an int survives. That argument leans on h's upper bound, so long long is the safer habit.

• With h = 6 → 23.

The time complexity is O(n log C), where C is the largest pile — about 30 rounds, each a 104 pass, so roughly 3 × 105 operations. The space complexity is O(1). That's the general rule for this pattern: rounds times the cost of one check.

Oh, one more thing — about the ceiling. I used ceil((double)p / k). That's safe here: values up to 109 are exact in a double, and when the true quotient is a whole number, correctly rounded division returns it exactly. Still, (p + k - 1) / k is the habit I'd rather build — integer division has no precision cliff.

I also random-tested this against a long long, integer-ceiling version on 20,000 cases, with no disagreement.
