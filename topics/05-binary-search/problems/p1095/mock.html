Alright, let me code this up. The main function finds the peak, then calls one helper twice — ascending on the left, descending on the right.

// MountainArray is provided by the judge: only get(index) and length()

class Solution {
    // binary search inside [lo, hi], a range known to be monotonic
    // ascending says whether it's the rising or the falling run
    int binarySearch(MountainArray& arr, int target, int lo, int hi, bool ascending) {
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            int value = arr.get(mid);

            if (value == target) {
                return mid;
            }

            // rising: too small → go right; falling: too small → go left
            if ((value < target) == ascending) {
                lo = mid + 1;
            } else {
                hi = mid - 1;
            }
        }

        return -1;
    }

public:
    int findInMountainArray(int target, MountainArray& mountainArr) {
        int n = mountainArr.length();

        // PHASE 1 · binary search the slope for the peak (two reads per round)
        int left = 0, right = n - 1;
        while (left < right) {
            int mid = left + (right - left) / 2;

            if (mountainArr.get(mid) < mountainArr.get(mid + 1)) {
                left = mid + 1;   // rising → mid can't be the peak, skip it
            } else {
                right = mid;       // falling → mid may be the peak, keep it
            }
        }
        int peak = left;

        // PHASE 2 · rising left half, peak included; first, for the smallest index
        int index = binarySearch(mountainArr, target, 0, peak, true);
        if (index != -1) {
            return index;
        }

        // PHASE 3 · falling right half
        return binarySearch(mountainArr, target, peak + 1, n - 1, false);
    }
};

One thing worth flagging is the helper's direction test: (value < target) == ascending. If the two booleans agree, go right; if they disagree, go left. On a falling run, "too small" means go left, so this one expression handles both sides.

Drop the == ascending part and the descending half breaks — on [0,3,2,1] looking for 1, it returns -1 instead of 3. And get(mid + 1) is always in range, because the peak loop runs only while left < right.

CANDIDATE

Time is O(log n) — three binary searches back to back. Space is O(1), just a few index variables.

But the number that actually matters here is calls to get: 4 log n, about 56 at the top end. I measured the worst case at n = 104 across every peak position and target: 53 calls, leaving 47 of headroom.

No overflow risk — values are only compared, never added, and the midpoint is lo + (hi − lo) / 2.

Oh, one more thing — a hash-map cache only takes the worst case from 53 down to 50, so I'd leave it out. And this all rests on strict monotonicity: on [0,0,1,0] looking for 0, this code returns 1 when the answer is 0.
