重點回顧// RECAP

面向要記住的那一句
真正的限制不是時間,是 get 只能呼叫 100 次(n 可到 10⁴)
整體結構找峰 → 左半升序二分 → 右半降序二分,三次二分串聯
找峰比較 get(m) 與 get(m+1):上坡 l = m+1、下坡 r = m(不減 1)
兩種模板找峰是 while(l<r) 收斂型;搜值是 while(lo<=hi) 可失敗型
最小索引靠先搜左半解決 —— 嚴格單調 ⇒ 一個值最多出現兩次,左半那個必定較小
合併升降序(v < target) == ascending 是 XNOR:一致往右、不一致往左
呼叫成本4 · log₂ n(找峰每輪 2 次),n=10⁴ 實測最壞 53,餘裕 47
型別值只做比較不做算術 ⇒ int 完全安全
前提嚴格單調。允許平台就會壞(見 App 1)

觀念題// CONCEPT Q&A

Q1. 找峰的兩個分支不對稱:上坡寫 left = mid + 1,下坡卻寫 right = mid 而不是 mid - 1。為什麼?寫成 mid - 1 會怎樣?
Q2. 把 (value < target) == ascending 展開成四種情況,說明每種該往哪邊縮。這個式子等價於哪個邏輯運算?
Q3. 題目要的是最小索引。程式裡卻沒有任何「找到後再往左壓」的邏輯 —— 那最小索引是怎麼保證的?請說出依賴的前提。
Q4. 算出 n = 10⁴ 時 get 的呼叫次數上界。為什麼常數是 4 而不是 3?出題者把上限訂在 100 有什麼用意?
Q5. 峰到底該歸給左半還是右半?列出所有可行的分法,並指出唯一會出錯的那一種。

範例 Trace// 兩個例子:走完三段 / 最小索引

例 A · arr=[1,3,5,7,6,4,2],target=4 —— 左半找不到,三個階段全部走一遍(動畫用的就是這個)。

// PHASE 1 · 找峰 R1: l=0 r=6 m=3 get(3)=7 get(4)=6 7 > 6 下坡 → r = m = 3 R2: l=0 r=3 m=1 get(1)=3 get(2)=5 3 < 5 上坡 → l = m+1 = 2 R3: l=2 r=3 m=2 get(2)=5 get(3)=7 5 < 7 上坡 → l = m+1 = 3 l == r → peak = 3 (值 7) // 3 輪 x 2 次 = 累計 6 次 get
// PHASE 2 · 左半升序二分 [0, 3] R1: lo=0 hi=3 mid=1 v=3 3 < 4,升序 → 往右 lo = 2 R2: lo=2 hi=3 mid=2 v=5 5 > 4,升序 → 往左 hi = 1 lo(2) > hi(1) → 左半沒有 4,回傳 -1 // 累計 8 次 get
// PHASE 3 · 右半降序二分 [4, 6] R1: lo=4 hi=6 mid=5 v=4 命中 → 回傳 5 // 累計 9 次 get
// OUTPUT 5 總共 9 次 get(上限 100)

例 B · arr=[1,2,3,4,5,3,1],target=3(官方範例) —— 3 同時出現在 index 2 和 index 5,正好考「最小索引」。

// PHASE 1 · 找峰 R1: l=0 r=6 m=3 get(3)=4 get(4)=5 上坡 → l = 4 R2: l=4 r=6 m=5 get(5)=3 get(6)=1 下坡 → r = 5 R3: l=4 r=5 m=4 get(4)=5 get(5)=3 下坡 → r = 4 peak = 4 (值 5) // 累計 6 次 get
// PHASE 2 · 左半升序二分 [0, 4] R1: lo=0 hi=4 mid=2 v=3 命中 → 回傳 2 // 累計 7 次 get。PHASE 3 完全沒跑到
// OUTPUT 2 // index 5 的值也是 3,但左半先命中就 return 了 —— 最小索引免費拿到
例 B 就是「順序不能換」的證據。若先搜降序半,這題會答 5。 實測把順序顛倒去跑 6360 組窮舉,錯 1100 組,最小反例是 [0,1,0] 找 0 → 答 2(正解 0)。

應用題// APPLICATION

App 1. 題目把「嚴格遞增/遞減」放寬成「非嚴格」(允許連續相等的平台)。這份程式碼還對嗎?請指出哪幾個地方會壞,並給具體反例。
App 2. 改成谷形陣列(先嚴格遞減、再嚴格遞增),一樣求 target 的最小索引。要改哪幾行?呼叫成本會變嗎?
App 3. 假設 get 的上限被砍到 45 次(n 仍是 10⁴)。現在這份程式碼會被判 WA 嗎?如果會,你要怎麼把呼叫數壓下來?
// ANSWERS
A1. 因為兩個分支拿到的資訊量不一樣。

上坡(get(m) < get(m+1)):m 落在遞增段裡,而遞增段的每一格都比右鄰小,所以 m 可以被證明不是峰 —— 能安全排除,寫 left = mid + 1。

下坡(get(m) > get(m+1)):m 有兩種可能 —— 它就是峰,或它在遞減段裡。兩種都只能推出「峰不在 m 右邊」,推不出「m 不是峰」,所以 m 必須留在候選區間裡,只能寫 right = mid。

寫成 mid - 1 會把峰丟出區間。實測:窮舉長度 3–8、值域 0–6 的全部 4363 座山,right = mid - 1 有 2242 座算錯峰位置;最小反例 [0,1,0] —— 真峰在 1,卻得到 0。同樣的窮舉下,原版 right = mid 錯 0 座。這也是二分的通則:能證偽的邊界才 +1,不能證偽的要保留。
A2. 四種情況:

① 遞增 + 值太小 → 更大的在右邊 → lo = mid + 1。式子:true == true = true ✓
② 遞增 + 值太大 → 往左 → hi = mid - 1。式子:false == true = false ✓
③ 遞減 + 值太小 → 遞減段裡更大的在左邊 → hi = mid - 1。式子:true == false = false ✓
④ 遞減 + 值太大 → 往右 → lo = mid + 1。式子:false == false = true ✓

等價於 XNOR(同或):兩個布林值相同就往右,不同就往左。白話版是「遞減段就是把比較反過來」。

省略 == ascending 的代價:降序半的方向全反,整個右半段失效。實測最小反例 arr=[0,3,2,1], target=1 → 回傳 −1(正解 3);6360 組窮舉錯 728 組。
A3. 靠「先搜左半、找到就 return」這個順序,不需要任何額外邏輯。

依賴的前提是「嚴格」單調。嚴格遞增段內不會有重複值,嚴格遞減段內也不會 —— 所以任何 target 在整座山上最多出現兩次(左半一次、右半一次)。而左半的索引 ≤ peak < peak+1 ≤ 右半的索引,左邊那個必定較小。先搜左半、命中即回,拿到的自然是最小索引。

對比 704:那裡陣列可以有重複值,要拿第一個出現位置就得用 lower_bound 式的「命中後繼續往左壓」。這題把那個工作外包給了「嚴格」這個保證,所以程式碼裡看不到它。前提一旦拿掉就會壞 —— 見 App 1。
A4. 上界 4 · log₂ n,n = 10⁴ 時是 56;實測最壞 53。

常數為什麼是 4:三次二分各約 log₂ 10⁴ ≈ 13.3 → 14 輪,但找峰那次每輪要讀 get(mid) 和 get(mid+1) 兩格,所以是 2×14 + 1×14 + 1×14 = 56,不是 3×14 = 42。

實測(窮舉所有峰位置 × 所有 target,含必失敗的 target):
n=3 → 6、n=100 → 26、n=1000 → 38、n=10⁴ → 53。每 10 倍 n 多 5~7 次,吻合 4·log₂n。

100 這個數字的用意:它剛好卡在 log 級與線性之間。4·log₂(10⁴) ≈ 53 放行;而任何 O(n) 做法在 n=10⁴ 都要上萬次,差了兩個數量級。出題者用呼叫預算取代了時間限制,把「你有沒有想到二分」變成硬性判定,連常數都算進去。
A5. 三種分法都對,只有一種會錯。判準只有一條:每個索引至少被某一邊蓋到,且左半先搜。

✓ [0, peak] + [peak+1, n-1] —— 原版,峰歸左半。
✓ [0, peak-1] + [peak, n-1] —— 峰歸右半。也對,因為峰值在山上只出現一次(它是唯一最大值),歸哪邊都是同一個索引。
✓ [0, peak] + [peak, n-1] —— 峰被兩邊重複蓋到。也對,只是理論上多驗一次;實測 n=10⁴ 最壞仍是 53 次,因為左半命中就 return 了,重複那次幾乎不會發生。
✗ [0, peak-1] + [peak+1, n-1] —— 兩邊都不含峰,峰值永遠找不到。實測 6360 組錯 1060 組,最小反例 [0,1,0] 找 1 → −1(正解 1)。

注意前三種在 6360 組窮舉裡都是錯 0 組。不是每個看起來可疑的邊界都真的有 bug —— 值得先把「這個 off-by-one 到底會不會漏掉東西」問清楚,而不是憑感覺改。
App 1. 會壞,而且是兩個獨立的地方同時壞。實測:窮舉長度 3–7、值域 0–4 的全部非嚴格山共 28635 組,錯 3155 組。最小反例 arr=[0,0,1,0], target=0 → 回傳 1(正解 0)。

① 找峰的三分法崩了。嚴格單調保證 get(m) 和 get(m+1) 不可能相等,所以只有上坡/下坡兩種情況。有平台之後出現第三種 get(m) == get(m+1),而程式的 < 會把它當成下坡送去 right = mid —— 但平台可能整段都在上坡側,峰其實在右邊,就被切掉了。

② 就算峰找對了,二分也拿不到最小索引。這才是 [0,0,1,0] 的真正病灶:峰確實找到 2,左半 [0,2] = [0,0,1] 卻不是嚴格遞增。二分找 0 時 mid=1 直接命中回傳 1,而 index 0 也是 0。A3 那個「一個值最多出現兩次」的前提沒了,命中即回就不再等於最小索引。

要修得改兩處:二分改成 lower_bound 式(命中後 hi = mid - 1 繼續往左壓);找峰在有平台時沒有 O(log n) 解 —— 這和 81 的處境一樣,重複值會把二分打回線性,最壞得掃 O(n),那就直接超出 100 次預算了。
App 2. 改三處,成本完全不變。谷形是山形的鏡像,結構一模一樣:

① 找峰的比較反向:get(mid) < get(mid+1) → get(mid) > get(mid+1)(下坡才往右走,收斂到谷底)。
② 左半改成遞減:binarySearch(..., 0, valley, false)。
③ 右半改成遞增:binarySearch(..., valley+1, n-1, true)。

binarySearch 本身一個字都不用改 —— 這正是把 ascending 做成參數的回報。

實測:窮舉長度 3–7、值域 0–5 的全部谷形陣列共 6360 組,與線性掃描參考解不一致 0,最多 get 11 次。[7,4,2,3,5,9] 找 3 → 3;[5,3,1,3,5,7] 找 5 → 0(左半先搜,拿到最小索引)。

成本仍是 4·log n,因為找谷底同樣是每輪讀相鄰兩格。「最小索引靠先搜左半」這條也照樣成立,理由不變:嚴格單調 ⇒ 一個值最多出現兩次。
App 3. 會被判 WA —— 實測最壞 53 > 45。而且光靠微優化補不上這 8 次,這才是這題有意思的地方。

先看錢花在哪:找峰 2 × 14 = 28 次、左半 ≤ 14、右半 ≤ 14。找峰佔了一半以上,因為它是唯一每輪讀兩格的階段。要省就得省在那裡。

試過的做法 · 快取。用 unordered_map 包一層 cachedGet,讀過的格子不再花配額 —— 找峰這輪的 mid+1 有機會是下一輪的 mid,第 2、3 階段也可能撞到找峰讀過的格子。實測結果:53 → 50,只省 3 次。因為各輪的 mid 分佈得很開,重疊本來就很罕見。空間 O(log n)、多五行程式碼,換 3 次 —— 仍然過不了 45。

結構性的路只有一條:把找峰的每輪成本從 2 降到 1。但這在「比較相鄰兩格」的框架下做不到 —— 判斷坡向本質上需要兩個相鄰的值,而已知的區間端點值和 arr[mid] 比對推不出坡向(遞增段和遞減段都可能出現同樣的大小關係)。所以 45 這個預算等於是把這個解法整個排除掉,得換一種問法。

真正的 100 次上限下,這些都不必做 —— 餘裕 47 次,多寫的快取是純負債。但「成本集中在找峰、而且是因為每輪兩次 get」這件事值得記住:在有呼叫預算的題目裡,常數不再是可以忽略的東西,它就是計分項。
