題目簡介// THE QUESTION

QUESTION

mountainArr 是一座山:先嚴格遞增到某個峰,再嚴格遞減到底。 回傳 target 的最小索引,沒有就回 -1。

但你看不到陣列 —— 只能呼叫 get(i) 逐格問值、length() 問長度。 而且 get 超過 100 次直接判 Wrong Answer。

這題把兩件事綁在一起考:① 山形陣列該怎麼搜(先找峰,再左右各二分); ② 一個硬性的呼叫預算。第二點才是這題的個性 —— n 可以到 10⁴,而你只有 100 次提問機會,連掃一遍陣列都做不到。

「100 次」不是隨便定的門檻。log₂(10⁴) ≈ 13.3,而這個解法要花 4 × log n 次左右 —— 實測最壞 53 次。出題者把上限訂在 100,剛好放行 log 級解法、擋掉所有線性做法。

為什麼要拆成三次二分// WHY THIS

A 從左掃到右 n 次 get
最直覺、也一定能拿到最小索引。但 n 可到 10⁴,而預算只有 100 —— 連 1% 都不到。這裡卡住的不是時間,是呼叫次數。
× REJECT · 超出預算
B 整段直接二分 log n 次
預算綽綽有餘,但答案是錯的:山形陣列不是有序的,同一個 v < target 可能該往左也可能該往右,二分沒有判斷依據。 必須先把它切成兩段各自有序的區間。
△ REJECT · 前提不成立
BOTH FAIL · ADOPT
C 找峰 → 左半升序二分 → 右半降序二分 4 log n 次
峰把陣列切成兩段各自嚴格單調的區間,每段都能二分。 找峰本身也是二分(比較相鄰兩格判斷在上坡還是下坡),只是每輪要花 2 次 get。 總計 2·log n + log n + log n,n = 10⁴ 時實測最壞 53 次。
● ADOPT · 53 / 100
3

核心策略 · 三步驟// STRATEGY

  1. 找峰:二分 [0, n-1]。比較 get(m) 與 get(m+1) —— 遞增代表還在上坡(l = m + 1),遞減代表已過峰(r = m)。收斂點就是峰。
  2. 左半升序二分 [0, peak](含峰)。找到就直接回傳。
  3. 右半降序二分 [peak+1, n-1]。左半沒有才進來,比較方向要反過來。
步驟 2 和 3 的順序不能換。題目要的是最小索引,而一個值在山上最多出現兩次(左右各一)。 先搜左半,拿到的自然是小的那個。實測把順序顛倒,最小反例 [0,1,0] 找 0 會答 2(正解 0)。

找峰為什麼只看相鄰兩格就夠// THE SLOPE TELLS YOU

LEMMA · 相鄰比較把「峰在哪一側」問成了是非題

山形保證嚴格遞增再嚴格遞減,所以對任何 m < n-1,get(m) 和 get(m+1) 不可能相等,只有兩種情況:

① get(m) < get(m+1)(上坡) —— m 落在遞增段裡。 遞增段的每一格都比右邊小,所以 m 絕不可能是峰,峰一定在它右邊 ⇒ l = m + 1 可以放心跨過 m。

② get(m) > get(m+1)(下坡) —— m 要嘛就是峰,要嘛在遞減段裡。 兩種都表示峰不在 m 右邊 ⇒ r = m,而且不能減 1,因為 m 自己還是候選。

兩條路都讓區間嚴格縮短,所以必定收斂;而每一步都保住「峰在 [l, r] 內」這個不變量,收斂點就是峰。 把 r = m 寫成 r = m - 1 就會把峰丟出區間 —— 實測 4363 座山裡有 2242 座算錯,最小反例 [0,1,0](真峰在 1,得到 0)。

// get(m+1) 會不會越界? 迴圈條件是 l < r,所以 m = l + (r-l)/2 滿足 l ≤ m < r 又 r ≤ n-1 ⇒ m < n-1 ⇒ m + 1 ≤ n - 1 // 恆在範圍內。實測 4363 座山、每格都加了越界偵測,零次觸發

一句洞察// INSIGHT

二分不一定要作用在值上 —— 這題的第一次二分是搜「斜率的轉折點」。 只要能用 O(1) 次觀察判斷「答案在左邊還是右邊」,那個東西就能二分, 不管它是索引、是答案(410)、還是這裡的坡向。
