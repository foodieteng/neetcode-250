Hmm, let me think about this for a sec.

A naive approach would be to start at the smallest legal capacity and step up until one works. Correct, but capacities run to 2.5 × 107, and each test costs a pass over the belt. I could also compute the best cuts directly with dynamic programming, but at 5 × 104 packages that's far too slow.

This problem reminds me of searching on the answer. Computing the minimum capacity is hard, but checking one capacity is easy — walk the belt, start a new day when the next package doesn't fit, count days. And it's monotonic: a bigger ship never needs more days.

So the capacities form a F F T T pattern, and I want the first T. The hard optimization moves into the binary search, and the check stays a simple greedy.

Here's the plan.

// search the range of capacities
left  = max(weights) // heaviest package must fit
right = sum(weights) // one day carries everything
check(cap): days needed by greedy packing <= days
while left < right:
  mid = left + (right - left) / 2
  if check(mid): right = mid
  else:          left = mid + 1
return left

One: search capacities from max(weights) up to sum(weights).
Two: a capacity fits if greedy packing in belt order needs at most days days.
Three: if mid fits, keep it as the right end; otherwise move past it.

One thing worth flagging — the lower bound is max(weights), not 1. Below that, the heavy package never fits, but my greedy would still return a number — it just opens a new day and loads it anyway — so the check accepts an impossible capacity and I return something too small.

And the greedy is optimal: pulling a package back into an earlier day that still has room keeps every day legal and never adds a day.

The trade-off: each check is O(n), over about 25 rounds. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int shipWithinDays(vector<int>& weights, int days) {
        // range: low = heaviest package (can't split), high = total (all in one day)
        int left = *max_element(weights.begin(), weights.end());
        int right = accumulate(weights.begin(), weights.end(), 0);

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (getDay(weights, mid) <= days) {
                right = mid;              // enough days → capacity may shrink, keep mid
            } else {
                left = mid + 1;          // too many days → too small, skip mid
            }
        }

        return left;                     // smallest feasible capacity; always exists
    }

    // greedy: load in belt order, start a new day only when it won't fit; returns days
    int getDay(vector<int>& weights, int k) {
        int day = 1, curW = 0;       // start on day 1 (not 0)

        for (int w : weights) {
            if (curW + w > k) {       // doesn't fit → start a new day
                curW = 0;
                day++;
            }
            curW += w;                  // either way, this package goes on today's ship
        }

        return day;
    }
};

One thing worth flagging — curW += w sits outside the if on purpose. When I start a new day, the package that triggered the switch hasn't been loaded yet; it becomes the first item of the new day. Tucked into an else, that package would silently vanish and I'd undercount days.

Two comparisons also matter. Inside, it's a strict >: filling the ship exactly is allowed. Outside, it's <=: using every available day is allowed. Flipping either one pushes the answer the wrong way.

The time complexity is O(n log Σw) — roughly 25 rounds, each a 5 × 104 pass, so around 106 operations. The space complexity is O(1). In the worst case it's the same rule as any search on the answer: rounds times the cost of one check.

Oh, one more thing — accumulate(begin, end, 0) with a literal 0 sums in int. That's fine here at 2.5 × 107, but if the weight limit ever grew, that line would be the first to overflow, and silently. Writing 0LL costs nothing.

I also random-tested against a brute-force scan over capacities — 200,000 cases, no disagreement.
