A naive approach would be to check every cell, which is O(m·n), and uses neither rule. A middle option is to walk down the rows to find the right one and then binary search it — that's O(m + log n). It would pass at these sizes, but it only uses half the structure.

This problem reminds me of binary search for a boundary, done twice. The column of first numbers is sorted, so I can binary search that to pick the row in O(log m). Then the row itself is sorted, so another O(log n). Added up that's log m + log n, which is log(m·n).

There's also a one-pass version that treats the whole thing as a flat array. I'll mention it at the end — same complexity.

Here's the plan. Two binary searches, same skeleton.

// pass 1 — pick the row, searching the first-number column
left = 0, right = m
test: matrix[mid][0] > target  // strict >
  true → right = mid  ·  false → left = mid + 1
row = left - 1  // the LAST row that is not too big
if left == 0 → return false  // row would be -1

// pass 2 — search inside that row
left = 0, right = n - 1
test: matrix[row][mid] >= target
return matrix[row][left] == target

One: search the first-number column for the first row that starts above the target, with a strict >.
Two: take left - 1 as the row; if left == 0, return false.
Three: search that row down to one cell and check it.

One thing worth flagging — pass one gives me the first row that's too big, and I want the one before it, because a row starting above the target is entirely above it. left - 1 is -1 when the target is below every row, so that guard is required.

The same reasoning forces the strict >: with >=, a target equal to a row's first number makes that row the boundary, and left - 1 lands one row too early.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool searchMatrix(vector<vector<int>>& matrix, int target) {
        // ── pass 1: binary search each row's first element; find the first row whose first element > target ──
        int left = 0, right = matrix.size();

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (matrix[mid][0] > target) {
                right = mid;              // this row is too big → keep mid as the right bound
            } else {
                left = mid + 1;          // this row's first element ≤ target → skip past it
            }
        }

        if (left - 1 < 0) return false;   // every row starts > target → can't exist

        int rowIdx = left - 1;          // last row whose first element ≤ target = the only possible row

        // ── pass 2: binary search inside that row, converging to one cell ──
        left = 0, right = matrix[rowIdx].size() - 1;

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (matrix[rowIdx][mid] >= target) {
                right = mid;              // might be the answer → keep it
            } else {
                left = mid + 1;          // too small → skip past it
            }
        }

        return matrix[rowIdx][left] == target;   // the only candidate, still has to be checked
    }
};

Pass one runs left from 0 to m over the first numbers, keeping mid as the right bound when that row starts too high. Then the guard, then rowIdx = left - 1. Pass two resets left = 0 and right = n - 1, and converges on one cell. The return still compares that cell to the target, because converging only gives me a candidate, not a hit.

One thing worth flagging — there's an asymmetry people often "fix" and break. I guard left == 0, but I do not guard left == m. Landing on m just means every row starts at or below the target, so left - 1 is m - 1, a perfectly real row — and the target may well live there. A symmetric guard would throw away every answer in the bottom row.

E — evaluate
C
CANDIDATE

The time complexity is O(log m + log n), which is O(log(m·n)) — about 7 + 7 rounds at these limits. The space complexity is O(1). Even a hit pays both passes in full — there's no early exit.

Oh, one more thing — the flat version. Since gluing the rows gives one sorted list, I can binary search indices 0 to m * n directly, turning an index into a cell with matrix[i / n][i % n]. One loop, no left - 1 reasoning; the trade is that arithmetic every step.

I'd also flag what this leans on: each row starts above where the previous one ended. Drop that, keep only "rows and columns increasing", and gluing no longer gives a sorted list. That's a different problem, usually solved by walking in from the top-right corner in O(m + n).
