重點回顧// RECAP

面向要點
本質不是找「等於」,是找 F F F T T T 的分界
區間左閉右開 [left, right),right 初值 = n
迴圈條件left < right(區間非空)
保留 midnums[mid] ≥ target → right = mid
丟掉 midnums[mid] < target → left = mid + 1
收斂後left = 第一個 ≥ target 的位置(可能 = n)
命中判定迴圈外:left != n && nums[left] == target
複雜度時間 O(log n),空間 O(1)

觀念題// QUIZ

Q1. 為什麼 right 的初值是 n 而不是 n − 1?這個選擇連帶決定了哪兩處的寫法?
Q2. 為什麼一邊是 right = mid(不減 1)、另一邊卻是 left = mid + 1(一定加 1)?用「mid 還可不可能是答案」來解釋。
Q3. 證明這個迴圈不會無窮迴圈。(提示:先說明 left ≤ mid < right 為什麼永遠成立。)
Q4. 迴圈結束後 left 的語意是什麼?為什麼還必須先檢查 left == n,才能去讀 nums[left]?
Q5. mid = left + (right − left) / 2 和 mid = (left + right) / 2 差在哪?本題的資料範圍會出事嗎?什麼情況會?

範例 Trace// [-1,0,3,5,9,12]

// CASE A: target = 9(命中) idx 0 1 2 3 4 5 nums -1 0 3 5 9 12 n = 6 [0,6) mid=3 nums[3]=5 < 9 → left = 4 [4,6) mid=5 nums[5]=12 >= 9 → right = 5 [4,5) mid=4 nums[4]=9 >= 9 → right = 4 [4,4) 空 → 離開迴圈,left = 4 驗證:left != 6 且 nums[4] == 9 // return 4
// CASE B: target = 2(不存在,但位置合法) [0,6) mid=3 nums[3]=5 >= 2 → right = 3 [0,3) mid=1 nums[1]=0 < 2 → left = 2 [2,3) mid=2 nums[2]=3 >= 2 → right = 2 [2,2) 空 → left = 2(第一個 ≥ 2 的位置 = 插入點) 驗證:left != 6,但 nums[2] = 3 != 2 // return -1
// CASE C: target = 100(比全部都大 → left 落在 n) [0,6) mid=3 5 < 100 → left = 4 [4,6) mid=5 12 < 100 → left = 6 [6,6) 空 → left = 6 == n 若沒有 left == n 這道檢查,下一行就會讀 nums[6] → 越界 UB // return -1
三個 case 剛好對應三種收尾:命中、位置合法但值不對、位置越界。 迴圈本身對三者一視同仁 —— 它只負責把 left 壓到分界,分類是迴圈外那兩行的事。

應用題// APPLY

App 1. 35. Search Insert Position:找不到時要回傳「應該插入的位置」。本題的程式碼要刪掉/改掉哪幾行?為什麼幾乎不用動?
App 2. 若陣列允許重複值,要找 target 第一次出現的位置,本骨架要不要改?那要找最後一次出現呢?(提示:把判斷式從 ≥ 換成 > 會得到什麼?)
App 3. 875. Koko Eating Bananas 這類「答案二分」為什麼也能套同一副骨架?此時 nums[mid] ≥ target 這個判斷要換成什麼,才能維持 F F F T T T 的單調性?
// ANSWERS
A1. 因為區間定義成左閉右開 [left, right) —— right 是「候選集合的右界外一格」,不是最後一個元素。初值取 n 才能讓一開始的候選集合涵蓋 0 … n−1 全部。它連帶決定另外兩處:迴圈條件必須是 left < right(而非 <=,否則會取到 mid = right = n 而讀越界),右分支必須是 right = mid(而非 mid − 1)。這三者是一套,不能跟閉區間寫法混搭。
A2. 關鍵是問「mid 本身還可不可能是答案」。當 nums[mid] ≥ target,mid 已經滿足條件,它可能就是第一個 ≥ target 的位置,不能丟 —— 寫 right = mid,而右開區間本來就不含 right…… 等等,正因為不含,把 right 設成 mid 時 mid 就被「移進了右邊那段已知全 T 的區域」,它仍是目前最好的候選被記住,只是不再重複測試。反過來 nums[mid] < target 時,mid 確定不可能是答案(它比 target 小),連它一起排除 → left = mid + 1。一句話:可能是答案就保留、確定不是就跨過。
A3. 先看 mid = left + (right − left) / 2:因為進迴圈時 left < right,即 right − left ≥ 1,整數除法向下取整得 0 ≤ (right−left)/2 < right−left,所以 left ≤ mid < right 恆成立。於是:走 right = mid 時,因 mid < right,right 嚴格變小;走 left = mid + 1 時,因 mid ≥ left,left 嚴格變大。兩個分支都讓區間長度至少減 1,長度非負且嚴格遞減 → 有限步內必然到 left == right,迴圈結束。(若右分支誤寫 left = mid,當區間剩兩格時 mid 恆等於 left,長度不變 → 無窮迴圈。)
A4. left 是「第一個滿足 nums[i] ≥ target 的索引」,也就是 C++ std::lower_bound 的結果。特別的是:當陣列裡所有元素都比 target 小時,不存在這樣的 i,此時 left 會停在 n(合法的「尾後位置」,但不是合法索引)。所以必須先擋 left == n 再去讀 nums[left],否則就是陣列越界的未定義行為。這也是 C/C++ 裡 && 短路求值的典型用法:left != n && nums[left] == target 順序不能反。
A5. 兩者數學上相等,差別在溢位:(left + right) 可能超過 INT_MAX(≈ 2.1×10⁹),而 left + (right − left) / 2 全程不會超過 right,永遠安全。本題 n ≤ 10⁴,和最多也才 2×10⁴,不會出事。但當二分的是數值範圍而不是索引時(例如 875 對 1…10⁹ 二分、或對 long long 上界二分),兩數相加就真的會溢位 —— 這是 JDK 的 binarySearch 也踩過的著名 bug。建議一律寫防溢位版,養成肌肉記憶。
App 1. 迴圈一行都不用改,只要把最後兩行的驗證整段刪掉,直接 return left; 即可。因為 35 題問的正是「第一個 ≥ target 的位置」——命中時那個位置就是 target 的索引,沒命中時它就是插入點,連 left == n 都不用特判(全部比 target 小時,插入位置本來就是 n)。704 = 35 的答案 + 一次命中驗證,這也是為什麼建議兩題一起記。
App 2. 找第一次出現:完全不用改。因為判斷式 ≥ 把「等於」歸在 T 這側,指標會一路往左壓,收斂到的必然是最左的 target(這正是 lower_bound 的定義)。找最後一次出現:把判斷式改成 nums[mid] > target(嚴格大於),此時 left 收斂到「第一個 > target 的位置」,也就是 upper_bound;答案是 left − 1(記得先確認 left − 1 ≥ 0 && nums[left−1] == target)。兩者相減 upper − lower 就是 target 的出現次數 —— 這就是 34 題(Find First and Last Position)。
App 3. 因為骨架真正要求的不是「陣列排序」,而是判斷式對候選值單調 —— 存在一個門檻,小於它全 F、大於等於它全 T。875 二分的是「每小時吃 k 根」這個答案而非索引,判斷式換成 canFinish(k):以速度 k 是否能在 h 小時內吃完。k 越大越容易吃完,所以 canFinish 隨 k 單調由 false 變 true,骨架照搬,收斂後的 left 就是最小可行速度。差別只有兩點:區間改成值域 [1, max(piles) + 1),以及每次判斷從 O(1) 的比大小變成 O(n) 的模擬 → 總複雜度 O(n log maxPile)。
