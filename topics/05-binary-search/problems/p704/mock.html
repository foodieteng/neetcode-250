Hmm, let me think about this for a second.

A naive approach would walk the array from the front and compare every value. That's correct, but it's O(n) and throws away the sorted order, and the problem asks for O(log n), so that's out.

This problem reminds me of a lower_bound-style binary search — a binary search written as a boundary search. One common style checks for equality inside the loop and returns early. The other only shrinks a range and checks once at the end. I'll take the second one: it has two branches instead of three, and the same skeleton answers any "first position where a condition turns true" question. One shape, many problems.

C
CANDIDATE

Here's the plan.

// range is half-open: [left, right)
left = 0, right = n
// invariant: [0, left) is all F · [right, n) is all T
while left < right:
  mid = left + (right - left) / 2
  if nums[mid] >= target: right = mid    // may be the answer — keep it
  else:                     left = mid + 1 // too small — drop it
left is now the first index with nums[i] >= target
answer = (left != n and nums[left] == target) ? left : -1

One: keep a half-open range [left, right), starting at 0 and n — everything before left is a no, everything from right on is a yes.
Two: while the range isn't empty, check the midpoint; if nums[mid] >= target, set right = mid, otherwise left = mid + 1.
Three: after the loop, left is the boundary — return it if it's in range and holds the target, else -1.

One thing worth flagging — the branches are asymmetric on purpose: a mid that passes could be the boundary, so I keep it; a mid that fails is proven too small, so I drop it. The three-branch version can stop early on lucky inputs, but both are O(log n) in the worst case.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int search(vector<int>& nums, int target) {
        int n = nums.size();
        int left = 0, right = n;          // [left, right): right-open, starts at n

        while (left < right) {            // go on while non-empty
            int mid = left + (right - left) / 2;   // overflow-safe (left+right)/2

            if (nums[mid] >= target) {
                right = mid;              // mid may be the answer → keep it
            } else {
                left = mid + 1;          // mid too small → drop it (+1)
            }
        }
        // on exit left == right == first position with value >= target

        if (left == n) return -1;       // everything is smaller
        return nums[left] == target ? left : -1;  // right spot, value may differ
    }
};

The range starts at 0 and n. Inside the loop I take an overflow-safe midpoint, then either pull right down to mid or push left past it. After the loop, left is the first position whose value is >= target.

One thing worth flagging — the left == n check is not a speed thing, it's a correctness thing. When every value is smaller than the target, the loop ends with left equal to n. That's a valid "past the end" position, but not a valid index. If I read nums[left] first, I'd read off the end of the array. So the order of those two checks matters.

Corner cases:

• Target 2, missing in the middle → ends on a 3, so -1.
• Target 100 → ends at n, and the guard fires first.
• Target -1, the very first cell → returns 0.
• A single [5] with target -3 → returns -1.

CANDIDATE

The time complexity is O(log n): each round at least halves the range, so 104 elements take about 14 rounds — and a missing target still pays all of them. The space complexity is O(1), a few ints and no recursion.

Why the loop always ends: with left < right, mid sits inside the range, so both right = mid and left = mid + 1 shrink it. Writing left = mid instead could loop forever on a two-cell range.

Oh, one more thing — I wrote the midpoint as left + (right - left) / 2. Here it doesn't matter, but over a value range near the int limit, left + right can overflow — a famous bug even Java's library binary search once had. So I always write the safe form.
