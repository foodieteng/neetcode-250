Hmm, let me think about this for a sec.

A naive approach would be to keep each key's history in a list and walk it backwards on every get. That's O(n) per query, and with 2 × 105 calls hitting one key, that's far too slow.

This problem reminds me of an upper_bound binary search. I want "the last entry at or before T", and the standard move for a "last one satisfying" query is to search for the first one that fails, then step back one.

So: a hash map from key to a sorted array of (timestamp, value) pairs. set appends. get binary searches for the first timestamp strictly greater than the query, then takes the entry before it.

P — plan
C
CANDIDATE

Here's the plan.

// dict: key -> vector of (timestamp, value), sorted by construction
set: dict[key].push_back({timestamp, value})
get: // find FIRST index whose timestamp > query
  left = 0, right = v.size()
  while left < right:
    mid = left + (right - left) / 2
    if v[mid].first > timestamp: right = mid
    else: left = mid + 1
  return left > 0 ? v[left - 1].second : ""

One: set pushes the pair onto that key's array.
Two: get searches a half-open range for the first entry that's too new.
Three: return the entry just before it, or empty.

One thing worth flagging — two details travel together. First, the test must be a strict >. With >=, an exact-hit entry would count as "too new", and stepping back would hand me the previous value — a bug only exact matches hit.

Second, because I answer with left - 1, I have to guard left == 0: that's when every timestamp is newer, and I'd index -1.

A tree map would be shorter but slower, buying middle inserts I never need. Does this approach sound good, or would you rather I think of another way?

class TimeMap {
public:
    unordered_map<string, vector<pair<int, string>>> dict;

    TimeMap() {}

    void set(string key, string value, int timestamp) {
        // timestamps strictly increase -> a plain push_back keeps it sorted
        dict[key].push_back({timestamp, value});
    }

    string get(string key, int timestamp) {
        auto it = dict.find(key);
        if (it == dict.end()) return "";

        const auto& v = it->second;   // alias, no copy -- see the next section

        // find "the first timestamp > query" = upper_bound
        int left = 0, right = v.size();

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (v[mid].first > timestamp) {
                right = mid;              // too new, answer is to the left (keep mid)
            } else {
                left = mid + 1;          // not too new yet, step past mid
            }
        }

        // left = first "too new" slot; we want the cell before it
        return left > 0 ? v[left - 1].second : "";
    }
};

set is one push_back. get finds the key, returns empty if it's missing, then runs the loop: too new means right = mid, otherwise left = mid + 1. At the end I return the entry before left, if there is one.

One thing worth flagging — the const auto& on that lookup. Plain auto would still be correct, but auto strips the reference, so it copies the entire history vector on every get. That turns an O(log n) query into O(n).

With 200000 gets on a key holding 200000 entries: 17.7 ms with the reference, about 122 seconds with the copy — roughly 6900× slower.

Let's dry-run the code with three entries, (1,"bar"), (4,"bar2"), (7,"bar3"), querying 5. The "too new?" pattern is F F T, so I expect the boundary at index 2 and the answer at index 1.

rangemidv[mid].first> 5 ?actionnew range
[0, 3)14no (F)left = mid + 1[2, 3)
[2, 3)27yes (T)right = mid[2, 2) → stop
left = 2 > 0 → v[2 - 1]step back"bar2"

The key step: index 1 was dropped from the search range on the very first step, and it's still the answer. That's not a bug — the search finds the boundary, and the answer is always one step behind it. "bar2".

Corner cases:

• querying 0 → everything is too new, left stays 0, and the guard returns "".
• querying 7 → nothing is too new, left reaches 3, giving "bar3", no guard needed.
• a key never set → hits the early return.

A cross-check against a tree map over 300004 operations found no disagreements.

E — evaluate
C
CANDIDATE

The time complexity is amortized O(1) for set — a hash lookup and an append — and O(log n) for get, where n is the number of entries for that key, not the total. The space complexity is O(total entries).

In the worst-case scenario every call targets one key, so n reaches 2 × 105, and each query is about 18 comparisons.

Oh, one more thing — if the increasing-timestamp guarantee were dropped, I'd switch each key's history to a tree map keyed by timestamp. set becomes O(log n) instead of amortized O(1), and get becomes upper_bound plus one step back — the same idea, just done by the library instead of by hand.
