完整實作// upper_bound − 1

p981.cpp C++17 
class TimeMap {
public:
    unordered_map<string, vector<pair<int, string>>> dict;

    TimeMap() {}

    void set(string key, string value, int timestamp) {
        // timestamp 嚴格遞增 → 直接 push_back 就維持有序
        dict[key].push_back({timestamp, value});
    }

    string get(string key, int timestamp) {
        auto it = dict.find(key);
        if (it == dict.end()) return "";

        const auto& v = it->second;   // 別名,不複製 —— 見下一節

        // 找「第一個 timestamp > 查詢值」= upper_bound
        int left = 0, right = v.size();

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (v[mid].first > timestamp) {
                right = mid;              // 太新了,答案在左邊(保留 mid)
            } else {
                left = mid + 1;          // 還不夠新,跨過 mid
            }
        }

        // left = 第一個「太新」的位置;要的是它前面那格
        return left > 0 ? v[left - 1].second : "";
    }
};

為什麼是 const auto& 而不是 auto// AUTO COPIES

一句話規則:auto 只負責推導「值」的型別,& 和 const 是你自己貼上去的修飾。 推導時 auto 會把來源剝皮 —— 丟掉 reference、丟掉 top-level const —— 剩下一個乾淨的值型別。 所以 auto x = e; 一定是新物件,一定走 copy constructor。

// 實測:auto 剝皮(來源型別 const vector<int>&) 寫法 is_reference is_const 推出的型別 auto x = src false false vector<int> auto& x = src true true const vector<int>& const auto& x = src true true const vector<int>& 位址:&src = 0x…e68 &x(auto) = 0x…e50 ← 不同的物件 &x(auto&) = 0x…e68 ← 同一個 // 注意 auto& 會「保留」來源的 const —— 只有裸 auto 會把 const 一起剝掉
寫法得到複製?
auto v一個新的值是
auto& v別名(來源若是 const,它也是 const)否
const auto& v唯讀別名否

為什麼這樣設計:auto x = y; 的直覺就是「複製一份」。若它偷偷保留 reference,x = 5 會改到別人。 所以標準把主動權交給你 —— 要 reference 就自己打 &。

MEASURED · 這一行在本題到底差多少

同樣 200000 次 get,只改 const auto& / auto 這一個字:

該 key 有 200000 筆　const auto& 17.7 ms　vs　auto 122239 ms　→ 6899×
該 key 有    1000 筆　const auto&  4.6 ms　vs　auto    203.7 ms　→   44×

兩列的呼叫次數一樣,差別只在 vector 多長 —— 這證明成本跟著容器大小走,不是跟著呼叫次數。 用 copy constructor 計數器再確認一次:auto 版每次呼叫觸發 200000 次 copy ctor(= 元素數),const auto& 版 0 次。 換句話說,auto 把一個 O(log n) 的查詢打回 O(n)。

auto 給你「一份新的」,const auto& 給你「原來那個」。 預設用 const auto&;要改原物件用 auto&;型別很小或真的需要獨立副本才用 auto。

什麼型別複製才有感// WHERE THE COST IS

不必對每個 auto 疑神疑鬼。實測同樣 2×10⁶ 次存取,兩種寫法的時間:

元素型別autoconst auto&比值
int1.03 ms1.04 ms1.0×
int*(裸指標)0.89 ms0.90 ms1.0×
vector<int>::iterator0.90 ms0.87 ms1.0×

分界線很清楚:元素本身會不會配置堆積記憶體。 int、指標、iterator 實測完全沒差(1.0×),短字串因為 SSO 也只差 1.3×; 一旦是堆積字串(60×)或容器(88×),就是量級等級的差別。 所以「小型別用 auto」不是偷懶,是實測支持的。

range-for 的兩個坑// THE LOOP TRAPS

// 坑一:忘了 & for (auto p : v) // 每輪複製一次 ✗ for (const auto& p : v) // ✓
// 坑二:遍歷 map 時寫死 pair 型別 for (const pair<string,int>& kv : m) // 看起來是 reference,其實照樣複製 ✗ for (const auto& kv : m) // ✓

第二個坑之所以陰險,是因為它不報錯。map 的元素型別是 pair<const string, int>, 和你寫的 pair<string,int> 型別對不上 —— 編譯器於是生一個暫時物件、再把 reference 綁上去。 複製發生了,而且每一輪都發生。

MEASURED · 用位址證明複製確實發生

for (const pair<Key,int>& kv : m)
elem 0: &kv = 0x16d9cae30　&*it = 0x146e05fe0　不同
elem 1: &kv = 0x16d9cae30　&*it = 0x146e05f60　不同
elem 2: &kv = 0x16d9cae30　&*it = 0x146e05ee0　不同
copy ctor 呼叫 3 次(= 元素數)

for (const auto& kv : m)
elem 0–2: &kv 與 &*it 完全相同,copy ctor 0 次

最能說明問題的是那三個 &kv —— 每一輪都是同一個堆疊位址(同一個暫存槽被重複使用), 而 &*it 才是真正走過三個節點。unordered_map 實測結果完全相同。

const auto& 的唯一風險// DANGLING

reference 不擁有物件,所以被綁的東西不能先死:

const auto& v = getObj().member; // ✗ 暫時物件當場消滅 → 懸空 const auto& v = it->second; // ✓ 綁的是 map 內部的真實資料 // 本題的 get 是唯讀函式,期間不會 erase 或 rehash,所以安全
在本題,it->second 指向 dict 內部真實存在的 vector,而 get 全程只讀不寫 —— 沒有 erase、沒有插入導致的 rehash,所以這個 reference 從頭到尾有效。 要小心的是「一邊遍歷一邊改容器」的場景,不是這裡。

下表的失敗筆數與反例都是窮舉實測:所有長度 1..6 的遞增 timestamp 子集(取自 {1,2,3,4,5})× 查詢值 0..6,共 217 組。

⚠ 對照 81:同樣是 l <= r,壞法完全不同

在 81,把迴圈條件改成 l <= r 行為測試測不出錯(只是越界讀),因為那題的 (D) 分支保證了 l++ 一定會推進。 這題沒有那個分支,所以同樣的改動會直接卡死:l == r == m 且 v[m].first > q 時 r = m 什麼都沒動,l 也不動 —— 實測 217 組中有 129 組無窮迴圈、另外 88 組讀到 v[v.size()] 越界。 同一個筆誤,在不同題目上的症狀天差地遠。
