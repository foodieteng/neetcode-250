重點回顧// RECAP

面向要點
核心三種回應只問一個是非題:「是不是猜小了」
兩個分支== 1 → left = mid + 1;否則 → right = mid
為何能合併-1 與 0 都滿足 pick ≤ mid
為何仍正確right = mid 保留 mid,猜中那格是最後倖存者
迴圈條件left < right(剩一格就停)
收尾return left —— 答案保證存在,不需驗證
溢位n 到 2³¹−1,mid 必須寫 left + (right−left)/2
複雜度O(log n) 次 guess,空間 O(1)

應用題// APPLY

App 1. 278. First Bad Version:給 API isBadVersion(v),版本一旦壞掉之後就全壞,求第一個壞版本。請說明它為什麼和本題是同一副骨架,以及判斷式該怎麼寫。
App 2. 若 guess() 的呼叫要付費,而你被允許記住之前問過的結果,O(log n) 次呼叫還能再壓低嗎?請從資訊量的角度論證下界。
App 3. 375. Guess Number Higher or Lower II:每猜錯一個數 x 要付 x 元,求「保證能贏」的最小金額。為什麼這題不能用二分,要改用區間 DP?每次該猜的還是中間那個數嗎?
// ANSWERS
A1. 因為兩種情況都推得pick ≤ mid。guess(mid) == -1 表示 mid 比 pick 大,即 pick < mid;guess(mid) == 0 表示 pick == mid。合起來就是 pick ≤ mid,也就是「答案落在 [left, mid] 之內」。而 right = mid 正是把區間右界收到 mid、且包含 mid —— 對兩種情況都保住了「pick 仍在 [left, right] 內」這條不變量。所以它們能共用同一行。
A2. 靠兩件事。第一,不變量:每一輪結束後 pick 仍在 [left, right] 內(A1 已證明兩個分支都維持它)。第二,終止性:因為 left ≤ mid < right,left = mid + 1 讓 left 嚴格變大、right = mid 讓 right 嚴格變小,區間每輪至少縮短 1,必定收斂到 left == right。這時區間只剩一格、而 pick 保證還在裡面 ⇒ 那一格就是 pick。猜中的那個數之所以留得下來,關鍵就是 right = mid 沒有把 mid 排除掉。
A3. 本版的迴圈條件是 left < right,離開時 left == right,區間恰好一格且必含答案,所以 return left 就是答案,沒有「找不到」這條路。三分支版的條件是 left <= right,語法上迴圈可能因區間變空而結束,編譯器要求所有路徑都有回傳值,所以必須補一句 return -1。但實際上那句永遠不會被執行 —— 題目保證 pick 存在,而不變量保證它一直在區間內,所以在區間縮空之前必然有某輪 mid == pick 而從 return mid 離開。那是純粹為了滿足編譯器的死碼。
A4. 猜中的那一格會被自己丟掉,答案就此消失。實測窮舉出的最小反例是 n = 3, pick = 2:[1,3] 取 mid = 2,guess(2) = 0 已經猜中,但這行把 right 設成 mid − 1 = 1,於是區間變成 [1,1]、left < right 不成立,迴圈結束回傳 left = 1 —— 錯(正解 2)。根本原因:mid − 1 是為「-1 太大」量身訂做的,對「0 猜中」卻是把答案本身排除。所以合併版與 mid − 1 不相容 —— 要嘛 right = mid(兩分支),要嘛把 0 拆出來提早 return(三分支),不能混。
A5. 臨界點是 left + right > INT_MAX = 2³¹ − 1 ≈ 2.147×10⁹。704 的 n ≤ 10⁴,兩者相加最多 2×10⁴,離溢位差了五個數量級。本題 n 本身就可以是 2³¹ − 1,二分後期很容易出現像 left = 1073741825, right = 2147483647 這樣的組合,相加立刻越界。實測那組值:(left + right) / 2 環繞後得到 -536870912(負數),接著去呼叫 guess(負數),結果毫無意義,而且 mid 跑出區間後迴圈也不再收斂。left + (right − left) / 2 全程不超過 right,得到正確的 1610612736。
App 1. 278 是同一副骨架的最純粹版本。版本序列是 好 好 好 壞 壞 壞 —— 對 isBadVersion(v) 這個是非題單調由 false 變 true,要找第一個 true,正是 lower_bound 的形狀。判斷式寫 if (isBadVersion(mid)) right = mid; else left = mid + 1;,收斂後 return left。和本題的對應關係:「壞版本」≙「pick ≤ mid」,兩者都是「條件成立就保留 mid,不成立就跨過」。另外 278 的 n 同樣可到 2³¹ − 1,一樣必須防溢位。
App 2. 不能再壓低,⌈log₂n⌉ 就是下界。用資訊論的計數論證:答案有 n 種可能,而每次 guess 最多回傳 3 種結果 —— 但其中 0 直接結束遊戲,真正用來「分割候選集合」的只有 ±1 兩種。k 次二元回應最多只能區分 2^k 種情形,要覆蓋 n 種可能就需要 2^k ≥ n,即 k ≥ log₂n。取中點之所以最優,是因為它讓兩邊剩下的候選數盡量相等,最壞情況最小化;偏離中點會讓某一側變大,最壞情況變差。所以二分是最壞情況下的最優策略。
App 3. 因為 375 的目標函數不再是「猜幾次」而是「付多少錢」,而代價與猜的數字大小有關,不再左右對稱。猜大的數字代價高,所以最佳策略會偏向先猜小一點的數,而不是正中間 —— 二分「取中點」的最優性論證(兩側候選數相等)在這裡失效。正確做法是區間 DP:令 dp[i][j] = 在區間 [i, j] 內保證獲勝所需的最小金額,則 dp[i][j] = mink∈[i,j] { k + max(dp[i][k−1], dp[k+1][j]) } —— 取 max 是因為要「保證」贏(對手會讓你走最壞的那邊),取 min 是因為你可以挑最好的 k。時間 O(n³)、空間 O(n²)。教訓:二分要求的是「單調 + 最壞情況對稱」,一旦代價不對稱就要換工具。
