A naive approach would be to call guess(1), guess(2), and so on. That's O(n), and with n around two billion it's hopeless.

This problem reminds me of plain binary search on a sorted array. The only difference is that I can't read the values — I can only ask the API. But binary search never needed an array. It needs a monotonic yes/no test, and guess gives me one.

There's a choice in how to write it. The obvious version has three branches and returns early on 0. I want to fold it into two branches instead, and I'll explain why in the plan.

CANDIDATE

Here's the plan. Each round I ask only one yes/no question: "was my guess too low?"

// closed range [left, right], the pick is always inside it
left = 1, right = n
while left < right:
  mid = left + (right - left) / 2
  if guess(mid) == 1: left = mid + 1  // too low — drop mid too
  else:                right = mid    // too high OR exact — keep mid
return left

One: left and right mark a closed range that always holds the pick.
Two: if mid is too low, left = mid + 1; otherwise right = mid.
Three: when one cell is left, return it.

One thing worth flagging — I'm merging "too high" and "exact" into the same line. -1 means the pick is below mid; 0 means it is mid. Both give pick <= mid, and right = mid keeps mid in range.

Shrinking to mid - 1 could save a round, but it throws away an exact hit — I'll pay at most one extra round to drop a branch and a dead code path.

Does this approach sound good, or would you rather I think of another way?

/**
 * Forward declaration of guess API.
 * @param  num   your guess
 * @return       -1 if num is higher than the picked number
 *                1 if num is lower than the picked number
 *                otherwise return 0
 * int guess(int num);
 */
class Solution {
public:
    int guessNumber(int n) {
        int left = 1, right = n;          // the answer is always in the closed range [left, right]
        while (left < right) {            // stop at one cell; no need to wait for an empty range
            int mid = left + (right - left) / 2;  // n can reach 2^31-1, so avoid overflow
            if (guess(mid) == 1) {
                left = mid + 1;          // too low → answer in (mid, right]
            } else {
                right = mid;              // too high or exact → answer in [left, mid]
            }
        }
        return left;                     // one cell left and the answer must exist → it's this one
    }
};

left starts at 1, right at n, and the loop runs while left < right. Each round calls guess exactly once — if the API were slow or metered, calling it twice would double the real cost. Too low moves left past mid; anything else sets right = mid.

One thing worth flagging — the midpoint is left + (right - left) / 2, never (left + right) / 2, because n can be INT_MAX. And there's no return -1 at the bottom. In the three-branch version you're forced to write one for the compiler, but it can never run, since the pick is guaranteed to exist. Here the loop ends with exactly one candidate, so the dead line has nowhere to live.

Let's also test with corner cases.

• n = 1: the loop never runs, so I return 1 with zero API calls.
• n = 2, pick = 2: mid rounds down to 1, too low, one call.
• n = INT_MAX, pick = 1: 31 calls.
• pick = INT_MAX: 30 calls, returning INT_MAX.

E — evaluate
C
CANDIDATE

The time complexity is O(log n), and the meaningful unit here is API calls, not instructions — one guess per round. The space complexity is O(1).

In the worst-case scenario that's 31 calls at n = 2^31 − 1. And that's essentially optimal: each call splits the candidates around one point, so k calls can only tell apart about 2k numbers.

Oh, one more thing — back to the overflow point. When the pick is in the upper half, the second round already has left = 1073741825 and right = 2147483647. (left + right) / 2 wraps around to -536870912 — a guess that isn't even in range, and the search stops converging. left + (right - left) / 2 gives 1610612736. Here it's the difference between working and not.
