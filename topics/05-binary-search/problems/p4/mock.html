Let me think about what a median actually is for a sec. A median isn't really "a number." It's a place where you cut. You split all the data into two halves of nearly equal size, with everything on the left at most everything on the right, and read the median off the values next to the cut. So don't hunt for the number — hunt for the cut. A cut has a position, which is a single number I can binary search on.

On the example, nums1 = [1,3] and nums2 = [2]: three items, so the median is the second smallest, 2. If the left half is {1,2} and the right is {3}, the median is the largest thing on the left.

Hmm, let me think about this for a sec.

A naive approach would merge both arrays and index the middle. That's O(m+n) time and space — correct, but exactly what the requirement forbids.

A better one finds the k-th smallest recursively, throwing away k/2 each time. That does hit O(log(m+n)), but it has a lot of edge cases: one side running short, the k = 1 base case, and calling it twice when the total is even.

This problem reminds me of binary searching a partition rather than a value. I know how many items the left half must hold — call it leftCount. So if nums1 contributes i items, nums2 contributes j = leftCount − i, automatically. Two unknowns collapse into one, and one unknown with a "too big / too small" test is exactly a binary search.

Here's the plan.

// the four values around the cut
L1 = last of nums1's left part   R1 = first of nums1's right part
L2 = last of nums2's left part   R2 = first of nums2's right part

// a cut is legal when
L1 <= R2  and  L2 <= R1

// otherwise, which way to move
L1 > R2 → nums1 gave too many → hi = i − 1
L2 > R1 → nums1 gave too few  → lo = i + 1

One: swap so nums1 is the shorter array, and set leftCount = (m + n + 1) / 2 — the +1 puts the spare item on the left when the total is odd.
Two: binary search i, the items nums1 gives the left half, with j = leftCount − i, and read the four values around the cut.
Three: the cut is legal when L1 <= R2 and L2 <= R1; within one array that order is free, since it's sorted.

If L1 > R2, nums1 gave too many; if L2 > R1, too few. Both can't fail at once, so the branches never conflict.

One thing worth flagging: the swap to m ≤ n isn't just for speed — it's what keeps j in bounds. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. After the swap and leftCount, it's a binary search on i: compute j, read the four neighbors, then move hi, move lo, or return — max(L1, L2) for an odd total, or its average with min(R1, R2) for an even one.

class Solution {
public:
    double findMedianSortedArrays(vector<int>& nums1, vector<int>& nums2) {
        int m = nums1.size(), n = nums2.size();

        // binary search the shorter array — also what keeps j in bounds
        if (m > n) {
            return findMedianSortedArrays(nums2, nums1);
        }

        // items in the left half; +1 puts the spare item on the left when odd
        int leftCount = (m + n + 1) / 2;

        int lo = 0, hi = m;
        while (lo <= hi) {
            int i = lo + (hi - lo) / 2;   // nums1 gives i items to the left half
            int j = leftCount - i;       // nums2's share follows

            // four values around the cut; ±∞ sentinels at the edges, no special case
            int L1 = (i == 0) ? INT_MIN : nums1[i - 1];
            int R1 = (i == m) ? INT_MAX : nums1[i];
            int L2 = (j == 0) ? INT_MIN : nums2[j - 1];
            int R2 = (j == n) ? INT_MAX : nums2[j];

            if (L1 > R2) {
                hi = i - 1;            // nums1 gave too many
            } else if (L2 > R1) {
                lo = i + 1;            // nums1 gave too few
            } else {
                if ((m + n) % 2) {
                    return (double)max(L1, L2);
                }

                return (max(L1, L2) + min(R1, R2)) / 2.0;
            }
        }

        return -1.0;   // unreachable: a legal cut always exists (never hit in 120k tests)
    }
};

One thing worth flagging is the sentinels. At an edge I use INT_MIN or INT_MAX, so they always lose inside max and min. Could the even branch add INT_MIN + INT_MAX? No — that needs an empty left half or an empty right half, and neither is possible. I also measured it: the largest sum was 2 × 106.

The time complexity is O(log min(m, n)) — better than the O(log(m+n)) that was asked, because I search only the shorter array. Space is O(1); the recursion goes at most one level deep, since after the swap m ≤ n.

In the worst case both arrays are 1000 long, so the loop runs about 10 times.

The loop is while (lo <= hi) with a return inside, because as i grows the states go too few, legal, too many — I want the middle stretch, not a boundary.

Oh, one more thing — the sentinel trick borrows two values out of the range. It's safe only because values are capped at ±106. If values could span the whole int range, the addition overflows, and I'd make the sentinels and the four locals long long.
