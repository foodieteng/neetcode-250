A naive approach would scan from the front until I hit a value >= target, and return that index. It's simple and correct, but it's O(n) and ignores the sorted order.

This problem reminds me of lower_bound from the C++ standard library — a binary search for the "first index with value at least target." So I'll hand-write lower_bound as a half-open binary search.

The nice part is what I don't write: no early return on equality, no separate "not found" path.

CANDIDATE

Here's the plan.

// half-open range [left, right)
left = 0, right = n
// invariant: [0, left) all < target · [right, n) all >= target
while left < right:
  mid = left + (right - left) / 2
  if nums[mid] >= target: right = mid    // may be the spot — keep it
  else:                     left = mid + 1 // too small — drop it
return left

One: keep a half-open range [left, right), starting at 0 and n — everything before left is too small, everything from right on is big enough.
Two: while the range isn't empty, check the midpoint; if nums[mid] >= target, set right = mid, otherwise left = mid + 1.
Three: return left.

One thing worth flagging — right starts at n, not n - 1. The answer can legally be n, when the target beats every element. If right started at n - 1, left could never climb past it, and every "bigger than everything" input would silently return the wrong number. So the half-open range is what makes n reachable.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int searchInsert(vector<int>& nums, int target) {
        int left = 0, right = nums.size();   // range [left, right), right = n

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (nums[mid] >= target) {
                right = mid;              // mid may be the spot → keep it
            } else {
                left = mid + 1;          // mid too small → drop it
            }
        }

        return left;                     // hit: the index; miss: the insert spot
    }
};

The range starts at 0 and the array size. Inside the loop I take an overflow-safe midpoint; if nums[mid] >= target I pull right down to mid, otherwise I push left past it. When the loop ends I just return left.

One thing worth flagging — there is no guard before that return, and adding one would be a bug. Coming from the plain search version, my instinct would be to write if (left == n) return -1;. Here n is a correct answer, not an error. So the guard I'd normally want is exactly the guard I must not write.

Corner cases:

• target = 5, a hit → returns 2.
• target = 7, bigger than all → walks off the end to 4.
• target = 0, smaller than all → right collapses to 0.
• A single [1] with target = 2 → returns 1.

E — evaluate
C
CANDIDATE

The time complexity is O(log n): the range at least halves every round, so about 14 rounds for 104 items, and every input pays them all — there's no early exit, by design. The space complexity is O(1), three ints and a loop.

It always ends: with left < right, mid sits inside the range, so right = mid and left = mid + 1 both shrink it every round.

Oh, one more thing — this function is a building block. Flip the test from >= to > and you get upper_bound; subtract the two and you get how many times a value occurs. And the O(n log n) longest increasing subsequence algorithm calls this in a loop, where landing on the length means extend — so "n is a real answer" shows up again there.
