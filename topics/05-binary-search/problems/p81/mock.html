Without duplicates, the search rests on one fact: rotating makes exactly one break point, so if I cut at the middle, the other half is fully sorted. That fact is still true here.

A naive approach would be to scan the whole array. It's O(n), and — I'll come back to this — that turns out to match the worst case of anything I can write. But it gives up on every easy input.

This problem reminds me of modified binary search on a rotated array — keep the half that's provably sorted — plus a fallback for when I can't tell the direction. When comparing tells me nothing, I stop trying to halve and just give up one cell. So: halve when I can, shrink by one when I must.

// closed range [left, right], shrink to one cell
while left < right:

One: keep a closed range [left, right] and shrink it to one cell.
Two: if nums[left] == nums[mid], check that cell against the target, then drop it.
Three: otherwise, keep the side the target can be in, and check the last cell.

One thing worth flagging — the check before dropping the cell is the whole ballgame. Every other shrink comes with a proof that the target can't be there; this one is a blind discard. The only way to discard blindly and stay correct is to look at the cell first.

And the direction isn't free: I checked nums[left], not nums[right], so right-- would discard a cell I never looked at.

There's a trade-off here: the fallback costs the log-time guarantee. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool search(vector<int>& nums, int target) {
        int left = 0, right = nums.size() - 1;

        while (left < right) {
            int mid = left + (right - left) / 2;

            // -- (D) equal ends -> can't tell which half is sorted, shrink by one cell --
            if (nums[left] == nums[mid]) {
                if (nums[left] == target) {
                    return true;          // check it before discarding it -- this line is key to correctness
                }

                left++;
                continue;
            }

            if (nums[left] < nums[mid]) {      // left half [left, mid] sorted
                if (nums[left] <= target && target <= nums[mid]) {
                    right = mid;              // inside the sorted half -> go there (keep mid)
                } else {
                    left = mid + 1;
                }
            } else {                            // otherwise right half [mid, right] sorted
                if (nums[mid] < target && target <= nums[right]) {
                    left = mid + 1;            // inside the sorted half -> go there (skip mid)
                } else {
                    right = mid;
                }
            }
        }

        return nums[left] == target;      // shrunk to one cell, still verify it
    }
};

First comes the new branch: if nums[left] == nums[mid], I return true if that cell is the target, otherwise left++ and continue. After that, it's the usual sorted-half logic — move into the sorted half if the target is inside its range, else jump to the other side. At the end I return whether the one remaining cell equals the target.

One thing worth flagging — the sortedness test here is a strict <. Without duplicates it has to be <=, because with two cells left, mid equals left. Here the equal case is already caught above, so an = would be dead code — strict < says exactly what it guards.

Now your follow-up. Yes, duplicates change the complexity, and they change the class, not the constant.

The time complexity is O(log n) when the ends differ, but O(n) in the worst case. The space complexity is O(1).

I measured it: at n = 5000, the worst input takes 4999 passes, exactly n - 1, while a duplicate-free array of the same size takes 13.

In the worst-case scenario the array is all equal with the target absent, so every round learns nothing and gives up one cell.

Oh, one more thing — O(n) isn't a weakness of this solution, it's a lower bound on the problem. Picture 5000 copies of 1 with a single 0 hidden somewhere. Unseen cells are indistinguishable from outside, so an adversary puts the 0 where you didn't look. Any algorithm must read Ω(n) cells in the worst case.
