題目簡介// THE QUESTION

QUESTION

和 33 完全相同的設定,只差一個字:陣列是非遞減(可以有重複值)後被旋轉。 給旋轉後的 nums 與 target,回傳 true / false(這次只問存不存在,不要索引)。 題目最後還追問一句:重複值會不會影響複雜度?如何影響、為什麼?

這題是本章唯一一題「二分被打敗」的例子 —— 最壞情況退化成 O(n),而且無法避免。 33 的應用題 3 已經預告過它:nums[left] == nums[mid] 時你無法判斷哪半有序。 這頁把那句話展開成完整的解法、證明,以及實測出來的退化數字。

2

33 的解法在這裡壞在哪// THE BROKEN INFERENCE

33 靠的推論:nums[l] ≤ nums[m] ⇒ 左半有序

33 的整個解法建立在一句話上:一個斷點最多只能弄壞一半,而「哪半有序」用兩端比大小就能判斷。 元素相異時這個判斷是可靠的 —— nums[l] < nums[m] 就代表左半沒有跨過斷點。

有了重複值,nums[l] 和 nums[m] 可能相等。這時候兩種完全不同的情況長得一模一樣: 左半是一整段相同的值(真有序),或者左半跨過了斷點但頭尾恰好同值(不有序)。 兩端比大小已經無法區分它們。

於是 33 的程式碼會把答案那半當成「已排除」丟掉。實測把 (D) 分支整段刪掉(= 33 的解法直接套用), 在窮舉的 4530 組測資中失敗 60 組,最小反例:

// 最小反例:33 的解法為什麼在這裡回錯 nums = [0,1,0,0,0] target = 1 正解 true(index 1 就是 1) 第一輪 left=0, right=4, mid=2 nums[0] = 0 , nums[2] = 0 → 相等! 33 的程式碼會走 nums[l] <= nums[m] 那支,判定「左半 [0,2] 有序,值域 [0,0]」 於是問:1 在 [0, 0] 內嗎?否 → left = mid + 1 = 3 可是左半 [0,1,0] 根本不是有序的,而答案就藏在裡面 —— 一步之內,答案被丟掉了 // 回傳 false(正解 true)。窮舉 4530 組中有 60 組因此失敗

核心策略 · 三步驟// STRATEGY

  1. 先問「判斷得出來嗎」:nums[left] == nums[mid] ⇒ 分不出哪半有序。此時先驗 nums[left] == target(命中就直接回 true),否則 left++ 丟掉這一格重來。
  2. 判斷得出來就照 33 走:nums[left] < nums[mid] ⇒ 左半有序,用兩端範圍判 target 在不在;否則右半有序,同理。收縮一律 right = mid 或 left = mid + 1。
  3. 收斂到單格再驗:return nums[left] == target;

為什麼「先驗再縮」才安全// THE LEMMA

LEMMA · 丟掉一格之前,必須先確認它不是答案

left++ 做的事是永久放棄索引 left。在 33 裡每次收縮都有理由(「這半的值域不含 target」), 但這裡的 left++ 沒有任何理由 —— 它純粹是「我判斷不出來,只好少看一格」。

所以丟之前必須自己檢查一次:if (nums[left] == target) return true;。 有了這一行,被丟掉的那一格就已經被完整檢查過,放棄它不會遺失資訊 —— 這才讓整個做法回到正確。

少了這一行有多嚴重?實測失敗 725/4530,最小反例只要兩格: nums = [0,1]、target = 0。mid = 0,nums[0] == nums[0] 進入 (D) 分支, 沒驗就 left++ → 收斂到 index 1,回傳 nums[1] == 0 = false,而 0 明明就在 index 0。

(D) 分支怎麼寫實測結果最小反例
先驗 target,再 left++ 正確(0/4530 失敗) —
直接 left++(沒驗) 失敗 725/4530 [0,1] t=0 → false(正解 true)
先驗 target,再 right-- 失敗 1234/4530 [0,1] t=1 → false(正解 true)
第三列值得記:縮的方向不能隨便換。right-- 丟掉的是 nums[right], 而我們只驗過 nums[left] —— 丟了一個沒檢查過的值,失敗率甚至比忘記驗更高(1234 vs 725)。 「驗哪一格,就只能丟那一格」。

複雜度 · 回答題目的 follow-up// COMPLEXITY

題目直接問了:重複值會不會影響複雜度?答案是會,而且是量級上的影響。這是實測數字,不是估算:

// 迴圈實際跑幾輪(每進一次 while 計 1) n = 1000 n = 5000 全部相等,target 不存在 999 4999 ← 最壞 全相等只有一格不同 999 4999 只有正中間一格不同 500 2500 完全沒有重複值(對照) 9 12 無重複的旋轉陣列 n=5000,掃過所有 target 的最大值 = 13 次 ≈ log₂5000 // 999 → 4999 隨 n 成 5 倍,恆等於 n−1 ⇒ 線性 O(n)
平均 O(log n)　　最壞 O(n)　　S = O(1)

兩個資料點 999(n=1000)與 4999(n=5000)恰好都等於 n−1,隨 n 線性成長; 同尺寸的無重複輸入只要 13 次。退化完全來自 (D) 分支的 left++。

WHY · 為什麼 O(n) 是躲不掉的

考慮 [1,1,1,…,1] 中藏了一個 0,位置未知。任何只看 O(log n) 個位置的策略, 都會有大量沒被看過的格子;而那些格子從外部完全無法區分(值都一樣、旋轉位置也猜不出)。 對手可以把 0 放進任何一個你沒看的格子 ⇒ 任何演算法最壞都得看 Ω(n) 格。 所以這不是解法不夠好,是問題本身的下界。

維度量級說明
Time · 平均O(log n)能判斷方向時照 33 砍半
Time · 最壞O(n)實測 n−1 次(n=5000 → 4999)
SpaceO(1)三個 int
對照 · 無重複(33)O(log n)實測 13 次

一句洞察// INSIGHT

重複值毀掉的不是「至少一半有序」這個事實,而是「用兩端比大小就能看出哪半有序」這個手段。 看不出來的時候,唯一安全的動作是 先驗過這一格、再放棄它 —— 能砍半就砍半,砍不了才付一格的代價,最壞加總成 O(n),而那正是這個問題的下界。
