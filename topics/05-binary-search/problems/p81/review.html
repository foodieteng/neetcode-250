應用題// APPLY

App 1. 把迴圈條件改成 left <= right(其餘不動)。窮舉 4530 組一筆都沒失敗、也沒有無窮迴圈。它到底有沒有問題?
App 2. 154. Find Minimum in Rotated Sorted Array II:含重複值求最小值。它的保守收縮寫的是 right-- 而不是 left++。為什麼那題可以、本題不行?
App 3. 若題目改成回傳 target 的任一索引(不存在回 −1),本題程式碼要改哪裡?若要回傳最小的索引呢?
// ANSWERS
A1. 引理本身完全沒壞 —— 旋轉仍然只製造一個斷點,以 mid 切開後仍然至少有一半是有序的。壞掉的是偵測手段:33 用 nums[left] 與 nums[mid] 比大小來判斷哪半有序,而有重複值時 nums[left] == nums[mid] 會讓兩種截然不同的情況長得一模一樣 —— 左半是一整段相同值(真有序),或左半跨過斷點但頭尾恰好同值(不有序)。資訊不足,不是定理失效。實測把這個分支刪掉(= 33 直接套用)失敗 60/4530,最小反例 [0,1,0,0,0]、target=1:nums[0]==nums[2]==0 被誤判成「左半有序、值域 [0,0]」,於是 1 被判定不在左半而丟掉整個左側 —— 答案就在那裡。
A2. 本質差別在有沒有排除的理由。33 的每一次收縮都伴隨一個證明(「這半的值域不含 target,所以答案不可能在裡面」)—— 丟掉是有根據的。而 (D) 分支的 left++ 沒有任何根據,它只是「我判斷不出來,只好少看一格」,是盲丟。盲丟一格唯一的安全做法,就是丟之前自己把它看完:if (nums[left] == target) return true;。有了這行,被放棄的那格已經被完整檢查,放棄它不遺失資訊。少了它實測失敗 725/4530,最小反例只要兩格:[0,1]、target=0 —— mid=0 進 (D),沒驗就 left++,收斂到 index 1,回傳 nums[1]==0 為 false,而 0 明明就在 index 0。
A3. 因為我們只驗過 nums[left],沒驗過 nums[right]。right-- 丟掉的是一個從未被檢查的值,那正是盲丟裡最不能做的事。實測 right-- 版失敗 1234/4530 —— 比「忘記驗」的 725 還更嚴重,最小反例 [0,1]、target=1:mid=0 進 (D),nums[0]=0 != 1,right-- → right=0,收斂到 index 0,回傳 nums[0]==1 為 false,而 1 就在 index 1。口訣:驗哪一格,就只能丟那一格。(若真想丟右邊,那就得改成先驗 nums[right] == target 再 right--。)
A4. 會,而且是量級上的影響:從 O(log n) 退化成最壞 O(n)。實測迭代次數(每進一次 while 計 1):n=1000 → 999、n=5000 → 4999,恆等於 n−1,兩個資料點隨 n 成 5 倍 ⇒ 線性;同尺寸的無重複旋轉陣列只要 13 次(≈ log₂5000)。最壞形狀是全部相等而 target 不存在(如 [1,1,…,1] 找 2),此時每輪都走 (D) 分支、只縮一格。

為什麼躲不掉:考慮 [1,1,…,1] 裡藏了一個 0,位置未知。任何只探測 O(log n) 個位置的策略,都會留下大量沒看過的格子,而那些格子從外部完全無法區分(值都一樣、旋轉點也推不出)。對手可以把 0 放進任何一個你沒看的格子 ⇒ 任何演算法最壞都必須看 Ω(n) 格。這是問題的下界,不是解法不夠聰明。
A5. 因為 81 把「相等」這個情況提前攔掉了。(D) 分支的條件正是 nums[left] == nums[mid],而它一旦成立就 continue —— 所以能走到判有序那一行時,必然 nums[left] != nums[mid],此處 < 與 <= 邏輯上完全等價,那個等號是永遠為假的死條件。33 沒有 (D) 分支,「區間剩兩格、mid == left」的情形會直接走到判有序,所以那裡的等號是必要的。實測:把 81 的 <= 改成 <,窮舉 4530 組 + 隨機 400000 組零失敗。同一行程式碼在 33 是必要的、在 81 是死的 —— 差別來自前面多攔了一種情況。
App 1. 有問題,而且是行為測試看不到的那種。它確實不會無窮迴圈:left == right 時 mid == left,必定進入 (D) 分支,要嘛 return、要嘛 left++ 使 left > right 而跳出。但跳出時 left 已經是 right + 1,最後那行 return nums[left] == target; 就讀到陣列外面。用 g++ -fsanitize=address 跑 nums=[1,1,1]、target=2,立刻報 heap-buffer-overflow(讀 nums[3])。

它之所以「測不出錯」,是因為會回 true 的情況都在迴圈內就 return 了,越界那次讀到的垃圾值只要不巧等於 target 就不會顯現 —— 這是典型的未定義行為:碰巧沒錯,不等於沒錯。教訓:窮舉對拍能證明邏輯,但證不了記憶體安全;那要靠 sanitizer。
App 2. 因為兩題要的東西不同,所以「安全」的定義也不同。154 要找的是最小值,它的收縮基準是 nums[mid] 與 nums[right] 比較;當 nums[mid] == nums[right] 時無法判斷,做 right-- 是安全的 —— 因為丟掉的 nums[right] 與 nums[mid] 值相同且 mid 仍在區間內,最小值若等於這個值,那個代表元素沒有被丟掉。

本題要的是某個特定 target 存不存在,丟掉的那一格可能正好就是唯一的 target,所以必須先驗。一般原則:保守收縮要丟的那一格,必須是「值已在區間內有代表」或「已被自己檢查過」——154 屬前者,81 屬後者。
App 3. 回傳任一索引:把兩處 return true / return nums[left] == target 換成回索引即可 —— (D) 分支裡 return left;,收尾 return nums[left] == target ? left : -1;。因為程式本來就握有位置,只是原題只要 bool 而把它丟掉了。

回傳最小索引:做不到還維持這個結構。(D) 分支的早退是「一碰到就回」,它撈到的是掃描過程中最先遇到的那個 target,不保證索引最小;而重複值讓「第一個出現位置」失去單調性(不像 704 可以靠 ≥ 一路往左壓)。要最小索引,實務上就直接線性掃描 O(n) —— 反正本題最壞也是 O(n),沒有損失量級。
