Hmm, let me think about this for a sec.

A naive approach would try every way to place the cuts — C(n−1, k−1), which is astronomically large for n = 1000 elements and k = 50 pieces. The next step up is a DP that tries every spot for the last cut. That's O(k · n²), about 5 × 107. It works, but it's slow and fiddly.

This problem reminds me of binary search on the answer. Asking for the best split is hard. But asking how few pieces I need if I cap every piece at v is one greedy pass. So I flip the optimization into a yes/no question and binary search on v. The trade-off: the DP gives the cut positions, binary search only gives the value — but the value is all the problem asks for.

Here's the plan.

// search space — both ends are real splits
left  = max(nums) ← "cut into n pieces"
right = sum(nums) ← "don't cut at all"

// the yes/no test, one greedy pass
check(v): walk left to right, keep a running sum;
  if adding x would pass v → cut, start fresh;
  return how many pieces that took.

// invariant
right is always already proven feasible;
left−1 and below are already proven infeasible.

One: search the cap between the max and the sum — both ends are real splits.
Two: for each cap, walk left to right with a running sum, cut whenever the next element would pass the cap, and count the pieces.
Three: if that count is <= k, keep the cap and go left; otherwise step past it.

Two things make this correct. Greedy really gives the fewest pieces, because pushing an early cut later never makes a later piece heavier. And the test is monotone: if a cap works, any bigger cap works, so I want the first T in F F F T T T.

One thing worth flagging: the test is pieces <= k, not pieces == k. Extra cuts only shrink pieces, and == would break the monotone shape. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. The main loop squeezes left and right toward the first feasible cap, and a helper counts pieces greedily.

class Solution {
public:
    int splitArray(vector<int>& nums, int k) {
        // range: smallest candidate = max element alone, largest = no cut at all
        int left = *max_element(nums.begin(), nums.end());
        int right = accumulate(nums.begin(), nums.end(), 0);

        while (left < right) {
            int mid = left + (right - left) / 2;

            if (countSegments(nums, mid) <= k) {
                right = mid;          // feasible → keep mid, keep pushing left
            } else {
                left = mid + 1;      // infeasible → mid ruled out, step past it
            }
        }

        return left;                // first feasible cap; always exists, no re-check
    }

private:
    // fewest pieces the greedy "fill while it fits" needs under limit
    int countSegments(vector<int>& nums, int limit) {
        int cur = 0, segments = 1;

        for (int x : nums) {
            if (cur + x > limit) {
                cur = 0;           // cut: reset, then add — not add, then reset
                segments++;
            }

            cur += x;
        }

        return segments;
    }
};

One thing worth flagging is the reset in that helper: when x doesn't fit, I zero cur and count a new piece first, then add x, because x belongs to the new piece. Drop the reset and cur becomes a prefix sum — on [7,9,5] with k = 2 it returns 16 instead of 14.

And because left starts at the max, every cap fits any single element, so I never need a separate check. Starting at 0 instead would make [6,7] with k = 2 return 6 instead of 7.

Time is O(n log S), where S is the total sum: each greedy pass is O(n), and the range halves every round. Space is O(1).

In the worst case the range is about 109 wide, so about 30 rounds — roughly 3 × 104 operations, versus 5 × 107 for the DP.

Let me think about overflow here. The sum tops out at 109, and INT_MAX is about 2.1 × 109, so int is safe, but only by about 2×. With bigger inputs I'd switch to long long.

Oh, one more thing — this all rests on non-negative values. With negatives, greedy stops being optimal: [4,4,-4] with a cap of 4 takes two greedy pieces, but one piece is enough. Then I'd fall back to the DP.
