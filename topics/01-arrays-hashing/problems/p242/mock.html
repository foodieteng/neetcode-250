A naive approach would sort both strings and compare them — that's O(n log n).

This problem reminds me of a frequency-count pattern: order doesn't matter, only counts do, and counting is O(n). I'll build a count table from s by incrementing, then walk t decrementing. If any character goes negative, or t has a character s never had, it's not an anagram. And there's a free early check: if the lengths differ, return false immediately.

I
INTERVIEWER

Why does "goes negative" mean it's not an anagram?

C
CANDIDATE

freq[c] is the inventory of c's that s supplied and t can still consume. Each c in t spends one. If t tries to spend a c when the inventory is already zero, dropping to -1 means t has more c's than s — the counts don't match.

P — plan
C
CANDIDATE

Here's the plan.

if s.size() != t.size(): return false  // lengths must match
for c in s: freq[c]++                  // build inventory
for c in t:
  if freq has no c OR --freq[c] < 0: return false
return true  // lengths equal + nothing went negative => all zero

One: if the lengths differ, return false.
Two: walk s and add one to each character's count — that's the inventory.
Three: walk t and spend one per character; if the key is missing or the count drops below zero, return false. Otherwise return true.

One thing worth flagging — I'll write the guard as count(c)==0 || --freq[c]<0, so the count check short-circuits. Otherwise, indexing a missing key with freq[c] would silently insert it. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool isAnagram(string s, string t) {
        if (s.size() != t.size()) return false;   // 長度不同,免比

        unordered_map<char, int> freq;

        for (char c : s) {
            freq[c]++;                        // s 建表:各字元 +1
        }

        for (char c : t) {
            if (freq.count(c) == 0 || --freq[c] < 0)
                return false;                  // t 消耗:沒這鍵、或減到負 → 偽
        }
        return true;                          // 長度已相等 + 沒人變負 → 真
    }
};

The length guard comes first. Then an unordered_map<char, int>: one loop over s builds the counts, and one loop over t spends them, returning false the moment a key is missing or a count goes negative. If t survives, return true.

The easy line to get wrong is that guard: count must be checked before the decrement, and the || short-circuits, so I never create a key by accident. That's O(n) time, and O(k) space, where k is the number of distinct characters.

I
INTERVIEWER

You didn't check that all counts are zero at the end. Isn't that a bug?

C
CANDIDATE

It's safe because of the length guard. The increments total s.size(), and the decrements total t.size(); those are equal. So if nothing ever went negative, every decrement legally came out of a positive inventory, and the total removed equals the total added. That forces every count back to exactly zero. "Nothing went negative" is equivalent to "all zero."

Without the length check that equivalence breaks — s="ab", t="a" would leave the b unchecked and falsely return true. That's exactly why the length guard comes first.

Let me think about complexity here.

Time is O(n), space is O(k).

And this answers the follow-up directly — because I used an unordered_map rather than a fixed int[26], the idea carries straight over to Unicode: any character, keyed by its full code point, can be a key, and the space grows with the distinct characters actually present.

If I'd hardcoded c - 'a' into a 26-slot array — which is faster for guaranteed lowercase — a Unicode character would index out of bounds. So the rule is: bounded, small alphabet → array; large or unknown → hash map.
