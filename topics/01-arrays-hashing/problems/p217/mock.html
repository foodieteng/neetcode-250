A naive approach would be a double loop comparing every pair. That's O(n2), which times out at 105. Sorting first puts equal values next to each other, so one pass finds a duplicate in O(n log n) time, but it reorders the input.

This problem reminds me of the classic seen-set pattern: remember every value I've passed, and the moment I'm about to record one that's already in the set, that's a duplicate. That's O(n) time. Since we only need existence, a set is enough — no need for counts.

class Solution {
public:
    bool containsDuplicate(vector<int>& nums) {
        int n = nums.size();
        unordered_set<int> seen;

        for (int i = 0; i < n; i++) {
            if (seen.count(nums[i])) return true;   // 先查:已看過 → 重複
            seen.insert(nums[i]);              // 再放:留給後面比對
        }
        return false;                            // 掃完沒撞到 → 全相異
    }
};

For each element, I ask the set whether it already holds the value; if so, I return true on the spot, and otherwise I insert it for later elements to compare against. If the loop ends, everything was distinct, so I return false.

The line that's easy to get wrong is the order of count and insert — count must come first, so I'm asking about earlier elements, not the one I just added. count returns 0 or 1 for a set, so it reads as a clean boolean. That's O(n) average time and O(n) space.

You said O(n) — is that guaranteed?

C
CANDIDATE

It's amortized, on average. Each lookup and insert is O(1) on average, but a hash table occasionally rehashes — reallocating buckets and moving everything, an O(n) event — and that cost spreads out to O(1) per operation.

The theoretical worst case is O(n) per operation if every key collides into one bucket, making the whole thing O(n2), but with a decent hash that essentially never happens. So: O(n) on average overall, O(n2) in the worst case under pathological collisions.
