Then a plain delimiter is out: a single string ["a,b"] would be split into two. The robust approach is length-prefixed framing — write each string's length before it, and decode by reading exactly that many characters.

M — match
C
CANDIDATE

Let me reason about why this is safe.

This problem reminds me of the length-prefix, or TLV, framing used in network protocols, and it fits for the same reason. Each chunk is length + '@' + payload. On decode, the pointer always sits at a length, which is pure digits, so the first '@' is guaranteed to be the framing marker — never a payload character. I then read the payload by count, so it never gets scanned. That works for any character set.

P — plan
C
CANDIDATE

Here's the plan.

// encode
for str: out += to_string(str.size()) + "@" + str
// decode, i starts at a length
while i < n:
  j = find('@', i); len = stoi(s[i..j-1])
  push s.substr(j+1, len); i = j + 1 + len

One: encode each string as its length, an '@', and the string.
Two: to decode, find the next '@' from i and parse the digits before it as the length.
Three: take exactly that many characters after it, then jump i past the whole chunk.

Two things worth flagging. First, the delimiter must be a non-digit, like '@', so it can't blend into the length. Second, the loop invariant: i always lands on the next length, because I jump the whole payload. Empty strings fall out for free — len=0 reads zero characters.

Does this approach sound good, or would you rather I think of another way?

I — implement
C
CANDIDATE

Let me write it. encode loops over the strings and appends the length, an '@', and the payload. decode keeps a pointer i: find the '@', turn the digits between i and j into len, cut len characters after the '@', and move on.

class Codec {
public:
    // encode: each chunk = length + '@' + content
    string encode(vector<string>& strs) {
        string enc = "";
        for (auto str : strs)
            enc = enc + to_string(str.size()) + "@" + str;
        return enc;
    }

    // decode: read the length → cut exactly that many chars
    vector<string> decode(string s) {
        int n = s.size(), i = 0;
        vector<string> dec;

        while (i < n) {
            int j = s.find('@', i);          // length | payload
            int len = stoi(s.substr(i, j - i));  // i..j-1 is pure digits
            dec.push_back(s.substr(j + 1, len)); // read exactly len chars
            i = j + 1 + len;               // jump the whole chunk
        }
        return dec;
    }
};

That matches the plan. One detail worth flagging — i = j + 1 + len skips over the entire payload, so any '@' inside it is never even looked at by find. Forget the + 1, or the len, and the pointer lands mid-chunk.

The highlighted row is the point: find('@',5) returns 6, not the '@' at index 8 inside n@p — because index 5 starts a length. We read 3 characters and jump to 10, so the inner '@' is pure data.

Corner cases:

• [""] → "0@" → back to [""], since len=0 reads nothing.
• A string of all '@'s round-trips.
• NUL bytes round-trip.

All check out.

E — evaluate
C
CANDIDATE

Decode is O(L) in L, the total number of characters — each character is read a constant number of times. Space is O(L) for the output, and the length prefix adds only a few bytes per string.

One thing worth flagging on encode: enc = enc + … copies the whole string built so far, every time; enc += … appends in place and keeps encode O(L) too.

One more thing — for a binary protocol I'd use a fixed-width length, say 4 bytes, instead of digits plus delimiter — no non-digit assumption, faster to parse. And this framing composes: nesting lists just wraps another length prefix around each encoded sublist.
