What gotcha?

C
CANDIDATE

If instead you append to nums in place, you must freeze the length first — int n = nums.size(); — and loop while i < n. If you carelessly loop while i < nums.size(), every push_back grows the size, so i never catches the moving bound. That's an infinite loop that grows the vector until you run out of memory. Freezing n cuts that chase.

C
CANDIDATE

Here's the plan.

n = nums.size()   // frozen
ans = array of size 2n
for i in [0, n):
  ans[i]    = nums[i]
  ans[i+n] = nums[i]
return ans

One: freeze n as the original size.
Two: make an array of size 2n.
Three: for each i below n, write nums[i] into both ans[i] and ans[i+n], then return ans.

It's index assignment on a pre-sized array — no push_back, no length-chasing, and O(n) time. Does this approach sound good, or would you rather I think of another way?

I — implement

Alright, let me code this up. The fresh-array version is the clearest: allocate 2n slots, then one loop fills the front half and the back half with plain index assignment.

vector<int> ans(2 * n);
for (int i = 0; i < n; i++) {
    ans[i]     = nums[i];   // 前半
    ans[i + n] = nums[i];   // 後半
}
return ans;

The in-place variant freezes n, then appends nums[i], so it reads the front half and writes the back half.

class Solution {
public:
    vector<int> getConcatenation(vector<int>& nums) {
        int n = nums.size();          // 先凍住原長度!
        for (int i = 0; i < n; i++) {
            nums.push_back(nums[i]);     // 讀前半、寫後半
        }
        return nums;
    }
};

One thing worth flagging — the easy line to get wrong is the in-place loop bound. It must be i < n with the frozen n, never nums.size(), or the loop chases its own growth forever.

Both are O(n) time. The in-place one uses no extra container; the fresh one is easier to reason about.

I
INTERVIEWER

In the in-place version you read nums[i] while pushing to the same vector. Is that safe?

C
CANDIDATE

Yes, for two reasons. First, i < n, so I only ever read the front half, [0, n), while push_back writes to [n, 2n). Those regions are disjoint, so a freshly appended element is never re-read.

Second, I index nums[i] fresh on every iteration, so nothing stale survives a reallocation, and push_back is required to work even when its argument lives in the same vector.

The one thing I'd avoid is caching a reference, int& r = nums[i], across the push — reallocation would invalidate r. Reserving 2n up front also guarantees no reallocation happens at all.
