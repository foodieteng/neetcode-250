Brute force checks every pair, which is O(n²). The key reframe: instead of asking "which two numbers pair up," I stand at each nums[i] and ask "what's the one number I need?" That's the complement target - nums[i], and it's uniquely determined.

This problem reminds me of the complement lookup pattern with a hash map: the question becomes "have I seen that value before, and at which index?" — and a hash map answers that in O(1).

One: start with an empty map from value to index.
Two: for each i, compute the complement, and if it's already in the map, return its index and mine.
Three: otherwise, store my own value and index.

One thing worth flagging — check the complement before storing myself. If I stored first, an element equal to half the target, like nums[i]=3, target=6, would find itself and I'd return {i, i}, using one element twice. Checking first means the map only holds earlier elements. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> twoSum(vector<int>& nums, int target) {
        int n = nums.size();
        unordered_map<int, int> seen;         // value -> index

        for (int i = 0; i < n; i++) {
            int comple = target - nums[i];    // the other half I need
            if (seen.count(comple))           // complement seen earlier?
                return {seen[comple], i};     // return both indices

            seen[nums[i]] = i;                // not found -> store self for later
        }
        return {-1, -1};                      // unreachable (guaranteed solution)
    }
};

One loop: compute the complement, look it up, and if it's there, return both indices; if not, store the current value with its index.

The line that's easy to get wrong is the store — it has to come after the lookup, not before, or a number that's half the target pairs with itself. The final return {-1, -1} is unreachable, since a solution is guaranteed.

O(n) amortized time, O(n) space — one pass, one lookup and one insert per element.
