Let me think.

A naive approach would literally delete each val with erase. But every erase shifts everything after it, so the whole thing becomes O(n²).

This problem reminds me of the slow/fast two-pointer pattern, because what I really need is an in-place filter. A fast pointer reads every element; a slow write pointer, i, marks where the next kept element goes. When the value isn't val, I write it at i and move i forward. When it is val, I skip it and leave i alone. At the end, everything in [0, i) is a kept element, and i is k.

I
INTERVIEWER

Is it safe to overwrite the same array while you're reading it?

C
CANDIDATE

Yes, because the write pointer never passes the read pointer. i only moves on a keep, so i ≤ read always. Every write lands on a slot I've already read, or on the current one, writing it back to itself. It never overwrites data I haven't reached yet, so no extra buffer is needed.

Alright, let me code this up. It's one range-for loop with a write pointer.

class Solution {
public:
    int removeElement(vector<int>& nums, int val) {
        int i = 0;                          // write pointer

        for (int num : nums) {              // read pointer
            if (num == val) continue;         // skip val, i stays

            nums[i++] = num;              // keep: write and advance
        }
        return i;                             // [0, i) is all non-val
    }
};

If num == val, I continue; otherwise I write nums[i++] = num. Then I return i.

One thing worth flagging — that write line does two jobs: it writes at i, then the post-increment moves i forward. The skip branch must not touch i. If i moved on a skip too, the two pointers would move together, and val would stay inside the first k. This is O(n) time, O(1) space, and it keeps the order of the kept elements.

I
INTERVIEWER

Could you do fewer writes?

C
CANDIDATE

Yes — if val is rare, a swap-with-end version writes less. When nums[i] == val, I copy the last element over it and shrink the effective length. Only the val positions get written, and kept elements never move.

The catch is that I must not advance i after that swap — the element pulled from the end hasn't been checked and might itself be val, so I re-check it in place.

The trade-off: swap writes once per val but reorders the array, while my overwrite version does up to n writes but keeps the order. Since order is flexible here, either is fine; I'd default to the overwrite one for clarity.

Let me think about complexity here.

Time is O(n) — one pass, constant work per element. Space is O(1) — just the write pointer. The most writes happen when nothing equals val: every element is written once, back onto itself.

Oh, one more thing — this write-pointer skeleton generalizes directly. Swap the keep condition, num != val, for something else and you get a whole family. Deduplicating a sorted array is "keep if different from the last kept." Pushing zeros to the back is "keep if non-zero, then pad the tail with zeros." It's really an in-place filter — the same thing std::remove_if does under the hood.
