This problem reminds me of the direct-address table pattern — a boolean array where mp[key] means "key is present." It fits because the key range is small and fixed. It gives O(1) for everything, and it can't collide, because every key owns a distinct slot.

I — implement

Alright, let me code this up. The constructor assigns 1000001 false slots; each operation is a single array access.

class MyHashSet {
public:
    vector<bool> mp;

    MyHashSet() {
        mp.assign(1000001, false);   // one slot per key, 0..10^6
    }

    void add(int key) {
        mp[key] = true;
    }

    void remove(int key) {
        mp[key] = false;
    }

    bool contains(int key) {
        return mp[key];
    }
};

Every operation is O(1). One thing worth flagging — remove needs no existence check. Setting a slot that's already false is harmless, so there's no branch at all. And because it's a vector<bool>, the whole table is bits, not bytes — about 125 KB, not 1 MB.

Now the general version, for unbounded keys.

C
CANDIDATE

For that, I'd use a fixed number of buckets plus separate chaining. The hash is key % B with a prime bucket count, B = 769, and each bucket is a linked list. The prime spreads keys evenly across buckets.

class MyHashSet {
    static const int B = 769;           // prime bucket count (fewer collisions)
    vector<list<int>> buckets;
    int h(int key) { return key % B; }  // hash function

public:
    MyHashSet() : buckets(B) {}

    void add(int key) {
        auto& b = buckets[h(key)];
        for (int x : b) if (x == key) return;   // already present → don't add twice
        b.push_back(key);
    }
    void remove(int key) {
        buckets[h(key)].remove(key);            // removes all equal values
    }
    bool contains(int key) {
        for (int x : buckets[h(key)]) if (x == key) return true;
        return false;
    }
};

One thing worth flagging — add has to scan its bucket first and return if the key is already there; otherwise I'd store duplicates and break set semantics. remove and contains only touch one bucket.

This is unordered_set in miniature — average O(1), but worst case O(n) if everything collides.

Let's trace the collision case in the bucket version, with B = 769. I add 5, then 774.

opbucket h(key)state
add(5)5[5]
add(774)774%769=5[5, 774] — collision
contains(774)5scan → found
remove(5)5[774]

The row that matters is add(774): 774 % 769 = 5, so it lands in the same bucket as 5, and the bucket chains both keys. contains(774) scans that bucket and finds it, and remove(5) leaves just [774].

Direct addressing never hits this — 5 and 774 own separate slots. I verified both versions against std::set over 20,000 random add / remove / contains operations — zero mismatches.

C
CANDIDATE

Let me think about complexity here.

Direct addressing: O(1) per op, O(range) space. Bucket version: average O(1), O(buckets + n) space. With at most 104 calls, either version is instant.

Oh, one more thing — direct addressing is really a hash table with buckets = range and identity hash h(k) = k, so every bucket holds at most one key. That's why it can't collide. A real hash table shrinks the bucket count far below the range, which forces collisions and chaining, and it grows by rehashing to keep the load factor bounded. Direct addressing skips all of that dynamic machinery by paying for the whole range up front.
