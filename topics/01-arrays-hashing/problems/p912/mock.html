Let me lay out the landscape.

Comparison sorts bottom out at O(n log n) — that's a proven lower bound, since telling apart n! permutations needs a decision tree of depth log(n!) = Θ(n log n). Merge sort is stable with that worst case but needs O(n) extra space; heap sort is in-place with the same guarantee; quicksort is fastest on average but O(n²) in the worst case.

This problem reminds me of non-comparison sorting: when keys are bounded integers, digits can be used directly as array indices. So I'll go with LSD radix sort, which sidesteps the bound entirely.

Here's the plan.

// radix LSD, one stable counting sort per digit
split into pos, neg (store |neg|)
for each digit exp = 1, 10, 100…:
  counting-sort by (x/exp)%10  // stable!
neg: reverse, negate → prepend to pos

One: split the array into non-negatives and negatives, storing the negatives as absolute values.
Two: for each digit — ones, tens, hundreds — run a stable counting sort on that digit.
Three: reverse the sorted negatives, negate them, and put them in front of the positives.

Two things worth flagging. First, each digit pass must be a stable counting sort — I fill from right to left with a prefix sum, so equal digits keep their order; otherwise a higher digit would scramble the lower-digit work.

Second, negatives: I reverse them because the largest magnitude is the most negative. Does this approach sound good, or would you rather I think of another way?

vector<int> radix(vector<int>& a, int exp) {          // counting sort on the digit (a/exp)%10
    int n = a.size(); vector<int> cnt(10, 0), output(n);
    for (int i = 0; i < n; i++) cnt[(a[i]/exp)%10]++;
    for (int i = 1; i < 10; i++) cnt[i] += cnt[i-1];   // prefix sum = end position of each digit
    for (int i = n - 1; i >= 0; i--) {                  // back to front → stable
        int d = (a[i]/exp)%10; output[--cnt[d]] = a[i];
    }
    return output;
}
void radixSort(vector<int>& a) {
    vector<int> pos, neg;
    for (int x : a) (x >= 0 ? pos : neg).push_back(x >= 0 ? x : -x);  // negatives stored as |x|
    int maxp = 0, minp = 0;
    for (int x : pos) maxp = max(maxp, x);
    for (int x : neg) minp = max(minp, x);
    for (int exp = 1; exp <= maxp; exp *= 10) pos = radix(pos, exp);  // positives: small → large
    for (int exp = 1; exp <= minp; exp *= 10) neg = radix(neg, exp);  // negatives (|x|): small → large
    reverse(neg.begin(), neg.end());                                 // largest |x| = most negative, goes first
    a.clear();
    for (int x : neg) a.push_back(-x);                                // negate and append
    for (int x : pos) a.push_back(x);
}

The radix helper is a counting sort on one digit: count each digit, turn the counts into end positions with a prefix sum, then place elements. radixSort splits by sign, runs that helper digit by digit on both halves, then reverses and negates the negatives and puts them first. sortArray just calls radixSort(nums) and returns the array.

One detail worth flagging — the placement loop runs from back to front, output[--cnt[d]] = a[i]. With prefix-sum end positions, that's exactly what makes each digit pass stable. Run it front to back and equal digits come out reversed, which breaks the earlier passes.

Corner cases:

• empty array → the loops just skip.
• all equal values → stability keeps the order.
• a single zero.

Time is O(d·n), where d is the digit count — effectively O(n) for 32-bit ints, since d ≤ 10. Space is O(n) for the counting buffers. It beats the comparison lower bound because it never compares two elements — digits index directly.

One more thing — if values were unbounded or not integers, radix wouldn't apply, and I'd fall back to merge sort, which is stable, or heap sort, which is in-place and safe in the worst case. A general-purpose choice would be introsort, which is what std::sort uses.
