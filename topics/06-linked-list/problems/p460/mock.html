So it's two-level ordering: frequency first, recency as the tiebreaker. That means an LRU list will show up inside this somewhere.

Three more. Does put on an existing key count as a use? Does a failed get count? And what's the value range? I'm asking because the natural "not found" return is -1, and I want to know whether -1 could also be a real value.

Good — values are non-negative, so -1 is a safe sentinel. If I lean on that, I'll say so explicitly, because if that guarantee went away it would be a real bug, not a style issue.

And capacity zero means put has to be a no-op — otherwise I'd insert, then immediately try to evict from an empty structure.

M — match
C
CANDIDATE

Hmm, let me think about this for a second. The whole difficulty is one question: how do I find the minimum-frequency key in O(1)?

A naive approach would scan everything on eviction — correct, and my reference for testing, but O(capacity).

A priority queue on (count, timestamp) can't update priorities in place, so it's O(log n), plus stale entries piling up. An ordered map from frequency to keys is clean, but still O(log n).

So the question becomes: can I avoid searching for the minimum at all?

I
INTERVIEWER

Can you?

C
CANDIDATE

Yes, because the minimum barely moves. This problem reminds me of bucketing by count with a running minimum instead of a heap — it fits because the minimum only moves in small, predictable steps.

Inserting a new key: its count is 1, the smallest possible, so the minimum becomes 1 — an assignment. Using the last key at the minimum: it moves to the next bucket, so the minimum is exactly minFreq + 1 — an increment. Anything else leaves the minimum bucket occupied.

So it only ever resets to 1 or steps up by 1, and a single integer can track it.

P — plan
C
CANDIDATE

Here's the plan: three maps plus that integer.

// m    -- the cache itself
m[key]    = {value, useCount}
// freq -- one LRU list per count; front = oldest in that bucket
freq[f]   = list<key>
// iter -- where each key sits inside its list
iter[key] = list<int>::iterator
// and
minFreq   = smallest count currently present
// eviction is then just:
victim    = freq[minFreq].front()

One: m maps each key to its value and use count.
Two: freq maps each count to an LRU list of keys.
Three: iter maps each key to its position in that list. Plus minFreq, the smallest count present — so the victim is just the front of that bucket.

One thing worth flagging is iter: promoting a key pulls it out of the middle of its list, and list::erase is O(1) only with the iterator in hand. And it must be a list, not a vector — a vector erase shifts elements and invalidates my stored iterators.

Does this approach sound good, or would you rather I think of another way?

I
INTERVIEWER

Sounds good. Why is front the right end to evict from?

C
CANDIDATE

Because I append with push_back on every use. So within a bucket, the list runs oldest to newest, and front is the least recently used — exactly the tiebreaker you specified.

Each bucket is its own little LRU list; the whole structure is a stack of LRU caches, with minFreq telling me which one to evict from.

I — implement
C
CANDIDATE

Alright, let me code this up.

class LFUCache {
public:
    LFUCache(int capacity) : cap(capacity), minFreq(0) {}   // minFreq initialised too

    int get(int key) {
        auto it = m.find(key);
        if (it == m.end()) return -1;
        touch(it);
        return it->second.first;
    }

    void put(int key, int value) {
        if (cap <= 0) return;

        auto it = m.find(key);          // test with find, not the return value
        if (it != m.end()) {
            it->second.first = value;
            touch(it);
            return;
        }

        if ((int)m.size() >= cap) {     // explicit cast, no sign-compare warning
            int victim = freq[minFreq].front();
            freq[minFreq].pop_front();
            if (freq[minFreq].empty()) freq.erase(minFreq);   // drop the empty bucket
            m.erase(victim);
            iter.erase(victim);
        }

        m[key] = {value, 1};
        freq[1].push_back(key);
        iter[key] = --freq[1].end();
        minFreq = 1;
    }

private:
    // one "use" -- shared by get and put
    void touch(unordered_map<int, pair<int, int>>::iterator it) {
        int key = it->first, f = it->second.second;

        freq[f].erase(iter[key]);
        if (freq[f].empty()) {
            freq.erase(f);                   // drop the empty bucket
            if (minFreq == f) ++minFreq;      // the only way the min goes up
        }

        ++it->second.second;
        freq[f + 1].push_back(key);
        iter[key] = --freq[f + 1].end();
    }

    int cap, minFreq;
    unordered_map<int, pair<int, int>> m;
    unordered_map<int, list<int>> freq;
    unordered_map<int, list<int>::iterator> iter;
};

One helper, touch, does a use: pull the key out of its bucket, erase the bucket if it's now empty — bumping minFreq if that was the minimum — then append the key to the next bucket. get and put both go through it, so they can't drift apart. On a full put, the victim is the front of the minFreq bucket, removed from all three maps.

Two deliberate choices. I check membership with m.find, not get(key) != -1 — values are non-negative, but I'd rather the code not depend on that. And I erase empty buckets; that's not cosmetic — I'll come back to it.

The two evictions are worth contrasting. put(3,3) drops key 2, which arrived after key 1 — frequency beat arrival order, since key 1 had been read. put(4,4) is a genuine tie at count 2, broken by recency, and front of that bucket is exactly the right node.

And get(3) is the step where minFreq climbs — bucket 1 goes empty, so the minimum becomes 2. That's the only line that raises it. That matches.

I
INTERVIEWER

What happens if you forget that increment?

C
CANDIDATE

You'd expect a wrong eviction. What you actually get is memory corruption, which is worse.

minFreq would point at an empty bucket, and eviction calls front() and pop_front() on it — undefined behaviour on an empty list. The shortest trigger is three operations at capacity 1: put(0,0), get(0), put(1,0). The get empties bucket 1, and the put reaches straight into it.

The thing I'd emphasize is that answer-comparison testing can't find this — hundreds of thousands of operations without one wrong return value. It's a sanitizer bug, not a diff bug, so I'd run this under ASan.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time: O(1) average for both operations — a few hash lookups, one list::erase, one push_back. Space: O(capacity) — but only because I erase empty buckets. Leave them, and freq grows with the highest count ever reached — with the number of operations, not the capacity.

Oh, one more thing — two design caveats. Without the O(1) requirement, I'd ship the ordered-map version: the minimum is just begin(), and the minFreq bug class disappears.

And LFU has a behavioural flaw: keys that were hot early keep counts new keys can't reach, so after the working set shifts they never leave. LRU fails the opposite way — one big scan flushes it. Neither dominates; in production you'd add aging.
