範例 Trace// LFUCache(2) · 官方範例

// 每一步之後的三張表狀態 操作 m（key → 值 / 次數） freq minFreq ───────────────────────────────────────────────────────────────────────────────── LFUCache(2) {} {} — put(1, 1) {1 → 1/次1} {1: [1]} 1 put(2, 2) {1 → 1/次1, 2 → 2/次1} {1: [1, 2]} 1 get(1) = 1 {1 → 1/次2, 2 → 2/次1} {1: [2], 2: [1]} 1 ← freq[1] 還有人 put(3, 3) {1 → 1/次2, 3 → 3/次1} {1: [3], 2: [1]} 1 ← 淘汰 key 2 get(2) = -1 （不變） （不變） 1 get(3) = 3 {1 → 1/次2, 3 → 3/次2} {2: [1, 3]} 2 ← freq[1] 空了,++ put(4, 4) {3 → 3/次2, 4 → 4/次1} {1: [4], 2: [3]} 1 ← 淘汰 key 1 get(1) = -1 get(3) = 3 get(4) = 4 // 與 LeetCode 官方範例的期望輸出完全一致
// 兩次淘汰,兩種理由 第 1 次(put(3,3)):key 1 次數 2、key 2 次數 1 → 比次數,淘汰 key 2。注意 key 1 更早進來卻活下來 —— LFU 不是 FIFO 第 2 次(put(4,4)):key 1 次數 2、key 3 次數 2 → 次數平手,比誰久沒用:key 1 上次用是 get(1),key 3 是 get(3),key 3 比較新 → 淘汰 key 1。而 freq[2] = [1, 3] 的 front 剛好就是 key 1 ✓
// 邊界(皆為實測) capacity = 0 put 第一行就 return,任何 get 都是 -1（200 次操作,全對) 剛建構就 get m 是空的,第一行 return —— 這條路徑完全沒讀 minFreq 剛建構就 put 內部 get 立刻 return -1;m.size()=0 < cap 不淘汰;最後才 minFreq = 1
順帶回答一個看了會發毛的問題:minFreq 在建構式裡沒有初始化,會不會讀到垃圾? 實測不會。把 minFreq 換成一個會記錄「讀取前是否寫入過」的型別, 跑 20 萬條隨機序列共 600 萬次操作,minFreq 被讀取 4998084 次,沒有任何一次發生在被寫入之前。 理由是:讀它的兩個位置都要求 m 非空,而 m 非空必定經過 put 尾端的 minFreq = 1。 但這仍然該補上 —— 它靠的是「目前的控制流剛好如此」,而不是任何保證。

應用題// APPLICATION

App 1. 把 freq 換成有序的 std::map,最小次數就是 begin(),minFreq 這個變數整個不用維護。實際上慢多少?值得換嗎?
App 2. LFU 有一個著名的弱點:早期紅過的 key 會賴著不走。請構造一個工作負載讓它現形,並和 LRU 對照。
App 3. 承 Q2 —— 拿掉 iter 表到底會慢多少?請量出來,而不是只說「變 O(n)」。
// ANSWERS
A1. 因為 minFreq 的變化量有界:要嘛歸 1,要嘛剛好 +1。

① 插入新 key ⇒ minFreq = 1。新 key 次數固定是 1,而 1 是可能的最小值 —— 不必比較,直接賦值。

② 使用某個 key,而它是最小桶裡的最後一個 ⇒ ++minFreq。
它從 freq[minFreq] 搬到 freq[minFreq + 1],舊桶空了。而新的最小值不可能大於 minFreq + 1 —— 因為剛剛那個 key 就落在那裡。所以答案必定是 minFreq + 1。

③ 使用某個 key,但最小桶還有別人 ⇒ 不變。
④ 淘汰 ⇒ 不需要處理。因為淘汰之後緊接著就是插入,①又把它設回 1。

這就是整題的關鍵洞察:「找最小」之所以貴,是因為每次都重新找。只要變化量有界,就可以用一個變數增量維護。
A2. 答案完全不會變,但每次 get 從 O(1) 退化成 O(桶大小)。

key 升級時要從舊桶的 list 中間把它拔出來。std::list::erase(it) 本身是 O(1) —— 但前提是你手上要有那個 iterator。沒有 iter 表,就得從 front 一路 ++ 找過去。

實測(見 App 3):改成掃描版,1250014 次 get 答案完全一致 —— 它不是錯,是慢。而在「桶內全滿、每次都存取排最後面那個」的持續最壞情形下,capacity = 2000 時每次 get 平均掃過 1000 個節點,慢 30 倍。

順帶說明為什麼是 list 而不是 vector:vector 從中間刪一個會讓後面所有元素移位,iter 表裡存的位置全部失效。list 的節點各自獨立,刪一個不影響其他 iterator —— 這是「存 iterator」這個做法能成立的前提。
A3. 因為桶內要維持「front = 最久沒用」,而 push_back 從尾巴追加才會有這個性質。

LFU 規定次數平手時退回 LRU。所以同一桶內必須照「上次使用時間」排序,最舊的在前面 —— 剛用過的 key 是最新的,當然排到最後。

實測:改成 push_front,4 萬條隨機序列共 410030 次 get,錯 5366 次(1840 條序列受影響)。
窮舉搜到的最小反例:
cap = 2 put(0,0) get(0) put(1,0) get(1) put(2,0) get(0) → 0 // 正解 -1

注意它需要 6 個操作才現形 —— 因為它只在「同一桶裡有兩個以上的 key,而且剛好要淘汰」時才會出錯。桶裡只有一個 key 時,front 和 back 是同一個,前後推無所謂。所以隨手測兩三筆完全測不出來。
A4. 會崩,不會答錯 —— 而這正是它可怕的地方。

實測(4 萬條隨機序列,410030 次 get):
· 答錯次數:0
· 淘汰時撈到空 list:30670 次

「一次都沒答錯」不是因為它是對的,是因為它活不到答錯 —— 程式先壞了。

最短觸發序列(窮舉搜出):
LFUCache cache(1); cache.put(0, 0); // freq[1] = [0],minFreq = 1 cache.get(0); // 0 升到 freq[2];freq[1] 空了,但 minFreq 沒跟著爬 cache.put(1, 0); // 滿了 → freq[minFreq=1].front() ← 空的 list // ASan: ERROR: AddressSanitizer: attempting free on address which was not malloc()-ed #7 in std::list<int>::pop_front()

對空 list 呼叫 front() / pop_front() 是 UB,不是「回傳某個預設值」。

這一課值得單獨記下來:「所有測資都過」和「沒有 bug」是兩件事。對答案比對而言,記憶體毀損是隱形的 —— 它只有 sanitizer 看得見,而且可能在很久以後、在完全無關的地方才爆出來。
A5. 隱憂是:-1 既被當成「不存在」,也可能是一個合法的值。

if (get(key) != -1) 用回傳值判斷 key 在不在。存了 -1 的 key,get 回傳 -1,於是 put 誤判它不存在,走進「插入新 key」那條分支。

為什麼在 LeetCode 上不會出事:題目保證 0 ≤ value ≤ 10⁹,值永遠不可能是 -1。

把值域放寬到允許負值,實測就現形:105752 次 get 中不一致 257 次。窮舉搜到的最小反例:
cap = 2 put(0, -1) put(1, 7) put(0, -1) get(1) → -1 // 正解 7

而且壞的不只是答案,是結構本身。誤判之後 m[key] = {value, 1} 直接覆蓋,但舊的那筆在 freq 裡的節點沒有被移除:
put(1,-1); put(2,5); → m 有 2 個 key,freq 裡也 2 個,一致 ✓ 再 put(1,9); → m 只剩 1 個,freq 裡還是 2 個,而且 key 1 出現兩次 接著 get(2) = -1 // key 2 被那次誤判當成受害者淘汰掉了

修法一行:用 m.find(key) != m.end() 判斷存在,不要看回傳值。 更一般的教訓:哨兵值(-1、0、INT_MIN)只有在它落在合法值域之外時才安全 —— 而那通常是題目給的,不是你能保證的。
App 1. 正確性完全一樣,而且慢得沒有想像中多 —— 但差距的方向很有意思。

把 freq 換成 std::map<int, list<int>>,最小次數就是 freq.begin()->first,minFreq 這個變數整個消失(空桶也必須 erase,否則 begin() 會指到空桶)。

實測正確性:與原碼交叉比對 2499982 次 get,不一致 0。

實測速度(40 萬次操作):
capacity = 100: 原碼 72.2 ns/op 有序 map 121.1 ns/op → 1.68 倍 capacity = 10000: 原碼 92.0 ns/op 有序 map 99.1 ns/op → 1.08 倍

反直覺的地方:capacity 越大,兩者反而越接近。因為 map 的 log 是對桶數取的,而桶數大約是「不同次數的個數」,通常遠小於 capacity —— capacity 大的時候 key 分散,每個 key 次數都低,桶反而少,log 幾乎等於常數。

結論:面試時 先寫有序 map 版(短、不需要維護 minFreq、少一整類 bug),然後說「這裡有一個 log,來自紅黑樹;follow-up 要 O(1) 的話我改用 unordered_map 加自己維護 minFreq」。知道 log 從哪裡來,比直接寫出最快的版本更能證明你懂。
App 2. 只要工作集換人,LFU 的命中率會掉到 0%,而且永遠回不來。

構造(capacity = 4):
階段一:key 0~3 各被使用 N 圈,次數衝到 N。
階段二:工作集整個換成 key 100~103,反覆循環 300 圈(共 1200 次存取)。

實測:
暖身 10 圈 → LFU 命中 0/1200 ( 0.0%) LRU 命中 1196/1200 (99.7%) 暖身 100 圈 → LFU 命中 0/1200 ( 0.0%) LRU 命中 1196/1200 (99.7%) 暖身 1000 圈 → LFU 命中 0/1200 ( 0.0%) LRU 命中 1196/1200 (99.7%)

連暖身 10 圈就已經完全鎖死了,而且再多的暖身也不會更糟 —— 因為 0% 已經到底。

機制:新 key 進來次數是 1,minFreq 立刻歸 1;下一個新 key 進來時,受害者就是「上一個新 key」 —— 舊的四個高次數 key 連被考慮的機會都沒有。新 key 之間互相淘汰,老 key 永遠不動。

這就是 LFU 的「快取污染 / 老化」問題,也是真實系統很少用純 LFU 的原因。實務上的解法是週期性把所有次數砍半(aging),或改用 LFU 與 LRU 的混合策略 ↗(例如 TinyLFU、ARC)。

但要說公平話:LRU 也有它的死穴 —— 一次「掃過全表」的循序存取就能把 LRU 整個沖掉,而 LFU 對這種情形反而免疫。沒有普遍最好的淘汰策略,只有適合特定存取模式的策略。
App 3. 答案一模一樣,但最壞情形慢 30 倍 —— 而且慢的幅度隨 capacity 線性成長。

改成「每次升級都從 front 掃過去找 key 的位置」:

正確性:1250014 次 get,不一致 0。它不是錯的,只是慢。

速度(持續最壞情形:桶內全滿,而且每一圈都存取排在最後面的那個):
capacity = 200: 有 iter 53.2 ns/get 無 iter 139.9 ns/get 慢 2.6 倍 平均掃過 100 個節點 capacity = 2000: 有 iter 55.0 ns/get 無 iter 1627.4 ns/get 慢 29.6 倍 平均掃過 1000 個節點

兩個數字要一起看:
· 「平均掃過的節點數」正好是 capacity / 2 —— 這是 O(桶大小) 的直接證據;
· 有 iter 那一欄從 53.2 到 55.0,幾乎不動 —— capacity 放大 10 倍,成本沒變。這才是 O(1) 長的樣子。

而且要注意「最壞情形」是怎麼構造出來的:我第一次量的時候忘了每圈要換方向,結果目標永遠落在 front,掃描版反而比較快(每次只掃 1 個)。只有讓目標持續落在桶的另一端,O(n) 才會現形 —— 這也提醒:效能測試如果不刻意構造最壞情形,量到的往往是最好情形。
