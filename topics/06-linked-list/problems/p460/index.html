題目簡介// THE QUESTION

QUESTION

實作一個 LFU(Least Frequently Used)快取,支援 get(key) 與 put(key, value)。 容量滿了要插入新 key 時,淘汰使用次數最少的那個; 若有多個並列最少,淘汰其中最久沒被用到的(也就是平手時退回 LRU)。

get 與 put 都算一次使用。查不到的 get 回傳 -1。

0 ≤ capacity ≤ 10⁴、0 ≤ key ≤ 10⁵、0 ≤ value ≤ 10⁹、最多 2×10⁵ 次呼叫。

Follow up:兩個操作都要 O(1) 平均時間複雜度。

LRU(146)只要回答「最久沒用的是誰」—— 一條 list 就夠了,front 就是答案。 而 LFU 要回答的是兩層問題:先比次數,次數平手再比時間。

如果每次淘汰都去掃一遍找最小次數,那是 O(capacity),follow-up 直接不及格。 整題的難點就是:怎麼把「找最小」壓成一次查表。 答案是 把「次數」當成桶的編號 —— freq[f] 裝著所有次數為 f 的 key,桶內再照使用順序排。 再額外記一個 minFreq,淘汰就是 freq[minFreq].front(),一步到位。

四種「找最小」的方式// WHY THIS

A 淘汰時掃過所有 key,挑次數最小的 O(capacity) / 次
最直覺,而且答案一定對 —— 本頁所有實測數字的參考解就是它。 但 capacity 上限 10⁴、呼叫 2×10⁵ 次,最壞是 2×10⁹ 次比較。 正確,但沒回答 follow-up。
△ 正確 · 但不是 O(1)
B priority_queue 依 (次數, 時間戳) 排 O(log n) + 髒資料
堆疊沒辦法「就地更新」某個元素的優先度,所以每次使用都得再塞一份新的進去, 淘汰時反覆彈出過期的舊紀錄。會動,但變成 O(log n),而且堆裡的髒資料量沒有上界。
× REJECT · 不是 O(1)
C map<int, list<int>> 有序容器,取 begin() O(log n)
用有序的 std::map,最小次數就是 begin(),連 minFreq 這個變數都不用維護。 寫起來最不容易錯。缺點只有一個:紅黑樹是 O(log n),不是 O(1)。
△ 好寫 · 但 O(log n)
D 雜湊桶 + 自己維護 minFreq O(1) 平均
用 unordered_map 當桶,再自己記住最小次數。 關鍵在於 minFreq 只會以兩種方式變動: 插入新 key 時直接歸 1,或是最小桶被搬空時恰好 +1 —— 兩種都是 O(1),永遠不需要「重新尋找最小」。
● ADOPT · 這就是本題答案
面試時 C 值得先講。它三句話說得完、正確性顯而易見, 然後再說「但 follow-up 要 O(1),那個 log 來自紅黑樹,我可以用桶 + 自己維護 minFreq 拿掉它」 —— 這比一開始就硬幹 D 安全得多,而且正好展示你知道 log 是從哪裡來的。

三張表,各自負責一件事// THE THREE MAPS

表型別負責回答
mkey → {值, 次數}「這個 key 在嗎?值多少?現在幾次?」
freq次數 → list<key>「次數是 f 的有哪些 key?誰最久沒用?」(front)
iterkey → list 裡的位置「這個 key 在它那條 list 的哪一格?」
minFreqint「現在最小的次數是多少?」
iter 這張表最容易被漏掉,但少了它整個 O(1) 就垮了。 key 升級時要從舊桶的 list 中間拔出來 —— std::list::erase(iterator) 本身是 O(1), 但前提是你手上要有那個 iterator。沒有 iter,就得從 front 掃過去找,變成 O(桶大小)。 而 list(而不是 vector)之所以必要,正是因為它從中間刪除不會讓其他 iterator 失效。

minFreq 為什麼永遠不用「重新尋找」// THE KEY LEMMA

LEMMA · minFreq 只有兩種變動方式,都是 O(1)

① 插入新 key ⇒ minFreq = 1。 新 key 的次數固定是 1,而 1 是可能的最小值 —— 不必比較,直接賦值。

② 使用某個 key,而它剛好是最小桶裡的最後一個 ⇒ minFreq 恰好 +1。 那個 key 從 freq[minFreq] 搬到 freq[minFreq + 1],舊桶空了。 而新的最小值不可能大於 minFreq + 1 —— 因為剛剛那個 key 就落在那裡。 所以答案必定是 minFreq + 1,++ 一下就對了。

③ 淘汰不會讓 minFreq 需要變動 —— 淘汰之後緊接著就是插入新 key,而 ① 又把它設回 1。

整支程式最關鍵的一行就是 ② 那一行:if (freq[minFreq].size() == 0) ++minFreq; 而它最詭異的地方是:把它刪掉,答案一次都不會錯 —— 它會直接記憶體錯誤。實測細節見程式碼頁。

一句洞察// INSIGHT

「找最小」之所以貴,是因為你每次都重新找。 而這題的最小值每次只會往下跳到 1、或往上爬 1 格 —— 只要變化量有界,就可以用一個變數增量維護它,而不必重算。 設計題的核心往往不是資料結構本身,而是「哪個量的變化夠小,小到可以用一個變數追蹤」。
