完整實作// THE CODE

原碼一字未改,只補上註解。它在 LeetCode 的約束下完全正確 —— 實測與 O(n) 暴力解交叉比對 1010737 次 get,不一致 0。

p460.cpp C++17 
class LFUCache {
public:
    LFUCache(int capacity) {
        cap = capacity;
    }

    int get(int key) {
        if (m.count(key) == 0) return -1;

        // 從舊桶拔出來 —— 靠 iter[key] 直接定位,所以是 O(1)
        freq[m[key].second].erase(iter[key]);
        ++m[key].second;

        // 插到新桶的尾端 —— front 永遠是該桶裡最久沒用的
        freq[m[key].second].push_back(key);
        iter[key] = --freq[m[key].second].end();

        // 最小桶被搬空了 ⇒ 新的最小值必定是 minFreq + 1
        if (freq[minFreq].size() == 0) ++minFreq;

        return m[key].first;
    }

    void put(int key, int value) {
        if (cap <= 0) return;

        // 命中就只改值 —— get 已經順便把次數加好了
        if (get(key) != -1) {
            m[key].first = value;
            return;
        }

        // 滿了 → 淘汰「次數最少的裡面,最久沒用的那個」
        if (m.size() >= cap) {
            m.erase(freq[minFreq].front());
            iter.erase(freq[minFreq].front());
            freq[minFreq].pop_front();
        }

        // 新 key 次數固定是 1 ⇒ minFreq 直接歸 1,不用比較
        m[key] = {value, 1};
        freq[1].push_back(key);
        iter[key] = --freq[1].end();
        minFreq = 1;
    }

private:
    int cap, minFreq;
    unordered_map<int, pair<int, int>> m;       // key → {值, 次數}
    unordered_map<int, list<int>> freq;          // 次數 → key 的 LRU list
    unordered_map<int, list<int>::iterator> iter; // key → 在 list 裡的位置
};

這是本題最值得記住的一課。 「測資全過」不代表沒事 —— 這個 bug 在 41 萬次 get 裡一次錯誤答案都不產生, 它產生的是記憶體毀損。而記憶體毀損可能在很久以後、在完全無關的地方才爆出來。 這種 bug 只有 sanitizer 抓得到,對答案比對是隱形的。

拿掉 ++minFreq 那一行 0 直接崩 cap=1: put(0,0) get(0) put(1,0) → ASan

注意 push_front 那個變體的最小反例需要 6 個操作。 它只在「同一桶裡有兩個以上的 key,而且要淘汰」時才會現形 —— 桶裡只有一個 key 時,front 和 back 是同一個。 而 >= 寫成 > 三個操作就爆,因為它讓快取多裝一個,每次滿載都錯。

兩個在 LeetCode 上看不出來的問題// LATENT ISSUES

問題 1 · 用 -1 當「不存在」的哨兵 —— 值本身就可能是 -1

if (get(key) != -1) 拿回傳值來判斷 key 在不在。 但 -1 同時也是一個合法的值 —— 存了 -1 的 key,get 會回傳 -1,於是 put 誤判它不存在。

LeetCode 保證 0 ≤ value ≤ 10⁹,所以這在題內永遠不會發生。 但把約束放寬到允許負值,實測就會現形:105752 次 get 中不一致 257 次。

窮舉搜到的最小反例:

cap = 2 put(0, -1) put(1, 7) put(0, -1) get(1) → -1 // 正解 7

而且它壞的不只是答案,是結構本身:

put(1, -1); put(2, 5); → m 有 2 個 key,freq 裡也是 2 個,一致 ✓ 再 put(1, 9); → m 只剩 1 個,但 freq 裡還是 2 個,而且 key 1 出現了兩次 接著 get(2) = -1 // key 2 被那次誤判當成受害者淘汰掉了
問題 2 · freq 的空桶永遠不會被清掉

key 每升一級就開一個新桶,而舊桶就算空了也留在 freq 裡。 於是 freq.size() 跟著最大使用次數成長 —— 也就是跟著操作次數成長, 而不是跟著 capacity。

// 實測 cap=10, 1000 次操作 → freq 桶數 93,其中 86 個是空的,活著的 key 只有 10 個 cap=10, 10000 次操作 → freq 桶數 883,其中 873 個是空的 cap=10,100000 次操作 → freq 桶數 8529,其中 8519 個是空的 cap=1,同一個 key 反覆 put 20 萬次 → freq 桶數 200000,空桶 199999,minFreq = 200000

題目上限 2×10⁵ 次呼叫,所以最壞是 20 萬個空桶 —— 記憶體吃得下,LeetCode 過得了。 但這讓空間從 O(capacity) 變成 O(操作次數),嚴格說已經不符合快取的定義了。

順帶一提第三個小問題:m.size() >= cap 是 size_t 比 int —— -Wsign-compare 會警告。但這裡不會出事,因為前面 if (cap <= 0) return; 已經保證 cap ≥ 1,轉成無號不會變成天文數字。寫成 (int)m.size() >= cap 就沒警告了。

把兩個問題都修掉// THE FIXED VERSION

改兩件事:用 find 判斷存在(不再依賴 -1 哨兵), 以及桶空了就 freq.erase 掉。

p460_fixed.cpp O(1) · O(capacity) 
class LFUCache {
public:
    LFUCache(int capacity) : cap(capacity), minFreq(0) {}   // minFreq 也初始化

    int get(int key) {
        auto it = m.find(key);
        if (it == m.end()) return -1;
        touch(it);
        return it->second.first;
    }

    void put(int key, int value) {
        if (cap <= 0) return;

        auto it = m.find(key);          // 用 find 判斷,不看回傳值
        if (it != m.end()) {
            it->second.first = value;
            touch(it);
            return;
        }

        if ((int)m.size() >= cap) {     // 顯式轉型,沒有 sign-compare 警告
            int victim = freq[minFreq].front();
            freq[minFreq].pop_front();
            if (freq[minFreq].empty()) freq.erase(minFreq);   // 空桶收掉
            m.erase(victim);
            iter.erase(victim);
        }

        m[key] = {value, 1};
        freq[1].push_back(key);
        iter[key] = --freq[1].end();
        minFreq = 1;
    }

private:
    // 「使用一次」的共同邏輯,get 與 put 都走這裡
    void touch(unordered_map<int, pair<int, int>>::iterator it) {
        int key = it->first, f = it->second.second;

        freq[f].erase(iter[key]);
        if (freq[f].empty()) {
            freq.erase(f);                   // 空桶收掉
            if (minFreq == f) ++minFreq;      // 同一行邏輯,只是寫法不同
        }

        ++it->second.second;
        freq[f + 1].push_back(key);
        iter[key] = --freq[f + 1].end();
    }

    int cap, minFreq;
    unordered_map<int, pair<int, int>> m;
    unordered_map<int, list<int>> freq;
    unordered_map<int, list<int>::iterator> iter;
};
// 修好版的實測 與暴力解交叉比對 2999995 次 get（20 萬條隨機序列）→ 不一致 0 cap=1,同一 key put 20 萬次 → freq 桶數 1 （原碼 200000） cap=10,10 萬次操作 → freq 桶數 10 （原碼 8529） 那個 -1 最小反例 → get(1) = 7 ✓ （原碼回傳 -1）
但要說清楚:在 LeetCode 上,原碼和這版是同樣正確的。 -1 哨兵靠的是題目的值域保證,空桶靠的是呼叫次數上限。 兩者都是「借來的正確性」 —— 面試時能主動說出「我這裡依賴了 value ≥ 0 這個條件」,比默默寫對更值錢。
