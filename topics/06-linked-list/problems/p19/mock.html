Hmm, let me think about this for a second.

A naive one-pass approach would be to push every node pointer into a vector and index into it. That works, but it spends O(n) space on something that shouldn't need any — and it uses nothing about the list being a list.

This problem reminds me of two pointers held at a fixed gap. If I move one pointer ahead by a fixed number of steps and then advance both together, the gap never changes. So when the front one runs off the end, the back one is at a known distance from the end — without ever counting the length.

That turns "walk to a position I don't know yet" into "walk until the front pointer hits null," which is a condition I can actually see.

P — plan
C
CANDIDATE

Here's the plan.

// setup
dummy -> head;   tail = curr = &dummy

// open the gap
advance curr by n + 1 steps

// move together — gap is invariant
while (curr) { tail = tail->next; curr = curr->next; }

// curr is off the end, so tail is n+1 from the end
tail->next = tail->next->next

One: a dummy node before head, with tail and curr both starting there.
Two: advance curr by n + 1 steps to open the gap.
Three: move both together until curr is null, then unlink tail->next.

The gap is n + 1, not n. With n, tail would land on the node I want to remove, and I can't delete from there. One extra step puts tail on the predecessor instead.

And I need a dummy node. When n equals the length, the node to remove is the head, which has no predecessor at all. The dummy invents one, so removing the head and removing anything in the middle become the same two lines, and returning dummy.next handles the head changing for free.

Does this approach sound good, or would you rather I think of another way?

INTERVIEWER

I — implement
C
CANDIDATE

Alright, let me code this up.

class Solution {
public:
    ListNode* removeNthFromEnd(ListNode* head, int n) {
        // dummy = the head's predecessor; when n == sz, the head is removed
        ListNode dummy(0, head);
        ListNode *tail = &dummy, *curr = &dummy;

        // open a gap of n+1: the extra step makes tail stop one node before
        for (int i = 0; i < n + 1; ++i) {
            curr = curr->next;
        }

        // move together; the gap never changes
        while (curr) {
            tail = tail->next;
            curr = curr->next;
        }

        // tail now sits right before the node to remove
        ListNode* victim = tail->next;
        tail->next = victim->next;
        delete victim;            // unlinking isn't enough — it still holds memory

        return dummy.next;
    }
};

Three things worth flagging.

The loop condition is while (curr), not while (curr->next) — the second stops a step early, so tail ends one node short and I'd unlink the wrong node.

The dummy lives on the stack, and I delete the removed node — unlinking alone leaves it allocated, and a heap dummy with no delete leaks two nodes per call.

And advancing curr by n + 1 without a null check is safe: the dummy plus sz nodes makes sz + 1 slots, and since n ≤ sz, the furthest I go lands exactly on null. That relies on your guarantee; without it, I'd need a null check there.

The row that matters is opening the gap: curr moves three steps while tail stays on the dummy, so the gap is 3. After that it stays 3 — that invariant is the whole algorithm. When curr falls off the end, tail is on node 3, and I unlink the 4. That matches.

Corner cases:

• [1], n = 1 → []: a single node returns empty.
• [1,2], n = 2 → [2]: removes the head — the case the dummy exists for.
• 30 nodes, n = 30: sends curr furthest, exactly onto null.

All 465 legal inputs match a reference. Dropping the dummy fails only 30 of them — exactly the head removals — so it's the most dangerous bug: it hides in the case people skip testing by hand.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time is O(sz) in a single pass — curr takes sz + 1 steps and tail takes sz − n. Space is O(1): two pointers and one stack-allocated dummy.

I do want to be honest about what "one pass" bought us, though. The two-pass version is also O(sz), with the same O(1) space and about the same number of pointer steps. One pass matters when a second traversal is genuinely expensive, like streaming data you can only read once.

Oh, one more thing — the gap is however many steps you need to stop before the target. If the problem were to return the nth node from the end, the gap would be plain n, with no dummy, since nothing gets modified. So: gap n to read, gap n + 1 to delete.
