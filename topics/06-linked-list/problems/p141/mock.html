Hmm, let me think about this for a second.

A naive approach would keep a hash set of node addresses as I walk. If I ever see one twice, there's a cycle; if I reach null, there isn't. That's O(n) time and correct, but it's O(n) space, which is exactly what you asked me to avoid.

Walking a fixed number of steps doesn't hold up either: I don't know n, and borrowing the stated maximum would smuggle a constraint into the algorithm.

This problem reminds me of Floyd's cycle detection — two pointers at different speeds. Picture a running track: if the path is a loop, the faster runner laps the slower one and they land on the same spot. If the path has an end, the faster runner hits it first. Two pointers, no container, O(1) space.

P — plan
C
CANDIDATE

Here's the plan.

// slow moves 1, fast moves 2
if there IS a loop  → fast catches slow  → return true
if there ISN'T      → fast reaches null → return false

// why it can't overshoot
once slow is in the loop, let d = how far fast trails slow
each round: fast +2, slow +1  → d decreases by exactly 1
so d must land on 0. it cannot step over it.

One: slow and fast both start at the head.
Two: each round, slow moves one step, fast moves two, then I compare.
Three: if they meet, return true; if fast reaches null, return false.

The key is the gap: once slow is in the loop, the speed difference is exactly one, so the gap shrinks by one per round and has to hit zero.

One thing worth flagging: I compare pointers, not values — values can repeat, so comparing val would report cycles that aren't there.

Also, both start at the head, so comparing before moving returns true for everything. I'll use a do-while so the first thing is a move; the cost is that the body runs once unconditionally, so I need a guard for empty and single-node lists. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up: a guard, then the do-while from the plan.

class Solution {
public:
    bool hasCycle(ListNode *head) {
        // do-while always runs the body once, and the body does
        // fast->next->next — so this line is required, not defensive
        if (!head || !head->next) return false;

        ListNode *slow = head, *fast = head;

        do {
            slow = slow->next;          // one step
            fast = fast->next->next;    // two steps

            // move, then compare — both start at head
            if (slow == fast) return true;

        } while (fast && fast->next);   // need both checks

        return false;
    }
};

Two details in the loop condition. fast being null means those two steps landed exactly past the end; fast->next being null means two more steps would run off. Drop either check and the next round dereferences null — and the order relies on && short-circuiting.

And the guard isn't a nicety: removing it under the sanitizers, both the empty list and a single node crash with a member access within null pointer.

Worth knowing: a plain while (fast && fast->next) with the same condition checks first, so the body is always safe and the guard isn't needed at all. Both are correct; the while version fails more gently if you forget a line.

The row that matters is round two: fast goes 2 → 3 → and then follows the back edge to 1. Once inside the loop it can never leave, and slow walks in behind it. One round later they meet at index 3 — not the entry at index 1, which is fine for a boolean.

Without a cycle, like [1,2,3,4,5], fast->next goes null after two rounds: false.

Corner cases:

• Empty, or [1] → false, through the guard.
• [1] pointing at itself → true in one round.
• [1,2], tail → head → true.

The shape depends only on length and back-edge index, so I ran all 1,891 shapes up to 60 under the sanitizers: zero wrong.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time is O(n). Without a cycle, fast covers two nodes a round, so about n/2 rounds. With one, slow needs μ rounds to enter the loop and at most λ more to be caught, and μ + λ is at most n.

Measured up to n = 300: worst case 150 rounds without a cycle, 300 rounds with one.

Space is O(1), two pointers, read-only.

Oh, one more thing — the usual reason for step 2 is that a bigger step could jump over. I checked: with step 3, detection still works on all 20,100 cycle shapes, because the starting gap 2μ mod λ is even whenever the loop length is even.

What breaks is the entry-finding follow-up, wrong on about three in ten shapes. So "use 2" is right, but the usual reason isn't.
