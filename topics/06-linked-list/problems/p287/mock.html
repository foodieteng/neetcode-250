You're given an array nums of n + 1 integers, where every integer is in the range [1, n] inclusive. There is exactly one repeated number. Return it.

Two constraints: you must not modify the array, and you may only use constant extra space.

Two clarifications. First — can the duplicate appear more than twice? Like [2,2,2,1,3]?

Second: is it guaranteed a duplicate exists at all?

Actually, I can answer that myself. It's pigeonhole. I have n + 1 items to place into n possible values, so at least one value is used twice. The extra guarantee — that only one value repeats — isn't needed for existence; it's what makes the answer unique.

That's the follow-up question, answered before I asked it. Go ahead.

M — match
C
CANDIDATE

Let me lay out the obvious approaches and let the constraints eliminate them.

Hash set — O(n) time but O(n) space. Breaks the space rule.

Sort — O(n log n), and sorting in place modifies the array, while a sorted copy costs O(n) space.

Negative marking — flip the sign of nums[abs(nums[i])]. O(1) space, but the sign bits are the memory, so it modifies the array.

Both constraints together block every "remember what I've seen" strategy. That's the signal: I need something that doesn't record anything.

I
INTERVIEWER

Do you have anything that survives both?

C
CANDIDATE

Yes — let me put a safe one on the table first, then try to beat it.

Binary search on the value, not the index. Pick a midpoint value mid, then count how many elements are <= mid. Pigeonhole again: if that count exceeds mid, the duplicate lives in the left half.

That's O(n log n) time, O(1) space, and it only reads the array. Both constraints satisfied. But you'd probably ask for linear, so let me look for a better angle.

I
INTERVIEWER

I would. Take a minute.

C
CANDIDATE

The values are in [1, n] and the indices are in [0, n]. So every value is itself a valid index — I can treat nums[i] as a pointer.

Define an edge from index i to index nums[i]. Every node has exactly one outgoing edge, so this is a linked list whose "next pointer" is an array lookup.

With finitely many nodes, walking from index 0 must revisit one: there is a cycle.

And the key detail: values are at least 1, so no edge ever points at index 0. Index 0 has no predecessor, so it's outside the cycle. The shape is a tail leading into a loop — a rho.

I
INTERVIEWER

And how does that give you the duplicate?

C
CANDIDATE

The entrance to the cycle is the one node with two incoming edges — one from the tail, one from wrapping around the loop.

Translate that back: an edge into node v means some index holds v. Two edges into v means two different indices hold the same value. That's the duplicate. So find the cycle entrance, and that's the answer.

This problem reminds me of finding where a linked list's cycle begins — Floyd's tortoise and hare fits exactly, with p->next replaced by nums[p].

P — plan
C
CANDIDATE

Let me walk [1,3,4,2,2] first.

// edges: i -> nums[i]
index : 0 1 2 3 4
nums  : 1 3 4 2 2
walk  : 0 -> 1 -> 3 -> 2 -> 4 -> 2 -> 4 -> ...
tail  : 0, 1, 3   // mu = 3
cycle : 2, 4      // lambda = 2
entrance = 2  // and 2 is indeed the repeated value

From index 0, the walk goes 1, 3, then 2, 4, 2, 4 — a tail of three into a cycle of length two, entering at 2, the repeated value.

Here's the plan.
One: start slow and fast together at nums[0].
Two: slow moves one step, fast moves two, until they meet — somewhere on the cycle, not necessarily the entrance; in this example they happen to coincide, which is misleading.
Three: reset slow to the start, leave fast at the meeting point, move both one step at a time; where they meet is the entrance.

I
INTERVIEWER

Why does phase two land on the entrance? Don't just tell me it works.

C
CANDIDATE

Measure from where both pointers start. Let mu be the distance to the entrance, lambda the cycle length, and d the steps slow has taken when they meet.

Fast has taken 2d, on the same node, so the difference 2d - d = d is a whole number of laps.

Walking mu steps from the start lands on the entrance by definition. Walking mu steps from the meeting point is like walking d + mu from the start, and the d is whole laps, so it cancels out.

Both reach the entrance after exactly mu steps — which is why they must move at the same speed.

I — implement
C
CANDIDATE

Alright, here's the code.

class Solution {
public:
    int findDuplicate(vector<int>& nums) {
        // both start at nums[0] — same as "each already took one step"
        int slow = nums[0], fast = nums[0];

        // phase 1: slow 1 step, fast 2 — find a meeting point (NOT the entrance)
        do {
            slow = nums[slow];
            fast = nums[nums[fast]];
        } while (slow != fast);

        // phase 2: slow back to start, fast stays; both 1 step at a time
        slow = nums[0];

        while (slow != fast) {
            slow = nums[slow];
            fast = nums[fast];
        }

        // meeting point = cycle entrance = 2 incoming edges = the duplicate
        return slow;
    }
};

Two things to call out.

The do-while is not stylistic. Both pointers start at nums[0], so they're already equal. A plain while would skip the loop, phase two would skip too, and the function degenerates into return nums[0].

The double index needs no bounds check. Every value is in [1, n], and the array has indices 0 through n, so both lookups in nums[nums[fast]] are provably in range — and there's no null to guard.

The row that matters is round two of phase one: slow and fast meet at 2, which here is also the entrance — a coincidence of this input. Stopping after phase one would pass this test and fail others. Phase two resets slow, and two rounds later they meet at 2 again. Returns 2. Correct.

Edge case: the smallest legal input, [1,1]. They meet at 1 in phase one, and phase two finds them already equal. Returns 1. Correct.

What if I told you a candidate wrote this with a plain while, and it passed most of their own tests?

C
CANDIDATE

I'd believe it, and that's the worst kind of bug — it just returns nums[0], which is the right answer surprisingly often: about 44% of all small inputs up to n = 6.

The shortest input that exposes it is [1,2,2] — it returns 1 instead of 2.

The general lesson: if two pointers start at the same node, "test then move" is a no-op. Either move first, or stagger the starting positions.

E — evaluate
C
CANDIDATE

Time O(n): phase one is bounded by tail plus cycle length, phase two by the tail, and both are at most n. Space O(1) — two integers.

The array is never written to. So both constraints hold, and the linear follow-up is answered.

One honest caveat: this leans hard on the values being [1, n] and not [0, n-1]. If zero were legal, index 0 could sit inside the cycle and the rho shape is gone. [0,1,1] breaks it — index 0 is a self-loop, and it returns 0 instead of 1.

Then I'd fall back to the binary search on values, which doesn't care where the range starts.
