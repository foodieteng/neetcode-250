Here's the thing that shapes the whole design: this problem asks for two things at once, and no single data structure gives me both.

A hash map finds a key fast, but it has no order, so it can't tell me who's oldest. A list keeps the order of use, but it can't find a key without walking it.

So I want both, side by side — and what ties them together is that the hash map stores the address of the list node. One lookup, and I'm holding the node.

This problem reminds me of the classic hash-map-plus-doubly-linked-list pairing.

One thing worth flagging — it has to be doubly linked. Even with the node in hand, a singly linked list can't unhook it without the node before it, and finding that means walking from the head. The O(1) lookup gets cancelled out by an O(n) unhook. With prev pointers, a node can unhook itself.

Here's the plan.

// state
list : oldest .......... newest      // order lives here
map  : key -> address of that node  // speed lives here

// invariant
the list is always sorted by last-use time.
nothing computes it — every operation just maintains it.

// the two moves
use(node) = unhook(node), then attach at the newest end
evict()   = take the node at the oldest end,
            remove it from both structures

One: the list holds the order, oldest to newest, and the map holds key → node address.
Two: a use unhooks the node and attaches it at the newest end.
Three: an eviction takes the node at the oldest end and removes it from both structures.

The invariant is that the list is always sorted by last use — nothing computes it, every operation just maintains it. There's a trade-off: two structures and two pointers per node, to turn eviction from a scan into a single step.

One thing worth flagging about the plan: whenever a node enters or leaves, both structures must change together. Unhook a node but forget the key, and the map keeps a ghost entry. Erase the key but forget to unhook, and the list keeps an orphan that can never be evicted.

class Node {
public:
    int key, val;
    Node *prev, *next;
    // store the key too -- eviction needs it for cache.erase()
    Node(int k = 0, int v = 0) : key(k), val(v), prev(nullptr), next(nullptr) {}
};

class LRUCache {
public:
    int sz;
    Node *left, *right;              // left end = oldest, right end = newest
    unordered_map<int, Node*> cache;  // key -> node address (this pointer is the bridge)

    // attach just before right = newest end. zero ifs: right always exists
    void insert(Node* node) {
        Node *back = right->prev;
        back->next = node;
        node->prev = back;
        node->next = right;
        right->prev = node;
    }

    // unhook in place. only a doubly linked list can: the predecessor is node->prev
    void remove(Node* node) {
        Node *prev = node->prev, *next = node->next;
        prev->next = next;
        next->prev = prev;
    }

    LRUCache(int capacity) {
        sz = capacity;
        left = new Node();            // two sentinels, linked to each other
        right = new Node();
        left->next = right;
        right->prev = left;
    }

    int get(int key) {
        if (cache.find(key) == cache.end()) return -1;  // a miss is not a use

        Node *node = cache[key];
        remove(node);                    // unhook
        insert(node);                    // attach at the newest end
        return node->val;
    }

    void put(int key, int value) {
        if (cache.find(key) != cache.end()) {
            Node *node = cache[key];
            node->key = key;              // redundant: node->key already equals key
            node->val = value;
            remove(node);
            insert(node);                // a put counts as a use too
            return;
        }

        if (cache.size() == sz) {
            Node *lru = left->next;     // no search for the victim: it's at the left end
            remove(lru);                 // clean both structures --
            cache.erase(lru->key);      // this is what node->key is for
        }

        Node *node = new Node(key, value);
        insert(node);
        cache[key] = node;
    }
};

Two dummy nodes, left and right, sit at the ends, so node->prev and node->next are never null — that's why remove and insert have zero if statements. A get hit unhooks the node and re-attaches it before right, the newest end. A put on an existing key updates the value and moves it the same way. Otherwise, if the cache is full, the victim is simply left->next.

One thing worth flagging — Node stores the key, which looks redundant. It isn't: at eviction I reach the node from the list side, and only the node knows which key to erase from the map.

C
CANDIDATE

Right. std::list is already a doubly linked list, so I drop my Node class and both dummies, and the map stores a list iterator instead. The front is the newest end. The one call that makes this work is splice: passing the same list as source and target moves a node inside the list in O(1).

class LRUCache {
public:
    LRUCache(int capacity) {
        cap = capacity;
    }

    int get(int key) {
        auto it = m.find(key);                  // must use find: m[key] would insert a missing key
        if (it == m.end()) return -1;           // a miss is not a use; l is untouched
        l.splice(l.begin(), l, it->second);     // second arg is l itself = move within the list
        return it->second->second;              // it stays valid after the move; m needs no update
    }                                             //   it->second is an iterator; -> reaches the pair

    void put(int key, int value) {
        auto it = m.find(key);
        if (it != m.end()) l.erase(it->second);   // hit: drop the old node first, or it's orphaned
        l.push_front(make_pair(key, value));     // always insert at the newest end (front)
        m[key] = l.begin();

        if (m.size() > cap) {                     // insert first, then check -> so > not >=
            int k = l.rbegin()->first;           // copy the key FIRST
            l.pop_back();                        //   pop_back returns nothing and frees the node
            m.erase(k);                          // clean both structures together
        }
    }

private:
    int cap;
    list<pair<int, int>> l;                     // order: front newest, back oldest
    unordered_map<int, list<pair<int, int>>::iterator> m;   // speed: key -> the node's iterator
};

Two details. First — after splice, the map needs no update. splice only rewires links, the node never moves, so the stored iterator stays valid.

Second — the order of the eviction lines matters. pop_back returns nothing and frees the node, so I copy the key first. Swap them, and the evicted key stays in the map pointing at freed memory — AddressSanitizer reports heap-use-after-free at the next splice.

C
CANDIDATE

Let me think about complexity here.

Time is O(1) average for both operations: one hash lookup plus a fixed number of pointer writes. The list half is worst-case O(1); the "average" comes only from the hash map.

Space is O(capacity) — one node and one map entry per key.

The worst case is every put being a new key on a full cache, so every call evicts. That's still O(1), because the victim is always the node at the oldest end.

C
CANDIDATE

Oh, one more thing — two notes on the versions.

Memory. Version 1 never deletes the evicted node. LeetCode won't catch it, but the leak grows with evictions — capacity 10 with 100,000 distinct keys leaks 100,002 nodes, about 2.3 MB. std::list frees its own nodes, so nothing is left outstanding.

A speedup. On a hit, put can edit the value in place and splice, instead of erase + push_front — about 8× faster on hitting puts.

It all works because list iterators stay valid; a vector breaks that.
