重點回顧// RECAP

面向要記住的那一句
核心組合雙向串列管順序,雜湊表管速度,而雜湊表的值是節點的位址
為什麼要「雙向」不是為了往回走,是為了能就地把自己拆下來(單向要先找前驅)
為什麼不用 vector搬移要 O(n),而且搬完索引全變,雜湊表存的位置整批失效
兩個哨兵買到什麼串列永遠非空 ⇒ remove / insert 各四行,零個 if
「使用一次」怎麼寫remove(node) 再 insert(node) —— 兩者都是 O(1)
淘汰誰left->next,不用比較也不用掃描
Node 為什麼要存 key淘汰時是從串列拿到節點的,而要拿它的 key 去 cache.erase
兩張表要同步只 remove 沒 erase ⇒ 幽靈項目;只 erase 沒 remove ⇒ 淘汰不掉的孤兒
最危險的變體「不搬到最新端」 —— 結構完全正常,只是策略悄悄變成 FIFO
記憶體被淘汰的節點沒有 delete,洩漏量正比於淘汰次數
驗證與暴力解比對 1200008 次 get,不一致 0;每一步比對完整順序與雙向連結,180 萬次全過
寫法二std::list + splice + unordered_map<int, list<...>::iterator> —— 資料結構完全一樣,只是節點交給容器管
為什麼 list 能存 iterator插入不失效、erase 只失效被刪的那一個、splice 全部不失效(vector 三條都不成立)
splice 做了什麼只改前後鏈結,節點原地不動 —— 實測前後位址皆 0x11d605ff0,所以 m 不用更新
list 版的記憶體未釋放 0 —— 容器解構時自己歸還全部節點,不必寫 delete 也不必寫解構子
list 版最致命的一行pop_back() 不回傳值而且直接釋放節點 ⇒ 先抄 key,再 pop;倒過來就是 heap-use-after-free

應用題// APPLICATION

App 1. 題目保證 1 ≤ capacity。如果拿掉這個保證,capacity = 0 會發生什麼事?
App 2. 被淘汰的節點沒有 delete。漏多少?而如果補上 delete,還要注意什麼?
App 3. 同一份工作負載下,LRU 和 LFU 誰的命中率比較高?請實際量出來。
// ANSWERS
A1. 因為「拆下一個節點」需要改的是它前面那個的 next。

雜湊表給了你 node 的位址,這解決了「找到它」。但 remove 要做的是:
prev->next = next; next->prev = prev;

單向串列裡,node 根本不知道 prev 是誰 —— 唯一的辦法是從頭走過去找哪個節點的 next 等於 node,那是 O(n)。

結果就是:O(1) 的查表,被 O(n) 的拆除整個抵銷掉。

所以「雙向」的用途不是「可以往回走」,是「可以就地把自己拆下來」。 同樣的理由讓 460 LFU 用 std::list 而不是 vector —— list 從中間刪除不會讓其他迭代器失效,而 vector 會讓後面全部位移、存起來的索引整批作廢。
A2. 它們買到的是「不必處理特例」,而不是「少寫幾行」。

哨兵讓串列永遠非空,於是任何一個真實節點的 prev 和 next 保證不是 nullptr(最差就是碰到哨兵)。remove 因此只有四行、零個 if。

沒有哨兵的話,remove 要分四種情況:
· 拆的是頭 → 要更新 head,而且 node->prev 是 nullptr,不能寫 prev->next;
· 拆的是尾 → 要更新 tail,node->next 是 nullptr;
· 拆的是唯一一個 → 頭尾都要更新;
· 拆的是中間 → 才是那四行。

insert 同理。四個特例乘以兩個函式,就是八段各自可能寫錯的分支。

這和 19、92 的 dummy 是同一招,只是那兩題只需要「頭的前驅」,這裡因為兩端都會被操作,所以頭尾各放一個。
A3. 因為淘汰時,你是從串列那一端拿到節點的。

Node *lru = left->next; // 從串列拿到的,只有一個指標 remove(lru); // 從串列拆下 —— 這步不需要 key cache.erase(lru->key); // 但要從雜湊表刪掉,就必須知道 key ←

雜湊表是 key → 節點的單向對應,你沒辦法用節點指標反查 key。缺了 node->key,唯一的辦法是掃過整張雜湊表找哪一項的 value 等於這個指標 —— O(capacity),整個 O(1) 就毀了。

順帶一提原碼裡 put 命中分支的 node->key = key; 是多餘的 —— 能走到那裡就代表 cache 裡有這個 key,而 cache[key] 指向的節點,它的 key 本來就等於 key。無害,但可以刪掉。
A4. 它會變成 FIFO(先進先出),而不是 LRU。

節點只在插入時進入串列尾端,之後再也不動 —— 於是順序永遠等於「進來的先後」,而不是「用過的先後」。

實測(6 萬條隨機序列,899995 次 get):錯 12937 次(6828 條序列受影響)。
窮舉搜到的最小反例:
cap = 2 put(0,0) put(1,10) get(0) put(2,20) get(0) → -1 // 正解 0

中間那個 get(0) 本來應該讓 key 0 活下來,但它沒搬,所以 put(2,20) 還是把它淘汰了。

這是所有變體裡最危險的一個,而它的失敗率反而最低(1.4%)。原因是: 它不會讓資料結構壞掉,也不會回傳垃圾 —— 雙向連結完好、雜湊表同步、容量正確,只是淘汰策略被悄悄換掉了。 你只有在「用過的東西後來被淘汰」這種特定序列上才看得見它。
A5. 因為它們是同一個錯誤 —— 「把哪一端當成最舊的」搞反了。

這條串列的語意完全建立在一個約定上:left 端最舊、right 端最新。而這個約定是由兩件事共同維持的:
· insert 永遠插在 right 端(「剛用過的最新」);
· 淘汰永遠取 left 端(「最舊的先走」)。

把其中任何一個翻過來,整條串列的方向語意就整個反轉 —— 產生的行為是完全對稱的。

實測證實了這一點:兩者的錯誤數一模一樣,都是 62902 / 899995,受影響序列都是 19511 / 60000,連最小反例都相同:
cap = 2 put(0,0) put(1,10) put(2,20) get(0) → 0 // 正解 -1

而如果兩個一起翻過來,它會變回完全正確的 LRU —— 只是串列的方向和你想的相反。 這類「約定型」的 bug 的特徵就是這樣:單獨翻一個會壞,一起翻反而沒事。
A6. 因為 splice 沒有搬動任何資料 —— 它只改前後兩根鏈結,節點本體原地不動。

實測直接印位址:splice 之前 &*it = 0x11d605ff0,splice 之後 &*it = 0x11d605ff0 —— 完全相同,而且 it == l.begin() 成立。m[key] 裡存的那個 iterator 指的還是同一塊記憶體, 所以它依然有效、依然指向正確的節點,一個字都不用改。

換成 vector 就完全不成立,而且是兩層失敗:
① 「把中間某一項搬到最前」本身就是 O(n) —— 後面所有元素都要往後挪一格。
② 挪完之後,你存在雜湊表裡的每一個位置都指向了錯的元素; 更糟的是 push_back 一旦觸發重新配置,整個 vector 換一塊記憶體,你存的每一根指標/迭代器全部作廢。

所以「雜湊表存位置」這一招,靠的不是雜湊表,是被指向的那個容器保證不亂動它的元素。 list 的三條保證(插入不失效、erase 只失效被刪的、splice 全部不失效)就是這題選它的全部理由。
A7. 對調之後就是 heap-use-after-free —— ASan 實測抓到,而且指得出是哪一個位元組。

把 int k = l.rbegin()->first; 和 l.pop_back(); 對調,變成:
l.pop_back(); m.erase(l.rbegin()->first);

問題有兩個,而且是疊在一起的:
① pop_back() 不回傳被刪的值(和 vector::pop_back 一樣) —— 想拿被淘汰的 key,只能在刪之前拿。
② 它會直接釋放那個節點。所以 pop_back 之後 l.rbegin() 指到的已經是另一個元素 —— 你會從雜湊表刪掉一個還活著的 key,而剛被淘汰的那個 key 反而留在 m 裡,指著一塊已經還掉的記憶體。

實測(ASan):heap-use-after-free,READ of size 8, 爆點不在 pop_back 那一行,而在後來的某一次 l.splice(...) —— 它讀的是那個幽靈 iterator 的鏈結指標 —— ASan 說得更精確: 位址落在一個 24 byte 區塊往內 8 bytes 的地方, 而 pair<int,int> 的 list 節點正好是 prev(8) + next(8) + pair(8) = 24 —— 位移 8 就是 next 指標; freed by 的堆疊指回 pop_back。

而「erase 只讓被刪的那一個失效」這條規則救不了它,原因就藏在那句話裡 —— 它保證的是「其他 iterator 還活著」,而這裡出事的正是被刪掉的那一個。 規則沒有被違反,是我們拿去用的剛好就是唯一那個已經死掉的。

對照程式碼頁第 6 節的陷阱表看很有意思:這個 bug 會崩,所以 ASan 一跑就抓到; 而「put 命中忘了 l.erase」ASan 完全乾淨,只是安靜地答錯 23032 次。 記憶體錯誤有工具幫你找,邏輯錯誤只有對拍找得到。
App 1. 會直接 SEGV —— 而且是寫入 nullptr,不是讀。

capacity = 0 時,第一次 put:cache.size() 是 0,sz 也是 0,0 == 0 成立,於是進入淘汰分支。但快取是空的,所以:
Node *lru = left->next; // 串列是空的 ⇒ left->next 就是 right 哨兵本身！ remove(lru); → prev = right->prev = left → next = right->next = nullptr （right 是最後一個,它的 next 從來沒被設過) → next->prev = prev; // 對 nullptr 寫入

實測(ASan + UBSan):
runtime error: member access within null pointer of type 'Node' AddressSanitizer: SEGV on unknown address 0x000000000008 The signal is caused by a WRITE memory access. #0 in LRUCache::remove(Node*) // 0x8 正是 prev 這個成員在 Node 裡的位移(key 4 + val 4)

修法有兩個層次:最直接是在 put 開頭加 if (sz <= 0) return;; 更根本的是把 cache.size() == sz 改成 >= —— 但那只是讓它不會「超收」,空快取的情形還是得靠守衛擋掉。

這是本章反覆出現的主題:題目給的約束不是裝飾。 1 ≤ capacity 買到的就是「淘汰分支永遠不會在空串列上執行」 —— 和 92 靠 right ≤ n 讓反轉迴圈不必檢查 nullptr 是同一種「借來的安全」。
App 2. 洩漏量正比於「淘汰次數」—— 而補上 delete 之後,順序會從無所謂變成致命。

實測(覆寫 Node::operator new / delete,sizeof(Node) = 24):
cap=2,put 三次(1 次淘汰) → new 5, delete 0 洩漏 5 個 = 2 哨兵 + 2 個活的 + 1 個被淘汰的 cap=10,put 10 萬個不同 key → new 100002, delete 0 洩漏 2.3 MB 快取本身明明只該佔 10 個節點 cap=10,反覆 put 同樣 10 個 key → new 12, delete 0 洩漏 12 個 （從不淘汰,所以幾乎不漏)

要修的有兩處:淘汰時 delete lru;,以及寫一個解構子把哨兵與所有活著的節點收掉。實測補完之後,同樣的 10 萬次測試 new = delete = 100002,洩漏 0。

但補 delete 會引進一個新陷阱。原碼裡「先 remove 再 erase」和「先 erase 再 remove」實測都是 0 錯(60000 條序列全過)—— 因為兩者互不相干,而 lru->key 在兩種順序下都讀得到。
那個「都讀得到」,靠的正是節點沒有被釋放。

// 補上 delete 卻寫成先 delete 再 erase delete lru; cache.erase(lru->key); ERROR: AddressSanitizer: heap-use-after-free READ of size 4 // 正是那個 int key

正確順序:remove → cache.erase(lru->key) → delete lru。 和 92 那兩行接線同一類:一個東西同時是「資料來源」和「銷毀目標」時,順序就不是風格問題。
App 3. 答案是「看工作負載」,而且差距量出來比想像中戲劇化。

拿 460 的 LFU 和本題的 LRU 跑同一份序列(get miss 就 put,統計命中率):

(a) 循序掃描:500 個 key 反覆循環 20 圈,cache 只裝 100 個
LRU 命中 0 / 10000 ( 0.0%) LFU 命中 0 / 10000 ( 0.0%) // 兩個一起陣亡
循環掃描是兩者共同的死穴 —— 每個 key 次數都一樣,LFU 的平手規則就退回 LRU,所以行為完全一致。

(b) 熱點負載:80% 的存取集中在 20 個 key,cache 裝 50 個
LRU 命中 159679 / 200000 (79.8%) LFU 命中 160181 / 200000 (80.1%) // 幾乎沒差
穩定的熱點下兩者難分軒輊 —— 這也是最常見的情形。

(c) 工作集切換:前 2000 次存取 key 0-3,後 2000 次改存取 key 100-103,cache 裝 4 個
LRU 階段一 99.8% 階段二 99.8% LFU 階段一 99.8% 階段二 0.0% ← LFU 的老化問題
LFU 完全崩掉:舊 key 的次數新 key 永遠追不上,於是新 key 之間互相淘汰,老 key 一個都不走。

(d) 一次性掃描:10 個熱點 key 各用 50 次 → 一次掃過 1000 個冷 key → 再回頭用熱點,cache 裝 20 個
LRU 掃描後第一輪 10 個熱點:命中 0/10 ← 熱點被整批沖掉 LFU 掃描後第一輪 10 個熱點:命中 10/10 ← 冷 key 次數只有 1,擠不掉
這裡換 LRU 吃虧 —— 但也別誇大:LRU 只是多付了 10 次 miss,之後 490 次兩者都是 100%。

結論:沒有普遍最好的淘汰策略。 LRU 在工作集會變動時穩,LFU 在有穩定熱點又會被掃描打擾時穩,而循環掃描兩個都救不了。 加上 LRU 的實作簡單得多(實測 5.8 ~ 71 ns/op,LFU 是 128 ~ 142),沒有特殊理由時 LRU 是更好的預設選擇。
