M — match
C
CANDIDATE

Hmm, let me think about this for a second.

The baseline is to dump all values into a vector, sort, and rebuild. That's O(N log N) time and O(N) space. It works, but it throws away the sortedness, so it's only a fallback.

Here's the observation that matters: the global minimum has to be the head of one of the lists. Each list is sorted, so it can't be buried in the middle. There are only k candidates at any moment, not N.

This problem reminds me of a k-way merge with a priority queue: repeatedly extract the minimum of k things — which is exactly what a min-heap is for.

I
INTERVIEWER

Before you go there — is there a way to reuse something simpler?

C
CANDIDATE

Yes, and it's worth saying out loud. Merging two sorted lists is a solved problem — the standard two-pointer merge — so I could apply it repeatedly.

The naive way is to fold left: merge list 0 with list 1, then that result with list 2, and so on. That's O(N·k), because the growing result gets rescanned every step.

The fix is a knockout tournament: merge in pairs, then merge the winners pairwise. Each node is touched once per round, and there are only log k rounds, so it's O(N log k).

So I have two O(N log k) options: divide and conquer, or a min-heap over the k heads. I'll write the heap; it costs O(k) extra space, while divide and conquer only needs the two-list merge.

P — plan
C
CANDIDATE

Here's the plan.

// INVARIANT: the heap holds at most one node per list —
// that list's smallest not-yet-taken node
seed: push every non-null head  // heap size ≤ k
loop: pop the min, append it to the tail
      if that node has a next, push it
// pop one, push one → heap stays ≤ k, never grows to N
stop when the heap is empty

One: seed the heap with every non-null head.
Two: pop the minimum, append it to the tail, and if that node has a next, push it.
Three: stop when the heap is empty.

The invariant: the heap holds at most one node per list — that list's smallest node not yet taken. So the heap contains every list's current minimum, and the heap top is the global minimum. Pop one, push one, so the heap never grows past k.

One thing worth flagging: two guards, both null-pointer traps. Seeding needs if (p), and the refill needs if (node->next). Does this approach sound good, or would you rather I think of another way?

I
INTERVIEWER

Where exactly would the null crash happen?

C
CANDIDATE

Usually on the push itself, not later in the loop — which surprises people.

push does a sift-up right away, and sift-up calls the comparator, which reads l1->val through the null pointer. So with one real list and one empty list, it crashes at the moment of insertion, before the merge loop even starts.

One exception: if the only list is empty, the null sits alone in the heap, there's nothing to compare it with, and the push survives. Then it crashes inside the loop instead, at node->next. Either way, it crashes.

I — implement
C
CANDIDATE

Alright, let me code this up. It follows the plan line for line: seed with the guard, then pop, append, refill, and return dummy.next.

class Solution {
public:
    ListNode* mergeKLists(vector<ListNode*>& lists) {
        // "greater than" = min-heap. priority_queue is a max-heap by default, so flip it
        auto cmp = [&](auto &l1, auto &l2) {
            return l1->val > l2->val;
        };

        priority_queue<ListNode*, vector<ListNode*>, decltype(cmp)> pq(cmp);

        // seed: each list's head. if (p) is required — lists[i] may be nullptr
        for (auto& p : lists) {
            if (p) pq.push(p);
        }

        ListNode dummy;                // on the stack, freed automatically on return
        ListNode* tail = &dummy;

        while (!pq.empty()) {
            auto node = pq.top(); pq.pop();   // heap top = global minimum

            tail->next = node;
            tail = tail->next;

            // pop one, push one ⇒ heap size always ≤ k
            if (node->next) pq.push(node->next);
        }

        // no tail->next = nullptr needed here — the list self-terminates
        return dummy.next;
    }
};

The comparator direction is the easiest thing to get backwards. priority_queue's contract is that cmp(a,b) returning true means a has lower priority — and lower priority sinks. So to get the smallest on top, the comparator says greater than: a bigger value means lower priority.

And I put the dummy on the stack. Heap-allocating it would leak one node per call, since nothing points at it after I return dummy.next.

I
INTERVIEWER

You didn't terminate the result list. Every node you appended still has its original next. Isn't that a bug?

C
CANDIDATE

It looks like one, but it isn't — because of why the loop stops.

Each iteration pops one and pushes one, unless node->next is null. So the heap can only become empty on an iteration where nothing was pushed — which means the last appended node was already the tail of its own list. It's self-terminating.

Contrast that with the two-list merge: its loop is while (a && b), which stops while one list still has nodes, so you must attach the rest. The difference is the termination condition.

That said — I'd probably still write the terminator. The guarantee is implicit, and it evaporates the moment someone changes the loop to, say, "pop exactly N times." One line is cheap insurance.

I
INTERVIEWER

What if two nodes have the same value?

C
CANDIDATE

The heap doesn't guarantee which one comes out first — it isn't a stable structure.

For this problem that's harmless, because the output is judged on values, and the value sequence is identical either way.

But I'd flag it if the nodes carried anything beyond the key — merging timestamped log streams, for instance, where reordering same-millisecond events changes the meaning. The fix is a tiebreaker: carry the list index alongside the pointer, and on equal values prefer the lower index.

The general test is: do equal keys carry information other than the key? If yes, you need stability.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time: O(N log k). Every node is pushed once and popped once — 2N heap operations — and each costs O(log k), because the heap never exceeds k. The log is over k, not N, and that's exactly what the invariant buys.

Space: O(k) for the heap.

Two things to add. Divide and conquer is genuinely competitive: same complexity, slightly fewer comparisons, and about the same speed in practice.

But the heap wins on one variant: if you only need the first M elements, it just stops after M pops, essentially independent of N. The heap is a streaming algorithm; the pairwise merge is a batch one.

And one honest caveat: for small k, like ten lists, the naive fold-left merge is actually faster — its small constant beats the heap overhead.
