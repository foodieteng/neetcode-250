完整實作// THE CODE

演算法與原碼一字未改,只修了記憶體(dummy 改放堆疊)。

p23.cpp C++17 
class Solution {
public:
    ListNode* mergeKLists(vector<ListNode*>& lists) {
        // 「大於」= 最小堆。priority_queue 預設是最大堆,所以要反過來
        auto cmp = [&](auto &l1, auto &l2) {
            return l1->val > l2->val;
        };

        priority_queue<ListNode*, vector<ListNode*>, decltype(cmp)> pq(cmp);

        // 播種:每條的頭。if (p) 不能省 —— lists[i] 可能是 nullptr
        for (auto& p : lists) {
            if (p) pq.push(p);
        }

        ListNode dummy;                // 放堆疊,離開函式自動回收
        ListNode* tail = &dummy;

        while (!pq.empty()) {
            auto node = pq.top(); pq.pop();   // 堆頂 = 全域最小

            tail->next = node;
            tail = tail->next;

            // 彈一個補一個 ⇒ 堆的大小恆 ≤ k
            if (node->next) pq.push(node->next);
        }

        // 這裡不需要 tail->next = nullptr —— 見第 3 節
        return dummy.next;
    }
};

l1->val > l2->val 這個「大於」很容易寫反。 std::priority_queue 的比較子語意是「優先度較低的排在前面」 —— 所以要做最小堆,比較子必須寫大於。 實測寫成小於,20 萬組錯 129342 組(最小反例:[3]、[]、[1] 回傳 [3,1])。

注意「拿掉 if (p)」的崩潰點:不是在 while 迴圈裡,是在 push 的當下。 push 會立刻做 sift-up 比較,而比較子第一件事就是 l1->val。 所以這個 bug 連迴圈都跑不到 —— 一旦有空串列就立刻死。

結尾不必收 —— 但要說得出理由// THE SELF-TERMINATING TAIL

每個被接上的節點,next 都還指著它原本那條串列的下一個。 程式從來沒有把結果的尾巴收成 nullptr,那為什麼不會拖出一條多餘的尾巴?

// 論證 迴圈條件：while (!pq.empty()) 每一輪： 彈出一個 → 若 node->next 存在就補一個 ⇒ 堆會變空,只可能因為「這一輪沒有補」 ⇒ 沒有補的唯一原因是 node->next == nullptr ⇒ 迴圈能結束 ⟺ 最後接上的節點本來就是某條串列的尾巴 // 實測(20 萬組隨機測資) 「迴圈結束時最後彈出的節點 next != nullptr」發生次數：0 結尾補上 tail->next = nullptr 之後的結果差異： 0
對照 21 就更清楚了。 21 的迴圈是 while (a && b) —— 它會在還有東西沒接完時結束, 所以必須補上 t->next = a ? a : b;。 而 23 的迴圈是「東西全部接完才結束」,所以尾巴自然就到位了。 同樣是合併,「迴圈為什麼停」不同,結尾要不要收也就不同。

dummy 一樣是漏的// THE LEAK

原碼寫的是 ListNode *dummy = new ListNode();,而回傳的是 dummy->next —— dummy 本身沒人指得到,也沒人 delete。

分治法:把 21 當零件用// DIVIDE & CONQUER

不用堆,只用 21 題的 merge2 —— 像單淘汰賽一樣一輪一輪配對,每輪串列數減半,所以只有 log k 輪。

p23_divide.cpp O(N log k) · 不用堆 
// 這就是 21 題,一字不改
ListNode* merge2(ListNode* a, ListNode* b) {
    ListNode dummy;
    ListNode* t = &dummy;

    while (a && b) {
        if (a->val <= b->val) { t->next = a; a = a->next; }
        else                    { t->next = b; b = b->next; }
        t = t->next;
    }

    t->next = a ? a : b;   // 21 的迴圈會提早停,所以這行必要
    return dummy.next;
}

ListNode* mergeKLists(vector<ListNode*> ls) {
    if (ls.empty()) return nullptr;

    // 每輪兩兩配對,串列數減半 ⇒ 只有 log k 輪
    while (ls.size() > 1) {
        vector<ListNode*> nx;
        for (size_t i = 0; i < ls.size(); i += 2) {
            nx.push_back(i + 1 < ls.size()
                ? merge2(ls[i], ls[i + 1])
                : ls[i]);       // 落單的直接晉級
        }
        ls.swap(nx);
    }

    return ls[0];   // merge2 對 nullptr 也安全,所以空串列不用特別處理
}

兩個值得注意的地方。 第一,k = 10 時「依序合併」反而最快(2.0 ms vs 堆的 4.4 ms)—— O(N·k) 在 k 很小時的常數比堆操作小得多, 漸進複雜度講的是趨勢,不是小規模下的勝負。

第二,分治法的比較次數在每一個 k 都比堆少(例如 k=1024:109946 vs 128784)—— 因為分治每個節點每層只比一次,而堆每次 pop 要做 sift-down,比較次數約是兩倍。 但實際耗時幾乎相同,因為堆的存取模式對快取更友善。

// ONE-LINE TAKEAWAY
priority_queue 的比較子語意是「優先度低的排前面」,所以最小堆要寫「大於」—— 寫反實測錯 129342/200000。而結尾不必收尾:迴圈能結束就代表最後那個節點的 next 是 nullptr,實測 20 萬組發生 0 次例外。分治法用 21 的 merge2 就能寫完,同樣 O(N log k),耗時幾乎一樣。
