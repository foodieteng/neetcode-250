題目簡介// THE QUESTION

QUESTION

給一個陣列,裡面裝著 k 條各自已經排序的串列頭。 把它們合併成一條排序好的串列並回傳。

0 ≤ k ≤ 10⁴、每條長度 0 ≤ len ≤ 500、總節點數 N ≤ 10⁴、 −10⁴ ≤ Node.val ≤ 10⁴。lists[i] 可能是 nullptr(空串列)。

第 21 題已經解決了 k = 2:兩條有序串列, 每次比較兩個頭,小的接走。這題只是把 2 換成 k —— 但「比較兩個」和「比較 k 個」的成本差很多。

核心觀察只有一句:整體的最小值,一定是某一條串列的頭 —— 因為每條都已經排序,不可能有更小的藏在中間。 所以問題退化成:「在 k 個候選裡反覆取最小」, 而那正是最小堆(priority queue)的工作。
2

三種合法解法,差在「怎麼找最小」// WHY THIS

A 全部值倒進 vector,排序後重建串列 O(N log N) 時間 · O(N) 空間
會過,但它完全沒有用到「每條已經排序」這個條件 —— 把有序的資料丟掉順序再重新排一次。 而且花了 O(N) 額外空間。
× REJECT · 浪費了前提
B 依序兩兩合併:先 1+2,結果再 +3,再 +4… O(N·k)
正確,而且只用 21 題的 merge2 就寫完了。 問題是前面的結果會被反覆掃過:第 i 次合併時,累積的長度已經很長了。 實測 k=1024 時比較次數是分治法的 46.5 倍。
△ 正確 · 但 O(N·k)
C 分治兩兩合併:1+2、3+4 … 再兩兩合併 O(N log k)
同樣只用 merge2,但改成像比賽晉級一樣一輪一輪配對。 每個節點只會被掃過 log k 輪。實測比較次數甚至比堆還少, 而且不需要額外的資料結構。
● 同樣優秀
D 最小堆:k 個頭放進堆,反覆取最小 O(N log k) · O(k) 空間
把「找最小」外包給堆。彈一個、補一個,堆的大小恆 ≤ k。 寫起來最直白,而且「一次處理一個節點」的節奏很適合改成串流版本 (見複習頁 App 3)。
● ADOPT · 本題的寫法
C 和 D 的漸進複雜度一樣,實測耗時也幾乎一樣 (N=200000, k=20000:堆 14.1 ms、分治 14.3 ms)。 差別在「你想付什麼代價」:堆多用 O(k) 空間換來更簡單的控制流,分治不用額外空間但要多寫一層迴圈。 面試時兩個都值得會 —— 而且能說出它們一樣快,比只會其中一個更有說服力。
3

核心策略 · 三步驟// STRATEGY

  1. 播種:把每條的頭推進最小堆 —— if (p) 的守衛不能省,因為 lists[i] 可能是 nullptr。
  2. 彈一個、補一個:取堆頂接到輸出尾端, 再把 node->next(若存在)補進堆 —— 這保證了「堆裡每條串列最多一個節點」,所以堆頂永遠是全域最小。
  3. 堆空了就結束:此時不必寫 tail->next = nullptr —— 理由見第 5 節,那是本題最容易被忽略的一點。
不變量:「堆裡的節點,每條串列最多貢獻一個」。 因為只有在彈出某條的節點時,才會補進那條的下一個。 而由於每條都已排序,那條「還沒被拿走的最小值」就是它現在在堆裡的那個 —— 所以堆頂就是全域最小,不需要再看其他任何節點。

為什麼沒寫 tail->next = nullptr 也沒事// THE HIDDEN LEMMA

這支程式從頭到尾沒有任何一行把結果的尾巴收成 nullptr。 每個接上去的節點,next 都還指著它原本那條串列的下一個。 那結果串列為什麼不會拖著一條不該存在的尾巴?

LEMMA · 最後被彈出的節點,next 必定是 nullptr

迴圈的結束條件是 「堆空了」。而每一輪的動作是:彈出一個,若 node->next 存在就補一個。

所以堆會變空,只可能是因為這一輪沒有補 —— 而「沒有補」的唯一原因就是 node->next == nullptr。

換句話說:迴圈能結束 ⟺ 最後接上的那個節點本來就已經是某條串列的尾巴。 它天生就是收好的。

// 實測(20 萬組隨機測資) 「迴圈結束時最後彈出的節點 next != nullptr」發生次數：0 在結尾補上 tail->next = nullptr 之後的結果差異： 0 // 那一行是真的多餘的,不是「碰巧沒事」
但這個結論是「借來的」——它完全依賴迴圈的終止條件。 如果哪天把迴圈改成別的寫法(例如「彈滿 N 次就停」),這個保證立刻失效。 所以雖然實測證明那一行多餘,寫上去也不算錯 —— 它把一個隱性的保證變成顯性的,代價只有一行。

複雜度// COMPLEXITY

T = O(N log k)　　S = O(k)(堆)

每個節點恰好被 push 一次、pop 一次 —— 實測 6 萬個節點: push 60000 次、pop 60000 次,一次不多一次不少。 而堆裡最多 k 個,所以每次操作是 O(log k)。

一句洞察// INSIGHT

「每條已經排序」這個前提,把「在 N 個裡找最小」壓縮成「在 k 個裡找最小」。 而 k 個候選是不是還能再壓縮?不行 —— 但可以讓「取最小」變便宜,那就是堆。 所有「合併有序資料」的題目都是同一個形狀:先問「候選有幾個」,再問「怎麼在候選裡快速取最小」。
