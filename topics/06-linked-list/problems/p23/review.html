重點回顧// RECAP

面向要記住的那一句
核心觀察全域最小一定是某一條的頭 ⇒ 問題退化成「在 k 個候選裡取最小」
不變量堆裡每條串列最多一個節點 ⇒ 堆頂就是全域最小
堆的大小彈一個補一個 ⇒ 恆 ≤ k(實測 k=200 時最大 size 恰好 200)
比較子方向最小堆要寫 > —— priority_queue 的語意是「優先度低的排前面」
if (p) 守衛不能省 —— push 當下就會比較,nullptr->val 立刻 SEGV
結尾不必收迴圈能結束 ⟺ 最後那個節點的 next 是 nullptr
對照 2121 的迴圈會提早停(while (a && b))⇒ 必須補 t->next = a ? a : b
複雜度O(N log k) 時間、O(k) 空間;每節點恰好 push 一次、pop 一次
三種寫法堆 / 分治都是 O(N log k) 且耗時幾乎相同;依序合併是 O(N·k)
記憶體dummy 用 new ⇒ 每次呼叫漏 1 個(本章第五次)

應用題// APPLICATION

App 1. 分治法和堆的複雜度一樣。那實務上該選哪個?有沒有哪種 k 反而該用最笨的「依序合併」?
App 2. 如果題目改成「只要前 M 小的元素」(例如 M=10,而 N=20 萬),兩種寫法的差距會變成多少?
App 3. 值相同時,原碼輸出的節點來自哪一條是不確定的。這算 bug 嗎?如果題目要求穩定(相同值時,原本在較前面 lists[i] 的先輸出),要怎麼改?
// ANSWERS
A1. 不變量:「堆裡的節點,每條串列最多貢獻一個,而且那個就是該條還沒被拿走的最小值」。

怎麼維持:播種時每條放進去一個;之後只有在彈出某條的節點時,才補進那條的下一個。所以任何時刻,每條在堆裡最多一個。

為什麼那個就是該條的最小:因為每條本來就已經排序 —— 已經被拿走的都比它小,還沒拿的都比它大。

兩者合起來:堆裡的 k 個節點,涵蓋了「每一條的當前最小」。而全域最小必定是其中之一(不可能藏在某條的中間)。所以堆頂就是全域最小,不需要看其他任何節點。

這就是為什麼只要 O(k) 空間就夠 —— 不需要把 N 個節點全放進堆裡。
A2. 因為 std::priority_queue 的比較子語意是「cmp(a,b) 為真代表 a 的優先度比 b 低」——低的沉下去,高的浮上來。

所以 l1->val > l2->val 的意思是「值大的優先度低」⇒ 值小的浮到頂 ⇒ 最小堆。

這個雙重否定是它最容易寫反的地方。一個記法:比較子和你要的效果永遠是相反的 —— 要最小堆就寫大於,要最大堆(預設)就寫小於。

實測寫成 <:20 萬組隨機測資錯 129342 組,最小反例:
lists = [3] [] [1] → [3, 1] // 正解 [1, 3]

注意它「只錯 65%」而不是全錯 —— 因為只有一條非空串列時,順序是那條自己決定的,堆的方向根本不影響。所以拿單一串列測是測不出這個 bug 的。
A3. 不能省 —— 而且崩的地方比想像中早:在 push 那一行,不是在 while 迴圈裡。

題目明說 lists[i] 可以是 nullptr(空串列)。而 pq.push(p) 會立刻做 sift-up 把新元素往上冒,而 sift-up 的第一件事就是呼叫比較子 —— 比較子的第一件事是 l1->val。

實測(lists = [ [1], nullptr ],ASan + UBSan):
runtime error: member access within null pointer of type 'ListNode' runtime error: load of null pointer of type 'int' AddressSanitizer: SEGV on unknown address 0x000000000000

位址是 0x0 而不是某個偏移,因為 val 剛好是 ListNode 的第一個成員。

順帶一提迴圈裡的 if (node->next) 也是同一件事 —— 拿掉它就會把 nullptr 補進堆裡,下一次比較一樣爆。 這支程式有兩個 null 守衛,而且它們防的是同一個東西:不要讓 nullptr 進到堆裡。
A4. 因為兩題的迴圈「為什麼停」不一樣。

23 的迴圈:while (!pq.empty())。每一輪彈一個,若 node->next 存在就補一個。
⇒ 堆會變空,只可能因為這一輪沒有補;
⇒ 沒有補的唯一原因是 node->next == nullptr;
⇒ 迴圈能結束 ⟺ 最後接上的節點本來就是某條串列的尾巴。
它天生就是收好的。

21 的迴圈:while (a && b)。它在其中一條先用完時就停 —— 而另一條還有東西沒接。所以必須補上 t->next = a ? a : b;。

實測:20 萬組隨機測資中,「迴圈結束時最後彈出的節點 next != nullptr」發生 0 次;而在結尾補上 tail->next = nullptr,結果完全沒有任何差別。

但這個保證是「借來的」 —— 它完全依賴迴圈的終止條件。如果把迴圈改成「彈滿 N 次就停」,保證立刻失效。 所以雖然實測證明那一行多餘,寫上去也不算錯:它把一個隱性的保證變成顯性的,代價只有一行。
A5. 堆裡最多 k 個;push 與 pop 各恰好 N 次。

堆的大小:播種放進 k 個(扣掉空串列),之後每彈一個最多補一個 —— 所以永遠不會超過 k。而它不是 N:這就是空間只要 O(k) 的原因。

操作次數:每個節點恰好進堆一次(播種或被前一個帶進來)、出堆一次。

實測(k = 200,每條 300 個,共 60000 個節點):
堆的最大 size = 200 （= k,一個不多) push 次數 = 60000 （= N) pop 次數 = 60000 （= N)

所以總成本是 2N 次堆操作 × 每次 O(log k) = O(N log k)。 注意 log 裡面是 k 不是 N —— 這正是「不把全部節點塞進堆」換來的好處。
App 1. 複雜度一樣,實測耗時也幾乎一樣 —— 但 k 很小時,最笨的那個反而最快。

實測(N = 200000 個節點):
k 每條長度 堆 依序合併 分治合併 ───────────────────────────────────────────────────── 10 20000 4.4 ms 2.0 ms 2.2 ms ← 依序最快！ 1000 200 7.8 ms 244.8 ms 6.8 ms 20000 10 14.1 ms 13385.3 ms 14.3 ms

k = 10 時「依序合併」比堆快一倍 —— 因為 O(N·k) 在 k=10 時的常數比堆操作小得多,而堆每次 push/pop 都有 sift 的開銷。

k = 20000 時依序要 13.4 秒,慢了 950 倍 —— O(N·k) 的代價完全顯現。

而堆與分治從頭到尾難分軒輊。有趣的是分治的比較次數在每個 k 都比堆少(k=1024:109946 vs 128784),因為分治每個節點每層只比一次,而堆的 pop 要做 sift-down,比較次數約兩倍 —— 但實際耗時幾乎相同,因為堆的存取模式對快取比較友善。

結論:面試寫哪個都行,但要能說出「它們一樣快」以及「k 小的時候笨方法反而贏」 —— 漸進複雜度講的是趨勢,不是小規模下的勝負。
App 2. 差距會變得非常懸殊 —— 因為堆可以「彈滿 M 次就收工」,而分治必須先把全部合併完。

實測(N = 200000,k = 100,每條 2000 個):
M 堆（彈 M 次就停) 分治（必須全部合併完) ────────────────────────────────────────────────────── 10 0.00 ms 7.88 ms 1000 0.05 ms 5.39 ms 200000 6.58 ms 5.19 ms ← 要全部時分治略勝

堆的成本是 O(k + M log k) —— 和 N 幾乎無關。要前 10 個就真的只做 10 次 pop。
分治的成本是 O(N log k) —— 不管你只要幾個,都得先把 20 萬個節點全部串好。

這是堆這個寫法真正的長處,而它在原題裡看不出來:它是「串流式」的 —— 一次產生一個,而且隨時可以停。

順帶一提,這正好也是 378 有序矩陣的第 k 小 ↗ 的解法 —— 把矩陣的每一列看成一條有序串列,然後彈 k 次就停。 同一支引擎,換個停止條件。
App 3. 不是 bug —— 因為題目只在乎「值的序列」,而值的序列永遠是對的。

值相同時,priority_queue 不保證哪個先出來(它不是穩定的資料結構)。所以節點的來源順序是實作決定的。

實測(刻意把值域壓成 {0, 1} 製造大量平手,20000 組):
「來源順序」與「穩定順序」不同的：15751 / 20000（78.8%) 「值的序列」不同的： 0 反例: lists = [1] [1,2] [1,2,2,3] [0,1] [1,2,2,3] 原碼來源 L3 L0 L1 L4 L3 L2 L1 L4 L2 L4 L2 L4 L2 穩定版 L3 L0 L1 L2 L3 L4 L1 L2 L2 L4 L4 L2 L4

七成八的情形下來源順序不一樣,但值一模一樣 —— 所以原碼在這題完全正確。

如果題目要求穩定,改法是在比較子加上第二個鍵:
struct Item { ListNode* n; int from; }; // 記住來自第幾條 auto cmp = [](const Item& a, const Item& b) { // 值不同就比值;值相同就比「來自哪一條」,索引小的優先 return a.n->val != b.n->val ? a.n->val > b.n->val : a.from > b.from; };

代價是每個堆元素多帶一個 int。實測這個版本與「穩定」的定義完全吻合。

值得記住的一般教訓:「堆不穩定」在合併題裡幾乎總是無害(因為只在乎值),但在「合併記錄」的場景就會變成真的 bug —— 例如合併多個時間序列的日誌,同一毫秒的事件順序被打亂就可能改變語意。 判準是:相同鍵的元素,除了鍵以外還攜帶其他資訊嗎?
