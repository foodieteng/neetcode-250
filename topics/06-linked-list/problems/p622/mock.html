M — match
C
CANDIDATE

Hmm, let me think about this for a second.

A naive approach would use a plain array and shift everything down after each dequeue — that's O(n) per operation.

This problem reminds me of the ring buffer pattern: keep a fixed array of size k and let the indices wrap with a single % capacity. The array stays linear; "circular" lives entirely in the arithmetic. So the real design question is: which variables do I keep as state?

I
INTERVIEWER

What are the options?

C
CANDIDATE

The obvious one is front and rear, and it's ambiguous.

// k = 3, state = (front, rear)
empty              : front = 0, rear = 0  // equal
after 3 enqueues : front = 0, rear = 0  // equal again, but FULL
// same two numbers, opposite states

With k = 3, an empty queue has both at 0 — and after three enqueues, they're both at 0 again, but now it's full. Same two numbers, opposite states.

Two standard fixes: waste a slot, or carry a boolean full flag. But both are repairs. The ambiguity comes from rear being a position, and positions wrap. What if I store size instead?

Counts don't wrap. Empty is size == 0, full is size == capacity — opposite ends of a number line, never both true. And rear is still recoverable: (front + size - 1) % capacity.

I
INTERVIEWER

Are the other two wrong, then?

C
CANDIDATE

No — all three are correct. It's a design preference, not a correctness argument.

The costs differ, though. Wasting a slot means array length and capacity are different numbers, so every modulo has to use k+1, and using k by accident is an easy mistake. The flag costs no space but must be updated in two places — and a state you must remember to synchronize is a state you can forget to synchronize.

(front, size) cost nothing and need no upkeep. That's why I'd pick them.

P — plan
C
CANDIDATE

Here's the plan.

first element  q[front]
next free slot q[(front + size) % capacity]     // skip the size occupied slots
last element   q[(front + size - 1) % capacity] // one back from the free slot

One: the first element is at front.
Two: the next free slot is (front + size) % capacity — skip the occupied slots.
Three: the last element is one back from that, (front + size - 1) % capacity.

One thing worth flagging is that -1 — without it, Rear reads the next free slot, which holds a 0 or a stale value, both plausible-looking.

And deQueue doesn't touch the array at all: it just advances front and decrements size. Does this approach sound good, or would you rather I think of another way?

I
INTERVIEWER

Sounds good. But you leave the old data sitting there? Doesn't that cause problems?

C
CANDIDATE

No, because membership is defined purely by the indices. Slot j is in the queue exactly when (j - front + k) % k < size — the stored value never appears in that test. A stale value just gets overwritten when the indices wrap around.

Clearing it would be worse: a pointless extra write, and writing 0 to mean "empty" makes a real 0 ambiguous.

That's also why every operation is O(1) in the worst case — no element is ever moved.

I — implement
C
CANDIDATE

Alright, let me code this up. The state is front, size, and capacity, over a vector of exactly k slots.

class MyCircularQueue {
private:
    // state is just two things: where the head is, how many. rear is computed
    int size, front, capacity;
    vector<int> q;

public:
    MyCircularQueue(int k) {
        q.resize(k, 0);          // exactly k slots, none wasted
        size = 0;
        front = 0;
        capacity = k;
    }

    bool enQueue(int value) {
        if (isFull()) return false;
        // next free slot = count size slots forward from the head
        q[(front + size) % capacity] = value;
        size++;
        return true;
    }

    bool deQueue() {
        if (isEmpty()) return false;
        // move the boundary only; the old value stays until a wrap overwrites it
        front = (front + 1) % capacity;
        size--;
        return true;
    }

    int Front() {
        if (isEmpty()) return -1;
        return q[front];
    }

    int Rear() {
        if (isEmpty()) return -1;   // this guard is load-bearing
        // one back from the free slot -- that -1 can't be dropped
        return q[(front + size - 1) % capacity];
    }

    // the two checks sit at opposite ends of a number line, never both true
    bool isEmpty() { return size == 0; }
    bool isFull()  { return size == capacity; }
};

enQueue writes at (front + size) % capacity, then bumps size. deQueue moves front forward by one, mod capacity, and decrements size. Front and Rear return -1 when empty.

Two things worth pointing at. enQueue and deQueue call the public predicates, isFull and isEmpty, rather than re-implementing the check — so the guard and the reported state can never disagree. And every modulo sits behind a guard, which will matter in a second.

The row that matters is enQueue(60): front is 2 and size is 3, so the slot is (2+3) % 5 = 0. It wraps, and overwrites the stale 10 from the first dequeue, without anyone ever having cleared it. 70 lands in slot 1, and the queue is full. That matches.

I
INTERVIEWER

You called the Rear guard "load-bearing." Why?

C
CANDIDATE

Because without it, an empty queue with front == 0 computes (0 + 0 - 1) % capacity. C++ truncates toward zero — the sign follows the dividend — so (-1) % 5 is -1, not 4. That's q[-1], out of bounds.

What makes it nasty is that it depends on k. At k = 1, (-1) % 1 is 0 — in bounds. It doesn't crash or trip a sanitizer; it quietly returns a stale value from slot 0. So the same bug is invisible at k = 1, and an out-of-bounds read at k ≥ 2.

Even with a safe modulo, I'd keep the guard — an empty queue owes the caller -1.

I
INTERVIEWER

How would you test this?

C
CANDIDATE

The input space is small enough to enumerate exhaustively. Six operations, and the state is two small integers. For k up to 4, I can generate every operation sequence up to length 7 and compare against a std::deque reference.

Two things I'd insist on. Compare the full queue contents after every single call, not just return values — a write-to-the-wrong-slot bug only surfaces several calls later. And assert every index is in bounds, because a bad index that lands in range, like the k = 1 case, is silent otherwise.

Then top it up with large k, and a long run that wraps front many times.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time: O(1) worst case for every operation, not amortized — there's no hash table, so no rehashing. Space: exactly k ints, with no pointers and nothing to leak. Overflow isn't reachable: front + size peaks at 1999.

Oh, one more thing — at k = 0, this code happens to be safe. isEmpty and isFull are both true, so every operation returns early and no modulo by zero is reached. Still, if the constraint were relaxed, I'd add an explicit capacity == 0 guard, because relying on that is correct but fragile.
