應用題// APPLICATION

App 1. 教科書的 (front, rear) 寫法有兩種補救方式:浪費一格,或加一個 full 旗標。它們都對嗎?和本題的寫法比,差在哪?
App 2. 題目保證 1 ≤ k。如果 k = 0 呢?(146 的 capacity = 0 會 SEGV,這題呢?)
App 3. 常聽說「% 是除法,很慢,應該換成條件減法」。在這題實際上快多少?
// ANSWERS
A1. 資訊量確實一樣(彼此可互推),但「歧義落在哪裡」完全不同。

rear 和 size 可以互相算出來:rear = (front + size) % k。所以它們攜帶的資訊是等價的。但等價的資訊,擺在不同的變數裡,產生的特例不一樣。

用 (front, rear):「空」是 front == rear,而「滿」也是 front == rear(繞了一整圈回到原點)。同一組數字,兩種完全相反的狀態 —— 所以必須額外做點什麼來區分。

用 (front, size):「空」是 size == 0,「滿」是 size == capacity。兩個判斷落在數線的兩端,不可能同時成立(除非 capacity == 0,而那正好是 App 2)。

關鍵在於:歧義不是被「修掉」的,是壓根沒發生。

實測那個「不補救就直接用 (front, rear)」的版本:320 萬次呼叫錯 546467 次,最小反例是 k=1 的第一個操作 —— enQueue(1) 直接回 false,因為 (0+1) % 1 == 0 == front,它認為滿了。那個佇列從出生到死亡連一個元素都裝不進去。
A2. 因為 front + size 指的是「下一個要寫的空位」,不是最後一個元素。

佇列裡有 size 個元素,佔據 front、front+1、…、front+size−1(都取模)。
· 最後一個在 front + size − 1;
· 下一個空位在 front + size —— 這正是 enQueue 用的位置。

所以 enQueue 和 Rear 的算式只差那個 −1,而它們指的是完全不同的格子。

實測拿掉 −1:3202668 次呼叫錯 134334 次,而索引越界 0 次 —— 它一直讀的是界內的格子,只是讀錯格子。最小反例只要兩個操作:
k = 2 enQueue(1) → true Rear() → 0 // 正解 1,它讀到的是還沒寫過的 q[1]

這種 bug 特別討厭,因為它讀到的是「合法初始化過的 0」,看起來完全像一個正常的值。
A3. 不能省 —— 而且它的表現會隨 k 而變,這才是最陰險的地方。

size == 0 且 front == 0 時,算式變成 (0 + 0 − 1) % capacity,也就是 (−1) % k。

C++ 的 % 是「往零截斷」,不是數學上的模 —— 結果的正負號跟著被除數:
(-1) % 1 = 0 ← 剛好落在界內 (-1) % 3 = -1 (-1) % 5 = -1 ← q[-1],真的越界了

實測拿掉守衛(3202668 次呼叫):回傳錯 264364 次,索引越界 176841 次。

注意「回傳錯」比「越界」多了 87523 次 —— 差額就是 k = 1 的情形。 最小反例是 k=1 時直接 Rear() 回傳 0(正解 -1):
(−1) % 1 == 0,所以它沒有越界,只是安安靜靜地讀了 q[0] 的殘留值。

換句話說:同一個 bug,k ≥ 2 時 sanitizer 會抓到,k = 1 時完全隱形。 只有跟參考解逐步比對才能兩種都抓到 —— 這也是為什麼我不只跑 ASan,還要有一個暴力參考解。

如果真的想寫得更防禦一點,可以用 (front + size − 1 + capacity) % capacity —— 先加一個 capacity 把被除數推成非負,這樣即使守衛失效也不會越界。但守衛本身仍然要留,因為空佇列該回的是 -1,不是任何一格的值。
A4. 因為「哪些格子算數」完全由 front 和 size 決定,陣列裡的值從不參與判斷。

形式化地說:索引 j 屬於佇列 ⟺ (j − front + k) % k < size。
這個式子裡沒有 q[j] —— 所以把 front 推一格、size 減一之後,那格自動就不算數了。

它會在下次繞回來時被自然覆蓋。動畫第 7 步 enQueue(60) 寫進 q[0],蓋掉的正是第 3 步 deQueue 留下的那個 10。

反過來說,如果真的去清空(例如填 0),有兩個壞處:
· 多做一次沒有必要的寫入;
· 而 0 是題目允許的合法 value(0 ≤ value ≤ 1000)—— 「這格是 0」從此無法區分「空的」還是「真的存了 0」。

這就是環狀佇列每個操作都是嚴格 O(1) 的原因:出隊是「移動邊界」而不是「刪除資料」,入隊是「覆蓋」而不是「插入」——全程沒有任何元素被搬動過。
A5. 它會讓佇列多裝一個,然後把最舊的元素默默蓋掉。

size > capacity 在 size == capacity 時是 false —— 已經滿了卻說沒滿,於是 enQueue 繼續寫。而它要寫的位置是 (front + capacity) % capacity == front —— 正好就是隊頭那一格。

實測:3202668 次呼叫回傳錯 167270 次,佇列內容錯 243076 次。
最小反例只要兩個操作:
k = 1 enQueue(1) → true enQueue(1) → true // 正解 false

注意「內容錯」比「回傳錯」多了 75806 次 —— 因為它蓋掉隊頭之後,錯誤的資料要等後面的 Front() 才會被看見,而中間那些操作的回傳值全都是「對的」。

這是本題的通用教訓:唯讀操作(Front/Rear)寫錯只會回報錯,寫入操作寫錯會污染狀態 —— 後者的破壞範圍大得多,但在只比對回傳值的測試裡反而顯得比較輕微。
App 1. 兩種補救都是正確的 —— 這不是對錯問題,是「哪一種比較不容易寫錯」。

三種表示法各自窮舉 k = 1..4 × 長度 1..6 的全部序列:
A (front, size) ← 本題 回傳錯 0 / 3202668 k=1000 時陣列佔 4000 bytes B (front, rear) + 浪費一格 回傳錯 0 / 3202668 k=1000 時陣列佔 4004 bytes C (front, rear) + full 旗標 回傳錯 0 / 3202668 k=1000 時陣列佔 4000 bytes

三個都對。差別在成本:

B 浪費一格 —— 必須配置 k + 1,而且容量與陣列長度不再相等,所有算式都要用 k+1 取模。最容易寫錯的地方就是不小心用了 k。

C 加旗標 —— 不浪費空間,但那個 bool full 要在 enQueue 和 deQueue 兩處各自維護。多一個必須同步的狀態,就多一處會忘記更新 —— 和 146 的「兩張表要同步」是同一類風險。

A(本題) —— 不浪費空間、不需要旗標、不需要任何補救。它的優勢不是「更快」或「更省」,而是沒有東西需要記得去維護。

面試時值得把這段講出來:「教科書的做法是浪費一格,但如果改存 size 而不是 rear,歧義根本不會發生」 —— 這比直接寫出答案更能證明你知道為什麼要浪費那一格。
App 2. 完全安全 —— 而這一點和 146 形成很好的對比。

實測 MyCircularQueue(0):
isEmpty() → true (size == 0) isFull() → true (size == 0 == capacity) enQueue(1) → false isFull 為真,在碰到 % capacity 之前就 return 了 deQueue() → false isEmpty 為真,同樣提早 return Front() → -1 Rear() → -1 // 沒有崩潰,沒有除以零,沒有越界

「空」和「滿」同時為真,聽起來很怪 —— 但對一個容量為 0 的佇列來說,那正是正確的描述。

安全的真正原因是:每一個 % capacity 都寫在守衛之後。 enQueue 先 isFull、deQueue 先 isEmpty、Front/Rear 先 isEmpty —— 而 capacity == 0 時這些守衛全部成立,所以除法一次都執行不到。

對照 146:那題 capacity = 0 時,cache.size() == sz 變成 0 == 0 為真,於是進入淘汰分支,對空串列取 left->next(就是 right 哨兵本身),然後對 nullptr 寫入 → SEGV。

兩題的差別不是運氣:622 的守衛是「這件事能不能做」,而 146 的判斷是「要不要先騰位置」 —— 前者在容量為 0 時退化成「什麼都不能做」(安全),後者退化成「先騰一個不存在的位置」(災難)。
App 3. 完全沒有變快 —— 這個「優化」在這裡是純粹的迷信。

把 % capacity 換成條件減法(if (i >= cap) i -= cap;),理論上避開了整數除法指令:
k = 8,2000 萬次操作: % 版 3.85 ns/op 條件減法 3.83 ns/op → 1.01 倍 k = 1000,2000 萬次操作: % 版 3.71 ns/op 條件減法 3.72 ns/op → 0.99 倍

差距在量測誤差之內。(條件減法版也窮舉驗證過:3202668 次呼叫,不一致 0 —— 它是對的,只是沒比較快。)

為什麼會這樣?因為瓶頸根本不在除法。每個操作只有幾個算術指令加一次陣列存取,而編譯器對 % 有很多手段(常數傳播、乘法倒數、以及分支預測極好的判斷)。把 3.8 ns 裡佔不到一成的東西優化掉,總時間看不出差別。

更值得注意的是:條件減法版沒有比較好讀 —— Rear() 那行變成一個三元運算式,而 % 版本一眼就看得懂在做什麼。

結論:這是一個「代價明確、收益為零」的交易。 而唯一能知道這件事的方法就是量它 —— 「除法很慢」這句話本身是對的,錯的是「所以在這裡值得避開」這個推論。
