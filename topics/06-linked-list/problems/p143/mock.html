Hmm, let me think about this for a second.

A naive approach would be: each time I need the current last node, walk from the head to find it, detach it, and splice it in. That's O(n) per node for n/2 nodes, so O(n2) — around 2.5 × 109 operations at 50,000. Too slow.

A second option is to copy the node pointers into a vector and relink from both ends — O(n) time and correct, since it stores pointers, not values, but it costs O(n) extra space.

This problem reminds me of the reverse-to-walk-backward pattern for singly linked lists. If I reverse the back half, walking backward from the tail becomes walking forward through the reversed half. Then it's three pieces I already know: find the middle with fast/slow pointers, reverse in place, and interleave. O(n) time, O(1) space.

Here's the plan.

// phase 1 — find the middle
slow = fast = head
while (fast && fast->next) { slow += 1; fast += 2; }

// phase 2 — reverse the back half, then CUT
l2 = reverse(slow->next);
slow->next = nullptr;  ← order matters, and this line does two jobs

// phase 3 — interleave
take one from l1, then one from l2, repeat

// invariant that falls out of phase 1
|l1| = floor(n/2) + 1  → l1 is always longer than l2

One: fast/slow pointers from the head, so slow stops where the first half ends.
Two: reverse the back half starting at slow->next, then cut.
Three: interleave, one node from each half, taking turns.

One thing worth flagging is the order in phase 2: reverse first, then cut. slow->next is my only way into the back half, so if I null it out first, the reverse gets a null pointer and the whole back half is lost.

And that cut line does two jobs. First, the front half's tail still points at what is now the tail of the reversed half — without the cut, phase 3 builds a cycle. Second, it also ends the final result; I'll explain why when I get there.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. Three phases plus an iterative reverse helper.

class Solution {
public:
    void reorderList(ListNode* head) {
        // ── Phase 1: fast/slow pointers find the middle (LC 141 skeleton) ──
        ListNode *slow = head, *fast = head;
        while (fast && fast->next) {
            slow = slow->next;
            fast = fast->next->next;
        }

        // ── Phase 2: reverse the back half, then cut (LC 206 skeleton) ──
        ListNode* l2 = reverseList(slow->next);
        slow->next = nullptr;   // without this line → phase 3 builds a cycle

        // ── Phase 3: interleave (LC 21 skeleton, but no comparisons) ──
        // the result always starts at head, so no dummy is needed
        ListNode* l1 = head->next;
        ListNode* tail = head;

        while (l1 || l2) {
            if (l2) {
                tail->next = l2;
                l2 = l2->next;
                tail = tail->next;
            }

            if (l1) {
                tail->next = l1;
                l1 = l1->next;
                tail = tail->next;
            }
        }
    }

private:
    // LC 206 iterative version, unchanged. Not the recursive one: n goes up to 5×10^4
    ListNode* reverseList(ListNode* head) {
        ListNode *prev = nullptr, *curr = head, *next = nullptr;

        while (curr) {
            next = curr->next;
            curr->next = prev;
            prev = curr;
            curr = next;
        }

        return prev;
    }
};

head is already L0, so I start tail at head and l1 at head->next, and each round attaches from the reversed half first, then from the front. That's also why there's no dummy node — I already know the first node, and the function returns void.

One thing worth flagging — I never write tail->next = nullptr at the end, and that's deliberate. Phase 1 leaves the front half longer, by one for odd n and two for even. So l2 runs out first, and the last node I attach is slow, whose next I nulled in phase 2. That's the cut's second job.

Let's dry-run the code with [1,2,3,4,5], expecting [1,5,2,4,3].

phasestepstate
1round 1slow → node 2, fast → node 3
1round 2slow → node 3, fast → node 5; fast->next null, stop
2reverseback half 4→5 becomes 5→4
2cutl1 = 1→2→3 (len 3), l2 = 5→4 (len 2)
3round 1attach 1, attach 5 → 1→5
3round 2attach 2, attach 4 → 1→5→2→4
3round 3attach 3; l2 empty → 1→5→2→4→3

The rows that matter are phase 2. Before the reverse, reaching node 5 meant walking the list; after it, node 5 is just l2's head — one pointer read.

In the last round I attach node 3 and stop. Node 3 is slow, so its next was already null — the result ends without a termination line. That matches.

Corner cases:

• [1] → [1]: a single node, where the back half is empty.
• [1,2] → [1,2]: the back half is empty too — the easiest case to forget.
• [1,2,3] → [1,3,2]: odd, halves differ by one.
• [1,2,3,4] → [1,4,2,3]: even, halves differ by two.

Since only the length shapes the result, every length from 1 to 2,000 was checked, with a step cap so a cycle can't hang the test.

Let me think about complexity here.

Time is O(n) — about n/2 rounds to find the middle, n/2 steps to reverse, and n steps to interleave, so roughly 2n pointer operations. Space is O(1) — a handful of pointers, no allocation. Even at 50,000 nodes it's linear, and the iterative reverse keeps the stack flat.

Oh, one more thing — if I reuse this to check whether a list is a palindrome, the phases carry over but the midpoint rule doesn't. This version leaves the front half longer, which is what lets me skip the termination line. A palindrome check needs the halves balanced: with this midpoint, [1,0] leaves an empty back half, the comparison never runs, and it wrongly says true.

The fix is the loop condition while (fast->next && fast->next->next). Reuse the structure, re-derive the boundaries.
