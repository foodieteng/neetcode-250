範例 Trace// [1,2,3,4,5] → [1,5,2,4,3]

// 階段 1 · 快慢指標找中點 原串列: 1 -> 2 -> 3 -> 4 -> 5 -> null 初始 slow = 第 1 個 fast = 第 1 個 第 1 輪 slow → 第 2 個 fast → 第 3 個 第 2 輪 slow → 第 3 個 fast → 第 5 個 fast->next 是 null → 跳出 slow 停在第 3 個
// 階段 2 · 翻轉後半 + 切斷 後半(slow->next)= 4 -> 5 -> null reverseList 之後 l2 = 5 -> 4 -> null slow->next = nullptr ⇒ l1 = 1 -> 2 -> 3 -> null (長度 3) ⇒ l2 = 5 -> 4 -> null (長度 2) // |l1| = 3 > |l2| = 2 —— 這是「不必收尾」的關鍵
// 階段 3 · 交錯合併 第 1 圈 接 l1 的 1 → 1 接 l2 的 5 → 1 -> 5 第 2 圈 接 l1 的 2 → 1 -> 5 -> 2 接 l2 的 4 → 1 -> 5 -> 2 -> 4 第 3 圈 接 l1 的 3 → 1 -> 5 -> 2 -> 4 -> 3 l2 已空,跳過 兩條都空 → 跳出
// OUTPUT 1 -> 5 -> 2 -> 4 -> 3 -> null 最後接上的是 l1 的尾巴 3 而 3 就是 slow,它的 next 早在階段 2 被設成 nullptr ⇒ 結果自動收尾,merge 迴圈裡不必寫 tail->next = nullptr // [1,5,2,4,3]

應用題// APPLICATION

App 1. 用階段 1 + 2 來做回文判斷(LeetCode 234)。可以直接把這題的中點程式碼搬過去嗎?
App 2. 如果允許 O(n) 額外空間,有沒有更短的寫法?什麼時候該選它?
App 3. 階段 2 如果用 206 的遞迴版翻轉,在 n = 5×10⁴ 時會不會出事?
// ANSWERS
A1. 因為單向串列只能往後走,而目標順序需要往回走。

目標是 L₀ → Lₙ → L₁ → Lₙ₋₁ → …,也就是交替從頭和從尾取。但「從尾取」在單向串列裡沒有捷徑 —— 你拿不到「尾巴的前一個」。

不翻轉的話:每次要取當前的尾巴,都得從頭走一遍找到倒數第二個、把它的 next 設成 nullptr。一次 O(n),要做 n/2 次 ⇒ O(n²)。n = 5×10⁴ 時是 2.5×10⁹ 級,必定 TLE。

翻轉之後,「往回走」變成「往前走」——後續每一步都是 O(1)。翻轉本身只花一次 O(n)。

這是鏈結串列題的通用交易:用一次 O(n) 的翻轉,把每一步的 O(n) 換成 O(1)。同樣的招式在 234、445 都會再出現。
A2. 症狀是「程式吊死」,不是回傳錯的答案。

翻轉後半之後,前半的尾巴(slow)還指著後半的舊頭——而那個舊頭現在是 l2 的尾巴。合併時把 l2 接進來,前後就接成了一個回路。

實測:拿掉這一行,n = 1..400 有 398 種長度成環(只有 n=1、n=2 逃過,因為後半是空的)。最小反例 n = 3,走出 1,3,2,3,2,3,2… 永遠走不完。

而且這裡有個測試上的實務陷阱:如果你的 dump / 比對函式沒有步數上限,第一個成環的變體就會把整個測試程式卡死,連「哪裡錯了」都看不到。本頁所有對拍的走訪都放了 guard > 3n + 10 的計數器。

這已經是 06 章第三次遇到「成環而非答錯」了(206 七種錯法有三種成環)。鏈結串列題的預設假設應該是:錯誤會以吊死的形式出現。
A3. 因為 |l1| > |l2| 恆成立,所以最後接上的一定是 l1 的尾巴 —— 而它早就被切斷了。

步驟一:證明 |l1| > |l2|。這個切法(兩者都從 head 起跑、while (fast && fast->next))得到 |l1| = ⌊n/2⌋ + 1,所以 |l1| − |l2| 是 1(n 奇數)或 2(n 偶數)。實測 n = 1..8:(1,0) (2,0) (2,1) (3,1) (3,2) (4,2) (4,3) (5,3)。

步驟二:合併時每圈先接 l1 一個、再接 l2 一個。既然 l1 比較長,l2 必定先空,之後的圈數只接 l1 —— 所以最後接上的必定是 l1 的尾巴。

步驟三:l1 的尾巴就是 slow,而 slow->next 在階段 2 就被設成 nullptr 了。

所以那行「切斷」做了兩件事:防止成環,以及順便把結果收尾。實測 n = 1..2000 全部長度,未終結 / 成環 0 次。

但這是「靠不變量省下來的一行」,不是「本來就不需要」。如果換一種找中點的方式讓 |l1| == |l2|(見 App 1),這個論證就垮了 —— 那時最後接的是 l2 的尾,得另外確認它有沒有被終結。
A4. 後半整段會失聯,結果只剩前半。

slow->next 是通往後半的唯一入口。如果先寫 slow->next = nullptr;,那麼下一行 reverseList(slow->next) 讀到的是 nullptr,回傳 nullptr —— l2 是空的,後半那些節點再也沒有任何指標指得到。

結果會是「前半原樣輸出」,而不是重排。

這和 206 的「先存 next 再改指標」是完全同一種依賴關係:覆蓋任何一根 next 之前,先確認沒有東西會因此失聯。206 用一個暫存變數買後路,這裡是靠「先用完再切」的順序。

一個檢查習慣:每寫一行 x->next = …,回頭問一句「原本那個 x->next 指的東西,還有別人指得到嗎?」
A5. 不是同一回事 —— 前兩題需要,這題不需要。

dummy 的用途是消掉「結果的頭是誰還沒決定」這個特例。所以判準是:動手接線之前,你知不知道第一個節點是誰?

題目結果的頭事先知道嗎dummy
21 合併不知道(看哪條的頭比較小)需要
2 相加不知道(要算完第一位才有那個節點)需要
143 本題知道 —— 就是 head不需要
這題的函式回傳 void、就地修改,而結果的第一個節點必定是 L₀ = head。所以直接 tail = head; l1 = head->next; 就能開始接。實測無 dummy 版跑 n = 1..400 全對。

而且原碼那個 dummy 是 new 出來的、沒有 delete —— 實測每次呼叫洩漏 1 個節點,呼叫 10 萬次漏 1562 KB。三題同一個洩漏,但只有這題的最佳修法是「整個拿掉」而不是「放堆疊」——因為它在這裡沒有解決任何問題。
App 1. 不能直接搬 —— 而且我原本以為可以,是實測打臉的。

回文判斷的做法確實是「找中點 → 翻轉後半 → 兩段對走比值」,骨架看起來完全一樣。但中點的定義不同:

143 需要前半比較長(那是 A3 那個不變量的來源),234 需要兩半盡量等長(否則沒得比)。同一行 while (fast && fast->next) 在偶數時讓兩半差 2:

 n   143 切法    234 該用的切法
 2   (2, 0)      (1, 1)
 4   (3, 1)      (2, 2)
 6   (4, 2)      (3, 3)

實測(30 萬組隨機,一半刻意造成回文):
照搬 while (fast && fast->next) → 判斷錯 18556/300000,最小反例 [1,0](|l2| = 0,比較迴圈一次都沒跑就回 true)。
改成 while (fast->next && fast->next->next) → 錯 0/300000。

另外 234 還多一個責任:比完要把後半翻回去還原,否則呼叫端拿到的是被改壞的串列。實測加上 slow->next = reverseList(second); 之後,30 萬組沒還原的 0 組。

教訓:「這兩題骨架一樣」通常是對的,但「所以可以整段複製」通常不是。三個階段可以復用,但每個階段的邊界要按新題目重新確認一次。
App 2. 有,而且短很多:把節點指標倒進 vector,再用雙指標從兩頭往中間接。

vector<ListNode*> a;
for (ListNode* p = head; p; p = p->next) a.push_back(p);

int i = 0, j = a.size() - 1;
while (i < j) {
  a[i]->next = a[j]; ++i;
  if (i == j) break;
  a[j]->next = a[i]; --j;
}
a[i]->next = nullptr;  // 這裡就必須自己收尾了

注意存的是「指標」不是「值」,所以沒有違反題目「不准改值」的要求 —— 我們仍然只是在重新接線。

實測:n = 1..500 順序錯 0;與三階段版逐項對拍不一致 0。

取捨:時間同樣 O(n),但空間從 O(1) 變成 O(n)。什麼時候選它:面試時如果卡在三階段的邊界、或時間不夠,先寫出這個版本拿到正確答案,再說「我知道可以用快慢指標 + 翻轉做到 O(1) 空間」 —— 比寫不完好得多。而題目沒有明文要求 O(1) 空間,所以它也是合法解。
App 3. 不會崩,但餘裕比想像中小 —— 而且完全沒必要冒這個險。

算一下:n = 5×10⁴ 時後半長度約 25000,所以遞迴深度 25000 層。206 那題實測過每層 48 bytes:

25000 × 48 = 1200000 bytes = 1171 KB ≈ 1.14 MB
ulimit -s = 8176 KB ⇒ 佔用 14.3%
206 實測的崩潰臨界約 173437 層 ⇒ 餘裕只剩 6.9 倍

所以在這個題目的上限下是安全的。但:
① 6.9 倍不算寬 —— 換個堆疊上限更小的環境(某些執行緒預設 512 KB 或 1 MB)就會爆;
② 迭代版一個字都不用多寫(206 的迭代版本來就只有四行),而且空間是 O(1)。

換句話說:這是一個「有風險但沒有回報」的選擇。遞迴版在 206 那題還有「比較好講直覺」的價值,但這裡它只是階段 2 的一個零件 —— 沒有人會因為你用遞迴翻轉而覺得你想得比較清楚。

順帶一提:如果題目把 n 放大到 10⁶,遞迴版就直接爆了(500000 層 × 48 bytes = 24 MB,遠超 8 MB),而迭代版毫無感覺。
