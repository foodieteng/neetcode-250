CANDIDATE

This problem reminds me of the standard three-pointer, in-place list reversal — flip one link per iteration. I already know that loop, so I'm not going to re-derive it. The new problem is the two ends.

Think of the list as three chunks: [prefix] [segment] [suffix]. Reversing the middle chunk swaps its head and tail. So afterwards:

· the prefix must point at the new segment head — which used to be at right;
· the new segment tail — which used to be at left — must point at the suffix.

Two links to fix. That's the whole problem.

I
INTERVIEWER

Do you need extra traversals to find those endpoints?

C
CANDIDATE

No — and that's the nice part. The reversal loop hands me all three for free.

When the loop finishes, prev is sitting on the last node it flipped, the old right — the new segment head. And next is sitting on the node just past it — the suffix head.

The third one I get by not moving a pointer: if I park a tail pointer on the node before the segment and never touch it, then tail->next still points at the old segment head — the new segment tail.

So: one walk to position tail, one walk to reverse, then two assignments. One pass.

I
INTERVIEWER

What about left == 1? There's no node before the segment.

C
CANDIDATE

Right — so I'll manufacture one. A dummy node in front of the head, and tail starts there.

That collapses "reverse from the head" and "reverse from the middle" into the same code path, and returning dummy.next handles the head changing without a special case.

I'll put it on the stack, not the heap — if I allocate it with new, nothing frees it, since I return dummy.next. That's a leak of one node per call.

// step 2 -- reverse n = right-left+1 = 3 links, in place

One: walk left - 1 steps from the dummy, so tail lands on node 1.
Two: reverse n = right - left + 1 links in place; afterwards tail->next is node 2, the new segment tail, prev is node 4, the new head, and next is node 5.
Three: relink in this order — 2->next = 5, then tail->next = 4.

One thing I want to flag before I write it: the length is right - left + 1, not right - left. Inclusive range — positions 2 through 4 is three nodes.

I
INTERVIEWER

Does the order of those two assignments matter?

C
CANDIDATE

Yes, and it's subtle enough that I'd want to say why out loud.

The first line reads tail->next to find the new segment tail. The second line writes tail->next. Same field. So if I write first, the only pointer to node 2 is gone, and tail->next->next would modify node 4 instead — turning 4 -> 3 into 4 -> 5 and dropping two nodes. It'd return [1,4,5].

And it would still look right for left == right, because the segment's head and tail are the same node — so a one-node test wouldn't catch it.

The fix that makes order irrelevant: stash ListNode* segTail = tail->next; before the reversal. If a field is both a source and a destination, copy it into a local first.

I — implement
C
CANDIDATE

Alright, let me code this up.

class Solution {
public:
    ListNode* reverseBetween(ListNode* head, int left, int right) {
        int n = right - left + 1;          // segment length, not right - left

        // dummy is the head's predecessor — what changes when left == 1
        ListNode dummy(0, head);
        ListNode* tail = &dummy;

        // ── ① position: walk left-1 steps from dummy, stop just before the range
        for (int i = 0; i < left - 1; i++) {
            tail = tail->next;
        }

        // ── ② reverse n links in place (the whole-list reversal loop, unchanged)
        ListNode *prev = nullptr, *curr = tail->next, *next = nullptr;
        for (int i = 0; i < n; i++) {
            next = curr->next;
            curr->next = prev;
            prev = curr;
            curr = next;
        }

        // ── ③ relink — the order cannot be swapped
        tail->next->next = next;   // old seg head (= new seg tail) → node after right
        tail->next = prev;         // prefix → new segment head

        return dummy.next;
    }
};

The middle block is exactly the standard reversal loop, with the termination swapped from "until null" to "n times". Everything else is boundary handling: the dummy on the stack, the walk to tail, and the two relink lines in that order.

The easy-to-get-wrong line is the very first one — n = right - left + 1, because the range is inclusive.

Now the edge cases I listed:

I
INTERVIEWER

Your reversal loop never checks whether curr is null. Is that safe?

C
CANDIDATE

Only because you guaranteed right <= n. That's borrowed safety, not inherent safety.

The loop trusts the count. If right could exceed the list length, curr would walk off the end, and next = curr->next would dereference null.

Hardening it is one extra condition — for (int i = 0; i < n && curr; i++) — plus a null check before the relink. I'd leave it out here: the constraint is stated, and defensive code against an impossible input just obscures the invariant. But I'd want to be able to answer this exact question, which is why I flagged the constraint up front.

E — evaluate
C
CANDIDATE

Time O(right), which is O(n) worst case: positioning is left - 1 steps, reversal is n steps — exactly right in total, and no node is visited twice. Space O(1) — four pointers and a stack-allocated dummy.

One alternative worth mentioning is head insertion: repeatedly lift the node after curr and splice it right behind tail. Same complexity, same single pass, and no relink step at all — so the ordering trap doesn't exist.

The tradeoff is pointer writes: three per node moved versus one per node flipped, so reversing a 500-node list end to end is roughly three times the writes.

Last thing — this generalizes. Reversing every group of k nodes is this exact function in a loop.
