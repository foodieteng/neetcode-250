重點回顧// RECAP

面向要記住的那一句
本質翻轉 = 把 n 根 next 全部反向,節點一個都不動
驗證方式翻轉前後節點位址集合要守恆 —— 實測 20 萬組皆守恆
迭代四行存 next → 反向 → 推 prev → 推 curr,順序唯一
迭代回傳return prev,不是 curr(迴圈正是因為 curr 變空才停)
遞迴兩行「接上」head->next->next = head 與「斷開」head->next = nullptr 必須成對
遞迴回傳return node,它全程都是原串列的最後一個節點
base case!head 擋空串列、!head->next 擋空指標解參考,各擋各的
最常見死法成環(七種錯法佔三種)—— 症狀是吊死不是答錯
複雜度都是 O(n) 時間;遞迴 O(n) 空間、迭代 O(1)
實測堆疊每層 48 bytes,n=5000 → 234 KB,崩潰臨界約 17 萬層

觀念題// CONCEPT Q&A

Q1. 迭代版的 next = curr->next; 看起來像可以省的暫存。能省嗎?如果直接寫成「先反向、再 curr = curr->next」會發生什麼?
Q2. 迭代版最後 return prev; —— 為什麼不是 return curr;?請說明迴圈是怎麼結束的。
Q3. 遞迴版的 head->next = nullptr; 少寫會怎樣?請說出症狀(不是「會錯」,而是實際會發生什麼)。
Q4. 遞迴版 base case 寫 if (!head || !head->next)。如果只寫 if (!head) 呢?這是「少一層防禦」還是「直接崩潰」?你要怎麼確認?
Q5. 兩種寫法時間都是 O(n),那為什麼一般建議預設寫迭代版?請給出實測數字,不要只說「遞迴比較耗空間」。

範例 Trace// [1,2,3,4,5],兩種走法

解法 B · 迭代 —— 看「已翻好 / 未動」兩段怎麼此消彼長。

// 初始 prev = null curr = 1 已翻好: null 未動: 1 -> 2 -> 3 -> 4 -> 5 -> null
// 第 1 圈 ① next = curr->next (存下 2) ② curr->next = prev (1 的箭頭反過來,指向 null) ③ prev = curr (prev → 1) ④ curr = next (curr → 2) prev = 1 curr = 2 next = 2 已翻好: 1 -> null 未動: 2 -> 3 -> 4 -> 5 -> null
// 第 2 ~ 4 圈(同樣四行) 第 2 圈 prev = 2 curr = 3 已翻好: 2 -> 1 -> null 未動: 3 -> 4 -> 5 -> null 第 3 圈 prev = 3 curr = 4 已翻好: 3 -> 2 -> 1 -> null 未動: 4 -> 5 -> null 第 4 圈 prev = 4 curr = 5 已翻好: 4 -> 3 -> 2 -> 1 -> null 未動: 5 -> null
// 第 5 圈 ① next = curr->next (取到 null) ②③④ 之後 prev = 5 curr = null 已翻好: 5 -> 4 -> 3 -> 2 -> 1 -> null 未動: null
// OUTPUT while (curr) 不成立 → 跳出 return prev = 節點 5 共 5 圈 // 5 -> 4 -> 3 -> 2 -> 1 -> null

解法 A · 遞迴 —— 注意下潛時什麼都沒做,全部工作在回程。

// 下潛(不改任何指標) → reverseList(1) 這段: 1 -> 2 -> 3 -> 4 -> 5 -> null → reverseList(2) 這段: 2 -> 3 -> 4 -> 5 -> null → reverseList(3) 這段: 3 -> 4 -> 5 -> null → reverseList(4) 這段: 4 -> 5 -> null → reverseList(5) 這段: 5 -> null ★ base case → 回傳 5(這就是最終的新 head)
// 回程(每層兩行) ← 回到 4: 5 指回 4,4 斷尾 已翻好: 5 -> 4 -> null 回傳 5 ← 回到 3: 4 指回 3,3 斷尾 已翻好: 5 -> 4 -> 3 -> null 回傳 5 ← 回到 2: 3 指回 2,2 斷尾 已翻好: 5 -> 4 -> 3 -> 2 -> null 回傳 5 ← 回到 1: 2 指回 1,1 斷尾 已翻好: 5 -> 4 -> 3 -> 2 -> 1 -> null 回傳 5
// OUTPUT 5 -> 4 -> 3 -> 2 -> 1 -> null 最大堆疊深度 5 // 回傳值從頭到尾都是節點 5,沒有任何一層改過它
把兩份 trace 疊起來看:指標被反向的順序剛好相反 —— 迭代是 1,2,3,4,5,遞迴是 5,4,3,2,1。 但最終每一根指標的狀態完全相同,這也是 20 萬組對拍零不一致的原因。

應用題// APPLICATION

App 1. 改成只翻轉第 m 到第 n 個節點(LeetCode 92)。迭代版要怎麼改?最麻煩的是哪一步?
App 2. 用「翻轉」來判斷串列是否為回文(LeetCode 234),而且要 O(1) 空間。怎麼做?有什麼副作用?
App 3. 節點數放大到 10⁶。兩份實作各會怎樣?請給出實測依據。
// ANSWERS
A1. 不能省 —— 那一行買的是「後路」。

單向串列裡,curr->next 是通往後半段的唯一一條路。curr->next = prev; 執行完的那一瞬間,原本後面那些節點沒有任何指標指得到 —— 它們不是「暫時找不到」,是永遠失聯(在 LeetCode 上是答錯,在真實系統裡就是記憶體洩漏)。

所以「先反向、再 curr = curr->next」讀到的已經是 prev,指標會往回走而不是往前。實測:窮舉 n = 0..7 共 8 種結構,這個寫法錯 6 種,最小反例 [1,2] 回傳 [1] —— 整整丟了一半。

這是鏈結串列題的通則:覆蓋任何一根 next 之前,先問「有沒有東西會因此失聯」。
A2. 因為迴圈正是「curr 變成 nullptr」才結束的。

while (curr) 跳出時,curr 必定是 nullptr —— 回傳它就是回傳空串列。

而 prev 的不變量是「已翻好那段的頭」。迴圈結束代表「還沒動那段」是空的,也就是整條都翻好了,所以 prev 指著的就是翻轉後的頭 —— 也就是原串列的最後一個節點。

實測:寫成 return curr,8 種結構錯 7 種,連 n = 1 的 [1] 都回空串列(唯一「對」的是 n = 0,因為答案本來就是空的)。

記法:迴圈變數走到界外才停,所以答案永遠在「落後一步」的那個指標上。
A3. 症狀是「程式吊死」,不是「回傳錯的答案」。

head->next->next = head; 讓後面那個節點指回自己,但自己本來也還指著它 —— 這一瞬間兩個節點互相指,形成長度 2 的環。head->next = nullptr; 就是把自己那一根斷掉。

實測:拿掉這一行,[1,2] 走出來是 2 → 1 → 2 → 1 → … 永遠走不完;8 種結構錯 6 種。

而且這類錯誤在測試裡有個實務陷阱:如果你的 dump / 比對函式沒有步數上限,第一個成環的變體就會把整個測試程式卡死,你連「哪裡錯了」都看不到。本頁所有對拍都在走訪裡放了 guard > 3n + 10 的計數器,才問得出「它是成環還是答錯」。

順帶一提:七種陷阱裡有三種都是成環(遞迴忘了斷尾、迭代 prev 初值寫 head、迭代 prev = curr 提前)。成環是這類題最典型的死法。
A4. 是直接崩潰,不是「少一層防禦」。

推導:少了 !head->next,遞迴會一路下潛到最後一個節點的 next,也就是傳進 nullptr。!head 命中回傳 nullptr,回到最後一個節點那一層時 head->next 是 nullptr,於是 head->next->next = head 就是對空指標做寫入。

怎麼確認 —— 用 sanitizer,不要用「跑跑看」。對 [1,2] 跑 g++ -fsanitize=address,undefined:
runtime error: member access within null pointer of type 'ListNode'
AddressSanitizer: SEGV on unknown address 0x000000000008
The signal is caused by a WRITE memory access.

兩個條件擋的是不同的東西:!head 擋「一開始就傳空串列」(n = 0),!head->next 擋「遞迴到底」。不是同一件事的兩種寫法。
A5. 因為遞迴版的空間是 O(n),而且這個 n 是呼叫堆疊的層數 —— 它有硬上限。

實測堆疊用量(拿區域變數的位址當堆疊指標代理量出來的):
n = 100 → 4752 bytes、n = 1000 → 47952 bytes、n = 5000 → 239952 bytes(234 KB) —— 每層固定 48.0 bytes。

崩潰臨界:系統 ulimit -s = 8176 KB,理論可容 8176×1024 / 48 ≈ 174421 層;二分實測崩潰起點約 173437 層,與理論差 0.6%。

所以在本題(n ≤ 5000)遞迴是安全的 —— 只用了上限的 2.9%,餘裕 34.9 倍。但面試官只要加一句「如果串列有一百萬個節點呢」,遞迴版就直接爆,而迭代版一個字都不用改。

另外,「能不能做到 O(1) 空間」本身就是這題最常見的追問。先給迭代版,再說「還可以用遞迴,但那是 O(n) 堆疊」,順序反過來會顯得沒想到。
App 1. 核心四行完全不用動,難的是「接回去」。

作法:先走到第 m−1 個節點,把它記成 prevLeft(它是翻轉段的前驅);再從第 m 個開始跑一模一樣的四行,跑 n − m + 1 圈。

最麻煩的是收尾的兩根指標:
① 翻轉段的原頭(第 m 個)翻完之後成了段尾,要接上「第 n+1 個節點」——所以跑之前得先把它存起來。
② prevLeft->next 要改指向翻轉段的新頭(也就是四行跑完後的 prev)。

另一個坑是 m == 1 —— 這時沒有 prevLeft,而且整條串列的頭會變。標準解法是在最前面掛一個 dummy 節點,讓「頭也可能被換掉」這件事消失,最後回傳 dummy->next。

「翻轉一段」+「dummy 頭」這兩招合起來,就是 25 題「K 個一組翻轉」的全部骨架。
App 2. 快慢指標找中點 → 翻轉後半段 → 兩段對走比對。

① 用快慢指標(fast 走兩步、slow 走一步)找到中點,O(n)。
② 對後半段套用本題的迭代版,得到一條反向的後半。
③ 從原頭與反向後半的頭同時往前走,逐個比 val;任何一個不等就回 false。

時間 O(n),空間 O(1) —— 相對於「把值倒進 vector 再雙指標比對」的 O(n) 空間,這就是它存在的理由。

副作用:它把輸入改壞了。函式回傳時,原串列的後半段是反的。面試時一定要主動說這件事,並補一句「如果呼叫端還要用這條串列,我會在回傳前再翻一次後半段還原」—— 那只是再跑一次同樣的四行,仍是 O(1) 空間。

「修改輸入」是 O(1) 空間解法很常見的隱藏代價,說出來比被問出來好。
App 3. 迭代版毫無問題;遞迴版必爆,而且我量過臨界值。

迭代版:空間 O(1),與 n 無關。10⁶ 個節點只是多跑 10⁶ 圈,時間仍是 O(n),一個字都不用改。

遞迴版:每層 48 bytes(實測,n = 100 / 1000 / 5000 三個點算出來都是 48.0),10⁶ 層需要約 48 MB 堆疊。而系統預設 ulimit -s = 8176 KB —— 差了約 6 倍。

實測崩潰臨界:我用二分找了一次,n ≈ 173437 還能跑、n ≈ 175000 就 stack overflow(理論值 174421,差 0.6%)。所以 10⁶ 遠遠超過,必定崩潰。

如果非要用遞迴,有兩條路:① 手動用一個 std::stack 模擬遞迴 —— 但那等於把 O(n) 從堆疊搬到堆積,不如直接寫迭代;② 改成尾遞迴形式並期待編譯器最佳化掉 —— 但那不可靠(-O0 下必定不會發生,標準也不保證)。

結論:這題的迭代版不只是「另一種寫法」,它是唯一能規模化的那個。
