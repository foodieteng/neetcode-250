Good. Then let me name what this problem is really about. A list with n nodes has n next pointers, and reversing means flipping every one of them. The nodes never move — only the arrows change.

And here's the part that makes it easy to get wrong: each node has exactly one way out. The moment I overwrite a next pointer, everything behind it is unreachable. So before I overwrite any pointer, I ask: does anything get orphaned by this?

On the example, [1,2,3,4,5], I want 5 → 4 → 3 → 2 → 1 → null. Node 1 ends up pointing at null, and node 5 becomes the head I return.

Hmm, let me think about this for a second.

A naive approach would push the values into a vector, then build a brand new list backwards. It works, but it allocates n new nodes, and if you asked for it in place, I'd have to start over.

A cheaper-looking trick is to reverse only the values and leave the pointers alone. That happens to pass, but it isn't really reversing the list, and it's useless once a follow-up forbids changing the values.

This problem reminds me of in-place pointer rewiring. The real question is which order I flip those n arrows in. Front to back gives me an iterative solution; back to front gives me a recursive one. I'll lead with the iterative one because it's O(1) space, then show the recursive one.

P — plan
C
CANDIDATE

Here's the plan.

// invariant, checked at the top of every loop
prev → head of the part that is already reversed
curr → head of the part that is untouched
(those two parts always split the whole list exactly)

// one turn of the loop
next = curr->next;   ← buy the escape route first
curr->next = prev;   flip this one arrow
prev = curr;
curr = next;

// loop ends when curr is null → prev is the new head

One: prev starts at null, curr at the head.
Two: each turn, save curr->next, flip curr's arrow back to prev, then move both forward.
Three: when curr hits null, prev is the new head.

The invariant: prev heads the part already reversed, curr heads the part still untouched, and together they split the whole list.

One thing worth flagging: that saved next is not a convenience variable. curr->next is my only route to the rest of the list, and the very next line overwrites it.

The trade-off: the recursive version reads more like the idea — "assume the rest is reversed, just fix my one arrow" — but it costs O(n) stack. The iterative one is O(1) space, so I'll lead with it. Does this approach sound good, or would you rather I think of another way?

INTERVIEWER

I — implement
C
CANDIDATE

Alright, let me code this up. Iterative first: the four-line loop from the plan, in that order.

class Solution {
public:
    ListNode* reverseList(ListNode* head) {
        ListNode *curr = head, *prev = nullptr, *next;

        while (curr) {
            next = curr->next;   // ① save the way out — ② overwrites it
            curr->next = prev;   // ② flip this one
            prev = curr;         // ③ prev moves up
            curr = next;         // ④ curr moves up
        }

        return prev;              // not curr — curr is nullptr here
    }
};

Two things worth flagging. I return prev, not curr — the loop ended because curr went null. And an empty list needs no special case: the loop never runs, and prev is already null.

Now the recursive one: reverse everything after head first, then fix one arrow.

class Solution {
public:
    ListNode* reverseList(ListNode* head) {
        // both needed: !head = empty list, !head->next = last node
        if (!head || !head->next) {
            return head;
        }

        // reverse the rest first; node is always the old tail
        ListNode* node = reverseList(head->next);

        head->next->next = head;   // next node points back to me
        head->next = nullptr;      // cut my tail, or the two form a cycle

        return node;                  // pass it up untouched, not head
    }
};

The two middle lines come as a pair. Say head is node 4: the first makes 5 point back at 4, but 4 still points at 5 — a cycle — so the second cuts it.

And the base case guards two things: !head catches an empty list; !head->next catches the bottom, where head->next->next would write through a null pointer.

Let me think about complexity here.

Time is O(n) for both — each node is visited once at O(1) cost.

Space is where they differ. Iterative is O(1): three pointers, regardless of length. Recursive is O(n), because every level holds a stack frame until the unwinding reaches it.

In the worst case here, n = 5000, I measured 48 bytes per frame, so about 234 KB, against an 8176 KB stack limit — about 3%. Safe.

Oh, one more thing — binary searching the depth, it blows the stack at around 173,000 frames, which agrees with the limit divided by 48 bytes. So with a million nodes the recursive version is out, and the iterative one needs no change. That's why I'd ship the iterative one by default.
