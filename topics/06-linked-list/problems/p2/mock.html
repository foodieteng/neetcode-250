A naive approach would convert each list to an integer, add them, then split the result back into digits. But it overflows: pack twenty 9s into a long long and you get 7766279631452241919 — a completely different 19-digit number.

Another option is to pad the shorter list with zeros first, then add position by position. That's correct, but it costs an extra pass, and I'd still handle the final carry separately.

This problem reminds me of grade-school column addition, the same idea big-number libraries are built on. At each position, add carry + a + b, keep the value mod 10, and pass the tens part forward. The arithmetic never leaves single-digit scale, so input length doesn't matter.

I'll build the result with a dummy head, so appending the first node and the tenth are the same line of code.

Here's the plan.

// one loop condition, three jobs
while (carry || l1 || l2)
  l1 / l2 → the lists can be different lengths
  carry   → both empty but a carry still needs a home

// one position
v = carry + (l1 ? l1->val : 0) + (l2 ? l2->val : 0)
carry = v / 10  // v <= 9+9+1 = 19, so carry is 0 or 1
v     %= 10
append a new node holding v

One: loop while there's a carry or either list still has nodes.
Two: at each position, v is the carry plus whichever digits exist; the new carry is v / 10, and v keeps v % 10.
Three: append a new node holding v, and return dummy.next.

One thing worth flagging is the loop condition. carry in there handles [9] + [1] = [0,1], where the sum is longer than either input. And it can't run away: v is at most 19, so carry is at most 1, and once both lists are empty that last round makes the carry 0. At most one extra round.

The two if checks handle unequal lengths on their own — an exhausted list contributes nothing, which is padding with zeros without actually padding.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    ListNode* addTwoNumbers(ListNode* l1, ListNode* l2) {
        // dummy only lives until we return, and is never returned → stack
        ListNode dummy;
        ListNode* tail = &dummy;
        int carry = 0;

        // one condition, three jobs: l1 left, l2 left, a final carry
        while (carry || l1 || l2) {
            int v = carry;          // bring in the previous digit's carry

            if (l1) {
                v += l1->val;
                l1 = l1->next;
            }

            if (l2) {            // an empty list adds nothing = padding with zeros
                v += l2->val;
                l2 = l2->next;
            }

            carry = v / 10;       // v ≤ 9+9+1 = 19, so carry is only 0 or 1
            v %= 10;

            tail->next = new ListNode(v);   // this new is needed: it is returned
            tail = tail->next;
        }

        return dummy.next;
    }
};

The line int v = carry; is the whole carry mechanism — it brings the spill-over in before the digits are added; everything else is bookkeeping.

One thing worth flagging: there are two allocation decisions here, and they go opposite ways. The new ListNode(v) for each result digit is correct — those nodes are the return value, so they must outlive the call. The dummy never escapes — I return dummy.next — so it lives on the stack. If I'd written new ListNode() for the dummy, nothing would ever free it: one leaked node per call.

So the useful question isn't "should I use new" — it's "does this thing get handed to the caller?"

Round three is the one that matters: l2 has run out, so its if (l2) simply doesn't fire, and that position adds only the carry and l1 — unequal lengths with no special case. Round four exists only because carry is in the loop condition: both lists are empty, and the leftover 1 becomes the new top digit. The result reads [8,9,0,1] — 1098. That matches.

Corner cases:

• [0] + [0] → [0], a single zero, no stray digit.
• [9] + [1] → [0,1].
• [1] + [9,9,9] → the carry ripples all the way to [0,0,0,1].
• 100 nines + 100 nines → 101 digits.

CANDIDATE

Let me think about complexity here.

Time is O(max(m, n)): every round consumes at least one digit or disposes of the final carry, so the loop runs at most max(m, n) + 1 times. The output is that size too, but the extra space is O(1) — just carry, v and tail.

The worst case is two lists of 100 nines: 101 digits with a leading 1.

Oh, one more thing — the ordering. If the digits were stored most significant first, the list walks forward while carries move the other way. I'd use two stacks to pop digits from the ones end and build the result by prepending — no dummy needed. That's O(m + n) extra space, and the input stays untouched.

So "reverse order" isn't an odd quirk — it's what keeps this to O(1) extra space.
