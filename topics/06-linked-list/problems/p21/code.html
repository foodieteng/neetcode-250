完整實作// THE CODE

演算法與原碼一字未改,只有 dummy 的配置方式修好了(見第 2 節),註解也一併更正。

p21.cpp C++17 
class Solution {
public:
    ListNode* mergeTwoLists(ListNode* l1, ListNode* l2) {
        // 真的放在堆疊上:函式結束自動消失,不必也不能 delete
        ListNode dummy;
        ListNode* tail = &dummy;

        while (l1 && l2) {
            if (l1->val <= l2->val) {   // <= 而非 <:平手取 l1,穩定合併
                tail->next = l1;
                l1 = l1->next;
            } else {
                tail->next = l2;
                l2 = l2->next;
            }

            tail = tail->next;        // 尾巴要跟著推,不然會一直覆蓋同一根
        }

        // 必有一條空了;剩下那條本來就有序且都 >= 已接好的最後一個
        tail->next = l1 ? l1 : l2;

        return dummy.next;            // 不是 &dummy —— dummy 只是假頭
    }
};

原碼那行 new 為什麼要改// THE LEAK

原本寫的是:

// 原碼 ListNode* dummy = new ListNode(); // stack-allocated: no leak ... return dummy->next; // 註解說反了:new 配置在「堆積」,而且沒有人 delete 這個 dummy

函式回傳的是 dummy->next,dummy 這個節點本身從此無人指得到 —— 沒有指標、沒有 delete。這就是教科書定義的記憶體洩漏。

// 實測(覆寫 ListNode::operator new / delete 精確計數) [原碼:new ListNode()] 建輸入串列配置 6 個,merge 又配置了 1 個 把結果整條 delete 掉之後:new = 7, delete = 6 ⇒ 洩漏 1 個節點 ← 正是那個 dummy [改成:ListNode dummy;] 建輸入串列配置 6 個,merge 又配置了 0 個 把結果整條 delete 掉之後:new = 6, delete = 6 ⇒ 洩漏 0 個節點 [累積效果] sizeof(ListNode) = 16 bytes 呼叫 100000 次 → 洩漏 100000 個節點 = 1562 KB // LeetCode 判題不檢查洩漏,所以兩種寫法都 AC
寫法配置在哪誰負責釋放每次呼叫洩漏
ListNode* d = new ListNode();堆積 heap沒有人16 bytes
ListNode dummy;堆疊 stack函式結束自動0
unique_ptr<ListNode> d(new …);堆積 heap解構時自動0
這裡 ListNode dummy; 是最好的選擇,理由不只是「不會漏」—— dummy 的生命週期本來就只需要活到函式結束,它根本不該被回傳出去。 用堆疊表達的正是這個意圖;用 new 則是在說「這東西要活得比這個函式久」,而那並不是真的。
為什麼「註解寫錯」比「單純漏掉」更值得記一筆

單純忘記釋放,是沒想到;寫上 // stack-allocated: no leak 卻用了 new, 是想過、但結論相反。前者 code review 抓得到,後者會讓 reviewer相信它已經處理過而跳過。 面試現場念出這句註解,面試官會直接追問 —— 那時答不出來的代價比沒寫註解大得多。

陷阱為什麼錯實測

[0] + [0] → [0]

洩漏 1 節點/呼叫

注意最後兩列的性質不同:new 那個是真 bug 但不影響輸出, < 那個是輸出正確但語意變了。 兩種都是「測試抓不到、review 才抓得到」的問題 —— 這類東西要靠自己說出來。
