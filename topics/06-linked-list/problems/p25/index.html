題目簡介// THE QUESTION

QUESTION

給一條串列的頭與一個整數 k,每 k 個節點一組就地反轉,回傳新的頭。

如果最後剩下不足 k 個,那一段保持原順序。 而且只能改指標,不能改節點的值。

1 ≤ k ≤ n ≤ 5000、0 ≤ Node.val ≤ 1000。

第 92 題做的是翻一段(left 到 right), 這題是翻很多段,而且段與段之間要串起來。 反轉本體和 206 / 92 完全一樣 —— 新東西只有兩件:怎麼判斷「還夠不夠一組」,以及怎麼把段與段接起來。

而遞迴讓第二件事幾乎免費。 每一層只負責一組:翻好前 k 個,剩下的丟給自己,再把兩截接起來 —— 「接起來」永遠只有一行:head->next = reverseKGroup(curr, k); 因為 head 翻完之後正好是這一組的段尾。

遞迴與迭代,各買到什麼// WHY THIS

A 把值倒進 vector,分段 reverse 再寫回 O(n) 空間 · 違反題意
寫起來最快,但題目明文說「不能改節點的值」 —— 它要的就是指標重接這件事本身。
× REJECT · 題目禁止
B 遞迴:翻一組,剩下交給自己 O(n/k) 堆疊
結構最乾淨:每層只想一組,「接回去」由呼叫堆疊自動處理, 不需要手動維護前一組的尾巴。代價是 O(n/k) 的堆疊深度。
● 本題的寫法
ALSO
C 迭代:dummy + tail,把 92 的兩行接線放進迴圈 O(n) 時間 · O(1) 空間
用一個 tail 指標記住「上一組的尾巴」,取代呼叫堆疊。 兩行接線和 92 一字不差,只是多了「先數夠不夠 k 個」和「把 tail 推到新段尾」。 沒有堆疊深度限制。
● 同樣正確 · 空間更好
B 和 C 都對(實測各 20 萬組 0 錯),但這題的原碼還有一個效能問題 —— 它每一層都重新數一次整條串列的長度, 讓時間複雜度變成 O(n²/k) 而不是 O(n)。 答案完全正確,而且在 LeetCode 上會過 —— 但 n=5000, k=1 時實測要 16.10 ms, 而只改一個迴圈的版本只要 0.041 ms。詳見程式碼頁。

核心策略 · 每一層三件事// STRATEGY

  1. 確認還夠不夠一組:不夠 k 個就原封不動回傳 —— 這就是遞迴的 base case,也正好實現了題目要求的「尾巴保持原順序」。
  2. 翻 k 圈:和 206 迭代版一字不差。 翻完後 prev = 新段頭,curr = 下一組的開頭, 而原本的 head = 這一組的新段尾。
  3. 接起來並回傳:head->next = reverseKGroup(curr, k); 然後 return prev;。
第 3 步只有兩行,而且每一層都長得一模一樣 —— 這正是遞迴買到的東西:92 要手動維護的那個 tail 指標, 在這裡由呼叫堆疊自動幫你記住了。

head->next 為什麼剛好是對的// THE KEY LEMMA

LEMMA · 翻完之後,head 就是這一組的段尾

進入這一層時,head 是這一組的第一個節點。 反轉會讓一段的頭尾對調 —— 所以翻完之後,head 變成最後一個。

而「最後一個」該接的,正是後面那一整段的處理結果。 於是 head->next = reverseKGroup(curr, k); 一行就對了。

同時 prev 停在原本的最後一個 = 新的段頭,所以 return prev;。 兩個端點都是反轉迴圈的副產品,一個都不用另外找 —— 和 92 的 LEMMA 1 是同一件事。

複雜度// COMPLEXITY

原碼 T = O(n² / k)　　S = O(n / k) 堆疊

那個 n² 來自「每一層都重新數一次整條長度」 —— 而它問的問題(「還夠不夠 k 個?」)其實只需要走 k 步。 改成只數 k 步,就變成 O(n)。

維度量級實測
正確性0 錯窮舉 n=0..12 × k=1..n+2 共 104 組 + 隨機 20 萬組
「數長度」的迴圈n²/2kn=5000, k=1 → 12502500 次(理論 12500000)
耗時(n=5000, k=1)16.10 ms只數 k 步的版本 0.041 ms;迭代版 0.014 ms
遞迴深度n/k + 1n=5000, k=1 → 5001 層
每層堆疊64 bytes實測(深度 100 用 6416,深度 200 用 12816)
題目上限的堆疊用量313 KB預設上限 8176 KB —— 安全
記憶體0 洩漏沒有任何 new —— 本章少數幾題之一
要說清楚:這在 LeetCode 上完全會過。 n ≤ 5000 時 n²/2 = 1250 萬次指標跳躍,大約 12 ms,遠低於時限。 但這是「題目上限剛好夠小」救了它,不是演算法本身沒問題 —— 而修好它只需要把一個 while 換成一個 for。

一句洞察// INSIGHT

遞迴把「記住上一組的尾巴」外包給了呼叫堆疊 —— 那正是 92 要手動維護的東西。 但也要注意它順手帶進來的成本:每一層都重新算一次全域資訊(這裡是長度), 是遞迴解法最常見的隱形二次方。 問自己一句:「這一層真的需要全部的資訊嗎,還是只需要眼前這 k 個?」
