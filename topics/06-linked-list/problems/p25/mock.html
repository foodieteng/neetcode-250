The reversal itself is a solved problem — three pointers, flip one link per step. What's new is doing it repeatedly and stitching the groups together.

This problem reminds me of plain recursion on a list: reverse the first k, and the rest of the list is the same problem.

The nice part is where the join lands. After reversal, the node I came in on, head, is this group's tail — exactly the node that must point at whatever comes next. So the join is one line: head->next = recurse(rest). Then I return prev, which is sitting on the new head of this group.

One: check whether a full group is left; if not, return head unchanged.
Two: reverse k links, exactly like the standard reversal.
Three: join and return — head->next gets the recursion on curr, and I return prev.

One thing worth flagging: recurse on curr, not prev. prev is still inside the group I just handled; passing it would re-process the same nodes and splice the result back into itself, which makes a cycle, and the recursion never terminates.

class Solution {
public:
    ListNode* reverseKGroup(ListNode* head, int k) {
        // 1. count the length — correct, but it walks the WHOLE remaining list
        int n = 0;
        ListNode *tail = head;
        while (tail) {
            tail = tail->next;
            n++;
        }

        // base case: fewer than k left → return as-is — exactly the "leftovers stay" rule
        if (n < k) return head;

        // 2. reverse exactly k links — the standard three-pointer reversal
        ListNode *prev = nullptr, *curr = head, *next = nullptr;
        for (int i = 0; i < k; i++) {
            next = curr->next;
            curr->next = prev;
            prev = curr;
            curr = next;
        }

        // 3. head is now this group's TAIL — hang the rest off it
        head->next = reverseKGroup(curr, k);

        return prev;   // prev is this group's new head
    }
};

One thing worth flagging is step one. I counted the whole remaining list, and the question being asked is "are there at least k nodes," not "how many nodes are there."

Since every level re-walks everything below it, that's n + (n−k) + (n−2k) + … — O(n²/k). At k = 1 and n = 5000, that's about 12.5 million pointer hops instead of 5000.

It's correct, but the fix is to stop after k steps — one loop change, and it becomes O(n).

Two things replace the call stack: a dummy node, because the first group changes the list's head and I need something to hang it off; and a tail pointer holding the previous group's tail.

ListNode* reverseKGroup(ListNode* head, int k) {
    ListNode dummy(0, head);
    ListNode* tail = &dummy;       // previous group's tail — a hand-rolled "call stack"

    while (true) {
        // first check that k nodes remain
        ListNode* chk = tail;
        for (int i = 0; i < k && chk; i++) chk = chk->next;
        if (!chk) break;                // fewer than k left → leave them as-is, done

        ListNode *prev = nullptr, *curr = tail->next, *next = nullptr;
        for (int i = 0; i < k; i++) {
            next = curr->next; curr->next = prev; prev = curr; curr = next;
        }

        ListNode* newTail = tail->next;   // old head = this group's new tail, stash it first
        tail->next->next = next;          // join the tail forward
        tail->next = prev;                // join the previous group to the new head
        tail = newTail;                    // next group continues from here
    }

    return dummy.next;
}

The one thing to be careful about is newTail. Both join lines involve tail->next — the first reads it to find the group's new tail, the second overwrites it. So I stash it before touching anything, the same reason the reversal loop saves next before clobbering curr->next.

O(n) time, O(1) space. If this were production code with an unbounded n, this is the one I'd ship.

Let me think about complexity here.

Time: the code as written is O(n²/k), because of the full-length count. With the k-step check, or the iterative version, it's O(n); each node is visited by the lookahead and by the reversal.

Space: O(n/k) for the recursion, O(1) for the iterative one.

For testing, the input space is small enough to enumerate: every n from 0 to 12, every k from 1 up past n, against a reference that reverses slices of a vector.

The variant I'd specifically test for is n being an exact multiple of k. If someone writes the base case as n <= k, that's the only input class that breaks — and the standard example, with k=2, won't catch it, because it ends with a remainder.
