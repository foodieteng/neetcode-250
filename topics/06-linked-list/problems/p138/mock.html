Good. Then let me name the actual difficulty.

next is easy — it only ever points forward, so by the time I need it I'm already there. But random can point anywhere. When I'm copying node 0, its random might point at node 5 — and the copy of node 5 doesn't exist yet. It might also point backward at a node I already copied, or at itself.

And that's the tell. Once a pointer can reach any node, this isn't really a list problem — it's a graph deep copy.

M — match
C
CANDIDATE

Hmm, let me think about this for a second.

A naive approach would be: copy a node, then recursively copy whatever its random points at. That doesn't terminate. If A's random points at B and B's points back at A, I bounce between them forever, allocating a node every bounce. And even without a cycle, a node reachable from three randoms would get copied three times, breaking the "exactly n nodes" rule.

This problem reminds me of memoized graph traversal. I keep a map from each original node → its copy. First time I see a node: make the copy, record it, then recurse. Every time after: hand back what's in the map.

That one map buys correctness — each original is copied exactly once — and termination — a backward random hits the map and returns. It's not a speedup; the algorithm doesn't work without it.

P — plan
C
CANDIDATE

Here's the plan.

// copy(node):
if node is null    → return null
if node in map     → return map[node]  (already done)

map[node] = new Node(node->val);  ← register BEFORE recursing
map[node]->next   = copy(node->next)
map[node]->random = copy(node->random)
return map[node]

One: if the node is null, return null.
Two: if it's already in the map, return its copy.
Three: otherwise create the copy, register it, then recurse on next and random, and return it.

One thing worth flagging is the order of that last step. The registration has to happen before the two recursive calls, not after. If I build the copy, recurse, and only then insert into the map, a node whose random points at itself will recurse into copy again, find nothing in the map, and allocate another node — forever.

Putting myself in the map first announces: "I'm already in progress, don't come back in."

Does this approach sound good, or would you rather I think of another way?

INTERVIEWER

I — implement
C
CANDIDATE

Alright, let me code this up. A thin public function creates the map and calls a recursive helper that does exactly those three steps.

class Solution {
public:
    Node* copyRandomList(Node* head) {
        // a fresh dict on every call — it can't be a member variable
        unordered_map<Node*, Node*> dict;
        return copy(head, dict);
    }

private:
    Node* copy(Node* head, unordered_map<Node*, Node*>& dict) {
        if (!head) {
            return head;
        }

        // already copied → hand it back; this one line blocks both
        // "building twice" and "infinite recursion"
        if (dict.count(head)) {
            return dict[head];
        }

        // register first, then recurse; reversed → a self-random recurses forever
        dict[head] = new Node(head->val);

        dict[head]->next   = copy(head->next, dict);
        dict[head]->random = copy(head->random, dict);

        return dict[head];
    }
};

One thing worth flagging: the map is a local variable, not a member of the class.

As a member, it would survive between calls, and its keys are addresses of original nodes. Once those nodes are freed, the allocator hands the same addresses to the next list, dict.count(head) says "already copied," and I return a deleted node. Running 2,000 lists through one Solution object, 1,997 hit a stale address.

And AddressSanitizer reports nothing, because it quarantines freed memory, so addresses aren't reused. A scratch table for one call has no business outliving that call.

The part that matters is the way back up. On the way down I only build nodes and follow next. Every random gets wired on the way up — and by then the whole chain is already in the map, so all three non-null randoms are hits, including the backward one from node 1 to node 0. Four nodes, nothing built twice. That matches.

It also means a wild random never deepens the recursion: at n = 1000, five different random layouts all measured exactly 1001 frames.

Corner cases:

• Empty list → hits the null guard, returns null.
• One node, random → itself: the copy points at the copy.
• All randoms → one node: it's still copied once.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time is O(n) — each node is allocated once and each of its two pointers is wired once, with O(1) average map operations.

Space is O(n), in two separate pieces: the map holds n entries, and the recursion holds up to n + 1 frames. At about 96 bytes a frame, n = 1000 is roughly 94 KB — about 1% of the default stack.

Oh, one more thing — if n went to 105, that becomes about 9.4 MB and blows the stack. I'd switch to two iterative passes: allocate every copy into the map, then wire next and random by lookup.

And for O(1) extra space, weave each copy right after its original, so the copy of A.random is A.random->next. It's twice the code, so I'd lead with the map version.
