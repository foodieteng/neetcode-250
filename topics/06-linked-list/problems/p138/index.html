題目簡介// THE QUESTION

QUESTION

每個節點除了 next,還多一根 random,可以指向串列裡的任何一個節點,或 null。 做一份深拷貝。

深拷貝的三個條件:剛好 n 個全新節點、值一一對應、 新串列的所有指標都指向新節點(一根都不能指回原串列)。0 ≤ n ≤ 1000。

困難點只有一個:拷貝節點 0 的時候,它的 random 可能指向節點 5 —— 而節點 5 的拷貝還不存在。next 沒這個問題(它只往後), 但 random 可以指向任何地方,包括還沒處理到的、以及已經處理過的。

這就是「圖的深拷貝」問題,只是包裝成串列。 解法也是圖論的標準解:一張「原節點 → 拷貝節點」的記憶表, 把「這個我拷過了嗎」變成 O(1) 查詢。 同樣的骨架直接可以搬去做 133 Clone Graph ↗。
2

為什麼需要記憶表// WHY THIS

A 碰到 random 就遞迴拷貝它 無限遞迴
random 可以指回前面、甚至指向自己。沒有記憶表的話, 拷貝 A → 拷貝 A 的 random B → 拷貝 B 的 random A → …永遠回不來。
× REJECT · 無限遞迴
B 先算出每個 random 的「索引」,再用索引接 O(n²) 或 O(n) + 額外陣列
可行,但「求某個節點的索引」本身就要走一遍 —— 除非你先建一張 節點 → 索引的表。那其實就是記憶表,只是繞了一圈。
△ 繞遠路
ADOPT
C 一張 dict: 原節點 → 拷貝節點 O(n) 時間 · O(n) 空間
第一次碰到某個原節點:新建拷貝、立刻記進表、再往下遞迴。 之後再碰到:直接查表拿,不重建。 這一張表同時解決了「還沒拷的」和「已經拷過的」兩種情形。
● ADOPT · O(n)
記憶表在這裡有兩個作用,不只是「加速」: ① 正確性 —— 保證同一個原節點只拷一次(否則新串列會超過 n 個節點); ② 終止性 —— 遇到指回去的 random 時能停下來。
3

核心策略 · 三步驟// STRATEGY

  1. 查表:if (dict.count(head)) return dict[head]; —— 拷過就直接給。
  2. 先登記,再遞迴:dict[head] = new Node(head->val); 必須在遞迴之前。順序反了,自環的 random 就會無限遞迴。
  3. 接兩根指標:next 和 random 各遞迴一次 —— 而遞迴本身會處理「已拷過」的情形。
先登記再遞迴是這類「圖上做記憶化」的通則: 把自己放進表裡,是在對後面說「我正在處理中,別再進來了」。

dict 是成員變數 —— 這是個真的 bug// THE STATE LEAK

問題:表跨呼叫殘留,而裡面全是懸空指標

unordered_map<Node*, Node*> dict; 寫在 class 裡,是成員變數 —— 它不會在函式結束時清空,而且鍵是原節點的位址。

第一次呼叫結束、那些節點被釋放之後,dict 裡留下的是一堆懸空指標。 接著 malloc 很可能把同樣的位址發還給下一條串列的節點 —— 於是 dict.count(head) 誤判成「這個我拷過了」,直接回傳一個已經 delete 掉的節點。

實測:用同一個 Solution 物件連續處理 2000 條不同的串列, 1997 條(99.85%)的新節點位址已經在舊 dict 裡,第一次就發生在第 1 輪。 直接走訪回傳值 → SEGV。

// 實測:同一個 Solution 呼叫兩次 Solution s; // 只建一個,兩次都用它 第 1 次:輸入 [1,2,3] → 拷貝 [1,2,3] dict.size() = 3 (釋放原串列與拷貝) 第 2 次:輸入 [9,8,7] 這三個「全新」節點的位址,在舊 dict 裡命中 1 / 3 個 → 拷貝 [8,7] ✗ 正解應為 [9,8,7] // 少了一個節點 —— 因為第一個節點被誤認成「已經拷過」,回傳了懸空指標
LeetCode 通常每筆測資新建一個 Solution,所以這份程式碼會 AC。 但那是判題框架剛好幫你把狀態清掉了,不是程式碼本身正確。 修法只有一行:把 dict 從成員變數改成區域變數(見程式碼頁)。
// 順帶一提:ASan 反而「蓋掉」這個 bug 用 g++ -fsanitize=address 跑同一個兩次呼叫的情境 → 沒有報錯,答案還是對的 原因:ASan 會把釋放的記憶體放進「隔離區」延後重用, 所以新節點拿不到舊位址,dict 就不會誤命中。 // 這類「靠位址重用才觸發」的 bug,sanitizer 不一定抓得到 —— 要靠設計上看出來

遞迴深度// EXACTLY n + 1

這份解法對 next 和 random 都遞迴, 直覺上會擔心「random 亂指會不會把深度弄得很深」。實測不會。

// 遞迴深度(n = 1000,五種 random 佈局) random = 下一個節點 最大深度 = 1001 random = 前一個節點 最大深度 = 1001 random = 全部指向最後一個 最大深度 = 1001 random = 全 null 最大深度 = 1001 random = 隨機 最大深度 = 1001 // 恆等於 n + 1,與 random 的佈局完全無關

原因:程式先把整條 next 鏈遞迴完,才回過頭接 random。 到了接 random 的時候,所有節點都已經在 dict 裡 —— 每個 random 遞迴都是第一行就命中回傳,深度只加 1。

// 堆疊實測 n = 100 → 9600 bytes (9.4 KB) 每層約 96 bytes n = 500 → 48000 bytes (46.9 KB) 每層約 96 bytes n = 1000 → 96000 bytes (93.8 KB) 每層約 96 bytes ← 題目上限 ulimit -s = 8176 KB ⇒ n=1000 只用了 1.1% // 每層 96 bytes 比 206 的 48 大一倍 —— 多出來的是 map 操作的區域變數
n ≤ 1000 讓遞迴很安全(只用 1.1% 的堆疊)。 但如果題目把 n 放大到 10⁵,93.8 KB 就會變成 9.4 MB,直接爆 —— 那時要換成迭代兩趟的版本(見複習頁 App 1)。

複雜度// COMPLEXITY

T = O(n)　　S = O(n)

每個原節點只被建立一次(靠記憶表保證),每次 dict 操作平均 O(1)。 空間是 dict 的 n 筆 + 遞迴堆疊的 n 層。

一句洞察// INSIGHT

只要指標可以指向「任意」節點,問題就從串列變成了圖 —— 而圖的深拷貝只有一個標準答案:一張「原 → 新」的記憶表。 它同時買到正確性(不重複建)和終止性(環不會無限遞迴)。
