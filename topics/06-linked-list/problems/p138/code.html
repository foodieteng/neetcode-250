完整實作// THE CODE

演算法與原碼一字未改,只把 dict 從成員變數改成區域變數(見第 2 節)。

p138.cpp C++17 
class Solution {
public:
    Node* copyRandomList(Node* head) {
        // dict 每次呼叫都是全新的 —— 不能放成員變數
        unordered_map<Node*, Node*> dict;
        return copy(head, dict);
    }

private:
    Node* copy(Node* head, unordered_map<Node*, Node*>& dict) {
        if (!head) {
            return head;
        }

        // 拷過就直接給 —— 這一行同時擋掉「重複建」和「無限遞迴」
        if (dict.count(head)) {
            return dict[head];
        }

        // 先登記,再遞迴 —— 順序反了,自環的 random 會無限遞迴
        dict[head] = new Node(head->val);

        dict[head]->next   = copy(head->next, dict);
        dict[head]->random = copy(head->random, dict);

        return dict[head];
    }
};

🎤 面試模擬 · UMPIRE mock interview transcript ↗

這是記憶化遞迴的標準形狀:查表 → 沒有就建並登記 → 遞迴填內容 → 回傳。 同一副骨架直接可以拿去做 133 Clone Graph ↗ —— 差別只是「兩根指標」變成「一個鄰居陣列」。

原碼那個 dict 為什麼要改// STATE THAT OUTLIVES THE CALL

原本寫的是:

// 原碼 class Solution { public: unordered_map<Node*, Node*> dict; // ← 成員變數 Node* copyRandomList(Node* head) { ... } }; // 函式結束時 dict 不會清空,而它的鍵是「原節點的位址」
失敗機制:位址被重用 → 舊 entry 誤命中 → 回傳懸空指標

第一次呼叫結束、原串列與拷貝都被釋放之後,dict 裡留下的是一整批懸空指標。

接著 malloc 很自然地把剛釋放的位址發還給下一條串列。 於是 dict.count(head) 回答「有」—— 但那筆記錄指的是上一次那個已經 delete 掉的拷貝。

結果就是:該建的節點沒建,回傳的是釋放過的記憶體。

// 實測 · 用同一個 Solution 物件呼叫兩次 Solution s; // 只建一個 第 1 次:輸入 [1,2,3] → 拷貝 [1,2,3] dict.size() = 3 (釋放原串列與拷貝) 第 2 次:輸入 [9,8,7] 這三個「全新」節點的位址,在舊 dict 裡命中 1 / 3 個 → 拷貝 [8,7] ✗ 正解 [9,8,7] 直接走訪那個回傳值 → SEGV(程式 exit code 139)
// 實測 · 命中率有多高 用同一個 Solution 連續處理 2000 條不同的串列(每條 4 個節點): 新串列的節點位址「已經在舊 dict 裡」的輪數:1997 / 2000 (99.85%) 第一次發生在第 1 輪 最後 dict.size() = 18,而且裡面全是懸空指標 // 不是罕見的巧合 —— 位址重用是 malloc 的正常行為
為什麼 sanitizer 抓不到這個

用 g++ -fsanitize=address 跑同一個「兩次呼叫」的情境,沒有任何報錯,答案還是對的。

原因是 ASan 會把釋放的記憶體放進隔離區(quarantine)延後重用,所以新節點拿不到舊位址, dict 就不會誤命中。這類「靠位址重用才觸發」的 bug,sanitizer 反而會蓋掉它 —— 只能從設計上看出來:一個函式的暫存表,不該活得比那次呼叫久。

LeetCode 通常每筆測資新建一個 Solution,所以原碼會 AC。 但那是判題框架幫你清了狀態,不是程式碼本身正確 —— 面試官問一句 「如果同一個物件被呼叫兩次呢」就會露餡。 修法一行:把 dict 移到函式裡。

為什麼必須「先登記,再遞迴」// REGISTER FIRST

// 正確順序 dict[head] = new Node(head->val); ← 先把「我在處理中」記下來 dict[head]->next = copy(head->next); dict[head]->random = copy(head->random); return dict[head];
// 顛倒的話 Node* c = new Node(head->val); c->next = copy(head->next); ← 這時 dict 裡還沒有 head c->random = copy(head->random); dict[head] = c; 若 head->random 指回 head 自己(或指回任何祖先): copy(head) → dict 沒有 → 又建一個新節點 → 又遞迴 → … // 無限遞迴,而且每一層都在 new 節點 —— 堆疊與堆積一起爆
「先把自己放進表裡」是在對後面的遞迴說:我正在處理中,別再進來了。 這是所有圖上記憶化的共通寫法 —— 133 Clone Graph 也是同一個順序,而且理由一模一樣。

正確性驗證// CROSS CHECK

「深拷貝」有三個條件,缺一不可 —— 所以驗證也分三項:

// 對拍(n = 0..12,random 隨機指向任一節點或 null,共 200000 組) ① 結構一致(val / next / random 的索引序列都相同) → 不一致 0 ② 與原串列共用節點 → 0 組 ③ 有 random 指到「新串列以外」的節點 → 0 組 節點數檢查(50000 組):new 出來的節點數 != n 的 → 0 組 官方範例 vals=[7,13,11,10,1], random=[null,0,4,2,0]: 原:vals=7 13 11 10 1 rnd=-1 0 4 2 0 拷:vals=7 13 11 10 1 rnd=-1 0 4 2 0 共用節點 0 個 ✓ // 三項都過才算深拷貝 —— 只比 val 序列是驗不出「指標指回原串列」的
第 ③ 項最容易漏掉。如果 random 忘了拷、直接沿用原本的指標, val 序列看起來完全正確 —— 只有「檢查 random 的目標是否落在新串列內」才驗得出來。 驗證方式要對得上題目真正的要求。

邊界與陷阱// PITFALLS

陷阱後果實測
dict 寫成成員變數 跨呼叫殘留 → 位址重用 → 回傳懸空指標 同物件 2000 次:1997 次踩到
走訪回傳值 → SEGV
先遞迴、後登記 random 指回祖先時無限遞迴,而且每層都在 new 堆疊與堆積一起爆
沒有記憶表,碰到 random 就遞迴 同上;而且就算沒環,同一個節點也會被拷貝多次 新串列超過 n 個節點
違反「exactly n brand new nodes」
random 直接沿用原指標 val / next 看起來全對,但 random 指回原串列 只比 val 序列驗不出來
要檢查目標是否落在新串列內
head == nullptr 沒問題 —— 第一行 if (!head) return head; 就擋掉了 n = 0 實測正確
注意前三列都不是「答案差一點」,而是崩潰、無限遞迴、或違反題目定義。 這題的錯法都很嚴重 —— 但也因此,只要記憶表用對了就很難錯。

// DICT: 那一行 count() 同時做了兩件事 if (dict.count(head)) return dict[head]; ① 正確性:同一個原節點只會被 new 一次 ⇒ 新串列恰好 n 個節點(實測 5 萬組全部相符) ② 終止性:random 指回祖先時,這一行讓遞迴停下來 ⇒ 沒有它就是無限遞迴 // 記憶表不只是「加速」,它是這個解法能成立的前提
// DEPTH: 為什麼 random 亂指也不會加深遞迴 程式先把整條 next 鏈遞迴完,才回過頭接 random ⇒ 接 random 時所有節點都已在 dict 裡 ⇒ 每個 random 的遞迴都在第一行就命中回傳,深度只 +1 實測 n = 1000,五種 random 佈局(指下一個 / 前一個 / 最後一個 / 全 null / 隨機): 最大深度全部 = 1001 = n + 1 // 深度與 random 的佈局完全無關
