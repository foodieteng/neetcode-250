重點回顧// RECAP

面向要記住的那一句
題型本質random 能指任意節點 ⇒ 這是圖的深拷貝,不是串列題
記憶表一張 原節點 → 拷貝節點,同時買到正確性 + 終止性

應用題// APPLICATION

App 1. 把 n 放大到 10⁵。這份遞迴解法還能用嗎?怎麼改成不遞迴?
App 2. 有沒有辦法做到 O(1) 額外空間(不算輸出)?
App 3. 這題的骨架能不能直接搬去做 133 Clone Graph ↗(任意圖的深拷貝)?
// ANSWERS
A1. 它擋掉兩件事,而且兩件都是致命的 —— 記憶表不是「加速」,是這個解法成立的前提。

① 正確性:同一個原節點只能拷一次。如果節點 5 被三個不同節點的 random 指到,沒有表的話它會被建三份 —— 新串列的節點數就超過 n,違反題目寫明的 "exactly n brand new nodes",而且那三份彼此還不是同一個節點,random 的對應關係整個垮掉。

② 終止性:random 可以指回去。random 能指向任何節點,包括自己、包括祖先。沒有表的話:拷 A → 拷 A 的 random B → 拷 B 的 random A → …永遠回不來,而且每一層都在 new,堆疊和堆積會一起爆。

實測:加了表之後,20 萬組隨機測資結構全對、共用節點 0、random 沒有一根指到新串列外;5 萬組檢查新建節點數,恆等於 n。

一句話:random 能指任意節點的那一刻,這題就從「串列」變成了「圖」——而圖的深拷貝只有記憶表這一個標準答案。
A2. 會無限遞迴,而且每一層都在配置記憶體。

顛倒之後長這樣:
Node* c = new Node(head->val);
c->next = copy(head->next);
c->random = copy(head->random);
dict[head] = c;  // ← 太晚了

具體輸入:n = 1,唯一那個節點的 random 指向自己。
copy(A) → dict 裡沒有 A → 建一個拷貝 → 遞迴 copy(A->random) = copy(A) → dict 裡還是沒有 A(因為登記在最後一行,還沒執行到)→ 又建一個 → 又遞迴 → …

更一般地,任何 random 指回祖先的情形都會觸發,例如 [A, B] 且 B.random = A。

「先把自己放進表裡」的語意是:對後面的遞迴宣告「我正在處理中,別再進來了」。這是所有圖上記憶化的共通寫法 —— 133 也是同一個順序,理由一模一樣。
A3. 有問題,而且是很嚴重的那種 —— LeetCode 會 AC 只是因為它每筆測資都新建一個 Solution。

dict 是成員變數 ⇒ 函式結束時不會清空,而它的鍵是原節點的位址。第一次呼叫結束、那些節點被釋放之後,dict 裡留下的是一整批懸空指標。接著 malloc 很自然地把剛釋放的位址發還給下一條串列 —— 於是 dict.count(head) 回答「有」,直接回傳一個已經 delete 掉的節點。

實測:
· 同一個 Solution 呼叫兩次,第一次 [1,2,3]、第二次 [9,8,7] → 第二次回傳 [8,7](少一個節點)。
· 連續處理 2000 條不同的串列:1997 條(99.85%)的新節點位址已經在舊 dict 裡,第一次就發生在第 1 輪。
· 直接走訪回傳值 → SEGV(exit code 139)。

而且 sanitizer 抓不到。用 -fsanitize=address 跑同樣的情境完全沒報錯 —— 因為 ASan 把釋放的記憶體放進隔離區延後重用,新節點就拿不到舊位址。這類「靠位址重用才觸發」的 bug,工具反而會蓋掉它。

修法一行:把 dict 移進函式當區域變數。而該問自己的問題是:「這個暫存表,有任何理由活得比這次呼叫久嗎?」沒有的話,它就不該是成員。
A4. 不會 —— 深度恆為 n + 1,而且與 random 的佈局完全無關。

原因:程式的順序是先接 next、再接 random。而 dict[head]->next = copy(head->next) 這一行會把整條 next 鏈(以及它們的 random)全部處理完才返回。所以輪到接 head 自己的 random 時,所有節點都已經在 dict 裡 —— 那次遞迴在第一行就命中回傳,深度只 +1。

實測(n = 1000,五種 random 佈局):
指下一個 / 指前一個 / 全指最後一個 / 全 null / 隨機 → 最大深度全部是 1001。

堆疊用量:每層約 96 bytes(比 206 純翻轉遞迴的 48 大一倍,多出來的是 map 操作的區域變數)。
n = 1000 → 93.8 KB,只佔 ulimit -s = 8176 KB 的 1.1%。

所以在這題的上限下遞迴很安全 —— 但那是 n ≤ 1000 給的。n 一到 10⁵ 就是 9.4 MB,直接爆(見 App 1)。
A5. 不夠 —— 只比 val 序列,最關鍵的那個錯誤剛好驗不出來。

題目對「深拷貝」寫了三個條件,驗證就該有三項:

① 結構一致 —— val 序列相同,而且random 指向的「索引」也要相同(不能比指標,要比索引)。
② 沒有共用節點 —— 新串列的節點位址集合與原串列交集為空。
③ 所有指標都落在新串列內 —— 每個 random 的目標,必須是新串列裡的某個節點。

為什麼第 ③ 項最重要:假設有人忘了拷 random,直接寫 copy->random = orig->random。這時 val 序列完全正確、next 結構完全正確 —— 只有「檢查 random 的目標在不在新串列裡」才驗得出來。而題目正是明文禁止這件事:"None of the pointers in the new list should point to nodes in the original list."

實測:三項各跑 20 萬組,全部 0 失敗;另加 5 萬組檢查新建節點數恰好等於 n。

通則:驗證方式要對得上題目真正的要求,而不是對得上「最容易寫的那個檢查」。
App 1. 遞迴會爆,要改成迭代兩趟 —— 而且改起來比想像中簡單。

先算爆不爆:深度 n + 1 = 100001,每層 96 bytes ⇒ 約 9.4 MB,超過 ulimit -s = 8176 KB。必爆。

迭代版:兩趟走訪,不遞迴。
unordered_map<Node*, Node*> m;
for (Node* p = head; p; p = p->next) m[p] = new Node(p->val);  // 第一趟:只建節點
for (Node* p = head; p; p = p->next) {
  m[p]->next   = m.count(p->next)   ? m[p->next]   : nullptr;
  m[p]->random = m.count(p->random) ? m[p->random] : nullptr;
}
return m.count(head) ? m[head] : nullptr;

為什麼變簡單了:第一趟結束後所有拷貝都已存在,第二趟接指標時不可能碰到「還沒建的節點」 —— 遞迴版之所以需要那個精巧的「先登記再遞迴」,正是為了處理這件事,而兩趟法直接把它繞開了。

實測:20 萬組隨機測資,結構錯 0、與原串列共用節點 0。時間仍是 O(n),空間是 O(n) 的 map(但沒有 O(n) 的堆疊)。

面試時這個版本其實更好講 —— 「先全部建好,再全部接線」比「記憶化遞迴」少一層心智負擔。
App 2. 可以 —— 把拷貝「織」進原串列,借原串列自己當那張表。

三趟走訪:
① 織入:在每個原節點後面插入它的拷貝,變成 A → a → B → b → C → c → …。
for (Node* p = head; p; ) { Node* c = new Node(p->val); c->next = p->next; p->next = c; p = c->next; }

② 接 random:關鍵的一行 —— 拷貝節點 a 就在 A 後面,所以 A.random 的拷貝就是 A.random->next。
for (Node* p = head; p; p = p->next->next) p->next->random = p->random ? p->random->next : nullptr;

③ 拆開:把兩條分離,並且把原串列還原。

核心洞察:「原節點 → 拷貝節點」的對應關係,不需要 hash map —— 用「緊鄰在後面」這個位置關係就能表達。這就是省掉 O(n) 空間的方法。

實測:20 萬組隨機測資,結構錯 0、共用節點 0,而且原串列在函式結束後完全還原。

取捨:額外空間 O(1),但三趟走訪、程式碼長一倍,而且第 ③ 步很容易寫錯(忘了還原原串列是最常見的)。面試時的順序應該是:先講記憶表版拿到正確答案,再說「如果要 O(1) 額外空間,可以把拷貝織進原串列」——而不是一開始就挑難的寫。
App 3. 可以,而且幾乎是逐行對應 —— 因為這題本來就是圖的深拷貝。

反過來看更有意思:138 其實是 133 的一個特例 —— 每個節點恰好有兩個「鄰居」(next 和 random),而且其中一個構成一條鏈。把它當成圖題來理解,比當成串列題容易得多。
