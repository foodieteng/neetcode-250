Hmm, let me think about this for a second.

A naive approach would check every substring's cost — O(n2) at best, too slow for 105.

This problem reminds me of a variable-length sliding window — grow always, shrink while invalid, track the max — where I just swap in a new validity rule. Grow r; while (r-l+1) - maxFreq > k, shrink from the left.

The most-frequent count maxFreq automatically picks the best letter to keep, so one pass covers all 26 letters. That's O(n).

I
INTERVIEWER

Do you recompute maxFreq when you shrink?

C
CANDIDATE

No — and that's the famous subtlety. I let maxFreq only ever increase. A stale, too-large maxFreq just makes the window "reluctant to shrink," so it slides at a fixed size. The window only stretches past that size when a real, larger count shows up in the current window, so the answer is never over-counted. That saves the O(26) recount on every shrink.

Alright, let me code this up. One loop over r: bump the letter's count and fold it into maxF in the same line, shrink while the replacements needed exceed k, then record the window length.

class Solution {
public:
    int characterReplacement(string s, int k) {
        unordered_map<char, int> freq;
        int maxL = 0, l = 0, n = s.size();
        int maxF = 0;                              // top letter count in the window (only grows)

        for (int r = 0; r < n; r++) {
            maxF = max(maxF, ++freq[s[r]]);          // expand + update the top count

            while (r - l + 1 - maxF > k) {            // replacements needed > k → invalid
                freq[s[l++]]--;                     // shrink from the left
            }

            maxL = max(maxL, r - l + 1);              // record the longest valid window
        }

        return maxL;
    }
};

The easy line to get wrong is the condition — it's (r-l+1) - maxF > k; flip either side and it breaks.

And since the window never shrinks below its best size, the while runs at most once per step, so it can be an if.
