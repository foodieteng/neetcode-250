On a sorted array, the distance to x is unimodal — it falls, then rises, like a V. So the k smallest distances cluster around the valley as one run.

If an optimal set skipped a middle element, that element is no farther than a chosen neighbor on the same side, so swapping it in never hurts. That means a contiguous optimum always exists.

Hmm, let me think about this for a second.

A naive approach would sort every number by distance, take the first k, and sort them again — O(n log n), and it ignores that the input is already sorted. Since the answer is a window, I only need to pick its left edge.

This problem reminds me of a shrink-from-both-ends window. Start with the whole array; while the window is bigger than k, drop whichever end is farther from x. That far end can't belong to the k closest, because everything inside is at least as close. That's n - k steps with O(1) extra space.

There's also a binary search on the left edge, which costs O(log(n − k) + k) and wins when k is small compared to n.

Three: return arr[l..r], which is already sorted.

class Solution {
public:
    vector<int> findClosestElements(vector<int>& arr, int k, int x) {
        int l = 0, r = arr.size() - 1;

        while (r - l + 1 > k) {                     // shrink until k remain
            if (abs(arr[r] - x) >= abs(arr[l] - x)) {
                r--;                                // right end farther (or tie) → drop right
            } else {
                l++;                                // left end farther → drop left
            }
        }

        return vector<int> (arr.begin() + l, arr.begin() + r + 1);  // k contiguous, already ascending
    }
};

Each loop step compares the two end distances and drops one end, until exactly k numbers remain. Then I return the slice from l to r — the end iterator is exclusive, so it's r + 1.

For the binary-search variant, I search the left edge, lo. At each mid, I compare x - arr[mid], the window's left end, with arr[mid + k] - x, the first number just past the window. If the left end is farther, the window moves right; otherwise it stays, so ties lean left.

// answer is a length-k contiguous window; left edge lo ∈ [0, n-k], binary-search lo
vector<int> findClosestElements(vector<int>& arr, int k, int x) {
    int lo = 0, hi = arr.size() - k;          // possible range of the left edge
    while (lo < hi) {
        int mid = (lo + hi) / 2;
        // which is farther from x: window's left end arr[mid], or the one just past it, arr[mid+k]
        if (x - arr[mid] > arr[mid + k] - x)  // left end farther → window moves right
            lo = mid + 1;
        else
            hi = mid;
    }
    return vector<int>(arr.begin() + lo, arr.begin() + lo + k);
}

One thing worth flagging — hi is n - k, not n - 1, which also keeps mid + k inside the array.

Corner case: x=-1, outside on the left. The right end is always farther, so it keeps dropping right, down to the leftmost k — no special case needed.

What breaks if you use > instead of >=?

On a tie, > falls to the else branch and drops the left, smaller end, keeping the larger one. That violates the rule that the smaller value wins on ties. The = is exactly the tie-break.

Let me think about complexity here.

// complexity
Shrink:        time O(n − k) + O(k) copy, extra space O(1) — result already sorted.
Binary search: O(log(n − k) + k) — locate the left edge, copy k.

The shrink version does one drop per step, so n - k steps, plus k to copy the answer, with O(1) extra space, and the result is already sorted. The binary search takes O(log(n − k)) to locate the left edge, plus k to copy.

Oh, one more thing — if the array weren't sorted, contiguity fails. Then I'd fall back to quickselect by distance, which is O(n) expected time, or a heap of size k.
