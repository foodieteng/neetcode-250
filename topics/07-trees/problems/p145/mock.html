Then here's the property I want on the table early, because it's the reason postorder exists at all.

In postorder, a node never comes out before its children — both subtrees are fully emitted first, so the root is always the very last value.

That's why postorder is the order you free a tree in, and the order for any bottom-up value like height, subtree sum, or subtree size. The children's answers are always ready before the parent needs them.

Here's the plan.

// invariant: postOrder(ans, x) appends exactly x's subtree,
// in postorder, to the end of ans. x lands LAST of that block.

postOrder(ans, x):
  if x is empty → return
  postOrder(ans, x.left)  // all of left
  postOrder(ans, x.right) // all of right
  ans.push_back(x.val)    // the node comes LAST

One: if the node is empty, return.
Two: recurse into the left child, then the right child.
Three: push the node's value last.

I'm using one shared vector<int> passed by reference, and each call appends only at the end, so its block stays in one piece.

One thing worth flagging — postorder is not the reverse of preorder. Preorder is node, left, right; reversing it gives right, left, node, but postorder is left, right, node. The correct identity: postorder equals the reverse of the node-right-left walk.

There's a trade-off here: that identity gives a short iterative solution with one stack, but it needs a reverse pass and a second explanation, and the plain recursion reads exactly like the definition. I'll go recursive.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> postorderTraversal(TreeNode* root) {
        vector<int> ans;
        postOrder(ans, root);
        return ans;
    }

    void postOrder(vector<int>& ans, TreeNode* root) {
        if (root == nullptr) return;   // the only base case

        postOrder(ans, root->left);     // ① the whole left subtree
        postOrder(ans, root->right);    // ② the whole right subtree
        ans.push_back(root->val);     // ③ both sides are back, now it's my turn
    }
};

The main function just calls the helper and returns the vector. The helper stops on nullptr, recurses left, recurses right, and only then pushes the value.

One thing worth flagging — the push sits after both calls, so every value is written on the way back up the stack. That's what makes this the right skeleton for any bottom-up computation: by the time that last line runs, both children are done.

Two details I'd keep as-is: the base case is the empty link, not a leaf check, which would crash on an empty tree and drop every leaf. And the & on ans is required, or each call fills a copy and a non-empty tree returns [].

Corner cases:

• Empty tree []: returns [] at once.
• Single node [1]: two empty calls, then push 1.
• [1,2,3] breaks the reverse-of-preorder idea: reversed preorder is [3,2,1], but true postorder is [2,3,1]. That false rule only holds on chains, where no node has two children.

Let me think about complexity here.

Time is O(n): exactly 2n + 1 calls, one per node plus one per empty link, since an n-node binary tree has exactly n + 1 empty links. Constant work per call.

Space is O(h) for the call stack, where h is the height; the output vector is O(n), but that's the answer itself.

In the worst case the tree is a chain, so h = n; a balanced tree is about log n. At 100 nodes neither is a problem.

Oh, one more thing — this version only reads the tree. But if I reused this skeleton to delete the tree, postorder is the safe order: in preorder I'd free a node and then read its child pointers, which is a use-after-free.
