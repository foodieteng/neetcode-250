Good, that greater-or-equal is going to matter later. Two things follow right away. The root is always good, because its path is just itself, so the answer is at least 1.

And here's what makes this cheap: I don't need the whole path, only one number from it — the maximum. "No larger value above me" is the same as "I'm at least as big as the largest value above me." So the path collapses into a single running max that I carry down.

Hmm, let me think about this for a second.

A naive approach would be to build, for each node, the full path from the root and scan it for a bigger value. That's O(h) per node, so O(n · h) — O(n²) on a chain, about 1010 operations at 105. Way too slow.

This problem reminds me of a top-down DFS that pushes information down the tree: each call inherits what it needs from its ancestors as a parameter. Here that's just one integer, the max seen so far. So it's a plain preorder DFS with one extra parameter.

P — plan
C
CANDIDATE

Here's the plan.

// mx = the largest value on the path above this node

good(node, mx):
  if node == null: return 0
  mx = max(mx, node.val)
  return (node.val >= mx)
       + good(node.left, mx)
       + good(node.right, mx)

One: an empty node contributes 0.
Two: update mx = max(mx, val), so mx is the largest value on the path including me.
Three: count 1 if val >= mx, then add both subtrees, passing the same mx down.

One thing worth flagging — I update before I test, which looks backwards. After the update, val >= mx_new exactly when val >= mx_old, so the two orderings agree — but only because the test is greater-or-equal. With a strict >, updating first makes the test always false, and the answer is 0 every time.

There's a trade-off here: I could carry the whole path, which generalizes to path follow-ups, but one integer is enough. Does this approach sound good, or would you rather I think of another way?

I — implement
C
CANDIDATE

Alright, let me code this up. It's three steps in order: update mx, compare myself with >=, and pass the same mx to both children.

class Solution {
public:
    int goodNodes(TreeNode* root, int mx = INT_MIN) {
        if (root == nullptr) return 0;

        mx = max(mx, root->val);          // ① update first (never decreases)

        return (int)(root->val >= mx)      // ② then compare self with >=
             + goodNodes(root->left, mx)    // ③ pass the same mx down
             + goodNodes(root->right, mx);
    }
};

One thing worth flagging — the INT_MIN sentinel. It's tempting to say it's safe because values only go down to -104, but the real reason is the >=: even a node holding INT_MIN leaves mx at INT_MIN and still counts.

Now, one thing I'm not happy about in my own code: the default argument. goodNodes is the public API, so a caller can write goodNodes(root, 5) — it compiles, and on the example it silently returns 1 instead of 4. In production I'd make the recursion a private helper, trading a silent bug for a loud one.

Corner cases:

• A null root returns 0 at the guard.
• A single node returns 1.
• A chain going down, [5,4,3,2,1], returns 1 — only the root.
• A tree of identical values returns n, since every comparison is a tie.

CANDIDATE

Let me think about complexity here.

Time is O(n) — each node is visited once with constant work. Space is O(h) for the recursion stack: about 17 frames on a balanced tree of 105 nodes, but 105 frames on a chain.

I measured that rather than guess: without optimization (-O0), on the default 8 MB stack, the crash point is about 130,000 frames, so the margin is only about 1.31×. Under a 1 MB stack (ulimit -s 1024), a 105-node chain segfaults.

Oh, one more thing — so the honest answer to "is this safe" is: it depends on the environment. Where I don't control the stack size, I'd rewrite it with an explicit stack of (node, max) pairs on the heap.
