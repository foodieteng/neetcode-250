題目簡介// THE QUESTION

QUESTION

一個節點 X 叫做「good」,如果從根到 X 的路徑上, 沒有任何節點的值大於 X。回傳 good 節點的數量。
節點數 1 ~ 10⁵,值 −10⁴ ~ 10⁴。

本章大部分的樹題是「由下往上」聚合(104 深度、 543 直徑)—— 這一題相反:它是「由上往下」帶狀態。

核心:沿路帶一個 mx,代表「從根走到我這條路上的最大值」。 每個節點只問一句:「我 >= mx 嗎?」 而 mx 只增不減 —— 遇到比較小的節點它不會被拉低, 所以它記住的永遠是「路上最大的那個」。
2

為什麼是 >= 而不是 >// WHY THIS

A 用 >(以為要「嚴格最大」) 全盤歸零
在「先更新再比」的寫法裡,> 永遠為假 —— 因為 mx 已經包含自己,root->val > max(mx, root->val) 不可能成立。 答案會變成 0。
× REJECT · 恆為假
B 對每個節點各自往上爬一次查路徑 O(n·h)
答案會對,但每個節點都要重走一次它的祖先鏈。 退化成鏈時就是 O(n²) —— 而 n 上限是 10⁵,那是 100 億次操作。
△ 對但太慢
ADOPT
C 把 mx 當參數往下傳,用 >= 比 O(n) 時間 · O(h) 空間
祖先鏈的資訊「已經在參數裡」了,不必重走。 而 >= 讓「平手」也算 good —— 因為題目說的是「沒有人大於我」,不是「我最大」。
● ADOPT · 一趟走完
⚡ 「平手也算」是這題最容易漏的地方。 範例 1 的答案之所以是 4 而不是 3,就是因為有一個節點剛好等於路徑最大值 (路徑 3 → 1 → 3 的那個 3)。 題目問的是「有沒有人比我大」,平手的人沒有比我大 —— 所以我仍然看得到。
3

核心策略 · 三步驟// THE SHAPE

  1. 更新:mx = max(mx, root->val); —— mx 只增不減。
  2. 判斷自己:(int)(root->val >= mx) —— 更新之後 mx 已含自己,所以這等價於「和舊的 mx 比」(見 LEMMA 1)。
  3. 往下傳:左右子樹都收到同一個更新後的 mx, 把三個數字加起來回傳。
注意這題的遞迴回傳的是數字,不是節點 —— 所以沒有 701、450 那個「回寫接線」的問題。 它的狀態是「往下傳」的參數,不是「往上傳」的回傳值。

兩個一定會被問到的「為什麼」// TWO LEMMAS

LEMMA 1 · 「先更新再比」和「先比再更新」為什麼等價

課本寫法是先比再更新:good = (val >= mx); nmx = max(mx, val);。 你的寫法是先更新再比。為什麼一樣?

更新後的 mx 只有兩種可能:
· 舊 mx 贏(val <= 舊mx)⇒ mx 沒變 ⇒ 測試就字面上等於 val >= 舊mx —— 和課本版一模一樣。
· val 贏(val > 舊mx)⇒ mx == val ⇒ 測試是 val >= val,恆為真 —— 而這個分支發生的條件正是 val > 舊mx,課本版同樣判它 good。
兩個分支都一致 ⇒ 等價。 實測:窮舉 1042 萬組(所有 n≤8 樹形 × {0,1,2} 全部賦值) + 隨機 20 萬組,零不一致。
⚡ 但這個等價依賴 >= —— 如果寫成 >,「先更新再比」會讓每個節點都判不是 good(答案恆為 0), 而「先比再更新」只是漏掉平手。所以 >= 在這個寫法裡是結構性的,不是風格選擇。

LEMMA 2 · ⚠ 預設參數把「內部狀態」暴露成了 public API

int goodNodes(TreeNode* root, int mx = INT_MIN) —— 很聰明, 省掉了一個 private helper。但那個 mx 現在是公開參數, 呼叫端可以傳。

實測:對範例 1 的樹,
· goodNodes(root) → 4 ✓(LeetCode 的呼叫方式)
· goodNodes(root, 5) → 1 ✗ —— 安靜地給出錯的答案,不會報錯、編譯全過。
而私有 helper 的設計讓這件事「根本寫不出來」 —— goodNodes(root, 5) 會是編譯錯誤,不是執行期的錯答案。
兩者在 1062 萬組正確性測試上完全相同,差別純粹在「呼叫端能不能弄壞它」。
(同樣的問題 98 驗證 BST 也有 —— 那題的 isValidBST(root, 0, 10) 會把一棵合法 BST 判成 false。)

// INT_MIN 當哨兵安不安全?(實測) 題目值域是 [-10^4, 10^4],所以 INT_MIN 永遠比任何節點小 ⇒ 安全 實測 [-10000,-10000,-9999](root 恰好是值域下界)→ 3,正確 超出約束的壓力測試(root 的值「就是」INT_MIN): [INT_MIN, INT_MIN, 0] → 3,root「仍然」被算成 good 原因:mx = max(INT_MIN, INT_MIN) = INT_MIN,而 INT_MIN >= INT_MIN 成立 ⚡ 如果寫成 >,root 會判自己不是 good,答案就錯了 ⇒ 是「>=」讓 INT_MIN 當哨兵是安全的,不是 INT_MIN 這個值本身 // 又一次:>= 不是風格,它同時撐住了「平手」和「哨兵撞值」兩件事

這題的堆疊餘裕(1.31 倍)是全章最小的 —— 因為它的 n 上限 10⁵ 也是全章最大。 在預設 8 MB 上安全,但在 1 MB 的環境就會 SIGSEGV。 要一個與環境無關的保證,就改用迭代(顯式 stack 或 BFS) —— 那樣「深度」這個煩惱就整個消失了。

一句洞察// INSIGHT

「由上往下帶狀態」和「由下往上聚合」是樹遞迴的兩個方向 —— 這題是前者:祖先的資訊放在參數裡往下傳,所以不必重走祖先鏈。
而 >= 不是風格選擇,它同時撐住了兩件事: 「平手也算 good」(題目問的是「有沒有人大於我」), 以及「INT_MIN 哨兵撞上合法值時不會出錯」。
