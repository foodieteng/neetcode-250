完整實作// TOP-DOWN STATE

p1448.cpp C++17 
class Solution {
public:
    int goodNodes(TreeNode* root, int mx = INT_MIN) {
        if (root == nullptr) return 0;

        mx = max(mx, root->val);          // ① 先更新(只增不減)

        return (int)(root->val >= mx)      // ② 再用 >= 比自己
             + goodNodes(root->left, mx)    // ③ 同一個 mx 往下傳
             + goodNodes(root->right, mx);
    }
};

🎤 面試模擬 · UMPIRE mock interview transcript ↗

三行做三件事,而且順序不能隨便換: ① 更新 → ② 比較 → ③ 傳下去。 如果把 ① 和 ② 對調(先比再更新),答案仍然正確(那是課本寫法)—— 但如果保持這個順序卻把 >= 改成 >,答案會恆為 0。 見下方走讀 PHASE 1。

邊界與陷阱// PITFALLS

陷阱症狀實測
保持「先更新」卻改成 > 答案恆為 0 範例 1 → 0(正解 4)
以為「good = 我最大」而用 > 漏掉所有平手的節點 範例 1 的 D(3) 會被漏掉
呼叫端傳了第二個參數 安靜答錯,不報錯 goodNodes(root, 5) → 1(正解 4)
對每個節點各自往上爬查路徑 退化鏈時 O(n²) n=10⁵ ⇒ 約 100 億次操作
mx 用 int 而值域更大時 哨兵可能撞值 本題安全(值域 ±10⁴);但靠的是 >=
前兩列其實是同一個誤解的兩種後果 —— 「good」被讀成「我是路上最大的」。 但題目說的是「沒有節點大於我」, 平手的節點沒有大於我 ⇒ 我仍然算 good。 實測:全部相等的 [5,5,5,5,5,5,5] 答案是 7(全部),不是 1。

細節走讀// LINE BY LINE

// PHASE 1: 「先更新再比」和「先比再更新」為什麼等價 —— 而且為什麼只在 >= 下等價 課本寫法(先比再更新): int good = (root->val >= mx) ? 1 : 0; int nmx = max(mx, root->val); 你的寫法(先更新再比): mx = max(mx, root->val); ... (root->val >= mx) ... 更新後的 mx 只有兩種可能,逐一檢查: ① 舊 mx 贏(root->val <= 舊mx) mx 沒變 ⇒ 測試字面上就是 root->val >= 舊mx ⇒ 和課本版「完全相同」 ② root->val 贏(root->val > 舊mx) mx == root->val ⇒ 測試是 root->val >= root->val ⇒ 恆為真 而這個分支發生的條件正是 root->val > 舊mx ⇒ 課本版也判它 good ⇒ 一致 兩個分支都一致 ⇒ 等價 實測:窮舉 10428178 組 + 隨機 200000 組,不一致 0 ⚡ 但把 >= 換成 > 就會爆炸: 更新後 mx >= root->val 恆成立 ⇒ root->val > mx 「永遠為假」 ⇒ 答案恆為 0(實測範例 1 給 0,正解 4) // 所以 >= 在這個寫法裡是結構性的:它讓「自己和自己比」這件事成立
// PHASE 2: mx「只增不減」是什麼意思 mx = max(mx, root->val) —— 這一行「不可能讓 mx 變小」 所以沿著任何一條根到節點的路徑,mx 的序列是「不遞減」的: 範例 1 的左路徑 A(3) → B(1) → D(3) A: mx = max(INT_MIN, 3) = 3 B: mx = max(3, 1) = 3 ← 沒被 1 拉低 D: mx = max(3, 3) = 3 這正是「路徑最大值」的定義 —— 它記住的是「路上最大的」,不是「上一個」。 ⚠ 常見錯誤:傳 root->val 而不是 max(mx, root->val) 那會變成「只和父節點比」,而不是「和整條路徑比」 —— 和 98 那題「只比父節點」是同一類錯誤 // 這題和 98 的共同點:祖先的約束必須「一路帶下去」,不能只看上一層
// PHASE 3: 預設參數的代價(實測) int goodNodes(TreeNode* root, int mx = INT_MIN) ~~~~~~~~~~~~~~~~ 這是 public API 的一部分 LeetCode 只會呼叫 goodNodes(root),所以線上沒問題。 但這個簽名「邀請」呼叫端傳第二個參數: 實測(範例 1 的樹): goodNodes(root) → 4 ✓ goodNodes(root, 5) → 1 ✗ 安靜答錯,編譯全過、零警告 私有 helper 的設計: public: int goodNodes(TreeNode* root); ← 只有一個參數 private: int dfs(TreeNode* root, int mx); ⇒ goodNodes(root, 5) 變成「編譯錯誤」,而不是「執行期錯答案」 兩者在 1062 萬組正確性測試上「完全相同」 差別純粹在:呼叫端能不能不小心弄壞它 // 同樣的問題 98 也有:isValidBST(root, 0, 10) 會把合法 BST 判成 false
// PHASE 4: INT_MIN 當哨兵,為什麼安全(以及靠什麼安全) 題目值域 [-10^4, 10^4] ⇒ INT_MIN 永遠嚴格小於任何節點值 ⇒ 哨兵不會撞值 實測 [-10000,-10000,-9999](root 恰在值域下界)→ 3,正確 超出約束的壓力測試(root 的值「就是」INT_MIN): [INT_MIN, INT_MIN, 0] → 3,root 仍被算成 good mx = max(INT_MIN, INT_MIN) = INT_MIN INT_MIN >= INT_MIN 成立 ⇒ good ✓ 但如果寫成 > : [INT_MIN, INT_MIN, 0] → 0,連 root 都判不是 good ✗ ⇒ 讓 INT_MIN 當哨兵安全的「不是 INT_MIN 這個值」,而是「>=」 對照 98 那題:那題值域吃滿整個 int,連 >= 都救不了,只能把型別抬到 long long // 同樣是哨兵問題,98 必須換型別,這題用 >= 就夠 —— 差別在值域有沒有吃滿

// ONE-LINE TAKEAWAY
順序是「更新 → 比較 → 傳下去」,而 >= 是結構性的:保持這個順序改成 > 會讓答案恆為 0(實測範例 1 給 0)。mx 只增不減,記住的是「路上最大的」不是「上一個」—— 傳 root->val 就退化成 98 那題「只比父節點」的錯誤。
