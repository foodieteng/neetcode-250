A naive approach would be to handle each node shape by hand: a leaf, only a left child, only a right child, both. That's four cases per node, and every one is a place to get it wrong — and it doesn't get faster, just longer.

This problem reminds me of a plain depth-first search on a tree. The definition of inorder is already recursive — left, node, right — so the code can be a direct copy of the definition.

Here's the plan.

// invariant: inorder(ans, x) appends exactly the values of
// x's subtree, in inorder, to the end of ans.

inorder(ans, x):
  if x is empty → do nothing, return
  inorder(ans, x.left)   // left subtree
  ans.push_back(x.val)   // the node
  inorder(ans, x.right)  // right subtree

One: if the node is empty, return.
Two: recurse into the left subtree.
Three: push the node's value, then recurse into the right subtree.

One shared vector<int> holds the answer; each call only appends to its end.

One thing worth flagging — the empty check isn't a speed guard, it's the base case. If I wrote the floor as a leaf check instead, two things break: an empty tree crashes reading root->left, and every leaf returns before its push, so leaf values are silently dropped.

An explicit stack would avoid recursion, but with 100 nodes the call stack isn't a risk. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> inorderTraversal(TreeNode* root) {
        vector<int> ans;
        inorder(ans, root);
        return ans;
    }

    void inorder(vector<int>& ans, TreeNode* root) {
        if (root == nullptr) return;   // the only stopping condition

        inorder(ans, root->left);       // 1. left: finish the whole left subtree first
        ans.push_back(root->val);     // 2. node: in the middle = "in"-order
        inorder(ans, root->right);      // 3. right
    }
};

The public function creates the answer vector, calls the helper on the root, and returns it. The helper is three lines after the null check — left, push, right — matching the plan line for line.

One thing worth flagging — the & in vector<int>& ans is a correctness detail, not a speed detail. Drop it and every call gets its own private copy: the pushes land in that copy, the copy dies at the end of the call, and the outer ans is never touched. So every non-empty tree would return [], while the empty tree still passes — exactly the kind of bug that looks fine on the first test.

Corner cases:

• Empty tree [] → returns [] at once.
• Single node [1] → gives [1], with no leaf case anywhere.
• Left chain [3,2,null,1] → pushes on the way back up, giving [1,2,3], the deepest shape.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time is O(n), and exactly so: every node and every empty link is entered once. A tree with n nodes has n + 1 empty links — 2n child slots, and n − 1 hold a real node. So it's exactly 2n + 1 calls, whatever the shape: 7 in our run.

Space is O(h) for the call stack, where h is the height. The output vector is the answer itself, so I don't count it as extra.

Worst case is a chain, where h = n. At 100 nodes that's fine; at a million, the chain would overflow the stack, and I'd switch to an explicit stack.

Oh, one more thing — the traversal never writes to the tree, so it's safe to rerun.
