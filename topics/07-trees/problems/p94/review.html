重點回顧// RECAP

面向要記住的那一句
本質中序 = 左 → 根 → 右,push_back 夾在兩個遞迴中間
核心直覺「被走到」和「被收錄」是兩個時刻,中間隔著整棵左子樹
第一個元素永遠是一路往左走到底的那個節點
根的位置下標 = 左子樹的節點數(這是 105 題重建二元樹的基礎)
終止條件root == nullptr,不是「是不是葉節點」—— 後者 197 種樹形全錯
ans 的 &是正確性不是效能。少了它,任何非空樹都回空陣列
呼叫次數恆為 2n + 1(n 實節點 + n+1 個 nullptr),與樹形無關
複雜度時間 O(n),空間 O(h) —— 是樹高不是節點數
實測堆疊每層 96 bytes;崩潰臨界 87150 層,n=100 有 871 倍餘裕
最陰險的錯前序/後序寫反,在斜鏈上會碰巧全對 —— 單筆測資測不出來

觀念題// CONCEPT Q&A

Q1. 終止條件為什麼寫 root == nullptr,而不是「如果是葉節點就 return」?後者看起來更早停、更有效率。請說出實際會發生什麼。
Q2. void inorder(vector<int>& ans, ...) 的那個 &,是為了效能還是為了正確性?如果拿掉,症狀是什麼?
Q3. 有人說「中序走訪就是把樹裡的值由小到大排出來」。這句話什麼時候對、什麼時候錯?
Q4. 這題空間複雜度是 O(h) 還是 O(n)?兩者什麼時候一樣?請給實測數字。
Q5. 你把前序和中序寫反了,但用 [1,null,2,null,3](純右鏈)測試卻通過了。為什麼?這告訴你關於測資設計的什麼事?

範例 Trace// [1,null,2,3] → [1,3,2]

用官方範例的小樹:根 1,沒有左子樹,右子樹是 2,而 2 的左子樹是 3。 縮排 = 遞迴深度。以下每一步都是實跑印出來的,不是手推。

// 進入根節點 1 ans = [] → inorder(1) 1 非 null,先遞迴 LEFT → inorder(1->left = null) root == nullptr → return ans = [] ★ push_back(1) ans = [1] // 1 沒有左子樹,所以它「立刻」就被收錄 —— 不用等
// 1 的第三行:進入右子樹 2 → inorder(1->right = 2) 2 非 null,先遞迴 LEFT → inorder(2->left = 3) 3 非 null,先遞迴 LEFT → inorder(3->left = null) return ans = [1] ★ push_back(3) ans = [1,3] → inorder(3->right = null) return ans = [1,3] 節點 3 結束,return // 2 一直在等 —— 它的左子樹(3)整棵做完,才輪到它
// 回到 2,再回到 1 ★ push_back(2) ans = [1,3,2] → inorder(2->right = null) return ans = [1,3,2] 節點 2 結束,return 節點 1 結束,return
// OUTPUT return ans = [1,3,2] 統計:8 次 inorder() 進入(3 個實節點 + 5 個 nullptr = 2n+1 = 2×3+1 ✓) 3 次 push_back 最大遞迴深度 4 // [1,3,2] —— 注意 3 排在 2 前面,因為 3 是 2 的左子樹
這棵小樹剛好示範了兩種極端:節點 1 沒有左子樹,所以走到就收錄; 節點 2 有左子樹,所以要等。 整個中序走訪,就是這兩種情況不斷重複而已。

應用題// APPLICATION

App 1. 改用顯式 std::stack 寫,不准用遞迴(這題最常見的追問)。請說出骨架,以及最難的那一步是什麼。
App 2. 給你一棵 BST,要找第 k 小的元素(LeetCode 230)。怎麼用這題的程式碼改?能不能不走完整棵樹?
App 3. 節點數放大到 10⁵,而且測資裡有退化成一條鏈的樹。這份遞迴會怎樣?請給實測依據,並說出你會怎麼改。
// ANSWERS
A1. 寫成葉節點判斷會「同時」犯兩個病,實測 197 種樹形全錯。

病一:崩潰。if (root->left == nullptr && root->right == nullptr) 這一行本身就在解參考 root。空樹 [] 傳進來,root 就是 nullptr,當場 SIGSEGV。而且不只空樹 —— 任何有「單邊子節點」的節點,遞迴進那個 nullptr 子樹時同樣爆炸。

病二:漏收。就算形狀剛好躲過崩潰(例如完美二元樹),葉節點在 push_back 之前就 return 了 —— 所有葉節點都被吞掉。實測 [1] 回 []。

「用 nullptr 當底」的價值就在這裡:葉節點不需要任何特殊待遇。它的左右各進去一層、各自立刻 return,然後它照常被 push_back —— 程式碼裡根本沒有「這是葉節點嗎」這種判斷,少一個分支就少一個寫錯的地方。
A2. 是正確性,不是效能。

少了 &,每一層拿到的是 ans 的一份拷貝。push_back 寫進拷貝,那一層 return 時拷貝連同寫進去的東西一起消失。最外層那個 ans 從頭到尾沒有被寫過。

症狀非常好認:任何非空樹都回空陣列。實測窮舉 197 種樹形錯 196 種,最小反例 [1] → [];唯一「對」的是空樹 [],因為答案本來就是空的。

除錯口訣:看到「答案永遠是空的」,先去看 helper 的簽名有沒有 &。(順帶一提,傳值也很慢 —— 每層複製整個 vector 會讓複雜度變成 O(n²) —— 但那是附帶傷害,主要問題是它根本不對。)
A3. 只有對 BST 才對;對一般二元樹完全錯。

BST 的定義是「左子樹所有值 < 根 < 右子樹所有值」。中序走訪剛好是「左 → 根 → 右」,所以對 BST 而言中序輸出必定遞增 —— 這是一個非常有用的性質(第 98 題「驗證 BST」、第 230 題「第 k 小」用的都是它)。

但這題沒說是 BST。一般二元樹的中序和值的大小毫無關係,它是位置決定的順序。實測本頁的範例樹輸出是 [4,2,6,5,7,1,3,9,8] —— 一點都不遞增。

這是這題最常見的觀念混淆:把「中序」和「排序」畫上等號。正確的說法是:中序是一種走訪順序;BST 的中序碰巧是遞增的。因果不能反過來。

順帶一提,如果真的把這題當排序做(壓平後 sort),不只複雜度變 O(n log n),答案在非 BST 上根本是錯的。
A4. 是 O(h);當樹退化成一條鏈時,h = n,兩者才一樣。

呼叫堆疊在任一瞬間只裝著「從根到目前節點」那一條路徑上的框,所以最深就是樹高(再加最底那層 nullptr)。

實測(同樣是 100 個節點):
· 退化成一條鏈 → 最大遞迴深度 101,堆疊約 9.7 KB
· 完美平衡樹 → 樹高只有 7,深度 8
同樣的 n,堆疊用量差了十幾倍。

每層實測固定 96 bytes(clean build,用 n=10000 的鏈量出 960000 bytes 除得)。系統 ulimit -s = 8176 KB,二分實測 87149 層存活、87150 層 SIGSEGV,回推 96.07 bytes/層,與量到的相符。

所以本題(n ≤ 100)遞迴有 871 倍餘裕,絕對安全。但「O(h),最壞退化成 O(n)」這句話要說完整 —— 只說 O(log n) 是默默假設了樹是平衡的,而題目沒有給這個保證。
A5. 因為純右鏈是前序和中序「碰巧相等」的唯一一族。

純右鏈上,每個節點的左子樹都是空的。中序的第一行 inorder(root->left) 變成 no-op,於是「左 → 根 → 右」退化成「根 → 右」 —— 那正是前序。

實測:窮舉 n = 0..8 全部 2056 種樹形,前序輸出等於中序輸出的每個 n 恰好只有 1 種,而且100% 都是純右鏈,無一例外。對稱地,後序寫成中序在純左鏈上也會碰巧全對。

關於測資設計,這件事的教訓是:
① 斜鏈是「退化」測資,不是「極端」測資。它讓左右不對稱的 bug 全部隱形 —— 因為根本沒有左右可比。
② 能區分三種走訪的最小樹,是有「左右都非空」的節點的樹。最小的是 [1,2,3]:前序 [1,2,3]、中序 [2,1,3]、後序 [2,3,1] —— 三個都不一樣。
③ 所以本頁所有陷阱表都是窮舉 197 種樹形跑出來的,而不是幾筆手寫測資。「我測過了」和「我窮舉過了」差很多。

面試現場的版本:自己舉例時,永遠先舉 [1,2,3],不要舉斜鏈。
App 1. 骨架:一路往左壓進 stack → 彈出即收錄 → 轉向右子樹。

vector<int> ans;
stack<TreeNode*> st;
TreeNode* curr = root;
while (curr != nullptr || !st.empty()) {
    while (curr != nullptr) {      // ① 一路往左壓到底
        st.push(curr);
        curr = curr->left;
    }
    curr = st.top(); st.pop();     // ② 彈出 = 它的左邊做完了
    ans.push_back(curr->val);
    curr = curr->right;            // ③ 轉向右子樹
}
最難的那一步是 ②。遞迴版裡,「這個節點的左子樹做完了沒」是由呼叫堆疊自動回答的 —— 函式 return 回來,就代表做完了。顯式版沒有人幫你記這件事,你得自己設計一個規則。

這裡的規則很漂亮:一個節點被 pop 出來的那一刻,就代表它的左子樹已經處理完。因為 ① 把它壓進去之後,只會繼續往更左邊壓;那些更左的節點一定比它先被 pop(stack 是後進先出)。所以「pop 出來」就等價於遞迴版的「左邊那個呼叫 return 了」。

複雜度不變:時間 O(n)(每個節點恰好進出 stack 一次),空間 O(h) —— 只是把「編譯器管的堆疊」換成「你自己管的堆疊」,那個 O(h) 一分都沒省。真正 O(1) 空間的走訪要用 Morris(把葉節點的空指標暫時接成「線索」),但那會暫時改動樹的結構,是另一個層次的題目。
App 2. 用「BST 的中序是遞增的」這個性質,而且可以提早停 —— 這正是 230 題。

既然 BST 的中序輸出必定遞增,那第 k 小就是中序的第 k 個。所以最直接的作法:跑這題的程式碼,回傳 ans[k-1]。

但可以不走完整棵樹。把 ans 換成一個計數器,在 push_back 那個位置改成:
inorder(root->left);
if (++count == k) { result = root->val; return; }   // 找到就記下
inorder(root->right);
再加上「已經找到就不要再往下走」的剪枝(每次進入函式先檢查 count >= k 就 return),時間就從 O(n) 降成 O(h + k) —— 只走到第 k 個就停。

值得注意的是:改的地方仍然是「push_back 的那個位置」。「在中序的第 ② 步做事」這個模式,在 BST 題裡會一直出現 —— 98 題驗證 BST 是在那裡比較「有沒有比前一個大」,230 題是在那裡數數。換句話說,你學的不是一題,是一個插槽。

顯式 stack 版更適合這題,因為「提早停」在迭代裡就是一個 break,不必處理遞迴的層層 return。
App 3. 退化鏈 + 10⁵ 節點,深度就是 10⁵ —— 在這台機器上還撐得住,但餘裕已經不大,而且會因環境而異。

實測數字:每層 96 bytes,系統 ulimit -s = 8176 KB,二分實測崩潰臨界 87150 層。
→ 10⁵ = 100000 層 > 87150,在這台機器的預設堆疊上,退化鏈的 10⁵ 會直接 stack overflow。

而且這個數字不可移植。崩潰臨界完全取決於 ulimit -s 和每層的 frame 大小,而 frame 大小又取決於編譯器和最佳化等級(本頁 instrumented build 量到 112 bytes/層、clean build 是 96)。「在我機器上跑得過」對這類問題不是證據。

我會怎麼改 —— 換成 App 1 的顯式 std::stack 版。理由:
① std::stack 的儲存在堆積(heap)上,不是呼叫堆疊,heap 的上限大得多(通常是可用記憶體,不是 8 MB)。
② 空間複雜度還是 O(h) —— 一分都沒省 —— 但它不會 stack overflow。這是「同樣的複雜度、不同的失敗模式」的典型例子。
③ 程式碼長一點,但不會因為換一台機器就掛掉。

面試時的說法:「遞迴版在 n ≤ 100 完全沒問題,我量過有 871 倍餘裕;但如果 n 到 10⁵ 而且樹可能退化,我會改寫成顯式 stack,因為呼叫堆疊有硬上限而 heap 沒有。」—— 給出臨界值,比說「遞迴比較耗空間」有說服力得多。
