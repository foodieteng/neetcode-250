Hmm, let me think about this for a sec.

A naive approach would be to read every value into a sorted list, drop the key, and rebuild a whole new BST. That is O(n) time, but it throws away the tree and does not reuse a single node.

This problem reminds me of a plain BST search, with one extra step at the end. The search is easy: compare with key, go left or right.

The trick is the in-order successor — the smallest value still bigger than the node, which is the leftmost node of the right subtree. Put that value into the spot and the BST rule holds. Then I delete the successor node instead. And the successor has no left child — that is what leftmost means — so that second delete always lands in the easy case.

Here's the plan.

// deleteNode(root, key) returns the new root of this subtree
root == null   → return null // key not here
root->val > key → recurse left, re-attach
root->val < key → recurse right, re-attach

// found it
0 or 1 child → return the child (or null)
2 children  → succ = leftmost of right subtree
               swap(root->val, succ->val)
               delete key from the right subtree

One: if the node is null, return null.
Two: if key is smaller or bigger, recurse into that side and store the returned root back.
Three: on a hit, zero or one child returns that child; two children finds the successor, swaps the values, and deletes key from the right subtree.

One thing worth flagging — I use swap, not a copy, so for a moment the right subtree is not a valid BST. It is still safe: the broken node is where the search ends, never a place where it makes a choice. Every node on the way is bigger than key, so I go left straight to it.

There's a trade-off here. The copy version stays valid throughout, but both give the exact same tree in every test I ran.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    TreeNode* deleteNode(TreeNode* root, int key) {
        if (root == nullptr) {
            return root;                  // key not present: do nothing
        }

        if (root->val > key) {
            root->left = deleteNode(root->left, key);
        } else if (root->val < key) {
            root->right = deleteNode(root->right, key);
        } else {
            // 0 or 1 child: hand the only child (or nullptr) up to the parent
            if (!root->left || !root->right) {
                return root->left ? root->left : root->right;
            }

            // two children: in-order successor = right subtree, then all the way left
            TreeNode* succ = root->right;
            while (succ->left) {
                succ = succ->left;
            }

            swap(root->val, succ->val);   // key moves into succ's spot
            root->right = deleteNode(root->right, key);
        }

        return root;
    }
};

The search branches recurse and store the returned root back into the child. On a hit, zero or one child returns whichever child exists. Two children walks to the leftmost node of the right subtree, swaps values, and deletes key from the right subtree.

One thing worth flagging — the one-child line. return root->left ? root->left : root->right; looks like it prefers the left on purpose. It does not. That line only runs when at most one child exists, so one of the two is always null. Writing it the other way round gives the same node — 0 differences over 19633 tree-and-key pairs. So it is not a trap. The real bug would be putting that line before the two-child check.

The time complexity is O(h), where h is the height. The space complexity is also O(h), from the recursion stack.

Let me think about complexity here. The two-child case does extra work, but not extra order — the successor walk and the second descent follow the same path, so the constant is about two: a thousand-node left chain gives 999 steps and 1001 calls.

In the worst-case scenario the tree is a straight chain, so it is O(n) time and O(n) stack — deep, but fine at 104.

Oh, one more thing — this rewrites values in place. If the caller kept a pointer to the node that held 3, it now reads 4. The copy version has the same issue; if pointers must stay meaningful, I would re-link nodes instead.
