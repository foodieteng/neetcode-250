重點回顧// RECAP

面向要記住的那一句
三種情況沒找到 → 往下;0/1 個小孩 → 直接接上去;兩個小孩 → 找替身
替身是誰中序後繼(右子樹一路往左)或前繼(左子樹一路往右)
為什麼只有這兩個要滿足 max(L) < v < min(R),而空隙的兩個端點就只有它們
為什麼不會無限遞迴後繼必定沒有左小孩 ⇒ 第二次刪除必落在簡單情況
swap 的暫時違反壞掉的節點是搜尋終點而非決策點 —— 實測 2652/2652 全程往左
swap vs copy產生的樹完全相同(19633 組 + 20 萬組隨機,零差異)
被摘掉的是誰持有 key 的那個節點 —— 實測 15521/15521,零例外
成本O(h) 但常數是 2(找後繼 + 遞迴刪,走同一條路)
回寫同樣必要,但失敗率只有 72.7%(701 是 99.98%)—— 更難被測到
假陷阱單子分支三元運算子寫反 → 完全等價,0/19633,別背成錯的

範例 Trace// 兩組:後繼在隔壁 vs 後繼很深

兩組都是實跑印出來的。 第一組是官方範例(後繼剛好是右小孩); 第二組刻意讓後繼「深 2 層」,才看得出「一路往左」那件事。

// A · 官方範例 [5,3,6,2,4,null,7] 刪 key=3(後繼就是右小孩) 1. deleteNode(node5, 3) 5 > 3 → 往左 2. deleteNode(node3, 3) 3 == 3 → MATCH 左 = node2 ✓、右 = node4 ✓ → 兩個小孩,要找替身 succ = node3->right = node4; node4->left == null → while 一步都沒走(0 步) SWAP: node3.val 3 ↔ node4.val 4 → node3 現在是 4、node4 現在是 3(key 被換下去) 3. deleteNode(node4, 3) node4 現在的值就是 3 → MATCH node4->left == null → 回傳 node4->right = nullptr ← 回寫:node3->right = nullptr ★ node4 在此被摘除 ← 回寫:node5->left = node3 結果 [5,4,6,2,null,null,7] calls = 3,後繼步數 = 0 // 注意:被丟掉的是「原本的 node4 物件」,而它被丟掉時身上寫的是 3(= key)
// B · 後繼較深:[10,5,15,null,null,13,20](13 的左子是 12)刪 key=10 1. deleteNode(node10, 10) 10 == 10 → MATCH,兩個小孩 找後繼:從右子樹根 15 出發一路往左 15 → 13 → 12 (走了 2 步) SWAP: root 10 ↔ succ 12 → 根現在是 12、而 key=10 被換到「最左節點」那個位置 ⚠ 此刻右子樹「暫時」不是合法 BST:10 比右子樹所有值都小,卻待在最深的左下角 2. deleteNode(node15, 10) 15 > 10 → 往左 ← 判「往左」 3. deleteNode(node13, 10) 13 > 10 → 往左 ← 又是「往左」 4. deleteNode(node12', 10) 它現在的值是 10 → MATCH 它是最左節點 ⇒ 沒有左小孩 ⇒ 回傳它的右小孩(nullptr) ← 回寫:node13->left = nullptr ★ 在此被摘除 結果 [12,5,15,13,20] calls = 4,後繼步數 = 2 // 下降的每一步都判「往左」—— 而那條全左的路,正好就是通往最左節點的路
B 組把整題的關鍵講完了: 「找後繼」走的路(15 → 13 → 12)和「回頭刪它」走的路(15 → 13 → 10)是同一條 —— 這既解釋了為什麼成本是 2h,也解釋了為什麼那個暫時的 BST 違反傷不到遞迴。

// ANSWERS
A1. 因為替身必須「剛好卡在兩棵子樹中間」,而滿足這個條件的值只有兩個。

被刪節點 X 有左子樹 L、右子樹 R。頂替它的值 v 必須滿足:
L 裡所有值 < v < R 裡所有值

原本 max(L) < X < min(R),X 被拿掉之後,那個空隙的兩個端點就只有:
· max(L) = 中序前繼(比 X 小的裡面最大的)
· min(R) = 中序後繼(比 X 大的裡面最小的)
其他任何值都會破壞順序。

「隨便挑一個小孩頂上來」為什麼不行:假設把左小孩頂上來,那右子樹整棵就沒地方掛了 —— 它比左小孩大,不能當它的左子樹;當右子樹又會蓋掉左小孩原有的右子樹。兩棵子樹都要保住,就只剩那兩個端點可選。

實測:前繼版和後繼版都正確(這也是題目說「答案可能不只一種」的原因)。但方向要配對 —— 選了前繼卻仍往右遞迴刪,兩子家族的 2652 組全數錯光。
A2. 因為壞掉的那個節點是搜尋的「終點」,而不是路上任何一個「岔路的決策點」。

論證:設後繼是 S(右子樹 Rt 的最左節點,值 m)。swap 之後:
· X->val = m —— m 是 Rt 的最小值且大於整棵左子樹,所以根這裡的 BST 性質仍然成立。
· S->val = key —— key 比 Rt 裡所有其他值都小,所以 Rt 暫時違反 BST,而且違反點只有 S 這一個。

現在看下降過程。對路徑上任何一個非 S 的節點 p:
p->val 完全沒被動過,而且 p->val > m > key ⇒ 判「往左」。
而這一路的 LEFT,正好就是通往最左節點 S 的那條路 —— 一步不多、一步不少。走到 S 時 S->val == key,命中。

換句話說:那個被改壞的值,在整個下降過程中從來沒有被用來做決定。

實測:窮舉 n=1..8 全部 BST 的「兩個小孩」情形共 2652 組 —— 下降路徑「全部往左」2652/2652,遞迴找不到節點的次數 0。

隱藏前提:值必須唯一(本題有保證)。允許重複值的話 key 可能在右子樹另有同值節點,但那個問題課本的 copy 版同樣有(見 App 3)。
A3. 完全相同 —— 不只是「都合法」,而是連形狀都逐位元一致。

實測:窮舉 19633 組 (樹, key) + 隨機 20 萬組,形狀差異 0。

為什麼:兩版物理上摘掉的是同一個節點物件 —— 都是後繼那個節點。唯一的差別只是「它被丟掉之前,身上寫的數字是 key 還是 succ->val」,而它下一步就消失了,外界永遠看不到。

更強的驗證:實測追蹤「哪個節點變成不可達」——
· key 存在的 15521 組:恰好一個節點被丟棄,而且它在被丟掉的當下,值恰好等於 key —— 15521/15521,零例外。
· key 不存在的 4112 組:零節點被丟棄。
· 全程無節點重複、無成環。

這個結果也順便證明了 swap 版的語義是對的:key 被一路「換」到樹底,最後被物理丟棄的確實是持有 key 的那個節點 —— 而不是持有後繼值的那個。所以要加 delete 也很安全(見 App 1)。
A4. 因為後繼「必定沒有左小孩」,所以第二次刪除一定落在簡單情況。

後繼是右子樹一路往左走到底的那個節點 —— 既然它是「最左」,它就不可能還有左小孩(有的話就還沒走到底)。

所以第二次遞迴刪它的時候,root->left 是 nullptr,必定進入 if (!root->left || !root->right) 那一支直接回傳 —— 不會再去找第三個替身。

對稱地:前繼是左子樹一路往右到底,必定沒有右小孩,同樣落在簡單情況。

所以整個流程最多只會發生「一次」替換,遞迴深度上限就是樹高 —— 這也是為什麼成本是 2h 而不是更糟。

實測佐證:2652 組「兩個小孩」的情形,第二次遞迴全部在後繼的位置命中並落入簡單分支,沒有任何一組需要第三層。
A5. 因為刪除多了兩條「不需要回寫」的逃生路;但這不代表它比較不嚴重 —— 只代表它更難被測到。

實測對照:
· 701 插入丟掉回寫 → 錯 4706/4707(99.98%),只有「空樹」逃得掉。
· 450 刪除丟掉回寫 → 錯 14270/19633(72.7%),巧合正確 5363 組。

那 5363 組恰好是兩條逃生路的總和:
① key 不存在(4112 組)—— 樹本來就沒有任何改動,回不回寫都一樣。
② 根節點自己就是目標 —— 回傳值直接被呼叫端接住,中間沒有任何一層需要回寫。

但「失敗率比較低」和「bug 比較輕微」是兩件事。回寫在這裡同樣是必要的;差別只在插入幾乎一測就爆,刪除卻有 27% 的組合看起來沒事。

這其實讓它更危險 —— 一個 100% 會爆的 bug 你第一次跑就發現了;一個 27% 會過的 bug 可能撐到上線。測資的覆蓋率決定你抓不抓得到,而不是 bug 的嚴重性。
App 1. 加在「0/1 個小孩」那一支,而且必須先存下 survivor 再 delete。

if (!root->left || !root->right) {
    TreeNode* survivor = root->left ? root->left : root->right;
    delete root;              // ← 就這一行
    return survivor;
}
⚠ 順序不能反:如果先 delete root; 再讀 root->left,那就是 use-after-free —— 而且它多半不會當場崩(那塊記憶體通常還沒被覆蓋),會變成隨機出現的詭異 bug。

為什麼這樣加是安全的(實測佐證):
· 每次成功刪除恰好一個節點變成不可達 → 15521/15521
· 那個節點在被丟掉的當下,值恰好等於 key → 15521/15521
· key 不存在時零節點被丟棄 → 4112/4112
· 全程無節點重複、無成環 ⇒ 不可能 double free

LeetCode 不要求釋放(它自己管理測資的樹),但真實程式裡漏掉就是每刪一次漏一個節點。面試時主動提一句「正式程式我會在這裡 delete,並且注意先取 survivor」是很好的加分。
App 2. 要自己記住 parent,而且「是左小孩還是右小孩」也要記 —— 最麻煩的是兩個小孩那一支。

TreeNode* deleteNode(TreeNode* root, int key) {
    TreeNode* parent = nullptr;
    TreeNode* curr = root;

    while (curr != nullptr && curr->val != key) {   // 1) 找到目標,順便記父節點
        parent = curr;
        curr = (curr->val > key) ? curr->left : curr->right;
    }

    if (curr == nullptr) {
        return root;                                 // key 不存在
    }

    if (curr->left && curr->right) {                 // 2) 兩個小孩:改成刪後繼
        TreeNode* succParent = curr;
        TreeNode* succ = curr->right;

        while (succ->left) {
            succParent = succ;
            succ = succ->left;
        }

        curr->val = succ->val;                       // 值搬上來
        curr = succ;                                 // 改成刪 succ
        parent = succParent;                         // 它的父節點也要換
    }

    TreeNode* survivor = curr->left ? curr->left : curr->right;   // 3) 摘除

    if (parent == nullptr) {
        return survivor;                             // 刪的是根 → 換根
    }

    if (parent->left == curr) {
        parent->left = survivor;
    } else {
        parent->right = survivor;
    }

    return root;
}
麻煩的地方有三個,全都是遞迴版「免費」得到的:
① 要記 parent —— 遞迴版靠還沒返回的堆疊框記住它(就是那個回寫)。
② 兩個小孩時,parent 也要跟著換(換成 succParent)—— 這是最容易寫錯的一步。
③ 要判斷「curr 是 parent 的左還是右小孩」 —— 遞迴版的 root->left = ... / root->right = ... 本身就帶著這個資訊。

好處:空間 O(1),而且不會 stack overflow —— 對照遞迴版在 ulimit -s 512 KB 下 n=10⁴ 會 SIGSEGV。

注意這裡我用了 copy 而非 swap:迭代版沒有「回頭再刪一次」的遞迴,所以直接搬值、改目標比較自然。
App 3. 會「刪掉其中一個」,但刪掉哪一個不保證 —— 而且這個問題 swap 版和 copy 版都有。

題目保證值唯一,所以這是超出約束的情形。但值得想清楚,因為真實的 BST 實作常常要處理重複值。

會出什麼問題:
① 下降時可能停在「錯的那一個」。root->val > key / < key 的二分在遇到相等時就停了,但相等的節點可能有好幾個,分散在不同深度。
② 對 swap 版特別的風險:swap 之後到右子樹找 key,如果右子樹裡本來就有另一個值等於 key 的節點,遞迴可能提前命中那一個,結果刪錯節點 —— 而本頁 LEMMA 1 的論證正是靠「key 比右子樹所有值都小」,重複值一出現,這個前提就破了。
③ 但 copy 版也沒有比較好:它去刪 succ->val,如果右子樹裡有兩個節點都等於 succ->val,同樣可能刪錯那一個。

實務上怎麼處理重複值:
· 最常見:節點加一個 count 欄位 —— 重複的值不開新節點,只把計數 +1;刪除就是計數 −1,歸零才真的摘掉。std::multiset 的底層概念類似。
· 或者規定「相等一律往右(或往左)」,讓相等的節點形成一條可預測的鏈 —— 但這會讓樹更容易退化。

面試時值得主動問一句「值保證唯一嗎?」 —— 這題的約束剛好給了保證,但那不是理所當然的。
