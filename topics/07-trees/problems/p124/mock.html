OK. Two things jump out. Values can be negative, so the tree could be all negative, and then the best path is just the single biggest node. And the tree isn't promised to be balanced, so the depth could be 30,000.

The key fact: every path has exactly one highest node. I'll call it the bend. From the bend, the path goes down the left side, the right side, or both. So if I try every node as the bend and take the best way down on each side, I cover every path.

The best path is 15 → 20 → 7 = 42. Its bend is 20, and it never touches the root; going through the root gives only 34, because -10 costs too much. That matches.

Hmm, let me think about this for a second.

A naive approach would take every pair of nodes, find the path between them through their common ancestor, and add it up. That's O(n2) pairs, and each path can be long — too slow for 3·104 nodes. But it's a great checker, and I'll use it later to test my code.

This problem reminds me of post-order tree DP, the longest-path-in-a-tree pattern. Each node gets answers from its children, updates a global best with itself as the bend, and returns a single "arm" to its parent. The only change is that we add up values instead of counting edges, and values can be negative.

C
CANDIDATE

Here's the plan.

// path(node): best sum going straight DOWN from node
if node is null: return 0
l = max(0, path(node.left))       // drop an arm that loses money
r = max(0, path(node.right))
ans = max(ans, node.val + l + r)  // node as the bend: both arms
return node.val + max(l, r)      // to the parent: ONE arm only

// start: ans = INT_MIN; path(root); return ans

One: path(node) is the best sum going straight down from it; null gives 0.
Two: clamp each child's result at zero to drop a losing arm.
Three: update ans with the node as the bend, using both arms, but return the node plus only the larger arm.

One thing worth flagging — those two numbers are different, and mixing them up is the classic bug: if I returned both arms, val + l + r instead of val + max(l, r), the parent would add itself on top, and the path would fork. And ans starts at INT_MIN, not 0, or an all-negative tree would wrongly get 0.

One trade-off: recursion depth is the tree height. An iterative post-order avoids that but is easier to get wrong, so I'll write the recursive one and check the stack later. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up.

class Solution {
public:
    int maxPathSum(TreeNode* root) {
        int ans = INT_MIN;                          // an all-negative tree must still update it
        path(root, ans);
        return ans;
    }

    int path(TreeNode* root, int& ans) {
        if (!root) return 0;

        int l = max(0, path(root->left, ans));      // drop a negative arm
        int r = max(0, path(root->right, ans));
        ans = max(ans, root->val + l + r);           // me as the bend: both arms

        return root->val + max(l, r);              // going up: carry one arm only
    }
};

The helper follows the plan line by line. Both children are fully done before I touch ans, so it's a true post-order, and the return value from the root call is thrown away — I only need ans.

One thing worth flagging — ans is a local in maxPathSum, passed down by reference, not a class member. That matters if the same Solution object is used twice. With a member that's never reset, calling on [-1] and then [-2] gives -1 the second time, because the old best is still there. The right answer is -2. The local version has no state to leak.

Let me think about complexity here.

Time is O(n): counting null children, it's exactly 2n + 1 calls, each doing constant work. Space is O(h) for the recursion stack — a balanced tree of 3·104 nodes is only 15 deep.

In the worst case the tree is a chain, 30,000 deep. With -O0 each frame is about 96 bytes, and on an 8 MB stack the crash depth is about 87,142 — a 2.9× margin. Fine, but not huge: an AddressSanitizer build does overflow on the longest chain. If stack is a concern, I'd switch to an iterative post-order.

Oh, one more thing — overflow. The biggest possible path is every node at 1000: 3·104 × 1000 = 30,000,000, about 71× below INT_MAX. And INT_MIN is only compared, never added to. So int is safe.
