Hmm, let me think about this for a sec.

A naive approach would be to find the height, then for each depth walk the whole tree and collect only the nodes at that depth. That works, but it walks all n nodes once per level — O(n · h), which is O(n2) on a skewed tree.

This problem reminds me of breadth-first search on a graph. A tree is just a graph with no cycles, so I do not even need a visited set. I will use BFS with a queue and process one full level per outer loop turn.

P — plan
C
CANDIDATE

Here's the plan.

// invariant: at the top of each outer loop turn,
// the queue holds exactly one full level, in left-to-right order.

push root
while queue not empty:
  sz = q.size()  // freeze the level width HERE
  pop exactly sz nodes, record their values
  push each popped node's children
  append that group to the answer

One: push the root.
Two: while the queue is not empty, freeze its size as sz — that is exactly how many nodes the current level has.
Three: pop exactly sz nodes, record their values, push their children, and append that group to the answer.

One thing worth flagging — I read the size once, before the inner loop starts. Inside the loop I push children into the same queue I pop from, so the size keeps changing. If the condition re-read q.size() every pass, the boundary would drift. It does not hang and it does not crash — it quietly blurs levels together.

There's a trade-off here. A null marker after each level, or node-and-depth pairs, also work; the size snapshot is the cheapest, with no sentinel to handle.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<vector<int>> levelOrder(TreeNode* root) {
        if (root == nullptr) {
            return {};
        }

        vector<vector<int>> ans;
        vector<int> level;
        queue<TreeNode*> q;
        q.push({root});

        while (!q.empty()) {
            auto sz = q.size();   // ← freeze the level width, before pushing any children
            level.clear();

            for (int _ = 0; _ < sz; _++) {
                auto u = q.front(); q.pop();
                level.push_back(u->val);

                if (u->left) {
                    q.push(u->left);
                }
                if (u->right) {
                    q.push(u->right);
                }
            }

            ans.push_back(level);
        }
        return ans;
    }
};

After the null guard, each outer turn freezes sz, clears the level buffer, then pops exactly sz nodes, recording each value and pushing its non-null children.

One thing worth flagging — sz is an unsigned size_t, and my counter is an int. That compiles, but it warns under -Wall -Wextra as a signed and unsigned comparison. Could it misbehave? Only with over two billion nodes in one level, and the cap is 2000. So it is a warning, not a bug — but int sz = (int)q.size(); once would make it clean.

The time complexity is O(n). Every node is pushed once and popped once, with constant work each.

The space complexity is O(w) for the queue, where w is the widest level, not counting the output. In the worst-case scenario the tree is perfect and the bottom level holds about half the nodes.

Let me think about complexity here. BFS costs O(width), DFS costs O(height), and those are opposite worst cases. On a perfect tree of 1023 nodes, my queue peaks at 512 while a recursive DFS goes only 10 frames deep. On a 1000-node chain, my queue never holds more than 1 node, while DFS goes 1000 frames deep. Neither is simply better.

Oh, one more thing — there is zero recursion here, so a deep tree cannot blow the stack.
