範例 Trace// [3,9,20,null,null,15,7]

官方範例 1。以下是實跑印出來的。 重點看每一輪的 sz 是在「什麼時候」被讀取的。

// 外層第 1 輪 初始 queue=[3] ans=[] sz = q.size() = 1 ← 凍結(此刻佇列只有 3) level.clear() level=[] i=0/1 deq 3 level=[3] enq {9,20} queue=[9,20] ── 內層結束:i 跑滿 sz=1 次,「即使佇列現在有 2 個」 ans.push_back(level) ans=[[3]] queue=[9,20] // 第一次看到重點:佇列長大了,但這一層只跑 1 次就收手
// 外層第 2 輪 —— 這一輪最關鍵 sz = q.size() = 2 ← 凍結(此刻佇列是 [9,20]) level.clear() level=[] i=0/2 deq 9 level=[9] enq {} queue=[20] i=1/2 deq 20 level=[9,20] enq {15,7} queue=[15,7] ── 內層結束:i 跑滿 sz=2 次 ⚡ 注意此刻:推完 15、7 之後,佇列「又剛好是 2 個」 如果條件寫成每圈重讀 q.size(),它會看到 i=1 < 2 而「繼續跑」 → 把 15 拖進這一層,變成 [9,20,15] ans.push_back(level) ans=[[3],[9,20]] queue=[15,7] // 凍結的 sz 是「唯一」隔開這一層和下一層的東西
// 外層第 3 輪 + OUTPUT sz = q.size() = 2 ← 凍結([15,7]) i=0/2 deq 15 level=[15] enq {} queue=[7] i=1/2 deq 7 level=[15,7] enq {} queue=[] ans.push_back(level) ans=[[3],[9,20],[15,7]] while (!q.empty()) 不成立 → 結束 return [[3],[9,20],[15,7]] 統計:入隊 5、出隊 5、level.push_back 5 次 —— 都等於 n 最大佇列長度 2 // 入隊 == 出隊 == n 是 BFS 的招牌恆等式:每個節點恰好進出一次
把第 2 輪單獨看,整題就講完了: 節點 20 推入小孩之後,佇列長度「碰巧又回到 2」 —— 這正是「每圈重讀 q.size()」會被騙的瞬間。 凍結的 sz 記住的是「推小孩之前」的狀態,而那才是這一層真正的寬度。

應用題// APPLICATION

App 1. 改成由下往上的層序(LeetCode 107),最後一層排最前面。最省事的改法是什麼?
App 2. 改成鋸齒狀層序(LeetCode 103):第 0 層左→右、第 1 層右→左、交替。有哪幾種改法?哪一種最好?
App 3. 不用佇列,改用 DFS 做層序。怎麼做?和 BFS 版各自的優劣是什麼?
// ANSWERS
A1. 不是無窮迴圈 —— 是「層會合併」,而且錯得很安靜。

為什麼不會無窮迴圈:每一圈仍然是「彈出 1 個、最多推入 2 個」,而樹是有限的,所以總會結束。實測加了 500 萬步的保護計數器,一次都沒觸發。

真正的症狀是分層錯亂:q.size() 會隨著小孩被推進去而變大,內層迴圈於是跑過了這一層的結尾,把下一層(甚至下下層)的節點吞進來。

實測:窮舉 n ≤ 9 全部 6918 種樹形,錯 6406 種。
· 最小反例 n=3:[1,2,3] → 錯成 [[1,2],[3]](正解 [[1],[2,3]])。
· 官方範例:正解 [[3],[9,20],[15,7]] → 錯成 [[3,9],[20,15],[7]] —— 每一層都被推移了。
· 完美樹 h=4 更誇張:第一「層」吞了 8 個節點、橫跨 4 個真實層級。

「不會崩、不會卡、只是答案悄悄錯掉」——這是最難發現的那種 bug。
A2. 因為斜鏈上「每一層只有一個節點」,那個 bug 根本沒有機會發作。

在一條鏈上,每一層彈出 1 個、最多只推入 1 個。所以 q.size() 在內層迴圈裡從 1 變成 1 —— 重讀和凍結讀到同一個數字,兩種寫法行為完全相同。

實測:6918 種樹形裡,錯誤版本「巧合正確」的 512 種,基本上就是各種鏈狀樹。n=5 的左斜鏈兩版都給 [[1],[2],[3],[4],[5]]。

對測資設計的教訓,和前面幾題是同一個:
① 斜鏈是「退化」測資,不是「極端」測資 —— 它讓所有和「分岔」有關的 bug 隱形。
② 這題需要的最小測資是「某一層有 2 個節點」,也就是 [1,2,3]。
③ 這和 144 前序的情況一模一樣:那題也是斜鏈讓前序/中序看起來相同。「我測過了」和「我測到對的形狀了」是兩回事。
A3. 沒有誰一定比較省 —— 它們的最壞情況是「相反」的。

實測(同樣的樹,同時量 BFS 佇列峰值和 DFS 遞迴深度):

樹形nBFS 佇列峰值DFS 遞迴深度誰贏
完美樹102351210DFS
左斜鏈100011000BFS
掃把形(長柄 + 寬底)1000250509相當
完全樹2000100011DFS
完美樹上 BFS 差了 51 倍,鏈上 DFS 差了 1000 倍 —— 完全對稱的兩個災難。

但 BFS 有一個結構性優勢:它的空間在堆積上,不是呼叫堆疊。所以它永遠不會 stack overflow —— 而本章前面每一題都得認真計算「n=10⁴ 的鏈會不會爆」。BFS 直接把那個問題消掉了,代價是完美樹上多用記憶體。

小細節:實測完全樹 n=2000 的佇列峰值是 1000,但最大層寬只有 977 —— 因為峰值出現在「層的中間」(還沒彈完的這層尾巴 + 已經推進去的下層小孩)。所以嚴格說是 O(w) 而不是「恰好 w」。
A4. 是 -Wsign-compare(有號/無號比較);在這題的約束下不可能出錯。

實測的完整警告文字:
warning: comparison of integers of different signs:
         'int' and 'size_type' (aka 'unsigned long') [-Wsign-compare]
   for (int _ = 0; _ < sz; _++) {
                   ~ ^ ~~
q.size() 回傳 size_t(無號),和 int _ 比較時 _ 會被提升成無號。只有在 _ 是負數時才會出事 —— 而那需要 _ 先溢位過 INT_MAX。

實測約束上限:n=2000 的最寬合法樹,佇列峰值 1000、單層最寬 977 —— 離 INT_MAX(21.4 億)還差約 210 萬倍。
要真的壞掉,需要「單一層超過 21 億個節點」 —— 光那些指標就要約 17 GB,比題目上限大 10⁶ 倍。

所以:風格上該修,正確性上無害。兩種修法都行:size_t sz 配 size_t _,或 int sz = (int)q.size()。後者正是 199 那題的寫法 —— 它在 -Wall -Wextra 下完全乾淨。
A5. 正確性完全不變;效能上「重用」比較省,而且在高瘦的樹上省很多。

正確性:level.clear() 在每次使用之前執行,不可能有上一層的殘留。實測兩種寫法在整個 206918 組對拍語料上輸出逐位元相同。

效能 —— 實測堆積配置次數(用全域 operator new 計數器):
樹重用 + clear()每圈新宣告省下
完美樹 n=1023297445
鏈 n=100010162015999
原因:clear() 保留容量。重用的 level 容量成長 1→2→4→…→512 之後就再也不重新配置了(實測完美樹上只有 10 次成長事件);每圈新宣告則是「每一層都從容量 0 重新長一次」。

鏈上省最多(1000 層省 999 次,幾乎每層一次) —— 層數越多,這個稅越重。

⚠ 但要說清楚:ans.push_back(level) 是「複製」,所以 ans 自己那 n 個元素的儲存兩種寫法都要付。重用只省掉「那個暫存 vector」的配置。真正最快的是 ans.push_back(std::move(level)) —— 但那就必須把 level 宣告在迴圈裡,因為 move 之後的 vector 不該再 clear() 重用。
App 1. 最省事的是:照常做,最後把 ans 整個反轉。

// ... 完全相同的 BFS ...
reverse(ans.begin(), ans.end());
return ans;
成本 O(levels) —— 只是把 vector<vector<int>> 的外層反轉,內層的 vector 只是移動指標,不會複製內容。

另一種寫法是 ans.insert(ans.begin(), level) —— 但那是 O(levels) 的搬移每一層都做一次,總共 O(levels²)。在鏈上(1000 層)就是 100 萬次搬移 vs 一次反轉的 1000 次。

或者用 deque 當 ans 並 push_front —— O(1) 每層,但回傳型別要轉回 vector,多一次複製。

結論:最後 reverse 一次最單純也最快。「先照常算再調整」通常比「邊算邊維護特殊順序」好。
App 2. 最好的改法是:照常 BFS,只在偶數/奇數層把 level 反轉。

bool leftToRight = true;

while (!q.empty()) {
    int sz = q.size();
    level.clear();

    for (int i = 0; i < sz; i++) {
        // ... 和原本完全一樣 ...
    }

    if (!leftToRight) {
        reverse(level.begin(), level.end());
    }
    leftToRight = !leftToRight;

    ans.push_back(level);
}
成本:每層一次 O(該層寬度) 的反轉,總共仍是 O(n)。

其他兩種改法比較差:
① 反著推入小孩(奇數層先推右再推左)—— 會搞亂佇列的層次結構,很容易寫錯,而且下一層的順序又要再反一次。
② 改用兩個 stack —— 這是經典解法,但 stack 的語義讓「怎麼推小孩」變成每層不同,程式碼比「BFS + 條件反轉」長而且更容易錯。

⚡ 一般原則(和 App 1 同一句):「先用最單純的方式算出來,再在最後調整」,比「在演算法內部維護一個會變的規則」好懂也好驗證。而且它讓那個凍結的 sz 保持原封不動 —— 那是整題最不該去動的東西。
App 3. DFS 帶一個 depth 參數,用 ans[depth] 當該層的桶。

void dfs(TreeNode* root, int depth, vector<vector<int>>& ans) {
    if (root == nullptr) {
        return;
    }

    if ((int)ans.size() == depth) {     // 第一次到達這個深度
        ans.push_back({});
    }

    ans[depth].push_back(root->val);

    dfs(root->left,  depth + 1, ans);
    dfs(root->right, depth + 1, ans);
}
關鍵是 if (ans.size() == depth) ans.push_back({}) —— 「第一次走到這個深度就開一個新桶」。

而且它一定先左後右,所以同一層的節點會按「左到右」被推進桶裡 —— 和 BFS 的順序完全一致。本頁的對拍參考解用的就是這個版本,20 萬組 + 窮舉 6918 種樹形,零不一致。

優劣對照:
· 空間:DFS O(h) vs BFS O(w) —— 見 A3,是相反的最壞情況。
· stack overflow 風險:DFS 有,BFS 完全沒有。
· 「提早停」的能力:BFS 天然適合「只要前 k 層」或「最短路徑」;DFS 要走完才知道有幾層。
· 程式碼長度:DFS 版其實更短,而且不需要那個凍結 sz 的技巧。

所以「層序一定要用 BFS」是個迷思 —— DFS 完全可以,只是你得自己記住深度。真正非 BFS 不可的是「逐層處理、而且要在中途停下來」那種題目。
