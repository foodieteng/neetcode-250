Hmm, let me think about this for a second.

A naive approach would be to check each node only against its two children. It's tempting, but it's wrong. The smallest breaking input has three nodes: [2,null,3,1]. 1 is the left child of 3, so it looks fine locally. But 1 sits in 2's right subtree, so it must be bigger than 2, and it isn't.

This problem reminds me of passing constraints down a recursion: each call gets the range its node must fit in. The other classic idea is that an inorder walk of a search tree is strictly increasing. Both are O(n). I'll go with the bounds version, because it states the rule directly and it can stop at the first bad node.

P — plan
C
CANDIDATE

Here's the plan.

// valid(node, L, R): is this subtree a BST with all values in (L, R)?
if node is null:           return true
if not (L < node.val < R): return false    // strict on both sides
return valid(node.left,  L, node.val)      // left: cap the top
   and valid(node.right, node.val, R)      // right: raise the floor
// start: valid(root, -inf, +inf)

One: a helper takes a node and an open range (L, R), and a null node is valid.
Two: fail if the node's value is not strictly inside the range.
Three: recurse left with the node's value as the new upper bound, and right with it as the new lower bound.

The other side carries through unchanged — that's how a limit from high up reaches deep nodes.

One thing worth flagging — the "infinity" values. Node values fill the whole int range, so any int sentinel is also a real value. With INT_MIN and a strict <, a single node [-2147483648] returns false. Switch to <=, and duplicates like [1,null,1] slip through. So the sentinel must live outside int: I'll use 64-bit bounds.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up.

class Solution {
public:
    bool isValidBST(TreeNode* root) {
        return valid(root, LONG_MIN, LONG_MAX);     // root's window = (−∞, +∞)
    }

    bool valid(TreeNode* root, long long L, long long R) {
        if (!root) return true;

        return (L < root->val && root->val < R)
            && valid(root->left, L, root->val)      // left: cap the top at val
            && valid(root->right, root->val, R);    // right: raise the floor to val
    }
};

isValidBST just starts the helper with the widest bounds. The helper does the range check, then recurses left with the node's value as the new top, and right with it as the new floor. The && chain short-circuits: once a check fails, nothing after it runs.

One thing worth flagging — I wrote LONG_MIN and LONG_MAX. On 64-bit Linux, long is 8 bytes, so that's fine. But on Windows with MSVC, long is only 32 bits, so LONG_MIN equals INT_MIN, and we're back to the int bug. The portable fix is LLONG_MIN / LLONG_MAX. Another option is TreeNode* bounds, with nullptr meaning "no limit" — no sentinel at all.

C
CANDIDATE

Let me think about complexity here.

Time is O(n): each node gets one call doing constant work. On a valid tree that's exactly 2n + 1 calls, counting null children. On an invalid tree the short-circuit can stop very early — if the root's left child is broken, it's just 2 calls, no matter the size.

Space is O(h) for the recursion stack. Worst case is a chain, 10,001 frames deep. On an 8 MB stack, the crash only comes at about 174,281 frames, a 17.4× margin, so recursion is fine here.

Oh, one more thing — why a separate helper instead of default arguments? With defaults, a caller could write isValidBST(root, 0, 10) by mistake, and the valid tree [20,10,30] would return false. A helper means the public function can only be called the right way.
