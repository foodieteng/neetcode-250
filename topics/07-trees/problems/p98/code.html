完整實作// RANGE PROPAGATION

p98.cpp C++17 
class Solution {
public:
    bool isValidBST(TreeNode* root,
                    long long mi = LONG_MIN,
                    long long mx = LONG_MAX) {
        if (root == nullptr) {
            return true;
        }

        return (mi < root->val && root->val < mx)
            && isValidBST(root->left,  mi, root->val)   // 往左:上界收成自己
            && isValidBST(root->right, root->val, mx);  // 往右:下界收成自己
    }
};

🎤 面試模擬 · UMPIRE mock interview transcript ↗

整個演算法就在那兩行遞迴的參數裡 —— 往左傳 (mi, root->val)、往右傳 (root->val, mx), 另一邊原封不動繼承。 「原封不動」那半邊,就是祖先的界線能穿過好幾層壓住深處節點的原因。
2

⚡ 為什麼是 long long// THE TYPE QUESTION

這是本題最值得問的問題。 答案不是「怕溢位」 —— 這段程式碼完全沒有算術,只有比較。 真正的理由是:哨兵必須待在值域之外,而值域已經吃滿了整個 int。

// 用 int 當哨兵會怎樣(實測) int mi = INT_MIN, mx = INT_MAX; 搭配嚴格比較 mi < val && val < mx 題目值域:-2^31 ~ 2^31-1 —— INT_MIN 和 INT_MAX「都是合法的節點值」 碰到值為 INT_MIN 的節點: mi < root->val => INT_MIN < INT_MIN => false ⇒ 一棵完全合法的單節點樹被判 false 實測: 最小反例 [-2147483648] 單一節點 含極值窮舉 9431 組錯 131 組 隨機 20 萬組 錯 104104 組(刻意大量使用 INT_MIN/INT_MAX) // 直接探針:[INT_MIN] → int 版回 0(錯)、long long 版回 1(對)
// 「那改成 <= / >= 不就好了?」—— 不行,會壞掉另一半 int mi = INT_MIN, mx = INT_MAX; 搭配寬鬆比較 mi <= val && val <= mx 哨兵問題解決了,但「重複值」被放行了 —— 而 BST 要求「嚴格」遞增 實測: 最小反例 [1,null,1] 兩個節點同值,應為 false 卻回 true 極值窮舉 9431 組錯 1045 組 最小 [-2147483648,null,-2147483648] {1,2,3} 窮舉 1042 萬組錯 84633 組 隨機 20 萬組 錯 2570 組 ⇒ 兩個 int 方案「各壞一半」: 嚴格版 擋不住「哨兵撞上合法值」 寬鬆版 擋不住「重複值」 只有把區間型別「抬高到 int 之外」才能兩者兼顧 // 這就是 long long 的真正理由 —— 不是溢位,是「哨兵需要站的位置」
另一個作法可以完全繞開型別問題:傳指標而不是值。
bool valid(TreeNode* root, TreeNode* lo, TreeNode* hi) —— 用 nullptr 表示「這一邊沒有界線」, 比較時寫 (!lo || lo->val < root->val)。 這樣連「值域比 long long 還大」的假想情況都不怕, 因為它根本不需要哨兵值。

⚠ LONG_MIN 還是 LLONG_MIN?// A LATENT PORTABILITY BUG

參數宣告成 long long,但初始值寫的是 LONG_MIN / LONG_MAX —— 那是 long 的極限,不是 long long 的。 這兩者相不相等,完全取決於平台。

// 本平台實測(macOS arm64,LP64) sizeof(int) = 4 sizeof(long) = 8 ← 關鍵:LP64 的 long 是 64-bit sizeof(long long) = 8 INT_MIN = -2147483648 LONG_MIN = -9223372036854775808 LLONG_MIN = -9223372036854775808 LONG_MIN == LLONG_MIN ? yes ← 本平台:兩者相同,程式碼「正確」 LONG_MIN == INT_MIN ? no ← Windows/MSVC(LLP64)會是 yes // 在 LeetCode(Linux/macOS)上這份程式碼完全正確 —— 主解 7000 萬組零錯誤
// 模擬 Windows(LLP64,long 是 32-bit)會發生什麼 在 MSVC 上,LONG_MIN 會展開成 -2147483648(也就是 INT_MIN) 所以參數變成: long long mi = (long long)INT_MIN, mx = (long long)INT_MAX 實測這個變體: 最小反例 [-2147483648] ← 和「用 int」那個 bug「完全一樣」 含極值窮舉 9431 組錯 131 組 ← 逐筆與 int 版相同 隨機 20 萬組 錯 104104 組 ← 逐筆與 int 版相同 {1,2,3} 窮舉 1042 萬組錯 0 組 ← ⚠ 這個測試集「不含極值」,完全掩蓋了 bug 一個字的修法:LONG_MIN → LLONG_MIN、LONG_MAX → LLONG_MAX // 注意倒數第二行:如果測資不含 INT_MIN/INT_MAX,這個 bug 一次都不會現形
結論分兩半,兩半都要說清楚:
① 在這個平台(以及 LeetCode)上,你的程式碼是正確的 —— 實測全部三個測試集共 7000 萬組零錯誤。
② 但 LONG_MIN 是「碰巧對」的常數 —— 它對不對取決於 sizeof(long),而那是平台決定的。 改成 LLONG_MIN 只要一個字,而且從「碰巧對」變成「一定對」。

// PHASE 1: 「只比父節點」為什麼抓不到 —— 最小反例只要 3 個節點 tree = [2,null,3,1] (root=2,右子=3,3 的左子=1) 2 \ 3 / 1 「只比父節點」的檢查: 節點 2:沒有左子;右子 3 > 2 ✓ 通過 節點 3:左子 1 < 3 ✓ 通過 節點 1:葉節點 ✓ 通過 ⇒ 判定 true 但真正的 BST 定義說:root=2 的「整棵右子樹」都必須 > 2 節點 1 在 2 的右子樹裡,卻是 1 < 2 ⇒ 不是 BST,正解 false 區間版怎麼抓到: 節點 3 的窗 = (2, +∞) ← 下界 2 從 root 傳下來 節點 1 的窗 = (2, 3) ← 往左:上界收成 3,「但下界還是 2」 檢查 2 < 1 ? 否 ⇒ 失敗 ✓ 正確抓到 實測規模:窮舉全樹形 × 相異值全排列 5992 萬組,「只比父節點」錯 28 萬組 // 那個「原封不動繼承下來的下界 2」,就是整個機制的核心
// PHASE 2: 窗是怎麼收窄的(官方範例 2 的實測 trace) tree = [5,1,4,null,null,3,6] 答案 false 1. 節點 5 窗 (-∞, +∞) -∞ < 5 < +∞ ✓ PASS 2. 節點 1 窗 (-∞, 5) -∞ < 1 < 5 ✓ PASS ← 往左:上界收成 5 3. null 窗 (-∞, 1) → true 4. null 窗 (1, 5) → true 5. 節點 4 窗 (5, +∞) 5 < 4 ? ✗ FAIL ← 往右:下界收成 5 ⇒ && 短路,節點 3 和 6 「從未被走訪」 ⇒ FINAL false 注意這個例子在「節點 4」就停了 —— 4 是 root 的右子卻小於 root,本地就違規 真正需要「遠房祖先」才抓得到的例子是 [5,4,6,null,null,3,7](見動畫) // 官方範例 2 其實不需要區間傳遞就能抓到 —— 所以動畫用了另一棵樹
// PHASE 3: 預設參數的風險(和 1448 同一個 pattern) public 簽名是 isValidBST(TreeNode*, long long, long long) ⇒ 呼叫端「可以」傳第二、三個參數,覆寫掉哨兵 實測: tree = [20,10,30] isValidBST(root) → true ✓ 正確 isValidBST(root, 0, 10) → false ✗ 一棵完全合法的 BST 被判非法 (10 和 30 都被關在 (0,10) 這個外加的窗外) tree = [-2147483648] isValidBST(root, 0, 10) → false ✗ 正解 true ⚠ 更危險的是:tree = [2,1,3] 配 (0,10) 「碰巧」仍回 true ⇒ 錯誤的呼叫「不一定會立刻暴露」 正確做法:public 只留 isValidBST(TreeNode*),把帶邊界的遞迴放進 private helper ⇒ 錯誤從「執行期靜默錯答」降級成「編譯期錯誤」 // 和 1448 的 goodNodes(root, 5) 完全同一個問題 —— 內部不變量不該暴露在 public 簽名上
// PHASE 4: 三種寫法的取捨 ① 區間往下傳(本題) 時間 O(n)、空間 O(h);不合法時可以極早短路(實測最少 2 次呼叫) 要小心:哨兵型別、嚴格比較、LONG vs LLONG ② 中序走訪 + 檢查嚴格遞增 概念最乾淨(BST 的中序必嚴格遞增),但要嘛存整個陣列 O(n) 空間 要嘛小心維護「前一個值」;而且「前一個值」也需要一個哨兵或一個 bool 旗標 ③ 傳「指標」而不是值:valid(root, TreeNode* lo, TreeNode* hi) 用 nullptr 表示「沒有界線」⇒ 完全不需要哨兵值 ⇒ 免疫整個型別問題,連「值域比 long long 還大」都不怕 面試建議:寫 ①,但主動說出「哨兵必須在值域之外,所以用 long long; 如果不想依賴型別,可以改傳指標」 // 能講出「為什麼是 long long」比會寫這題本身更能顯示你想過細節

long long 不是怕溢位(這裡沒有算術),是因為值域吃滿整個 int,哨兵沒有 int 可以站 —— 用 int 嚴格比較擋不住哨兵撞值、寬鬆比較擋不住重複值,各壞一半。而 LONG_MIN 是「碰巧對」的常數:在 Windows 上它會退化成 INT_MIN。
