題目簡介// THE QUESTION

QUESTION

判斷一棵二元樹是不是合法的 BST。定義是: 每個節點的整棵左子樹都嚴格小於它,整棵右子樹都嚴格大於它。
節點數 1 ~ 10⁴,值域是完整的 int 範圍 —— −2³¹ ~ 2³¹−1,INT_MIN 和 INT_MAX 都可能出現。

注意定義裡那兩個「整棵」 —— 這正是本題的全部難度。 不是「左小孩比我小、右小孩比我大」就好, 而是「左子樹每一個節點都比我小」。

解法:讓每個節點繼承一個「合法區間」(mi, mx),並在往下走的時候收窄它。 往左走 ⇒ 上界收成自己的值;往右走 ⇒ 下界收成自己的值。 這樣「遠房祖先」的約束就會一路傳到任意深的地方 —— 而這正是「只比父節點」抓不到的東西。

為什麼「只比父節點」不夠// WHY THIS

A 只在每個節點檢查「左小孩 < 我 < 右小孩」 錯 28 萬組
每個節點局部都合法,整棵樹卻不是 BST。 最小反例只要 3 個節點:[2,null,3,1] —— 節點 1 是 3 的左小孩(1 < 3 ✓), 但它在 root=2 的右子樹裡,必須 > 2。
× REJECT · 看不夠遠
B 中序走訪,檢查是否嚴格遞增 也完全正確
BST 的中序必定嚴格遞增(94 那題的性質)。 本頁就是拿它當對拍參考解 —— 7000 萬組零不一致。 缺點:要嘛存整個陣列 O(n) 空間,要嘛得小心維護「前一個值」。
△ 對,另一種思路
ADOPT
C 往下傳一個會收窄的區間 (mi, mx) O(n) 時間 · O(h) 空間
每個節點只問一句:「我落在繼承來的窗裡嗎?」 往左把上界換成自己、往右把下界換成自己 —— 祖先的約束就自動被帶到任意深的地方。
● ADOPT · 區間往下傳
實測「只比父節點」的錯誤規模:窮舉全樹形 × 相異值全排列共 5992 萬組, 錯 28 萬組; 而在「值只有 {1,2,3} 可重複」的 1042 萬組裡錯 1896 組。 比例看起來不高,但最小反例只要 3 個節點 —— 它不是罕見的邊角,只是需要「祖孫關係」才觸發。
3

核心策略 · 窗怎麼收// THE SHAPE

  1. 根節點的窗是 (−∞, +∞) —— 任何值都合法。
  2. 檢查自己:mi < root->val && root->val < mx, 兩邊都要嚴格(BST 不允許重複值)。
  3. 往左走:(mi, root->val) —— 上界收成自己。
  4. 往右走:(root->val, mx) —— 下界收成自己。
關鍵在第 ③ ④ 步「只換一邊」 —— 另一邊原封不動地繼承下去, 所以 root 設下的界線可以一路穿過好幾層,壓住很深的節點。 這就是「遠房祖先的約束」是怎麼傳下去的。

⚡ 為什麼一定要用 long long// THE TYPE QUESTION

LEMMA 1 · 用 int 當哨兵會被「值域邊界」撞死

題目的值域是完整的 int 範圍 —— INT_MIN 和 INT_MAX 都是合法的節點值。 如果哨兵寫成 int mi = INT_MIN,那麼碰到一個值就是 INT_MIN 的節點時:
mi < root->val ⇒ INT_MIN < INT_MIN ⇒ false —— 一棵完全合法的單節點樹被判成 false。

實測:int + 嚴格比較的版本,
· 最小反例就是單節點 [-2147483648]
· 含極值的窮舉 9431 組錯 131 組
· 隨機 20 萬組(刻意大量使用 INT_MIN/INT_MAX)錯 104104 組
⚠ 那「改成 <= / >= 不就好了?」—— 不行,那會壞掉另一半: 寬鬆比較讓哨兵過關,但同時把重複值也放行了(BST 要求嚴格遞增)。 實測最小反例 [1,null,1],在 1042 萬組窮舉中錯 84633 組。
兩個 int 方案各壞一半 —— 只有「把區間的型別抬高到 int 之外」才能兩者兼顧。

LEMMA 2 · ⚠ LONG_MIN 不是 long long 的極限 —— 一個潛伏的可攜性 bug

你的參數宣告成 long long,但初始值寫的是 LONG_MIN / LONG_MAX —— 那是 long 的極限,不是 long long 的。 這兩者是否相同,取決於平台。

本平台實測(macOS arm64,LP64):
sizeof(long) = 8,LONG_MIN == LLONG_MIN ⇒ 程式碼正確 (主解在全部三個測試集共 7000 萬組上零錯誤)。
但在 Windows / MSVC(LLP64)long 是 32-bit ⇒ LONG_MIN 會退化成 INT_MIN ⇒ 就變成 LEMMA 1 那個 bug。
模擬實測(把哨兵換成 (long long)INT_MIN,也就是 MSVC 上展開的樣子): 最小反例同樣是 [-2147483648],含極值窮舉錯 131 組、 隨機 20 萬組錯 104104 組 —— 與 int 版逐筆相同,就是同一個 bug。
一個字的修法:改用 LLONG_MIN / LLONG_MAX。

// 本平台實測(決定 LONG_MIN 是多少的關鍵) sizeof(int) = 4 sizeof(long) = 8 ← LP64。Windows 是 4,這就是差別所在 sizeof(long long) = 8 INT_MIN = -2147483648 LONG_MIN = -9223372036854775808 LLONG_MIN = -9223372036854775808 LONG_MIN == LLONG_MIN ? yes ← 本平台:安全 LONG_MIN == INT_MIN ? no ← Windows(LLP64)會是 yes:壞掉 若 LONG_MIN 退化成 INT_MIN,單節點 [INT_MIN] 會發生什麼: mi < root->val => -2147483648 < -2147483648 => FALSE ⇒ 一棵合法的樹被判 false // 結論:這份程式碼在 LeetCode(Linux/macOS)上完全正確,但把常數換成 LLONG_ 更穩
另一個常見替代方案:改傳「指標」而不是「值」 —— bool valid(TreeNode* root, TreeNode* lo, TreeNode* hi), 用 nullptr 表示「沒有界線」。 這樣就完全不需要哨兵值,自然免疫整個型別問題 —— 而且它連「值域比 long long 還大」的假想情況都不怕。

一句洞察// INSIGHT

BST 的定義是「整棵子樹」,所以檢查也必須帶著「整棵子樹的約束」往下走。 那個會收窄的窗 (mi, mx),就是把祖先的界線帶到任意深處的載具 —— 往左換上界、往右換下界,另一邊原封不動繼承。
而 long long 不是為了「怕溢位」,是因為哨兵必須待在值域之外 —— 值域已經吃滿整個 int,哨兵就沒有 int 可以站了。
