Hmm, let me think about this for a sec.

A naive approach would be to serialize each tree to a string, with markers for the null slots, then compare the strings. That works, but it builds two full strings before it can find a difference that might be at the very first node.

This problem reminds me of a parallel DFS — the same walk as a normal traversal, just with two pointers moving together. It fits because "same tree" is defined recursively: the roots match and both subtree pairs match. And it can stop the instant it finds a mismatch.

C
CANDIDATE

Here's the plan.

// at least one is null:
if (!p || !q) return p == q;

// both are real:
return p.val == q.val
       && same(p.left, q.left)
       && same(p.right, q.right);

One: if at least one pointer is null, return whether p == q.
Two: otherwise, compare the two values.
Three: recurse left with left and right with right, all joined by &&.

One thing worth flagging — that first line looks like a trick. Inside it, at least one pointer is null, so p == q can only be true if both are null. Two nulls, they match; one null, they don't. Both cases, one line.

The two-line version — if (!p && !q) return true; then if (!p || !q) return false; — says the same thing more plainly, but I want to be able to justify the one-liner, not just recite it. Does this approach sound good, or would you rather I think of another way?

I — implement

CANDIDATE

Alright, let me code this up. The guard handles the null cases, then one return chains the value check and the two recursive calls with &&.

class Solution {
public:
    bool isSameTree(TreeNode* p, TreeNode* q) {
        // at least one is null: "equal" means "both are null"
        if (!p || !q) {
            return p == q;
        }

        return (p->val == q->val)
            && isSameTree(p->left,  q->left)     // left with left
            && isSameTree(p->right, q->right);   // right with right
    }
};

One thing worth flagging — the guard has to come first, and not only to avoid a crash on p->val. It is what makes p == q mean "both null". That comparison is on pointers, not on trees. If I dropped the guard and compared pointers for every pair, two separate trees with the same content would come out false, because they never share an address.

The row that matters is the root's left: 2 against 1, so the && short-circuits — neither child pair of that node is visited, and false travels straight back up. Two calls in total; identical trees would have taken 7.

Let's also test with corner cases.

• Both empty: the guard fires and two nulls are equal, so true.
• One empty: the guard fires, false.
• Two single nodes with the same value: both child pairs are null pairs, so true.
• [1,2] against [1,null,2]: on the left, a node meets a null, so false.

C
CANDIDATE

The time complexity is O(min(np, nq)) — the recursion can't go further than the smaller tree, because the guard stops each branch when one side runs out. The space complexity is O(min(hp, hq)), for the call stack.

In the worst-case scenario the answer is true, since nothing short-circuits: two identical chains of 100 nodes take 201 calls, while trees that differ at the root take 1.

Oh, one more thing — a testing point. If a test harness passes the same object as both p and q, a broken pointer-comparison version passes every equal test, for the wrong reason. An equal pair must be two separate copies with the same content.
