面向要記住的那一句
本質兩棵樹並排遞迴,難點在「兩個指標各自可能為空」的三種組合
那一行 base caseif (!p || !q) return p == q; —— 一行吃掉兩種 null 情形

它什麼時候錯搬到 base case 外面就變成比指標 —— 錯 338/8165

Q2. 同樣是 p == q,為什麼放在 base case 裡是對的,搬到外面當一般比較就錯了?

範例 Trace// p=[1,2,1] q=[1,1,2] → false,2 次呼叫

官方範例 3。兩棵樹形狀完全相同,只有值不一樣。 以下每一步都是實跑印出來的。

// 第 1 次呼叫:比對兩個根 call(p = 節點1, q = 節點1) 兩邊都非空 → !p || !q 不成立,不進 base case 比值:1 == 1 ✓ 相等 → && 的第一個運算元為真,繼續求值第二個 → 呼叫 isSameTree(p->left, q->left) // 注意:這一趟從頭到尾「沒有」用到 base case —— 短路是值驅動的
// 第 2 次呼叫:發現不同 → 短路 ① call(p = 節點2, q = 節點1) 兩邊都非空 比值:2 != 1 ✗ 不相等 *** 短路 ① *** (p->val == q->val) 為 false,&& 立刻停止 → 這個節點自己的兩個子遞迴「一次都沒有被呼叫」 → 回傳 false
// 回到第 1 次呼叫 → 短路 ② 回到 call(節點1, 節點1):左子樹的遞迴回傳了 false *** 短路 ② *** 「左相同」已經是 false,所以「右相同」不會被求值 → isSameTree(p->right, q->right) —— 也就是 (節點1, 節點2) 這一對 「從來沒有被建立過」 → 回傳 false
// OUTPUT return false 總呼叫次數 = 2 (完整走訪這兩棵 3 節點的樹需要 7 次 = 2n+1) 被消掉的呼叫 = 5 從未被拜訪的節點: p 的右小孩(值 1)、q 的右小孩(值 2) 以及節點2 / 節點1 底下的 4 次空指標探測 // 7 個可能的呼叫裡有 5 個被短路消掉 —— 這不是微優化,是量級的差別
值得注意:這個 trace 裡 base case 一次都沒有被觸發 —— 兩個短路都是值不同造成的。 如果換成官方範例 2(p=[1,2] vs q=[1,null,2]), 短路就會發生在 base case 上(一邊是 nullptr、一邊不是)—— 兩種「不相同」走的是不同的路徑,值得各測一次。

應用題// APPLICATION

App 1. 判斷一棵樹是否左右對稱(LeetCode 101)。這題的程式碼要改哪裡?
App 2. 判斷 subRoot 是不是 root 的子樹(LeetCode 572)。怎麼用這題當零件?複雜度是多少?
App 3. 不用遞迴,改成迭代比較兩棵樹。要用什麼資料結構?
// ANSWERS
A1. 因為進到這個分支時,「已經知道至少有一個是 nullptr」。

在這個前提下逐一檢查:
· p 空、q 空 → p == q 是 true(兩個都是 nullptr,位址相等)→ 正確,兩棵空樹相同 ✓
· p 空、q 非空 → 一個是 nullptr、一個不是,不可能相等 → false ✓
· p 非空、q 空 → 同上 → false ✓
· 兩個都非空 → 根本不會進來(!p || !q 為假)

實測:與明確的兩行版本(if (!p && !q) return true; + if (!p || !q) return false;)在 51174 個配對上逐一比對,分歧 0。

而第四列「不會進來」其實同樣重要:它保證了下一行的 p->val 和 q->val 一定安全。所以這一行同時做了兩件事:終止判斷,以及為後面的解參考提供安全保證。

實測漏掉「只有一個空」的情形(只寫 if (!p && !q) return true;),8165 個配對中有 3896 個當場 SIGSEGV —— 因為程式會掉下去解參考 nullptr。
A2. 因為 C++ 的 == 對指標比的是「位址」,不是「指向的內容」。

放在 base case 裡:我們已經知道至少有一個是 nullptr。在這個受限的情況下,「位址相等」剛好等價於「兩個都是 nullptr」,也剛好等價於「這兩棵(空)樹相同」。三件事碰巧重合,所以寫 p == q 是對的。

搬到外面:兩個指標可能都指向非空的節點。此時「位址相等」代表它們是同一個節點物件 —— 這比「內容相同」嚴格得多。兩棵各自建立、內容完全一樣的樹,位址不同,會被判成「不同」。

實測:把整個函式主體換成 return p == q;,8165 個配對錯 338 個,最小反例 p=[1] vs q=[1](deep copy 的兩棵單節點樹)。唯一答對 true 的是 p=[] vs q=[] —— 因為兩邊真的都是 nullptr,位址真的相等。

一般教訓:一個運算式的正確性可以完全依賴它所在的上下文。把「在某個前提下成立」的程式碼搬到別處,是很常見的 bug 來源 —— 所以這種「聰明的一行」值得配一句註解,說明它依賴什麼前提。
A3. 最壞情況是「兩棵樹完全相同」—— 也就是答案為 true 的時候。

這通常和直覺相反,因為大多數題目的最壞情況是某種極端輸入(最大、最長、最退化)。

理由:只要有任何一處不同,某個 && 就會短路,底下全部不必看。而「完全相同」代表「沒有任何一處可以短路」 —— 整棵樹非走完不可。

實測(兩棵 n = 100 的樹):
· 完全相同 → 201 次呼叫(2n+1)← 最壞
· 根的值就不同 → 1 次呼叫 ← 最好,省 201 倍
· 只有最深最右的節點不同 → 149 次(仍省 26% —— 已匹配的左子樹要走完,但之後全砍)

而且「相同時恰好是 2n+1」與樹的形狀完全無關 —— 窮舉 n = 0..8 全部 2056 種樹形實測,每一種都一樣。

這在面試裡是個很好的觀察,值得主動說:「這題的最壞情況其實是答案為 true 的時候,因為那是唯一無法短路的情況。」它顯示你理解的是執行過程,而不只是複雜度符號。
A4. 因為遞迴不可能走得比「比較淺的那棵樹」更深。

兩個指標是並排往下走的。走到某個位置時,只要其中一棵先「用完」(該位置是 nullptr),就會立刻命中 base case 回傳,不會再往下探索另一棵樹剩下的部分。

所以總工作量受限於比較小的那棵樹,寫成 O(min(np, nq)) 比寫 O(n) 精確。

具體例子:一棵 10⁴ 節點的樹 vs 一棵單節點樹 —— 只要幾次呼叫就結束(比完根,兩邊各遞迴一次就碰到 nullptr),而不是 2×10⁴+1 次。

這個「min」在 572 子樹判斷那題會變得很重要:那題要對 root 的每個節點呼叫一次 isSameTree,總複雜度是 O(n × m) —— 而每次比較只花 O(min(...)) 而不是 O(n),實務上快得多(見 App 2)。

寫複雜度時,寫出「真正限制工作量的那個量」比套用一般公式更有價值。
A5. 會讓「用 p == q 比指標」這個嚴重的 bug 顯示 0 失敗、完美通過。

如果測試程式對「相等的配對」直接傳同一個物件(isSameTree(t, t)),那麼:
· 相等的配對 → p == q 為 true ✓(因為真的是同一個指標)
· 不相等的配對 → p == q 為 false ✓(不同物件)
兩種情況都「碰巧」正確 —— 這個把整棵樹比較退化成指標比較的 bug,會 100% 通過你的測試。

正確的做法:對 q 做 deep copy。本頁的 8165 個配對全部都對 q 做了 deep copy,才讓那 338 個「內容相等但物件不同」的配對現形。

同一份測資設計裡還有第二個關鍵決定:值域要「小」。對拍用的是 [0,3] 這種小字母表 —— 如果值域用 ±10⁴ 隨機取,幾乎每一對樹都會在第一個節點就明顯不同,「形狀相同但值不同」這一整類根本測不到。實測的配對組成也是刻意混合的(完全相同 / 差一個值 / 差一個結構 / 全隨機 各約 5 萬組),true 與 false 的比例是 55120 : 144880 —— 兩邊都有足夠樣本。

一般教訓:「測資怎麼造」和「程式怎麼寫」一樣會決定你抓不抓得到 bug。共用物件、值域過大、只測隨機資料 —— 這三個都會讓真實的 bug 隱形。
App 1. 把兩個遞迴的參數「交叉」配對,並改成拿同一棵樹的左右子樹當起點。

bool isMirror(TreeNode* a, TreeNode* b) {
    if (!a || !b) return a == b;             // ← 這一行一字不改

    return (a->val == b->val)
        && isMirror(a->left,  b->right)      // ← 交叉!左配右
        && isMirror(a->right, b->left);      // ← 交叉!右配左
}

bool isSymmetric(TreeNode* root) {
    return root == nullptr || isMirror(root->left, root->right);
}
只改了兩個字:left/right 的配對方式。base case 完全不用動 —— 「兩個都空 → 相同、只有一個空 → 不同」這件事,對「相等」和「鏡像相等」都成立。

有意思的是:這個「交叉版」正好是本題陷阱表裡的 M6(左右比錯邊)。實測它在原題上錯 365/8165,最小反例 p=[1,null,2] vs q=[1,null,2](兩棵一模一樣的樹被判成不同)。同一段程式碼,在這題是 bug、在 101 題是正解 —— 差別只在你要問的問題是什麼。

順帶一提,226 那題的 App 2 提過另一個做法:「翻轉右子樹再比較是否相同」。邏輯上也對,但它會改壞輸入 —— 而上面這個交叉遞迴完全不碰輸入,是更好的選擇。
App 2. 對 root 的每一個節點各呼叫一次 isSameTree。

bool isSubtree(TreeNode* root, TreeNode* subRoot) {
    if (root == nullptr) {
        return subRoot == nullptr;
    }

    return isSameTree(root, subRoot)              // 以「這裡」為起點試一次
        || isSubtree(root->left,  subRoot)        // 或者答案在左子樹裡
        || isSubtree(root->right, subRoot);
}
注意這裡用的是 || 而不是 &&:子樹判斷是「存在某個位置匹配」,而不是「處處都要匹配」。|| 同樣會短路 —— 一旦找到就不再往下找。

複雜度:O(n × m)(n = root 節點數,m = subRoot 節點數)。看起來很糟,但實務上快得多,原因正是上面 Q4 講的:每次 isSameTree 只花 O(min(...)),而且絕大多數位置在比到第一個值就短路了(實測:根值不同 → 1 次呼叫)。所以「n 次比較」裡,絕大部分是 O(1) 的。

如果要真正的線性解:把兩棵樹都序列化成帶 null 標記的字串(見 144 的 App 3),然後用 KMP 判斷子字串 —— O(n + m)。但要小心加分隔符號,否則值 1 和 12 會黏在一起造成假匹配。

面試時的順序:先給上面這個 O(n×m) 的直觀解並說明它為什麼實測不慢,再提序列化 + KMP 當作進階選項。
App 3. 用一個 stack(或 queue),但一次推入一對指標。

bool isSameTree(TreeNode* p, TreeNode* q) {
    stack<pair<TreeNode*, TreeNode*>> st;
    st.push({p, q});

    while (!st.empty()) {
        auto [a, b] = st.top();
        st.pop();

        if (!a && !b) {
            continue;                    // 兩個都空 → 這一對沒問題
        }
        if (!a || !b || a->val != b->val) {
            return false;                // 只有一個空,或值不同 → 立刻結束
        }

        st.push({a->left,  b->left});
        st.push({a->right, b->right});
    }

    return true;
}
關鍵是「成對推入」 —— stack 裡放的不是節點,而是「待比較的一對」。這樣就把「兩棵樹並排走」這件事顯式地表達出來了。

三種 null 情形仍然要處理,只是換了形式:「兩個都空」→ continue(這一對通過,不用往下);「只有一個空」→ 併進那個 return false 裡。遞迴版用 return p == q 一行搞定的事,迭代版拆成了 continue 和 return false 兩條路。

短路仍然存在:那個 return false 就是短路 —— 一發現不同立刻結束,剩下的配對全部不再處理,效果和遞迴版的 && 完全一樣。

用 stack 是 DFS、換成 queue 就是 BFS,兩者都對 —— 因為「兩棵樹是否相同」和檢查順序無關(和 226 翻轉一樣是「順序自由」的問題)。不過 BFS 有個實務優勢:它會先比較淺層,而淺層的差異通常更早被發現。
