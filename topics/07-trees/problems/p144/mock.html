A naive approach would be to read the tree level by level with a queue and then reorder the values into preorder. That doesn't work cleanly — a level mixes values from different subtrees, so I'd have to rebuild parent links to unmix them. More work and more risk, for the same O(n).

Here's the plan.

// invariant: preorder(ans, x) appends exactly x's subtree,
// in preorder, to the end of ans. Nothing else is touched.

preorder(ans, x):
  if x is empty → return
  ans.push_back(x.val)   // the node comes FIRST
  preorder(ans, x.left)  // then all of left
  preorder(ans, x.right) // then all of right

One: if the node is empty, return.
Two: push the node's value.
Three: recurse left, then right.

I'm using one shared vector<int> passed by reference, and every call only appends, so the three blocks land in order by themselves.

One thing worth flagging — inorder, preorder and postorder are the same function; only the position of the one push_back line changes. So I'll pick my test tree carefully: on a right-leaning chain, preorder and inorder give the same answer. The smallest tree that separates all three is [1,2,3].

There's a trade-off here: preorder is easy to write iteratively with a stack, but with 100 nodes the recursion is safe and reads like the definition, so I'll go recursive.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    vector<int> preorderTraversal(TreeNode* root) {
        vector<int> ans;
        preorder(ans, root);
        return ans;
    }

    void preorder(vector<int>& ans, TreeNode* root) {
        if (root == nullptr) return;   // the only base case

        ans.push_back(root->val);     // ① root: record on arrival, wait for no one
        preorder(ans, root->left);      // ② the whole left subtree
        preorder(ans, root->right);     // ③ the whole right subtree
    }
};

The main function makes an empty vector, calls the helper on the root, and returns it. The helper is exactly the plan: stop on nullptr, push the value, recurse left, recurse right.

One thing worth flagging — the base case is root == nullptr, not a leaf check. A leaf check would crash on the empty tree and on any node with one child, and every leaf would return before its push, so leaf values go missing. With null as the floor, a leaf needs no special case.

And the & on ans is required — without it each call fills its own copy, and a non-empty tree returns [].

• Single node [1]: push 1, then two empty calls.

Let me think about complexity here.

Time is O(n): exactly 2n + 1 calls, one per node plus one per empty link, because an n-node binary tree has exactly n + 1 empty links. Each call is constant work, and push_back is amortized O(1).

Space is O(h) for the call stack, where h is the height; the output vector is O(n), but that's the answer.

In the worst case the tree is a chain, so h = n; balanced, it's about log n. If the tree could be huge and skewed, I'd switch to the iterative stack version — push root, then pop, emit, push right, push left.

Oh, one more thing — the tree is only read, never changed, so it's safe to traverse again or share between readers.
