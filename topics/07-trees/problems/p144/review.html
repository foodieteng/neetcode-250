重點回顧// RECAP

面向要記住的那一句
本質前序 = 根 → 左 → 右,push_back 在兩個遞迴之前
核心直覺走到就收錄,不用等任何人 —— 三種走訪裡唯一如此
簽名性質 ①第一個元素恆為根(實測 2055/2055;而 back()==root 只中 1/2055)
簽名性質 ②輸出恆為 [根 | 整棵左子樹 | 整棵右子樹] —— 三段連續不交錯
為什麼重要「三段連續」是 105 重建二元樹、297 序列化的基礎
終止條件root == nullptr,不是葉節點判斷 —— 後者 197 種樹形全錯
呼叫次數恆為 2n + 1,與樹形完全無關(2056 種樹形實測)
複雜度時間 O(n),空間 O(h);與中序、後序成本完全相同
最危險的錯左右對調 —— 在所有鏈狀樹上碰巧全對(64/197,巧合率 32.5%)
測資鐵則永遠用 [1,2,3],不要用斜鏈 —— 斜鏈上前序與中序輸出相同

範例 Trace// 9 節點 → [1,2,4,5,6,7,3,8,9]

樹:根 1;1.left=2, 1.right=3;2.left=4, 2.right=5; 3.right=8;5.left=6, 5.right=7;8.left=9。 縮排 = 遞迴深度。以下每一步都是實跑印出來的。

// 根 + 整棵左子樹(前 6 個元素) preorder(node 1) ★ push_back(1) ans = [1] preorder(node 2) // 1 的左 ★ push_back(2) ans = [1,2] preorder(node 4) // 2 的左 ★ push_back(4) ans = [1,2,4] preorder(null) → return // 4 是葉節點 preorder(null) → return preorder(node 5) // 2 的右 ★ push_back(5) ans = [1,2,4,5] preorder(node 6) ★ push_back(6) ans = [1,2,4,5,6] preorder(null) ×2 → return preorder(node 7) ★ push_back(7) ans = [1,2,4,5,6,7] preorder(null) ×2 → return // 到這裡 [1 | 2,4,5,6,7] —— 根 + 整棵左子樹,「一整塊」排在一起
// 整棵右子樹(後 3 個元素) preorder(node 3) // 1 的右,現在才輪到 ★ push_back(3) ans = [1,2,4,5,6,7,3] preorder(null) → return // 3 沒有左子樹 preorder(node 8) // 3 的右 ★ push_back(8) ans = [1,2,4,5,6,7,3,8] preorder(node 9) // 8 的左 ★ push_back(9) ans = [1,2,4,5,6,7,3,8,9] preorder(null) ×2 → return preorder(null) → return // 8 沒有右子樹 // 右子樹的 3 個節點也是「一整塊」—— 沒有和左子樹的任何節點交錯
// OUTPUT return ans = [1,2,4,5,6,7,3,8,9] └┬┘ └───┬───┘ └──┬──┘ 根 整棵左子樹 整棵右子樹 統計:19 次 preorder() 進入(9 實節點 + 10 個 nullptr = 2n+1 = 2×9+1 ✓) 9 次 push_back 最大遞迴深度 4(節點 6 與 7 所在的那一層) // 對照:同一棵樹的中序是 [4,2,6,5,7,1,3,9,8] —— 根 1 被夾在正中間
把這個 trace 和中序那一頁的疊起來看: 同一棵樹、同樣 19 次呼叫、同樣 9 次 push_back, 差別只在每次 push_back 發生在哪一個時刻。 前序在「進入時」推、中序在「左邊回來後」推、後序在「兩邊都回來後」推。

// ANSWERS
A1. 第一個一定是根;最後一個沒有對應的保證。

push_back 是函式體的第一個動作(nullptr 檢查之後)。最外層那次呼叫傳進來的就是 root,所以它必定第一個被推進去,任何子樹的節點都排在它後面。

實測:窮舉 n = 1..8 全部 2055 棵樹,ans.front() == root->val 命中 2055/2055。

最後一個沒有保證 —— 作為對照組實測 ans.back() == root->val 只命中 1/2055,那唯一一棵是單節點樹(頭尾同一格)。

「根在最後」是後序的簽名,不是前序的。三種走訪的根位置各自是:前序最前、後序最後、中序在「左子樹節點數」那一格。記住這三句,就能一眼認出一串輸出是哪種走訪。
A2. 「三段連續」= 左子樹的所有節點是一整塊、右子樹的所有節點也是一整塊,兩塊不交錯。

前序輸出永遠長這樣:[根 | 整棵左子樹的前序 | 整棵右子樹的前序]。以本頁範例樹為例:[1 | 2,4,5,6,7 | 3,8,9]。中序就不是這樣 —— 中序是 [左子樹 | 根 | 右子樹],根被夾在中間。

為什麼這讓重建成為可能:
① 前序的第一個元素 —— 直接讀出根是誰(這是前序給的資訊)。
② 拿這個根去中序裡找位置 —— 它左邊的所有元素就是左子樹、右邊的就是右子樹(這是中序給的資訊)。於是我們知道了左子樹有幾個節點,設為 k。
③ 回到前序:根後面的 k 個就是左子樹的前序,再後面的就是右子樹的前序 —— 而這一步之所以能切,正是因為「三段連續」。如果左右子樹的節點在前序裡是交錯的,你根本不知道該切在哪。
④ 對兩半遞迴。

一句話:前序告訴你「誰是根」,中序告訴你「左右各有多少」,兩個資訊合起來才唯一決定一棵樹。
A3. 因為左右對調在所有「鏈狀樹」上碰巧完全正確 —— 這一族佔了 32.5%。

實測:窮舉 n = 0..6 共 197 種樹形,左右對調錯 133 種、對 64 種。這 64 種的分佈是 1, 1, 2, 4, 8, 16, 32,也就是 n ≥ 1 時的 2ⁿ⁻¹。

這一族的共同特徵:每個節點至多只有一個小孩 —— 也就是鏈狀樹。注意不只是純左鏈或純右鏈,而是任何左右轉彎的單子鏈都算,例如 [1,null,2,3]、[1,2,null,null,3]。

為什麼:交換 left 和 right 的遞迴順序,只有在「兩邊都有東西」時才看得出差別。如果每個節點至多一個小孩,那麼其中一邊永遠是 nullptr —— 先走空的還是先走非空的,結果一模一樣。

最小反例是 [1,2,3]:根同時有左右小孩,正解 [1,2,3]、對調後 [1,3,2]。

教訓:測資裡一定要有「同時擁有左右小孩」的節點。這也是為什麼本頁所有陷阱表都是窮舉 197 種樹形跑出來的 —— 這個 bug 的巧合率高到單靠幾筆手寫測資幾乎必然漏掉。
A4. 因為 stack 是後進先出 —— 要讓左邊先被處理,就必須把它後放。

vector<int> ans;
if (root == nullptr) return ans;
stack<TreeNode*> st;
st.push(root);
while (!st.empty()) {
    TreeNode* curr = st.top(); st.pop();
    ans.push_back(curr->val);
    if (curr->right) st.push(curr->right);   // 先放右
    if (curr->left)  st.push(curr->left);    // 後放左 → 先被 pop
}
寫反了(先 push left 再 push right)會得到「鏡像前序」 —— 也就是 根 → 右 → 左。這正是上一題那個左右對調的變體,會錯 133/197 種樹形,而且在鏈狀樹上還是碰巧全對,所以你很可能測不出來。

記法:stack 的 push 順序和 pop 順序永遠相反。你想要的輸出順序是「左先」,所以 push 順序就要「右先」。每次寫 stack 版走訪都要停下來問一次這件事。

順帶一提,這個迭代版比中序的迭代版簡單很多 —— 原因見 App 2。
A5. 三者的工作量完全相同;看到的時間差是量測雜訊與快取效應,不是演算法差異。

指令數層面 —— 完全相同:同樣的 n = 100 樹,三者的呼叫次數都是 201(2n+1),差 0。這不是巧合:三份程式碼只差 push_back 那一行的位置,遞迴結構一個字都沒變。

牆鐘層面(10⁵ 次重複,實測):
· 平衡樹 → 前序 77.7ms、中序 75.9ms、後序 74.0ms(差異在雜訊內)
· 退化左鏈 → 前序 116.3ms、中序 122.3ms、後序 134.9ms
· 退化右鏈 → 前序 69.1ms、中序 69.7ms、後序 127.6ms(後序慢了 1.85 倍)

怎麼解讀:注意差異的正負號會隨樹形翻轉 —— 平衡樹上後序最快,右鏈上後序最慢。一個真正的演算法差異不會這樣忽正忽負。這種模式是分支預測與記憶體存取樣式造成的,和「哪一種走訪比較快」無關。

面試時的正確答案:「三者複雜度完全相同,都是 O(n) 時間、O(h) 空間,指令數也一樣 —— 選哪一種只看你要什麼順序,不看效能。」拿牆鐘差異去論證「前序比較快」是過度解讀量測雜訊,反而扣分。
App 1. 前序給「誰是根」,中序給「左右各多少」—— 缺一不可。

作法:
① 取前序的第一個元素 → 就是根。
② 在中序裡找到這個值的位置 i → 中序的 [0, i) 是左子樹、(i, end) 是右子樹,左子樹有 k = i 個節點。
③ 回到前序,根後面的 k 個是左子樹的前序、再後面的是右子樹的前序(靠的就是「三段連續」)。
④ 對兩半遞迴。

優化:第 ② 步的「在中序裡找位置」如果每次都線性掃,總複雜度會退化成 O(n²)。先用一個 unordered_map<int,int> 把「值 → 中序下標」建好,查詢就變 O(1),整體 O(n)。(這也是為什麼那題會保證節點值互不相同 —— 否則這個 map 就建不起來。)

為什麼只有前序不夠:前序 [1,2] 可能來自「2 是 1 的左小孩」,也可能來自「2 是 1 的右小孩」 —— 兩棵不同的樹,前序完全相同。前序只說了「1 在 2 前面」,沒說 2 掛在哪一邊。中序補的正是這個資訊:中序 [2,1] 表示 2 在左、[1,2] 表示 2 在右。

順帶一提:「前序 + 後序」則不足以唯一決定一棵樹(單子節點的情形仍然有歧義)—— 必須是「前序 + 中序」或「後序 + 中序」。中序是那個不可或缺的。
App 2. 因為前序「走到就收錄」,所以節點被 pop 出來的當下就能直接輸出 —— 不必記住任何額外狀態。

骨架見 A4:pop → 輸出 → push right → push left,四行。

對比中序的迭代版(見 94 那一頁的 App 1):它需要一個雙層迴圈 —— 外層判斷「還有沒有東西要做」,內層「一路往左壓到底」,pop 出來之後還要轉向右子樹。

差別的根源:中序必須回答「這個節點的左子樹做完了沒」。遞迴版靠函式 return 自動回答;顯式版沒人幫你記,得靠「一路往左壓到底,pop 出來就代表左邊做完了」這個技巧來間接表達。

前序根本不需要問這個問題 —— 它進來就收錄,沒有任何「等待」要追蹤。所以狀態機退化成「一個 stack、pop 就輸出」。

一般規律:走訪的迭代版有多複雜,取決於那個順序需要「等」多久。前序不等(最簡單),中序等左邊(中等),後序要等兩邊,迭代版最麻煩 —— 標準技巧是走「根 → 右 → 左」再把結果整個反轉,或者額外記一個「上次訪問的節點」來判斷右子樹回來了沒。
App 3. 因為前序的第一個就是根,反序列化時可以「邊讀邊建」,一次掃完。

序列化:跑前序,但連 nullptr 也要輸出一個標記(例如 #):
void ser(TreeNode* root, string& out) {
    if (root == nullptr) { out += "#,"; return; }
    out += to_string(root->val) + ",";
    ser(root->left, out);
    ser(root->right, out);
}
反序列化:維護一個「讀到第幾個」的游標,每次取出一個 token:是 # 就回傳 nullptr,否則建節點,然後遞迴建左、遞迴建右 —— 順序和序列化時完全一樣,所以游標一路往前走就對了,不用回頭。

為什麼 null 標記不能省:這正是 App 1 提到的歧義 —— 沒有 #,前序 [1,2] 分不出 2 是左小孩還是右小孩。加上 null 標記之後,前序序列就唯一決定一棵樹了,不再需要中序來補資訊。

為什麼前序比中序、後序適合:
· 前序 —— 根先出現,反序列化時先建根再建子樹,遞迴方向和讀取方向一致,一次掃完。
· 中序 —— 根在中間,你不知道該在哪裡切,即使加了 null 標記也還原不出來(這是中序的已知缺陷)。
· 後序 —— 可以做,但要從後往前讀(根在最後),而且左右子樹的建立順序要跟著反過來,比較容易寫錯。

所以 297 題的標準解就是「前序 + null 標記」。另一個常見選擇是 BFS 層序(LeetCode 自己顯示樹的格式就是這個),但遞迴寫起來沒有前序漂亮。
