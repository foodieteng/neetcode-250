Hmm, let me think about this for a second.

A naive approach would copy the rule word for word: scan the whole tree, delete every target leaf, and repeat until a scan deletes nothing. It's correct, but a long chain of targets needs a fresh scan for every level, so that's O(n²) work.

This problem reminds me of post-order DFS — the pattern for when a parent's answer depends on its children's final answers. I clean the left subtree, clean the right subtree, and then look at the node. By then its children are final, so the chain reaction happens for free, in one pass.

CANDIDATE

Here's the plan.

// f(node) = root of the cleaned subtree (or null)
f(null)       → null
node.left  = f(node.left)   ← children first
node.right = f(node.right)
if node is now a leaf and node.val == target → null
else → node
// invariant: when we check a node, its children are final

One: null returns null.
Two: clean both children and write the results back into left and right — a child that comes back nullptr was deleted.
Three: if the node is now a leaf with the target value, return null; otherwise return the node.

One thing worth flagging — the order is a correctness requirement, not a style choice. Take [1,null,1] with target 1. Pre-order checks the root while it still has a child, keeps it, deletes the child, and never looks at the root again. It returns [1] instead of an empty tree — and it fails 37,770 exhaustive cases.

There's a trade-off here: an explicit stack is safer for very deep trees, but 3000 levels is fine, and recursion is easier to check. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    TreeNode* removeLeafNodes(TreeNode* root, int target) {
        if (!root)
            return nullptr;

        // ① clean both subtrees first and attach the results back (a deleted one returns nullptr)
        root->left = removeLeafNodes(root->left, target);
        root->right = removeLeafNodes(root->right, target);

        // ② now the children are final: delete self only if all three conditions hold
        return (!root->left && !root->right && root->val == target) ? nullptr
                                                                    : root;
    }
};

Base case first. Then I clean both children and assign the results back. The last line asks one question: is this node a leaf now, and is it the target? If yes, return nullptr; if not, return the node.

One thing worth flagging — that assignment back into root->left and root->right is not optional. If I call the recursion and throw away the result, the parent still points to the deleted child, so [1,null,1] stays unchanged. And the leaf test needs &&, not ||. With ||, a node with only one child counts as a leaf, so [1,null,2] with target 1 returns an empty tree, losing a child that should stay.

Let me think about complexity here.

Time is O(n): each node is visited once, and each null child is one quick call — exactly 2n + 1 calls, so 6001 for 3000 nodes. Space is O(h), just the call stack.

In the worst case the tree is a straight chain, 3001 calls deep, and that runs fine; a balanced tree is only 13 calls deep. For something like a million nodes, I'd switch to the explicit stack.

Oh, one more thing — my code cuts deleted nodes out but never frees them. On an all-target chain that's 3000 leaked nodes. LeetCode accepts that, but in production C++ I'd delete root right before returning nullptr, or use smart pointers.
