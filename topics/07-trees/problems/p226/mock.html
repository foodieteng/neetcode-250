Good. Then let me say what a mirror means in terms I can test.

If I read the tree left to right — that's an inorder walk — mirroring should give me the same values back in the opposite order. So inorder of the inverted tree is the reverse of inorder of the original.

I want to be careful not to over-claim, though: the same is not true for preorder. Preorder always puts the root first, and reversing would put it last, so the two only agree on a tree of zero or one nodes. Inorder works because it's the only one of the three where the node sits between its two subtrees.

Hmm, let me think about this for a sec.

A naive approach would be to read the tree level by level, reverse each level's values, and write them back. That only moves values, never shape — on a lopsided tree like [1,null,2], the lone child stays on the right, so it's simply wrong, and it builds extra arrays too.

This problem reminds me of the standard depth-first recursion on a tree. The mirror of a tree is: mirror the left subtree, mirror the right subtree, then swap the two child pointers. The definition is recursive, so the code can be too.

P — plan
C
CANDIDATE

Here's the plan.

// invariant: invertTree(x) mirrors the whole subtree at x
// and returns x itself — same node, never a new one.

invertTree(x):
  if x is empty → return empty
  x.left  = invertTree(x.left)  // mirror below first
  x.right = invertTree(x.right)
  swap(x.left, x.right)      // then swap the pointers
  return x

One: if the node is empty, return empty.
Two: mirror the left subtree and the right subtree.
Three: swap the two child pointers and return the node.

Here, I'm using the return value to keep track of the subtree root; since I mutate in place, it's always the node I was handed.

One thing worth flagging — I swap the child pointers, not the values. Swapping values moves numbers while the shape stays the same, which is wrong whenever the two sides have different shapes, and it skips any node with only one child. Swapping pointers moves the whole subtree, shape and all.

There's a trade-off here: an explicit queue avoids recursion depth, but it's more lines, and with 100 nodes recursion is safe.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up.

class Solution {
public:
    TreeNode* invertTree(TreeNode* root) {
        if (root == nullptr) return nullptr;

        root->left = invertTree(root->left);     // ① left subtree mirrored first
        root->right = invertTree(root->right);   // ② right subtree mirrored too
        swap(root->left, root->right);          // ③ then swap my own two pointers

        return root;
    }
};

nullptr returns nullptr; otherwise I invert both subtrees, assign them back, swap the two pointers, and return the root.

One thing worth flagging — I recurse first and swap after, so the swaps happen on the way back up, in postorder: the deepest nodes first, the root last.

That's not a requirement. Swapping first and then recursing is also correct, because the swap at a node and the mirroring inside its subtrees touch different pointers. What matters is that every node gets swapped exactly once, and that I swap pointers rather than values.

And a leaf still swaps two null pointers — a harmless no-op.

Corner cases:

• Empty tree []: returns nullptr.
• Single node [1]: swaps two nulls and comes back unchanged — it's its own mirror.
• [1,2] → [1,null,2] — exactly the case a value swap would skip, since there's no second value to pair with.

Let me think about complexity here.

Time is O(n): exactly 2n + 1 calls, one per node plus one per empty link, since an n-node binary tree has exactly n + 1 empty links. Constant work each.

Space is O(h) for the call stack, where h is the height, and I allocate nothing — no new nodes, no extra arrays.

In the worst case the tree is one long chain, so h = n; balanced, it's about log n. At 100 nodes that's not a concern; on a very deep tree I'd switch to the queue version.

Oh, one more thing — this is fully in place: same nodes, same returned root. The flip side is that the original tree is gone, so if a caller still needs it, I'd copy first and say so at the API boundary.
