PART A · 觀念題// 5 題 × 10 分

第 1 題10 分
為什麼要交換子樹指標而不是交換節點的值?請給最小反例,並說出換值會犯的兩種病。
解答與說明 · ANSWER▾
因為換一根指標就搬動整棵子樹,換值只搬得動一個節點。最小反例是 [1,null,2]。

病一:單邊子樹時,swap 根本不會發生。[1,null,2] 只有右小孩,root->left 是 nullptr。想換值就得寫 swap(root->left->val, root->right->val) —— 解參考 nullptr 直接爆。加上「兩邊都非空才換」的保護之後,它就什麼都不做了:輸出 [1,null,2],正解是 [1,2]。

病二:就算兩邊都在,換值也只換了「一個節點的內容」,形狀完全沒動。任何左右形狀不同的樹都會壞掉。

實測:窮舉 197 種樹形錯 194 種。巧合對的只有 3 種:[]、[1]、[1,2,3] —— 而 [1,2,3] 過關純屬巧合(兩個孩子都是葉節點,換值和換子樹剛好結果相同)。只要任一孩子有自己的後代、或某節點只有一個孩子,立刻現形。

一句話:指標是「整棵子樹的把手」,值只是一個節點的內容物。
第 2 題10 分
如果把 swap 移到兩個遞迴呼叫之前,還對嗎?為什麼?請給實測依據。
解答與說明 · ANSWER▾
還是對的 —— 實測窮舉 197 種樹形,失敗 0 種。

這常被誤當成陷阱,擔心「先換了,遞迴進去的不就是已經被搬過的孩子嗎?」

為什麼沒問題:翻轉是「上下無關」的操作。
· swap(root->left, root->right) 動的是 root 自己的兩根指標。
· invertTree(子樹) 動的是 子樹「內部」的指標。
兩者碰的是不同的東西,互不干擾。而且每個孩子「要被翻成什麼樣子」只取決於它自己的結構,和「它現在掛在左邊還是右邊」完全無關 —— 所以先換再各自翻、和先各自翻再換,結果同構。

對比:這一點和 145 後序那類題目正好相反。在 104(求深度)、110(判平衡)、543(求直徑)裡,「自己的答案依賴子樹的答案」,順序就是死的,必須後序。而翻轉不依賴子樹的任何回傳資訊,所以順序自由。

判斷法則:問「我這一步需要子樹先算出什麼東西給我嗎?」需要 → 順序固定;不需要 → 順序自由。
第 3 題10 分
怎麼驗證你的翻轉真的對了?請給一條可以直接寫成測試的恆等式,並說明為什麼不能用前序版。
解答與說明 · ANSWER▾
用中序:inorder(invert(T)) == reverse(inorder(T))。

這是「鏡射」的一個可以直接寫成測試的定義:把樹左右照鏡子之後,由左而右讀出來的順序,恰好是原本的倒序。

實測:窮舉 n = 0..8 全部 2056 棵樹,命中 2056/2056,零反例。

用本頁的範例驗算:原樹中序 [1,2,3,4,6,7,9] → 翻轉後中序 [9,7,6,4,3,2,1] ✓。

為什麼不能用前序:preorder(invert(T)) == reverse(preorder(T)) 只命中 2/2056(只有 n ≤ 1 的平凡情形)。
原因很直接:前序把根釘在第一個,但反轉會把根丟到最後 —— 這兩件事天生矛盾,只有在「頭尾同一格」(單節點)時才碰巧相容。最小反例 [1,null,2]:preorder = [1,2]、reverse = [2,1],但 preorder(invert) = [1,2]。

只有中序撐得住反轉,因為它的結構是 [左 | 根 | 右] —— 根在中間、左右對稱,鏡射之後就變成 [右' | 根 | 左'],整個反轉剛好對上。

另一條也很好用的性質:invert(invert(T)) == T(實測 2056/2056) —— 翻兩次會還原,所以 invert 是自身的反函數。
第 4 題10 分
手寫 swap 時忘了暫存變數(a = b; b = a;),症狀是什麼?會當場崩潰嗎?
解答與說明 · ANSWER▾
症狀有兩種,而且都不會當場崩潰 —— 這才是最麻煩的地方。

錯誤寫法:root->left = root->right; 然後 root->right = root->left;。第二行讀到的 left 已經被第一行改掉了,所以等於 right = right。

實測兩種病狀(都是真的量出來的):
① 弄丟節點 —— [1,2](只有左孩子):distinct 節點數 before = 2 → after = 1。左子樹被 nullptr 覆蓋,那個節點從樹上消失、也沒被釋放 = 記憶體洩漏。
② 製造別名 —— [1,null,2](只有右孩子):輸出印成 [1,2,2]。同一個節點同時掛在 left 和 right 兩個槽,節點數「看起來」從 2 變成 3。

為什麼「不崩潰」比崩潰更糟:兩種病狀都是答案悄悄變錯,不是拋例外。而別名共享在真實系統裡更危險 —— 之後要釋放這棵樹時會 delete 同一個節點兩次(double free),那時才崩,而且崩在離現場很遠的地方。

修法:直接用 std::swap(root->left, root->right);非要手寫就三行,先存 tmp。實測窮舉 197 種樹形,這個 bug 錯 195 種,只有 [] 和 [1] 倖免。
第 5 題10 分
程式碼裡的 root->left = invertTree(root->left); —— 這個回寫是必要的嗎?什麼情況下它會變成必要?
解答與說明 · ANSWER▾
在這題是冗餘的;但在「會替換節點」的操作裡就變成必要。

為什麼這題冗餘:invertTree() 回傳的永遠就是傳進去的那個指標 —— 它只交換孩子,從不建立或替換節點。實測 2000 棵隨機非空樹,invertTree(root) == root 命中 2000/2000。所以 root->left = invertTree(root->left) 實際等於 root->left = root->left,寫成下面這樣完全等價:
invertTree(root->left);
invertTree(root->right);
swap(root->left, root->right);
什麼時候會變成必要 —— 當遞迴「可能回傳不同的節點」時。典型例子:
· BST 插入(LeetCode 701):往空位插入時會 new 一個新節點,那個新節點必須被接回父節點,靠的就是 root->left = insert(root->left, val);。
· BST 刪除(LeetCode 450):刪掉一個節點後,子樹的根會換人,同樣得靠回寫接回去。
· 刪除葉節點(LeetCode 1325):子樹可能整棵消失變成 nullptr。

這個「node->child = recurse(node->child)」的回寫模式,是所有「會改變樹結構」的遞迴的標準骨架。它讓「這一層可能換掉子樹的根」這件事自動被處理掉,不必在父節點裡寫一堆 if。

面試時值得主動說:「這個回寫在本題是冗餘的,因為節點不會被替換;但我習慣這樣寫,因為換成 BST 插入或刪除時它就是必要的。」

PART B · 手走模擬// 1 題 × 10 分

第 6 題10 分
拿一張紙,照程式手走 [4,2,7,1,3,6,9] → [4,7,2,9,6,3,1]:逐步寫出關鍵變數的變化,最後回傳什麼?決定結果的是哪一步?
解答與說明 · ANSWER▾

官方範例。注意 swap 發生的順序是後序的 —— 1 → 3 → 2 → 6 → 9 → 7 → 4,根在最後。 以下每一步都是實跑印出來的。

// 左半邊:下潛到底,然後回程 swap ENTER invertTree(node 4) // 根,先不動 ENTER invertTree(node 2) // 也先不動 ENTER invertTree(node 1) invertTree(null) → return nullptr invertTree(null) → return nullptr ★ SWAP 於 node 1: L=null <-> R=null (葉子,無效果) RETURN node 1 ENTER invertTree(node 3) invertTree(null) ×2 → return nullptr ★ SWAP 於 node 3: L=null <-> R=null (葉子,無效果) RETURN node 3 ★ SWAP 於 node 2: L=子樹(1) <-> R=子樹(3) ← 第一次真的動到東西 RETURN node 2 // 2 現在是 (3, 1) // 葉節點也照樣執行 swap,只是交換兩個 nullptr —— 程式碼裡沒有葉節點的特判
// 右半邊:完全相同的流程 ENTER invertTree(node 7) ENTER invertTree(node 6) invertTree(null) ×2 → return nullptr ★ SWAP 於 node 6: 無效果 RETURN node 6 ENTER invertTree(node 9) invertTree(null) ×2 → return nullptr ★ SWAP 於 node 9: 無效果 RETURN node 9 ★ SWAP 於 node 7: L=子樹(6) <-> R=子樹(9) RETURN node 7 // 7 現在是 (9, 6)
// 最後一步:根 ★ SWAP 於 node 4: L=子樹(2) <-> R=子樹(7) 注意此時 子樹(2) 已經是 (3,1)、子樹(7) 已經是 (9,6) → 根只需要把「這兩整塊」對調,不必管它們內部長什麼樣 RETURN node 4
// OUTPUT return root = [4,7,2,9,6,3,1] 統計:16 次 invertTree() 進入(7 實節點 + 8 個 nullptr = 2n+1 = 2×7+1 ✓) 7 次 SWAP(每個實節點一次;其中 4 次發生在葉子上,交換 null <-> null 無效果) SWAP 順序:1 → 3 → 2 → 6 → 9 → 7 → 4 ← 完全是後序,根在最後 // 全程零配置:節點位址集合前後完全相同,回傳的就是傳進來的那個 root
用中序檢查這個結果:原樹中序 = [1,2,3,4,6,7,9], 翻轉後中序 = [9,7,6,4,3,2,1] —— 恰好是倒序 ✓。 這就是 inorder(invert(T)) == reverse(inorder(T)) 的具體樣子, 也是你在面試現場最快能自我驗證的方法。

PART C · 應用題// 3 題 × 13–14 分

第 7 題13 分
用迭代寫翻轉(不准遞迴)。用 BFS 還是 DFS?程式碼骨架長什麼樣?
解答與說明 · ANSWER▾
BFS 或 DFS 都可以 —— 因為順序無關(見 第 2 題),隨便挑一個好寫的。

BFS 版(用 queue,最直觀):
TreeNode* invertTree(TreeNode* root) {
    if (root == nullptr) return nullptr;

    queue<TreeNode*> q;
    q.push(root);

    while (!q.empty()) {
        TreeNode* curr = q.front();
        q.pop();
        swap(curr->left, curr->right);      // 出隊就換,順序無所謂

        if (curr->left)  q.push(curr->left);
        if (curr->right) q.push(curr->right);
    }

    return root;
}
把 queue 換成 stack 就是 DFS 版,其他一個字都不用改 —— 這正是「翻轉是上下無關操作」的最好證明:走訪順序完全不影響結果。(對比:如果是求深度或判平衡,你就不能這樣隨便換,因為那些需要子樹先回報結果。)

複雜度:時間仍是 O(n)。空間變成 O(w)(w = 最大寬度)而不是 O(h) —— 對平衡樹來說 BFS 其實更耗空間(最底層有 n/2 個節點),對退化鏈則相反(BFS 佇列裡永遠只有 1 個)。迭代版的真正好處不是省空間,是不會 stack overflow(queue 用的是 heap)。

上面這個 BFS 版正是本頁對拍用的獨立參考解 —— 20 萬組零不一致。
第 8 題13 分
判斷一棵樹是不是左右對稱(LeetCode 101)。能不能「翻轉右子樹然後比較兩邊相等」?這樣做有什麼副作用?更好的做法是什麼?
解答與說明 · ANSWER▾
可以,但會「改壞輸入」;更好的做法是寫一個「鏡像比較」的雙參數遞迴。

「翻轉右子樹再比較」的做法:invert(root->right),然後檢查 isSameTree(root->left, root->right)。邏輯上正確,因為對稱的定義就是「左子樹 = 右子樹的鏡像」。

副作用:它把輸入改壞了。函式回傳時,原樹的右半邊已經被翻掉,整棵樹不再是原來那棵。這是一個純查詢函式產生了寫入的副作用 —— 在面試裡一定要主動說出來,並補一句「如果呼叫端還要用這棵樹,我會在回傳前再翻一次還原」。而且它還多跑了一趟 O(n)。

更好的做法 —— 直接寫「鏡像比較」,不修改任何東西:
bool isMirror(TreeNode* a, TreeNode* b) {
    if (a == nullptr && b == nullptr) return true;
    if (a == nullptr || b == nullptr) return false;

    return a->val == b->val
        && isMirror(a->left,  b->right)     // 交叉比較!
        && isMirror(a->right, b->left);
}
// isSymmetric(root) 就是 root == nullptr || isMirror(root->left, root->right)
關鍵在那兩行「交叉」:a 的左要和 b 的右比。「交叉遞迴」本身就表達了鏡像,所以完全不需要真的去翻轉任何東西。時間 O(n)、空間 O(h),而且不碰輸入。

一般原則:能用「比較」表達的,就不要用「修改再比較」—— 少一個副作用就少一類 bug。
第 9 題14 分
節點數放大到 10⁵,而且測資含退化成鏈的樹。這份遞迴會怎樣?請給實測依據。
解答與說明 · ANSWER▾
這份遞迴在 10⁵ 的退化鏈上還撐得住 —— 我量過臨界值是 26 萬層。

實測數字:每層 64 bytes(n=5000 的鏈量到 320224 bytes,收斂到 64.0),系統 ulimit -s = 8176 KB。二分實測崩潰臨界:261327 層存活、261718 層 SIGSEGV。

所以 10⁵ = 100000 < 261327 —— 會過,但餘裕只剩 2.6 倍。

但我不會直接說「安全」,因為這個數字不可移植:
① 崩潰臨界完全取決於 ulimit -s。評測機常見的 1 MB 或 512 KB 堆疊會把臨界壓到 三萬多層 / 八千層 —— 10⁵ 就過不了。
② frame 大小取決於編譯器和最佳化等級。同一份程式碼,加了量測探針就從 64 bytes 變成 80,臨界跟著往下掉。「在我機器上跑得過」對這類問題不算證據。

我會怎麼改 —— 換成 第 7 題 的迭代版。理由:queue/stack 的儲存在堆積上,上限是可用記憶體而不是 8 MB。空間複雜度沒有變好(O(w) 對 O(h),平衡樹上 BFS 甚至更耗),但它不會 stack overflow —— 同樣的複雜度、不同的失敗模式。

面試講法:「這題 n ≤ 100,遞迴有 2613 倍餘裕,我會直接寫遞迴。如果 n 到 10⁵ 而且樹可能退化,我會改迭代 —— 呼叫堆疊有硬上限,heap 沒有。」
