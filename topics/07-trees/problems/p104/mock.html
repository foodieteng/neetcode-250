Hmm, let me think about this for a sec.

A naive approach would be to list every root-to-leaf path, measure each one, and take the longest. That works, but it stores paths I never need — the number of leaves can be linear in n.

This problem reminds me of a plain post-order DFS, the "solve the children first, then combine" shape. It fits because the answer at a node is a pure function of the two child answers.

BFS by levels is the other option. It also gives the right answer, but its queue can hold about n/2 nodes at the widest level. I'll go with recursion because the code is two lines and the combine step is obvious. If the tree could be very deep, BFS would be the safer pick.

P — plan
C
CANDIDATE

Here's the plan.

// contract: maxDepth(x) = number of nodes on the
// longest path from x down to a leaf

maxDepth(null) = 0
maxDepth(x)    = 1 + max(maxDepth(x.left), maxDepth(x.right))

One: an empty subtree returns 0.
Two: otherwise, recurse into both children.
Three: return one plus the bigger of the two.

One thing worth flagging — the base case has to return 0, not 1. If it returns 1, every answer comes out exactly one too big — not one per level.

The reason is that max is transparent to a shared offset: 1 + max(a+1, b+1) equals (1 + max(a,b)) + 1. The extra one rides along instead of piling up. Over every tree shape up to 7 nodes, the error was +1 every time.

There's a trade-off here. Recursion uses a call stack as deep as the tree; BFS doesn't. For this input size recursion is fine. Does this approach sound good, or would you rather I think of another way?

I — implement

CANDIDATE

Alright, let me code this up.

class Solution {
public:
    int maxDepth(TreeNode* root) {
        if (root == nullptr) return 0;   // empty tree has no nodes, depth 0

        return 1 + max(maxDepth(root->left),    // how deep the left side is
                       maxDepth(root->right));  // how deep the right side is → take the deeper one, add this level
    }
};

The null check returns 0, and the second line is one plus the max of the two recursive calls.

One thing worth flagging — max here is an ordinary function, not a short-circuit operator like &&. Both arguments are evaluated before max runs, so both recursive calls always happen; no side is ever skipped.

That's why the work is completely predictable: one call per node plus one per empty slot, and a tree with n nodes has n + 1 empty slots. So it's exactly 2n + 1 calls, whatever the shape.

The only row where max makes a real choice is the root: it sees 1 on the left and 2 on the right, throws the left away, and returns 3. Everywhere else the two sides tie. Eleven calls, matching 2n + 1 with n = 5.

Corner cases:

• Empty tree → hits the guard, returns 0.
• Single node → 1 + max(0, 0), which is 1.
• A left-going chain of 5 nodes → 5.
• Swap max for + → still compiles, but silently counts nodes instead.

Let me think about complexity here.

Time is O(n): every node is visited once with O(1) work, and the exact call count is 2n + 1.

Space is O(h) for the call stack. In the worst-case scenario the tree is one long chain, so h = n and the stack is O(n); on a balanced tree it's O(log n).

Oh, one more thing — since the call count doesn't depend on shape, the running time is fully determined by n. Shape only changes the stack depth, never the number of calls, and that's a direct result of max not short-circuiting.
