範例 Trace// [3,9,20,null,null,15,7] → 3

官方範例:根 3;3.left=9(葉)、3.right=20; 20.left=15、20.right=7(都是葉)。 以下每一步都是實跑印出來的。縮排 = 遞迴深度。

// 下潛:一路走到 nullptr,途中什麼都沒算 1. ENTER maxDepth(node 3) [root] 2. ENTER maxDepth(node 9) [3.left] 3. ENTER maxDepth(nullptr) [9.left] 4. return 0 ← 第一個數字誕生 5. ENTER maxDepth(nullptr) [9.right] 6. return 0 7. return 1 + max(0, 0) = 1 ← 節點 9 回報 1 // 步驟 1~3 完全沒有計算 —— 只是「走到底」
// 右半邊:兩個葉節點各回報 1 8. ENTER maxDepth(node 20) [3.right] 9. ENTER maxDepth(node 15) [20.left] 10. ENTER maxDepth(nullptr) → return 0 12. ENTER maxDepth(nullptr) → return 0 14. return 1 + max(0, 0) = 1 ← 節點 15 回報 1 15. ENTER maxDepth(node 7) [20.right] 16. ENTER maxDepth(nullptr) → return 0 18. ENTER maxDepth(nullptr) → return 0 20. return 1 + max(0, 0) = 1 ← 節點 7 回報 1 21. return 1 + max(1, 1) = 2 ← 節點 20 回報 2(兩邊一樣深)
// 根節點:max 在這裡真正發揮作用 22. return 1 + max(1, 2) = 3 ↑ ↑ │ └─ 節點 20 回報的 2 └──── 節點 9 回報的 1 ← 被 max 丟掉 FINAL = 3
// OUTPUT return 3 統計:11 次 maxDepth() 呼叫(5 實節點 + 6 個 nullptr = 2n+1 = 2×5+1 ✓) 6 次 return 0(每個 nullptr 一次)—— 所有數字的起點 最大遞迴深度 3 數字的成長路徑: 0(nullptr) → 1(葉節點 9、15、7) → 2(節點 20) → 3(根) // 答案 3 對應的最長路徑是 3 → 20 → 15(或 3 → 20 → 7),共 3 個節點
整個 trace 裡,max 只有在最後一步真正做了決定 —— 前面幾次都是 max(0,0) 或 max(1,1),兩邊一樣。 只有根節點的 max(1, 2) 丟掉了一條比較短的路。 這就是為什麼「左右不對稱」的測資才測得出 max 有沒有寫對。

應用題// APPLICATION

App 1. 用 BFS 逐層算最大深度(不用遞迴)。骨架長什麼樣?它和遞迴版相比,空間上誰比較好?
App 2. 改成算 LeetCode 111 最小深度。要改哪裡?為什麼不能只把 max 換成 min?
App 3. 用這題的骨架寫 LeetCode 543 二元樹的直徑。要多加什麼?為什麼不能只看根節點的左右深度相加?
// ANSWERS
A1. 因為 nullptr 不是節點;而且錯誤是固定的 +1,不會放大。

深度的定義是「路徑上的節點數」,而 nullptr 代表「這裡沒有樹」,它不佔一個節點。所以空樹的深度是 0。

為什麼錯誤不會放大 —— 因為 max 不累加偏移。設 H' 是錯誤版本、H 是正確版本,假設左右子樹都偏移了 1:
H'(x) = 1 + max(H(左)+1, H(右)+1) = 1 + max(H(左), H(右)) + 1 = H(x) + 1
兩邊「同時 +1」可以被提到 max 外面,所以偏移一路乾淨地傳上來,始終是 1。

實測:窮舉 n = 0..7 共 626 種樹形全錯,而且 H'(t) − H(t) 的取值集合只有 {1} 這一個值 —— 與樹形完全無關。連空樹都回 1。

對比:如果換成加法(1 + 左 + 右),偏移就會翻倍累積,那才是「越深錯越多」。「max 對常數偏移是透明的、加法不是」——這個性質在 110 那題還會再出現一次(見 110:那裡 base case 寫錯 1 竟然完全不影響答案,因為它被減法消掉了)。
A2. 不是。最小反例 [1,null,2]。

最小深度的定義是「根到最近的葉節點」,而葉節點的定義是左右都空。

[1,null,2]:節點 1 有右小孩、沒有左小孩。
1 + min(maxDepth(null), maxDepth(2)) = 1 + min(0, 1) = 1 + 0 = 1
那個 0 來自「不存在的左子樹」,直接把 min 吃掉了。但深度 1 的位置是節點 1,它有小孩,根本不是葉節點。真正的 minDepth 是 2(路徑 1 → 2)。

實測:1+min 與真 minDepth 在 496/626 種樹形上不同,而且 1+min == 真minDepth ⟺ 該樹是「滿二元樹」(每個節點 0 或 2 個小孩)—— 因為滿二元樹沒有單邊子樹的節點,那個陷阱就不存在。

正確寫法要特判「某一邊空就強制走另一邊」:
if (root == nullptr) return 0;
if (root->left  == nullptr) return 1 + minDepth(root->right);
if (root->right == nullptr) return 1 + minDepth(root->left);
return 1 + min(minDepth(root->left), minDepth(root->right));
max 版不需要這個特判,因為 max 會自動忽略那個 0。這是 max 和 min 的不對稱之處 —— 也是「把 max 改成 min」這種看似無害的修改為什麼危險。
A3. 不會跳過 —— 兩個遞迴都會被完整執行。

std::max(a, b) 是一個普通函式。C++ 的規則是:引數必須先全部算完,才能呼叫函式。所以 maxDepth(root->left) 和 maxDepth(root->right) 兩個都得先跑完,結果才會被送進 max。

這和 && / || 完全不同 —— 那兩個是短路運算子,語言明文保證右邊可能不被求值。max 沒有這種保證,也不可能有。

實測:刻意造一棵極不對稱的樹(左邊掛 5 條邊的鏈、右邊只有 1 個節點),觀察到深度 6、呼叫次數 15 = 2×7+1;把它左右鏡像過來,還是深度 6、呼叫 15 次。兩邊都被走完,和哪邊比較深無關。

這正是複雜度乾淨的原因:沒有任何節點被跳過,所以呼叫次數恆為 2n+1,與樹形完全無關(窮舉 2056 種樹形實測,每個 n 的 min == max)。

對比 110 判平衡:那題用的是 &&,真的會短路 —— 而且短路大幅改變了它的實際複雜度。同樣是樹遞迴,「用的是函式還是短路運算子」會導致完全不同的成本分析。
A4. 在一般環境不會爆(餘裕 17 倍),但這是第一題需要真的算一下的。

實測數字(clean -O2 build,未插樁):
· 每層 48 bytes —— 由崩潰深度回推得 48.03,並與組語 stp x22, x21, [sp, #-48]! 核對相符
· 崩潰臨界 174300 層(三次二分皆得同一個邊界:174299 存活、174300 崩)
· ulimit -s = 8176 KB

最壞情況:樹退化成一條鏈,深度 10001,需要約 10000 × 48 = 469 KB。

不同堆疊上限下的實測結果:
· 8176 KB(本機預設)→ 存活,只用 5.7%,餘裕約 17 倍
· 1024 KB → 存活
· 512 KB → 存活,但實測 10802 層就崩 —— 對 10⁴ 而言只剩約 8% 餘裕
· 448 KB → SIGSEGV

我的答案在什麼條件下會改變 —— 兩個:
① 堆疊上限。512 KB 就已經很緊,再小就過不了。
② 最佳化等級。-O0 每層變成 64 bytes,實測在 512 KB 上 8099 層就崩,10⁴ 直接過不了。

所以正確說法是:「在 8 MB 或 1 MB 堆疊上安全;但這個結論依賴堆疊上限和編譯選項,不是演算法本身的性質。」如果要一個與環境無關的保證,就改用 App 1 的 BFS 版 —— queue 在 heap 上,沒有 8 MB 這種硬上限。
A5. 你會得到「節點總數」—— 那是另一個有意義的量,正好是 LeetCode 222。

1 + 左 + 右 的遞迴式,就是「子樹大小」的定義式:自己算 1 個,加上左右子樹各有幾個。

實測:窮舉 n = 0..7 共 626 種樹形,這個版本的輸出與節點總數完全相符(626/626);而與「葉節點數」只相符 2/626(就是 [] 和單節點)。所以它不是「算錯的深度」,它是正確的 countNodes。

它作為 maxDepth 的錯誤率:錯 498/626。巧合對的 128 種恰好是「樹退化成一條鏈」的情形 —— 因為鏈上節點數剛好等於深度。

這個對照很值得記,因為它示範了「同一個遞迴骨架,換掉合併運算就變成另一題」:
· 1 + max(左, 右) → 樹高(LC104)
· 1 + 左 + 右 → 節點數(LC222)
· 1 + min(左, 右) + 單邊特判 → 最小深度(LC111)
· 左 + 右 並記錄全域最大 → 直徑(LC543)

骨架永遠是「先問兩邊,再合併」;真正定義題目的是「合併那一步做什麼」。這也是為什麼把 max 換成 + 這種「小改動」會徹底換一題 —— 它改的正是題目的核心。
App 1. BFS 逐層,數有幾層;空間上「誰比較好」取決於樹的形狀。

int maxDepth(TreeNode* root) {
    if (root == nullptr) return 0;

    queue<TreeNode*> q;
    q.push(root);
    int levels = 0;

    while (!q.empty()) {
        int levelSize = q.size();       // 先記下這一層有幾個

        for (int i = 0; i < levelSize; i++) {
            TreeNode* curr = q.front();
            q.pop();
            if (curr->left)  q.push(curr->left);
            if (curr->right) q.push(curr->right);
        }

        levels++;                        // 排乾一整層 = 深度 +1
    }

    return levels;
}
關鍵是 int levelSize = q.size(); 這一行 —— 先把「這一層有幾個」拍照存下來,再剛好排乾那麼多個。如果直接寫 while (!q.empty()) 而不分層,你就數不出「層數」了。這個「先記 q.size()」的模式是所有層序題(102、107、199、515)的共同骨架。

空間比較 —— 沒有一面倒的贏家:
· 遞迴版 O(h),BFS 版 O(w)(w = 最大寬度)
· 完美平衡樹:h ≈ log n 但 w ≈ n/2 → 遞迴版好非常多
· 退化成鏈:h = n 但 w = 1 → BFS 版好非常多

但 BFS 有一個結構性優勢:queue 配置在 heap 上,不會 stack overflow。所以在 A4 那種「堆疊上限很小」的環境下,BFS 是唯一穩的選擇,即使它在平衡樹上用更多記憶體。——「同樣的複雜度、不同的失敗模式」。

這個 BFS 版正是本頁對拍用的獨立參考解,20 萬組零不一致。
App 2. 要加「單邊子樹」的特判 —— 不能只把 max 換成 min(理由見 A2)。

int minDepth(TreeNode* root) {
    if (root == nullptr) return 0;

    // 只有單邊子樹時,「空的那邊」不算一條通往葉節點的路
    if (root->left  == nullptr) return 1 + minDepth(root->right);
    if (root->right == nullptr) return 1 + minDepth(root->left);

    return 1 + min(minDepth(root->left), minDepth(root->right));
}
根源是「最小深度必須走到葉節點」這個條件。maxDepth 不需要這個特判,因為 max 會自動忽略掉空子樹回傳的 0;但 min 會被那個 0 綁架,回報一條「根本走不到葉子」的假路徑。

實測:不加特判的 1+min 與正確 minDepth 在 496/626 種樹形上不同,兩者相等當且僅當該樹是滿二元樹(沒有單邊子樹的節點)。

順帶一提,minDepth 用 BFS 其實更漂亮:第一個碰到的葉節點就是答案,可以立刻 return,不必走完整棵樹。對「有一條很淺的路、但其他地方很深」的樹,BFS 版會快非常多 —— 這是少數幾個「BFS 明顯優於 DFS」的樹題。
App 3. 要多一個「全域最大值」—— 因為直徑不一定通過根節點。

int longestPath = 0;                       // 全域,記錄目前看過的最大直徑

int path(TreeNode* root) {                 // 回傳「高度」,順便更新全域最大
    if (root == nullptr) return 0;

    int left = path(root->left), right = path(root->right);
    longestPath = max(longestPath, left + right);   // ← 在「每個節點」都試一次

    return 1 + max(left, right);           // 這一行和 104 一模一樣
}
骨架完全是 104:return 1 + max(左, 右) 那一行一個字都沒改。多的只有中間那一行 —— 在每一個節點都試算一次「穿過我的最長路徑 = 左高 + 右高」,並更新全域最大。

為什麼不能只看根 —— 因為直徑可能整條落在某棵子樹裡,根本沒碰到根。
實測:窮舉 n = 0..7 共 626 種樹形,有 48 種(7.67%)的直徑不通過根。
而且最小反例要 n = 6 才出現 —— n ≤ 5 的 65 種樹形,「只看根」全部碰巧正確。這就是為什麼這個 bug 幾乎不可能靠手算小例子發現:你得刻意造出「一邊很淺、另一邊掛著一條深的斜鏈」的形狀。

詳細內容見 543 那一頁 —— 它把「為什麼需要全域最大」這件事完整展開。

值得注意的是這裡有個單位陷阱:path() 回傳的是「節點數」,而 left + right 出來的卻是「邊數」(兩邊各自的「+1 根節點」都不在裡面)。這個混用剛好是對的,而題目要的正是邊數 —— 實測 n=1 的單節點樹回傳 0 ✓。
