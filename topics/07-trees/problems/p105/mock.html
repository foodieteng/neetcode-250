A naive approach would be to do the same split, but scan the inorder range each time to find the root. That scan is O(n) per node, so on a chain it adds up to O(n2). It still passes at n = 3000, but it's wasted work.

This problem reminds me of divide and conquer on a tree: each call owns one subtree, and the root splits it into two smaller problems of the same shape. The only slow part is finding the root in inorder. Since values are unique, a hash map from value to inorder index, built once, makes each lookup O(1).

// setup: value -> index in inorder (values are unique)
rootToIdx[inorder[i]] = i
// build(preL, inL, inR): subtree = inorder[inL..inR], its root is preorder[preL]
if inL > inR: return null
rootV    = preorder[preL]
rootIdx  = rootToIdx[rootV]
leftSize = rootIdx - inL   // the bridge between the two arrays
left  = build(preL + 1,            inL,         rootIdx - 1)
right = build(preL + leftSize + 1, rootIdx + 1, inR)

One: map each value to its inorder index.
Two: a helper takes preL, where the subtree starts in preorder, plus [inL, inR], its range in inorder.
Three: the root is preorder[preL], leftSize is its inorder index minus inL, the left child starts at preL + 1, and the right child at preL + leftSize + 1.

One thing worth flagging — those are two different coordinates. At node 9, the preorder position is 1 but the inorder range starts at 0, so one shared pair L, R for both recurses forever. leftSize is the only bridge between the arrays.

There's a trade-off here: a global preIdx++ skips that math, but only works if I build left before right. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    TreeNode* buildTree(vector<int>& preorder, vector<int>& inorder) {
        unordered_map<int, int> rootToIdx;           // value → inorder index
        int n = inorder.size();
        for (int i = 0; i < n; i++) {
            rootToIdx[inorder[i]] = i;
        }

        return build(preorder, inorder, 0, 0, n - 1, rootToIdx);
    }

    TreeNode* build(vector<int>& preorder, vector<int>& inorder, int preL, int inL, int inR, unordered_map<int, int>& rootToIdx) {
        if (inL > inR) return nullptr;                 // empty range

        int rootV = preorder[preL];                      // first in preorder = root
        int rootIdx = rootToIdx[rootV];                  // root's position in inorder
        int leftSize = rootIdx - inL;                    // left subtree size

        TreeNode* node = new TreeNode(rootV);
        node->left = build(preorder, inorder, preL + 1, inL, rootIdx - 1, rootToIdx);
        node->right = build(preorder, inorder, preL + leftSize + 1, rootIdx + 1, inR, rootToIdx);

        return node;
    }
};

buildTree fills the map from inorder, then calls build on the whole range, starting at preorder 0. build returns nullptr on an empty range, reads the root, looks up its index, computes leftSize, and recurses with the two ranges from the plan.

One thing worth flagging — the base case checks the inorder range, inL > inR, not preL. An empty range means an empty subtree, so I return nullptr before I ever read preorder[preL]. The last leaf's empty right child arrives with preL == n, so reading first would go out of bounds.

Corner cases:

• preorder = [-1] → [-1] — negative values are fine as map keys.
• Only right children, pre=[1,2], in=[1,2] → [1,null,2] — that's where the +1 matters: without it, the right call reuses the root, then reads preorder[-1].
• Only left children, pre=[1,2], in=[2,1] → [1,2].

Let me think about complexity here.

Time is O(n): building the map is O(n), then there are exactly 2n + 1 calls to build, each doing O(1) work thanks to the map. Space is O(n) for the map, plus O(h) for the recursion stack.

Worst case the tree is a chain, so the recursion depth is 3001, which is fine on the default stack; if n were in the millions, I'd switch to an explicit stack.

And the map is worth it: on a 3000-node left chain, a linear scan took 2.75 ms, and the map took 0.195 ms.

Oh, one more thing — the map only works because the values are unique. That's why I asked about it at the start. With duplicates, the tree wouldn't even be unique.
