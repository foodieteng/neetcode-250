用前序 + 中序重建二元樹

// CONCEPT · 前序給根,中序給切點

題目簡介// THE QUESTION

QUESTION

給你同一棵二元樹的 preorder(前序)和 inorder(中序)走訪結果, 把原本的樹建回來。
節點數 1 ~ 3000,值 -3000 ~ 3000,所有值互不相同。
範例:preorder = [3,9,20,15,7]、inorder = [9,3,15,20,7] → [3,9,20,null,null,15,7]。

兩個陣列各自只知道一半的事: 前序的第一個一定是根,但不知道左右子樹在哪裡分界; 中序知道分界(根的左邊全是左子樹),但不知道誰是根。 把兩個拼起來,就能一層一層切下去。
2

為什麼用「hash map + 索引區間」// KNOCKOUT

A 一組 L, R 同時管兩個陣列 無限遞迴
用同一個 L 當「前序的起點」又當「中序的左界」。 同一棵子樹在兩個陣列裡的起點一般不同,這樣寫就把兩套座標混在一起。 實測失敗 618 / 625(n≤7 全部樹形),連官方範例 1 都 segfault。
× REJECT · WRONG
B 每層線性搜尋根在中序的位置 O(n²)
邏輯正確(實測 0 / 625 失敗),但每層都掃一遍中序找根。 斜鏈時就是 O(n²)。 實測 n=3000 左斜鏈 2.75 ms,map 版 0.195 ms(約 14 倍)。
△ 對但較慢
ADOPT
C 先建 值→中序索引 的 map,再用索引切區間 O(n) 時間 · O(n) 空間
中序區間用 [inL, inR],前序只要一個起點 preL, 兩者靠 leftSize(左子樹大小)連起來。 實測 build() 恰好被呼叫 2n + 1 次,與樹形無關。
● ADOPT · O(n)
3

核心策略 · 三步驟// STRATEGY

  1. 找根:preorder[preL] 就是這棵子樹的根。
  2. 切中序:查 map 得到 rootIdx;左子樹 = [inL, rootIdx−1], 右子樹 = [rootIdx+1, inR],leftSize = rootIdx − inL。
  3. 切前序:左子樹從 preL+1 開始, 右子樹要再跳過整個左子樹,從 preL + leftSize + 1 開始。遞迴兩邊。
preorder = [ 根 | 左子樹 leftSize 個 | 右子樹 ]
inorder  = [ 左子樹 leftSize 個 | 根 | 右子樹 ]

動畫演示// VISUALIZER

盯著兩個陣列上「左子樹 / 右子樹」的底色區塊:同一棵子樹在兩個陣列裡長度永遠一樣,但位置不一樣。 前序的左子樹緊接在根後面,中序的左子樹在根前面。 所以一定要用兩個起點,leftSize 就是用來換算兩者的。
5

為什麼兩個陣列不能共用索引// THE REAL BUG

// LEMMA: 同一棵子樹,在兩個陣列裡的「起點」不同

對任何子樹:它在前序和中序裡佔一樣多格,但起點一般不一樣。 前序從根開始,中序從最左邊的節點開始。

所以遞迴至少要帶兩個獨立的起點:preL(前序)和 inL(中序), 再加一個長度或終點 inR。

如果把它們合成一個 L,算出來的 leftSize = rootIdx − L 可能變成負數。

// 舊版(共用 L, R)在官方範例 1 上實際發生的事 preorder = [3,9,20,15,7] inorder = [9,3,15,20,7] build(L=0, R=4):root = pre[0] = 3,idx[3] = 1,leftSize = 1 − 0 = 1 左:build(L=1, R=1) root = pre[1] = 9,idx[9] = 0 leftSize = 0 − 1 = −1 ← 9 在中序的位置在 L 的左邊 左:build(1, 0) → nullptr 右:build(1 + (−1) + 1, 1) = build(1, 1) ← 跟自己一模一樣 → 無限遞迴 → stack overflow // 實測:範例 1 直接 segfault;n≤7 全部 625 種樹形失敗 618 種

複雜度// COMPLEXITY

每個節點只被建立一次,每次查 map 是 O(1);空的區間各被呼叫一次後立刻回傳。 額外空間是 map 的 O(n),加上遞迴深度 O(h)。

一句洞察// INSIGHT

前序負責「誰是根」,中序負責「怎麼切」,leftSize 負責把兩邊的座標對齊。 前序、中序走訪各自的順序見 144 和 94; 這題就是把那兩個順序倒過來用。 兩個陣列一定要各有各的索引,共用一組 L, R 連範例都過不了。
