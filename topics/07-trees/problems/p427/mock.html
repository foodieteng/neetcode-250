Hmm, let me think about this for a second.

A naive approach would be to build the full tree all the way down to single cells, then walk back up and merge any parent whose four children are equal leaves. That works, but it's two ideas in one: build, then clean up.

This problem reminds me of plain divide and conquer on a square — like a segment tree, but in 2D. The state is a square, and the four quadrants are the four sub-problems. I'll go top-down: test the square, and split only if the test fails. That's the rule from the problem, read literally.

Here's the plan.

// state: (length, r, c) = side + top-left corner
// invariant: build(length, r, c) returns the tree
//           for exactly that length × length square

build(length, r, c):
  if isSame(length, r, c): // all one value
    return Node(grid[r][c], isLeaf = true)
  node = Node(grid[r][c], isLeaf = false) // val ignored
  h = length / 2
  node.topLeft     = build(h, r,     c)
  node.topRight    = build(h, r,     c + h)
  node.bottomLeft  = build(h, r + h, c)
  node.bottomRight = build(h, r + h, c + h)
  return node

One: describe a square by three numbers, (length, r, c) — its side and its top-left corner — so I never copy a sub-grid.
Two: if every cell matches the top-left cell, return a leaf with that value.
Three: otherwise make an internal node and recurse on four half-size squares — right is c + h, down is r + h.

One thing worth flagging — the check comes before the split, and that order is the whole reason the tree is minimal: four equal leaf children would mean their parent's square was uniform, so isSame would have made a leaf.

There's a trade-off here: checking first re-reads cells the parent already read. Bottom-up would read each cell once, but top-down is simpler. Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up.

class Solution {
public:
    Node* construct(vector<vector<int>>& grid) {
        return build(grid, grid.size(), 0, 0);
    }

    // compare every cell against grid[r][c]; stop at the first mismatch
    bool isSame(vector<vector<int>>& grid, int length, int r, int c) {
        int val = grid[r][c];
        for (int i = 0; i < length; i++) {
            for (int j = 0; j < length; j++) {
                if (val != grid[r + i][c + j]) return false;
            }
        }
        return true;
    }

    Node* build(vector<vector<int>>& grid, int length, int r, int c) {
        Node *root;
        if (isSame(grid, length, r, c)) {
            root = new Node(grid[r][c], true);       // leaf
        } else {
            root = new Node(grid[r][c], false);      // internal node: any val is accepted

            root->topLeft = build(grid, length / 2, r, c);
            root->topRight = build(grid, length / 2, r, c + length / 2);
            root->bottomLeft = build(grid, length / 2, r + length / 2, c);
            root->bottomRight = build(grid, length / 2, r + length / 2, c + length / 2);
        }
        return root;
    }
};

isSame compares every cell against the square's own top-left cell and returns false at the first mismatch. build makes a leaf if the square is uniform; otherwise it makes an internal node and recurses four times with length / 2.

One thing worth flagging — the internal node reuses grid[r][c] as its val. The judge ignores val when isLeaf is false, so on Example 1 my root prints as [0,0] instead of [0,1], and it's still accepted.

Let me think about complexity here. This one is easy to get wrong.

Time is O(n² log n). Group the work by level: squares on one level have the same side, don't overlap, and together cover at most the whole grid, so one level reads at most n² cells. There are log2n + 1 levels. At n = 64, the ceiling is 4096 × 7 = 28,672 reads.

Space is O(n²) for the output tree — the checkerboard gives 5461 nodes — and the stack is at most 7 frames, since the side halves every level.

I wouldn't claim either. 2.375 n² is real, but only for n = 4: across all 65,536 grids, the worst reads 38 cells, and 38 / 16 = 2.375.

At n = 8 there's already a grid that reads 178 cells, about 2.78 n². So a fixed constant is the wrong way to state it; the safe statement is the level bound.

Oh, one more thing — to drop the log factor, I'd go bottom-up: build the four children first, and merge only if all four are leaves with the same value. Each cell is read once. At this size both are instant, so I'd still ship top-down for clarity.
