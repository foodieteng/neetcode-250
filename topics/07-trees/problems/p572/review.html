範例 Trace// root=[3,4,5,1,2] sub=[4,1,2] → true

官方範例 1。以下是插樁後直接印出來的呼叫樹,縮排 = 巢狀深度。

// 完整呼叫樹(實跑) isSubtree#1(root=3) guard1 (!subRoot)? sub=4 非空 → 不開火 guard2 (!root)? root=3 非空 → 不開火 isSame#1(3,4) = false ← 根值 3 != 4 ★ 短路 A:&& 的第一個運算元就 false → 節點 3 底下的 1、2「完全沒被 isSame 走訪」 → 這次比對只花「1 次」呼叫,不是 3 次 isSubtree#2(root=4) ← isSame 失敗 → || 繼續,往左子樹找 isSame#2(4,4) 4 == 4 ✓ isSame#3(1,1) 1 == 1 ✓ isSame#4(null,null) guard → p==q → true isSame#5(null,null) guard → p==q → true = true isSame#6(2,2) 2 == 2 ✓ isSame#7(null,null) guard → true isSame#8(null,null) guard → true = true = true ← 整棵子樹逐位對齊到底 = true ★ 短路 B:isSubtree(root->left) 回 true → isSubtree(root->right) 「一次都沒有被呼叫」 → 節點 5 從頭到尾沒被搜尋過 = true
// OUTPUT return true isSubtree 呼叫 2 次、isSame 呼叫 8 次 注意兩個「沒發生的事」: ① 節點 3 底下的 1、2 —— 被短路 A 跳過(isSame 一比就死) ② 節點 5 整棵 —— 被短路 B 跳過(找到了就不再找) // 5 個節點的 root,實際只有 3 個被 isSame 碰過
// 對照:官方範例 2(只多掛一個節點,答案就翻了) root = [3,4,5,1,2,null,null,null,null,0] ← 比範例 1 多一個節點 0 掛在 2 底下 sub = [4,1,2] → false (實測 isSubtree 13 次、isSame 11 次) 關鍵那一步: isSame(節點2, 節點2):值相同 ✓ isSame(節點0, null) ← root 的 2 有左子 0,sub 的 2 沒有 !p||!q 成立 → return p == q → 「非 null == null」→ false ✓ 正確拒絕 而且因為在節點 4 沒匹配成功,|| 會繼續往下找 —— 所以呼叫次數比範例 1 多得多 // 兩個官方範例只差一個節點 —— 題目自己就在考「部分匹配不算子樹」
把兩個範例並排看,就是這題的全部: 範例 1 命中(整棵對齊到底),範例 2 只差一個多出來的節點就失敗。 而錯誤的「走完就算」版本會把範例 2 也判成 true —— 官方範例 2 存在的唯一目的,就是抓這個 bug。

// ANSWERS
A1. 因為「子樹」要求「從那個節點往下整棵都相同」,root 那邊不能有多出來的節點。把關的是 isSame 的 base case。

if (!p || !q) return p == q;

當 subRoot 已經走到 nullptr、而 root 那邊還有一個真節點時:p 非空、q 是 nullptr → p == q 是 false → 整個匹配當場失敗。

最小反例 root=[1,2]、subRoot=[1]:根值都是 1、對上了,但 root 的節點 1 底下還掛著一個 2,所以不是子樹。

官方範例 2 就是這件事的放大版:root=[3,4,5,1,2,null,null,null,null,0] 比範例 1 只多了一個節點 0 掛在 2 底下,答案就從 true 翻成 false。

換句話說:「子樹」不是「包含一段」,而是「某個節點連同它的全部後代」。這和字串的 substring 很像但更嚴格 —— 字串的 substring 可以在中間停,樹的子樹不行,它必須一路到葉子。
A2. 因為這個 bug 只會多報 true、從不漏報 —— 所以你拿正例去測,它全部答對。

實測:18556 個配對中,「sub 走完就成功」只錯 1700 個(9%),而且 失敗全部是 false-positive。正解為 true 的 1252 個配對,它一個都沒錯。

為什麼:當 subRoot 真的是子樹時,「走完就算成功」和「比到底」結論一樣 —— 因為那時候本來就剛好同時走完。兩者只在「root 那邊多出東西」時才分岔,而那種情形的正確答案是 false。

所以測不出來的原因是測資的形狀不對:你需要的不是更多正例,而是「差一點點就不是子樹」的反例 —— subRoot 是某棵子樹的嚴格前綴。

「知道 bug 的方向」在這裡特別有用:
· 只會多報 true(如本題兩個部分匹配 bug)→ 要用應該回 false 的反例抓。
· 只會漏報(如「只遞迴左子樹」,實測 448 個失敗全是 false-negative)→ 要用應該回 true 的正例抓,而且匹配要藏在右子樹。
兩種 bug 需要的測資完全相反。
A3. 外層 || 是「樂觀」的、內層 && 是「悲觀」的 —— 同一個機制的兩種極性。

外層 ||(找位置):一旦某個位置成功,就不再找其他位置。
實測 root 是 n=127 的完美樹、subRoot 是一片葉子:isSubtree 只呼叫 7 次,而拿掉短路要 255 次 —— 省 97%。

內層 &&(比對):一旦某處不同,就不再往下比。
實測同一組:isSame 15 次 vs 拿掉短路的 381 次 —— 省 96%。
更極端的例子:兩條 n=100 的鏈在根就匹配,isSame 201 次 vs 10200 次 —— 省 98%。

官方範例 1 裡兩個短路都看得到:isSame(3,4) 在根值就死(所以節點 3 底下的 1、2 沒被走訪,那次比對只花 1 次呼叫);接著左子樹匹配成功,節點 5 整棵從未被搜尋。全程 isSubtree 2 次、isSame 8 次。

一個有趣的例外:當答案必定是 false 時,外層短路救不了你 —— 實測「sub 的值在 root 裡不存在」的情形,isSubtree 短路版與無短路版同樣是 201 次。|| 只在「找得到」時才省得下來,而 && 在任何情況都省。
A4. 不會 —— 實測平均每次 isSubtree 只觸發 0.62 次 isSame。

O(n×m) 的推導是「對 n 個位置各做一次 O(m) 的比較」,但那假設每次比較都真的走完 m 個節點。實際上絕大多數位置在「比第一個值」就出局了。

實測 20 萬組隨機配對:
· isSame 呼叫中 61.0% 在第一次值比較就返回
· 平均每次 isSubtree 觸發 0.62 次 isSame(總計 1317499 / 2129681)

連刻意構造的最壞情況也沒碰到上界:root 是 100 個全 0 的鏈、subRoot 是 50 個全 0 再接一個 9 —— 理論上界 100×50 = 5000,實測 isSame 3875 次。而一般情況(值不同)只要 100~150 次,差了三十幾倍。

所以真正的成本更接近 O(n + 匹配到的位置數 × m)。面試時的說法:「最壞是 O(n×m),但要湊出最壞情況需要大量重複值;隨機資料下 && 讓大多數比對退化成 O(1),我量過平均每個位置不到一次呼叫。」 —— 說得出「為什麼上界很鬆」比只背上界有價值得多。
A5. 坑在「分隔符號」—— 沒處理好會把一個 token 的後半截當成匹配。

具體會錯的例子(實測驗證過):
· root = [12](單一節點,值 12)→ naive 前序序列化 "12##"
· subRoot = [2](單一節點,值 2)→ 序列化 "2#"
· "2#" 是 "12##" 的 substring → naive 判定 true
· 但正確答案是 false —— root 裡根本沒有值為 2 的節點,那個 2 是 12 的後半個字元。

修法:每個 token 都要有明確的邊界。本頁對拍用的參考解是:每個實節點前綴 ^ 當 node-start marker、每個 token 後接 ,:
· [12] → "^12,#,#,",不含 "^2,#,#," → 正確 false ✓
· [1,2](1 有左子 2)→ "^1,^2,#,#,#,",含 "^2,#,#," → 正確 true ✓

而這個坑最危險的地方是:隨機測資完全測不到。本頁的 20 萬組對拍用的值域是 [0,3] —— 全是單字元,naive 版和正確版差異 0 組。必須手工構造 12 vs 2 這種「多位數」的例子才會現形。

另外別忘了 null 標記本身也不能省(見 144 的 App 3):沒有 #,[1,2] 和 [1,null,2] 會序列化成同一個字串。
App 1. 把兩棵樹序列化成帶 null 標記與分隔符號的字串,再用 KMP 找子字串 —— O(n+m)。

void ser(TreeNode* t, string& out) {
    if (t == nullptr) {
        out += "#,";                       // null 標記 + 分隔
        return;
    }

    out += "^" + to_string(t->val) + ",";   // node-start marker + 值 + 分隔
    ser(t->left,  out);
    ser(t->right, out);
}
// isSubtree = KMP(serialize(root), serialize(subRoot))
三個都不能省的細節:
① null 標記(#) —— 沒有它,[1,2] 和 [1,null,2] 序列化相同。
② 分隔符號(,)+ node-start marker(^) —— 沒有它,[12] 會「包含」[2](見 A5,實測驗證過)。
③ 用 KMP 而不是 string::find —— 樸素找子字串最壞是 O(n×m),那就白做了。

複雜度:序列化 O(n+m)、KMP O(n+m) ⇒ 總共 O(n+m),但額外空間也是 O(n+m)(遞迴版只要 O(h))。

面試時的取捨:先給遞迴版(短、好懂、實測夠快),再說「如果 n×m 真的會爆,可以序列化成字串用 KMP 做到線性,但要小心分隔符號」。能主動講出那個 12 vs 2 的坑,比會寫 KMP 更能顯示你想過細節。
App 2. 把回傳型別從 bool 換成收集容器,並且拿掉外層的短路。

void collect(TreeNode* root, TreeNode* subRoot, vector<TreeNode*>& hits) {
    if (root == nullptr) {
        return;
    }

    if (isSame(root, subRoot)) {
        hits.push_back(root);       // 記下來,但「不 return」
    }

    collect(root->left,  subRoot, hits);   // 兩邊都還是要繼續找
    collect(root->right, subRoot, hits);
}
關鍵是「找到之後不能停」 —— 原版的 || 一找到就短路,那正是我們現在不要的行為。

複雜度會變嗎 —— 上界不變,實際成本變高。
· 上界仍是 O(n×m):本來最壞也是每個位置都要比一次。
· 但「實際」會變慢,因為失去了外層短路。實測參考:完美樹 n=127 找一片葉子,有短路 isSubtree 7 次、無短路 255 次 —— 這 36 倍的差距現在必須付出去。
· 內層 && 的短路還在(那 61% 的提早退出照樣有效),所以不會退化到理論最壞。

一個值得注意的細節:巢狀匹配是可能的。如果 subRoot 是一棵「自相似」的樹(例如全部節點同值的鏈),一個匹配位置的祖先也可能是匹配位置 —— 所以 hits 裡的節點之間可能有祖孫關係,不是互斥的。要不要去重、怎麼去重,得看題目怎麼定義。
App 3. 把值比較那一項拿掉就好 —— 但會變慢,而且慢得很明顯。

bool sameShape(TreeNode* p, TreeNode* q) {
    if (!p || !q) {
        return p == q;                     // 這一行完全不變
    }

    return sameShape(p->left,  q->left)    // 只少了 p->val == q->val
        && sameShape(p->right, q->right);
}
為什麼「會變慢」而不是變快 —— 這題的直覺是反的。

值比較是最便宜、也最容易失敗的那個條件,而它排在 && 的最前面。實測顯示 61% 的 isSame 呼叫就是靠它提早退出的。拿掉它,你就失去了最有效的剪枝 —— 每次比對都得真的走完整個形狀才知道成不成立。

而且「形狀相同」比「完全相同」寬鬆得多,所以匹配會變多、外層 || 也更早找到 —— 這一項是變快的。兩個效應方向相反,淨結果取決於資料:值很分散時大幅變慢(失去了主要剪枝),值本來就重複很多時差不多(那個剪枝本來就沒在發揮作用)。

一般教訓:&& 鏈裡「便宜且容易失敗」的條件要放最前面。這題把 p->val == q->val 放在兩個遞迴之前,不是隨手寫的順序,而是效能上的正確選擇 —— 把它放到後面(先遞迴再比值)結果一樣正確,但剪枝就完全失效了。
