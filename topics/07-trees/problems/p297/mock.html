A naive approach would write only the values and rebuild a tree from them. That's fast, but just wrong: it throws away the shape, and [1,2] and [1,null,2] both become "1 2". So the real work isn't speed — it's making the format unambiguous.

This problem reminds me of level-order traversal with a queue: the bracket format used to display test-case trees, like [1,2,3,null,null,4,5], is exactly BFS with null holes. The other option is a preorder DFS with null markers. Both work. I'll pick BFS, because it's a plain loop with a queue, so there's no recursion depth to worry about on a 104-node chain.

// serialize: BFS, write EVERY popped slot, nulls too
if root is null: return ""         // empty tree = empty string
q = [root]
while q not empty:
    node = pop
    if node: s += val + " "; push left; push right
    else:    s += "n "            // hole marker

// deserialize: same BFS order, each popped node eats 2 tokens
if data is empty: return null
root = first token; q = [root]
while read token L:
    node = pop
    if L != "n": node.left = new(L); push it
    read token R
    if R != "n": node.right = new(R); push it

One: serialize with BFS, writing every popped slot — a value and a space, or n for a null.
Two: deserialize in the same order: the first token is the root, then each popped node eats two tokens, left then right, and only real children join the queue.
Three: on both sides, the empty string means the empty tree.

One thing worth flagging — the right child's read isn't checked, and that's safe. n nodes have 2n child pointers. Every node except the root fills one of them, so n - 1 are real and n + 1 are null. That's 2n + 1 tokens: after the root, exactly two per node.

The trade-off: about half the tokens are markers, but trimming trailing ones breaks that count, so I keep them. Does this approach sound good, or would you rather I think of another way?

class Codec {
public:
    // Encodes a tree to a single string.
    string serialize(TreeNode* root) {
        if (root == nullptr) return "";

        string s;
        queue<TreeNode*> q;
        q.emplace(root);

        while (!q.empty()) {
            TreeNode* node = q.front();
            q.pop();
            if (node != nullptr) {
                s += to_string(node->val) + " ";
                q.emplace(node->left);          // push nulls too
                q.emplace(node->right);
            } else {
                s += "n ";                          // null marker
            }
        }
        return s;
    }

    // Decodes your encoded data to tree.
    TreeNode* deserialize(string data) {
        if (data.empty()) return nullptr;

        stringstream ss(data);
        string word;
        ss >> word;
        TreeNode* root = new TreeNode(stoi(word));
        queue<TreeNode*> q;
        q.emplace(root);

        while (ss >> word) {                         // left child's token
            TreeNode* node = q.front();
            q.pop();
            if (word != "n") {
                node->left = new TreeNode(stoi(word));
                q.emplace(node->left);
            }
            ss >> word;                                // right child's token
            if (word != "n") {
                node->right = new TreeNode(stoi(word));
                q.emplace(node->right);
            }
        }

        return root;
    }
};

Serialize pushes null children too, so it writes a marker for every hole. Deserialize only pushes real nodes, because a null slot has no children to fill, and the while (ss >> word) read stops cleanly when the tokens run out.

One thing worth flagging — the empty tree. Serialize returns "", and deserialize checks data.empty() first. The two must match: if I'd encoded the empty tree as "n ", deserialize would call stoi("n") and throw std::invalid_argument. Also, Codec has no member state, so separate Codec objects for the two calls work the same as one shared object.

C

Let me think about complexity here.

Time is O(n) both ways: 2n + 1 slots, each pushed and popped once. Space is O(n) too. The string is the big part — at most 80,002 characters at 104 nodes, when every value is -1000. The queue is O(n) at worst: it peaks at 10,001 on a balanced tree, but stays tiny on a chain.

In the worst case the tree is a long chain, and that's where BFS pays off: no recursion, so a 106-node chain round-trips fine, while a recursive preorder, also correct, crashes on it.

Oh, one more thing — bad input. A cut-off string won't crash, it quietly builds a wrong tree: "1 2" gives 1 with two children of 2. For a real service, I'd check the second ss >> word and reject bad strings.
