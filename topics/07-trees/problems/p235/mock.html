Good. Then here is the thing I want to say up front: I don't have to search for anything. In a general binary tree I'd have to find p and q first. In a BST the values tell me which way to go, so this is not a search, it is a descent.

Let me put it as an interval: lo = min(p, q), hi = max(p, q). At any node there are only three answers. Bigger than hi — both targets are on the left, so I go left. Smaller than lo — I go right. Otherwise the node is inside the range, the two targets split here, and that node is the answer.

Hmm, let me think about this for a sec.

A naive approach would be to ignore that this is a BST: walk the whole tree, record the path from the root to p and to q, and take the last node they share. That works, but it is O(n) time and O(n) space, and it throws away the one thing that makes this problem interesting.

This problem reminds me of a binary search. In binary search I compare the target to the middle and drop half the array. Here I compare the range [lo, hi] to the current node and drop a whole subtree. Same two-way decision, just walking pointers instead of indices.

P — plan
C
CANDIDATE

Here's the plan.

// invariant: the LCA is always inside the current subtree
lo = min(p, q)
hi = max(p, q)

at node:
  hi < node // whole range is left -> go left
  lo > node // whole range is right -> go right
  else // node is inside [lo, hi] -> this is the answer

One: compute lo and hi from the two values.
Two: if hi is smaller than the node, go left; if lo is bigger, go right.
Three: otherwise the node is inside the range — return it.

The invariant: the answer is always inside the subtree I'm standing on, because I only ever drop a side that holds neither target.

One thing worth flagging — the first node inside the range is the answer, and I can stop. Below it, one target goes left and the other goes right, so no deeper node has both.

There's a trade-off here. Recursion reads cleanly, but every call is a tail call, so it can also be an O(1)-space loop. I'll write the recursion first and mention the loop at the end. Does this approach sound good, or would you rather I think of another way?

I
INTERVIEWER

Sounds good. Code it up.

I — implement
C
CANDIDATE

Alright, let me code this up. Three branches, one comparison each, no bookkeeping.

class Solution {
public:
    TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
        if (max(p->val, q->val) < root->val) {
            return lowestCommonAncestor(root->left, p, q);   // both smaller than me
        } else if (min(p->val, q->val) > root->val) {
            return lowestCommonAncestor(root->right, p, q);  // both bigger than me
        } else {
            return root;                                       // split point = answer
        }
    }
};

One thing worth flagging — the two comparisons are < and >, and they have to be strict. That is a correctness requirement, and it is exactly the own-ancestor case.

If I loosen the first one to <= and p itself is the split node, so max(p, q) == root, the strict version stops and returns it. The <= version says "still go left", and walks past the answer into a subtree it can never come back up from.

CANDIDATE

Let's dry-run the code with an example. Same tree, p = 2 and q = 4, so lo = 2 and hi = 4, and I expect node 2.

The row that matters is the second call, at node 2. 4 is not less than 2, and 2 is not greater than 2 — that is where strictness earns its keep. With >= I'd have gone right, past the answer. Both tests fail, so it returns node 2. Two calls.

Let's also test with corner cases.

• 2, 8 split at the root: node 6, one call.
• 3, 5, the deepest split: node 4, three calls.
• 0, 5, both under 2: node 2, two calls.
• The call count is always the depth of the answer plus one.

Sure enough that I checked it by brute force. Every BST on the values {0..n-1}, for n = 1..8 — 2055 trees — and every ordered pair (p, q): 118621 triples.

Strict comparisons: zero failures. <=: 54283 failures, and they are exactly the triples where the answer is the larger target — the own-ancestor case, nothing else.

The surprise is that most of those failures do not crash. About 71% quietly return a wrong node, because the subtree it walks into still holds the other target. In the example tree, p = 0, q = 2 should give 2; the <= version returns 0. Always wrong on that set, and usually silent about it — the worse failure mode.

E — evaluate
C
CANDIDATE

Let me think about complexity here.

The time complexity is O(h), the height — exactly the depth of the answer plus one; on a balanced tree, O(log n). The space complexity is O(h) for the call stack.

In the worst-case scenario the tree is a sorted chain, 105 deep. At -O2 the compiler turns the tail call into a loop. At -O0 it doesn't, and an 8 MB stack survives with a margin of only about 1.31×.

I'd rather not depend on the compiler, so here is the loop: same three branches, O(1) space, and it agrees with the recursion on every triple.

class Solution {
public:
    TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
        int lo = min(p->val, q->val);
        int hi = max(p->val, q->val);

        while (root != nullptr) {
            if (hi < root->val) {
                root = root->left;
            } else if (lo > root->val) {
                root = root->right;
            } else {
                return root;
            }
        }

        return nullptr;   // guaranteed to return above; this line only keeps the compiler happy
    }
};

Oh, one more thing — no null check is deliberate, safe only because both targets exist. Break that promise and it usually returns a wrong node rather than crashing.
