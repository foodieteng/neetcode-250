觀念題// CONCEPT Q&A

Q1. 為什麼「第一個落在 [min, max] 區間內的節點」就是 LCA?請分別論證它是共同祖先與它是最近的。
Q2. 那兩個比較為什麼必須是嚴格的 < 和 >?寫成 <= 會怎樣 —— 是答錯還是崩潰?(兩種都會發生,比例是多少?)

範例 Trace// 同一棵 BST,三組 (p,q)

BST [6,2,8,0,4,7,9,null,null,3,5]。 三組實跑,示範「答案埋得多深,就走多少步」。

// A · p=2, q=8 → 6(官方範例 1,只走 1 步) 區間 [min, max] = [2, 8] call#1 at node 6: max=8 min=2 max=8 < 6 ? 否 min=2 > 6 ? 否 → 落在區間內(2 <= 6 <= 8)→ RETURN 6 calls = 1,depth(LCA=6) = 0 ✓ 符合「calls = depth + 1」 // 一個在左、一個在右 ⇒ 根就是分岔點,立刻結束
// B · p=2, q=4 → 2(官方範例 2,走 2 步;p 自己就是答案) 區間 [min, max] = [2, 4] call#1 at node 6: max=4 min=2 max=4 < 6 ? 是 → 兩個目標都比 6 小,必在左子樹 → 往左 call#2 at node 2: max=4 min=2 max=4 < 2 ? 否 min=2 > 2 ? 否 ← 注意:min「等於」2,所以「嚴格大於」不成立 → 落在區間內(2 <= 2 <= 4)→ RETURN 2 calls = 2,depth(LCA=2) = 1 ✓ // 這一步就是「嚴格比較」在守的地方:寫成 >= 的話會往右走過頭
// C · p=3, q=5 → 4(走 3 步,答案埋得最深) 區間 [min, max] = [3, 5] call#1 at node 6: max=5 < 6 → 往左 call#2 at node 2: min=3 > 2 → 往右 call#3 at node 4: max=5 < 4 ? 否;min=3 > 4 ? 否 → 落在區間內(3 <= 4 <= 5)→ RETURN 4 calls = 3,depth(LCA=4) = 2 ✓ // 同一棵樹,三組答案分別走 1、2、3 步 —— 完全由「答案在哪」決定
三組 trace 一起看,那條恆等式就很明顯了: 呼叫次數 = LCA 的深度 + 1。 實測在 2055 棵 BST 的全部 118621 組上零例外。 所以這題的成本既不是 O(n)、也不是固定的 O(h),而是「答案埋得多深」。

應用題// APPLICATION

App 1. 如果輸入不是 BST,只是一般二元樹(LeetCode 236)。要怎麼寫?複雜度變成多少?
App 2. 改成回傳從 p 到 q 的完整路徑。怎麼利用這題的結果?
App 3. 如果要對同一棵樹回答非常多組 (p, q) 查詢,還適合每次都走一趟嗎?
// ANSWERS
A1. 兩個部分要分開論證。

① 它是「共同祖先」。走到節點 v 的時候,p 和 q 都還在 v 的子樹裡 —— 因為前面每一步排除掉的,都是「由 BST 性質確定不含它們」的那一側(兩個都比我小就一定在左邊)。而條件 min ≤ v ≤ max 表示一個在 v 的左半邊(或就是 v)、另一個在右半邊(或就是 v) —— 所以 v 同時是兩者的祖先。

② 它是「最近」的。從 v 再往下走任何一步,就會甩掉其中一個目標:往左會丟掉 max 那一側,往右會丟掉 min 那一側。所以 v 是最後一個還能同時擁有兩者的節點 —— 這正是「最近共同祖先」的定義。

實測:與兩個完全不使用 BST 性質的獨立參考解比對 —— ① 一般二元樹 LCA(LC236 的左右都遞迴版)、② 各求根到 p、根到 q 的路徑再取最長共同前綴 —— 在 2055 棵 BST × 118621 組上皆零不一致。

用「不靠捷徑的解」去對拍「靠捷徑的解」,才真的驗證了捷徑是對的 —— 這比自己跟自己比對有意義得多。
A2. 因為要守住「一個節點可以是自己的後代」;而寫錯的症狀是崩潰,不是答錯。

<= 的意思變成「兩個目標都小於等於我 ⇒ 往左」。但如果 max(p,q) 剛好就是我自己,答案本來就應該是我 —— 它卻往左走了。

⚠ 而「走過頭」的後果大多不是崩潰 —— 這是最容易記錯的一點。左子樹裡通常還有另一個目標,所以它多半會落在某個真實節點上並把它交出來。實測 54283 組失敗的分佈:38762 組(71%)安靜回傳錯節點、只有 15521 組(29%)走到 nullptr 而 SIGSEGV。
官方那棵樹的具體例子:p=0, q=2 正解是 2,<= 版回傳 0,完全不崩。

實測(2055 棵 BST × 118621 組):
· < → <=:失敗 54283 組,而且失敗集合恰好等於「LCA == max(p,q)」那一族(特徵化零誤差)。
· > → >=:對稱地失敗 54283 組,恰好是「LCA == min(p,q)」。
· 最小反例小到不能再小:單節點樹 [0]、p = q = 0。

而 p == q 的那 15521 組會同時踩到兩個 bug(此時 LCA == max == min),所以兩者的最小反例是同一個。

什麼時候才會真的崩:走到「沒有節點可走」的時候。p == q 的那 15521 組正是如此(此時 LCA == max == min,兩個 bug 同時發作),所以兩者的最小反例都是單節點樹 [0]、p=q=0。

教訓:別把「這個 bug 會崩潰」當成安全網。七成的情況它安靜地給你一個看起來合理的節點 —— 而崩潰反倒是比較幸運的那三成,至少它會告訴你出事了。
A3. 不是漏寫 —— 它是靠「題目保證 p、q 都存在」換掉的。

為什麼安全:從 root 出發,每一步排除的都是「確定不含 p 和 q」的那一側,所以p 和 q 永遠都還在目前的子樹裡。既然子樹裡至少還有兩個(或一個)真實節點,就一定會在走到 nullptr 之前先碰到分岔點。

前提被打破時的代價(實測,雖然 constraints 禁止):
情況一:p 或 q 不在樹中。絕大多數是「安靜答錯」而非崩潰 —— 實測 23020 組「查詢一個樹中不存在的內部值」的輸入,只有約 0.9% 段錯誤,99% 安靜回傳一個看起來合理的節點(查詢超出值域的值則 0% 崩潰)。例如 BST {3,5,7} 查 q=6 → 回傳 5,不崩潰。
情況二:輸入根本不是 BST。[5,1,9,7,3](7 被放在左子樹,違反 BST),查 p=7, q=9,真答案是 5 → 這份程式碼回傳 9。另一個形狀 [5,9,null,8] 查 p=8, q=9 → 走到 null 然後 SIGSEGV。

「安靜答錯」比崩潰危險得多 —— 崩潰會立刻告訴你出事,錯答案會一路傳下去。

面試時的正確做法:主動說出這個假設。「題目保證兩個節點都存在,所以我不需要 null 檢查;如果不能假設,我會加上 if (!root) return nullptr;,代價是一行。」——顯示你知道自己在依賴什麼,而不是碰巧沒寫。
A4. h 最壞是 n(BST 退化成排序鏈);而「會不會爆」的答案取決於編譯器最佳化 —— 這是本章第一次。

BST 沒有平衡保證,所以一條「已排序」的鏈是完全合法的輸入 —— h = n = 10⁵。

實測(clean build,未插樁):
· -O2 → clang 施行尾呼叫最佳化(TCO):三個 return 全在 tail position,遞迴被編譯成迴圈,實質 O(1) 堆疊。實測 n = 4000 萬 在 ulimit -s 512 KB 下仍然存活 —— 根本量不到崩潰點。
· -O0 → 沒有 TCO,這才是真正的最壞情況(二分兩次結果一致):
　8176 KB → 130722 存活 / 130723 崩 ⇒ 對 n=10⁵ 安全邊際只有 1.31 倍
　1024 KB → 16290 崩界 ⇒ n=10⁵ 直接 SIGSEGV
　512 KB → 8098 崩界 ⇒ 同樣 SIGSEGV

所以「我在 LeetCode 上過了」不等於「這段程式碼在深度上是安全的」 —— 它過是因為評測機開了最佳化,而 C++ 標準並不保證 TCO。

結論很簡單:直接寫迭代版。這題是純尾遞迴,改成 while 迴圈邏輯一個字都不用改(實測 118621 組答案完全一致),空間 O(h) → O(1),而且不依賴任何編譯器行為。
A5. 這份程式碼沒有風險;但「兩邊異號」那個經典技巧會溢位。

為什麼這份安全:它只做比較,完全沒有算術。max/min 是挑一個出來,</> 是比大小 —— 沒有任何加減乘。
實測:BST {-10⁹, 0, 10⁹} 查 p=-10⁹, q=10⁹ → 回傳 0,正確;連 {INT_MIN, 0, INT_MAX} 都正常,無 UB。

會溢位的是這種寫法:
if ((p->val - root->val) * (q->val - root->val) <= 0) return root;
它的想法很漂亮 —— 「兩個差異號(或有一個是 0)就代表 root 夾在中間」。但實測拆開來看:
· 10⁹ − (−10⁹) = 2000000000 —— 這一步其實還放得進 int(INT_MAX = 2147483647)
· 但兩個相乘 = 4×10¹⁸,遠遠超過 int → 溢位,結果是垃圾值
所以真正的殺手是那個乘法,不是減法。(要救也可以 —— 轉成 long long 再乘,或乾脆用兩個比較,也就是原本的寫法。)

一般經驗:題目把值域開到 ±10⁹(而不是 ±10⁴)通常就是在暗示「別用相減或相乘的技巧」。而「只比較、不算術」的寫法天生免疫 —— 這是原解法一個容易被忽略的優點。
App 1. 失去 BST 性質就不能「二選一」,只能兩邊都找 —— 變成 O(n)。

TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
    if (root == nullptr || root == p || root == q) {
        return root;                       // 找到其中一個,或走到底
    }

    TreeNode* left  = lowestCommonAncestor(root->left,  p, q);
    TreeNode* right = lowestCommonAncestor(root->right, p, q);

    if (left != nullptr && right != nullptr) {
        return root;                       // 一邊一個 ⇒ 我就是分岔點
    }

    return (left != nullptr) ? left : right;   // 都在同一邊,往上傳
}
結構上的差別很值得比較:
· 235(BST):由上往下,每步二選一,O(h),而且是尾遞迴。
· 236(一般樹):由下往上(後序骨架!),兩邊都要走,O(n),不是尾遞迴(回來之後還要合併)。

「兩邊都非 null ⇒ 我是答案」的判斷,和 235 的「值落在區間內」是同一件事的兩種說法 —— 都是在偵測「分岔點」。差別只在:BST 能用值直接算出該往哪走,一般樹只能走過才知道。

實測:本頁的對拍參考解之一就是這個 236 版,在 118621 組上與 BST 版零不一致 —— 它永遠正確,只是慢。
App 2. 先用 LCA 把路徑切成兩段:p → LCA 和 LCA → q。

樹上任兩點的路徑是唯一的,而且必定經過它們的 LCA。所以:
① 找到 LCA(就是這題)。
② 從 LCA 往下找 p,記下路徑 —— 在 BST 裡這也是「二選一」的下降,O(h)。
③ 同樣找 q。
④ 把第 ② 段反轉,接上 LCA,再接第 ③ 段。

// 在 BST 裡找一條「從 from 往下到目標值 target」的路徑
void pathDown(TreeNode* from, int target, vector<TreeNode*>& out) {
    while (from != nullptr) {
        out.push_back(from);

        if (target < from->val) {
            from = from->left;
        } else if (target > from->val) {
            from = from->right;
        } else {
            return;                        // 到了
        }
    }
}
總複雜度 O(h),空間 O(h)(存路徑)。

順帶一提:「兩點距離 = depth(p) + depth(q) − 2 × depth(LCA)」 —— 這個公式在樹論裡到處都是,而它的核心就是「路徑必過 LCA」。如果只要距離而不要路徑,連存路徑都不用,算三個深度就好。
App 3. 查詢很多時,應該改用「預處理 + O(1) 查詢」的作法。

單次查詢 O(h) 已經很好,但如果有 Q 組查詢,總成本是 O(Q × h) —— 而 BST 退化時 h = n,那就是 O(Q × n),會爆。

標準作法:Binary Lifting(倍增法)。
· 預處理 O(n log n):對每個節點 v 存 up[v][k] = 「v 往上跳 2ᵏ 步的祖先」,同時記錄每個節點的深度。
· 每次查詢 O(log n):先把深的那個「跳到」和淺的同深度,再讓兩個一起往上二分跳,直到父節點相同。

更快的作法:Euler Tour + 稀疏表(Sparse Table) —— 把樹的歐拉序列壓成陣列,LCA 就變成區間最小值查詢(RMQ),預處理 O(n log n)、每次查詢 O(1)。

怎麼選:
· Q 很小 → 就用這題的 O(h) 版本,零預處理、程式碼五行。
· Q 很大、樹是靜態的 → Binary Lifting(好寫、好記、夠快)。
· Q 極大且要極致 → Euler Tour + RMQ。

值得注意:這些進階作法都不需要 BST 性質 —— 它們對任意樹都成立。換句話說,一旦查詢次數變成瓶頸,BST 那個漂亮的捷徑反而不是重點了,重點變成「如何攤平重複的往上走」。
