範例 Trace// [40,20,60,10,30,50,70] 插入 25

官方範例 2。以下是插樁後印出來的實際呼叫樹, 重點是看「哪一個賦值真的存下了新指標」。

// 階段一 · 下降(三個賦值一路「掛起」) 1. insert(root=40, 25) 40 > 25 → 往左 [ 40.left 的賦值:掛起,等遞迴回傳 ] 2. insert(40->left = 20, 25) 20 < 25 → 往右 [ 20.right 的賦值:掛起 ] 3. insert(20->right = 30, 25) 30 > 25 → 往左 [ 30.left 的賦值:掛起 ] // 走到這裡,有三個賦值同時懸著 —— 這就是「回程要接線」的那條路
// 階段二 · 新節點誕生(但還沒接上任何人) 4. insert(30->left = nullptr, 25) root == nullptr → return new TreeNode(25) ⚠ 此刻的狀態: · 新節點已經存在於記憶體裡 · 但「樹上沒有任何節點指向它」 · 它自己也不知道該掛在誰底下 · 它「只存在於這個回傳值裡」 原因:遞迴收到的 root 是「30->left 這個 nullptr 的副本」 把副本指向新節點,不會影響 30 的 left 欄位 // 這一格就是整題的核心 —— 新節點此時是「無根的」
// 階段三 · 回程接線(只有第一個是真的) 5. ← 回到第 3 層: 30->left = (新節點 25) ★★★ 真正的接線 這一個賦值是新節點「唯一」被掛上去的機會 return 30 6. ← 回到第 2 層: 20->right = 30 (原本就是 30 → 恆等賦值) return 20 7. ← 回到第 1 層: 40->left = 20 (原本就是 20 → 恆等賦值) return 40 ← 回傳「原本的根」,根沒被換掉
// OUTPUT [40,20,60,10,30,50,70,null,null,25] 呼叫次數 = 4 = 新葉子的深度(3) + 1 配置次數 = 1 三個回寫裡「只有 1 個」存下了新指標(第 5 步) 實測:與獨立的迭代 + parent 指標版對拍 窮舉 4707 組 + 隨機 200000 組,樹形逐位元相同 // 「大部分回寫都是恆等賦值」正是丟掉它在小測資上看起來沒事的原因
第 4 步和第 5 步之間那個「空檔」,就是這題要教的東西。 新節點在第 4 步誕生,但要到第 5 步才「屬於這棵樹」 —— 中間那一瞬間它是一個無主的指標。 丟掉回寫,它就永遠停在那個狀態。

// ANSWERS
A1. 新節點會被 new 出來、回傳、然後掉在地上 —— 樹原封不動,而且那個節點洩漏了。

原因在 C++ 的參數傳遞:遞迴收到的是「指標的副本」。
insertIntoBST(root->left, val) 傳進去的是 root->left 那個 nullptr 的一份拷貝。遞迴內部執行 return new TreeNode(val); 時,那個新節點只存在於回傳值裡 —— 樹上沒有任何節點指向它,它自己也不知道該掛在誰底下。

把回傳值接住的那個賦值,就是它唯一的一條路。

實測:窮舉 626 棵 BST × 每個插入位置 = 4707 組,拿掉回寫錯 4706 組。而且失敗集合以集合相等驗證,恰好等於「原樹非空」(零分歧)。
唯一答對的那 1 組是空樹 —— 因為那時 root == nullptr 發生在最外層,新節點直接被 return 給呼叫端,根本沒有經過任何賦值。

順帶一提,這個 bug 還會洩漏記憶體 —— 每插入一次就漏一個節點。在 LeetCode 上看不出來,在真實系統裡會累積。
A2. 差別在「遞迴回傳的是不是一個新的指標」。準則:遞迴會不會產生新節點、或換掉子樹的根?

· 701(本題):base case new 出一個全新的節點並回傳它 ⇒ 回傳值是一個「原本不存在於樹上」的指標 ⇒ 必須靠賦值接進去。
· 226 翻轉:遞迴只交換既有節點的兩根子指標,回傳的永遠是傳進去的那個指標(實測 2000 棵樹,invertTree(root) == root 命中 2000/2000)⇒ 那個賦值是 root->left = root->left,恆等的。

把兩題放進同一支程式、用同一個窮舉宇宙跑:
226 翻轉:比較 626 棵樹,有回寫 vs 無回寫  →  結果不同 = 0
701 插入:比較 4707 組,有回寫 vs 無回寫  →  結果不同 = 4706
同一行程式碼,一邊 0、一邊 4706。

這個判準在後面還會用到:450 刪除節點(子樹的根會換人)、1325 刪除葉節點(子樹可能整棵消失)—— 都是「會換掉子樹根」,所以回寫都是必要的。

實務建議:兩邊都寫它。因為它讓「這一層可能換掉子樹的根」這件事自動被處理掉,不必在父節點裡寫一堆 if;而在不需要的地方它只是一個恆等賦值,沒有成本。
A3. 只有一個真的存下新東西 —— 就是最底下那一個;其他全都是恆等賦值。

以本頁的 trace 為例,回程有三個回寫:
· 30->left = 新節點 ← ★ 真正的接線(把一個原本不在樹上的指標存進去)
· 20->right = 30 ← 原本就是 30,寫了等於沒寫
· 40->left = 20 ← 原本就是 20,同上

但你事先不知道哪一層才是真的那一層 —— 它取決於 val 會落在哪個空位,而那要走到底才知道。所以每一層都得寫。

這也解釋了一件事:為什麼「丟掉回寫」這個 bug 在小測資上看起來好像沒事。因為絕大多數的回寫本來就是恆等的 —— 只有最深的那一個有作用,而它剛好是最容易被忽略的那一個。

一般化的說法:這個模式付出了 O(h) 個「多餘」的賦值,換來「不必在父節點裡判斷子樹根有沒有換人」。這是一個很划算的交換 —— 賦值是 O(1) 的,而那些 if 會讓程式碼變得非常難讀。
A4. 因為這題「遞迴回來之後還要做事」,235 沒有。後果是 -O2 消不掉堆疊框。

尾遞迴的定義:遞迴呼叫的結果直接就是本層的回傳值,呼叫回來之後沒有任何事要做。

· 235 BST LCA:return lowestCommonAncestor(root->left, p, q); —— 直接回傳遞迴結果 ✓ 尾遞迴。
· 701(本題):root->left = insertIntoBST(...); 然後 return root; —— 回來之後要賦值,而且回傳的是「自己」不是遞迴結果 ✗ 不是尾遞迴。

組語實證(arm64, -O2):
bl   __Z13insertIntoBSTP8TreeNodei    ← 真的 call(不是 b 跳轉)
str  x0, [x19, #8]                     ← 回來之後才寫 ⇒ 框不能提前丟
stp  x20, x19, [sp, #-32]!             ← 每層固定配置 32 bytes
後果:-O2 只是把框縮小,並沒有消掉它。實測崩潰深度 -O0 = 104256(80 B/frame)、-O2 = 261284(32 B/frame)。
那個 80 值得解釋一下:成員函式要在框裡存 this,所以比同樣邏輯的自由函式(實測 64 B、崩潰 ~130362)多一個 16-byte 台階。LeetCode 的提交格式正是成員函式,所以引用 80。
對比 235:那題 -O2 發出 b(跳轉),遞迴變成迴圈,堆疊維持 O(1),量不到崩潰點。

判準記這一句:「不是看它是不是遞迴,是看『呼叫回來之後還有沒有事要做』。」而這題的「那件事」正是回寫 —— 所以「必須回寫」和「不是尾遞迴」其實是同一件事的兩面。
A5. 新節點永遠是葉子,而且既有結構一個節點都不會動。

這個作法只做一件事:往下走到一個 nullptr 的空位,把新節點掛上去。它從不旋轉、不重組、不搬動任何既有節點。

實測(窮舉 626 棵 BST × 4707 次插入,四個不變量皆 0 違反):
· 插入後仍是合法 BST
· 節點集合恰好 = 原集合 ∪ {val}
· 新節點永遠是葉子
· new TreeNode 恰好 1 次

順帶一提:題目說「可能有多種合法插法,回傳任何一種都可以」 —— 那是因為理論上你可以做旋轉、把新值插在中間再重組。但這個作法其實是唯一決定的:實測與獨立的迭代版對拍窮舉 4707 組 + 隨機 20 萬組,樹形逐位元完全相同。

代價是:它不會維持平衡。連續插入排序資料就會退化成一條鏈(見 App 3)—— 真正的平衡樹(AVL、紅黑樹)之所以複雜,就是因為它們必須重組結構,而那時「子樹的根會換人」,回寫模式就更不可或缺了。
App 1. 回寫模式還在,而且更關鍵 —— 難在「被刪的節點有兩個小孩」的情況。

TreeNode* deleteNode(TreeNode* root, int key) {
    if (root == nullptr) {
        return nullptr;
    }

    if (root->val > key) {
        root->left = deleteNode(root->left, key);      // ← 同樣的回寫
    } else if (root->val < key) {
        root->right = deleteNode(root->right, key);
    } else {
        // 找到了,三種情況
        if (root->left == nullptr)  return root->right;   // ← 子樹的根「換人」了
        if (root->right == nullptr) return root->left;

        // 兩個小孩:找右子樹的最小值(中序後繼)頂上來
        TreeNode* succ = root->right;
        while (succ->left != nullptr) {
            succ = succ->left;
        }
        root->val = succ->val;                            // 把值搬上來
        root->right = deleteNode(root->right, succ->val);  // 再去刪掉那個後繼
    }

    return root;
}
回寫在這裡比插入更不可或缺:插入時只有最深那一層會換人,刪除時「被刪節點所在的那一層」的子樹根一定會換人(return root->right)。

難點是「兩個小孩」那一支:不能直接刪,因為兩棵子樹要接到哪裡去?標準解法是找中序後繼(右子樹一路往左到底,也就是右子樹的最小值)把它的值搬上來,再遞迴去刪掉那個後繼 —— 而後繼必定「至多只有一個小孩」,所以退化成簡單情況。

用前繼(左子樹的最大值)也完全對稱可行 —— 這也是為什麼刪除的結果不唯一。
App 2. 會變得漂亮很多 —— 回寫真的可以省掉,因為你拿到的是「欄位本身」而不是副本。

void insert(TreeNode*& node, int val) {       // ← 注意這個 &
    if (node == nullptr) {
        node = new TreeNode(val);             // 直接寫進「呼叫端的欄位」
        return;
    }

    if (node->val > val) {
        insert(node->left, val);              // 不需要接住回傳值
    } else if (node->val < val) {
        insert(node->right, val);
    }
}
// 呼叫:insert(root, val);   root 本身若為 null 也會被正確填上
關鍵差別:TreeNode*& 是「指向指標的參考」 —— 遞迴拿到的不是 root->left 的副本,而是 root->left 這個欄位本身的別名。所以 node = new TreeNode(val); 直接就改到了父節點的 left。

這正好反證了 A1 的說法:回寫之所以必要,純粹是因為「傳的是副本」。一旦傳的是參考,那條「回家的路」本來就存在,回寫自然就不需要了。

那為什麼 LeetCode 不用這個寫法?因為題目的函式簽名是固定的(TreeNode* insertIntoBST(TreeNode* root, int val)),必須回傳 TreeNode*。但在你自己的資料結構程式碼裡,TreeNode*& 或 TreeNode** 通常更乾淨 —— 這也是很多 C 語言教科書寫二元樹插入時用 TreeNode** 的原因。
App 3. 會退化成一條鏈 —— 每次插入都變成 O(n),建整棵樹要 O(n²)。

依序插入 1, 2, 3, …, n:每個新值都比現有的全部都大,所以每次都一路往右走到底。結果是一棵只有右子樹的鏈,樹高 n。

實測對照(本頁的複雜度表):
· 平衡 BST n=1023 → 每次插入都只要 11 次呼叫
· 退化鏈 n=1000 插入新的最大值 → 1001 次呼叫
差了將近 100 倍,而且那還只是 n=1000。

而且不只是慢 —— 還會爆堆疊。遞迴版在 n=10⁴ 的鏈上需要約 640 KB(-O0),在 512 KB 的環境下就 SIGSEGV。

三種解法:
① 打亂插入順序 —— 隨機順序建出的 BST,期望高度是 O(log n)。最簡單,但你不一定能控制輸入。
② 用自平衡樹(AVL、紅黑樹)—— 插入時旋轉重組,保證 O(log n)。而重組正是「子樹的根會換人」,所以回寫模式在那裡是絕對必要的。
③ 如果資料本來就有序,直接用「有序陣列 + 二分」,或由中點遞迴建樹(LeetCode 108)—— 一次就建出完美平衡的 BST,O(n)。

這也回答了「為什麼實務上很少直接用裸 BST」:std::map / std::set 底層是紅黑樹,正是為了避開這個退化問題。
