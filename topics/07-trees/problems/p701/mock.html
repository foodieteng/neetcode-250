A naive approach would be to read every value into a sorted list, add val, and rebuild a balanced BST. That is correct, but O(n) time and O(n) extra space, and it reshapes a tree that was already fine.

This problem reminds me of a plain binary search, just on a tree instead of an array. Each compare drops one whole side — except when I run out of tree, I build a node instead of returning "not found". So I'll do a simple recursive descent.

P — plan
C
CANDIDATE

Here's the plan.

// contract: insert(node, val) returns the root of that
// subtree AFTER val has been added into it

insert(node, val):
  if node is null: return new node(val)
  if node.val > val: node.left  = insert(node.left, val)
  if node.val < val: node.right = insert(node.right, val)
  return node

// invariant: the returned pointer is ALWAYS the correct
// root of that subtree, whether it changed or not

One: if the node is null, return a new node holding val.
Two: otherwise compare, and recurse into the left or right child.
Three: store what that call returns back into the child, then return the node.

One thing worth flagging — that store is not decoration, it is the wiring. The recursive call only got a copy of the parent's child pointer, so the new node has no other way into the tree. Drop the store and the node leaks while the tree stays unchanged.

There's a trade-off here. A loop with a parent pointer uses O(1) space; the recursion costs O(h) stack. I'll take the recursion because it is easier to read, and check the stack math at the end.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    TreeNode* insertIntoBST(TreeNode* root, int val) {
        // Reached an empty slot — the new node is born here
        if (root == nullptr) {
            return new TreeNode(val);
        }

        if (root->val > val) {
            root->left = insertIntoBST(root->left, val);    // ← write-back: the wiring
        } else if (root->val < val) {
            root->right = insertIntoBST(root->right, val);   // ← same as above
        }

        return root;   // root was not replaced; hand it back as-is
    }
};

A null root is the empty slot, so I return a new node. Otherwise the comparison picks a side, and I store the recursive result back into that child before returning root.

One thing worth flagging — on the way back up, only one of those stores saves something new. In our example, 30->left = 25 is the real one; 20->right = 30 and 40->left = 20 just put back pointers that were already there. But I cannot know in advance which level is the real one, so every level needs the store.

I
INTERVIEWER

I've seen people write that same pattern in the invert-tree problem. Is it always needed?

C
CANDIDATE

No, and that is a good contrast. In invert binary tree the write-back looks the same, but it is redundant. That recursion only swaps fields on existing nodes and always returns the pointer it was handed, so storing it back is a no-op.

Over all 626 tree shapes with up to 7 nodes, dropping it there changes zero results. Here, dropping it breaks 4706 out of 4707 cases — only the empty tree survives.

So my test is one question: can this recursion create a new node, or swap in a different subtree root? If yes, the write-back is the wiring. If no, it is decoration.

The time complexity is O(h), where h is the height — one compare per level, and I never look at a sibling. The space complexity is O(h) for the call stack, plus the one node I allocate.

In the worst-case scenario the tree is one long chain, so h = n and both become O(n). If the tree is balanced, it's O(log n).

Let me think about complexity here — specifically the stack, since that worst case is real at 104 nodes.

C
CANDIDATE

One thing I want to be precise about: this is not a tail call. After the recursive call comes back, I still store the result and return root, so the compiler cannot turn it into a jump.

In the arm64 assembly at -O2, it's a real call followed by the store:

stp  x20, x19, [sp, #-32]!   // 32-byte frame per level
...
bl   __Z13insertIntoBSTP8TreeNodei  // a real call, not a jump
str  x0, [x19, #8]            // the write-back, AFTER the call

So -O2 only shrinks the frame, to 32 bytes per level. On an 8 MB stack, the crash depth is about 261,000 at -O2, and about 104,000 at -O0. 104 levels fits easily.

But with a 512 KB stack, the -O0 build segfaults at 104 while -O2 survives. So on a thread with a small stack, I'd switch to the iterative version.
