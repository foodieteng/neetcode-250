A naive approach would be to collect every value into an array, sort it, and return index k - 1. That's O(n log n) time and O(n) space. It works for any binary tree, but it ignores the search-tree property completely.

This problem reminds me of "inorder traversal as a sorted stream." Since inorder already comes out sorted, I just count as I go, and stop caring once the count hits k. No array, no sort — the only extra memory is the recursion stack.

CANDIDATE

Here's the plan.

// state: rank = how many more visits until the answer
rank = k
// inorder(node)
if node is null or rank <= 0: return   // null, or already found
inorder(node.left)
rank = rank - 1                        // "visit" this node
if rank == 0: ans = node.val           // the kth visit
inorder(node.right)

One: keep a member counter rank, starting at k — how many more visits until the answer.
Two: walk inorder, and each visit takes one off rank.
Three: when rank hits 0, the node I'm on is the answer, and any call that starts with rank <= 0 returns right away.

One thing worth flagging — rank must be shared across all the calls. If I passed it by value, the count from the left subtree would never come back up to the parent. That's wrong on tiny inputs: [2,1], k = 1 returns 2 instead of 1.

There's a trade-off here: an explicit stack avoids recursion, but at 104 nodes recursion is safe, so I'll keep it simple. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int ans, rank;                                   // shared by every recursion level

    int kthSmallest(TreeNode* root, int k) {
        rank = k;
        inorder(root);
        return ans;
    }

    void inorder(TreeNode* root) {
        if (!root || rank <= 0) return;             // checked only on entry

        inorder(root->left);
        if (--rank == 0) ans = root->val;         // the k-th node visited
        inorder(root->right);
    }
};

kthSmallest sets rank = k, runs inorder, and returns ans.

One thing worth flagging — it's --rank == 0, pre-decrement: it subtracts first, then compares. If I wrote rank-- == 0, it would compare the old value. On [1] with k = 1, the old value is 1, so the check fails and ans is never set. Across every search tree up to 7 nodes and every k, that's 4,081 cases, and rank-- gets all of them wrong. So this one character is a correctness issue, not style. And ans is always set, because k <= n.

Let's dry-run the code on example 2, [5,3,6,2,4,null,null,1] with k = 3. I expect 3.

The row that matters is the visit to 3: rank hits 0 and ans becomes 3, so the output is correct.

But the early exit is only checked when a call starts. Node 5 already made its left call, so on the way back it still visits itself, taking rank to -1, and calls right on 6. So every went-left ancestor of the answer costs one extra visit — k + L in total.

The fix is small: check rank again right after the left call, and return as soon as I set ans.

void inorder(TreeNode* root) {
    if (!root || rank <= 0) return;
    inorder(root->left);
    if (rank <= 0) return;                         // answer found in the left subtree
    if (--rank == 0) { ans = root->val; return; }  // it's me: skip the right subtree
    inorder(root->right);
}

Then visits are exactly k — here, 7 calls and 3 visits.

Corner cases:

• [1], k = 1 → 1, that node.
• [2,1], k = 1 → 1 — the case pass-by-value breaks.

C
CANDIDATE

Let me think about complexity here.

Time is O(h + k + L) for this code: h to walk down to the smallest value, k visits, and L extra visits on the way back up. Since L <= h, that's still O(h + k), and the fix removes the L term.

It matters on a left chain with k = 1: every node is a went-left ancestor, so the original makes 20,001 calls and 10,000 visits just to find the smallest. With the fix, it's 1 visit.

Space is O(h) for the recursion stack. Worst case is a chain, 10,001 frames deep. The crash only comes at about 261,408 frames, a 26× margin, so recursion is fine here.

C
CANDIDATE

Right now every query starts over and costs O(h + k). To make it faster, I'd store one more number in each node: the count of nodes in its left subtree.

// each node keeps leftSize = # nodes in its left subtree
node = root
loop:
  if k <= node.leftSize:       node = node.left     // answer is on the left
  elif k == node.leftSize + 1: return node.val      // it's this node
  else: k -= node.leftSize + 1; node = node.right   // skip left + me

If k is at most the left size, the answer is on the left. If k equals left size + 1, it's this node. Otherwise I subtract left size + 1 from k and go right.

Each query is now O(h). The cost moves to the updates: on insert or delete, I fix the counts along the path, which is also O(h). If I keep the tree balanced, h stays at O(log n) for both.

Oh, one more thing — the original early exit looks like it stops everything, but it only fires when a new call starts. That's why I'd always add the second check after the left call.
