範例 Trace// [3,9,20,null,null,15,7] → true

官方範例。方括號裡是「這次 depth() 花了幾次呼叫」。 以下每一步都是實跑印出來的。

// 第 1 步:檢查根節點 isBalanced(3) depth(9) = 1 [3 次呼叫,走訪 {9}] depth(20) = 2 [7 次呼叫,走訪 {20, 15, 7}] ← 15 和 7 第一次被走 abs(1 - 2) = 1 <= 1 ✓ 通過 → && 沒有短路,繼續遞迴檢查兩棵子樹 // 光是量根的左右高度,整棵樹就已經被走過一遍了
// 第 2 步:檢查節點 9(葉節點) isBalanced(9) depth(nullptr) = 0 [1 次] depth(nullptr) = 0 [1 次] abs(0 - 0) = 0 <= 1 ✓ isBalanced(nullptr) → true isBalanced(nullptr) → true → 節點 9 回傳 true // 葉節點必定平衡 —— 但程式碼還是老實跑了兩次 depth(nullptr),沒有特判
// 第 3 步:檢查節點 20 —— 這裡出現重複 isBalanced(20) depth(15) = 1 [3 次呼叫] ← 15 「第二次」被走訪 depth(7) = 1 [3 次呼叫] ← 7 「第二次」被走訪 abs(1 - 1) = 0 <= 1 ✓ → 繼續遞迴檢查 15 和 7(都是葉節點,各 2 次呼叫,都通過) → 節點 20 回傳 true → 節點 3 回傳 true // 15 和 7 在第 1 步就被走過了,這裡又走一次 —— 這就是「由上往下」的代價
// OUTPUT return true 每個節點被 depth() 走訪的次數: 節點 9 → 1 次 節點 20 → 1 次 節點 15 → 2 次 ★ 節點 7 → 2 次 ★ 總計 depth() 呼叫 22 次 由下往上版只需要 11 次(2n+1 = 2×5+1)—— 剛好一半 一般規律:深度 d 的節點會被 depth() 走 d+1 次(它自己 + 每個祖先各一次) // 這棵樹只有 5 個節點就差了一倍;完美樹 n=4095 時差 11 倍
注意這棵範例樹是平衡的,所以兩個 && 短路都沒有觸發 —— 整棵樹被完整探索。這正是「最壞情況是平衡樹」的具體樣子: 能讓程式走完全程的樹,必定是通過所有檢查的樹,也就是平衡樹。

應用題// APPLICATION

App 1. 把由下往上的 −1 旗標改成回傳 pair。為什麼這個版本更通用?什麼情況下 −1 的技巧會失效?
App 2. 改成回傳「第一個不平衡的節點」而不只是 true/false。要怎麼改?
App 3. 如果題目改成「左右高度差不超過 k」,或者「左右節點數差不超過 1」(權重平衡),程式要怎麼改?後者為什麼是更嚴格的條件?
// ANSWERS
A1. 因為不平衡可能藏在某棵子樹「內部」,而根看起來完全正常 —— 這種形狀最少需要 6 個節點。

要騙過「只檢查根」,樹必須同時滿足兩件事:根的左右高度差 ≤ 1(看起來沒事),但某棵子樹內部的高度差 ≥ 2。

實測:窮舉 n ≤ 8 全部 2056 種樹形,「只看根」錯 164 種,但:
· n = 0,1,2,3,4,5 → 0 種失敗(全部 65 種樹形都碰巧正確)
· n = 6 → 16 例　· n = 7 → 32 例　· n = 8 → 116 例

最小反例 [1,1,1,null,1,null,1,null,null,null,1](n = 6):
· 根:左高 3、右高 2 → 差 1,看起來完全沒問題 ✓
· 但左小孩:左高 0、右高 2 → 差 2 ✗ —— 不平衡藏在這裡

「n ≤ 5 全部碰巧正確」就是它難發現的原因。你在紙上畫的例子幾乎都在這個範圍內,那裡「只看根」永遠是對的。

而且這和 543 直徑那題是同一種陷阱:兩題的最小反例都要 6 個節點,兩題都是「局部的極端值藏在子樹裡,根看不到」。看到「每一個節點」或「不一定通過根」這類字眼,就要立刻想到窮舉驗證,而不是手算幾個例子。
A2. 不對。實測退化鏈是線性的,真正的上限是 O(n log n)。

為什麼退化鏈不慢:&& 會短路。一條長度 n 的鏈,在根節點就有 depth(左) = n−1、depth(右) = 0,abs(n−1) > 1 第一個條件就 false —— 兩個 isBalanced 遞迴完全不會被呼叫。

實測 depth() 呼叫次數(退化左鏈):
n=250 → 500、n=500 → 1000、n=1000 → 2000、n=2000 → 4000
每次加倍只變 2.0 倍 —— 嚴格線性。若真是 O(n²),n=2000 應該要 4002000 次,實測只有 4000 次,差 1000 倍。而 isBalanced() 的呼叫次數永遠是 1。

真正的最壞情況是「平衡樹」。推理很簡單:一棵樹要被「完整探索」,就代表它處處通過檢查 —— 也就是它是平衡的;而平衡樹的高度 h = O(log n),每個節點最多被重複走 O(log n) 次 ⇒ 上限 O(n log n),不可能到 O(n²)。

實測完美樹的額外成本:n=1023 → 9.0 倍、n=4095 → 11.0 倍、n=4180 → 11.5 倍。倍率每次加倍約 +0.7,正是 Θ(log n) 的成長。

教訓:短路運算子會改變複雜度分析,而紙上分析很容易漏掉這一點。(對比 104:那題用的是 max —— 普通函式,不短路,所以兩邊一定都走完。)
A3. 這題完全不會錯(0/2056);但 104 那題會全錯(626/626)。

原因是「這個值後來怎麼被使用」。

base case 回 1 會讓每個節點的高度一律 +1(常數偏移,見 104 的 A1:max 不會累加偏移,所以它乾淨地傳到最上面)。

· 104 把高度直接當答案回傳 → 偏移一路傳到輸出 → 全錯,而且是恆定 +1。
· 110 只用到高度的差:
abs( (H(左)+1) − (H(右)+1) ) = abs( H(左) − H(右) )
兩邊的 +1 在減法裡乾淨地互相消掉了。

實測:窮舉 2056 種樹形,這個變體失敗 0 種 —— 它是九個變體裡唯一一個「錯了但完全無害」的。

值得記住的一般原則:一個 bug 會不會造成傷害,取決於下游怎麼消費那個值。常數偏移會被減法消掉,但不會被加法或直接回傳消掉。所以「這段程式碼有 bug」和「這個 bug 會讓答案錯」是兩件事 —— 不過在正式的程式碼裡我還是會把它改對,因為下一個人可能會把 depth() 拿去別的地方用。
A4. 因為高度永遠不可能是負的,所以 −1 不會和任何真實高度混淆。

這是一個常見手法:用值域裡「不可能出現的值」來夾帶一個額外的布林資訊,免得多開一個回傳值或多傳一個參數。空樹回 0、任何非空樹回 ≥ 1,所以 −1 是安全的哨兵值。

它還帶來一個附加好處:提早結束。一旦某處回傳 −1,上面每一層都直接往上傳、不再計算 —— 等於免費得到了短路。

更好的做法(見 App 1):回傳 pair<int, bool> 或一個小 struct。理由:
① 不依賴「剛好有個不可能的值」這個巧合。如果哪天題目改成「高度可以是負的」(例如帶權重的樹),−1 的技巧立刻失效。
② 可讀性更好 —— {height, isBalanced} 直接說出它在表達什麼,不必靠註解解釋 −1 是什麼意思。

面試時兩種都可以,但要能說出「為什麼 −1 是安全的」 —— 也就是你知道自己在依賴一個值域假設,而不是碰巧寫對。這正是這類問題想聽到的東西。
A5. 會誤殺,不會漏抓 —— 因為「節點數差 ≤ 1」是比「高度差 ≤ 1」嚴格得多的條件。

實測:窮舉 2056 種樹形,這個變體錯 42 種,而且 42 個失敗全部是「把平衡樹判成不平衡」(false-BAD) —— 一個漏抓都沒有。最小反例 [1,1,1,null,null,1,1]:高度平衡 ✓,但左子樹 1 個節點、右子樹 3 個節點,節點數差 2 ✗。

為什麼嚴格得多:高度只看最長的那條路,節點數看的是整棵子樹的量。一棵高度 3 的子樹可以有 3 個節點(一條鏈),也可以有 7 個(完美樹)—— 高度相同,節點數可以差很多。所以「節點數平衡 ⇒ 高度平衡」,但反過來不成立。

順帶一提,這個「錯誤」其實是一個真實存在的資料結構條件,叫做權重平衡(weight-balanced),用在某些平衡樹的實作裡。它不是「壞掉的高度平衡」,而是「另一種更強的平衡定義」 —— 只是這題要的不是它。

「知道 bug 的方向」比「知道它錯幾筆」有用得多:
· 過嚴(只誤殺)→ 你的測資裡要有「形狀不對稱但仍平衡」的樹才抓得到。
· 過鬆(只漏抓,例如「只看根」)→ 要有「不平衡藏在深處」的樹才抓得到。
兩種 bug 需要的測資完全不同 —— 這就是為什麼本頁的陷阱表要窮舉所有樹形,而不是挑幾筆。
App 1. 回傳 pair<int,bool>,把「高度」和「平衡與否」分成兩個欄位。

pair<int, bool> check(TreeNode* root) {
    if (root == nullptr) {
        return {0, true};
    }

    auto [leftHeight,  leftOk]  = check(root->left);
    auto [rightHeight, rightOk] = check(root->right);

    int  height = 1 + max(leftHeight, rightHeight);
    bool ok     = leftOk && rightOk && abs(leftHeight - rightHeight) <= 1;

    return {height, ok};
}
// isBalanced(root) 就是 check(root).second
為什麼更通用:它不依賴「值域裡剛好有個不可能的值」。

−1 技巧會失效的情況:
① 合法值域包含負數。例如題目改成「節點帶權重,高度是路徑上的權重和」,權重可以是負的 —— 這時 −1 就是一個合法的高度,哨兵和真實值混在一起,整個技巧崩潰。
② 要回傳的東西不只一個。例如同時要高度和節點數,你就沒有第二個哨兵可用了。
③ 別人來維護時容易誤解 —— −1 是什麼意思要靠註解,{height, ok} 則自我說明。

代價:pair 版少了「早退」(上面這寫法會把兩邊都算完)。要保留早退就在拿到 leftOk == false 時直接 return {0, false}; —— 兩者可以兼得。

一般原則:哨兵值是「借用值域的空隙」,而 pair/struct 是「誠實地擴充回傳型別」。前者短、後者穩;值域一旦變寬,前者就得改寫。
App 2. 把回傳型別換成節點指標,並確保「回報最先發現的那一個」。

TreeNode* culprit = nullptr;      // 第一個不平衡的節點

int check(TreeNode* root) {
    if (root == nullptr) return 0;

    int left  = check(root->left);
    int right = check(root->right);

    if (culprit == nullptr && abs(left - right) > 1) {
        culprit = root;           // 只記第一個,之後不再覆蓋
    }

    return 1 + max(left, right);
}
關鍵在 culprit == nullptr 這個守衛:沒有它,後來發現的不平衡節點會蓋掉先發現的。

但「第一個」是什麼意思?這裡要講清楚。因為這是後序走訪,「最先被發現」的是最深、最左的那個不平衡節點 —— 不是「離根最近」的那個。

如果你要的是「離根最近的不平衡節點」,那就不能用早退,要改成由上往下檢查:從根開始,第一個高度差 > 1 的節點就是答案(而它上面的祖先都通過了)。這正好是你原本那份「由上往下」寫法的優勢 —— 它天然就是從根往下檢查的順序。

一般原則:「回傳第一個違規者」這種需求,一定要先問清楚「第一個」是按哪種走訪順序定義的。不同的順序需要不同的骨架,而且兩者都合理 —— 這是值得在面試裡主動澄清的問題。
App 3. 「差 ≤ k」只要改一個常數;「節點數差 ≤ 1」則要換掉回傳的量。

① 高度差 ≤ k:把 abs(left − right) <= 1 改成 <= k,其他一個字都不用動。
值得注意的是 k 會影響「不平衡有多難出現」:k = 0 要求完全等高(只有完美樹通過);k 越大條件越鬆,k ≥ n 時所有樹都通過。實測 k = 0(也就是把 <= 1 寫成 < 1)錯 64/2056,全部是誤殺 —— 和 A5 一樣是「過嚴」型的錯誤。

② 節點數差 ≤ 1(權重平衡):要把遞迴回傳的東西從「高度」換成「節點數」:
int size(TreeNode* root) {
    if (root == nullptr) return 0;

    return 1 + size(root->left) + size(root->right);   // max 換成 +
}
注意合併運算從 max 變成 + —— 這正是 104 的 A5 提過的:同一個骨架,換掉合併運算就換一題(max → 樹高、+ → 節點數)。

為什麼節點數版更嚴格:高度只看最長的那條路,節點數看整棵子樹的量。高度 3 的子樹可以有 3 個節點(鏈)也可以有 7 個(完美樹)—— 所以「節點數平衡 ⇒ 高度平衡」,反之不成立。實測:用節點數判斷會把 42/2056 棵真正平衡的樹誤判成不平衡,而且一個漏抓都沒有 —— 正是「嚴格得多」的實證。

這個更強的條件在實務上有名字:權重平衡樹(weight-balanced tree),某些平衡樹實作用的就是它,因為它能給出比高度平衡更強的操作成本保證。
