A naive approach would be to ignore the "every node" part and only check the root. It's one line, and it's wrong — I'll come back with a number on how wrong.

This problem reminds me of a post-order height computation, because the height helper is the standard 1 + max recursion. The only new thing is that I need the height at every node and a yes-or-no answer at every node.

There are two ways to put those together. Top-down: at each node, ask for both child heights and check the gap, then recurse into the children. Bottom-up: compute each height once and carry a "failed" signal up with it. I'll write top-down first because it maps directly onto the definition, and then talk about bottom-up.

CANDIDATE

Here's the plan.

// depth(x): plain height
depth(null) = 0
depth(x)    = 1 + max(depth(x.left), depth(x.right))

// isBalanced(x): the definition, written out
isBalanced(null) = true
isBalanced(x) =
  |depth(x.left) - depth(x.right)| <= 1
  && isBalanced(x.left)
  && isBalanced(x.right)

One: a depth helper returns the plain height, 0 for empty.
Two: an empty tree is balanced.
Three: otherwise, the gap at this node must be <= 1, and both children must be balanced too, chained with &&.

One thing worth flagging — checking only the root is not a small error. Over every tree shape up to 8 nodes, the root-only check is wrong on 164, and every shape with 5 nodes or fewer passes by accident.

The smallest counterexample needs six nodes: [1,1,1,null,1,null,1,null,null,null,1]. The root sees heights 2 and 3, so it looks fine, but its right child sees 0 and 2. That's why this bug survives casual tests.

There's a trade-off. Top-down reads like the definition but recomputes heights; bottom-up computes each height once but needs a sentinel. Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool isBalanced(TreeNode* root) {
        if (root == nullptr) return true;

        int left = depth(root->left), right = depth(root->right);
        return abs(left - right) <= 1
            && isBalanced(root->left)       // ← these two lines make it "every node"
            && isBalanced(root->right);
    }

    int depth(TreeNode* root) {
        if (root == nullptr) return 0;

        return 1 + max(depth(root->left), depth(root->right));
    }
};

The empty tree is balanced. Otherwise I take both child depths, and return whether the gap is at most one, and the left subtree is balanced, and the right subtree is balanced. The depth helper is the usual 1 + max of both sides.

One thing worth flagging — the && here isn't just style. It short-circuits: the moment the gap test fails, both recursive calls are skipped entirely. Hold on to that, because it changes the complexity story in a way people usually get wrong.

The waste: nodes 15 and 7 are each walked twice — once when the root measures its right side, and again when 20 measures its own sides. In general, a node d levels below the root gets walked d times, once per checked ancestor.

Corner cases:

• Empty tree → true immediately.
• Single node → gap 0 and two null children, so true.
• The six-node counterexample → false, failing at the root's right child — exactly what the root-only check misses.

C
CANDIDATE

Let me think about complexity here. The usual claim is O(n2), with a long chain as the bad case. I want to push back on that, because I measured it.

On a chain, the root's gap fails at once, and && skips both recursive calls. Chains of 250 up to 2000 nodes took 500 up to 4000 depth calls. Doubling the input doubles the work: linear.

In general, each node is walked once per checked ancestor, so time is O(n · h). A perfect tree gives O(n log n) — 9.0× the bottom-up count at n = 1023, 11.0× at n = 4095. But it can go higher: a comb, a passing spine with stick branches, reaches O(n1.5). Space is O(h) for the call stack.

CANDIDATE

Oh, one more thing — the bottom-up version fixes this and is worth writing.

class Solution {
public:
    bool isBalanced(TreeNode* root) {
        return check(root) != -1;
    }

    // returns the height; if anything below is unbalanced, returns -1 and passes it all the way up
    int check(TreeNode* root) {
        if (root == nullptr) return 0;

        int left = check(root->left);
        if (left == -1) {
            return -1;                   // left side already broken, no need to compute the right
        }

        int right = check(root->right);
        if (right == -1) {
            return -1;
        }

        if (abs(left - right) > 1) {
            return -1;                   // this level is unbalanced
        }

        return 1 + max(left, right);       // balanced: return the real height
    }
};

One function returns the height, but returns -1 to mean "something below me is not balanced". If either child comes back -1, pass it straight up; if the gap is over one, return -1; otherwise return 1 + max. That's a single pass, O(n).

The sentinel is safe for a specific reason: a real height can never be negative — the smallest honest value is 0, for an empty subtree. If the function could legitimately return a negative, this trick would be unsafe and I'd need a separate flag.
