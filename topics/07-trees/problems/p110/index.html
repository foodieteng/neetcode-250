題目簡介// THE QUESTION

QUESTION

給二元樹的根節點,判斷它是否高度平衡 —— 也就是每一個節點的左右子樹高度差都不超過 1。 節點數 0 ~ 5000,節點值 −10⁴ ~ 10⁴。

這題的定義有一個很容易讀漏的字:「每一個節點」。 不是只看根、也不是只看某幾層 —— 樹裡每一個節點都必須滿足這個條件。

這題也是本章第一次出現「同一題有兩種寫法,成本不同」的情況: 由上往下(在每個節點現場量高度)和 由下往上(一趟遞迴同時算高度與判斷)。 兩者都會過,但成本差很多 —— 而且「差多少」這件事,實測結果和大多數人的直覺不一樣。

兩種寫法// TOP-DOWN vs BOTTOM-UP

A 只檢查根節點的左右高度差 錯 164/2056
讀漏了「每一個節點」。 實測窮舉 n ≤ 8 全部 2056 種樹形,錯 164 種; 而且 n ≤ 5 全部碰巧正確,最小反例要 n = 6。
× REJECT · 手算測不出來
B 由上往下:每個節點現場呼叫 depth() O(n log n)
完全正確(窮舉 n ≤ 10 共 23714 種樹形,零不一致), 就是你寫的這一份。但每個節點會被重複走訪 —— 深度 d 的節點被走 d+1 次。
△ 正確但多做工
BOTH WORK · PREFER
C 由下往上:回傳高度,不平衡就回 −1 O(n)
一趟走完,每個節點只被進入一次(2n+1 次呼叫)。 用「不可能的回傳值」−1 兼作失敗旗標, 發現不平衡就一路往上傳,提早結束。
● 建議預設
⚠ 一個常見但錯誤的說法:「由上往下是 O(n²)」。 實測不是。因為 && 會短路 —— 退化成一條鏈時,根節點的高度差就過大,兩個遞迴直接被跳過, 實測呼叫次數只有 2n,是線性的。 真正被完整走完的是平衡樹,而平衡樹的 h = O(log n), 所以實際上限是 O(n log n)。詳見程式碼頁的實測表。

核心策略 · 三步驟// THE SHAPE

你的寫法 · 由上往下

  1. 量自己的左右高度:各呼叫一次 depth()。
  2. 檢查自己:abs(left − right) <= 1。
  3. 還要檢查子樹:&& isBalanced(left) && isBalanced(right) —— 這兩個遞迴就是「每一個節點」那句話的實現,少了它們就是上面的錯誤 A。

更快的寫法 · 由下往上

  1. 先問兩邊的高度(這部分和 104 一模一樣)。
  2. 任一邊是 −1 就直接往上傳 −1 —— 底下已經壞了,不必再算。
  3. 自己也檢查一次:差 > 1 就回 −1,否則回 1 + max(左, 右)。
由下往上之所以能一趟做完,是因為它順便把高度算出來了。 由上往下每到一個節點都重新量一次高度,而那個高度其實在上一層就已經算過。 「把已經算過的東西順手帶上來」是所有樹形遞迴優化的共同手法。

兩個一定會被問到的「為什麼」// TWO LEMMAS

LEMMA 1 · 「只看根」為什麼一定要 6 個節點才露餡

要騙過「只檢查根」,你需要一棵樹同時滿足兩件事: 根的左右高度差 ≤ 1(看起來沒問題),但某棵子樹內部的高度差 ≥ 2。

實測:窮舉 n ≤ 8 全部 2056 種樹形,「只看根」錯 164 種, 但 n = 0,1,2,3,4,5 一種都沒錯 —— 首次失敗在 n = 6(16 例),n = 7 有 32 例,n = 8 有 116 例。
最小反例是 [1,1,1,null,1,null,1,null,null,null,1]: 根的左高 3、右高 2,差 1 看起來沒事; 但左小孩的左高 0、右高 2,差 2 —— 那裡才是不平衡的地方。
所以在紙上畫 3~5 個節點的例子,永遠發現不了這個 bug。

LEMMA 2 · base case 寫錯成 1,竟然完全無害

在 104 求深度那題,把 depth() 的 base case 從 return 0 改成 return 1 會全部答錯(626/626)。 但在這一題,同樣的錯誤完全不影響答案。

實測:窮舉 2056 種樹形,這個變體失敗 0 種。
原因:它讓每個節點的高度一律 +1(常數偏移), 而這題只用到高度的「差」 —— (left+1) − (right+1) = left − right,偏移在減法裡乾淨地消掉了。
這是七個變體裡唯一一個「錯了但不影響結果」的,值得記住: 一個錯誤會不會造成傷害,取決於後面怎麼用那個值。

// 九種改法的實測結果(窮舉 n = 0..8,共 2056 種樹形) 只檢查根,不遞迴子樹 → 錯 164/2056,n <= 5 全部碰巧對,最小反例要 n = 6 只遞迴左子樹 → 錯 34/2056,失敗都是「不平衡藏在右子樹」,同樣要 n = 6 <= 1 寫成 < 1(要求完全等高) → 錯 64/2056,最小反例 [1,null,1] 忘記 abs → 錯 275/2056,只抓得到「左比右高」一個方向 depth 忘記 +1 → 錯 1988/2056,depth 恆為 0 ⇒ 所有樹都「看起來平衡」 用「節點數」代替「高度」 → 錯 42/2056,條件過嚴 —— 只會誤殺,永遠不會漏抓 isBalanced 漏 nullptr 檢查 → SIGSEGV,連 [] 都炸 depth 漏 nullptr 檢查 → SIGSEGV,最小觸發 [1]([] 反而僥倖過) depth base case 回 1 → 錯 0/2056 ← 這個是「無害」的,見 LEMMA 2 // 注意倒數第二列:[] 僥倖過是因為外層 guard 先擋掉,depth() 根本沒被呼叫

一句洞察// INSIGHT

「每一個節點」那五個字,就是這題的全部。 漏掉它 → 錯 164/2056,而且 n ≤ 5 全部碰巧對,手算永遠測不出來。
而優化的方向是「別重複算已經算過的東西」 —— 由上往下在每個節點重新量高度,由下往上則讓遞迴順手把高度帶上來, 並用 −1 這個不可能的高度值兼作失敗旗標。
