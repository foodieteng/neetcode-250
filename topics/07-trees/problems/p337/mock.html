Hmm, let me think about this for a second.

A naive approach would try every valid set of houses — exponentially many, so at 104 nodes it never finishes.

This problem reminds me of dynamic programming on a tree: a take-it-or-skip-it choice per node, where the state is a subtree. The recursion alone is still exponential, because both branches reach into the same grandchildren. So I'll add a memo keyed by node pointer. Each node is solved once, and the whole thing becomes O(n).

P — plan
C
CANDIDATE

Here's the plan.

// rob(node) = the most money from this whole subtree
rob(null) = 0

// two choices at every node
robThis  = node.val + rob(4 grandchildren)
skipThis = rob(node.left) + rob(node.right)
rob(node) = max(robThis, skipThis)

// memo[node] caches the answer so each node is solved once

One: rob(null) is 0.
Two: rob this is the node's value plus its four grandchildren; skip this is rob(left) + rob(right).
Three: take the max and cache it by node pointer.

One thing worth flagging — the key must be the pointer, not the value, since two nodes can share a value over different subtrees.

There's a trade-off here: a post-order pass returning a {rob, skip} pair needs no map at all. I'm picking the memo because the rob-or-skip story reads directly off the code, and the time is the same. Does this approach sound good, or would you rather I think of another way?

I — implement
C
CANDIDATE

Alright, let me code this up. The memo is a class member.

class Solution {
private:
    unordered_map<TreeNode*, int> memo;

public:
    int rob(TreeNode* root) {
        if (root == nullptr) return 0;
        if (memo[root]) return memo[root];   // ⚠ tests the value, not presence

        int ll = 0, lr = 0, rl = 0, rr = 0;
        if (root->left) {
            ll = rob(root->left->left);       // grandchildren
            lr = rob(root->left->right);
        }
        if (root->right) {
            rl = rob(root->right->left);
            rr = rob(root->right->right);
        }

        return memo[root] = max(root->val + ll + lr + rl + rr,   // rob this one
                               rob(root->left) + rob(root->right)); // skip it
    }
};

Null returns 0, and a cached node returns its answer. Then I collect the four grandchildren, and return the max of rob this and skip this, storing it in the memo on the same line.

One thing worth flagging — the if (root->left) and if (root->right) guards exist so I can write root->left->left without dereferencing a null pointer. When a child is missing, its two values stay at 0, which is exactly what a missing subtree is worth.

Let me think about that. Good question — that's the line I marked, and my cache check is wrong.

if (memo[root]) tests the value, not whether the key is there. A subtree whose true answer is 0 stores 0, which reads back as false, so that node is recomputed every single time.

The answers stay correct; this is purely a speed bug. And memo[root] on a miss inserts a 0 entry, so memo.size() still ends at exactly the node count. That's why it's easy to miss.

So how do you fix it?

C
CANDIDATE

It's one word. Ask whether the key is present instead of whether the value is truthy:

if (memo.count(root)) return memo[root];

The fix gives identical answers on over a million test cases — purely a performance fix. With it, the call count is exactly 4n − 1 for any tree shape. That's clean O(n).

E — evaluate
C
CANDIDATE

Let me think about complexity here.

Time is O(n) with a working memo — each node is solved once, with a fixed amount of work. Space is O(h) for the stack plus O(n) for the map.

In the worst case the tree is a single chain. Measured at -O0, a frame is about 56 bytes, and the default 8 MB stack survives about 149,373 levels, so n = 10⁴ has a 14.94× margin. This isn't a tail call, so the compiler can't flatten it.

C
CANDIDATE

Oh, one more thing — the map is a class member on the heap, so it costs nothing per recursive call.

If I wanted only O(h) space, I'd switch to the pair version: one post-order pass returning {rob, skip}, and no map at all. Same time, less space.
