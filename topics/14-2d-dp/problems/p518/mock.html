This problem reminds me of an unbounded knapsack — infinite supply of each item — and I'm counting, not optimizing. dp[i] = number of combinations making amount i, seeded with dp[0] = 1.

And this is the part that actually matters — the whole problem lives in two independent loop decisions, and I want to be explicit about both. First, which loop is outer: coins outside gives combinations, amounts outside gives permutations. Second, the inner direction: ascending lets me reuse a coin, which is unbounded; descending uses each item once, which is 0/1 knapsack.

// axis 1: WHICH LOOP IS OUTER -> combinations vs permutations
coin outer   -> combinations (order ignored)  // this problem
amount outer -> permutations (order counts)

// axis 2: INNER DIRECTION -> unbounded vs 0/1
ascending  -> unbounded knapsack (reuse a coin)  // this problem
descending -> 0/1 knapsack (each item once)

So I want coin outer + ascending inner.

I
INTERVIEWER

Why does putting the coin loop outside give you combinations? Convince me.

C
CANDIDATE

Because it's secretly a 2-D table with the first dimension rolled away. The honest state is dp[k][i] = combinations making i using only the first k coin types. With the coin loop outside, after round k the array literally means that — after the coin=1 round it's "using only {1}", after the coin=2 round it's "using only {1,2}".

That imposes a fixed consideration order. When I add a 2, it can only attach to a state where coin 1 is already finished — there is no code path that produces "2 before 1". So each multiset is counted exactly once. The dedup isn't code I wrote; it's a consequence of the loop nesting.

Flip it, and dp[i] becomes the number of sequences — 1+2 and 2+1 both get counted.

Here's the plan.

// dp[i] = number of combinations making amount i
dp[0] = 1  // empty combination
for each coin:           // OUTER = coin -> combinations
  for i = coin to amount:  // ASCENDING -> unbounded
    dp[i] += dp[i − coin]
return dp[amount]

One: set dp[0] = 1, for the empty combination.
Two: for each coin, outer, sweep i from the coin's value up to amount, ascending.
Three: add dp[i − coin] into dp[i], and return dp[amount].

Starting i at coin also removes the need for an index guard — i − coin can never go negative. Does this approach sound good, or would you rather I think of another way?

I — implement

Alright, two loops and one line of work.

class Solution {
public:
    int change(int amount, vector<int>& coins) {
        vector<unsigned int> dp(amount + 1, 0);
        dp[0] = 1;                        // take no coin = one way to make 0

        for (int coin : coins) {              // outer = coin → combinations (order ignored)
            for(int i = coin; i <= amount; i++) {  // inner ascending → unbounded (reuse allowed)
                dp[i] += dp[i - coin];
            }
        }

        return (int)dp[amount];
    }
};

Coin outside, ascending inside, and the inner line just adds the ways to make the remainder. The line that's easy to get wrong is the loop order — swap the two loops and it still compiles, still runs, and silently counts permutations instead.

That's O(n · amount) time ≈ 300 × 5000 = 1.5M, and O(amount) space. amount = 0 needs no special case — the inner loop never runs and it returns dp[0] = 1.

I
INTERVIEWER

I told you the answer fits in a signed 32-bit int. So why unsigned?

C
CANDIDATE

That's a good push, and I want to be precise — you guaranteed the final answer fits. You didn't guarantee the intermediate cells do, and they're separate claims.

Concrete legal input: coins = [2,4,6,...,300] and amount = 4999. All coins even, amount odd, so the answer is dp[4999] = 0, and your guarantee holds perfectly. But dp[4998] is astronomically large; 2378 of the 5000 cells exceed INT_MAX.

With int, those += are signed overflow, which is undefined behaviour. With unsigned int, overflow is well-defined wraparound mod 232, and since the answer cell is 0 anyway, the result is still right. So here unsigned is load-bearing, not superstition. The habit I'd want is: bound the answer, then separately bound the intermediates.

Oh, one more thing — this is pseudo-polynomial: cost scales with the magnitude of amount, not its bit-length. If amount could be 109 but coins.length ≤ 3, I'd abandon the table and go number-theoretic — for a fixed handful of coins, the count has a closed form in the amount. Small n with a huge amount → math; large n with a modest amount → knapsack.

And if each coin had a usage cap, that's a bounded knapsack: I'd sum over how many of that coin I use, because treating copies as separate items would double-count the same multiset.
