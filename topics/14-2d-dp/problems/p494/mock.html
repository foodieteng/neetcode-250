Hmm, let me think about this for a sec.

The honest baseline first: brute force over all 2^n sign choices is 2^20 ≈ 10^6 here — that actually passes, but only because n ≤ 20; it doesn't see the structure.

The reframe: assigning signs is the same as splitting into two piles, the plus pile with sum P and the minus pile with sum N.

P − N = target  // the expression's value
P + N = total   // sum of all numbers — a constant
// ---------------------- add the two, N cancels
2P = target + total  =>  P = (target + total) / 2

And this is the part that matters — P is a constant I can compute, not a variable to search over. So the question becomes how many subsets sum to P. This problem reminds me of a 0/1 knapsack, in its counting form — subset sum, but counting ways instead of asking yes or no.

INTERVIEWER

Nice. Any inputs where that formula breaks?

C
CANDIDATE

Yes, two — and I'd guard both before allocating anything.

One: if total < |target| it's unreachable — the best I can do is all-plus or all-minus. Worse, P goes negative: nums=[1], target=-5 gives P = -2, and allocating a vector of size -1 blows up.

Two: if target + total is odd, P isn't an integer, so it's impossible. This one is nastier because it fails silently — integer division truncates and you get a plausible wrong answer. nums=[2,2], target=1: every ±2±2 is even, so the answer is 0, but without the guard you'd compute P=2 and return 2.

P — plan
C
CANDIDATE

Here's the plan.

// dp[s] = number of subsets summing to s
total = sum(nums)
if (total < |target| || (target + total) odd) return 0
P = (target + total) / 2

dp[0] = 1  // empty subset: one way to make 0
for each num:
  for s = P down to num:  // DOWN = each number used once
    dp[s] += dp[s − num]  // counting: += , not ||
return dp[P]

One: compute the total, and return 0 if either guard fires.
Two: set P = (target + total) / 2, and seed dp[0] = 1, for the empty subset.
Three: for each number, sweep s from P down to that number, adding dp[s − num] into dp[s], and return dp[P].

Two notes. The skeleton is identical to the yes-or-no subset-sum knapsack — the only change is that || becomes +=: "can I" uses OR, "how many" uses plus. And the descending inner loop is what keeps it 0/1 rather than unbounded. Does this approach sound good, or would you rather I think of another way?

C
CANDIDATE

Alright, let me code this up. Guards first, then P, then the 1-D table with a descending inner loop.

class Solution {
public:
    int findTargetSumWays(vector<int>& nums, int target) {
        int total = accumulate(nums.begin(), nums.end(), 0);
        int sum = target + total;

        // guard 1: target outside [−total, total] → impossible
        // guard 2: sum is odd → P is not an integer → impossible
        if (total < abs(target) || sum & 1) return 0;

        int plus = sum / 2;            // P = (target + total) / 2, a constant

        vector<unsigned int> dp(plus + 1, 0);
        dp[0] = 1;                  // empty set: one way to make sum 0

        for (int num : nums) {
            for (int i = plus; i >= num; i--) {   // high to low: each number used once
                if (dp[i - num] != 0) {            // pure speed-up, can drop
                    dp[i] += dp[i - num];        // counting: use +, not OR
                }
            }
        }

        return (int)dp[plus];
    }
};

The line that's easy to get wrong is the guard: the parity check has to sit next to the range check, before the division, because the division never complains — it just truncates.

That's O(n·P) time and O(P) space. The if (dp[i - num] != 0) is just a micro-optimization — correctness doesn't depend on it.

I
INTERVIEWER

You used unsigned int. Why? Is that necessary?

C
CANDIDATE

That's a fair challenge — it's not necessary here. Let me bound the answer: it counts sign assignments, and there are only 2^n of those, so with n ≤ 20 the answer is at most 2^20 = 1,048,576 — around 0.05% of INT_MAX. Every intermediate dp[i] is also a subset count, so it's bounded the same way. int is fine; the unsigned is harmless insurance, not load-bearing.

It would be load-bearing in a counting problem where intermediate counts genuinely exceed INT_MAX — there int is signed overflow, which is undefined behaviour, whereas unsigned wraps well-defined. The right habit is to bound the answer first, then pick the type — not reach for unsigned out of superstition.

Time is O(n·P) ≈ 20 × 1000 = 20k, and space is O(P). Versus 2^20 for brute force — 50× fewer operations, and more importantly it stops being exponential in n.

Oh, one more thing — this is pseudo-polynomial: the cost tracks the magnitude of P, not its bit-length. If values could be 10^9 with n still ≤ 20, the table becomes unbuildable and I'd switch to meet-in-the-middle: enumerate the signed sums of each half, hash one side, and look up the complement. That's O(2^(n/2)). Small n with big values → meet-in-the-middle; big n with small values → knapsack.
