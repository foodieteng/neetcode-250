Hmm, let me think about this for a second.

A naive approach would recurse over every path, picking right or down at each step. That's exponential, and it reaches the same cells over and over.

This problem reminds me of a 2-D grid DP, because each cell's count depends only on its neighbors. Let dp[i][j] = the number of paths to cell (i,j). Since I only move right or down, I reach it either from above (i-1,j) or from the left (i,j-1), so dp[i][j] is the cell above + the cell to the left. The first row and column are all 1 — only one straight path along an edge.

C
CANDIDATE

Here's the plan.

// dp[i][j] = paths to (i,j)
init whole grid to 1  // first row/col = 1
for i in 1..m-1, j in 1..n-1:
  dp[i][j] = dp[i-1][j] + dp[i][j-1]
return dp[m-1][n-1]

One: fill the whole grid with ones, which covers the first row and column.
Two: for every inner cell, add the cell above and the cell to the left.
Three: return the bottom-right cell.

One thing worth flagging — because each cell only needs the row above plus its left neighbor, I can drop to a single row: dp[j] += dp[j-1], scanning left to right, for O(n) space. Does this approach sound good, or would you rather I think of another way?

The 2-D grid first. The table starts as all ones, and the double loop from index 1 adds up + left.

class Solution {
public:
    int uniquePaths(int m, int n) {
        vector<vector<int>> dp(m, vector<int>(n, 1));  // first row/col default to 1

        for (int i = 1; i < m; i++) {
            for (int j = 1; j < n; j++) {
                dp[i][j] = dp[i - 1][j] + dp[i][j - 1]; // up + left
            }
        }

        return dp[m - 1][n - 1];
    }
};

And the O(n)-space rolling version keeps just one row.

class Solution {
public:
    int uniquePaths(int m, int n) {
        vector<int> dp(n, 0);
        dp[0] = 1;                       // start

        for (int i = 1; i <= m; i++) {       // roll row by row
            for (int j = 1; j < n; j++) {
                dp[j] += dp[j - 1];       // dp[j](up) += dp[j-1](left)
            }
        }

        return dp[n - 1];
    }
};

Both are O(mn) time. One thing worth flagging — the rolling scan must go left to right, so dp[j-1] is already this row's value, the left neighbor, while dp[j] is still last row's, the cell above.

Also, its outer loop runs m times, i <= m: the row starts as [1,0,0,…], so the first pass just builds row 0.

Time is O(mn), space O(mn), or O(n) with the rolling row.

Oh, one more thing — there's also a pure-math answer: a path is a choice of which m-1 of the m+n-2 steps go down, so it's C(m+n-2, m-1), in O(min(m,n)) time. But I'd keep the DP as the template — it extends directly to grids with obstacles or with cell costs, where the closed form breaks.
