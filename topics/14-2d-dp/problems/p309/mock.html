Hmm, let me think about this for a sec.

Greedy won't work — summing every positive price rise is the no-cooldown answer, and it overshoots, as I just showed. So it's DP, and the question is what the state is.

The day alone is not enough: two days with the same index and the same cash can have different futures, depending on whether I'm holding, and whether I just sold. This problem reminds me of a state machine DP — a few parallel states per day instead of one value. At the end of each day I'm in exactly one of three states:

hold — holding a share
sold — just sold today  // tomorrow is the cooldown
rest — no share, did NOT just sell  // free to buy tomorrow
I
INTERVIEWER

Why two different "no share" states? Isn't that redundant?

C
CANDIDATE

That's exactly where the cooldown lives, so it's worth being precise. The two states can hold the same amount of cash — but they have different legal moves tomorrow. From sold I cannot buy; from rest I can.

The general rule I go by: two situations can share a state only if their futures are identical. Same value doesn't matter; same options does. Merging them here would silently delete the cooldown rule.

And notice — nothing in my code will count cooldown days. The rule is encoded in the state graph itself, not in a counter.

P — plan
C
CANDIDATE

Here's the plan — three transitions, each looking only at yesterday.

hold[i] = max(hold[i−1], rest[i−1] − p[i])  // keep, or buy — ONLY from rest
sold[i] = hold[i−1] + p[i]  // sell today; must have held yesterday
rest[i] = max(rest[i−1], sold[i−1])  // stay idle, or finish cooling down

base:   hold[0] = −p[0], sold[0] = 0, rest[0] = 0
answer: max(sold[n−1], rest[n−1])  // NOT hold

One: hold is the max of keeping yesterday's hold, or buying today out of yesterday's rest.
Two: sold is yesterday's hold plus today's price.
Three: rest is the max of yesterday's rest and yesterday's sold.

On day 0, hold is −prices[0] and the other two are 0; the answer is the max of sold and rest on the last day.

One thing worth flagging: the entire cooldown is one word — hold reads rest[i−1], never sold[i−1]. Yesterday's sale money has to spend a day walking to rest before it can buy anything. And sold has no max, on purpose: sold means "I sold today", so there's exactly one way in. Does this approach sound good, or would you rather I think of another way?

I
INTERVIEWER

Why exclude hold from the answer?

C
CANDIDATE

hold means I'm still holding a share on the last day — that money is unrealized, and the value already has the purchase cost subtracted. Ending while holding is never better than having sold, since a price is never negative. Including it wouldn't give a wrong answer; it's just never the max.

I — implement
C
CANDIDATE

Three arrays first — they map 1:1 to the recurrence, and I can print the table to debug.

class Solution {
public:
    int maxProfit(vector<int>& prices) {
        int n = prices.size();

        vector<int> hold(n), sold(n), rest(n);
        hold[0] = -prices[0];          // buy on day 0: cash = −p[0]
        sold[0] = 0;
        rest[0] = 0;

        for (int i = 1; i < n; ++i) {
            hold[i] = max(hold[i - 1], rest[i - 1] - prices[i]);  // buy only from rest = cooldown
            sold[i] = hold[i - 1] + prices[i];                // sell: must have held yesterday
            rest[i] = max(rest[i - 1], sold[i - 1]);          // sold yesterday, cooled down today
        }

        return max(sold[n - 1], rest[n - 1]);   // skip hold: holding is never optimal
    }
};

The line that's easy to get wrong is the buy: hold reads yesterday's rest minus today's price, not yesterday's sold.

Then, since every state reads only i−1, the arrays are pure waste — three variables suffice, for O(1) space. I copy yesterday's three values into prev_ variables before updating.

class Solution {
public:
    int maxProfit(vector<int>& prices) {
        int hold = -1 * prices[0];
        int sold = 0;
        int reset = 0;
        for (int i = 1; i < prices.size(); i++) {
            int prev_hold = hold;          // freeze yesterday's three values first
            int prev_sold = sold;
            int prev_reset = reset;

            hold = max(prev_hold, reset - prices[i]);
            sold = prev_hold + prices[i];
            reset = max(prev_reset, prev_sold);
        }

        return max(sold, reset);
    }
};

O(n) time, O(1) space. n = 1 needs no special case: the loop never runs, and it returns max(0, 0) = 0.

INTERVIEWER

On the hold line of the second version you read reset, not prev_reset. Is that a bug?

C
CANDIDATE

Good question, and I want to be honest about it — it's correct today, because reset isn't reassigned until the third line, so it still holds yesterday's value. But it's correct by accident of ordering, not by construction, and that's a bad property.

Those three lines look order-independent, since they read snapshots. So a future reader moves the reset line to the top. Now hold reads the new reset, which means buying with money I sold yesterday. The cooldown silently disappears, and [1,2,3,0,2] returns 4 instead of 3 — the no-cooldown answer.

So I'd write prev_reset there too. If I take snapshots, I should use them everywhere; then the order really doesn't matter.

Let me think about complexity here.

Time is O(n) — three max operations per day. Space is O(1) for the variable version.

Oh, one more thing — the O(1) trick works only because the cooldown is exactly one day, so everything depends on yesterday. If the cooldown were k days, the buy would have to reach k days back, so I'd keep O(k) days of history.

And this whole family of stock problems is one state machine with different rules: with no cooldown, sold and rest merge; a transaction fee goes on the sell edge; a limit on transactions adds a count dimension. The question is always what the rule forces me to remember — the states fall out of that.
