Hmm, let me think about this for a second.

A naive framing is a table dp[i][j][whoseTurn], tracking two separate scores. But there's a cleaner trick.

This problem reminds me of interval DP: the state is a subarray piles[i..j], and every move shrinks it from one end. Then I track the score difference, not two scores. Define dp[i][j] as the net score — current player minus opponent — that the player to move can guarantee on that range. The game is symmetric, so this doesn't depend on who is moving. The player dimension disappears, and I'm back to a 2-D table.

dp[i][j] = max( piles[i] − dp[i+1][j],  // take the left pile
                piles[j] − dp[i][j−1] ) // take the right pile
base: dp[i][i] = piles[i]

dp[i][j] is the max of two options: take the left pile, piles[i] − dp[i+1][j]; or take the right pile, piles[j] − dp[i][j−1]. The base case is one pile: dp[i][i] is just that pile.

And the minus is the whole point — after I take a pile, my opponent becomes the player to move on what's left, so that smaller dp is their net advantage — and their gain is my loss. If I wrote +, I'd be modeling two players cooperating, which is the wrong game entirely. The answer is dp[0][n−1] > 0 — Alice nets positive.

class Solution {
public:
    bool stoneGame(vector<int>& piles) {
        int n = piles.size();
        // dp[i][j] = net score (self − opponent) the player to move gets on piles[i..j]
        vector<vector<int>> dp(n, vector<int>(n, 0));

        for (int i = 0; i < n; i++) {
            dp[i][i] = piles[i];              // one pile left → take it all
        }

        for (int L = 2; L <= n; L++) {            // interval length, small first
            for (int i = 0; i + L - 1 < n; i++) {
                int j = i + L - 1;
                dp[i][j] = max(piles[i] - dp[i + 1][j],    // take left
                                piles[j] - dp[i][j - 1]);   // take right
            }
        }
        return dp[0][n - 1] > 0;            // net > 0 ⇔ Alice wins
    }
};

I build an n × n table, set the diagonal, then loop the length L from 2 to n, and for each start i set j = i + L − 1 and take the max of left-minus and right-minus.

One thing worth flagging — the outer loop has to be the length. A plain double loop over i, j would read dp[i+1][j] before it's filled. The inner bound, i + L − 1 < n, keeps j inside the array.

That's O(n²) time and O(n²) space; I could roll it down to O(n) by keeping one diagonal, but at n = 500 it's already tiny.

C

Yes — actually those two constraints make the answer always true, and there's a short proof. Split the piles into even-indexed and odd-indexed groups. Since the count is even, the two ends always have opposite parity. Alice can commit to taking only even-indexed piles, or only odd ones — whatever Bob takes, the pile he exposes keeps her parity available. So she can guarantee the entire even group or the entire odd group, her choice. The two groups sum to an odd total, so they can't be equal — she picks the larger one and wins. So return true; is technically correct here.

But I'd still submit the DP. The moment the problem relaxes — any pile count and ties allowed, or a different scoring rule — the parity trick collapses and only the interval DP survives. I'd mention the shortcut as an observation, not lean on it.

The DP is O(n²) time and space; the shortcut is O(1).

Oh, one more thing — the score-difference framing is really a reusable template for two-player take-from-the-ends games. If ties are allowed, it's the same code with the answer relaxed to >= 0. If a move scores "the sum of what remains" instead of the pile taken, it keeps the exact skeleton, and you get that sum in O(1) from a prefix-sum array. The invariant across all of them is that single minus sign encoding "now it's the opponent's turn".
