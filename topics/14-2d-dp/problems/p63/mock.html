// dp[i][j] = paths to (i,j)
if start or end is obstacle: return 0
dp[start] = 1
for each cell:

One: if the start or end is an obstacle, return 0.
Two: seed the start with 1.
Three: for each cell, an obstacle stays 0, otherwise add the cell above and the cell to the left; return the bottom-right.

One thing worth flagging — the first row and column are not all 1 here: once an edge hits an obstacle, everything after it is 0, because the straight corridor is cut. The padded 2-D version: the extra border of zeros is a sentinel, and real cell (i-1, j-1) lives at dp[i][j].

class Solution {
public:
    int uniquePathsWithObstacles(vector<vector<int>>& obstacleGrid) {
        int m = obstacleGrid.size(), n = obstacleGrid[0].size();
        vector<vector<int>> dp(m + 1, vector<int>(n + 1, 0)); // extra ring of 0 sentinels

        if (obstacleGrid[0][0] || obstacleGrid[m - 1][n - 1]) return 0;

        dp[1][1] = 1;                        // seed: the real start (0,0)

        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                if (obstacleGrid[i - 1][j - 1] == 1) continue; // obstacle → stays 0

                dp[i][j] = dp[i][j] + dp[i - 1][j] + dp[i][j - 1]; // up + left
            }
        }

        return dp[m][n];
    }
};

And an O(n)-space rolling version that reuses one row.

class Solution {
public:
    int uniquePathsWithObstacles(vector<vector<int>>& g) {
        int m = g.size(), n = g[0].size();
        vector<long long> dp(n, 0);
        dp[0] = 1;

        for (int i = 0; i < m; i++) {
            for (int j = 0; j < n; j++) {
                if (g[i][j] == 1) dp[j] = 0;         // obstacle → 0
                else if (j > 0) dp[j] += dp[j - 1]; // up (old dp[j]) + left (dp[j-1])
                // j==0 and not an obstacle: dp[0] carries over (= value above)
            }
        }

        return (int)dp[n - 1];
    }
};

Both are O(mn) time. One thing worth flagging — in the padded version, the update adds onto dp[i][j] itself instead of overwriting it. That's what keeps the seed: at the start, up and left are both sentinel zeros, so a plain assignment would wipe the 1.

And in the rolling version, an obstacle must set dp[j] = 0 explicitly; it still carries last row's value, so skipping it would wrongly treat the cell as passable.

Oh, one more thing — the whole change from the plain grid-path count is one line: obstacle → 0. The padding trick removes the first row and column special cases, and the closed-form combinatorics dies here because obstacles break the assumption that "every down/right sequence is a valid path." Swap the + for a min and set obstacles to ∞, and it becomes a minimum-cost path with walls.
