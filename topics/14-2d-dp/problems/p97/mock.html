Hmm, let me think about this for a sec.

The greedy trap first. "If s1's next character matches, take it" fails whenever both strings offer the same character. Take s1="aa", s2="ab", s3="aaba". Greedy takes both a's from s1, then is stuck matching "ab" against "ba"; the right move was to take the second a from s2, and no local rule tells you that. So I need to keep both branches alive — that's DP.

The state: dp[i][j] = can s1's first i characters and s2's first j characters interleave into s3's first i+j? This problem reminds me of a two-string grid DP — one index per string, and each cell is built from its up and left neighbours.

I
INTERVIEWER

You said i+j. Don't you need a third dimension for the position in s3?

C
CANDIDATE

Good catch — that's the key observation. No, because nothing is ever skipped: if I've consumed i characters of s1 and j of s2, they've filled exactly the first i+j slots of s3. So the third index is a function of the other two, and it collapses away. The character I'm matching right now is always s3[i+j-1]. Two dimensions suffice.

Here's the plan.

// dp[i][j] : s1[0..i) + s2[0..j) -> s3[0..i+j)
if (m + n != s3.size()) return false
dp[0][0] = true
k = i + j − 1  // the char being placed

dp[i][j] = (dp[i−1][j] && s1[i−1] == s3[k])  // take from s1 — "up"
        || (dp[i][j−1] && s2[j−1] == s3[k])  // take from s2 — "left"

return dp[m][n]

One: if the lengths don't add up, return false; otherwise the empty corner is true.
Two: a cell is true if I can come from above by taking s1's character, or from the left by taking s2's character, and that character matches s3[i+j-1].
Three: return the bottom-right cell.

Two things worth spelling out. It's OR, not AND — the character comes from s1 or s2, and either working path is enough. And the && inside each branch matters: a character matching isn't enough, the previous cell must also be reachable, otherwise I'd accept a path that already died earlier. Does this approach sound good, or would you rather I think of another way?

2-D table first: fill the first column from s1 only, the first row from s2 only, then every inner cell from up or left.

class Solution {
public:
    bool isInterleave(string s1, string s2, string s3) {
        int m = s1.size(), n = s2.size();
        if (m + n != s3.size()) return false;

        vector<vector<bool>> dp(m + 1, vector<bool>(n + 1, false));
        dp[0][0] = true;

        for (int i = 1; i <= m; i++)            // s1 only
            dp[i][0] = (s1[i - 1] == s3[i - 1] && dp[i - 1][0]);

        for (int j = 1; j <= n; j++)            // s2 only
            dp[0][j] = (s2[j - 1] == s3[j - 1]) && dp[0][j - 1];

        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                dp[i][j] = (s1[i - 1] == s3[i + j - 1] && dp[i - 1][j])  // take s1 (up)
                    || (s2[j - 1] == s3[i + j - 1] && dp[i][j - 1]); // take s2 (left)
            }
        }

        return dp[m][n];
    }
};

Now the follow-up. Each cell reads only up and left — and this is the part that matters — there's no diagonal. So rolling one row works with no temp variable: before I overwrite dp[j] it still holds the previous row's value, which is "up", and dp[j-1] was already updated this row, which is "left".

class Solution {
public:
    bool isInterleave(string s1, string s2, string s3) {
        int m = s1.size(), n = s2.size();

        if (m + n != s3.size()) return false;   // lengths don't add up → no chance

        vector<bool> dp(n + 1, false);
        dp[0] = true;

        for (int i = 1; i <= n; i++)              // first row: s2 only
            dp[i] = (s2[i - 1] == s3[i - 1] && dp[i - 1]);

        for (int i = 1; i <= m; i++) {
            dp[0] = dp[0] && s1[i - 1] == s3[i - 1];  // first column: s1 only

            for (int j = 1; j <= n; j++) {
                dp[j] = (dp[j] && s1[i - 1] == s3[i + j - 1])   // old dp[j] = up → take s1
                    || (dp[j - 1] && s2[j - 1] == s3[i + j - 1]); // new dp[j-1] = left → take s2
            }
        }

        return dp[n];
    }
};

O(mn) time, O(n) space. One thing worth flagging — the line that resets dp[0] at the top of each row is easy to forget. Without it, dp[0] stays true forever, even after s1's prefix stops matching.

Let's dry-run the tricky one, where greedy breaks: s1="aa", s2="ab", s3="aaba" — expected true.

dp[1][2]2 → 'b'dp[0][2]=F ✗dp[1][1]=T, 'b' ✓T
dp[2][1]2 → 'b'dp[1][1]=T, 'a' ✗dp[2][0]=T, 'a' ✗F
dp[2][2]3 → 'a'dp[1][2]=T, 'a' ✓dp[2][1]=F ✗T → true

The cell that decides it is dp[1][2]: from above is dead, but from the left, dp[1][1] is true and s2's b matches the b in s3, so it's true. From there, taking s1's last a reaches the corner. dp[2][1] is a dead end, and it doesn't matter — one surviving path is enough. That matches.

Corner cases:

• "aabcc" / "dbbca": "aadbbcbcac" → true, "aadbbbaccc" → false.
• "" / "" / "" → true.

Time is O(mn) — every cell is O(1). Space O(n) for the rolled version, O(mn) for the table. With m, n ≤ 100 that's 10k cells, trivial.

Oh, one more thing — if I had to output an actual interleaving rather than a yes or no, I'd keep the full 2-D table and backtrack from (m,n), so the rolled version wouldn't do. If the question became "how many interleavings", I'd swap the OR for a + and seed dp[0][0]=1 — the counting analogue. And with three source strings, it's dp[i][j][k], with the target position still collapsing out as i+j+k.
