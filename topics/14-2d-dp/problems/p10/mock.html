This problem reminds me of two-string DP — the same grid shape as classic sequence alignment, with one string on each axis. Let dp[i][j] mean: does s[0..i) fully match p[0..j). The transition depends entirely on what kind of character p[j-1] is.

I
INTERVIEWER

Walk me through the cases.

C
CANDIDATE

Case A — p[j-1] is a letter or .: if it matches s[i-1], consume one char from each side and take the diagonal dp[i-1][j-1].

Case B — p[j-1] is *: it pairs with p[j-2] as a group "x*", and two independent ways can succeed, OR'd together:

zero times:   dp[i][j-2]       // drop the whole "x*"
one or more: (p[j-2]==s[i-1] || p[j-2]=='.') && dp[i-1][j]
             // consume one s char, keep "x*"

Here's the part that trips people up — the arrows go different directions. Zero jumps left by two (j-2), without touching s. One-or-more jumps up by one (i-1), keeping x* in place so it can eat again. That "keep j fixed, move i up" is exactly how * matches many.

I
INTERVIEWER

Why does "one or more" need the character check, but "zero" doesn't?

C
CANDIDATE

Because "one or more" is actually using x to match an s char — so x must be able to match it (equal, or x is .). Skip that guard and a* would gobble any character, effectively becoming .* — s="b", p="a*" should be false, but you'd wrongly get true. "Zero times" throws the pattern away without touching s at all, so there's no character to validate. Eat a char, check the char; drop the pattern, don't.

Here's the plan.

dp[0][0] = true                  // empty matches empty
for j = 2..n:  dp[0][j] = p[j-1]=='*' && dp[0][j-2]
for i = 1..m, j = 1..n:
  letter / '.'  → dp[i-1][j-1]
  '*'           → dp[i][j-2] || (char ok && dp[i-1][j])
return dp[m][n]

One: dp[0][0] is true — empty matches empty. Then seed the first row. An empty s can only be matched by patterns that are all "x*" groups taken zero times: dp[0][j] = (p[j-1]=='*' && dp[0][j-2]), starting at j=2. The main loop starts at i=1, so it can't produce this row itself.
Two: fill every i, j with case A or case B.
Three: return dp[m][n].

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    bool isMatch(string s, string p) {
        int m = s.size(), n = p.size();
        vector<vector<bool>> dp(m + 1, vector<bool>(n + 1, false));
        dp[0][0] = true;                     // empty matches empty

        // first row: empty s only matches "x*" groups (zero times)
        for (int j = 2; j <= n; j++)
            dp[0][j] = (p[j - 1] == '*' && dp[0][j - 2]);

        for (int i = 1; i <= m; i++) {
            for (int j = 1; j <= n; j++) {
                if (s[i-1] == p[j-1] || p[j-1] == '.') {
                    dp[i][j] = dp[i][j] || dp[i-1][j-1];   // letter/. → diagonal
                } else if (p[j-1] == '*') {
                    bool zero = (j-2 >= 0 && dp[i][j-2]);          // x* zero times
                    bool oneMore = (p[j-2] == s[i-1] || p[j-2] == '.')
                                   && dp[i-1][j];                         // x* eats one more
                    dp[i][j] = dp[i][j] || zero || oneMore;
                }
            }
        }
        return dp[m][n];
    }
};

An (m+1) × (n+1) table, dp[0][0] true, the first-row loop, then the double loop with the two cases.

One thing worth flagging — the one-or-more term reads dp[i-1][j]: the same column, one row up, not the diagonal. That's what lets x* stay in place and eat again.

That's O(mn) time and space, and m, n ≤ 20, so it's tiny. A plain recursion without memo is also correct, but blows up exponentially on the * branches — the DP is what tames it.

Time and space are both O(mn); space compresses to O(n), since each row only needs itself and the row above.

Oh, one more thing — the reason this is a Hard while a plain two-string DP is a Medium is the variable-length match. A letter consumes exactly one input char (one diagonal arrow), but * can consume zero (left-by-two) or many (up-by-one) — that variability is what forces multiple transition directions. The shell-wildcard version is actually a touch easier, because its * matches anything and needs no character guard. And I could write this top-down with memoization instead, which reads more directly off the "* means try-zero-or-try-one" definition — same O(mn), lower mental overhead.
