Hmm, let me think about this for a second.

A naive approach would enumerate every subsequence of s, which is 2m — hopeless at a thousand.

This problem reminds me of two-string prefix DP: a table where cell (i, j) compares the first i characters of s with the first j characters of t. Because I'm counting, the cells combine by addition, not max or OR.

So dp[i][j] is the number of subsequences of s[0..i) that equal t[0..j). The decision at each cell is what to do with s[i-1] — take it to match t[j-1], or skip it.

INTERVIEWER

Write the recurrence.

C
CANDIDATE
if s[i-1] == t[j-1]:
  dp[i][j] = dp[i-1][j]      // skip s[i-1]
          + dp[i-1][j-1]  // take it to match t[j-1]
else:
  dp[i][j] = dp[i-1][j]      // can only skip

If s[i-1] == t[j-1], the cell is the cell above — skip it — plus the cell diagonally up-left — take it. Otherwise, it's just the cell above, since I can only skip.

And here's the part worth stressing — even when the characters match, I still add the "skip" branch. Matching doesn't force me to use this character; I might instead match t[j-1] against an earlier equal character in s. Those are different index sets, so both count. That's exactly why the three b's in the example give 3 and not 1.

I
INTERVIEWER

I notice you never read the "left" cell, dp[i][j-1]. LCS uses it. Why not here?

C
CANDIDATE

Good eye — that's the structural heart of the difference. In LCS the two strings are symmetric: I'm free to skip a character from either one, so on a mismatch I compare "skip s" (up) against "skip t" (left). Here t is a fixed target — every character of t must be matched, so I can never skip a t character. The only skip available is "skip s", which is the up cell. There's no "skip t", hence no left. It also means this table is asymmetric — swapping s and t changes the answer, unlike LCS.

Base cases pin it down.

dp[i][0] = 1  for all i  // empty t: exactly one way (take nothing)
dp[0][j] = 0  for j >= 1 // empty s can't form a non-empty t
answer   = dp[m][n]

The first column is all ones: an empty t has exactly one way — take nothing. The first row is zero past the corner: an empty s can't form a non-empty t. The whole first column must be 1, not just dp[0][0] — those cells feed the "take" branch for every row.

So, the plan.
One: build an (m+1) × (n+1) table and set the first column to 1.
Two: fill it row by row — on a match, up + diagonal; otherwise, just up.
Three: return the bottom-right cell.

Does this approach sound good, or would you rather I think of another way?

class Solution {
public:
    int numDistinct(string s, string t) {
        int m = s.size(), n = t.size();
        // dp[i][j] = # subsequences of s[0..i) equal to t[0..j)
        vector<vector<unsigned long long>> dp(m + 1, vector<unsigned long long>(n + 1, 0));

        // base: an empty t always has exactly 1 way (take nothing)
        for (int i = 0; i <= m; ++i) {
            dp[i][0] = 1;
        }

        for (int i = 1; i <= m; ++i) {
            for (int j = 1; j <= n; ++j) {
                if (s[i - 1] == t[j - 1]) {
                    // take s[i-1] to match t[j-1] → dp[i-1][j-1]; skip it → dp[i-1][j]
                    dp[i][j] = dp[i - 1][j] + dp[i - 1][j - 1];
                } else {
                    // characters differ, can only skip s[i-1]
                    dp[i][j] = dp[i - 1][j];
                }
            }
        }
        return dp[m][n];
    }
};

The first loop sets the whole first column to 1. Then for each pair of prefixes, if the last characters match, the cell is the cell above plus the cell up-left — skip + take; otherwise it just copies the cell above. I return dp[m][n].

One thing worth flagging — the table is unsigned long long, even though the answer fits in an int. That's deliberate.

I
INTERVIEWER

You said the answer fits in a 32-bit int, yet you're using unsigned long long. Isn't that overkill?

C
CANDIDATE

It looks like overkill, but it isn't — and I want to be precise about why. You guaranteed the final answer fits. You did not guarantee the intermediate cells do.

Take s = 35 'a', t = 30 'a' — a legal input. With all identical characters, each cell is a binomial coefficient, dp[i][j] = C(i,j). The final cell, C(35,30) = 324,632, fits easily. But C(35,17) ≈ 4.5 billion, past INT_MAX, and eleven cells in that table overflow. Middle columns count shorter targets, and binomials peak in the middle.

With int, those additions are signed overflow, which is undefined behaviour. Unsigned arithmetic is defined: it wraps modulo 264, and since the true answer fits, the final value is still exact. So it's load-bearing, not superstition.
