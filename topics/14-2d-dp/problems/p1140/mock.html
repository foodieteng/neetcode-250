First, greedy fails precisely because of that side effect: taking X piles pushes the opponent's cap to max(M, X), letting them sweep more next turn. So I need DP.

This problem reminds me of minimax game DP over a suffix. The state is a starting index plus the current cap: dp[i][m] = the most the player to move can collect from piles[i..] when the cap is m. The game is symmetric, so it doesn't depend on who is moving — but I do need the extra dimension m, because "how many piles I can take" changes as the game evolves.

How do you express the transition? Taking X piles gives you those X piles, but then what?

Here's the neat part — I use a suffix sum, so I never track "what I took" separately. Let suffixSum[i] be the total of piles[i..]. After I take the first x piles, my opponent faces piles[i+x..] with cap max(m,x), and collects dp[i+x][max(m,x)]. Everything from index i onward that isn't theirs is mine, so:

mine = suffixSum[i] − dp[i+x][max(m, x)]

That single subtraction folds together "the x piles I grabbed" and "whatever I claw back afterward" — the x piles are already inside suffixSum[i]. It's the same minus-sign trick as other two-player take games, expressed through a suffix sum.

class Solution {
public:
    int stoneGameII(vector<int>& piles) {
        int n = piles.size();

        // dp[i][m] = most the player to move can take from piles[i..] with M = m
        vector<vector<int>> dp(n, vector<int>(n + 1, 0));

        // suffixSum[i] = sum of piles[i..]
        vector<int> suffixSum(n, 0);
        suffixSum[n - 1] = piles[n - 1];
        for (int i = n - 2; i >= 0; i--)
            suffixSum[i] = suffixSum[i + 1] + piles[i];

        for (int i = n - 1; i >= 0; i--) {       // i from the back (depends on larger i)
            for (int m = 1; m <= n; m++) {
                if (i + 2 * m >= n) {            // BASE: can reach the end → take all
                    dp[i][m] = suffixSum[i];
                } else {                          // GENERAL: try taking x piles
                    for (int x = 1; x <= 2 * m; x++) {
                        dp[i][m] = max(dp[i][m],
                            suffixSum[i] - dp[i + x][max(m, x)]);
                    }
                }
            }
        }
        return dp[0][1];                     // from the start, M = 1, Alice first
    }
};

A table of n rows by n + 1 columns, the suffix sums, then i from the back and m from 1 to n, with the base-or-general split inside.

One thing worth flagging — the table needs n + 1 columns, because the m loop runs all the way to n. And the base check, i + 2*m >= n, must come before the x loop, or i + x runs off the end.

That's O(n³) time — n² states times an O(n) inner loop — and O(n²) space. At n = 100, that's about a million operations.

Why max(m, x) and not just x?

C
CANDIDATE

Because the rule updates M to max(M, X) — it never decreases. If I took fewer piles than the current cap, x < m, the cap stays m, not x. Writing just x hands the opponent the wrong cap, and the answer is simply wrong.

It's not even wrong in a predictable direction, because dp isn't monotonic in m. For [3,2,2,1,1,3,1,5], the correct answer is 11, but the x-only version returns 10. The monotonic M is exactly why the state has to carry m at all.

The decision is one pile versus two. Taking one leaves the opponent dp[1][1], which is 16, so I get 10. Taking two pushes their cap to 2, they get 17, and I get only 9. So max(10, 9) = 10 — taking just 1 pile wins.

Also checked: [1,2,3,4,5,100] → 104, and a single pile → itself.

Time is O(n³), space O(n²) — fine for n ≤ 100.

Oh, one more thing — the inner x loop can be removed. For x ≤ m, the opponent's cap stays m; for larger x, it becomes x. Each half is a sliding-window minimum, which brings it to O(n²), though it's overkill here.

And the shape generalizes: it's the same minus-sign trick, just with the state carrying a monotonic parameter M instead of a right endpoint. If M were fixed instead of growing, the whole thing collapses to a 1-D game.
