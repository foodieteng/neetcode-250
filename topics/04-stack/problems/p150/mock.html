A naive approach would be to convert back to infix, or build an expression tree. But that reintroduces the very complexity postfix removes.

This problem reminds me of the classic stack evaluation of postfix expressions — postfix is built for a stack. Numbers get pushed; an operator pops its two operands, which are always the top two, computes, and pushes the result back.

Here's the plan.

// one int stack, single pass
for each token:
  number   → push(stoi(token))
  operator → y = pop(); x = pop(); push(x op y)
answer = the single remaining element

One: keep one int stack and make a single pass.
Two: a number gets pushed; an operator pops y, then pops x, and pushes x op y.
Three: the answer is the single remaining element.

One thing worth flagging — operand order. The stack is LIFO, so the right operand y is popped first and the left operand x second, and I compute x op y. For + and * the order doesn't matter, but for - and /, swapping them gives the wrong answer.

Does this approach sound good, or would you rather I think of another way?

Alright, let me code this up. One int stack, one loop over the tokens.

class Solution {
public:
    int evalRPN(vector<string>& tokens) {
        stack<int> st;
        string op = "+-*/";

        for (string token : tokens) {
            if (op.find(token) == string::npos) {  // not an operator → number
                st.push(stoi(token));
                continue;
            }

            int y = st.top(); st.pop();          // popped first = right operand
            int x = st.top(); st.pop();          // popped second = left operand
            if (token == "+") {
                st.push(x + y);
            } else if (token == "-") {
                st.push(x - y);              // x - y, don't swap
            } else if (token == "*") {
                st.push(x * y);
            } else {
                st.push(x / y);              // x / y, truncates toward zero
            }
        }
        return st.top();
    }
};

A number gets parsed with stoi and pushed. For an operator, I pop y first, then x, and push x op y through an if-else chain. At the end I return the top.

One thing worth flagging — the test op.find(token) == string::npos checks whether the whole token is a substring of "+-*/". Operators are single characters and match. Any number string, including "-11", does not, so negatives are correctly treated as numbers.

Let's dry-run ["2","1","+","3","*"]. I expect 9.

tokenactionstack
"2"push 2[2]
"1"push 1[2, 1]
"+"y=1, x=2 → push 3[3]
"3"push 3[3, 3]
"*"y=3, x=3 → push 9[9]

The row that matters is the "+": y=1, x=2, and I push 3. Each operator collapses the top two numbers into one sub-result, which feeds the next operator, and "*" turns 3 and 3 into 9. Order wouldn't matter for +, but for - it would.

Let's also test corner cases.

• A single number ["42"] returns just 42.
• ["3","-4","+"]: -4 is pushed as a number, giving -1.
• And 6 / -132 truncates toward zero to 0, matching C++ integer division.
