This problem reminds me of an invariant-maintenance pattern: keep the container in the order the reads want, and pay to restore it on every write.

Here the invariant is that front → back runs newest → oldest. Each push restores it by rotating the previous size elements behind the new one. pop and top read the front, and empty just asks the queue.

Here's the plan.

// invariant: front → back = newest → oldest
push(x):
  sz = q.size()  // BEFORE pushing x
  q.push(x)
  repeat sz times: q.push(q.front()); q.pop();
pop / top → q.front()   empty → q.empty()

One: in push, record the size before pushing x.
Two: push x to the back.
Three: rotate that many times — push the front to the back, then pop the front.

One thing worth flagging — the size must be recorded before the push. Rotating sz + 1 times would carry x to the back too, and the order would be wrong.

CANDIDATE

Alright, let me code this up. It's one queue.

class MyStack {
    queue<int> q;
public:
    MyStack() {}

    void push(int x) {
        int sz = q.size();                    // number of old elements
        q.push(x);                            // x goes to the back first
        for (int i = 0; i < sz; i++) {        // rotate sz times
            q.push(q.front()); q.pop();       // move the front to the back
        }                                     // → x is now at the front (= top)
    }

    int pop() {
        int v = q.front(); q.pop();           // take front = top, O(1)
        return v;
    }

    int top() { return q.front(); }           // front = top, O(1)
    bool empty() { return q.empty(); }
};

push saves the old size, adds x, and rotates the old elements behind it, so x is now the front. pop reads the front and removes it; top just returns the front; empty asks the queue.

The line to get right is int sz = q.size(); at the top of push — it has to come before q.push(x). A two-queue version does the same thing with a scratch queue: push x into it, pour the old queue in behind it, then swap the two.

Yes, the pop-heavy version. push goes straight to the back in O(1). On pop, I rotate the front size - 1 elements to the back so the newest lands at the front, then remove it, which is O(n). top either does the same rotation and sends the element to the back again, or reads a cached last-pushed value.

I'd pick based on which operation dominates: many pushes → pop-heavy; many reads → push-heavy.

push is O(n), since it rotates size elements. pop, top, and empty are O(1). Space is O(n) for one queue.

The mirror problem, a queue built from two stacks, does better: with a lazy transfer each element moves at most once, so every operation is amortized O(1), even though a single pop can still be O(n).
