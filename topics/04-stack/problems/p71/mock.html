Editing the string directly — deleting the segment before each .. — is fiddly with all the slash edge cases.

This problem reminds me of a stack used as an undo history: each name steps one level down, and a .. undoes the most recent step, which is exactly last in, first out. So splitting into segments and pushing names onto a stack is cleaner: .. pops, empty and . are skipped, everything else pushes.

// split on '/', four cases per segment
getline(ss, seg, '/'):
  seg == ".." → pop if stack not empty
  seg == "." or empty → skip
  else → push seg
join stack with '/', or "/" if empty

One: split the path on the /.
Two: for each segment, .. pops if the stack isn't empty, . or empty is skipped, anything else is pushed.
Three: join the stack with slashes, or return a single / if it's empty.

One thing worth flagging — I'll split with getline(ss, seg, '/') on a string stream, with the slash as the delimiter. The leading slash and consecutive slashes naturally produce empty segments, so collapsing multiple slashes falls out for free by skipping empties. And I match .. as a whole string, so ... stays a name.

Alright, let me code this up. I read segments with getline on a string stream, run the four cases against a stack<string>, and return a single / when the stack ends up empty.

class Solution {
public:
    string simplifyPath(string path) {
        stringstream ss(path);              // treat the string as an input stream
        string component;
        stack<string> st;

        while (getline(ss, component, '/')) {  // split on '/'
            if (component == "..") {
                if (!st.empty()) st.pop();      // go up (ignore if empty)
            } else if (component == "." || component.empty()) {
                continue;                       // '.' or empty segment → skip
            } else {
                st.push(component);              // a real name (incl. "...")
            }
        }

        if (st.empty()) return "/";          // root

        string ans = "";
        while (!st.empty()) {
            ans = '/' + st.top() + ans;       // prepend, top to bottom
            st.pop();
        }
        return ans;
    }
};

One thing worth flagging — getline's third argument is the delimiter; without it, it defaults to newline and the whole path comes back as one chunk. And since a stack only exposes the top, I pop from the top and prepend each directory, so the answer still reads left to right.

The rows that matter are the two ..s: they pop b, then a, back to root, and then c is pushed. The leading empty segment and the . are skipped, and the trailing slash yields no segment at all, because getline stops at the end of the stream. Answer: /c. That matches.

Corner cases:

• /../ → /, since .. on an empty stack is ignored.
• /... → /..., because ... is a name.
• /home//foo/ → /home/foo, since the double slash just makes an empty segment.

The time complexity is O(n) for the split — one pass, with constant-time checks per segment. The space complexity is O(n) for the stack of segments.

To be precise, prepending copies the partial answer every time, so the join can be O(n2) in the worst case.

Oh, one more thing — using a vector<string> instead of a stack makes the join a simple front-to-back concatenation, no prepending, and the whole thing truly O(n).
